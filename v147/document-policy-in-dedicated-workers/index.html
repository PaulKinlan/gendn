Document Policy in Dedicated Workers

Limited availability

  • Chrome · dev trial (147)
  • Edge · not separately reported
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register — no web-features entry at webstatus.dev for Document Policy or this worker extension. Chrome 147 lists it as a developer trial (behind a flag); the feature detail (chromestatus API, updated 2026-03-06) records no ship milestone and standards status “Proposed”. No Firefox or Safari positions are recorded.

Chrome 147 adds developer-trial support for Document Policy in dedicated workers. A worker loaded over the network takes its policy from the Document-Policy header on the worker script’s own HTTP response; workers created from local schemes (blob:, data:) clone the policy of their creator. That lets policy-gated features — the motivating case is the JS Self-Profiling API’s js-profiling gate — work inside workers instead of being limited to the main document.

Developer trial — API surface may move

This is behind a flag in Chrome 147 (milestone listing); the feature detail records no ship estimate (status “Proposed”, updated 2026-03-06). To try it:

  • Launch Chrome with --enable-blink-features=DocumentPolicyInDedicatedWorker (runtime-enabled feature DocumentPolicyInDedicatedWorker, status “experimental”), or enable chrome://flags/#enable-experimental-web-platform-features.
  • Serve the worker script with the Document-Policy header you want the worker to run under — the creating page’s policy is not applied to network-loaded workers.
Source: chromestatus.com/feature/6242687411945472; Chromium runtime_enabled_features.json5

There is no new error surface: an absent or unparseable Document-Policy header on the worker script response does not throw at worker creation — each policy-gated feature simply falls back to its spec-defined default (for js-profiling: off), exactly as in document contexts.

why it exists

Dedicated workers are the standard way to move heavy work off the main thread, but Document Policy previously applied only to documents. Features gated behind a policy — most concretely the JS Self-Profiling API, which requires a Document-Policy: js-profiling opt-in — were simply unavailable in workers, even when the site had opted in at the document level. That left developers with no way to attribute CPU cost to JS stacks inside a worker’s event loop. Extending Document Policy to workers closes the gap without new API surface.

The response-driven model (rather than inheriting the creator’s policy) is deliberate: a worker script is a standalone HTTP resource that can carry its own headers, and inheriting would let one origin’s policy constrain another origin’s script — the same worker would behave differently depending on which document started it. Inheritance is limited to blob:/data: workers, which have no response of their own.

Source: ChromeStatus motivation; explainer — “Rationale: Why Response Headers for Network Workers?”

Syntax

No new JavaScript API is introduced — the surface is the existing Document-Policy HTTP response header, now honored on dedicated-worker script responses:

// HTTP response for the worker script (not the page)
HTTP/1.1 200 OK
Content-Type: text/javascript
Document-Policy: js-profiling

With the policy active in the worker, policy-gated APIs become available there. The explainer’s example uses the JS Self-Profiling API:

// Inside the worker, once Document-Policy: js-profiling applies
const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10_000 });
doWork();
const trace = await profiler.stop();
console.log(JSON.stringify(trace));
Source: explainer — “Network Worker with Document-Policy Header” and “Using Profiler in Worker” (header and profiler snippet as given there)
