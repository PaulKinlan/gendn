Document Policy in Dedicated Workers

Limited availability — developer trial

  • Chrome · developer trial in 147 (behind a flag)
  • Edge · proposal authored by Edge engineers; no separate ship record
  • Firefox · no signal
  • Safari · no signal

There is no webstatus.dev web-feature entry for this behavior, MDN has no page for the Document-Policy header (HEAD-checked 404, 2026-09-27), and BCD has no http/headers/Document-Policy.json file — the compat picture below is entirely interim data from the ChromeStatus record.

Chrome 147 lets Document Policy take effect inside dedicated workers, as a developer trial. A network-loaded worker’s policy comes from the worker script’s own Document-Policy response header — the creating page’s policy is deliberately not propagated — while blob:/data: workers, which have no HTTP response, clone the creator’s policy. The motivating use case is enabling the policy-gated JS Self-Profiling API in workers.

Developer trial This behavior is behind a flag in Chrome 147: the Blink runtime feature is DocumentPolicyInDedicatedWorker (status experimental in runtime_enabled_features.json5, verified 2026-09-27). Enable it with --enable-blink-features=DocumentPolicyInDedicatedWorker, or turn on everything experimental via chrome://flags/#enable-experimental-web-platform-features. The API surface may change before it ships — do not use in production.

syntax

The header itself is unchanged from the Document Policy draft — what’s new is which response it is read from. The ABNF, quoted from §7.2.1:

# A Structured Header whose value must be a dictionary (RFC 8941)
Document-Policy = sf-dictionary

# Served on the WORKER SCRIPT's response to enable a policy in that worker:
HTTP/1.1 200 OK
Content-Type: text/javascript
Document-Policy: js-profiling

Policy source per worker type, from the explainer’s proposed model (dedicated workers are what Chrome 147’s trial covers; the explainer also defines shared and service workers for completeness):

Worker scriptEffective Document Policy
Network-loaded (https: …)Parsed from the worker script’s own response header. Any creator policy is ignored — “no merge/intersection”. Without the header, each feature falls back to its spec-defined default (for js-profiling, off).
blob: / data:Clones the creator’s Document Policy, “since no HTTP response exists to consult” (blob: clones from the environment that created the blob; data: from the document that created the worker).
Source: Document Policy draft §7.2.1 (ABNF verbatim); Document Policy in Workers explainer (per-type semantics, quoted)

why response headers, not inheritance

The explainer rejects blanket inheritance from the creating document: a page’s policy applied to a cross-origin worker script would create “owner-dependent behavior where the same worker script behaves differently depending on which document started it”, and would override what the script’s own origin intended. Response-driven policy keeps each origin in control of its own feature gating, matches HTML’s policy-container model (which already scopes inheritance to local schemes), and avoids enabling feature hooks — and their runtime overhead — in every worker of an opted-in page.

Practical consequence: opting your page into a policy does not opt in its workers. To use a policy-gated feature in a dedicated worker, serve the worker script itself with the Document-Policy header (or create the worker from a blob:/data: URL so it clones the page’s policy).

Source: explainer — “Rationale: Why Response Headers for Network Workers?” and “Considered Alternatives”

examples

Enabling the JS Self-Profiling API inside a dedicated worker — the explainer’s motivating case:

// main.js — the page's own Document-Policy header is irrelevant here
// (module worker: the crunch.js below uses top-level await)
const worker = new Worker("/scripts/crunch.js", { type: "module" });

// Server config: serve /scripts/crunch.js with
//   Document-Policy: js-profiling

// crunch.js (inside the worker) — from the explainer:
const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10_000 });
doWork();
const trace = await profiler.stop();
console.log(JSON.stringify(trace));

// Alternative without touching server config: a blob: worker has no
// HTTP response, so it CLONES the creating page's Document Policy —
// serve the PAGE with `Document-Policy: js-profiling` instead.
const src = await (await fetch("/scripts/crunch.js")).text();
const blobWorker = new Worker(
  URL.createObjectURL(new Blob([src], { type: "text/javascript" })),
  { type: "module" },
);
Source: profiler snippet quoted from the explainer; framing gendn-derived (labelled accordingly)
