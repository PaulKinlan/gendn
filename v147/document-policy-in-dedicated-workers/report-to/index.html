The report-to parameter

The violation-reporting parameter any Document-Policy directive may carry. It names a reporting endpoint — registered with the Reporting API’s Reporting-Endpoints header — to which "document-policy-violation" reports for that feature are delivered, with a *-token default, a none off switch, and a report-only delivery mode via Document-Policy-Report-Only.

Developer trial — worker-scope reporting unspecified

Same availability as the parent feature: behind the DocumentPolicyInDedicatedWorker flag in Chrome 147 per the milestone-147 listing (chromestatus.com/feature/6242687411945472). The reporting model below is the draft’s document-policy model; how violation reports are delivered from a worker-scope policy is not yet specified anywhere — see Lifecycle.

Syntax

A Structured Field parameter on a document policy directive (or on the wildcard * token). The shapes below are quoted from the draft’s own reporting examples — something/something-else are the draft’s placeholder directive names:

// Per-feature endpoint(s)
Document-Policy: something=1.0;report-to=endpoint1, something-else=?0;report-to=endpoint2

// Default endpoint for all features, via the * token
Document-Policy: something=1.0, something-else=?0, *;report-to=endpoint

// Disable reporting for one feature while a default is set
Document-Policy: something=1.0;report-to=none, something-else=?0, *;report-to=endpoint

// Report-only delivery (no enforcement)
Document-Policy-Report-Only: something=1.0;report-to=endpoint
Source: Document Policy draft §6.1.1 — the report-to parameter; §6.1.2 — default endpoint (*); §6.1.3 — report-to=none; §6.2 — report-only mode (examples quoted from the draft)

Inputs

The parameter value is an endpoint name (a string), or the keyword none. For delivery to work the name must be registered on the same response with the Reporting API’s Reporting-Endpoints response header — a Structured Field dictionary whose entry values are collector URL strings. The Document Policy draft names the endpoint; registration itself is entirely the Reporting API’s contract.

// Register the name, then reference it:
HTTP/1.1 200 OK
Reporting-Endpoints: endpoint1="https://reports.example.com/collect"
Document-Policy: something=1.0;report-to=endpoint1
Source: Reporting API — the Reporting-Endpoints header; Document Policy draft §6.1.1

Outputs

When a supported, enforced directive is violated, the browser generates a report of type "document-policy-violation" (per the draft’s violation-report algorithm) and the Reporting API POSTs a JSON array to the registered collector URL with Content-Type: application/reports+json. Each report carries type, url (the reporting document, stripped of credentials/fragments), age, user_agent, and a type-specific body:

POST /collect HTTP/1.1
Content-Type: application/reports+json

[{
  "type": "document-policy-violation",
  "url": "https://site.example/page",
  "age": 27,
  "user_agent": "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36",
  "body": {
    "featureId": "something",
    "sourceFile": null,
    "lineNumber": null,
    "columnNumber": null,
    "disposition": "enforce"
  }
}]

The body members are defined algorithmically by the draft’s violation-report steps (there is no formal IDL interface for the body in the current draft — the member list below is the §9.10 algorithm’s own construction):

document-policy-violation body — members per §9.10
MemberTypeContent
featureIdstringThe violated configuration point’s string representation (the directive name)
sourceFilestring or nullURL of the source file where the violation occurred; null if unavailable
lineNumbernumber or nullLine in the source file; null if unavailable

Source: Document Policy draft §9.10 violation-report algorithm (report type and body construction: featureId, sourceFile, lineNumber, columnNumber, disposition); Reporting API — report delivery (POST format, media type, report fields)

Errors

The parameter defines no throwing or rejecting surface. The failure modes are silent by design:

Failure modes — nothing throws
ConditionBehavior
Endpoint name not registered via Reporting-EndpointsReports queue against a name with no destination and are never delivered — the Reporting API delivers only to registered endpoints; no console error is mandated by either spec.
report-to=noneThe defined off switch: reporting for that feature is disabled (§6.1.3).
Directive without report-to in Document-Policy-Report-OnlyHas no effect at all in that header (§6.2).
Delivery failure (collector unreachable)The Reporting API’s delivery attempts back off and eventually drop the reports; the page is not notified.
Source: Document Policy draft §6.1; Reporting API — delivery

Lifecycle

  • Configuration: the policy (and any report-to parameters) is parsed from the response headers when the document loads; endpoint names resolve against the same response’s Reporting-Endpoints dictionary.
  • Endpoint precedence: a feature’s own report-to overrides the * default — reports go to one endpoint, never both (§6.1.2); none disables that feature’s reporting outright.
  • Violation → report: an enforced violation runs the draft’s §9.10 algorithm, generating a "document-policy-violation" report; under Document-Policy-Report-Only the report is generated with no enforcement (§6.2).
  • Queued delivery: reports are queued and delivered out-of-band by the Reporting API’s delivery machinery (batched POSTs, retries with backoff) — not synchronously at violation time.
  • Scope boundary: reporting is only possible from the page which configures the policy; a nested page violating a required policy does not report to the embedder (§6.1).
  • Worker scope — unspecified: stated honestly, neither the draft (whose §6 covers document policies) nor the workers explainer specifies which reporting configuration a dedicated worker consults or how worker-scope violations are delivered. Treat worker-scope reporting as unspecified rather than assuming the document model transfers.
Source: Document Policy draft §6.1; §9.10; Reporting API — delivery

Security and privacy

Violation reports disclose page activity to the named collector: the report’s url identifies the reporting document (stripped per the Reporting API’s serialization rules) and its body identifies the violated feature. The draft’s scope rule bounds the disclosure: only the page which configures the policy can receive its reports — a cross-origin embedder cannot use a required policy to harvest violation reports from a nested page (§6.1). Delivery security (endpoint URL requirements, batching, credentials) is governed by the Reporting API.

Source: Document Policy draft §6.1 (scope rule); Reporting API — delivery
