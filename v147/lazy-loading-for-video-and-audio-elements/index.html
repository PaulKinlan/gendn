Lazy loading for video and audio elements

Limited availability

  • Chrome · 150 (partial 148–149)
  • Edge · 150
  • Firefox · not supported (in development)
  • Safari · not supported

Not Baseline. The web-features register tracks this as loading-lazy-media with Baseline status “limited”: Chrome and Chrome for Android 150 (2026-06-30), Edge 150 (2026-07-02), no Firefox or Safari support yet. This page documents the Chrome 147 developer-trial stage of the feature.

Adds the loading attribute to <video> and <audio> elements, letting browsers defer media resource loading until the element is near the viewport — the same mechanism already available for <img> and <iframe>.

Documented at the developer-trial stage In Chrome 147 this feature was in developer trial behind a flag: the runtime-enabled feature is LazyLoadVideoAndAudio (enable with --enable-blink-features=LazyLoadVideoAndAudio or chrome://flags/#enable-experimental-web-platform-features). It has since shipped: partial support in Chrome 148–149 (the attribute is not honoured for <source> selection — crbug.com/514611050) and full support from Chrome 150; the runtime feature is now status: stable on trunk. The spec change has merged into the HTML Standard. Source: Chromium runtime_enabled_features.json5 (LazyLoadVideoAndAudio); mdn/browser-compat-data html/elements/video.json

why it exists

Since Chrome 76, <img loading="lazy"> and <iframe loading="lazy"> have let browsers skip fetching off-screen resources until the user scrolls close to them. The same pattern has never applied to <video> and <audio>, which start loading their source files as soon as the parser encounters them regardless of position on the page. Long-form pages with multiple embedded videos pay a large up-front network cost even when most users never scroll to those media elements. The loading attribute on media elements closes this gap and aligns behaviour across all embeddable resources.

Source: chromestatus feature summary; WHATWG HTML PR #11980

Syntax

The loading attribute is a lazy loading attribute — an enumerated attribute with two keywords — applied to the <video> and <audio> media elements:

<video loading="eager" | "lazy"> … </video>
<audio loading="eager" | "lazy"> … </audio>
Keywords and states
KeywordStateMeaning
eagerEagerFetch the media resource immediately, regardless of position on the page (the pre-existing behaviour).
lazyLazyDefer fetching the media resource until conditions defined by the user agent are met — in practice, until the element is within the browser's lazy-loading distance threshold of the viewport.

Missing and invalid values. As a lazy loading attribute, the missing value default and invalid value default are both the Eager state: omitting the attribute or writing an unrecognised value (for example loading="defer") behaves exactly like loading="eager".

Source: HTML Standard §2.5.7 Lazy loading attributes; HTML Standard — media elements: loading

IDL reflection: HTMLMediaElement.loading

The content attribute is reflected as an IDL attribute on HTMLMediaElement (so it is inherited by both HTMLVideoElement and HTMLAudioElement), verbatim from the HTML Standard's HTMLMediaElement interface:

[CEReactions] attribute DOMString loading;

Per the spec, “the loading IDL attribute must reflect the loading content attribute, limited to only known values”: reading el.loading returns "eager" or "lazy" only — an unrecognised or missing content attribute reads back as "eager". Assigning to el.loading sets the content attribute; switching a deferred element from lazy to eager runs the stored lazy-load resumption steps immediately (see lifecycle below).

Source: HTML Standard — media elements: loading (IDL and reflection)

Behavior and lifecycle

Where it applies. The attribute applies to all media elements — <video> and <audio> — in any browsing context. It is plain declarative HTML: no JavaScript, no secure-context requirement, no permission, and no origin-trial token is needed (in Chrome 147 the runtime flag above must be enabled). In Chrome 148–149 the attribute was not honoured when the resource is chosen via <source> children (crbug.com/514611050); from Chrome 150 both the src attribute and <source> selection paths defer.

Lifecycle with loading="lazy"
Network requestDeferred until the element enters the browser-defined lazy-load distance threshold from the viewport; the deferred fetch is stored as the element's lazy load resumption steps.
Switching to eagerChanging the attribute's state to Eager (markup or el.loading = "eager") runs the stored resumption steps at once — the fetch starts immediately. A lazily loaded <video> with a deferred poster also runs its poster resumption steps.
preload interactionA preload="none" hint continues to suppress loading. loading="lazy" takes effect only when the browser would otherwise begin fetching; combine loading="lazy" preload="metadata" to defer, then fetch only metadata.
AutoplayAn element with autoplay and loading="lazy" begins playing once loaded, which happens when it enters the threshold zone.
JavaScript .play()Calling .play() before the resource is loaded triggers an immediate load, overriding the lazy deferral.
Source: HTML Standard — media elements: loading (state-change steps); chromestatus feature summary; BCD html/elements/video.json (partial-support note)

Examples

Basic lazy video

<video loading="lazy" controls>
  <source src="feature-demo.mp4" type="video/mp4">
  <source src="feature-demo.webm" type="video/webm">
</video>

Lazy audio

<audio loading="lazy" controls>
  <source src="podcast-episode.mp3" type="audio/mpeg">
  <source src="podcast-episode.ogg" type="audio/ogg">
</audio>

Combining with preload

<!-- Best practice for a long page with many videos:
     lazy defers fetching; preload="metadata" limits initial load to just
     duration/dimensions once the element enters the threshold zone. -->
<video loading="lazy" preload="metadata" controls>
  <source src="explainer.mp4" type="video/mp4">
</video>

Detecting support

// The IDL attribute lives on HTMLMediaElement.prototype and is
// inherited by both HTMLVideoElement and HTMLAudioElement.
const supportsLazyMedia = 'loading' in HTMLMediaElement.prototype;
if (!supportsLazyMedia) {
  // Fall back to IntersectionObserver-based lazy loading
}

Security and privacy

The attribute adds no new capability, permission, or secure-context requirement — it only changes when an already-permitted media fetch happens. The observable consequence of the specified deferral behaviour is timing: with loading="lazy", the media server receives the request only when the element nears the viewport, so request timing can reveal scroll proximity to the embedding page's media origin (the same property that <img loading="lazy"> has had since Chrome 76). No log, identifier, or DOM state beyond the ordinary media request is exposed.

Source: deferral behaviour per HTML Standard — media elements: loading; no additional security section is defined for lazy loading attributes in HTML Standard §2.5.7
