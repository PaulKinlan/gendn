Lazy loading for video and audio elements

Limited availability

  • Chrome · 150 (148–149 partial: not for <source>)
  • Edge · mirrors Chrome
  • Firefox · not shipped (positive position)
  • Safari · not shipped (positive position)

Baseline status from the loading-lazy-media web-feature: limited availability (queried 2026-09-20). Per-version rows from BCD html/elements/video.json and audio.json (verified 2026-09-20) — see the full table.

Adds the loading attribute to <video> and <audio> elements, letting browsers defer media resource loading until the element is near the viewport — the same mechanism already available for <img> and <iframe>.

Milestone snapshot — the feature has since shipped

This page records the Chrome 147 milestone, where the feature was in developer trial behind chrome://flags/#enable-experimental-web-platform-features. Both blockers noted at the time have since resolved: the spec change, WHATWG HTML PR #11980, merged on 2026-03-23 into the HTML living standard, and the attribute shipped on by default: partially in Chrome 148 (not honored for <source> children, crbug.com/514611050) and fully in Chrome 150, per BCD; the LazyLoadVideoAndAudio entry in runtime_enabled_features.json5 is status: "stable" (verified 2026-09-20). Firefox and Safari have not shipped it, so cross-browser code still needs the feature-detect fallback.

syntax

Content-attribute grammar — a standard lazy loading attribute, defined once in the HTML living standard and now used by <img>, <iframe>, <video>, and <audio> (quoted verbatim, fetched 2026-09-20): “A lazy loading attribute is an enumerated attribute with the following keywords and states: lazy — Lazy — used to defer fetching a resource until some conditions are met; eager — Eager — used to fetch a resource immediately; the default state.” A missing or unrecognized value therefore behaves as eager.

<video loading="lazy"> … </video>
<audio loading="eager"> … </audio>   <!-- eager is the default state -->

DOM reflection (HTML living standard — media elements): HTMLMediaElement gains attribute DOMString loading, and “the loading IDL attribute must reflect the loading content attribute, limited to only known values” — so reading video.loading yields "eager" or "lazy", and assigning it sets the content attribute:

const video = document.querySelector("video");
video.loading = "lazy";          // same as setting the attribute in markup
console.log(video.loading);      // "lazy"
Source: HTML § lazy loading attributes; HTML § media elements; PR #11980

why it exists

Since Chrome 76, <img loading="lazy"> and <iframe loading="lazy"> have let browsers skip fetching off-screen resources until the user scrolls close to them. The same pattern has never applied to <video> and <audio>, which start loading their source files as soon as the parser encounters them regardless of position on the page. Long-form pages with multiple embedded videos pay a large up-front network cost even when most users never scroll to those media elements. The loading attribute on media elements closes this gap and aligns behaviour across all embeddable resources.

Source: chromestatus summary and WHATWG HTML PR #11980 (May 2026; PR since merged)

the attribute

Attributeloading
Elements<video>, <audio>
loading="eager"Default. Load the resource immediately, same as current behavior without the attribute.
loading="lazy"Defer resource loading until the element is within the browser's lazy-loading distance threshold from the viewport. The exact threshold is browser-defined and may vary by network conditions.
<source> caveatIn Chrome 148–149 the attribute was not honored when the media resource came from <source> children (only from a src attribute) — fixed in Chrome 150 (crbug.com/514611050, recorded in BCD)

When loading="lazy" is set:

Network requestDeferred until the element enters the lazy-load intersection zone.
preload interactionA preload="none" hint continues to suppress loading. loading="lazy" takes effect only when the browser would otherwise begin fetching.
AutoplayAn element with autoplay and loading="lazy" will begin playing once loaded, which happens when it enters the threshold zone.
JavaScript .play()Calling .play() before the resource is loaded triggers an immediate load, overriding the lazy deferral.
<video poster>The poster-image fetch also consults the “will lazy load element steps”, so a lazy video defers its poster too (HTML living standard — media elements)
Source: WHATWG HTML PR #11980 (merged into the living standard) and the chromestatus summary

example

Basic lazy video

<video loading="lazy" controls>
  <source src="feature-demo.mp4" type="video/mp4">
  <source src="feature-demo.webm" type="video/webm">
</video>

Lazy audio

<audio loading="lazy" controls>
  <source src="podcast-episode.mp3" type="audio/mpeg">
  <source src="podcast-episode.ogg" type="audio/ogg">
</audio>

Combining with preload

<!-- Best practice for a long page with many videos:
     lazy defers fetching; preload="metadata" limits initial load to just
     duration/dimensions once the element enters the threshold zone. -->
<video loading="lazy" preload="metadata" controls>
  <source src="explainer.mp4" type="video/mp4">
</video>

Detecting support

const supportsLazyMedia = 'loading' in HTMLVideoElement.prototype;
if (!supportsLazyMedia) {
  // Fall back to IntersectionObserver-based lazy loading
}

security and privacy

The attribute adds no new capability: deferred requests are the same media fetches the element would make anyway, under the same CORS and content-security rules. The one observable property is inherent to all lazy loading attributes: because the fetch fires when the element nears the viewport, its timing reveals approximate scroll position to the server hosting the media — exactly as <img loading="lazy"> has since Chrome 76. Pages that consider scroll behavior sensitive should not gate third-party-hosted media on it. Nothing else changes: no new headers, no new origins, no persistent state.
