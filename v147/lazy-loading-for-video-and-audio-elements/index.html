Lazy loading for video and audio elements

Limited availability

  • Chrome 150+ (148–149 partial)
  • Edge 150+
  • Firefox · not supported
  • Safari · not supported

Baseline: Limited availability — the webstatus.dev entry loading-lazy-media (queried 2026-08-16) records Chrome and Chrome for Android available since 150 (2026-06-30) and Edge since 150 (2026-07-02), with no Firefox or Safari implementation yet. In Chrome 147 — this page’s milestone — the feature was still in developer trial behind a flag.

Adds the loading attribute to <video> and <audio> elements, letting browsers defer media resource loading until the element is near the viewport — the same mechanism already available for <img> and <iframe>.

In developer trial in Chrome 147

In Chrome 147 this feature was behind a flag: enable chrome://flags/#enable-experimental-web-platform-features, or launch with --enable-blink-features=LazyLoadVideoAndAudio — the runtime-enabled feature is LazyLoadVideoAndAudio in runtime_enabled_features.json5 (status stable on current main). Per BCD the attribute later shipped by default: partially in Chrome 148 (not honored for <source> children — crbug.com/514611050) and fully in Chrome 150. The spec change is now merged into the WHATWG HTML standard (this page originally tracked the then-open PR #11980).

Syntax

The loading attribute on media elements is a lazy loading attribute — an enumerated attribute with two states, whose missing-value and invalid-value defaults are both Eager:

<video loading="eager" … >   <!-- default: load immediately -->
<video loading="lazy"  … >   <!-- defer until near the viewport -->
<audio loading="eager" … >
<audio loading="lazy"  … >

It is reflected in the DOM on HTMLMediaElement (so both HTMLVideoElement and HTMLAudioElement inherit it), verbatim from the standard’s IDL:

partial interface HTMLMediaElement {
  [CEReactions] attribute DOMString loading;
};

Normative behavior when the attribute is in the Lazy state, from the WHATWG HTML standard:

Lazy-state behavior (WHATWG HTML)
InteractionSpecified behavior
preload“When the loading attribute is in the Lazy state, it takes precedence over the preload attribute by deferring data fetching.”
poster (video)If poster is present and loading is Lazy, the user agent must defer loading the poster image source data until the element’s lazy load resumption steps are invoked.
autoplayIf autoplay is present and loading is Lazy, the user agent must also defer starting playback (and any associated network requests) until the resumption steps are invoked.
State change Lazy → EagerChanging the attribute’s state to Eager runs the stored lazy load resumption steps (and poster resumption steps), i.e. loading starts immediately.
<audio> without controls“audio elements without a controls attribute will not be displayed by the user agent, preventing them from lazy loading.”
Scripting disabledLazy loading is disabled (the element loads eagerly) — an anti-cloaking measure shared with the other lazy loading attributes.
Source: WHATWG HTML — media elements, loading; WHATWG HTML — lazy loading attributes (both fetched 2026-08-16)

why it exists

Since Chrome 77 (per BCD html.elements.img.loading and html.elements.iframe.loading), <img loading="lazy"> and <iframe loading="lazy"> have let browsers skip fetching off-screen resources until the user scrolls close to them. Before this feature, the same pattern did not apply to <video> and <audio>: without a loading attribute (or with it unsupported), media elements start loading per the media loading algorithm as soon as the parser encounters them, regardless of position on the page — so long-form pages with multiple embedded videos paid a large up-front network cost even when most users never scrolled to them. The loading attribute on media elements closes this gap and aligns behaviour across all embeddable resources (shipped by default since Chrome 150, as the banner and compatibility table record).

Source: chromestatus feature summary; WHATWG HTML — media loading attribute

the attribute

Attribute summary
Attributeloading
Elements<video>, <audio>
loading="eager"Default. No lazy-loading deferral — fetching follows the normal media loading algorithm and the preload hint, same as without the attribute (loading="eager" preload="none" can still avoid fetching data).
loading="lazy"Defer resource loading until the element is within the browser’s lazy-loading distance threshold from the viewport. The exact threshold is browser-defined and may vary by network conditions.

When loading="lazy" is set:

Lazy-state effects
Network requestDeferred until the element enters the lazy-load intersection zone.
preload interactionThe Lazy state takes precedence over preload: the preload hint’s behavior is deferred until the lazy load resumption steps run.
AutoplayAn element with autoplay and loading="lazy" defers starting playback until it enters the threshold zone and its resumption steps run.
JavaScript .play()Calling .play() before the resource is loaded triggers an immediate load, overriding the lazy deferral.
Source: WHATWG HTML — media loading attribute; chromestatus summary

example

Basic lazy video

<video loading="lazy" controls>
  <source src="feature-demo.mp4" type="video/mp4">
  <source src="feature-demo.webm" type="video/webm">
</video>

Compatibility note: in Chrome 148–149 the attribute was not honored for <source> children (crbug 514611050); from Chrome 150 the form above lazy-loads as expected.

Lazy audio

<audio loading="lazy" controls>
  <source src="podcast-episode.mp3" type="audio/mpeg">
  <source src="podcast-episode.ogg" type="audio/ogg">
</audio>

Note: the standard points out that <audio> without controls is not displayed, which prevents it from lazy loading — give lazy audio elements visible controls.

Combining with preload

<!-- Best practice for a long page with many videos:
     lazy defers fetching; preload="metadata" limits initial load to just
     duration/dimensions once the element enters the threshold zone. -->
<video loading="lazy" preload="metadata" controls>
  <source src="explainer.mp4" type="video/mp4">
</video>

Detecting support

const supportsLazyMedia = 'loading' in HTMLVideoElement.prototype;
if (!supportsLazyMedia) {
  // Fall back to IntersectionObserver-based lazy loading
}

// The IDL attribute reflects the content attribute (HTMLMediaElement.loading)
const video = document.querySelector("video");
video.loading = "lazy";              // setter — same as loading="lazy" in markup
console.log(video.loading);          // "lazy"
video.setAttribute("loading", "bogus");
console.log(video.loading);          // reflected string; the state falls back to Eager
