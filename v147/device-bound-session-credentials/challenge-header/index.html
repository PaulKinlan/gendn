DBSC protocol reference · challenge header

Secure-Session-Challenge header

The server’s cached or immediate challenge request. It is a response List Structured Field despite older prose calling it a string.

Syntax

The processing algorithm parses Secure-Session-Challenge as an RFC 9651 list. Each usable member is an sf-string with a required string id parameter.

Secure-Session-Challenge = sf-list

Secure-Session-Challenge: "c-9c17";id="session-42"

Inputs and constraints

Challenge members
ItemRequirement / behavior
Challenge valueAn opaque sf-string. The server should issue short-lived, unpredictable, one-time values and retain a small recent-challenge window for races.
idRequired sf-string naming an existing session in the response URL’s registrable-domain store.
Other parametersThe draft says they should be ignored.
Response statusA normal response caches a next proof challenge. A 403 during refresh requests a new proof immediately.

Outputs

For a matching session whose bound cookie could be set by the response, Chrome caches the challenge. On a refresh 403, it retries using the cached challenge and a signed Secure-Session-Response.

Errors and recovery

Malformed list members, non-string values, absent/non-string id, unknown session IDs, and cookie-policy-ineligible responses are ignored. A 403 without a usable newly cached challenge cannot produce a proof; the current Chromium fetcher reports invalid challenge rather than inventing one.

Source discrepancy: the Chrome developer guide shows a simplified 403 example without ;id=. The current Editor’s Draft requires a string id parameter for a challenge. Send ;id="…"; do not guess that a missing identifier will be interoperable.

Context

Servers may return the header on responses in the session’s context. The browser identifies the session using the response URL plus id; the value is not a cross-site routing mechanism.

Lifecycle

Cache now for the next refresh, or return 403 to force the next signing round. A server must accept a recent previous challenge as well as the newest one because concurrent deferred requests and latency can race. Chromium’s current implementation limits challenge rounds per fetch; that numerical limit is implementation behavior, not a portable server contract.

Examples

HTTP/1.1 403 Forbidden
Secure-Session-Challenge: "refresh-nonce-2";id="session-42"

# Cache a next challenge without forcing an immediate refresh:
HTTP/1.1 200 OK
Secure-Session-Challenge: "next-nonce";id="session-42"

Compatibility

Implementation and standards position
ItemRequirement / behavior
ChromeChromeStatus lists Chrome as in development, with desktop milestone 145 and no Android value; availability is controlled by implementation and feature configuration.
FirefoxNo signal; the Mozilla standards-position issue is the public evidence, not an implementation commitment.
SafariNo signal; the Mozilla standards-position issue is the public evidence, not an implementation commitment.
Other enginesUnknown. The W3C document is an Editor’s Draft, not a final interoperable Recommendation.

Security and privacy

Challenges are proof nonces, not session credentials. Make them unpredictable, expire them quickly, bind them to the server session and expected public key, and consume them on successful verification. Do not make challenge acceptance a device fingerprinting oracle.
