CSS update: decoupling of Width and Style properties

Behavior change — aligned across all current engines; no Baseline register entry

  • Chrome · 147 (desktop, Android, WebView)
  • Edge · Chromium-based (not separately reported)
  • Firefox · shipped (column-rule list handling fixed in Firefox 147)
  • Safari · shipped (WebKit column-rule update landed)

This is a computed-value behavior change to existing properties, not a new feature: a webstatus.dev query returns zero matches and BCD has no sub-feature key for it under border-width, outline-width, or column-rule-width (all verified 2026-09-06). Cross-engine alignment is evidenced directly: the current stable runs of Chrome 152, Edge 152, Firefox 155, and Safari 26.6 all pass the relevant WPT computed-value tests (outline-width-computed 9/9, column-rule-width-computed 3/3, border-width-interpolation 256/256; wpt.fyi stable runs of 2026-09-05, queried via the wpt.fyi search API 2026-09-06).

Chrome 147 aligns with the updated CSS specifications and with Firefox and WebKit: the computed values of border-width, outline-width, and column-rule-width are now independent of their corresponding *-style properties. Previously Chrome forced the computed width to 0px when the style was none or hidden. For outline-width and column-rule-width the resolved value returned by getComputedStyle() now also reflects the authored value; for border-width the resolved value is defined as the used value and still reads 0px when border-style is none/hidden — a deliberate backward-compatibility carve-out.

what changed

border-*-width — computed value Forced to 0px when border-style: none | hidden Authored value (absolute length, snapped as a border width), independent of border-style
border-*-width — resolved value (getComputedStyle()) 0px when style is none | hidden Unchanged: still 0px — the spec defines the resolved value as the used value, and the used width is 0 when the style is none/hidden (deliberate backward compatibility)
outline-width — computed and resolved value Forced to 0 when outline-style: none Both reflect the authored value
column-rule-width — computed and resolved value Forced to 0 when column-rule-style: none | hidden Both reflect the authored value; the none/hidden styles now force the used value to 0 instead
Rendering / layout Unchanged either way — a border, outline, or column rule whose style is none/hidden still paints nothing and occupies no space (used width 0)
Source: ChromeStatus record (summary + interop/compat assessment, verbatim on the resolved-value carve-out); CSS Backgrounds 3 §3.3; CSS UI 4 §outline-width; CSS Multicol 1 §column-rule-width

why it changed

CSS historically special-cased these three width properties so their computed value became 0px whenever the corresponding *-style was none or hidden, even when the author specified a nonzero width. With CSS Gap Decorations extending column-rule-* to accept lists of values and repeaters, applying that special case became ambiguous (which list item's style zeroes which width?) and difficult to define consistently. Making *-width computed values independent of *-style gives these properties an intuitive model and preserves the author-specified value — the CSSWG resolved to move the zeroing from computed-value time to used-value time across the four affected specs (PR #11913).

It is also an interop fix: Firefox and WebKit already implemented the decoupled computed values, so code that read widths back on those engines behaved differently in Chrome. Chrome 147 closes the gap.

Source: ChromeStatus record — motivation (verbatim in substance); csswg-drafts PR #11913; csswg-drafts issue #11494

syntax: the affected propdefs, before and after

The value grammar of all three properties is unchanged (<line-width> = <length [0,∞]> | thin | medium | thick); what changed is each propdef's Computed value line plus new used/resolved-value prose. Verbatim from the merged Editor's Drafts (all fetched 2026-09-06):

CSS Backgrounds and Borders Level 3 §3.3:

Name: border-top-width, border-right-width, border-bottom-width, border-left-width
Value: <line-width>
Initial: medium
Inherited: no
Percentages: N/A
Computed value: absolute length, snapped as a border width
Animation type: by computed value

The removed text read: “…; zero if the border style is none or hidden” (PR #11913 diff). Two sentences were added in its place, verbatim:

The resolved value for the border-width properties is the used value.

If the border-style corresponding to a given border-width is none or hidden,
then the used width is 0.

CSS Basic User Interface Level 4 §3.2:

Name: outline-width
Value: <line-width>
Initial: medium
Inherited: no
Percentages: N/A
Computed value: absolute length, snapped as a border width
Animation type: by computed value

(Previously: “…; 0 if the outline style is none”.) outline-width has no border-style-like resolved-value carve-out, so its resolved value follows its computed value.

CSS Multi-column Layout Level 1 §4.4:

Name: column-rule-width
Value: <line-width>
Initial: medium
Applies to: multicol containers
Inherited: no
Percentages: N/A
Computed value: absolute length, snapped as a border width
Animation type: by computed value type

The style-interaction sentence in §4.3 now reads, verbatim: “The none and hidden values force the used value of column-rule-width to be 0.” (previously “the computed value”). CSS Gap Decorations Level 1 received the matching edit for its list-valued column-rule-width/row-rule-width, dropping the force-to-0 computed-value special case entirely.

Source: css-backgrounds-3 ED; css-ui-4 ED; css-multicol-1 ED; PR #11913 diff (before/after text)

computed vs. resolved vs. used — what you can now observe

The change is precisely scoped to value-resolution stages, so knowing which API surfaces which stage matters:

  • Computed value — what inheritance, transitions/animations interpolation, and computedStyleMap() (CSS Typed OM) operate on. All three properties now keep the authored width here regardless of style. Practical wins: border-width: inherit picks up the real authored width from a styleless parent, and a transition on border-width that passes through a border-style: none state interpolates from the authored width instead of snapping from 0 (covered by the WPT border-width-interpolation suite).
  • Resolved value — what getComputedStyle() returns. For outline-width and column-rule-width the resolved value is the computed value, so it now reports the authored width. For border-*-width the spec pins the resolved value to the used value, so getComputedStyle().borderTopWidth still returns 0px when border-style is none/hidden — existing feature-detection and layout-measurement code keeps working.
  • Used value — what layout and painting consume. Unchanged for all three: styleless borders, outlines, and rules still render nothing and take no space.

Why the asymmetry? Compatibility data: Chrome's use counters showed resolved-value reads of border-width are common enough that changing them was risky, while resolved-value reads of outline-width/column-rule-width (≈2.37% of page loads) are dominated by automated getComputedStyle() sweeps that do not depend on the property's semantics; computed-value observation of all three was below 0.0001%. The carve-out keeps border-width's script-visible resolved value stable while fixing the model underneath.

Source: ChromeStatus record — interoperability and compatibility risks (UseCounter figures verbatim); css-backgrounds-3 resolved/used-value prose; CSSOM — resolved value

examples

Reading the three properties back after Chrome 147 — note the border carve-out:

/* stylesheet */
.box {
  border-style: none;   border-width: 4px;
  outline-style: none;  outline-width: 6px;
}
const box = document.querySelector(".box");

// Computed value (CSS Typed OM) — decoupled for ALL three properties:
box.computedStyleMap().get("border-top-width").toString();
// Chrome 147+: "4px"   (previously "0px")

// Resolved value — border-width is pinned to the used value:
getComputedStyle(box).borderTopWidth;
// Chrome 147+: still "0px"  (unchanged, matches Firefox and Safari)

// Resolved value — outline-width follows the computed value:
getComputedStyle(box).outlineWidth;
// Chrome 147+: "6px"   (previously "0px")

Transition continuity — a border that fades in without a width snap:

.card {
  border-style: none;
  border-width: 4px;              /* computed value survives style: none */
  transition: border-width 0.3s;
}
.card:hover {
  border-style: solid;            /* appears at 4px immediately — and a
                                     separate width change now animates
                                     from 4px, not from 0px */
}

security and privacy

  • No new exposure surface. The change alters which stage of value resolution existing, same-origin-readable CSSOM APIs report; it introduces no storage, networking, cross-origin, or sensor surface. The newly visible data is the page's own authored stylesheet values.
  • Fingerprinting delta is a version signal only. getComputedStyle().outlineWidth under outline-style: none distinguishes pre-/post-change engine versions — comparable to any behavior fix and weaker than the UA string; the ChromeStatus record's UseCounter analysis explicitly attributes most resolved-value reads to existing scraping/fingerprinting sweeps that do not depend on these semantics.
  • Review status on the record: both the security and privacy launch-review fields read “Pending” on the ChromeStatus API record (fetched 2026-09-06); no security or privacy risks are asserted in the intent. gendn records that status honestly rather than claiming completed review.
Source: ChromeStatus API record — security_review_status / privacy_review_status, interop-compat UseCounter analysis
