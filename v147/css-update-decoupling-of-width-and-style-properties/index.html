CSS update: decoupling of Width and Style properties

Limited availability — newly interoperable behavior

  • Chrome · 147 (enabled by default)
  • Firefox · Shipped/Shipping
  • Safari · Shipped/Shipping
  • Edge · no separate signal (Chromium)

This is a behavior change to long-Baseline properties, not a new feature: webstatus.dev has no entry for the decoupling itself (checked 2026-08-23). Chrome 147 adopts what Firefox and WebKit already ship (ChromeStatus API record: both “Shipped/Shipping”), closing the gap per the updated CSS specifications.

From Chrome 147, the computed values of border-width, outline-width, and column-rule-width are independent of their corresponding *-style properties: they always reflect the author-specified value instead of being forced to 0px when the style is none or hidden. The used width of an invisible border or rule is still 0 — nothing changes visually. What you observe from script differs by property: getComputedStyle() returns the authored value for outline-width and column-rule-width (resolved = computed), but still 0px for border-width, whose resolved value is defined as the used value.

syntax

No new syntax — the change is in the computed-value line of three existing property definitions. The normative sentences, verbatim from the current drafts (fetched 2026-08-23):

/* css-backgrounds-3 — border-width:
   "If the border-style corresponding to a given border-width is none or
    hidden, then the used width is 0."
   "The resolved value for the border-width properties is the used value."
   Changes: the computed-value-of-0 special case is removed. */

/* css-ui-4 — Changes:
   "Removed the special case of outline-width having a computed value of 0
    when outline-style is none or hidden." */

/* css-multicol — column-rule-width:
   "The none and hidden values force the used value of column-rule-width
    to be 0."
   Changes: "Removed the special case of column-rule-width having a
    computed value of 0 when column-rule-style is none or hidden." */

border-width

Computed value: the authored <line-width>, no longer zeroed by border-style: none | hidden. Used width with an invisible style: 0 (unchanged). Because css-backgrounds-3 defines the resolved value of the border-width properties as the used value, getComputedStyle() still reports 0px for a none-style border. The decoupled computed value matters where computed values are consumed directly: inheritance (border-width: inherit), transitions and animations that start from or interpolate the computed value, and custom-property/registered-property machinery.

outline-width

Computed value: the authored value — css-ui-4's changelog records the removal of the 0-when-none special case. outline-width is not on CSSOM's used-value list for resolved values, so its resolved value is the computed value: getComputedStyle() now returns the authored width even while outline-style: none hides the outline. This is the script-visible half of the change.

column-rule-width

Same shape as outline-width: css-multicol keeps “the none and hidden values force the used value of column-rule-width to be 0” while its changelog removes the computed-value special case — so the rule stays invisible and takes no gap space, but getComputedStyle() resolves to the authored value.

Source: css-backgrounds-3 §4.3; css-ui-4 outline-width + Changes; css-multicol column-rule-width + Changes — all fetched 2026-08-23; edited by PR #11913

Source: ChromeStatus API record — summary (“the resolved values … for outline-width and column-rule-width will also reflect the specified values”); css-backgrounds-3

why it exists

The zeroing special case dated from CSS 2 and made the three width properties behave unlike every other property: what you wrote was not what computed. Firefox and WebKit had already dropped it, so Chrome's behavior was a source of cross-browser bugs — code that read getComputedStyle().outlineWidth got different answers per engine. The CSSWG resolved issue #11494 to remove the computed-value special case across css-backgrounds, css-ui, css-multicol and css-gaps (PR #11913), and Chrome 147 “aligns with Firefox and WebKit, which have already implemented this behavior” (ChromeStatus).

Source: CSSWG issue #11494; ChromeStatus record — summary

examples

/* The widths are authored but the styles are off — nothing is painted. */
.box  { border-style: none;  border-width: 4px; }
.box  { outline-style: none; outline-width: 6px; }
.cols { column-rule-style: none; column-rule-width: 8px; }

const box = document.querySelector(".box");
const cs = getComputedStyle(box);

cs.outlineWidth;     // Chrome 147+: "6px"  (previously "0px") — resolved = computed
cs.borderTopWidth;   // "0px" in every engine — resolved = used value, border invisible

// Where the border-width decoupling *does* show up: transitions.
// Toggling border-style no longer snaps the computed width to 0, so
// a width transition continues from 4px instead of restarting at 0.
box.style.borderStyle = "solid";
Source: behavior per css-backgrounds-3, css-ui-4, css-multicol; resolved-value split per the ChromeStatus API record

security and privacy

No new capability, data flow, or fingerprinting surface: the change only alters which value existing CSSOM APIs report for three properties, converging on what Firefox and WebKit already expose. The main risk is compatibility, not security — code that relied on Chrome's old 0px readback for outline-width/column-rule-width (for example, testing parseInt(cs.outlineWidth) === 0 to detect a hidden outline) must check the *-style property instead.

Source: change scope per the ChromeStatus API record; no security considerations are raised in CSSWG issue #11494
