CSS update: decoupling of Width and Style properties

Behavior change — converging across engines

  • Chrome · 147 (desktop + Android)
  • Edge · expected to mirror Chrome
  • Firefox · already implemented (bug 1998285)
  • Safari · already implemented (WebKit bug 304940)

There is no dedicated web-features/webstatus.dev entry for this computed-value change (checked 2026-09-27; the base properties themselves are ancient — BCD border-width records Chrome 1 / Firefox 1 / Safari 1). The ChromeStatus record states the change “aligns Chrome with Firefox and WebKit, which have already implemented this behavior”; see the full table.

Chrome 147 aligns with the updated CSS specifications: the computed values of border-width, outline-width, and column-rule-width are now independent of their corresponding *-style properties, instead of being forced to 0px when the style is none or hidden. The zeroing moves to the used value. For outline-width and column-rule-width the change is also visible in getComputedStyle(); for border-width it is not, because CSSOM resolves border-width to its used value.

syntax

No grammar changes — the change is in each property’s Computed value line and in where the zeroing happens. Quoted verbatim from the current drafts (read 2026-09-27):

PropertyComputed value (current spec)Where the zeroing lives now
border-*-width (css-backgrounds-3)“absolute length, snapped as a border width”“The resolved value for the border-width properties is the used value. If the border-style corresponding to a given border-width is none or hidden, then the used width is 0.”
outline-width (css-ui-4)“absolute length, snapped as a border width”Used value (no resolved-value-is-used-value rule, so getComputedStyle() returns the computed, decoupled value)
column-rule-width / row-rule-width (css-gaps-1)“list of absolute lengths, snapped as a border width”Used value (same as outline-width: the resolved value reflects the specified value)
Source: CSS Backgrounds & Borders 3; CSS Basic UI 4; CSS Gap Decorations 1; csswg PR #11913

what changed

PropertyBefore Chrome 147Chrome 147+
border-width Computed value forced to 0px when border-style: none Computed value reflects the authored value; getComputedStyle() still returns 0px when the style is none/hidden, because CSSOM resolves border-width to its used value (see syntax)
outline-width Computed value forced to 0px when outline-style: none Computed value and the getComputedStyle() resolved value reflect the authored value
column-rule-width Computed value forced to 0px when column-rule-style: none Computed value and the getComputedStyle() resolved value reflect the authored value

Where the border-width part of the change is observable: everything keyed to the computed value — inheritance (border-width: inherit now inherits the authored width, not 0px) and transitions/animations, whose animation type is “by computed value”, so toggling border-style from none to solid no longer makes width transitions start from 0px.

Source: ChromeStatus summary (“the resolved values … for outline-width and column-rule-width will also reflect the specified values”); resolved-value rule per css-backgrounds-3; animation type per the propdefs cited in syntax

examples

What getComputedStyle() reads back in Chrome 147+ — note the deliberate difference between outline-width and border-width:

.box {
  border-style: none;   border-width: 4px;
  outline-style: none;  outline-width: 6px;
}

const cs = getComputedStyle(box);
cs.outlineWidth;  // "6px" in Chrome 147+  (previously "0px")
cs.borderWidth;   // still "0px" — CSSOM resolves border-width
                  // to its USED value, which is 0 while
                  // border-style is none/hidden

/* Where the border-width decoupling shows up instead: */
.card {
  border-style: none;
  border-width: 4px;
  transition: border-width 200ms;
}
.card.framed { border-style: solid; }
/* Before 147: adding .framed changed the COMPUTED width 0px→4px,
   so a width transition ran from zero.
   147+: the computed width was 4px all along — only the style
   flips, and no width transition fires. */
Source: snippet gendn-derived from the ChromeStatus summary and the spec resolved-value rules cited above (labelled accordingly)

browser compatibility

The base properties are universal (BCD css/properties/border-width.json: Chrome 1, Firefox 1, Safari 1, verified 2026-09-27). BCD does not yet record the computed-value decoupling itself, so that row is interim data from the ChromeStatus record and the vendor bugs it links:

CapabilityChromeFirefoxSafari
border-width / outline-width / column-rule-width (base properties, BCD)111
Decoupled computed values (no BCD note yet; interim data)147 (ChromeStatus)Already implemented (bug 1998285, the ChromeStatus record’s Firefox view)Already implemented (bug 304940, the ChromeStatus record’s Safari view)

Because all current engines converge on the new model, feature-detection is rarely needed; audit code that read outlineWidth/columnRuleWidth from getComputedStyle() and relied on "0px" as a proxy for “style is none” — read the *-style property instead.

Source: BCD css/properties/border-width.json; ChromeStatus API record (vendor views + bug links)
