Autofill event

Limited availability

  • Chrome · origin trial (v147 listing) · behind AutofillEvent
  • Edge · no signal
  • Firefox · no signal
  • Safari · no signal

Chrome-only, experimental. webstatus.dev's only “autofill” entry is the unrelated :autofill CSS pseudo-class; the event has no web-features or BCD entry (checked 2026-08-23). The ChromeStatus API record lists Firefox and Safari views as “No signal”.

The autofill event fires at the document when the user agent is about to autofill form fields. Its autofillValues attribute exposes the [element, value] pairs the browser intends to fill, and its refill callback lets the page restructure a dynamic form (say, add the state selector a US address needs) and ask the browser to retry the fill against the updated form. Defined by the WICG Autofill Event draft, which also adds a full-address autocomplete token.

Origin trial — API surface may change; exact enable steps Listed under “Origin trial” for Chrome 147 in the milestone=147 listing (re-verified 2026-08-23). To use it:
  • Local testing: launch Chrome with --enable-blink-features=AutofillEvent. The Blink runtime feature AutofillEvent is status: "experimental" with origin_trial_feature_name: "AutofillEvent" and origin_trial_allows_third_party: true in runtime_enabled_features.json5 (verified 2026-08-23).
  • Origin trial: register in the Chrome Origin Trials console (third-party tokens allowed) and serve the token via Origin-Trial header or meta tag.
  • Feature-detect: if ("AutofillEvent" in window) { … } — the interface is absent when the feature is off.

syntax

The complete IDL, from the spec's IDL index (fetched 2026-08-23):

[Exposed=Window]
interface AutofillEvent : Event {
  constructor(DOMString type, optional AutofillEventInit eventInitDict = {});
  readonly attribute FrozenArray<AutofillValueEntry> autofillValues;
  readonly attribute RefillCallback? refill;
};

callback RefillCallback = Promise<undefined> ();

dictionary AutofillEventInit : EventInit {
  sequence<AutofillValueEntry> autofillValues = [];
  boolean allowRefill = true;
};

typedef sequence<any> AutofillValueEntry;
// AutofillValueEntry is a tuple of [HTMLElement, DOMString]
// where the first element is the form control and the second is the value to fill

AutofillEvent.autofillValues

Read-only FrozenArray of autofill value entries — each a two-element tuple of the HTMLElement form control that will receive a value and the DOMString value the user agent intends to fill into it (spec §2.1). Because the event fires before the fill, handlers can inspect these pairs to decide whether the current form structure fits the data. Iterate with destructuring: for (const [element, value] of event.autofillValues). The data is limited to what the user agent intends to fill into this page's forms.

AutofillEvent.refill

Nullable callback attribute (RefillCallback, returning Promise<undefined>). Calling event.refill() after modifying the form “signals to the user agent that the form has been modified and that it should retry the autofill operation with the updated form structure” (spec §1). On the second dispatch — the retry after form modification — refill is null, which prevents infinite refill loops; it is also null when the original event was created with allowRefill: false. Always null-check before calling.

AutofillEventInit dictionary

Extends EventInit with autofillValues (default []) and allowRefill (default true). Together with the public constructor this lets third-party autofill providers — password managers, extensions — construct and dispatch synthetic AutofillEvents with the same shape, “ensuring consistent behavior regardless of the autofill source” (spec §6.1).

the full-address autocomplete token

The spec also defines a new autofill field name: setting autocomplete="full-address" on a form signals that the page wants the user's complete address data — including fields not currently present in the form — so it can build the right fields dynamically from the event. The user agent SHOULD request permission before exposing address data beyond the rendered fields (spec §5):

<form autocomplete="full-address">
  <input name="country" autocomplete="country">
  <div id="dynamic-address-fields"></div>
</form>
Source: WICG Autofill Event spec — IDL index, §2 Concepts, §3 Interface, §5 full-address (all fetched 2026-08-23)

processing model

Per spec §4, one autofill operation proceeds:

  1. The user explicitly triggers autofill (e.g. picks a suggestion). The user agent computes the value entries it intends to fill.
  2. An AutofillEvent is created — type "autofill", bubbles true, cancelable false, its values list and allow-refill flag set — and dispatched at the document.
  3. Handlers run before the fill: they may restructure the form and call refill().
  4. The user agent performs the autofill operation on the (possibly updated) form.
  5. If refill() was called, the event is dispatched a second time with the recomputed entries and refill set to null — no further retries.

The event cannot be canceled — the page cannot use it to block autofill, only to adapt to it.

Source: WICG spec §4 Processing Model

why it exists

Autofill on dynamic forms is unreliable: address forms in particular change shape per country — selecting a country adds, removes, and reorders fields — and the browser's fill “may not respond correctly to the rendered form” (spec introduction). The ChromeStatus summary frames the same problem: developers previously had no reliable signal that autofill was happening, and no way to “modify their forms to fit the autofilled data and let the browser know when they have done so”. The event plus refill() closes that loop.

Source: WICG spec §1 Introduction; ChromeStatus record — summary

examples

The spec's checkout scenario — add a state selector when a US address is about to be filled, then ask the browser to refill:

document.addEventListener("autofill", async (event) => {
  // What is the browser about to fill?
  let countryValue = null;
  for (const [element, value] of event.autofillValues) {
    if (element.autocomplete === "country") {
      countryValue = value;
      break;
    }
  }

  // A US address needs a state field this form doesn't have yet.
  if (event.refill && countryValue === "US") {
    addStateSelector();          // restructure the form
    await event.refill();        // browser retries with the new field
    // The retry dispatches a second autofill event with refill === null.
  }
});

ChromeStatus also links two standalone demos by the feature's author: autofill event demo and credit-card autofill demo.

Source: WICG spec §1.2 Example (adapted); ChromeStatus sample links

security and privacy

  • Values are exposed before commit. The event reveals autofill values to JavaScript before they land in the fields, so the spec requires that it only fire “after explicit user consent to autofill has been given (e.g., by selecting an autofill suggestion from a dropdown)” — never speculatively.
  • Scope is limited to data the user agent intends to fill into this page's forms; the API shape keys every value to a rendered (or refill-added) form control.
  • The full-address token widens that scope deliberately — complete address data including fields not in the form — which is why the spec has the user agent request permission for it.
  • Refill is bounded: the second dispatch carries refill === null, so a page cannot drive unbounded fill loops.
  • Third-party providers (password managers, extensions) can dispatch synthetic AutofillEvents with the same structure, keeping page behavior consistent across autofill sources.
Source: WICG spec §6 Security and Privacy Considerations
