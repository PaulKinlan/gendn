Autofill event

Limited availability

  • Chrome · origin trial 147–152 (desktop + Android)
  • Edge · not available (Chrome origin trial)
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register: a webstatus.dev query returns zero matches and the ChromeStatus record marks the Web Feature ID as “Missing feature” (both verified 2026-09-13). Firefox and Safari positions have been requested but not stated (mozilla/standards-positions#1361, WebKit/standards-positions#431). MDN does not yet document this event (MDN search API, checked 2026-09-13).

A new autofill event, fired at the Document when the browser is about to autofill form controls. The event carries the list of [element, value] pairs the browser intends to fill, so a page can adapt a dynamic form to the incoming data — and its refill callback lets the page ask the browser to fill again after the form has been restructured.

Origin trial — Chrome 147 to 152

The Autofill event is in origin trial from Chrome 147 to Chrome 152 (desktop and Android). The API surface may change before it ships by default — do not copy this contract into production without a trial token and feature detection. To use it:

  • Production (origin trial): register for the “AutofillEvent” origin trial and serve the token. The trial allows third-party tokens (origin_trial_allows_third_party: true), so embedded checkout/autofill providers can enable it for their embedders.
  • Local testing: the Blink runtime feature is AutofillEvent, status experimental — launch with --enable-blink-features=AutofillEvent, or enable chrome://flags/#enable-experimental-web-platform-features.
Source: Intent to Experiment: Autofill event (milestones 147–152, LGTM 2026-02-19); runtime_enabled_features.json5 (fetched 2026-09-13).

why it exists

Autofill relies on static forms, but address forms are dynamic almost by definition: different geographies need different fields, and selecting a country re-orders, adds, or removes inputs. Today’s “industry standard” workaround is a set of hidden form fields that try to anticipate and capture the right information and then surface it to the user — brittle, complex, and it entrenches a hidden-field technique that bad actors also abuse. Because autofill mediates the interaction, the browser may fill a form the page was about to restructure, and the page has no reliable signal that a fill happened or a way to ask for another pass.

The autofill event closes that loop: the browser announces the values it is about to fill, the page adapts its form to fit them (for example adding a state selector for US addresses), and the page calls event.refill() to tell the browser the form changed so it can fill again. The explainer’s goals: make autofill more reliable for users (paving a path to deprecating hidden-field filling), reduce implementation-specific hacks for site developers, and give third-party autofill providers hooks that work with the same API.

Source: spec §1 Introduction; explainer; ChromeStatus motivation.

Syntax

The full WebIDL, from the specification’s §3:

[Exposed=Window]
interface AutofillEvent : Event {
  constructor(DOMString type, optional AutofillEventInit eventInitDict = {});
  readonly attribute FrozenArray<AutofillValueEntry> autofillValues;
  readonly attribute RefillCallback? refill;
};

callback RefillCallback = Promise<undefined> ();

dictionary AutofillEventInit : EventInit {
  sequence<AutofillValueEntry> autofillValues = [];
  boolean allowRefill = true;
};

typedef sequence<any> AutofillValueEntry;
// AutofillValueEntry is a tuple of [HTMLElement, DOMString]
// where the first element is the form control and the second is the value to fill

Transcription note: the spec’s rendered IDL block contains a bikeshed markup artifact (stray href/id attribute text leaking into the two autofillValues member lines, in both §3 and the IDL Index as published 2026-09-13); it is removed above without semantic change — the member names and types are as defined by the spec’s §3.1 attribute prose.

Source: spec §3 The AutofillEvent Interface.

the event and its members

The autofill event

Syntaxdocument.addEventListener("autofill", (event) => { … }) — the firing algorithm creates an AutofillEvent, sets type to "autofill", bubbles to true, cancelable to false, and dispatches it at the document. There is no onautofill IDL event-handler attribute in the spec — use addEventListener().
Listener inputThe listener receives the AutofillEvent instance. The user agent matches form controls to autofill data via the control’s autocomplete attribute (the HTML autofill field names) and implementation-defined heuristics.
Event payloadautofillValues — the frozen list of [HTMLElement, DOMString] entries about to be filled — and refill — the refill callback, or null.
ErrorsDispatch itself has no error surface (the event is not cancelable; preventDefault() is a no-op). Exceptions thrown inside a listener follow ordinary DOM event dispatch error reporting and do not stop the fill: the autofill operation is performed after dispatch regardless.
Context & exposure[Exposed=Window] — window documents only, not workers. Fired at each Document involved in the fill (the explainer: the target is the frame document, because the autofill notion of “form” may span shadow DOM or multiple documents, loosely following HTMLFormElement). In Chrome 147 the event only fires with the origin-trial token or flag enabled (see the origin-trial block).
LifecycleFires when the user agent’s autofill mechanism is triggered and the user has selected values — before the values are committed, and in particular before any focus, input, change, or blur events caused by the fill. The autofill operation runs immediately after dispatch. If the page calls refill(), one retry dispatch follows with refill set to null (no infinite loops).

Spec/explainer drift, disclosed: the explainer says the event “does not bubble and is not cancelable” and names the values property values (with boolean values for checkboxes/radios), while the published spec initializes bubbles to true and defines autofillValues with DOMString values. This page documents the spec text of 4 March 2026; treat the flag and naming details as movable while the origin trial runs.

Source: spec §4.1 Firing the Autofill Event, §4.3 Integration with HTML Autofill; explainer — JavaScript interface.

AutofillEvent() constructor

Syntaxnew AutofillEvent(type) · new AutofillEvent(type, eventInitDict)
Parameterstype — a DOMString, conventionally "autofill". eventInitDict — an optional AutofillEventInit dictionary (defaults to {}), which also accepts the inherited EventInit members bubbles, cancelable, and composed.
ReturnsA new AutofillEvent whose autofillValues is a frozen copy of eventInitDict.autofillValues (default []).
ErrorsStandard WebIDL conversion errors only: a TypeError if eventInitDict.autofillValues is not iterable as sequence<AutofillValueEntry>. The spec defines no constructor-specific exceptions.
ContextAny Window context where the interface is exposed. The main consumers are third-party autofill providers (e.g. password-manager extensions), which the spec invites to construct and dispatch AutofillEvents with the same structure so pages behave consistently regardless of the autofill source.
LifecycleA synthetic, page-dispatched AutofillEvent is an ordinary DOM event: dispatching it does not make the user agent fill anything — only user-agent-initiated fills run the §4.1 algorithm. A synthetic event’s refill is null unless the dispatching provider supplies its own refill machinery.
Source: spec §3, §6.1 Third-Party Autofill Providers; WebIDL — FrozenArray.

AutofillEvent.autofillValues

Read-only FrozenArray<AutofillValueEntry> — the list of [HTMLElement, DOMString] tuples the user agent is about to fill. Full reference, including the tuple shape and its caveats: autofillValues.

AutofillEvent.refill

Read-only RefillCallback? — call it after restructuring the form to request one more fill pass; null on retry dispatches or when the user agent does not permit a refill. Full reference, including all rejection paths: refill.

AutofillEventInit dictionary

Syntaxdictionary AutofillEventInit : EventInit { sequence<AutofillValueEntry> autofillValues = []; boolean allowRefill = true; };
MembersautofillValues — a sequence<AutofillValueEntry>, default []: the entries the constructed event will report. allowRefill — a boolean, default true: sets the event’s internal allow refill flag; when false, a refill() call on the event rejects. Inherits bubbles/cancelable/composed from EventInit.
EffectPopulates the constructed event’s autofill values list and allow refill flag — the same internal state the user agent sets when it fires the event itself.
ErrorsStandard WebIDL dictionary conversion: a non-sequence autofillValues throws TypeError at construction; allowRefill is coerced to boolean. No dictionary-specific exceptions are defined.
ContextUsed only as the constructor’s second argument — chiefly by third-party autofill providers synthesizing events (spec §6.1).
LifecycleRead once during construction; later mutation of the dictionary object has no effect on the constructed event (its values list is copied and frozen).
Source: spec §3 The AutofillEvent Interface; WebIDL — FrozenArray.

The "full-address" autocomplete token

Syntax<form autocomplete="full-address"> — a new autofill field name for the autocomplete attribute, introduced by this specification alongside the event.
Applies toA form control (the spec: “when a form control has the autocomplete attribute set to "full-address"”); the spec’s own example sets it on the <form> element. It extends the HTML autofill field name vocabulary.
EffectThe user agent SHOULD request permission to access the user’s complete address data, including fields not present in the current form — those extra values then arrive through the autofill event’s autofillValues, so the form can add the fields it needs.
ErrorsNone defined — an unsupported token is simply ignored by the autocomplete processing model; a denied permission yields ordinary per-field autofill. The permission prompt’s shape is left to the user agent (SHOULD-level requirement).
ContextMeaningful only where the Autofill event feature is enabled (origin trial / flag in Chrome 147–152). Not part of the HTML Standard’s token list as of 2026-09-13.
LifecycleDeclarative — evaluated whenever the user agent runs autofill against the form; combine with an autofill listener + refill() to build the address form dynamically around the granted data.

The spec’s own example, using the token together with an autofill listener to build the address form around the granted data:

<form autocomplete="full-address">
  <input name="country" autocomplete="country">
  <div id="dynamic-address-fields"></div>
</form>
Source: spec §5 The "full-address" Autocomplete Token; explainer §2 “full-address”.

Examples

Log what the browser is about to fill (note the listener is on document, not on the form or its fields):

document.addEventListener("autofill", (event) => {
  for (const [element, value] of event.autofillValues) {
    console.log(`about to fill ${element.name || element.id} with "${value}"`);
  }
});

The spec’s canonical checkout example — add a US state selector when the autofilled country is US, then ask for a refill (condensed from spec §1.2):

document.addEventListener("autofill", async (event) => {
  let countryValue = null;
  let formElement = null;
  for (const [element, value] of event.autofillValues) {
    if (element.autocomplete === "country") {
      countryValue = value;
      formElement = element.form;
      break;
    }
  }

  if (event.refill !== null && countryValue === "US" &&
      !formElement.querySelector('[autocomplete="address-level1"]')) {
    const stateSelect = document.createElement("select");
    stateSelect.autocomplete = "address-level1";
    stateSelect.name = "state";
    stateSelect.innerHTML = `<option value="">Select state...</option>
      <option value="CA">California</option> ...`;
    formElement.querySelector('[autocomplete="postal-code"]')
      .before(stateSelect);

    try {
      await event.refill(); // one more fill pass over the modified form
    } catch (e) {
      // InvalidStateError: too late, refill already pending, or not allowed
    }
  }
});

A third-party autofill provider (e.g. a password-manager extension) synthesizing the same signal for pages (spec §6.1) — note that dispatching it does not make the browser fill anything:

const event = new AutofillEvent("autofill", {
  autofillValues: [[emailInput, "user@example.com"]],
  allowRefill: false,
});
document.dispatchEvent(event);

The feature owner’s own demos, linked from the ChromeStatus record: autofill event demo and credit-card autofill demo (both 200, 2026-09-13; they require a browser with the trial enabled and stored autofill data).

Source: spec §1.2 Example, §6.1; ChromeStatus sample links.

security and privacy

  • Values are exposed before commit. The event hands autofill values to JavaScript before they land in form fields. Mitigation: user agents SHOULD fire the event only after explicit user consent to autofill (e.g. the user picked a suggestion from the autofill dropdown) — the event never runs ahead of the user’s choice.
  • Scope of disclosure is bounded by the fill. The data passed to the event is limited to what the user agent intends to fill into forms on the page — the API shape requires an element as the key for every value, so there is no side channel to profile data the page could not otherwise receive.
  • Refill adds fields after consent. After refill(), the form likely contains fields that were not present when the user consented. The spec directs user agents to still consider user consent before filling the new fields, as they already do for automatic refills.
  • "full-address" is permission-mediated. Requesting the complete address (fields beyond the rendered form) SHOULD trigger a user-agent permission request — it is explicitly not silent bulk disclosure.
  • Hidden-field displacement. A stated goal is replacing the hidden-form-field pattern, which today both powers legitimate dynamic forms and is abused to exfiltrate autofill data users never see being filled.
Source: spec §6 Security and Privacy Considerations; explainer (security questionnaire in-repo).
