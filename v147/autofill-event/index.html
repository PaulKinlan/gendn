Autofill event

Limited availability

  • Chrome · origin trial (started 147; current window unrecorded)
  • Edge · unknown
  • Firefox · no signal
  • Safari · no signal

This API is not Baseline: it is a Chrome origin trial with no publicly recorded implementation elsewhere (other-browser state unknown — see the compatibility table). webstatus.dev has no web-feature entry for the autofill event (the autofill web-feature there covers the general autocomplete mechanism, not this event; features API checked 2026-08-30), BCD has no AutofillEvent entry (raw path 404, 2026-08-30), MDN has no page, and the ChromeStatus record reports “No signal” from Firefox and Safari.

The autofill event fires at the Document when the browser is about to autofill form fields — before the values are committed. The event carries the list of element/value pairs the browser intends to fill (autofillValues) and, when permitted, a one-shot refill callback: the page can reshape its form to fit the incoming data (say, country-specific address fields) and ask the browser to run autofill again against the modified form.

Source: Autofill Event — Draft Community Group Report, 2026-03-04 (fetched 2026-08-30); chromestatus.com/feature/5137581018841088
Origin trial — surface may change, and this page’s earlier revision is superseded The event entered origin trial in Chrome 147 (this page’s milestone listing category) and remains experimental at trunk: Blink’s runtime_enabled_features.json5 lists AutofillEvent with status: "experimental", origin_trial_feature_name: "AutofillEvent", and third-party tokens allowed (fetched 2026-08-30). A token from developer.chrome.com/origintrials is required in production — and the ChromeStatus record lists no trial end milestone, so check the origin-trial console for the currently accepted window before relying on a token; without one, test behind chrome://flags/#enable-experimental-web-platform-features. The specification is a WICG Draft Community Group Report (2026-03-04) and has changed materially since this page was first written — the event was previously described here as firing on individual form controls after autofill completed; the current draft and the Blink implementation fire it at the document before values are committed. Everything below reflects the 2026-08-30 sources.

Syntax

Web IDL, verbatim from the spec’s IDL index (fetched 2026-08-30):

[Exposed=Window]
interface AutofillEvent : Event {
  constructor(DOMString type, optional AutofillEventInit eventInitDict = {});
  readonly attribute FrozenArray<AutofillValueEntry> autofillValues;
  readonly attribute RefillCallback? refill;
};

callback RefillCallback = Promise<undefined> ();

dictionary AutofillEventInit : EventInit {
  sequence<AutofillValueEntry> autofillValues = [];
  boolean allowRefill = true;
};

typedef sequence<any> AutofillValueEntry;
// AutofillValueEntry is a tuple of [HTMLElement, DOMString]

Divergence in Blink, disclosed: the shipping implementation’s autofill_event.idl at trunk (fetched 2026-08-30) has no constructor and types autofillValues as FrozenArray<AutofillFieldData>, where AutofillFieldData is a dictionary { Element field; DOMString value; } — a named-member object per entry, not the spec draft’s two-element tuple. Feature-detect the shape (entry.field vs entry[0]) rather than assuming either; the draft and implementation are still converging. The refill callback IDL matches the spec.

Source: spec IDL index; Blink autofill_event.idl, autofill_field_data.idl, autofill_refill_callback.idl — all fetched 2026-08-30.

why it exists

Autofill on dynamic forms is brittle: address forms in particular change shape by country (fields re-ordered, added, removed), but the browser fills the form as it existed when the user picked a suggestion. The entrenched workaround — hidden form fields that anticipate and capture values — is complex, and the same hidden-field technique is abused by bad actors. Firing an event before values are committed lets the page inspect what is about to be filled, adapt the form to fit (e.g. show country-specific fields), and — via refill() — ask the browser to fill again against the modified structure, paving a path away from hidden-field hacks.

Source: spec §1 Introduction and §1.1 Goals, fetched 2026-08-30.

the event contract

Firing and refill semantics (spec §3–§4)
FiringWhen the user selects values from the autofill UI, the user agent MUST fire autofill at the document before committing the values; the fill operation runs immediately after dispatch (§4.1, §4.3). type is "autofill", bubbles true, cancelable false.
autofillValuesThe entries the browser intends to fill — each pairs a form control with the profile value destined for it. Matching uses the control’s autocomplete attribute (HTML autofill field names) plus implementation-defined heuristics (§2.1). Only data the user agent already intends to fill into this page is exposed (§6).
refillNullable one-shot callback. Calling it returns a promise; the browser re-matches autofill data against the modified form, fires a retry autofill event (whose refill is null), and performs the fill (§4.2). refill is null on retry dispatches and whenever the user agent deems refilling inappropriate — the null-on-retry rule prevents infinite modify/refill loops (§3.1).
Refill errorsThe refill promise rejects with an InvalidStateError DOMException if called after the implementation-defined timeout since dispatch, if the event’s allow-refill flag is false, or if a refill is already pending (§4.2).
full-addressNew autofill field name: a control with autocomplete="full-address" asks the user agent (with permission) for the complete address data set, so the event can deliver fields the current form doesn’t yet show (§5).
Synthetic constructionThe spec IDL defines constructor(type, AutofillEventInit) with init members autofillValues (default []) and allowRefill (default true) so third-party autofill providers (password managers, extensions) can construct and dispatch structurally identical events (§3, §6.1). A synthetic event’s refill reflects allowRefill; entries follow the same element/value shape. Blink does not expose this constructor today (see the Syntax divergence note) — in Chrome’s origin trial only browser-fired events exist.
Consent & third partiesThe event SHOULD fire only after explicit user consent to autofill (picking a suggestion). Password managers and extensions can dispatch structurally identical AutofillEvents so pages behave consistently regardless of autofill source (§6, §6.1).
Source: spec §3, §4 Processing Model, §6 Security and Privacy, fetched 2026-08-30.

Examples

Adapting a form before the fill lands

// The event fires at the document, BEFORE values are committed.
document.addEventListener("autofill", async (event) => {
  let reshaped = false;
  for (const entry of event.autofillValues) {
    // Blink today: { field, value } dictionary; spec draft: [field, value] tuple.
    const field = entry.field ?? entry[0];
    const value = entry.value ?? entry[1];
    // field.autocomplete reflects the WHOLE token list (e.g.
    // "section-blue shipping country"): test the TERMINAL field token, and
    // keep the grouping prefix (section-* / shipping / billing) — a
    // "shipping address-level1" control must not suppress the billing one,
    // and the inserted control must join the country field's group so
    // refill can associate it with the right address. HTML's grammar also
    // allows a trailing "webauthn" token ("shipping country webauthn"):
    // strip it first, or it masquerades as the field token.
    const parseTokens = (list) => {
      const t = (list || "").trim().split(/\s+/);
      if (t.at(-1) === "webauthn") t.pop();
      return t;
    };
    const tokens = parseTokens(field.autocomplete);
    const group = tokens.slice(0, -1).join(" ");
    const hasPrefecture = [...(field.form?.elements ?? [])].some((el) => {
      const t = parseTokens(el.autocomplete);
      return t.at(-1) === "address-level1" && t.slice(0, -1).join(" ") === group;
    });
    if (tokens.at(-1) === "country" && value === "JP" && field.form && !hasPrefecture) {
      // Reshape the form for the incoming data — e.g. a prefecture field.
      // The absence guard matters: the retry event after refill() carries
      // the same country value, and must not append a second field. The
      // reshaped flag is set only after the insertion actually happens.
      const prefecture = document.createElement("input");
      const autofillName = group ? group + " address-level1" : "address-level1";
      prefecture.autocomplete = autofillName; // carries the group tokens
      prefecture.name = autofillName.replaceAll(" ", "-"); // submits with the form, unique per group
      prefecture.placeholder = "Prefecture";
      prefecture.setAttribute("aria-label", "Prefecture"); // accessible name — placeholder alone is not one
      field.form.append(prefecture);
      reshaped = true;
    }
  }

  // One-shot: ask the browser to re-run autofill against the modified form.
  // Only when the form was actually reshaped — a no-op refill just makes
  // every listener observe the fill twice. Null on retry dispatches. The
  // promise rejects with InvalidStateError after the implementation-defined
  // timeout, when allow-refill is false, or when a refill is already
  // pending — and EventTarget never consumes an async listener's promise,
  // so an uncaught rejection here would surface as unhandledrejection.
  if (reshaped && event.refill) {
    try {
      await event.refill();
    } catch (err) {
      // The initial fill still landed; only the re-run was declined.
      console.warn(`refill unavailable (${err.name}): ${err.message}`);
    }
  }
});

Requesting the complete address with full-address

<!-- autocomplete="full-address" (spec §5) asks the user agent, with
     permission, for the user's COMPLETE address data — including fields
     this form doesn't show yet — so the autofill event can deliver them
     and the page can build the right fields before the fill lands. -->
<form>
  <label for="address-field">Address</label>
  <input id="address-field" name="address" autocomplete="full-address">
  <label for="country-field">Country</label>
  <input id="country-field" name="country" autocomplete="country">
  <div id="dynamic-address-fields"></div>
</form>
Source: spec §5 The "full-address" Autocomplete Token (the §5 named in the snippet comment), fetched 2026-08-30

Placement note, disclosed: the spec’s normative sentence says “when a form control has the autocomplete attribute set to full-address”, so the token is shown on a control here — a <form> element’s own autocomplete attribute only accepts on/off in HTML’s autofill section. The draft’s own §5 example places it on the <form>, contradicting its normative text — a draft inconsistency, not a documented second syntax.

Synthetic construction (third-party autofill providers)

// Spec §3 + §6.1: a password manager or extension can construct and
// dispatch a structurally identical event so pages behave the same
// regardless of autofill source. NOT runnable against Chrome today —
// Blink's IDL exposes no constructor (divergence disclosed above);
// this is the draft's defined constructor surface, verbatim semantics.
const emailField = document.createElement("input");
emailField.autocomplete = "email";
emailField.setAttribute("aria-label", "Email"); // accessible name — autocomplete provides none
(document.forms[0] ?? document.body).append(emailField);
const event = new AutofillEvent("autofill", {
  bubbles: true, // match the browser-fired contract (bubbles, not cancelable)
  autofillValues: [[emailField, "user@example.com"]], // default []
  allowRefill: false,                                 // default true
});
document.dispatchEvent(event);
