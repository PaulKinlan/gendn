Autofill event

Limited availability

  • Chrome · origin trial (147+, experimental)
  • Edge · not shipped
  • Firefox · no signal
  • Safari · no signal

This API is not Baseline: it is a Chrome origin trial with no cross-browser implementation. webstatus.dev has no web-feature entry for the autofill event (the autofill web-feature there covers the general autocomplete mechanism, not this event; features API checked 2026-08-30), BCD has no AutofillEvent entry (raw path 404, 2026-08-30), MDN has no page, and the ChromeStatus record reports “No signal” from Firefox and Safari.

The autofill event fires at the Document when the browser is about to autofill form fields — before the values are committed. The event carries the list of element/value pairs the browser intends to fill (autofillValues) and, when permitted, a one-shot refill callback: the page can reshape its form to fit the incoming data (say, country-specific address fields) and ask the browser to run autofill again against the modified form.

Source: Autofill Event — Draft Community Group Report, 2026-03-04 (fetched 2026-08-30); chromestatus.com/feature/5137581018841088
Origin trial — surface may change, and this page’s earlier revision is superseded The event entered origin trial in Chrome 147 (this page’s milestone listing category) and remains experimental at trunk: Blink’s runtime_enabled_features.json5 lists AutofillEvent with status: "experimental", origin_trial_feature_name: "AutofillEvent", and third-party tokens allowed (fetched 2026-08-30). A token from developer.chrome.com/origintrials is required in production; without one, test behind chrome://flags/#enable-experimental-web-platform-features. The specification is a WICG Draft Community Group Report (2026-03-04) and has changed materially since this page was first written — the event was previously described here as firing on individual form controls after autofill completed; the current draft and the Blink implementation fire it at the document before values are committed. Everything below reflects the 2026-08-30 sources.

Syntax

Web IDL, verbatim from the spec’s IDL index (fetched 2026-08-30):

[Exposed=Window]
interface AutofillEvent : Event {
  constructor(DOMString type, optional AutofillEventInit eventInitDict = {});
  readonly attribute FrozenArray<AutofillValueEntry> autofillValues;
  readonly attribute RefillCallback? refill;
};

callback RefillCallback = Promise<undefined> ();

dictionary AutofillEventInit : EventInit {
  sequence<AutofillValueEntry> autofillValues = [];
  boolean allowRefill = true;
};

typedef sequence<any> AutofillValueEntry;
// AutofillValueEntry is a tuple of [HTMLElement, DOMString]

Divergence in Blink, disclosed: the shipping implementation’s autofill_event.idl at trunk (fetched 2026-08-30) has no constructor and types autofillValues as FrozenArray<AutofillFieldData>, where AutofillFieldData is a dictionary { Element field; DOMString value; } — a named-member object per entry, not the spec draft’s two-element tuple. Feature-detect the shape (entry.field vs entry[0]) rather than assuming either; the draft and implementation are still converging. The refill callback IDL matches the spec.

Source: spec IDL index; Blink autofill_event.idl, autofill_field_data.idl, autofill_refill_callback.idl — all fetched 2026-08-30.

why it exists

Autofill on dynamic forms is brittle: address forms in particular change shape by country (fields re-ordered, added, removed), but the browser fills the form as it existed when the user picked a suggestion. The entrenched workaround — hidden form fields that anticipate and capture values — is complex, and the same hidden-field technique is abused by bad actors. Firing an event before values are committed lets the page inspect what is about to be filled, adapt the form to fit (e.g. show country-specific fields), and — via refill() — ask the browser to fill again against the modified structure, paving a path away from hidden-field hacks.

Source: spec §1 Introduction and §1.1 Goals, fetched 2026-08-30.

the event contract

Firing and refill semantics (spec §3–§4)
FiringWhen the user selects values from the autofill UI, the user agent MUST fire autofill at the document before committing the values; the fill operation runs immediately after dispatch (§4.1, §4.3). type is "autofill", bubbles true, cancelable false.
autofillValuesThe entries the browser intends to fill — each pairs a form control with the profile value destined for it. Matching uses the control’s autocomplete attribute (HTML autofill field names) plus implementation-defined heuristics (§2.1). Only data the user agent already intends to fill into this page is exposed (§6).
refillNullable one-shot callback. Calling it returns a promise; the browser re-matches autofill data against the modified form, fires a retry autofill event (whose refill is null), and performs the fill (§4.2). refill is null on retry dispatches and whenever the user agent deems refilling inappropriate — the null-on-retry rule prevents infinite modify/refill loops (§3.1).
Refill errorsThe refill promise rejects with an InvalidStateError DOMException if called after the implementation-defined timeout since dispatch, if the event’s allow-refill flag is false, or if a refill is already pending (§4.2).
full-addressNew autofill field name: a control with autocomplete="full-address" asks the user agent (with permission) for the complete address data set, so the event can deliver fields the current form doesn’t yet show (§5).
Consent & third partiesThe event SHOULD fire only after explicit user consent to autofill (picking a suggestion). Password managers and extensions can dispatch structurally identical AutofillEvents so pages behave consistently regardless of autofill source (§6, §6.1).
Source: spec §3, §4 Processing Model, §6 Security and Privacy, fetched 2026-08-30.

Examples

Adapting a form before the fill lands

// The event fires at the document, BEFORE values are committed.
document.addEventListener("autofill", async (event) => {
  for (const entry of event.autofillValues) {
    // Blink today: { field, value } dictionary; spec draft: [field, value] tuple.
    const field = entry.field ?? entry[0];
    const value = entry.value ?? entry[1];
    if (field.autocomplete === "country" && value === "JP") {
      addJapaneseAddressFields(); // reshape the form for the incoming data
    }
  }

  // One-shot: ask the browser to re-run autofill against the modified form.
  // Null on retry dispatches, and rejects with InvalidStateError after the
  // implementation-defined timeout or if a refill is already pending.
  if (event.refill) {
    await event.refill();
  }
});

The ChromeStatus record’s own runnable samples are Yoav Weiss’s autofill event demo and credit-card autofill demo (both HTTP 200, 2026-08-30).
