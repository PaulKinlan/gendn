Autofill event

Limited availability

  • Chrome · origin trial (147)
  • Edge · not separately reported
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register — no web-features entry in the webstatus.dev feature query (the register’s autofill entry is the unrelated :autofill CSS pseudo-class). Chrome 147 listed this as an origin trial per the chromestatus milestone-147 listing; the current feature detail (chromestatus API, updated 2026-02-28) records no ship milestone, Chrome implementation status “Proposed” (browsers.chrome.status), and standards maturity “Incubation” (standards.maturity — WICG Community Group). Firefox (mozilla/standards-positions#1361) and Safari (WebKit/standards-positions#431) have open position requests with no signal.

A new autofill event, dispatched at the document when the browser is about to run an autofill operation. The event carries the list of form controls and values that will be filled (autofillValues) and a refill() callback, letting pages adapt dynamic forms to the autofilled data — for example adding a state selector for a US address — and then ask the browser to run one more fill pass over the updated form.

Origin trial — API surface may move

The Autofill event is experimental. Chrome 147’s milestone listing carries it as an origin trial; the feature detail currently records no active trial registration and no ship estimate (Chrome implementation status “Proposed”, updated 2026-02-28). To use it:

  • Check for a registerable “Autofill event” trial at developer.chrome.com/origintrials (origin-trial feature name AutofillEvent, third-party tokens allowed).
  • For local development: launch Chrome with --enable-blink-features=AutofillEvent (runtime-enabled feature AutofillEvent, status “experimental”, so chrome://flags/#enable-experimental-web-platform-features also enables it).
  • Feature-detect with typeof AutofillEvent !== "undefined" before relying on it.

why it exists

Getting autofill to work reliably with dynamic forms is hard: the browser matches a user’s profile against the form as it exists at fill time, so fields the page adds in response to earlier values (a state dropdown once the country is known, a card-type field once the number prefix is known) get missed, and pages had no reliable signal that an autofill pass happened at all. The autofill event gives the page the full set of control/value pairs the browser is about to fill, a chance to restructure the form to fit that data, and — via refill() — a way to tell the browser the form changed so it can run one more pass over the updated structure.

Source: ChromeStatus summary; WICG explainer

Syntax

IDL from the WICG draft:

[Exposed=Window]
interface AutofillEvent : Event {
  constructor(DOMString type, optional AutofillEventInit eventInitDict = {});
  readonly attribute FrozenArray<AutofillValueEntry> autofillValues;
  readonly attribute RefillCallback? refill;
};

callback RefillCallback = Promise<undefined> ();

dictionary AutofillEventInit : EventInit {
  sequence<AutofillValueEntry> autofillValues = [];
  boolean allowRefill = true;
};

typedef sequence<any> AutofillValueEntry;
// AutofillValueEntry is a tuple of [HTMLElement, DOMString]
// where the first element is the form control and the second is the value to fill

Members
MemberContract
AutofillEvent(type, eventInitDict)Constructor for synthesizing the event: takes the event type string (use "autofill") and an optional AutofillEventInit (default {}); returns an AutofillEvent whose autofillValues is the frozen form of the init’s list and whose refill is populated per allowRefill. Standard EventInit members (bubbles, cancelable, composed) apply via inheritance.
autofillValuesFrozen array of [HTMLElement, DOMString] tuples — each form control that will receive an autofilled value, paired with the value from the user’s autofill profile. The user agent matches controls to profile data before firing.
refillNullable callback. After modifying the form to fit the incoming data, call it to signal the form has been updated and have the user agent retry the autofill operation against the new structure; it returns a Promise<undefined> that resolves after the retry dispatch and re-fill. It rejects with an “InvalidStateError” DOMException if called after the implementation-defined refill timeout, if allowRefill was false, or if a refill is already pending (§4.2). On the second dispatch of the event (after form modifications) the attribute is null, preventing infinite refill loops — though a reference captured from the first event stays callable and settles per the rejection rules above.
AutofillEventInit.autofillValuesConstructor-dictionary seed list (default []) of [HTMLElement, DOMString] entries for a synthesized event — how browser extensions and third-party autofill providers construct structurally identical events so pages behave consistently regardless of the autofill source.
AutofillEventInit.allowRefillConstructor-dictionary flag (default true) controlling whether the synthesized event carries a refill callback.
Source: WICG Autofill Event — §2 Concepts, §3 The AutofillEvent Interface, §4 Processing Model

Neither attribute getter throws, but refill() has defined failure settlements (§4.2): the returned promise rejects with an “InvalidStateError” DOMException when the call comes after the implementation-defined refill timeout (measured from the event’s dispatch timestamp), when the event’s allow-refill flag is false, or when a refill is already pending (a repeat call). Nulling the refill attribute on the retry dispatch only affects that second event object — a callback reference captured from the first event (for example const refill = event.refill) remains invocable, and a late or repeated call through it settles as one of those rejections rather than being impossible. Handle the rejection instead of assuming it cannot occur. The constructor is still subject to standard Web IDL argument conversion: passing a non-iterable autofillValues (for example new AutofillEvent("autofill", { autofillValues: 1 })) or an otherwise unconvertible init member throws a TypeError at construction, exactly as for any dictionary-taking DOM constructor. For the user-agent-dispatched event, feature-detect the interface rather than wrapping listeners in try/catch.

Examples

The spec’s motivating pattern — add a country-dependent field, then ask for a refill:

document.addEventListener('autofill', async (event) => {
  // Find the country value among the incoming [element, value] pairs
  let countryValue = null;
  for (const [element, value] of event.autofillValues) {
    if (element.autocomplete === 'country') { countryValue = value; break; }
  }

  // US addresses need a state selector this form doesn't have yet
  if (event.refill && countryValue === 'US') {
    addStateSelector();        // modify the form to fit the data
    try {
      await event.refill();    // ask the browser to fill the updated form
    } catch (err) {
      // InvalidStateError: refill timeout elapsed, refill disallowed, or a
      // refill is already pending (spec §4.2). The listener's returned
      // promise is ignored by the event system, so catch it here.
      console.warn('refill rejected:', err.name);
    }
  }
});
Source: condensed from the example in WICG Autofill Event — §1.2 Example; Chrome’s sample demos: autofill event demo, credit-card demo

Constructing the event yourself — for example to exercise an autofill listener in a test without a real browser fill. Both AutofillEventInit members and their spec defaults (autofillValues = [], allowRefill = true) come from the IDL quoted in the Syntax section; each AutofillValueEntry is a [formControl, valueToFill] pair:

const nameField  = document.querySelector('input[autocomplete="name"]');
const emailField = document.querySelector('input[autocomplete="email"]');

const event = new AutofillEvent('autofill', {
  bubbles: true,                          // UA-fired autofill events bubble (spec §4.1)
  autofillValues: [                       // sequence<AutofillValueEntry>, default []
    [nameField,  'Ada Lovelace'],
    [emailField, 'ada@example.com'],
  ],
  allowRefill: true,                      // boolean, default true
});

document.dispatchEvent(event);            // the UA dispatches at the Document (spec §4.1)

A synthetic event carries your autofillValues but does not make the browser fill anything — only user-agent-fired events are backed by a real fill operation, and the refill machinery (§4.2) responds to the user agent’s own dispatch.

Source: constructor and AutofillEventInit IDL (member defaults) from WICG Autofill Event — §3 The AutofillEvent Interface; dispatch/bubbles behavior from §4.1 Firing the Autofill Event (fetched 2026-07-26)

Security and privacy

The event exposes autofill values to JavaScript before they are committed to form fields, so the spec directs user agents to fire it only after explicit user consent to autofill (for example, selecting a suggestion from the dropdown), and to limit the data to what the user agent intends to fill into this page’s form — the API shape keys every value to a concrete element. After a refill(), the form likely contains new fields the user has not seen; the user agent should still weigh user consent before filling them. Browser extensions and third-party autofill providers (password managers) can dispatch structurally identical AutofillEvents so pages behave consistently regardless of the autofill source.

Source: WICG Autofill Event — §6 Security and Privacy Considerations, §6.1 Third-Party Autofill Providers
