AutofillEvent.refill()

The nullable callback carried by a user-agent-fired autofill event. After restructuring the form to fit the incoming autofillValues, calling it asks the browser to re-match the user’s autofill data against the updated form and run one more fill pass. It returns a Promise<undefined> with three defined “InvalidStateError” rejection paths.

Origin trial — API surface may move

Same availability as the parent interface: Chrome 147 origin trial per the milestone-147 listing, behind the AutofillEvent runtime flag for local development. The callback is only meaningful on user-agent-dispatched events — see Lifecycle for the synthetic-event caveat. Exposure: Window, via AutofillEvent (chromestatus.com/feature/5137581018841088).

Syntax

// IDL (WICG draft, verbatim)
readonly attribute RefillCallback? refill;
callback RefillCallback = Promise<undefined> ();

// Usage
if (event.refill) {
  await event.refill();
}

The attribute is nullable: it is a function when the event’s allow-refill flag is true and the event is the first dispatch; it is null on the retry dispatch (see Lifecycle) and on synthetic events constructed with allowRefill: false.

Source: WICG Autofill Event — §3 The AutofillEvent Interface (IDL, verbatim)

Inputs

None. RefillCallback takes no arguments — the user agent already holds the event’s associated document and re-derives the fill data itself: the processing steps compute “the updated autofill value entries (re-matching the user’s autofill data against the modified form)”. The effective input is the current DOM state of the form at call time, which is why you restructure the form before calling.

Source: WICG Autofill Event — §4.2 Processing a Refill Request

Outputs

A Promise<undefined>. On success the user agent, in parallel: re-matches the autofill data, queues a task to fire a second autofill event (with allowRefill false, so its refill attribute is null), performs the fill on the updated form, and then resolves the promise with undefined. Resolution therefore signals that the retry dispatch and re-fill have happened — there is no fill data in the resolution value itself.

Source: WICG Autofill Event — §4.2 (return promise, parallel steps, resolve with undefined)

Errors

Rejection paths — all reject the returned promise with an “InvalidStateError” DOMException
ConditionSpec rule (§4.2)
Called after the refill timeoutIf elapsed time since the event’s dispatch timestamp exceeds an implementation-defined refillTimeout, reject. The timeout balances responsiveness against giving pages time to restructure; no numeric value is standardized.
Refill disallowedIf the event’s allow-refill flag is false, reject. (On UA-fired retry dispatches the attribute is also null, but a captured reference still hits this rule.)
Refill already pendingIf the event’s refill pending flag is already true — a repeat call on the same event object, including through a captured reference — reject.

Nothing throws synchronously; all three failures settle the returned promise. Because the event system ignores the promise an async listener returns, an unhandled rejection here surfaces as an unhandledrejection — wrap the call in try/catch (or .catch()).

Source: WICG Autofill Event — §4.2 (the three reject steps and the timeout note, quoted semantics)

Lifecycle

  • First dispatch: the UA fires autofill at the document with allow-refill true; refill is a callable function. The clock for the refill timeout starts at the event’s dispatch timestamp.
  • Successful call: sets the event’s refill pending flag (blocking repeats), re-matches data, fires the retry dispatch with allow-refill false, performs the fill, resolves the promise.
  • Retry dispatch: the second event’s refill attribute is null, preventing infinite refill loops.
  • Captured references: nulling the attribute only affects the second event object. A reference captured from the first event (const refill = event.refill) remains invocable; a late or repeat call through it settles with one of the rejections above rather than being impossible.
  • Synthetic events: a page-constructed AutofillEvent carries a refill per its allowRefill init, but only user-agent-fired events are backed by a real fill operation — the refill machinery responds to the UA’s own dispatch, not to script dispatch.
Source: §4.1 Firing the Autofill Event; §4.2 Processing a Refill Request; §3.1 Attributes (refill pending flag, dispatch timestamp)

Examples

document.addEventListener('autofill', async (event) => {
  const needsRestructure = adaptFormTo(event.autofillValues);

  if (needsRestructure && event.refill) {
    try {
      await event.refill();   // resolves after the retry dispatch + re-fill
    } catch (err) {
      // InvalidStateError: timeout elapsed, refill disallowed, or already pending.
      console.warn('refill rejected:', err.name);
    }
  }
});

Restructure synchronously (or as fast as possible) before calling — the implementation-defined timeout runs from the event’s dispatch, so long awaits before refill() risk the timeout rejection. The parent page’s Examples section shows the full country→state-selector pattern and a live embedded demo.

Source: pattern composed from WICG Autofill Event — §1.2 Example and the §4.2 settlement rules

Security and privacy

The callback itself adds no data exposure beyond the parent event: it returns no fill values, and the re-fill it triggers flows through the same §4.1 firing steps (a fresh event carries the re-matched autofillValues). The spec’s security considerations for the interface apply unchanged — autofill values reveal stored personal data to the page, which is the parent event’s disclosure, not a new one introduced by refill(). The repeat-call and timeout rejections bound how often a page can make the UA re-run matching.

Source: WICG Autofill Event — §6 Security and Privacy; rejection bounds from §4.2
