AutofillEvent.refill

Limited availability

  • Chrome · origin trial 147–152
  • Edge · not available
  • Firefox · no signal
  • Safari · no signal

Chrome origin trial only (Intent to Experiment, milestones 147–152); no Baseline or BCD entry — see browser compatibility. Android WebView does not yet support autofill retriggering (ChromeStatus) — expect refill to be null there.

The read-only refill attribute of the AutofillEvent interface returns a RefillCallback — or null. Calling the callback tells the user agent the page has restructured its form in response to the announced values and asks it to run one more fill pass over the modified form, within an implementation-defined time window.

Origin trial — surface may move

Part of the Autofill event origin trial (Chrome 147–152); see the feature page’s enable steps (trial name AutofillEvent, or --enable-blink-features=AutofillEvent). The refill timeout is deliberately implementation-defined; do not hard-code timing assumptions.

Syntax

// WebIDL (specification):
readonly attribute RefillCallback? refill;
callback RefillCallback = Promise<undefined> ();

// Call form — always null-check first:
if (event.refill !== null) {
  await event.refill();
}
Source: spec §3 The AutofillEvent Interface.

Value

A RefillCallback, or null. The spec makes refill null when:

  • the event is dispatched as a retry after a previous call to refill (this is what prevents infinite fill loops), or
  • the user agent determines that refilling is not appropriate for this autofill operation.

The explainer gives concrete cases for the second bullet: the browser may not support refills for the kind of data being filled (for example supporting refills for addresses but not for banking details), and Android WebView does not support retriggering at all.

Source: spec §3.1 Attributes; explainer — refill semantics; ChromeStatus — WebView note.

The RefillCallback

Syntaxcallback RefillCallback = Promise<undefined> (); — invoked as event.refill().
ParametersNone — the callback takes no arguments; the user agent re-matches the user’s already-selected autofill data against the current form structure on its own.
Return valueA Promise<undefined>. On success the user agent fires a fresh autofill event (with updated entries and refill = null), performs the fill on the modified form, and then resolves the promise with undefined.
RejectionsAll three documented failure modes reject with an "InvalidStateError" DOMException: (1) the elapsed time since the event’s dispatch timestamp exceeds the implementation-defined refillTimeout; (2) the event’s allow refill flag is false (retry dispatches, or a synthetic event constructed with allowRefill: false); (3) the event’s refill pending flag is already true (a second call on the same event). The explainer adds that an implementation may also decline a refill — rejecting the promise — if the form changed too substantially.
ContextOnly meaningful on a user-agent-fired event, inside or shortly after the autofill listener, within the timeout window. The spec’s guidance: user agents SHOULD choose a timeout that balances responsiveness with giving pages adequate time to call refill.
LifecycleFirst call flips the event’s refill pending flag and, in parallel, re-matches entries and queues a task that fires the retry autofill event (with allowRefill = false), performs the fill, and resolves the promise. Subsequent calls on the same event reject. Exactly one retry per user-initiated fill is possible.
Source: spec §4.2 Processing a Refill Request; explainer — programmatic refills.

Context and exposure

Available on AutofillEvent instances in Window contexts ([Exposed=Window]). In Chrome 147–152 the interface exists only with the origin-trial token or the AutofillEvent Blink feature enabled. On a synthetic (page-constructed) event, refill is not wired to the user agent’s autofill machinery — only events fired by the §4.1 algorithm can actually trigger a browser refill.

Source: spec §3–4; ChromeStatus — Autofill event (5137581018841088).

Lifecycle and state transitions

DispatchEvent fires with dispatch timestamp set to the current high-resolution time, allow refill = true, refill pending = false.
Window openThe page may call refill() until the implementation-defined timeout elapses (measured from the dispatch timestamp).
Refill requestedrefill pending → true; entries re-matched in parallel against the modified form.
Retry dispatchA new autofill event fires with the updated entries and allow refill = false (so its refill is null); the fill is performed; the original promise resolves.
TerminalNo further refills for this autofill operation — a fresh user-initiated autofill starts the cycle again.

Examples

Restructure, then request the second pass (null-check first — retry dispatches and unsupported fills have refill === null):

document.addEventListener("autofill", async (event) => {
  if (event.refill === null) return; // retry pass, or refill unsupported

  const changed = adaptFormTo(event.autofillValues);
  if (!changed) return; // nothing to redo — don't burn the one refill

  try {
    await event.refill();
    // Resolved: the browser refilled the modified form and fired a
    // second autofill event (with refill === null) before this point.
  } catch (err) {
    // InvalidStateError: too slow (timeout), already pending, or not allowed.
    console.warn("refill declined:", err.name);
  }
});

Guarding against a double call on the same event:

let refillRequested = false;
document.addEventListener("autofill", async (event) => {
  if (event.refill && !refillRequested) {
    refillRequested = true;      // second call would reject anyway
    await event.refill();
  }
});
Source: patterns derived from spec §1.2 Example and §4.2; explainer — example code.

Security and privacy

Refill is rate- and scope-limited by design: one retry per fill (the pending flag and the nulled refill on retry dispatches prevent loops), a browser-controlled timeout bounds how long a page can hold the capability, and the user agent may decline entirely. Because the retried form “is likely to include new fields that weren’t present the first time the user agent filled the form”, the spec directs user agents to still consider user consent before filling those new fields. The explainer’s open questions flag the cross-frame angle — whether refill() is limited to the calling frame and whether simultaneous cross-origin refills could communicate information — as unresolved.

Source: spec §6 Security and Privacy Considerations; explainer — open questions.
