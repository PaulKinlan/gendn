AutofillEvent.autofillValues

Limited availability

  • Chrome · origin trial 147–152
  • Edge · not available
  • Firefox · no signal
  • Safari · no signal

Chrome origin trial only (Intent to Experiment, milestones 147–152); no Baseline or BCD entry — see browser compatibility.

The read-only autofillValues attribute of the AutofillEvent interface returns the frozen list of autofill value entries — [HTMLElement, DOMString] tuples pairing each form control with the value the user agent is about to fill into it.

Origin trial — surface may move

Part of the Autofill event origin trial (Chrome 147–152); see the feature page’s enable steps (trial name AutofillEvent, or --enable-blink-features=AutofillEvent). The explainer still names this property values and allows boolean entries for checkboxes/radios — the published spec says autofillValues with DOMString values. This page follows the spec.

Syntax

// WebIDL (specification):
readonly attribute FrozenArray<AutofillValueEntry> autofillValues;

// Access form:
const entries = event.autofillValues;
for (const [element, value] of entries) { /* ... */ }
Source: spec §3 The AutofillEvent Interface.

Value

A FrozenArray<AutofillValueEntry> — a frozen (immutable) array, per WebIDL FrozenArray semantics, of autofill value entries. The spec: “Each entry is a tuple where the first element is an HTMLElement (the form control to be filled) and the second element is a DOMString (the value to fill).” For a user-agent-fired event the list is the set of controls the user’s selected autofill profile matched; for a constructed event it is whatever AutofillEventInit.autofillValues supplied (default []).

Source: spec §3.1 Attributes, §2.1 Autofill Value Entries.

The AutofillValueEntry tuple

Syntaxtypedef sequence<any> AutofillValueEntry; — by convention a two-element tuple: entry[0] is the HTMLElement, entry[1] is the DOMString value. Destructure as const [element, value] = entry;
InputsNot applicable as a callable surface — the tuple is a data shape produced by the user agent (or by AutofillEventInit.autofillValues for synthetic events), never invoked by the developer; its producers are documented under value.
Element / value semanticsentry[0] is typed HTMLElement rather than HTMLInputElement | HTMLSelectElement | HTMLTextAreaElement because contenteditable hosts and form-associated custom elements can also be autofilled (explainer). entry[1] is the value the user agent intends to fill — see lifecycle for why the control may not end up holding it.
ErrorsNone defined — reading entries never throws. Because the containing array is frozen, mutating it (e.g. entries.push(…)) throws TypeError in strict mode per ordinary frozen-object semantics (WebIDL).
ContextAppears in two places: the event’s autofillValues attribute and the AutofillEventInit.autofillValues dictionary member. Matching of controls to profile data uses the control’s autocomplete attribute (HTML autofill field names) plus implementation-defined heuristics.
LifecycleEntries are a snapshot taken when the event is fired — before the fill. It is not guaranteed the element actually has that value afterwards: the explainer’s examples include a handler changing/removing the element, an <input maxlength> truncating the value, a non-color value for <input type=color>, or a <select> with no matching <option>. On a refill, the user agent re-matches and fires a fresh event with updated entries.
Source: spec §2.1, §4.2; explainer — JavaScript interface.

Context and exposure

Available on AutofillEvent instances only, in Window contexts ([Exposed=Window]) — the event is dispatched at the Document. In Chrome 147–152 the attribute exists only with the origin-trial token or the AutofillEvent Blink feature enabled; feature-detect with typeof AutofillEvent !== "undefined" before relying on it.

Source: spec §3, §4.1; ChromeStatus — Autofill event (5137581018841088).

Lifecycle

The list is set by the firing algorithm (“Set event’s autofill values list to entries”) before dispatch and never changes for the lifetime of the event object. A refill does not mutate the original event — it queues a new autofill event whose entries are “the updated autofill value entries (re-matching the user’s autofill data against the modified form)”. Read the values synchronously in the listener; holding the array across the fill is safe (it is frozen) but the DOM elements it references may have changed.

Source: spec §4.1–4.2 Processing Model.

Examples

Find the country the browser is about to fill, without touching any field values:

document.addEventListener("autofill", (event) => {
  for (const [element, value] of event.autofillValues) {
    if (element.autocomplete === "country") {
      updateShippingPreview(value); // e.g. show duties/taxes hint
    }
  }
});

Defensive iteration — the entries are a pre-fill snapshot, so re-check the DOM afterwards:

document.addEventListener("autofill", (event) => {
  const snapshot = event.autofillValues; // FrozenArray — safe to keep
  queueMicrotask(() => {
    for (const [element, intended] of snapshot) {
      if (element.isConnected && element.value !== intended) {
        // maxlength clamp, unmatched <option>, or a handler changed it
        revalidate(element);
      }
    }
  });
});
Source: patterns derived from spec §1.2, §2.1 and the explainer’s value-divergence list.

Security and privacy

This attribute is the disclosure surface of the whole feature: it exposes profile values to script before they are committed to fields. The spec’s bounds: the event SHOULD only fire after explicit user consent to autofill, and the data “is limited to data that the user agent intends to fill into forms on the page, given that the API shape requires an element as the key to the autofill values” — a page cannot enumerate profile data it has no matching control for, except via the permission-mediated "full-address" token.

Source: spec §6 Security and Privacy Considerations.
