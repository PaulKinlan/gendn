Sec-CH-Device-Memory

Limited availability

  • Chrome · 97+ (legacy Device-Memory alias since 61); new buckets from 147
  • Edge · 97+ (mirrors Chrome per BCD)
  • Firefox · not implemented
  • Safari · not implemented

Part of the device-memory web feature, Baseline status limited (Chromium-only); BCD marks the header experimental. Chrome 147 changes the values the hint can carry — see the feature overview.

Sec-CH-Device-Memory is an HTTP Client Hint request header that advertises the device's approximate RAM in GiB — the same bucketed value as navigator.deviceMemory — to servers that opt in with Accept-CH. From Chrome 147 the possible values are 1, 2, 4, 8 on Android and 2, 4, 8, 16, 32 everywhere else.

Syntax

# ABNF (specification, verbatim) — a structured-field decimal:
Sec-CH-Device-Memory = sf-decimal

# On the wire:
Sec-CH-Device-Memory: 8

If the header occurs in a message more than once, the last value overrides all previous occurrences.

Source: spec §3 Sec-CH-Device-Memory (Client Hint) Header Field.

Opting in (server side)

Like all high-entropy client hints, the header is not sent by default. A server requests it with the Accept-CH response header, or the equivalent HTML <meta http-equiv> element:

Accept-CH: Sec-CH-Device-Memory

On subsequent requests to that (secure) origin, a compatible browser then advertises the device memory bucket. There is nothing to configure client-side; the page cannot alter the value.

Source: spec §3.1 Client Hint examples.

Value

A structured-field decimal set to the user agent's deviceMemory: physical RAM in GiB rounded to the nearest power of two and clamped to implementation-defined bounds. In Chrome 147+ that means 1, 2, 4, or 8 on Android and 2, 4, 8, 16, or 32 elsewhere (previously 0.25–8 on all platforms). Servers must parse it as a decimal — historic values are fractional — and must not reject values outside today's set: the bounds change over time, and mis-handling unexpected values is exactly what broke x.com logins during this change's beta rollout.

Source: spec §3; spec §2; Intent to Ship thread (x.com incident, 2026-02-13).

Failure modes

There is no error channel: the hint is simply absent when the server has not opted in, when the connection is not HTTPS, when the browser does not implement the API (Firefox, Safari), or on a first request before Accept-CH has been seen. Server logic must therefore treat the header as optional and fall back to a default experience — never gate a response on its presence or on a closed set of values.

Source: spec §3; spec §5 (HTTPS-only); BCD http/headers/Sec-CH-Device-Memory.json.

Lifecycle

First requestNo hint — the browser has not yet seen the origin's Accept-CH.
After opt-inThe browser remembers the origin's hint preferences and attaches the header to subsequent secure requests for as long as the preference is retained.

DuplicatesIf the field occurs more than once in a message, the last occurrence wins (spec §3).

the legacy Device-Memory header

Chrome has sent this hint under the unprefixed name Device-Memory since Chrome 61 — before the Sec-CH- convention existed. BCD records it as deprecated and non-standard (the current spec defines only Sec-CH-Device-Memory), but Chrome still supports it, and its values changed in Chrome 147 identically:

SyntaxDevice-Memory: 8 — same decimal value as Sec-CH-Device-Memory, under the legacy name. Not defined in the current specification text.
Opt-inSame client-hints mechanism: the server requests it by name, Accept-CH: Device-Memory, over HTTPS.
ValueThe user agent's bucketed deviceMemory: from Chrome 147, 1–8 on Android and 2–32 elsewhere; 0.25–8 before (BCD notes record the same 147 change on this key).
Failure modesSame as the prefixed header: absent without opt-in, on insecure transport, or in non-Chromium browsers; no error channel. Lacking the Sec- prefix, it is not a forbidden header name, so it is spoofable in scripted requests — another reason not to trust it for anti-abuse decisions.
StatusDeprecated, non-standard (BCD "deprecated": true, "standard_track": false). Chrome 61+, Edge 79+, never in Firefox/Safari. Tracked by its own use counter as the “deprecated name”.
MigrationPrefer Sec-CH-Device-Memory for new code (Chrome 97+). Servers currently reading Device-Memory keep working, but should accept both names and expect the value set to keep evolving. No removal milestone is announced.
Source: BCD http/headers/Device-Memory.json (fetched 2026-09-13); MDN: Device-Memory header; Chrome use counter — Client Hints (deprecated name).

Examples

The specification's opt-in exchange, verbatim (values updated to a Chrome 147 desktop bucket):

# Server response — opt in to the hint (or use an equivalent
# <meta http-equiv="Accept-CH" content="Sec-CH-Device-Memory">):
HTTP/1.1 200 OK
Accept-CH: Sec-CH-Device-Memory

# Subsequent browser request:
GET /example HTTP/1.1
Sec-CH-Device-Memory: 32

Accepting both the current and the legacy Device-Memory name robustly on the server (values are decimals; the set changes over time):

// Node.js / Express
function deviceMemoryGiB(req) {
  const raw = req.get("Sec-CH-Device-Memory") ?? req.get("Device-Memory");
  const mem = Number.parseFloat(raw);
  return Number.isFinite(mem) && mem > 0 ? mem : undefined;
}

app.get("/example", (req, res) => {
  res.set("Accept-CH", "Sec-CH-Device-Memory");
  const mem = deviceMemoryGiB(req);
  // Threshold logic only — never an allowlist of known values.
  res.render(mem !== undefined && mem <= 2 ? "lite" : "full");
});
Source: spec §3.1 Client Hint examples (exchange verbatim; server snippet is this reference's own, applying the spec's parsing rules).

Security and privacy

  • HTTPS only. The hint is never sent over insecure transport (spec §5).
  • Opt-in by design. Servers must explicitly request it via Accept-CH; it is not broadcast by default, which limits passive fingerprinting.
  • Coarsened value. Same single-significant-bit rounding and clamped bounds as the JavaScript API; Chrome 147's bound changes reduce low-end fingerprinting entropy.
  • Sec- prefix. The prefixed name cannot be set by page JavaScript, so servers can trust it was produced by the browser — unlike the legacy Device-Memory name (see above).
Source: spec §5 Security & privacy considerations; spec §6.1.
