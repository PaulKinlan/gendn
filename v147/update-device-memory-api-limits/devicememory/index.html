v147 · device memory api · property

navigator.deviceMemory

Limited availability

  • Chrome · 63+ (window), 65+ (workers); new buckets from 147
  • Edge · 79+ (mirrors Chrome per BCD)
  • Firefox · not implemented
  • Safari · not implemented

Part of the device-memory web feature, Baseline status limited (Chromium-only). Chrome 147 changes the values this property can return — see the feature overview.

navigator.deviceMemory returns the approximate amount of device RAM in GiB, coarsened to a privacy-preserving bucket. From Chrome 147 the possible values are 1, 2, 4, 8 on Android and 2, 4, 8, 16, 32 everywhere else. Available in both window and worker contexts.

Syntax

// WebIDL (specification, verbatim):
[
  SecureContext,
  Exposed=(Window,Worker)
] interface mixin NavigatorDeviceMemory {
  readonly attribute double deviceMemory;
};
Navigator includes NavigatorDeviceMemory;
WorkerNavigator includes NavigatorDeviceMemory;

// Read forms:
const mem = navigator.deviceMemory;       // in a window
const mem = self.navigator.deviceMemory;  // in a worker
Source: spec §4 Device Memory JavaScript API.

Value

A read-only double: the device's physical RAM in GiB, rounded to the nearest power of two (a single significant bit) and clamped to implementation-defined bounds. The property takes no parameters and cannot be set; everything about the returned number is determined by the hardware and the browser's bounds. In Chrome 147+ the possible values are:

Android1, 2, 4, 8
Desktop and other platforms2, 4, 8, 16, 32
Before Chrome 147 (all platforms)0.25, 0.5, 1, 2, 4, 8

The bounds are explicitly implementation-defined and subject to change; do not treat any value set as exhaustive. Fractional values (like the retired 0.25) are valid doubles, so parse accordingly if the value is serialized.

Source: spec §2 Computing device memory value; approximated_device_memory.cc (M147 branch, bounds verbatim).

Exceptions

None. The getter never throws in a supporting browser — the spec's getter steps are simply to return the user agent's precomputed deviceMemory. In browsers that do not implement the API (Firefox, Safari), and in non-secure contexts in supporting browsers (the mixin is [SecureContext]), the property is undefined; reading it is not an error, so feature-detect with an undefined check rather than try/catch.

Source: spec §4; BCD api/Navigator.json (Firefox/Safari version_added: false).

Context and exposure

ReceiversNavigator and WorkerNavigator — the NavigatorDeviceMemory mixin is included in both, so the value is readable from documents and from dedicated/shared/service workers.
Exposure[Exposed=(Window,Worker)].
Secure contextRequired ([SecureContext]): HTTPS pages only, per the spec's security section (“will only be available to HTTPS secure contexts”).
PermissionsNone — no prompt, no permissions policy gate defined by this specification.
PlatformsChromium browsers only. In Chrome: windows since 63, workers since 65; no iOS support (iOS Chrome uses WebKit).
Source: spec §4; spec §5; BCD api/Navigator.json; BCD api/WorkerNavigator.json.

Lifecycle

When computedChrome computes the bucketed value once from total physical memory and caches it (ApproximatedDeviceMemory::Initialize); it does not vary with memory pressure or free memory — it reflects installed RAM, not available RAM.
StabilityConstant for the life of the browsing session; there is no change event. Re-reading is cheap but pointless.
Across contextsWindow and worker contexts on the same device report the same bucket.
Across versionsThe value a given machine reports can change when the browser updates its bounds — exactly what Chrome 147 does (a 0.5 GB Android phone moves from 0.5 to 1; a 64 GB desktop moves from 8 to 32). Persisted or server-side assumptions about the value set must tolerate this.
Source: approximated_device_memory.cc (M147 branch); spec §2.

Examples

The specification's own guarded patterns — disable for known-low, or enable for known-high-or-unknown:

const mem = navigator.deviceMemory;

// Either disable features if it is known to be a low-memory device
if (mem && mem < 2) {
  // disable features to provide a better experience
}

// Or, alternatively only enable features if the device memory is
// either not provided, or known to be above minimum requirements
if (!mem || mem > 4) {
  // enable features to provide a better experience
}

Segmenting high-end desktops, possible from Chrome 147:

if ((navigator.deviceMemory ?? 0) >= 16) {
  // Only desktop-class Chrome 147+ devices reach here.
  await loadOnDeviceModel();
}

In a worker, for RUM beacons:

// worker.js
const analyticsData = {
  memory: self.navigator.deviceMemory, // undefined outside Chromium
  // ... other metrics
};
navigator.sendBeacon("/endpoint", JSON.stringify(analyticsData));
Source: spec §4.1 JavaScript examples (first snippet adapted verbatim).

Security and privacy

  • Fingerprinting is the design constraint. The value is rounded to a single significant bit and clamped to bounds chosen to “exclude rare device memory values”; Chrome 147 retired the 0.25/0.5 buckets precisely because reporting a rare bucket identifies a user.
  • Secure contexts only. The property is absent on HTTP pages.
  • No exact values. A 24 GB machine reports 16 or 32 (nearest power of two), never 24.
  • Passive read. No permission, prompt, or user gesture — the mitigation is entirely in the value coarsening and bounds.
Source: spec §5 Security & privacy considerations; Intent to Ship (privacy rationale).
