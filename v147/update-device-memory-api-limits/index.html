Update Device Memory API limits

Limited availability

  • Chrome · 63+ (navigator.deviceMemory), 97+ (Sec-CH-Device-Memory); new buckets from 147
  • Edge · 79+ / 97+ (mirrors Chrome per BCD)
  • Firefox · not implemented
  • Safari · not implemented

The Device Memory API has the web-features ID device-memory, whose Baseline status is limited — it is a Chromium-only API (webstatus.dev API query, verified 2026-09-13). This page documents the Chrome 147 change to the reported value buckets; the API surface itself is unchanged and much older.

Chrome 147 updates the memory buckets reported by the Device Memory API (navigator.deviceMemory and the Device-Memory / Sec-CH-Device-Memory client hints), expanding the upper range on desktop to 16 and 32 GB and dropping the rarely-seen 0.25 and 0.5 GB buckets to better reflect today's device landscape. Ships in Chrome 147 on desktop, Android, and WebView.

what changed

The Device Memory API reports RAM in privacy-preserving buckets (the physical amount is rounded to the nearest power of two, then clamped to implementation-defined bounds) rather than the exact amount. Chrome 147 updates the clamping bounds, which changes the possible reported values:

PlatformBefore Chrome 147Chrome 147+
Android0.25, 0.5, 1, 2, 4, 81, 2, 4, 8
Desktop (Windows, Mac, Linux)0.25, 0.5, 1, 2, 4, 82, 4, 8, 16, 32

The 0.25 GB and 0.5 GB buckets are removed everywhere: Chrome's internal stats showed the lower bounds “are rarely used and so present a privacy risk” — a rare value is a strong fingerprinting signal. The upper range on desktop expands to 16 GB and 32 GB to let developers segment high-end devices (a request tracked in w3c/device-memory#50, motivated in part by on-device AI workloads); Android keeps 8 GB as its ceiling because “>8GB RAM is still rare for mobile devices”.

The rollout was bumpier than expected, and the history explains the final numbers. The original intent (January 2026) proposed 2, 4, 8 on Android and targeted Chrome 146; the 1 GB bucket was restored after a Google Search test-suite regression showed real sites still serve reduced content to devices reporting ≤1 GB. The change then had to be disabled again in the 146 Beta after the new 16/32 values tripped a server-side check that blocked x.com logins (fixed on X's side), and it was re-enabled for Chrome 147; a bot-protection vendor (Kasada) later shipped a similar fix. The whole saga is on the record in the intent thread.

Source: blink-dev Intent to Ship: Update Device Memory API limits (initial proposal 2026-01-19; Android-1GB revision 2026-01-27; x.com report and move to 147 on 2026-02-13; re-enable 2026-02-23; Kasada report 2026-03-19); approximated_device_memory.cc (M147 branch).

why it exists

The bucket values were set when the API shipped (Chrome 61–63 era, 2017) and were “based on common device capabilities at the time”. Device capabilities have moved on in both directions: the low buckets (0.25, 0.5, and even 1 GB) are now seen so rarely that reporting one identifies a user more than it helps a developer, while the 8 GB cap lumps mid-range laptops together with 64 GB workstations just as memory-hungry capabilities (such as on-device LLMs) make the difference matter.

The change is deliberately paired with spec work: the specification's computing algorithm now states the bounds are implementation-defined, “should include the majority of device memory values but exclude rare device memory values to mitigate device fingerprinting”, and that “Implementations may adjust these bounds over time” — so consumers of this API must not hard-code today's value set. That is the lasting lesson of this milestone: both compat incidents during rollout came from software that assumed the 2017 values were permanent.

Source: ChromeStatus motivation; Device Memory API §2 Computing device memory value; Intent to Ship thread.

Syntax

The affected surface, verbatim from the specification. The JavaScript API (full reference: navigator.deviceMemory):

[
  SecureContext,
  Exposed=(Window,Worker)
] interface mixin NavigatorDeviceMemory {
  readonly attribute double deviceMemory;
};
Navigator includes NavigatorDeviceMemory;
WorkerNavigator includes NavigatorDeviceMemory;

The HTTP client hint (full reference: Sec-CH-Device-Memory), a structured-field decimal:

Sec-CH-Device-Memory = sf-decimal
Source: spec §4 Device Memory JavaScript API (IDL verbatim); spec §3 Sec-CH-Device-Memory (Client Hint) Header Field (ABNF verbatim).

the Chrome 147 change in detail

What a developer relying on device-memory values needs to know about the migration itself:

New value setsAndroid: 1, 2, 4, 8. Windows, macOS, Linux, ChromeOS and everything else: 2, 4, 8, 16, 32. Values remain GiB as a JavaScript double / header sf-decimal; only the set of possible values changed. In M147 code: kMinMemory = 2.0f; kMaxMemory = 32.0f; with an Android override of 1.0f / 8.0f.
Input (unchanged)Physical device RAM, rounded to the nearest power of two by the spec algorithm, then clamped to the implementation-defined bounds above. Nothing a page sends affects the value; the bounds are the only thing Chrome 147 changes.
Observable effectsAll three read surfaces move together: navigator.deviceMemory in windows and workers, Sec-CH-Device-Memory, and the deprecated Device-Memory header. A low-end Android phone that reported 0.5 now reports 1; a 0.5 GB desktop machine reports 2; a 64 GB workstation that reported 8 now reports 32.
Failure modesNo new error paths — the change cannot throw. The observed compat risks are in consumer logic: code gating on navigator.deviceMemory < 1 is now unreachable everywhere, < 2 is unreachable on desktop, and server-side allowlists of the 2017 value set mis-classify values 16 and 32 as invalid (the x.com login blockage and the Kasada bot-protection incident during rollout were exactly this).
Where it appliesChrome 147 on desktop, Android, and Android WebView; no iOS milestone (iOS Chrome does not run Blink's device-memory bucketing). Enabled by default with the kUpdatedDeviceMemoryLimitsFor2026 kill switch (M147 branch); unconditional at trunk. Other Chromium browsers inherit the change as they rebase.
Rollout historyTargeted 146 with Android 2,4,8 (intent 2026-01-19; LGTMs from Alex Russell, Yoav Weiss, Daniel Bratell) → Android 1 GB restored after a Search memory regression on a sub-1GB test device (2026-01-27) → disabled in Beta after x.com login blockage; milestone moved to 147 (2026-02-13) → re-enabled for 147 (2026-02-23). The bounds are expected to change again in future milestones; the spec now says implementations may adjust them over time.
Migration adviceTreat the value as an ordering signal (“less than N” / “at least N”), never as an enum of known constants. Use threshold comparisons with a default branch for undefined (non-Chromium browsers) and unknown future values — see examples.
Source: approximated_device_memory.cc (M147 branch, bounds verbatim); features.cc (M147 branch, kill switch); Intent to Ship thread; ChromeStatus record.

Examples

Reading device memory, written to survive bucket changes (threshold comparisons, no equality against known values):

// navigator.deviceMemory returns one of the new bucket values
console.log(navigator.deviceMemory);
// Android: 1, 2, 4, or 8
// Desktop: 2, 4, 8, 16, or 32

// Code that relied on values below 1 will never match in Chrome 147+
if (navigator.deviceMemory < 1) {
  // This branch is now unreachable
  showLowMemoryMode();
}

// Robust: threshold comparisons with an explicit unsupported branch
const mem = navigator.deviceMemory; // undefined in Firefox/Safari
if (mem === undefined) {
  useDefaultExperience();
} else if (mem <= 2) {
  useLiteExperience();
} else if (mem >= 16) {
  enableHighEndFeatures(); // reachable on desktop from Chrome 147
}

Opting in to the client hint on the server — the values in the request header change identically in Chrome 147:

Accept-CH: Sec-CH-Device-Memory

GET /example HTTP/1.1
Sec-CH-Device-Memory: 32
Source: spec §4.1 JavaScript examples; spec §3.1 Client Hint examples.

security and privacy

  • This change is itself a privacy fix. Reporting a now-rare bucket (0.25 or 0.5 GB) makes a user stand out; removing rare buckets shrinks the fingerprinting surface at the low end. Chrome's internal stats review “confirm[ed] the lower bounds are rarely used and so present a privacy risk”.
  • The new high-end buckets trade some entropy for utility. 16 and 32 add distinguishable states on desktop; the spec's guidance is that bounds “should include the majority of device memory values but exclude rare device memory values”, and the intent thread records the privacy review of exactly this trade (Android deliberately keeps its 8 GB cap while >8 GB remains rare there).
  • Coarsening is unchanged. Values are still rounded to a single significant bit and clamped; the exact RAM amount is never exposed. Both the header and the JavaScript API remain restricted to HTTPS secure contexts ([SecureContext]).
  • Anti-abuse consumers must not treat the value set as fixed. Two bot/abuse systems (x.com login protection, Kasada) blocked users when unfamiliar values appeared. Bounds are implementation-defined and will change again.
Source: spec §5 Security & privacy considerations; ChromeStatus security section; Intent to Ship thread.
