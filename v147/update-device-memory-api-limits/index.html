Update Device Memory API limits

Limited availability

  • Chrome · new limits from 147 (API since 63)
  • Edge · Chromium-based (API since 79)
  • Firefox · not supported
  • Safari · not supported

The underlying Device Memory API is not Baseline: the webstatus.dev entry for device-memory reports Baseline status “limited” with Chromium-only implementations (verified 2026-09-06), and BCD api.Navigator.deviceMemory records no Firefox or Safari support. The limits change documented here is Chromium-specific behavior shipping in Chrome 147 on desktop, Android, and WebView per the ChromeStatus record.

Chrome 147 updates the privacy-preserving memory buckets reported by the Device Memory API — navigator.deviceMemory and the Device-Memory / Sec-CH-Device-Memory client hint headers. The floor rises on every platform (dropping the outdated 0.25 and 0.5 GiB buckets) and the ceiling on desktop expands to 32 GiB, so the possible values become 1, 2, 4, 8 on Android and 2, 4, 8, 16, 32 everywhere else, replacing the old 0.25–8 range on all platforms.

what changed

The Device Memory API reports RAM in privacy-preserving buckets rather than the exact amount: the physical memory is rounded to the nearest power of two, then clamped to an implementation-defined range. Chrome 147 changes only the clamping bounds:

Possible reported values (GiB)
PlatformBefore Chrome 147Chrome 147+
Android0.25, 0.5, 1, 2, 4, 81, 2, 4, 8
Desktop (Windows, macOS, Linux, ChromeOS)0.25, 0.5, 1, 2, 4, 82, 4, 8, 16, 32
  • Higher floor. The 0.25 and 0.5 GiB buckets disappear everywhere; desktop additionally loses the 1 GiB bucket. Internal Chrome stats and external RUM-provider review confirmed the low buckets were rarely reported, so they had become a fingerprinting vector rather than a capability signal.
  • Higher desktop ceiling. 16 and 32 GiB let sites segment high-end machines — the change developers requested in w3c/device-memory #50 (closed), motivated in part by memory-hungry workloads such as on-device AI.
  • Android ceiling unchanged at 8 GiB — deliberately not raised yet, because >8 GiB remains rare on mobile devices (per the ChromeStatus security-risks review).
Source: ChromeStatus summary + security risks; w3c/device-memory #50 (proposal); blink-dev Intent to Ship

syntax

The change adds no new surface; these are the affected contracts. The Web IDL, verbatim from the Device Memory 1 specification (W3C Working Draft, 2026-03-30, § 4):

[
  SecureContext,
  Exposed=(Window,Worker)
] interface mixin NavigatorDeviceMemory {
  readonly attribute double deviceMemory;
};

Navigator includes NavigatorDeviceMemory;
WorkerNavigator includes NavigatorDeviceMemory;

The deviceMemory getter returns the user agent’s coarsened device memory in GiB — from Chrome 147, always one of the values in the table above.

The client hint header, with its ABNF verbatim from the same spec (§ 3 — a Structured Fields decimal):

Sec-CH-Device-Memory = sf-decimal

Chrome sends Sec-CH-Device-Memory (since Chrome 97) and also the legacy pre-Sec-CH- spelling Device-Memory (since Chrome 61), which BCD marks deprecated and non-standard. Both carry the same clamped value, and both are opt-in via Accept-CH:

Accept-CH: Sec-CH-Device-Memory

GET /example HTTP/1.1
Sec-CH-Device-Memory: 8
Source: Device Memory 1, W3C WD 2026-03-30 (IDL § 4, header § 3, examples § 3.1, verbatim); BCD http.headers.Sec-CH-Device-Memory

how the reported value is computed

The spec’s algorithm (§ 2.1) rounds physical memory to the nearest power of two, then clamps: “If deviceMemory < minimumLowerBound, then deviceMemory is minimumLowerBound. If deviceMemory > maximumUpperBound, then deviceMemory is maximumUpperBound.” After PR #53 both bounds are implementation-defined: “Implementations may adjust these bounds over time. These bounds may differ on different device types.” That spec change is what allowed Chrome to move its bounds without a spec violation (the TAG review was recorded “Not applicable” because the values were always documented as subject to change).

Chrome’s bounds now live in approximated_device_memory.cc (trunk, fetched 2026-09-06):

// Limit the values to reduce fingerprintability.
// See: https://crbug.com/454354290 for updated limits.
float kMinMemory = 2.0f;
float kMaxMemory = 32.0f;

#if BUILDFLAG(IS_ANDROID)
  // Allow smaller lower limits on Android where lower RAM is still common.
  kMinMemory = 1.0f;
  kMaxMemory = 8.0f;
#endif

Because rounding happens before clamping, every reported value is a power of two within the platform’s [min, max] range — which yields exactly the value sets in what changed.

Source: Device Memory 1 § 2.1 (algorithm, quoted verbatim); Chromium approximated_device_memory.cc (excerpt verbatim, comment abridged); w3c/device-memory PR #53 (merged 2026-01-19)

context and exposure

  • Secure contexts only. The IDL is [SecureContext]; the headers are likewise restricted to HTTPS (spec § 5). On insecure pages navigator.deviceMemory is undefined.
  • Window and workers. Exposed=(Window,Worker) — the same clamped value is readable from Navigator and WorkerNavigator.
  • Headers are opt-in. Sec-CH-Device-Memory / Device-Memory are only sent after the server opts in via Accept-CH (or the equivalent <meta http-equiv>), per the Client Hints model.
  • No feature-detecting the new limits. Nothing announces which bucket set a browser uses. Code can detect the API ('deviceMemory' in navigator) but not the bounds; infer them only from the reported value’s range, or from the UA version via the compat table below.
  • Migration impact. From Chrome 147, comparisons against retired buckets are dead code: on Android navigator.deviceMemory < 1 is never true, on desktop < 2 is never true — and a desktop machine with 512 MiB RAM now reports 2. Low-memory heuristics keyed on 0.25/0.5 must be re-thresholded. Conversely RUM segmentation can now distinguish 8 vs 16 vs 32 GiB desktops.
Source: Device Memory 1 §§ 3–5; ChromeStatus adoption expectation

lifecycle

  1. Computed once, then constant. Chromium caches physical memory at initialization (ApproximatedDeviceMemory::Initialize()) and derives the clamped value from it; navigator.deviceMemory does not change while a page runs, and there is no change event.
  2. Headers per request, after opt-in. Once a server’s Accept-CH: Sec-CH-Device-Memory preference is registered, subsequent eligible requests carry the hint with the same clamped value.
  3. Rollout. The new bounds ship enabled by default in Chrome 147 on all platforms (desktop, Android, WebView) with no origin trial and no flag to flip; the kill switch exists only for emergency reversion. A user updating from 146 to 147 may observe the reported value change (e.g. a 0.5 GiB Android device jumping to 1) with no page-visible notification.
Source: Chromium ApproximatedDeviceMemory (cached static); Device Memory 1 § 3; intent thread (rollout plan)

examples

Reading the coarsened value, with the post-147 buckets and a migration-safe threshold:

// navigator.deviceMemory returns one of the new bucket values (GiB)
console.log(navigator.deviceMemory);
// Android: 1, 2, 4, or 8
// Desktop: 2, 4, 8, 16, or 32

// Code that relied on values below 1 will never match in Chrome 147+
if (navigator.deviceMemory < 1) {
  // Unreachable on Android from 147 (and < 2 is unreachable on desktop)
  showLowMemoryMode();
}

// Migration-safe tiering: threshold against the surviving buckets,
// and treat the API as absent in Firefox/Safari
const mem = navigator.deviceMemory ?? 4; // fallback guess
const tier = mem <= 2 ? "lite" : mem <= 8 ? "standard" : "premium";

Opting in to the client hint on the server, then adapting the response:

HTTP/1.1 200 OK
Accept-CH: Sec-CH-Device-Memory

// A later request from Chrome 147 on a 16 GiB laptop:
GET /app HTTP/1.1
Sec-CH-Device-Memory: 16
Device-Memory: 16

Further interactive demos on the showcase feature page: Adaptive Loading Demo, Quality Tier Picker, Memory Budget Optimizer, and Compatibility Lab (all HEAD-checked 200, 2026-09-06).

security and privacy

  • This change is itself a privacy mitigation. As device capabilities improved, the 0.25 and 0.5 GiB buckets came to identify rare devices — internal stats and external RUM providers confirmed they were seldom reported, making them a fingerprinting signal. Raising the floor shrinks the identifying power of the low end.
  • The new high-end buckets add entropy at the top. The desktop set moves from six buckets capped at 8 GiB to five buckets reaching 32 GiB; the 16/32 GiB segmentation was judged acceptable after (internal-only) data review, and the spec’s general mitigation (single-significant-bit rounding + bounds, § 5) still applies. The spec directs implementations to keep reviewing bounds as hardware shifts — exactly what this change does.
  • Trust boundaries unchanged. Secure-context-only exposure and the opt-in client hints model are untouched; no new information category is revealed, only the granularity at the extremes changes.
Source: Device Memory 1 § 5 (Security Considerations); ChromeStatus security risks (data review, quoted findings); w3c/device-memory #50
