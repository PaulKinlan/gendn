JS Profiling in Dedicated Workers

Limited availability

  • Chrome 94+ (main thread)
  • Chrome 147 · workers, dev trial
  • Firefox · no signal
  • Safari · no signal

Baseline: Limited availability. The underlying JS Self-Profiling API is Chromium-only — the webstatus.dev entry profiler (queried 2026-08-16) records Chrome availability since 94 (2021-09-21) with no Firefox or Safari implementation. The dedicated-worker exposure this page documents is a Chrome 147 developer trial; BCD api.Profiler has no worker-support subfeature yet.

Chrome 147 adds developer trial support for the JavaScript Self-Profiling API (Profiler) inside dedicated workers. Previously only available on the main thread in Chrome, this lets worker scripts collect their own JavaScript call-stack samples, enabling fine-grained profiling of CPU-intensive work that’s already been offloaded to a worker.

Developer trial in Chrome 147

The worker exposure is behind a flag in Chrome 147: enable chrome://flags/#enable-experimental-web-platform-features, or launch with --enable-blink-features=ProfilerAPIForDedicatedWorker — the runtime-enabled feature is ProfilerAPIForDedicatedWorker (status experimental; the main-thread ProfilerAPI is stable) in runtime_enabled_features.json5. Profiling also remains gated by the js-profiling Document Policy (the chromestatus summary notes Document Policy support for workers is tracked separately). The API surface may change before it ships — do not rely on it in production.

Syntax

Verbatim from the WICG draft (fetched 2026-08-16) — note the exposure is already (Window, Worker) in the spec; Chrome 147’s dev trial brings the implementation in line for dedicated workers:

[Exposed=(Window, Worker)]
interface Profiler : EventTarget {
  readonly attribute DOMHighResTimeStamp sampleInterval;
  readonly attribute boolean stopped;

  constructor(ProfilerInitOptions options);
  Promise<ProfilerTrace> stop();
};

dictionary ProfilerInitOptions {
  required DOMHighResTimeStamp sampleInterval;
  required unsigned long maxBufferSize;
};

typedef DOMString ProfilerResource;

dictionary ProfilerTrace {
  required sequence<ProfilerResource> resources;
  required sequence<ProfilerFrame> frames;
  required sequence<ProfilerStack> stacks;
  required sequence<ProfilerSample> samples;
};

dictionary ProfilerFrame {
  required DOMString name;
  unsigned long long resourceId;
  unsigned long long line;
  unsigned long long column;
};

dictionary ProfilerStack {
  unsigned long long parentId;
  required unsigned long long frameId;
};

dictionary ProfilerSample {
  required DOMHighResTimeStamp timestamp;
  unsigned long long stackId;
};
Source: WICG JS Self-Profiling — IDL

why it exists

Many performance-sensitive applications move heavy computation into dedicated workers to keep the main thread responsive — data processing, cryptography, image manipulation, WebAssembly calls, etc. Without profiling support in workers, developers had to rely on external DevTools profiling or indirect measurement.

The JS Self-Profiling API allows scripts to collect statistical call-stack samples of their own execution and report them as structured JSON-compatible traces. Extending this to dedicated workers lets performance engineers measure exactly where worker CPU time is spent without special DevTools attachment — with the capability still gated by the js-profiling Document Policy.

Source: WICG JS Self-Profiling API; chromestatus feature summary

example

Profiling inside a dedicated worker

// Serve the document with:  Document-Policy: js-profiling
// (profiling is policy-gated; worker policy propagation is tracked separately)

// Inside a dedicated worker script (requires the flag in Chrome 147)
const profiler = new Profiler({
  sampleInterval: 10,     // required — ms between samples (UA may round up)
  maxBufferSize: 10_000,  // required — max samples before auto-stop
});

profiler.addEventListener("samplebufferfull", () => {
  // Buffer filled before stop(): the session has already stopped.
});

// ... run your computation ...
await doHeavyWork();

const trace = await profiler.stop();
// trace: { resources, frames, stacks, samples } — JSON-serializable
postMessage({ trace });
