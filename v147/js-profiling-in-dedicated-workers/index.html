JS Profiling in Dedicated Workers

Limited availability

  • Chrome · Profiler on the main thread since 94; in dedicated workers: developer trial, behind a flag
  • Edge · Profiler on the main thread since 94; no shipped worker signal
  • Firefox · not implemented
  • Safari · not implemented

The underlying JS Self-Profiling API has the web-features entry “Profiler”, Baseline status limited (Chrome/Edge 94, Firefox and Safari unshipped; verified via the webstatus.dev API, 2026-09-13). The worker exposure documented here has no web-features entry of its own — a webstatus.dev query for “js-self-profiling” returns zero matches — and is not part of any Baseline set.

Chrome adds developer trial support for the JavaScript Self-Profiling API (Profiler) inside dedicated workers. Previously only available on the main thread, this lets worker scripts collect their own JavaScript call-stack samples, enabling fine-grained profiling of CPU-intensive work that's already been offloaded to a worker.

Developer trial — behind a flag

This API surface may change before it ships. Do not use it in production. To try it, enable Experimental Web Platform features at chrome://flags/#enable-experimental-web-platform-features, or launch Chrome with --enable-experimental-web-platform-features (the flag named by the ChromeStatus record). The Blink runtime features behind that umbrella are ProfilerAPIForDedicatedWorker (“When enabled, dedicated workers can use profiler API”), DocumentPolicyInDedicatedWorker, and DocumentPolicyJSProfilingMode — all status experimental in runtime_enabled_features.json5 (fetched 2026-09-13).

Milestone note (honest correction). This page was published against the Chrome 147 developer-trial listing. As of 2026-09-13 the ChromeStatus record's dev-trial stage records desktop_first: 154 and the feature appears in the milestone=154 listing under “In developer trial (Behind a flag)” — the trial timeline moved after this page was created. The API record still lists overall Chrome status as “Proposed”, with no shipped milestone. This page's route and feature identity are stable; treat Chrome 154 as the current dev-trial target.

why it exists

Many performance-sensitive applications move heavy computation into dedicated workers to keep the main thread responsive — data processing, cryptography, image manipulation, WebAssembly calls. Existing worker performance APIs (User Timing, PerformanceObserver, Resource Timing) reveal when tasks are slow, but not why: they cannot attribute CPU cost to specific JavaScript stacks inside the worker event loop. Without profiling support in workers, developers had to rely on external DevTools profiling or indirect measurement.

The JS Self-Profiling API allows scripts to collect statistical call-stack samples of their own execution and report them as structured JSON-compatible traces. Extending it to dedicated workers lets performance engineers measure exactly where worker CPU time is spent without special DevTools attachment. The blocker was policy plumbing, not the profiler itself: the API is gated by the Document-Policy header, whose semantics were undefined for workers — that gap is tracked in WICG/js-self-profiling#33 and addressed by the Document Policy in Workers explainer (Microsoft Edge; motivating partners include large web clients such as Outlook that delegate parsing and computation to workers). Chrome's ChromeStatus record notes web-developer sentiment as positive, citing partners “profiling performance-critical work offloaded to dedicated workers”.

Source: Document Policy in Workers explainer — Motivation; WICG/js-self-profiling#33; ChromeStatus record.

Syntax

The change this feature implements is a one-line exposure widening in the specification IDL, merged as “Extend Profiler to Workers” (PR #88, 2026-02-18) — verbatim diff:

- [Exposed=Window]
+ [Exposed=(Window, Worker)]
  interface Profiler : EventTarget { … };

The full interface, verbatim from the current specification:

[Exposed=(Window, Worker)]
interface Profiler : EventTarget {
  readonly attribute DOMHighResTimeStamp sampleInterval;
  readonly attribute boolean stopped;

  constructor(ProfilerInitOptions options);
  Promise<ProfilerTrace> stop();
};

Context and exposure: the specification exposes Profiler on Window and all Worker globals, and the same commit rewrote the constructor's policy check to read the policy value from the current global object when it “is a Window or a WorkerGlobalScope”. Chrome's developer trial is narrower than the spec IDL: the Blink runtime feature is ProfilerAPIForDedicatedWorker (“dedicated workers can use profiler API”), i.e. DedicatedWorkerGlobalScope only — shared and service workers are not part of this trial, and Document Policy support for workers is tracked as a separate deliverable per the ChromeStatus summary. The IDL carries no [SecureContext] attribute; upstream tests exercise the API over HTTPS. Same-realm rules apply unchanged: a profiler samples only the realm it was constructed in, so a worker's profiler observes that worker's execution, not the page's (see security and privacy).

Source: spec — The Profiler Interface; spec commit e603c27 (PR #88); runtime_enabled_features.json5; ChromeStatus record.

Document Policy gating in workers

Constructing a Profiler is authorized by Document Policy configuration points; without an authorizing policy the constructor throws a "NotAllowedError" DOMException. Header syntax:

# Preferred (enum: "eager" | "lazy"):
Document-Policy: js-profiling-mode=lazy

# Deprecated boolean form (still supported for backwards compatibility):
Document-Policy: js-profiling
js-profiling-modeEnum configuration point, allowed values "eager" and "lazy"; default is the empty string (API not authorized). eager signals profiling during load is expected — the UA may warm up profiling infrastructure early, at possible FCP/LCP cost. lazy defers initialization until the first Profiler is constructed — cheaper at load, with possible INP cost at first construction.
js-profiling (deprecated)Boolean configuration point, default false; semantically equivalent to js-profiling-mode=eager. If both are specified, js-profiling-mode takes precedence and js-profiling MUST be ignored.
How a worker gets a policyPer the explainer: for network-delivered worker scripts, the policy comes from the worker script's own HTTP response headers; local-scheme workers (blob:, data:) inherit the policy from their creator document, cloned using the same rules as policy-container cloning in HTML. The policy is fixed when the worker is created — there is no runtime renegotiation.
Chrome status of the worker-policy pieceThe ChromeStatus summary states the API “remain[s] gated by Document Policy” and that “Document Policy support for workers [is] tracked separately”; in the trial both halves sit behind the same experimental flag (DocumentPolicyInDedicatedWorker).
Source: spec — Document Policy; Document Policy in Workers explainer; ChromeStatus summary.

The Profiler interface in workers

Everything the main-thread API offers becomes available inside the worker: the surface below is documented member-by-member, with full nine-dimension contract tables, on the child reference Profiler (in dedicated workers).

MemberKindSummary
new Profiler(options)constructorStarts a profiling session for the current realm; throws RangeError for a negative sampleInterval and NotAllowedError without an authorizing Document Policy
sampleIntervalattributeRead-only DOMHighResTimeStamp; the session's effective sample interval
stoppedattributeRead-only boolean; true iff the session state is stopped
stop()methodStops the session and resolves with the collected ProfilerTrace; rejects InvalidStateError if already stopped
samplebufferfulleventFired when the sample buffer reaches maxBufferSize; the session moves to stopped
ProfilerInitOptionsdictionaryRequired sampleInterval (ms, ≥ 0) and maxBufferSize (samples)
ProfilerTracedictionaryresources / frames / stacks / samples — the deduplicated, JSON-serializable trace
ProfilerSampledictionaryOne sample: timestamp plus optional stackId
ProfilerStackdictionaryInterned stack node: frameId plus optional parentId
ProfilerFramedictionaryInterned frame: name, optional resourceId, line, column

Examples

Profiling a computation inside a dedicated worker. The worker script's HTTP response must carry the Document Policy header (network workers get their policy from their own response headers):

# Response headers for /heavy-worker.js
Document-Policy: js-profiling-mode=lazy
// heavy-worker.js — dedicated worker (Chrome developer trial, behind
// chrome://flags/#enable-experimental-web-platform-features)
self.onmessage = async ({ data }) => {
  const profiler = new Profiler({
    sampleInterval: 10,     // desired ms between samples
    maxBufferSize: 10_000,  // stop after this many samples
  });

  const result = doHeavyWork(data);   // the code being attributed

  const trace = await profiler.stop();
  // trace is a JSON-serializable ProfilerTrace:
  // { resources, frames, stacks, samples }
  self.postMessage({ result, trace });
};
// main.js — feature-detect before relying on worker-side profiling
const worker = new Worker("/heavy-worker.js");
worker.postMessage(payload);
worker.onmessage = ({ data: { result, trace } }) => {
  if (trace) sendTraceToAnalytics(JSON.stringify(trace));
  render(result);
};

// Inside the worker, guard for browsers without the trial:
//   if (typeof Profiler === "undefined") { /* skip profiling */ }
Source: spec — Examples (main-thread originals, adapted to the worker global per the exposure change); explainer — header delivery for network workers.

security and privacy

  • Cross-origin script contents. The take-a-sample algorithm only includes frames from scripts served CORS-same-origin (via the classic-script muted errors check); browser builtins are attributed to the invoking script and excluded when that script is inaccessible. A worker profiler therefore cannot leak the contents of cross-origin scripts it imports without CORS.
  • Cross-origin execution. The realm check means execution contexts whose realm differs from the profiling session's are not observable. In a dedicated worker this bounds the trace to that worker's own realm — a worker profiler cannot observe the document, other workers, or cross-origin iframes sharing the agent cluster.
  • Timing attacks. Sample timestamps must come from the same clock source as High Resolution Time's current high resolution time (here, the worker's time origin), so the API introduces no new high-resolution timing side channel beyond what performance.now() already exposes in the worker.
  • Explicit opt-in. The Document Policy gate means profiling capability is never on by default: a server must opt the worker script in via its own response headers (or the creator document must hold the policy, for blob:/data: workers). Mozilla's standards position on the base API records security concerns; Firefox has not shipped it.
Source: spec — Privacy and Security; explainer — policy delivery; mozilla/standards-positions#477.
