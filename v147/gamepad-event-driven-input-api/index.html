Gamepad Event-Driven Input API

Limited availability

  • Chrome · 147 behind a flag
  • Edge · no data
  • Firefox · no support
  • Safari · no support

The event-driven input event has no web-features entry and no BCD entry yet, so webstatus.dev computes no Baseline status for it. The parent Gamepad feature is Baseline Widely available (low date 2017-03-27, high date 2019-09-27) on webstatus.dev (verified 2026-11-22) — that covers navigator.getGamepads() polling, not this event. Per the ChromeStatus record the event is Chromium-only and still in development (Firefox and Safari: no signal). Treat it as experimental and keep a polling fallback.

An extension to the Gamepad API that fires a gamepadrawinputchanged event (named rawgamepadinputchange in the ChromeStatus summary — see Syntax) whenever new input data arrives from the device, eliminating the need to poll navigator.getGamepads() on every animation frame. Reduces input latency for games and interactive applications that care about sub-frame responsiveness.

In developer trial This feature is in development and behind a flag in Chrome 147. Enable chrome://flags/#enable-experimental-web-platform-features to test it (the Blink runtime feature GamepadRawInputChangeEvent has status experimental in the Chrome 147 branch’s runtime_enabled_features.json5, so launching Chrome with --enable-blink-features=GamepadRawInputChangeEvent also enables it). The event name and interface shape may change before shipping.

why it exists

The existing Gamepad API requires polling: you call navigator.getGamepads() inside a requestAnimationFrame loop, which runs at most at the display refresh rate (typically 60 Hz). A gamepad can report input at 1000 Hz or higher. The gap means input events can be 1–16 ms stale before the application sees them — unacceptable in competitive games or precision controllers. An event-driven model fires immediately when the hardware reports new data, independently of the frame rate, enabling applications to respond at the device's native rate.

Source: chromestatus summary and web developer signals referenced in the feature entry, May 2026.

Syntax

No W3C specification text defines this event yet. The first block shows the two ways to listen; the IDL blocks after it are quoted verbatim from Chromium’s Chrome 147 branch (7727) source; it matches the “proposed WebIDL” appendix of the explainer except for Chromium’s RuntimeEnabled extended attribute (license header omitted).

window.addEventListener("gamepadrawinputchanged", (event) => { /* GamepadRawInputChangeEvent */ });
window.ongamepadrawinputchanged = (event) => { /* … */ };

GamepadRawInputChangeEvent interface

[
    Exposed=Window,
    RuntimeEnabled=GamepadRawInputChangeEvent
] interface GamepadRawInputChangeEvent : GamepadEvent {
    constructor(DOMString type, optional GamepadRawInputChangeEventInit eventInitDict = {});
    readonly attribute FrozenArray<long> axesChanged;
    readonly attribute FrozenArray<long> buttonsValueChanged;
    readonly attribute FrozenArray<long> buttonsPressed;
    readonly attribute FrozenArray<long> buttonsReleased;
    readonly attribute FrozenArray<long> touchesChanged;
};

It inherits gamepad (the Gamepad snapshot) from GamepadEvent. The five arrays hold indices into the snapshot’s axes, buttons and touches arrays, per the explainer’s event properties:

AttributeIndices of…
axesChangedaxes whose value changed since the last event
buttonsValueChangedbuttons whose value changed
buttonsPressedbuttons that transitioned to pressed
buttonsReleasedbuttons that transitioned to released
touchesChangedentries of gamepad.touches whose position or presence changed

The constructor takes a GamepadRawInputChangeEventInit dictionary; constructing the event yourself (for example in tests) does not involve hardware and dispatches nothing until you call dispatchEvent().

GamepadRawInputChangeEventInit dictionary

dictionary GamepadRawInputChangeEventInit : GamepadEventInit {
  FrozenArray<long> axesChanged;
  FrozenArray<long> buttonsValueChanged;
  FrozenArray<long> buttonsPressed;
  FrozenArray<long> buttonsReleased;
  FrozenArray<long> touchesChanged;
};

Event handler

// window_gamepad.idl (excerpt)
[RuntimeEnabled=GamepadRawInputChangeEvent] attribute EventHandler ongamepadrawinputchanged;

Feature-detect with "ongamepadrawinputchanged" in window or "GamepadRawInputChangeEvent" in window; both are absent unless the runtime feature is enabled.

Security and privacy

The explainer’s considerations section states that a gamepad user gesture (for example a button press) is required before gamepadrawinputchanged events start firing, and that the event exposes no state not already exposed by polling.

Source: gamepad_raw_input_change_event.idl, gamepad_raw_input_change_event_init.idl, window_gamepad.idl and event_type_names.json5 at Chromium branch-heads/7727 (fetched 2026-11-22; branch mapped to M147 by chromiumdash); explainer — Appendix: proposed WebIDL.

shape of the API

One new event on window that fires for every hardware input report:

gamepadrawinputchanged event

Targetwindow
Fires whenThe gamepad hardware reports new button or axis data, at the device's native polling rate — independent of requestAnimationFrame.
event.gamepadA snapshot Gamepad object with the current button and axis state at the time of the report.
event.gamepad.indexIndex matching the existing navigator.getGamepads() array.
event.gamepad.buttonsArray of GamepadButton objects with pressed, touched, and value.
event.gamepad.axesArray of axis values in the range [-1, 1].
event.gamepad.timestampHigh-resolution timestamp of the hardware report.
event.axesChanged … event.touchesChangedIndex arrays naming exactly which inputs changed — see the GamepadRawInputChangeEvent interface.
Source: W3C Gamepad working draft and chromestatus summary, May 2026; event name and index arrays from Chromium’s IDL (2026-11-22). Field names may change before ship.

Event-driven input loop (replaces polling)

// Previously: polling inside rAF
function pollLoop() {
  const gamepads = navigator.getGamepads();
  if (gamepads[0]) {
    handleInput(gamepads[0]);
  }
  requestAnimationFrame(pollLoop);
}

// With gamepadrawinputchanged: fires at device rate, not frame rate
if ('ongamepadrawinputchanged' in window) {
  window.addEventListener('gamepadrawinputchanged', (event) => {
    handleInput(event.gamepad);
  });
} else {
  requestAnimationFrame(pollLoop); // fallback: keep polling
}

Low-latency button handler

window.addEventListener('gamepadrawinputchanged', (event) => {
  const { gamepad } = event;

  // Only look at what changed (indices into gamepad.buttons / gamepad.axes)
  for (const i of event.buttonsPressed) console.log(`button ${i} pressed`);
  for (const i of event.buttonsReleased) console.log(`button ${i} released`);

  // A button (index 0) — fire at native device rate
  if (gamepad.buttons[0].pressed) {
    triggerAction(gamepad.index, 'A', gamepad.timestamp);
  }

  // Left stick X axis
  const leftX = gamepad.axes[0];
  if (Math.abs(leftX) > 0.1) {
    moveCharacter(leftX);
  }
});
Source: W3C Gamepad API spec and feature summary, May 2026; event name and index arrays per Chromium’s IDL and the explainer code sample (2026-11-22).

relation to the existing Gamepad API

Polling model (navigator.getGamepads())Still works. Returns snapshot at rAF rate. Good for most games; no changes needed.
gamepadrawinputchanged eventsFires at hardware rate. Use when latency or missed inputs at sub-frame granularity matter.
gamepadconnected / gamepaddisconnectedUnchanged. Still the mechanism for detecting connect/disconnect.
