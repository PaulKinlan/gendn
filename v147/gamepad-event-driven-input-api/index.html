Gamepad Event-Driven Input API

Limited availability

  • Chrome · in development, behind a flag
  • Edge · not separately reported
  • Firefox · no signal
  • Safari · no signal

Not a Baseline feature: webstatus.dev has no web-features entry for the event (the host gamepad feature is Baseline widely available — that covers the polling API, not this event; queried 2026-10-25), and BCD’s api/Window.json records only the gamepadconnected/gamepaddisconnected events (no raw-input-change key, verified 2026-10-25). The ChromeStatus record reads “In development” with no shipping milestone.

An extension to the Gamepad API that fires a gamepadrawinputchanged event whenever new input data arrives from the device, eliminating the need to poll navigator.getGamepads() on every animation frame. Reduces input latency for games and interactive applications that care about sub-frame responsiveness.

In developer trial This feature is in development and behind a flag. The exact enable steps (verified 2026-10-25): chrome://flags/#gamepad-raw-input-change-event (the flag the ChromeStatus record names) or --enable-blink-features=GamepadRawInputChangeEvent — the runtime feature record is status: "experimental" with origin-trial name GamepadRawInputChangeEvent. The event name and interface shape may change before shipping — the name has already changed once (see the naming note below).

why it exists

The existing Gamepad API requires polling: you call navigator.getGamepads() inside a requestAnimationFrame loop, which runs at most at the display refresh rate (typically 60 Hz). A gamepad can report input at 1000 Hz or higher. The gap means input events can be 1–16 ms stale before the application sees them — unacceptable in competitive games or precision controllers. An event-driven model fires immediately when the hardware reports new data, independently of the frame rate, enabling applications to respond at the device's native rate.

Source: chromestatus summary and web developer signals referenced in the feature entry, May 2026.

syntax and shape of the API

One new event on window that fires for every hardware input report. Shipping Chromium IDL, quoted verbatim from gamepad_raw_input_change_event.idl at trunk (2026-10-25); the explainer’s proposed WebIDL matches:

[
    Exposed=Window,
    RuntimeEnabled=GamepadRawInputChangeEvent
] interface GamepadRawInputChangeEvent : GamepadEvent {
    constructor(DOMString type, optional GamepadRawInputChangeEventInit eventInitDict = {});
    readonly attribute FrozenArray<long> axesChanged;
    readonly attribute FrozenArray<long> buttonsValueChanged;
    readonly attribute FrozenArray<long> buttonsPressed;
    readonly attribute FrozenArray<long> buttonsReleased;
    readonly attribute FrozenArray<long> touchesChanged;
};

gamepadrawinputchanged event

Targetwindow (handler attribute ongamepadrawinputchanged, per dom_window_gamepad.h)
Fires whenThe gamepad hardware reports a new input frame (a timestamped HID report with all button and axis values), at the device's native polling rate — independent of requestAnimationFrame (explainer definition).
event.gamepadInherited from GamepadEvent: a snapshot Gamepad object with the current button and axis state at the time of the report (index, buttons, axes, timestamp as in the polling API).
event.axesChangedFrozenArray<long> — indices of the axes whose values changed in this input frame.
event.buttonsValueChangedFrozenArray<long> — indices of buttons whose analog value changed.
event.buttonsPressedFrozenArray<long> — indices of buttons that transitioned to pressed.
event.buttonsReleasedFrozenArray<long> — indices of buttons that transitioned to released.
event.touchesChangedFrozenArray<long> — indices of changed touch inputs.
Source: Chromium IDL (verbatim); gamepad_event.idl; explainer; fetched 2026-10-25. The attribute meanings are stated by the explainer; the shape may change before ship.

example

Event-driven input loop (replaces polling)

// Previously: polling inside rAF
function pollLoop() {
  const gamepads = navigator.getGamepads();
  if (gamepads[0]) {
    handleInput(gamepads[0]);
  }
  requestAnimationFrame(pollLoop);
}

// With gamepadrawinputchanged: fires at device rate, not frame rate
window.addEventListener('gamepadrawinputchanged', (event) => {
  handleInput(event.gamepad);
});

Low-latency button handler

window.addEventListener('gamepadrawinputchanged', (event) => {
  const { gamepad } = event;

  // React only to buttons that changed in THIS input frame:
  for (const i of event.buttonsPressed) {
    triggerAction(gamepad.index, i, gamepad.timestamp);
  }

  // Left stick X axis — only when it actually moved
  if (event.axesChanged.includes(0)) {
    const leftX = gamepad.axes[0];
    if (Math.abs(leftX) > 0.1) {
      moveCharacter(leftX);
    }
  }
});
Source: event shape per the Chromium IDL and explainer; examples gendn-derived from those contracts (labelled accordingly), 2026-10-25.

relation to the existing Gamepad API

Polling model (navigator.getGamepads())Still works. Returns snapshot at rAF rate. Good for most games; no changes needed.
gamepadrawinputchanged eventsFires at hardware rate. Use when latency or missed inputs at sub-frame granularity matter.
gamepadconnected / gamepaddisconnectedUnchanged. Still the mechanism for detecting connect/disconnect.
