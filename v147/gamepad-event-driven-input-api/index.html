Gamepad Event-Driven Input API

Limited availability

  • Chrome · flag (147+) / origin trial (149+)
  • Edge · mirrors Chromium
  • Firefox · no support
  • Safari · no support

Not Baseline, and not tracked as a web-feature: webstatus.dev lists only the base Gamepad API (Baseline Widely available) and its haptics/touch/VR extensions. BCD has no api/GamepadRawInputChangeEvent.json entry (404 on 2026-11-08). The ChromeStatus record shows the event in developer trial from Chrome 147 and an origin trial from Chrome 149, with no ship milestone.

An extension to the Gamepad API that fires a gamepadrawinputchanged event on window whenever a connected gamepad reports new input. You no longer have to poll navigator.getGamepads() on every animation frame. Each event carries a snapshot Gamepad plus index arrays saying exactly which axes, buttons and touches changed, so latency-sensitive games can respond at the device’s report rate.

In developer trial This feature is in development and behind a flag in Chrome 147. Enable it with chrome://flags/#gamepad-raw-input-change-event (the flag named in the ChromeStatus record), with chrome://flags/#enable-experimental-web-platform-features, or by launching with --enable-blink-features=GamepadRawInputChangeEvent. The Blink runtime feature GamepadRawInputChangeEvent is status: "experimental" with an origin-trial name of the same spelling in runtime_enabled_features.json5 (checked 2026-11-08). The event name and interface shape may change before shipping. The name has already changed once: early material (including the ChromeStatus summary) says rawgamepadinputchange, but Chromium dispatches gamepadrawinputchanged.

Evidence divergence, resolved 2026-11-08. An earlier revision of this page used the ChromeStatus summary’s event name rawgamepadinputchange and attributed it to the W3C Gamepad specification. That name does not occur in the spec. Chromium’s event_type_names.json5 registers gamepadrawinputchanged, and navigator_gamepad.cc dispatches it. The explainer and the ChromeStatus sample demo use the same name. This page now documents what Chromium implements; the ChromeStatus summary text is stale.

why it exists

The existing Gamepad API requires polling: you call navigator.getGamepads() inside a requestAnimationFrame loop, which runs at most at the display refresh rate (typically 60 Hz). A gamepad can report input at 1000 Hz or higher. The gap means input can be 1–16 ms stale before the application sees it, and short presses that start and end between two polls are missed entirely. An event-driven model fires when the hardware reports new data, independently of the frame rate.

Security and privacy. According to the explainer, gamepadrawinputchanged events fire only after a gamepad user gesture (for example a button press). This guards against fingerprinting connected devices. The events expose no state that polling doesn’t already expose. Chromium samples gamepad data only while a gamepad event listener exists and the page is visible (navigator_gamepad.cc), so a background tab receives no events.

Source: explainer — accessibility, privacy, and security considerations; chromestatus summary; w3c/gamepad#4.

Syntax

WebIDL as implemented in Chromium (gamepad_raw_input_change_event.idl, …_init.idl, window_gamepad.idl; fetched 2026-11-08). It is identical to the explainer’s appendix apart from the RuntimeEnabled extended attribute:

[Exposed=Window, RuntimeEnabled=GamepadRawInputChangeEvent]
interface GamepadRawInputChangeEvent : GamepadEvent {
  constructor(DOMString type, optional GamepadRawInputChangeEventInit eventInitDict = {});
  readonly attribute FrozenArray<long> axesChanged;
  readonly attribute FrozenArray<long> buttonsValueChanged;
  readonly attribute FrozenArray<long> buttonsPressed;
  readonly attribute FrozenArray<long> buttonsReleased;
  readonly attribute FrozenArray<long> touchesChanged;
};

dictionary GamepadRawInputChangeEventInit : GamepadEventInit {
  FrozenArray<long> axesChanged;
  FrozenArray<long> buttonsValueChanged;
  FrozenArray<long> buttonsPressed;
  FrozenArray<long> buttonsReleased;
  FrozenArray<long> touchesChanged;
};

// On Window (window_gamepad.idl)
[RuntimeEnabled=GamepadRawInputChangeEvent] attribute EventHandler ongamepadrawinputchanged;
window.addEventListener("gamepadrawinputchanged", (event) => { /* … */ });
window.ongamepadrawinputchanged = (event) => { /* … */ };
new GamepadRawInputChangeEvent("gamepadrawinputchanged", { gamepad, buttonsPressed: [0] });
Source: Chromium IDL; explainer — proposed WebIDL.

shape of the API

One new event on window, dispatched for each input change of a connected gamepad:

gamepadrawinputchanged event

Targetwindow. The event does not bubble and is cancelable (Chromium creates it with Bubbles::kNo, Cancelable::kYes). Cancelling has no defined effect.
Fires whenChromium compares the newly sampled gamepad state with the previous one and finds a changed axis, button value, pressed state or touch. One event per changed gamepad, without coalescing. It fires only while a gamepadrawinputchanged listener (or ongamepadrawinputchanged) is registered and the page is visible.
event.gamepadInherited from GamepadEvent: a snapshot Gamepad (id, index, connected, mapping, buttons, axes, touches, timestamp) at the moment of the change.
event.axesChangedFrozenArray<long> of indices into gamepad.axes whose value changed since the last event.
event.buttonsValueChangedIndices into gamepad.buttons whose value changed (includes analog triggers moving without crossing the pressed threshold).
event.buttonsPressedIndices of buttons that went from released to pressed.
event.buttonsReleasedIndices of buttons that went from pressed to released.
event.touchesChangedIndices into gamepad.touches whose touch state or position changed (touchpad/trackpad controllers).
Constructor inputstype (string) and an optional GamepadRawInputChangeEventInit. It extends GamepadEventInit, whose gamepad member is specified inconsistently. The W3C Recommendation-track snapshot declares required Gamepad gamepad, the editor’s draft declares Gamepad? gamepad = null, and Chromium’s gamepad_event_init.idl implements Gamepad? gamepad (with a TODO to make it required, crbug 647693). In Chrome, omitting it does not throw and event.gamepad is null; passing a non-Gamepad object throws a TypeError (WebIDL interface conversion). The array members are optional; in Chromium an omitted array reads as empty. Non-numeric entries convert to long under the usual WebIDL rules. Verified in headless Chrome 153 with --enable-blink-features=GamepadRawInputChangeEvent (2026-11-08): new GamepadRawInputChangeEvent("gamepadrawinputchanged", {buttonsPressed: [0, "2"]}) gives gamepad === null, axesChanged [], buttonsPressed [0, 2] (frozen), isTrusted === false. {gamepad: {}} throws TypeError. Without the flag, neither GamepadRawInputChangeEvent nor ongamepadrawinputchanged exists on window, which makes "GamepadRawInputChangeEvent" in window a reliable feature test.
Source: Chromium navigator_gamepad.cc (DispatchGamepadRawInputChangedEvent); explainer — event properties; Gamepad spec — GamepadEventInit. Field names may change before ship.

example

Event-driven input loop (replaces polling)

// Previously: polling inside rAF
function pollLoop() {
  const gamepads = navigator.getGamepads();
  if (gamepads[0]) {
    handleInput(gamepads[0]);
  }
  requestAnimationFrame(pollLoop);
}

// With gamepadrawinputchanged: fires per input change, not per frame.
// Feature-detect, and keep polling as the fallback.
if ("GamepadRawInputChangeEvent" in window) {
  window.addEventListener("gamepadrawinputchanged", (event) => {
    handleInput(event.gamepad);
  });
} else {
  requestAnimationFrame(pollLoop);
}

React only to what changed

window.addEventListener("gamepadrawinputchanged", (event) => {
  const pad = event.gamepad;

  for (const i of event.buttonsPressed) {
    triggerAction(pad.index, i, pad.timestamp);   // e.g. i === 0 is "A" on a standard mapping
  }
  for (const i of event.buttonsReleased) {
    releaseAction(pad.index, i);
  }
  for (const i of event.axesChanged) {
    const value = pad.axes[i];                     // -1.0 … 1.0
    if (i === 0 && Math.abs(value) > 0.1) moveCharacter(value);
  }
  for (const i of event.touchesChanged) {
    const touch = pad.touches[i];
    updateTrackpad(touch.touchId, touch.position);
  }
});

relation to the existing Gamepad API

Polling model (navigator.getGamepads())Still works. Returns a snapshot at whatever rate you call it. Good for most games; no changes needed.
gamepadrawinputchanged eventsOne per input change, uncoalesced. Use when latency or missed sub-frame presses matter. The explainer deliberately leaves out frame alignment and coalescing (a getCoalescedEvents()-style gamepadinputchange was considered and rejected for now). Expect a high event rate and keep handlers cheap.
gamepadconnected / gamepaddisconnectedUnchanged. Still the mechanism for detecting connect/disconnect. If a pad disconnects and reconnects in one update, Chromium dispatches disconnect before connect, and both before any input event for that pad.
Source: explainer — alternatives considered; navigator_gamepad.cc (MaybeDispatchGamepadEvents).
