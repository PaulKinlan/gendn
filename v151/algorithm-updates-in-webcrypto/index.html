Algorithm Updates in WebCrypto

Limited availability

  • Chrome · 155 (BCD, experimental)
  • Edge · mirrors Chrome (BCD)
  • Firefox · preview · KEM methods only (BCD)
  • Safari · no support (BCD)

Not on the Baseline register (no web-features entry for this feature at webstatus.dev, re-verified 2026-10-06). Browser support is now recorded in browser-compat-data (fetched 2026-10-06): Chrome 155 for all six new SubtleCrypto members, flagged experimental; Firefox carries the four encapsulate/decapsulate methods in preview builds only. ChromeStatus (updated 2026-09-11) still records status “Proposed” with no desktop ship milestone — it lags the shipped state recorded by BCD and Chromium trunk.

A modernization of the Web Cryptography API: post-quantum algorithms (ML-KEM, hybrid PQ/classical KEMs, ML-DSA, SLH-DSA), modern AEAD ciphers (AES-OCB, ChaCha20-Poly1305), the SHA-3/Keccak family (SHA3 digests, cSHAKE, TurboSHAKE, KangarooTwelve, KMAC), and the Argon2 password KDF — plus new SubtleCrypto methods for key encapsulation (encapsulateKey/decapsulateKey and their -Bits forms), getPublicKey, and a static supports() capability check.

Shipped experimental in Chrome 155 — the trial paths below are historical

Chromium trunk reads the runtime feature WebCryptoPQC as status “stable” (runtime_enabled_features.json5, fetched 2026-10-06) and BCD records Chrome 155 for all six new members (experimental). The developer trial (Chrome 150, behind a flag) and the desktop origin trial (Chrome 151–154) have concluded. Every algorithm remains OPTIONAL to implement per the spec, and other engines’ support is partial — so feature-detection is still required:

  • Chrome 155 and later: feature-detect with the static SubtleCrypto.supports(operation, algorithm) before calling — algorithm availability varies by build and platform.
  • Chrome 151–154 (concluded): the “WebCrypto Additional Algorithms” desktop origin trial with public registration, at developer.chrome.com/origintrials. The origin-trial id 1379790335835635713 and feature name WebCryptoAdditionalAlgorithms202606 were recorded from the chromestatus listing during the 2026-07-28 verification; neither appears in the chromestatus API response re-fetched 2026-10-06 nor in trunk runtime_enabled_features.json5, so both are reported as a historical record, unverified against current sources.
  • Chrome 150 (historical): developer trial behind --enable-blink-features=WebCryptoPQC.
  • Serve over HTTPS — the partial interface is exposed with [SecureContext] in Window and Worker contexts.

Syntax

The update extends SubtleCrypto with four key-encapsulation methods (KEM support for ML-KEM), a public-key derivation helper, and a static feature-detection method. IDL from the WICG draft:

[SecureContext, Exposed=(Window,Worker)]
partial interface SubtleCrypto {
  Promise<EncapsulatedKey> encapsulateKey(
    AlgorithmIdentifier encapsulationAlgorithm,
    CryptoKey encapsulationKey,
    AlgorithmIdentifier sharedKeyAlgorithm,
    boolean extractable,
    sequence<KeyUsage> keyUsages
  );
  Promise<EncapsulatedBits> encapsulateBits(
    AlgorithmIdentifier encapsulationAlgorithm,
    CryptoKey encapsulationKey
  );

  Promise<CryptoKey> decapsulateKey(
    AlgorithmIdentifier decapsulationAlgorithm,
    CryptoKey decapsulationKey,
    BufferSource ciphertext,
    AlgorithmIdentifier sharedKeyAlgorithm,
    boolean extractable,
    sequence<KeyUsage> keyUsages
  );
  Promise<ArrayBuffer> decapsulateBits(
    AlgorithmIdentifier decapsulationAlgorithm,
    CryptoKey decapsulationKey,
    BufferSource ciphertext
  );

  Promise<CryptoKey> getPublicKey(
    CryptoKey key,
    sequence<KeyUsage> keyUsages
  );

  static boolean supports(DOMString operation,
                   AlgorithmIdentifier algorithm,
                   optional [EnforceRange] unsigned long? length = null);
  static boolean supports(DOMString operation,
                   AlgorithmIdentifier algorithm,
                   AlgorithmIdentifier additionalAlgorithm);
};
Source: WICG WebCrypto Modern Algorithms — Partial SubtleCrypto interface 
enum KeyFormat { "raw-public", "raw-private", "raw-seed", "raw-secret",
                 "raw", "spki", "pkcs8", "jwk" };

enum KeyUsage { "encrypt", "decrypt", "sign", "verify", "deriveKey", "deriveBits",
                "wrapKey", "unwrapKey",
                "encapsulateKey", "encapsulateBits",
                "decapsulateKey", "decapsulateBits" };

dictionary EncapsulatedKey {
  CryptoKey sharedKey;
  ArrayBuffer ciphertext;
};

dictionary EncapsulatedBits {
  ArrayBuffer sharedKey;
  ArrayBuffer ciphertext;
};
Source: WICG WebCrypto Modern Algorithms — Data types, Encapsulation dictionaries
sharedKey — documented cells
DimensionSourced fact
inputsNo source fact. sharedKey is a dictionary field, not a callable: it has no parameter list and a caller never passes it. It is set by the encapsulate algorithm, not by the caller. (The word sharedKey also names the sharedKeyAlgorithm/sharedKey local in encapsulateKey()/decapsulateKey(), but that is a different, same-named variable — see outputs.)
outputsThe draft sets it to the encapsulated shared secret. In encapsulateKey() (§3.2.1): “Let encapsulatedKey be a new EncapsulatedKey dictionary with sharedKey set to sharedKey and ciphertext set to the ciphertext field of encapsulatedBits.” The type differs by dictionary (§4): CryptoKey sharedKey in EncapsulatedKey (dfn), versus ArrayBuffer sharedKey in EncapsulatedBits (dfn). In encapsulateBits() the EncapsulatedBits result carries the raw bits: “Let result be the result of converting encapsulatedBits to an ECMAScript Object in realm, as defined by [WebIDL].”
errorsNo source fact. A dictionary field raises nothing; the throw/reject sites belong to the six methods (§3.2.1–§3.2.5), not to the field. There is no field-level error prose in §4.
contextNo source fact. The draft gives the two dictionaries no [SecureContext]/Exposed attribute and no context prose — they are plain data types. The [SecureContext, Exposed=(Window,Worker)] marker sits on the partial interface SubtleCrypto (§3), not on either dictionary, so it does not attach to sharedKey.
compatibilityNo source fact. BCD api/SubtleCrypto.json carries no sharedKey key (only the six method keys); there is no compatibility datum for the field.
securityPrivacyThe field holds the shared secret, and the draft’s only statement about it is the §4 definition sentence: “The EncapsulatedKey dictionary represents an encapsulated key comprised of a sharedKey and a ciphertext.” There is no dedicated Security/Privacy Considerations section in the draft (no “security”/“privacy” heading exists), so beyond that definition sentence and the interface-level [SecureContext] there is no field-level security/privacy fact to cite.
Source: WICG §4 Encapsulation dictionaries; §3.2.1; §3.2.2; BCD api/SubtleCrypto.json (no sharedKey key)
ciphertext — documented cells
DimensionSourced fact
inputsNo source fact as a field. As a dictionary member ciphertext is not callable and is set by the encapsulate algorithm. Separately, ciphertext is a BufferSource parameter to decapsulateKey()/decapsulateBits(), consumed per §3.2.3: “Let ciphertext be the result of getting a copy of the bytes held by the ciphertext parameter passed to the decapsulateKey() method.” (and the analogous decapsulateBits() step in §3.2.4). That is the parameter, not the dictionary field.
outputsThe draft sets it to the encapsulation ciphertext (the material sent to the recipient). In encapsulateKey() (§3.2.1): “Let encapsulatedKey be a new EncapsulatedKey dictionary with sharedKey set to sharedKey and ciphertext set to the ciphertext field of encapsulatedBits.” The type is the same in both dictionaries (§4): ArrayBuffer ciphertext in both EncapsulatedKey (dfn) and EncapsulatedBits (dfn).
errorsNo source fact. A dictionary field raises nothing; there is no field-level error prose in §4.
contextNo source fact. The two dictionaries carry no [SecureContext]/Exposed attribute and no context prose; the interface-level [SecureContext, Exposed=(Window,Worker)] does not attach to ciphertext.
compatibilityNo source fact. BCD api/SubtleCrypto.json carries no ciphertext key; there is no compatibility datum for the field.
securityPrivacyThe field holds the public encapsulation ciphertext (transmitted, not secret), and the draft’s only statement about it is the §4 definition sentence: “The EncapsulatedBits dictionary represents encapsulated key bits comprised of a sharedKey and a ciphertext.” There is no dedicated Security/Privacy Considerations section in the draft, so beyond that definition sentence there is no field-level security/privacy fact to cite.
Source: WICG §4 Encapsulation dictionaries; §3.2.1; §3.2.3; §3.2.4; BCD api/SubtleCrypto.json (no ciphertext key)

The draft also extends JsonWebKey with pub and priv fields (WICG §5, per RFC 9964) for the algorithms’ JWK representations.

New SubtleCrypto members
MemberContract
encapsulateKey(alg, key, sharedAlg, extractable, usages)Runs the KEM encapsulation against the recipient public key and resolves to an EncapsulatedKey: the freshly encapsulated shared secret as a CryptoKey (algorithm sharedAlg, with the requested usages) plus the ciphertext to send
encapsulateBits(alg, key)Same encapsulation, but the shared secret comes back as raw ArrayBuffer bits (an EncapsulatedBits) instead of an imported CryptoKey

decapsulateBits(alg, key, ciphertext)Decapsulates to raw ArrayBuffer bits
getPublicKey(key, keyUsages)Derives the public CryptoKey from an asymmetric private key, so only the private half needs to be stored
static supports(operation, algorithm, length?) / static supports(operation, algorithm, additionalAlgorithm)Static capability check: is this algorithm identifier (with parameters, key length, or a second algorithm) supported for the named operation on this build?

Errors

The six methods (encapsulateKey, encapsulateBits, decapsulateKey, decapsulateBits, getPublicKey, and exportKey) fail in two different ways, and they are not interchangeable: a named DOMException that an implementer can catch by name, versus a promise rejection produced by algorithm normalization whose value is the normalization result itself and carries no name to catch. Every throw and rejection below is a step of the WICG — WebCrypto Modern Algorithms draft (the partial SubtleCrypto interface, §3.2); the W3C Web Cryptography API base Recommendation contributes none of these sites — they are all new draft algorithm steps.

Promise rejections from normalization — not catchable by name

Six sites return a promise rejected with the normalization result, not with a named DOMException. An implementer cannot catch these by name because the rejection value is the failed normalization result itself.

Unnamed normalization rejections (6)
MethodTrigger clause (verbatim, WICG draft)
encapsulateKey()“If an error occurred, return a Promise rejected with normalizedEncapsulationAlgorithm.”
encapsulateKey()“If an error occurred, return a Promise rejected with normalizedSharedKeyAlgorithm.”
encapsulateBits()“If an error occurred, return a Promise rejected with normalizedEncapsulationAlgorithm.”

Because these rejections are returned (not thrown), the draft's throw-to-rejection convention does not apply to them — see the Lifecycle section.

supports() — no throw contract, and the one implied WebIDL TypeError

The static supports() method never throws: every failure path returns false. This is stated by the draft's own algorithm, not an inference:

supports() — no-throw contract
Clause (verbatim, WICG draft)
“If operation is not one of "encrypt", "decrypt", "sign", "verify", "digest", "generateKey", "deriveKey", "deriveBits", "importKey", "exportKey", "wrapKey", "unwrapKey", "encapsulateKey", "encapsulateBits", "decapsulateKey", "decapsulateBits" or "getPublicKey", return false.”
“If an error occurred, return false.”

Separate from that algorithm contract is a WebIDL binding-level TypeError implied by the IDL — not an algorithm step. The first overload declares optional [EnforceRange] unsigned long? length = null, so a length that is a non-integer or outside [0, 232−1] produces a WebIDL TypeError before the algorithm body runs. The draft's algorithm does not raise this — the [EnforceRange] extended attribute in the IDL does.

Source: WICG §3.2.1, §3.2.2, §3.2.3, §3.2.4, §3.2.5, §3.2.6, §3 (IDL)

Lifecycle

For each of the six methods the contract records one of exactly two cases: the draft states the promise/parallel-task pattern (quoted below), or the draft does not state it (recorded as an absence, not composed and not “not-applicable”). The draft states the pattern identically in §3.2.1–§3.2.5; the four sentences are:

“Let realm be the relevant realm of this.”

“Let promise be a new Promise.”

“Return promise and perform the remaining steps in parallel.”

“Queue a global task on the crypto task source, given realm’s global object, to perform the remaining steps.”

And the draft converts any throw inside the parallel work into a promise rejection with this convention, stated verbatim in each of the same five methods:

“If the following steps or referenced procedures say to throw an error, queue a global task on the crypto task source, given realm’s global object, to reject promise with the returned error; and then terminate the algorithm.”

Per method, confirmed against the draft’s own text (presence of the five sentences checked in each §3.2.x body):

Lifecycle — per method
MethodPromise/parallel-task pattern
encapsulateKey()The draft states it — all four sentences above, plus the rejection convention.
encapsulateBits()The draft states it — all four sentences above, plus the rejection convention.
decapsulateKey()The draft states it — all four sentences above, plus the rejection convention.
decapsulateBits()The draft states it — all four sentences above, plus the rejection convention.
getPublicKey()The draft states it — all four sentences above, plus the rejection convention. One difference the source itself makes: its NotSupportedError (“then return a Promise rejected with a NotSupportedError”) is returned before “Let realm be the relevant realm of this.”, so that rejection does not go through the queue-a-global-task convention.
supports()The draft does not state the pattern. supports() is synchronous and “returns a boolean”, with no “Let promise be a new Promise” step, no parallel section, and no queue-a-global-task step. This is a difference the source itself makes (the method has no promise at all), not one drawn here.

What the draft does not state: it has no dedicated lifecycle prose beyond the sentences above, and it assigns the two dictionary fields (sharedKey, ciphertext) no lifecycle of their own — they are populated by the encapsulate/decapsulate algorithms and have no independent “created when” step beyond being fields of the dictionaries named in §4. The draft also does not state any timing or ordering guarantee for the “Queue a global task … perform the remaining steps” step relative to the encapsulate/decapsulate operation other than what the quoted sentences say.

Source: WICG §3.2.1, §3.2.2, §3.2.3, §3.2.4, §3.2.5, §3.2.6

The new algorithm roster

Twelve algorithm families are registered — 37 registered names in total — each with its own operations section in the spec (key generation, import/export, and the operations below). All are optional to implement per the spec — use SubtleCrypto.supports() to detect them. The Reference column cites both the crypto-math standard and the WICG registration section that carries the web-facing grammar (registered name strings, WebIDL parameter dictionaries, JWK mappings).

Examples

// 1. Feature-detect first — the method and every algorithm are optional
const kemOK = SubtleCrypto.supports?.("encapsulateKey", "ML-KEM-768") ?? false;
if (!kemOK) throw new DOMException("ML-KEM-768 is unavailable", "NotSupportedError");

// 2. Recipient generates an ML-KEM key pair
const pair = await crypto.subtle.generateKey("ML-KEM-768", true, [
  "encapsulateKey", "decapsulateKey",
]);

// 3. Sender encapsulates a shared secret against the recipient public key
const { sharedKey, ciphertext } = await crypto.subtle.encapsulateKey(
  "ML-KEM-768", pair.publicKey, "AES-GCM", true, ["encrypt", "decrypt"],
);
// -> send { ciphertext } to the recipient; keep sharedKey local

// 4. Recipient decapsulates with the private key — same shared secret
const recovered = await crypto.subtle.decapsulateKey(
  "ML-KEM-768", pair.privateKey, ciphertext, "AES-GCM", true, ["encrypt", "decrypt"],
);
Source: composed from the WICG partial SubtleCrypto interface and ML-KEM registered names and operations; the draft does not provide an ML-KEM JavaScript example.

The three remaining methods — encapsulateBits, decapsulateBits, and getPublicKey — are not exercised by the snippet above. The short composed example below covers them. Like the example above, it is composed from the named sources, not copied from the draft, and the draft does not provide a JavaScript example for these members. It reuses pair (the ML-KEM key pair generated above) and uses only identifiers the draft or the example above already declare.

// encapsulateBits — the raw-bits form: no CryptoKey import of the shared secret
// sourceRef: https://wicg.github.io/webcrypto-modern-algos/#SubtleCrypto-method-encapsulateBits
const bits = await crypto.subtle.encapsulateBits("ML-KEM-768", pair.publicKey);
// bits.sharedKey → ArrayBuffer; bits.ciphertext → ArrayBuffer (send this)
// sourceRef: https://wicg.github.io/webcrypto-modern-algos/#x4-encapsulation-dictionaries

// decapsulateBits — recover the same raw bits on the recipient side
// sourceRef: https://wicg.github.io/webcrypto-modern-algos/#SubtleCrypto-method-decapsulateBits
const bitsRecovered = await crypto.subtle.decapsulateBits(
  "ML-KEM-768", pair.privateKey, bits.ciphertext,
);
// bitsRecovered → ArrayBuffer, equal to bits.sharedKey

// getPublicKey — recover the public half from a stored private key
// sourceRef: https://wicg.github.io/webcrypto-modern-algos/#SubtleCrypto-method-getPublicKey
const recoveredPublic = await crypto.subtle.getPublicKey(
  pair.privateKey, ["encapsulateKey"],
);
Source: composed from the WICG encapsulateBits method, decapsulateBits method, getPublicKey method, and Encapsulation dictionaries; the draft does not provide an ML-KEM JavaScript example for these three members. The usage value "encapsulateKey" in the getPublicKey call is the KeyUsage enum member declared in the same partial interface (the draft’s getPublicKey prose does not itself enumerate which usages each algorithm supports for a public key).
