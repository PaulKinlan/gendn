Connection Allowlists - Embedded Enforcement

Extends Connection Allowlists (shipped in Chrome 152) with an opt-in embedded-enforcement handshake modeled on CSP Embedded Enforcement. An embedder declares a required allowlist on an <iframe connectionallowlist="..."> element (reflected as HTMLIFrameElement.connectionAllowlist); the browser sends Sec-Required-Connection-Allowlist with the frame navigation, blocks any framed document that fails to opt in (via a satisfying Connection-Allowlist header, an Allow-Connection-Allowlist-From response header, or local-scheme inheritance), and propagates the unresolved requirement down the frame and worker tree so descendants can only tighten — never loosen — the constraint.

Limited availability — Origin trial in Chrome 157–168 (not yet enabled by default); Firefox and Safari have no implementation yet

  • Chrome · Origin trial 157–168 (desktop, Android, WebView; not yet shipped enabled by default)
  • Edge · Mirrors Chromium origin trial (Microsoft authored the spec & explainer)
  • Firefox · Positive on base Connection Allowlists (#1322); no embedded-enforcement implementation
  • Safari · No signal (#583)

No web-features entry or BCD record exists for Embedded Enforcement yet (checked 2026-11-27 against webstatus.dev and BCD api/HTMLIFrameElement.json); base connection-allowlists is Limited availability (Chrome/Edge 152). MDN has no reference pages for HTMLIFrameElement.connectionAllowlist, Sec-Required-Connection-Allowlist, or Allow-Connection-Allowlist-From.

Origin trial in Chrome 157–168 (not yet enabled by default): To enroll in production, register for the ConnectionAllowlistEmbeddedEnforcement origin trial (ID 3609072151384031233) at Chrome Origin Trials and deliver the token on the embedding document. For local testing without a token, enable chrome://flags/#enable-experimental-web-platform-features or launch Chromium with --enable-blink-features=ConnectionAllowlistEmbeddedEnforcement (defined with status: "experimental" and origin_trial_feature_name: "ConnectionAllowlistEmbeddedEnforcement" in runtime_enabled_features.json5; there is no dedicated chrome://flags toggle).

why it exists

Base Connection Allowlists (Connection-Allowlist) restricts only the document or worker whose response delivered the header. A cross-origin <iframe> establishes its own policy container from its own HTTP response, so an unconstrained third-party widget embedded inside a tightly allowlisted host page could still exfiltrate data sent to it over postMessage() or URL parameters. Embedded Enforcement closes that bypass by letting the embedder require a minimum allowlist of its framed documents (and any nested frames or workers inside them), while requiring explicit opt-in from cross-origin documents so embedders cannot silently break unwilling third-party sites.

Source: Embedded Enforcement explainer; W3C Connection Allowlists §4; ChromeStatus 5657801797009408.

Syntax

Embedded Enforcement spans one reflected WebIDL attribute on HTMLIFrameElement (§4.1), two HTTP headers (§4.2), and the policy-container opt-in and satisfies subsumption algorithm (§4.3–§4.4):

partial interface HTMLIFrameElement {
  [CEReactions] attribute DOMString connectionAllowlist;
};
<!-- Embedder declares required allowlist on <iframe> (RFC 9651 Structured Field list) -->
<iframe connectionallowlist='("https://good.example" response-origin)'
        src="https://widget.example/"></iframe>

# Browser -> framed document (forbidden Sec-* request header, set by user agent only):
Sec-Required-Connection-Allowlist: ("https://good.example" response-origin)

# Framed document opts in via either:
# (1) An asserted Connection-Allowlist that satisfies (is a subset of) the requirement:
Connection-Allowlist: (response-origin)
# (2) Or Allow-Connection-Allowlist-From (ABNF: origin-or-null / "*"):
Allow-Connection-Allowlist-From: https://embedder.example
# (3) Or implicit inheritance via policy container for local schemes (about:srcdoc, data:).

This reference documents all four developer-facing surfaces: the <iframe connectionallowlist> content & reflected IDL attribute, the Sec-Required-Connection-Allowlist request header, the Allow-Connection-Allowlist-From response header, and the opt-in handshake, satisfies strictness comparison, and policy container inheritance.

Source: W3C Connection Allowlists §4.1; §4.2; Blink html_iframe_element.idl.

<iframe connectionallowlist> & HTMLIFrameElement.connectionAllowlist

Inputs. Set the connectionallowlist HTML content attribute (case-insensitive in HTML) or assign the reflected iframe.connectionAllowlist DOMString property using the exact RFC 9651 Structured Field list-of-inner-lists grammar of the Connection-Allowlist header: a parenthesized inner list of quoted URLPattern strings and/or the response-origin token, with optional inner-list parameters (redirects=allow|block, webrtc=allow|block, report-to=<token>; both redirects and webrtc default to block). In Blink (ParseConnectionAllowlistAttribute()), a valid attribute value must be non-empty, at most 4096 characters (kMaxLengthConnectionAllowlistAttribute), parse cleanly as a Structured Field list whose first item is an inner list (with zero parser issues and no CR/LF), and be at least as strict as any requirement the embedder already inherited from its own parent.

Outputs. Reading iframe.connectionAllowlist reflects the raw content attribute string (empty string if unset). At navigation time, HTML’s determine the required connection allowlist algorithm snapshots the validated attribute string (or falls back to the embedder’s inherited parent required string if the attribute is empty, over-long, malformed, or looser than parent required) into target snapshot params and navigation params. Because the attribute is snapshotted per navigation (mirroring sandbox), mutating iframe.connectionAllowlist takes effect on the frame’s next navigation.

Source: W3C Connection Allowlists §4.1; §4.4 Obtaining and enforcing a requirement; Blink html_iframe_element.cc.

Sec-Required-Connection-Allowlist request header

Inputs. Generated automatically by the browser process during create navigation params by fetching whenever the navigation’s snapshotted required connection allowlist is non-null. Because its name begins with Sec-, Sec-Required-Connection-Allowlist is a Fetch forbidden request-header: page JavaScript cannot set, spoof, or delete it via fetch() or new Request().

Outputs. The framed server receives the unresolved serialized Structured Field requirement string verbatim (for example Sec-Required-Connection-Allowlist: ("https://good.example" response-origin)). Keeping the string unresolved ensures that the response-origin token resolves against the framed document’s own response URL rather than freezing to the embedder’s origin, allowing servers to inspect what is required and decide whether to opt in.

Source: W3C Connection Allowlists §4.2; §5.2 Integration with HTML.

Allow-Connection-Allowlist-From response header

Inputs. Returned by the framed HTTP response using the ABNF grammar Allow-Connection-Allowlist-From = origin-or-null / "*" (identical to Allow-CSP-From): either a single serialized origin such as https://embedder.example (with scheme, host, and non-default port if any, no trailing slash or path), the literal string null (for opaque origins), or the wildcard * to consent to any embedder.

Outputs. Per §4.2, the browser compares the header value byte-for-byte against * or the byte-serialized embedder request origin (with zero URL parsing, matching Fetch’s Access-Control-Allow-Origin check). When it matches, the navigation is allowed to commit and the browser enforces the embedder’s required allowlist inside the framed document’s policy container alongside any allowlist the response itself asserted.

Source: W3C Connection Allowlists §4.2; W3C CSP Embedded Enforcement.

Opt-in handshake, satisfies subsumption, and policy container inheritance

Inputs. When a child navigable receives a navigation response under a non-null required connection allowlist, Fetch runs should be blocked by Connection Allowlist embedded enforcement against the response’s headers, URL, and the embedder’s request origin.

Outputs & three opt-in paths. A framed navigation succeeds if and only if one of the following three opt-in conditions holds:

Connection Allowlists Embedded Enforcement opt-in paths and resulting policy container state (W3C Connection Allowlists §4.3–§4.4)
Opt-in pathConditionEnforced allowlists on framed document
1. Asserted Connection-Allowlist satisfies requirementResponse’s parsed Connection-Allowlist (enforcing) satisfies the requirement: every asserted URLPattern struct appears in the requirement’s pattern list (conservative syntactic set-membership; no semantic subsumption), and if the requirement sets redirects=block or webrtc=block the candidate also sets block. An empty () allowlist is a subset of every allowlist.Document’s own stricter/equal Connection-Allowlist is enforced (the redundant requirement is not appended), and the unresolved requirement string is stored in the policy container’s required connection allowlist for descendants.
2. Allow-Connection-Allowlist-From headerHeader equals * or byte-matches the embedder’s serialized request origin.Parsed requirement is appended to the document’s policy container connection allowlists alongside any own headers, and the unresolved requirement string is stored for descendants.
3. Local-scheme document (about:srcdoc, data:)Implicit opt-in (no HTTP response).Inherits the embedder’s entire policy container directly, including both its enforced allowlists and its required connection allowlist.

Never-loosen rule across nesting. When a constrained frame embeds a grandchild iframe with its own connectionallowlist attribute, the browser checks whether the grandchild’s attribute is at least as strict as the inherited requirement (treating response-origin literally as equal to itself before any response URL is known). If the grandchild attempts to loosen the policy, its attribute is ignored and the parent’s stricter requirement is inherited unchanged.

Source: W3C Connection Allowlists §4.3 Comparing allowlists; §4.4 Obtaining and enforcing; §5.2 HTML integration.

Errors, malformed inputs, and blocked navigations

  • No opt-in (navigation blocked): If a framed HTTP response omits both a matching Allow-Connection-Allowlist-From header and a satisfying Connection-Allowlist header, Fetch replaces the navigation response with a network error (the iframe fails to load and logs a console/DevTools Issue message).
  • Malformed asserted Connection-Allowlist: Parses to null and does not count as an opt-in; unless Allow-Connection-Allowlist-From matches, the frame is blocked.
  • Malformed, empty, or >4096-character connectionallowlist attribute: Ignored defensively by Blink (ParseConnectionAllowlistAttribute()) so an unparseable value is never emitted in Sec-Required-Connection-Allowlist. If the embedder already has an inherited requirement, that inherited requirement continues to apply unchanged; if there is no inherited requirement, no requirement is enforced (rather than blocking the frame).
  • Origin mismatch or trailing slash in Allow-Connection-Allowlist-From: Because matching is byte-for-byte against the serialized origin (no URL parsing), returning https://embedder.example/ with a trailing slash fails to match https://embedder.example and blocks the frame.
  • Syntactic-only satisfies mismatch: Because satisfies uses URL-pattern-struct equality rather than semantic subsumption, asserting ("https://good.example/api/v1") does not satisfy a requirement of ("https://good.example/*") unless the server either matches the exact pattern or sends Allow-Connection-Allowlist-From.
  • Ungovernable contexts (fenced frames): Contexts whose requests are not governed by their embedder’s policy container (such as fenced frames) are blocked whenever an embedder requires a connection allowlist of them.
Source: W3C Connection Allowlists §4.4; §6.2 Security; Blink html_iframe_element.cc.

Context, exposure, and feature detection

HTMLIFrameElement.prototype.connectionAllowlist is exposed in Window contexts when the ConnectionAllowlistEmbeddedEnforcement runtime feature is active (via origin trial token in Chrome 157–168 or the experimental web platform flag). Feature-detect via "connectionAllowlist" in HTMLIFrameElement.prototype before assuming browsers will send Sec-Required-Connection-Allowlist or enforce frame blocking; browsers without the feature ignore the HTML attribute and load the iframe unrestricted. Workers inherit policy container’s required connection allowlist via clone a policy container.

Source: Blink html_iframe_element.idl; W3C Connection Allowlists §5.2.

Lifecycle, navigation snapshotting, and propagation

  1. Attribute declaration: Embedder sets <iframe connectionallowlist="..."> or assigns iframe.connectionAllowlist. Blink validates length (≤4096) and Structured Field syntax and syncs the requirement to the browser process.
  2. Navigation snapshot: On every navigation of the child navigable (including child-initiated navigations and redirects), the browser snapshots the effective requirement (the iframe’s valid attribute if at least as strict as the parent’s requirement, otherwise the parent’s requirement) into target snapshot params → navigation params.
  3. Request header & opt-in check: For HTTP(S) navigations, the browser attaches Sec-Required-Connection-Allowlist to the outgoing request and evaluates the final response’s Allow-Connection-Allowlist-From and Connection-Allowlist headers; failure aborts the navigation with a network error.
  4. Policy container commit & inheritance: On opt-in (or for about:srcdoc / data: local-scheme documents), the resolved requirement is enforced on all outgoing connections (subresource fetches, navigations, WebSockets, WebTransport, DNS prefetch) for the lifetime of that document, and the unresolved string persists on its policy container so descendant frames and workers inherit it with fresh per-frame response-origin resolution.
Source: W3C Connection Allowlists §5.2 Integration with HTML; Embedded Enforcement explainer.

Examples

Interactive handshake lab & full HTML / HTTP opt-in handshake

<!-- On https://embedder.example (with origin trial token for Chrome 157-168) -->
<iframe
  connectionallowlist='("https://api.good.example/*" response-origin)'
  src="https://widget.example/embed">
</iframe>
# 1. Request sent automatically by the browser (forbidden Sec-* header):
GET /embed HTTP/1.1
Host: widget.example
Sec-Required-Connection-Allowlist: ("https://api.good.example/*" response-origin)

# 2a. Opt-in Option A: acknowledge the embedder origin (enforced via policy container):
HTTP/1.1 200 OK
Allow-Connection-Allowlist-From: https://embedder.example

# 2b. Opt-in Option B: assert an own Connection-Allowlist that satisfies the requirement:
HTTP/1.1 200 OK
Connection-Allowlist: (response-origin)

Feature detection and dynamic connectionAllowlist reflection in JavaScript

function createConstrainedWidgetFrame(widgetUrl, allowedPatterns) {
  const supportsEmbeddedEnforcement =
    "connectionAllowlist" in HTMLIFrameElement.prototype;

  const iframe = document.createElement("iframe");
  const serialized = `(${allowedPatterns.join(" ")})`;

  if (supportsEmbeddedEnforcement) {
    // Takes effect on the navigation triggered when src is assigned (like sandbox).
    iframe.connectionAllowlist = serialized;
  } else {
    // Fallback attribute reflection for inspection; older browsers will not enforce it.
    iframe.setAttribute("connectionallowlist", serialized);
  }

  iframe.src = widgetUrl;
  return { iframe, supportsEmbeddedEnforcement };
}
Source: W3C Connection Allowlists §4.1; Blink html_iframe_element.idl.

Security and privacy

  • Mandatory opt-in: Cross-origin frames are never silently constrained; they must assert a satisfying Connection-Allowlist or return Allow-Connection-Allowlist-From naming the embedder (or *), preventing embedders from probing or breaking unwilling cross-origin sites.
  • Browser-process trust boundary: Even under a compromised-renderer threat model, the renderer only reflects and length-validates the attribute; the browser process enforces every trust decision (subsumption check, emitting Sec-Required-Connection-Allowlist, verifying opt-in, storing the requirement on the policy container, and re-checking on every navigation).
  • No relaxation & conservative failure: Descendants can only tighten requirements; malformed asserted allowlists parse to null and fail closed; ungovernable contexts such as fenced frames are blocked when an embedder sets a requirement.
  • Same-origin & worker boundary caveats: Connection Allowlists govern network connections, not postMessage() / BroadcastChannel / MessageChannel. Same-origin contexts with different allowlists remain an open follow-up (potentially requiring agent-cluster isolation); isolate untrusted widgets on distinct origins or with iframe sandbox, and restrict blob: shared workers with CSP worker-src.
  • Privacy: Exposes Sec-Required-Connection-Allowlist to the framed server by design (analogous to Sec-Required-CSP) so it can decide whether to opt in; introduces no persistent storage or cross-site tracking state.
Source: W3C Connection Allowlists §6.2 Security — Embedded Enforcement; Embedded Enforcement explainer (Security & Privacy).
