CSS position-visibility:anchor{s}-valid

Ships the anchor-valid keyword on the CSS position-visibility property. When an absolutely positioned element references its default anchor box (via position-area, anchor(), anchor-size(), or anchor-center) and that default anchor cannot be resolved to an acceptable anchor element, position-visibility: anchor-valid computes the positioned box’s visibility to force-hidden so orphaned tooltips and popovers vanish instead of floating over unrelated content.

Limited availability — singular anchor-valid ships in Chrome 157, Safari 27, and Firefox 162 (earlier Firefox 147 and Safari 26.2 shipped plural anchors-valid)

  • Chrome · 157 (anchor-valid; flag CSSPositionVisibilityAnchorValid)
  • Edge · 157 (mirrors Chromium)
  • Firefox · 162 for anchor-valid (147 for deprecated anchors-valid)
  • Safari · 27 for anchor-valid (26.2 for deprecated anchors-valid)

The anchor-positioning web-feature is currently Limited availability on webstatus.dev (Chrome/Edge 157, Safari 27; Firefox pending 162). BCD css/properties/position-visibility.json records anchor-valid in Chrome 157, Safari 27, and Firefox 162 (checked 2026-11-27). Although MDN’s position-visibility page lists the keyword name, it omits the default-anchor-only rule, acceptable-anchor resolution criteria, multi-keyword composition prose, and worked anchor-valid examples (and its formal definition table still lists Initial value: anchors-visible) — so gendn publishes a complete spec-backed reference here.

why it exists

When an anchor-positioned popover, tooltip, or callout loses its anchor — because the anchor was removed from the DOM, hidden with display: none, moved out of anchor-scope, or placed inside content-visibility: hidden skipped contents — CSS Anchor Positioning falls back to the positioned element’s containing block, leaving the callout stranded in a meaningless corner of the viewport. Chrome originally implemented the plural keyword anchors-valid under crbug.com/329703412, then reverted it because checking every anchor referenced by any anchor() or anchor-size() function on an element was ambiguous and expensive. The CSSWG subsequently narrowed the semantics to evaluate only the default anchor box and renamed the keyword to singular anchor-valid (w3c/csswg-drafts#10201), making it clear, predictable, and shippable in Chrome 157.

Source: ChromeStatus 5136856479039488; crbug.com/329703412; w3c/csswg-drafts#10201.

Syntax

Formal CSS value-definition grammar from CSS Anchor Positioning Module Level 1 §6.6 (note the || combinator: one or more of anchor-valid, anchor-visible, and no-overflow may appear in any order, mutually exclusive with always):

position-visibility = always | [ anchor-valid || anchor-visible || no-overflow ]

/* Initial value: anchor-visible
   Applies to:    absolutely positioned boxes
   Inherited:     no
   Computed:      as specified
   Animation:     discrete */

Blink’s PositionVisibility::ParseSingleValue() accepts anchor-valid (enabled by CSSPositionVisibilityAnchorValid) alongside anchor-visible (plus legacy alias anchors-visible) and no-overflow. Blink does not parse the never-shipped plural spelling anchors-valid.

This reference covers both parts of the Chrome 157 position-visibility: anchor-valid contract: default-anchor-only anchor-valid semantics and multi-keyword composition with anchor-visible and no-overflow.

Source: CSS Anchor Positioning 1 §6.6; Blink longhands_custom.cc.

position-visibility: anchor-valid — default-anchor-only semantics

Inputs. Applies to an absolutely positioned box whose position-visibility list includes anchor-valid, evaluated against that box’s default anchor (established by position-anchor: <anchor-name>, or an implicit anchor such as a Popover invoker when position-anchor: auto / normal resolves one).

Outputs & hiding trigger. Per CSS Anchor Positioning 1 §6.6, position-visibility: anchor-valid computes the positioned box’s visibility to force-hidden (strongly hidden: neither the element nor any descendant with visibility: visible paints or receives hit-testing, while layout geometry is preserved) if and only if both conditions hold:

  1. The box actually references the default anchor box — for example, via position-area, an omitted-anchor anchor() or anchor-size() function, or anchor-center alignment.
  2. The default anchor box cannot be resolved to an acceptable anchor element.

Multi-keyword composition with anchor-visible and no-overflow

Inputs & outputs. Because the grammar uses || (always | [ anchor-valid || anchor-visible || no-overflow ]), authors can combine anchor-valid with anchor-visible and/or no-overflow in any order, separated by whitespace. The conditions are evaluated as a logical OR: the positioned box becomes strongly hidden whenever any listed condition fails:

  • position-visibility: anchor-valid anchor-visible — hides the positioned box if its default anchor disappears or is scrolled/clipped out of view by an intervening box.
  • position-visibility: anchor-valid anchor-visible no-overflow — hides the positioned box if its default anchor is invalid, invisible/clipped, or the positioned box still overflows its inset-modified containing block after position-try-fallbacks.
  • No duplicate keywords & exclusive with always: Repeating a keyword (anchor-valid anchor-valid) or combining always with anchor-valid (always anchor-valid) is a parse error and causes the declaration to be dropped.
  • Chained anchors: If positioned box A becomes strongly hidden due to position-visibility: anchor-valid (or anchor-visible), another positioned box B using A as its default anchor with position-visibility: anchor-visible is also hidden so chained callouts do not float detached.
Source: CSS Anchor Positioning 1 §6.6; Blink longhands_custom.cc.

Errors, invalid values, and cross-browser fallbacks

  • Parse-time invalidation: Unknown keywords (including plural anchors-valid in Chrome 157), duplicate keywords (anchor-valid anchor-valid), or combining always with any other keyword fail parsing in PositionVisibility::ParseSingleValue(). The entire position-visibility declaration is ignored and falls back to the preceding valid declaration (or initial value anchor-visible).
  • Cross-browser plural/singular cascade fallback: Firefox 147–161 and Safari 26.2–26.x recognize only plural anchors-valid / anchors-visible, whereas Chrome 157 recognizes only singular anchor-valid (plus anchor-visible and deprecated alias anchors-visible). List the plural declaration first, followed by the singular declaration so every engine keeps the one it understands.
  • Feature detection & JS fallback: Test native support with CSS.supports("position-visibility", "anchor-valid"). For engines without either spelling, observe anchor disconnection or visibility with MutationObserver / isConnected and toggle the hidden attribute on the tooltip.
Source: Blink longhands_custom.cc; BCD css/properties/position-visibility.json.

Context, applicability, and accessibility

position-visibility: anchor-valid applies only to absolutely positioned boxes (position: absolute or position: fixed) inside normal CSS stylesheets, inline styles, Shadow DOM stylesheets, and CSS.supports(). It requires no secure context, permission, or user activation. Because CSS Anchor Positioning does not create or alter ARIA/accessibility relationships (CSS Anchor Positioning 1 §7), visually hiding an element with anchor-valid (visibility: force-hidden) removes it from painting and hit-testing, while authors remain responsible for proper semantic associations (such as Popover API popovertarget or aria-describedby) and keyboard focus management if the anchor is dynamically removed.

Source: CSS Anchor Positioning 1 §6.6; CSS Anchor Positioning 1 §7 Accessibility Implications.

Layout evaluation timing, serialization, and animation

Evaluation & layout lifecycle. Default-anchor resolution runs during out-of-flow layout whenever the anchor’s DOM connection, anchor-name, anchor-scope, display type, or content-visibility state changes. Because anchor-valid resolves to visibility: force-hidden rather than display: none, the positioned element keeps its layout box without triggering re-layout of siblings, and immediately reappears if an acceptable default anchor becomes valid again.

Canonical CSSOM serialization. Per Blink’s PositionVisibility::ParseSingleValue() and CSSValueFromComputedStyleInternal(), regardless of the authored order, multi-keyword lists serialize in canonical grammar order: anchor-valid first, then anchor-visible, then no-overflow (for example, position-visibility: no-overflow anchor-valid serializes as "anchor-valid no-overflow").

Animation. position-visibility has animation type discrete: transitions and animations flip between keyword lists at 50% progress rather than interpolating continuously.

Source: CSS Anchor Positioning 1 §6.6; Blink longhands_custom.cc.

Examples

Live demo & default-anchor-only CSS pattern

.trigger {
  anchor-name: --card-trigger;
}

.callout {
  position: fixed;
  position-anchor: --card-trigger;
  position-area: block-end span-inline-end;

  /* Cross-browser overlap: Firefox 147–161 & Safari 26.2 use plural;
     Chrome 157+, Safari 27+, Firefox 162+ use singular. */
  position-visibility: anchors-valid anchors-visible;
  position-visibility: anchor-valid anchor-visible;
}
Source: CSS Anchor Positioning 1 §6.6; CPS conformance suite.

Feature detection, multi-keyword composition & serialization probe

const supportsAnchorValid = CSS.supports("position-visibility", "anchor-valid");
const supportsComposed = CSS.supports(
  "position-visibility",
  "anchor-valid anchor-visible no-overflow",
);

function inspectCanonicalOrder() {
  const el = document.createElement("div");
  el.style.setProperty(
    "position-visibility",
    "no-overflow anchor-visible anchor-valid",
  );
  // Canonical grammar order in Chrome 157: "anchor-valid anchor-visible no-overflow"
  return {
    supportsAnchorValid,
    supportsComposed,
    serialized: el.style.getPropertyValue("position-visibility"),
  };
}

Security and privacy

position-visibility: anchor-valid is a pure CSS layout/paint visibility rule evaluated strictly within the element’s own document and anchor scope. It exposes no cross-origin information, introduces no new permissions, storage, or network surface, and leaks no fingerprinting signal beyond standard CSS feature support probing via CSS.supports().

Source: ChromeStatus 5136856479039488; CSS Anchor Positioning 1 §6.6.
