CSS corner shorthand properties

Limited availability

  • Chrome · targeted at 157 (shorthands; corner-shape itself shipped in 139)
  • Edge · mirrors Chrome
  • Firefox · not shipped; position “Positive”
  • Safari · not shipped; “In development” view

Not a Baseline feature: the shorthands have no BCD entries yet (BCD css/properties/ has no corner.json or corner-top-left.json — both raw fetches 404, 2026-11-01) and no MDN pages (the corner URL 404s). The umbrella corner-shape web-feature is Baseline limited (Chrome/Edge 139 only, queried 2026-11-01).

A family of shorthands for corner styling in CSS Borders and Box Decorations Level 4: the corner shorthand plus per-corner (corner-top-left, …, logical corner-start-start, …) and per-edge (corner-top, …, logical corner-block-start, …) sub-shorthands. Each sets both the corner’s border-radius component and its corner-shape component in one declaration — so a squircle corner is one line: corner: squircle 1rem.

Experimental — may still be mid-rollout

The milestone=157 listing files this under “Enabled by default”, but as of 2026-11-01 the runtime flag record for CSSCornersShorthand still reads status: "experimental" at trunk and the ChromeStatus record’s status text reads “Proposed” — so the shorthands may not yet be on by default in your Chrome 157. To test regardless: enable chrome://flags/#enable-experimental-web-platform-features or launch with --enable-blink-features=CSSCornersShorthand, and feature-detect with CSS.supports("corner", "squircle 1rem") before relying on them.

why it exists

Chrome 139 shipped corner-shape (superellipse corners: squircle, bevel, scoop, notch, …), but styling one corner still took two declarations across two property families — a radius longhand and a shape longhand. The shorthands collapse that: one property per corner (or edge, or all four) that accepts both components, mirroring how border bundles width/style/color. The ChromeStatus summary frames them as letting authors set “both border-radius and corner-shape for individual corners” in a single declaration.

Source: ChromeStatus API record; explainer; css-borders-4 §3.9

syntax

Value grammars quoted verbatim from the css-borders-4 Editor’s Draft propdef tables (fetched 2026-11-01). || means either or both components, in any order:

/* the whole-box shorthand */
corner: <'corner-shape'> || <'border-radius'>
  /* initial: 0 · applies to: all elements (but see prose) */

/* per-corner sub-shorthands:
   corner-top-left | corner-top-right | corner-bottom-left | corner-bottom-right
   corner-start-start | corner-start-end | corner-end-start | corner-end-end */
corner-top-left: <'corner-top-left-shape'> || <'border-top-left-radius'>

/* per-edge sub-shorthands (set the two corners of one edge):
   corner-top | corner-right | corner-bottom | corner-left
   corner-block-start | corner-block-end | corner-inline-start | corner-inline-end */
corner-top: <'corner-top-shape'> || <'border-top-radius'>

The shape component takes a <corner-shape-value> (a keyword such as round, squircle, bevel, scoop, notch, straight, or a superellipse() function — documented on MDN’s corner-shape page); the radius component takes the corresponding border-radius longhand or shorthand grammar.

Source: css-borders-4 §3.9 propdef tables (grammar verbatim; keyword list via MDN corner-shape)

what each shorthand sets

ShorthandLonghands set
cornerAll four corner-*-shape longhands and all four border-*-radius longhands (an omitted component resets to its initial value, per CSS shorthand rules)
corner-top-left (and the other 3 physical + 4 logical per-corner forms)That corner’s corner-…-shape and border-…-radius longhands
corner-top (and the other 3 physical + 4 logical per-edge forms)The two corners of that edge: its corner-…-shape pair (<'corner-top-shape'> accepts {1,2} values) and its border-…-radius pair

Like every CSS shorthand, these reset the longhands they cover: corner: 1rem sets all radii to 1rem and all corner shapes back to their initial round. Declaration-order interleaving with the longhands follows the cascade as usual.

Source: css-borders-4 §3.9 (propdef tables); shorthand reset behavior per css-cascade-5 §shorthand properties

errors and graceful degradation

CSS properties don’t throw: in a browser without the shorthands, the whole declaration is invalid and dropped at parse time, and the longhands it would have set keep their prior values. Safe adoption pattern — declare longhands first, shorthand after, or gate on support:

.card {
  border-radius: 1rem;              /* works everywhere */
}
@supports (corner: squircle 1rem) {
  .card { corner: squircle 1rem; }  /* upgraded corners where supported */
}

/* The same pattern gates the sub-shorthands: */
@supports (corner-top-left: scoop 1rem) {
  .ticket { corner-top-left: scoop 1rem; }
}
@supports (corner-top: bevel 1rem) {
  .tab { corner-top: bevel 1rem; }
}

Because the fallback is “the declaration never applies”, pages degrade to ordinary rounded (or square) corners.

Source: declaration-dropping per css-syntax-3; css-conditional @supports

where it applies

The shorthands apply wherever their longhands do: corner-shape and border-radius apply to “all elements where border-radius can apply” (the per-corner/edge shorthands’ propdefs say “all elements (but see prose)”, deferring to the same longhand applicability). No permission, secure-context, or policy gate — availability is purely the flag state above. Usable in stylesheets, inline style, and CSS.supports().

Source: css-borders-4 §3.9 propdef tables (“Applies to” rows)

examples

/* One squircle card corner-set — was two declarations: */
.card {
  corner: squircle 1.5rem;
  /* equivalent to:
     corner-shape: squircle;
     border-radius: 1.5rem; */
}

/* Mixed corners: scooped top edge, round bottom */
.ticket {
  corner-top: scoop 1rem;
  corner-bottom: round 0.5rem;
}

/* One notched corner, logical (follows writing direction) */
.tag {
  corner-start-start: notch 0.75rem;
}

security and privacy

Pure paint-level syntax sugar over existing longhands: the shorthands expose no new rendering capability, no new measurable state, and no cross-origin surface beyond what border-radius and corner-shape already provide. The ChromeStatus record flags no security or privacy risks, and css-borders-4 carries no considerations specific to the shorthands (checked 2026-11-01; gendn-derived summary, labelled as such).

Source: ChromeStatus API record; css-borders-4
