CORS enforcement for Background Fetch

Aligns Chromium’s Background Fetch downloads with the Fetch CORS protocol by passing each request’s originating RequestMode (such as "cors" or "same-origin") into the Network Service instead of treating downloads as navigation requests (kNavigate). Cross-origin Background Fetch downloads now require valid CORS opt-in headers (Access-Control-Allow-Origin, and Access-Control-Allow-Credentials: true when credentials are included) and undergo companion Fetch security checks including CORP/COEP/DIP and Local Network Access.

Limited availability — Background Fetch is Chromium-only; Network Service CORS enforcement ships enabled by default in Chrome 157 (desktop and Android)

  • Chrome · 157 (desktop, Android; WebView & iOS unsupported; base API since Chrome 74)
  • Edge · Mirrors Chromium (157; base API since Edge 79)
  • Firefox · No implementation (Background Fetch unsupported)
  • Safari · No implementation (Background Fetch unsupported)

The background-fetch web-feature is Limited availability on webstatus.dev (Chrome 74, Edge 79; Firefox and Safari unsupported; checked 2026-11-27). BCD api/BackgroundFetchManager.json and MDN’s BackgroundFetchManager docs cover the baseline API surface but do not document Chrome 157’s Network Service CORS enforcement change, preflight restriction, or migration requirements — so gendn publishes a dedicated reference here.

why it exists

The Background Fetch specification routes every background request through Fetch so the same cross-origin security checks apply as regular fetch(). Historically, however, Chromium’s Download Service constructed the underlying network request with RequestMode::kNavigate (the mode used for top-level browser downloads), which bypassed Network Service CORS checks as well as companion security policies such as CORP, COEP, Document Isolation Policy (DIP), and Local Network Access. Although Chromium applied a post-response browser-side filter (BackgroundFetchCrossOriginFilter) to suppress unreadable response bodies, the underlying request still bypassed wire-level Fetch enforcement. Chrome 157 closes this bypass by propagating the originating fetch_request_mode (kCors / kSameOrigin) directly into network::ResourceRequest::mode.

Source: ChromeStatus 6210300985606144; Chromium download_utils.cc; Chromium Issue 515243254.

Syntax

This feature adds no new WebIDL methods or dictionaries — it enforces the existing Fetch CORS protocol across registration.backgroundFetch.fetch(), cross-origin HTTP response headers (Access-Control-Allow-Origin), Chromium’s RequiresCorsPreflight() gate (which produces failureReason = "fetch-error"), and Service Worker completion via backgroundfetchfail / record.responseReady:

// Client or Service Worker call (mode defaults to "cors"; "no-cors" rejects with TypeError)
const bgFetch = await registration.backgroundFetch.fetch(
  id,
  [new Request("https://cdn.example.com/archive.bin", { mode: "cors", credentials: "omit" })],
  { title: "Downloading archive", downloadTotal: 10_485_760 }
);

// Required response headers on cross-origin targets (credential-less):
Access-Control-Allow-Origin: *
// Or exact origin (mandatory when credentials: "include"):
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true

// Service Worker completion / failure observation:
// - Success: "backgroundfetchsuccess" -> await record.responseReady
// - CORS / preflight block (RequiresCorsPreflight): "backgroundfetchfail" with failureReason === "fetch-error"

This reference documents the three behavioral contracts developers must satisfy in Chrome 157+: request mode & Network Service CORS enforcement, cross-origin CORS-preflight blocking, and failure state & record.responseReady behavior.

Source: WICG Background Fetch fetch(); WHATWG Fetch CORS protocol; Chromium download_utils.cc.

Request mode & Network Service CORS enforcement (backgroundFetch.fetch())

Inputs. Each entry passed to registration.backgroundFetch.fetch(id, requests, options) is converted to a Fetch Request whose mode defaults to "cors" (or may be explicitly set to "cors" or "same-origin") and whose credentials defaults to "same-origin" (may be "omit", "same-origin", or "include"). Passing a Request with mode: "no-cors" is rejected upfront in Blink (background_fetch_manager.cc) with a TypeError ("the request mode must not be no-cors").

Outputs & wire behavior. In Chrome 157 (background_fetch_delegate_proxy.cc → download_driver_impl.cc → download_utils.cc), Chromium appends the serialized Origin header for CORS and non-GET/HEAD requests and copies fetch_request_mode onto network::ResourceRequest::mode:

Cross-origin CORS-preflight blocking (RequiresCorsPreflight())

Inputs. Before dispatching a request to the Download Service, Chromium’s BackgroundFetchJobController::RequiresCorsPreflight() inspects every cross-origin request’s HTTP method and header list against Fetch’s CORS-safelisted definitions:

  • Non-safelisted methods: Any cross-origin method other than GET, HEAD, or POST (for example PUT, PATCH, or DELETE) triggers a preflight requirement.
  • CORS-unsafe headers: Any cross-origin request header not on Fetch’s CORS-safelisted request-header list (for example Authorization, X-API-Key, or Content-Type: application/json) triggers a preflight requirement.

Outputs. Because Chromium’s browser-side Background Fetch controller does not yet execute CORS OPTIONS preflight exchanges, any cross-origin request for which RequiresCorsPreflight() returns true is immediately terminated without hitting the network and marked with FailureReason::FETCH_ERROR (exposed in JS as registration.failureReason === "fetch-error"). Same-origin requests bypass RequiresCorsPreflight() and may use custom methods or headers freely.

Source: Chromium background_fetch_job_controller.cc (RequiresCorsPreflight); WHATWG Fetch CORS-safelisted request headers.

Failure state, progress suppression, and BackgroundFetchRecord.responseReady

Inputs. In the Service Worker, listen for backgroundfetchsuccess and backgroundfetchfail (and optionally backgroundfetchabort), inspect event.registration.result and event.registration.failureReason, and resolve each downloaded record via await event.registration.matchAll() followed by await record.responseReady.

Outputs. When a cross-origin request fails CORS enforcement or RequiresCorsPreflight():

  • The registration transitions to result === "failure" with failureReason === "fetch-error" and dispatches the backgroundfetchfail event to the Service Worker.
  • Per BackgroundFetchJobController::DidUpdateRequest() and AbortFromDelegate(), if a cross-origin check fails, Chromium suppresses downloaded byte-progress updates and masks download-total-exceeded behind "fetch-error" so cross-origin resource sizes are never leaked to the calling origin.
  • Awaiting record.responseReady on a failed/blocked record rejects (rather than yielding an unreadable opaque body or leaking cross-origin bytes).
Source: WICG Background Fetch BackgroundFetchRecord; Chromium background_fetch_job_controller.cc; Chromium background_fetch_cross_origin_filter.cc.

Errors, failure reasons, and migration checklist

  • TypeError at backgroundFetch.fetch() call time: Thrown immediately if any request uses mode: "no-cors", fails CSP, uses a blocked port/scheme (non-HTTPS except loopback), embeds URL credentials, or lacks transient user activation / permission.
  • backgroundfetchfail with failureReason === "fetch-error" (CORS rejection): Occurs when a cross-origin server omits Access-Control-Allow-Origin, returns * for a credentials: "include" request, omits Access-Control-Allow-Credentials: true, fails CORP/COEP/DIP or Local Network Access checks, or triggers RequiresCorsPreflight() via a non-safelisted method or custom header.
  • record.responseReady rejection: Rejects for any record whose network fetch failed; wrap await record.responseReady inside try / catch in backgroundfetchfail handlers when salvaging partial multi-file downloads.
  • Migration fixes: (1) Add Access-Control-Allow-Origin (and Access-Control-Allow-Credentials: true if needed) on cross-origin CDNs serving Background Fetch assets; (2) remove non-safelisted headers like Authorization from cross-origin Background Fetch requests (use signed URLs or proxy through your own origin instead); (3) never pass mode: "no-cors".
Source: Blink background_fetch_manager.cc; Chromium background_fetch_job_controller.cc; ChromeStatus 6210300985606144.

Context, exposure, and prerequisites

BackgroundFetchManager is exposed on ServiceWorkerRegistration.prototype.backgroundFetch in secure contexts (Window and ServiceWorkerGlobalScope) and requires an active registered Service Worker. Calling backgroundFetch.fetch() from a window context requires transient user activation (or background-fetch permission), and only https: URLs (or http: for loopback IPs during local development) are permitted. In Chromium, the Network Service CORS enforcement applies to both desktop and Android Chrome 157+; Android WebView and iOS do not support Background Fetch.

Source: WICG Background Fetch BackgroundFetchManager; Blink background_fetch_manager.cc; ChromeStatus 6210300985606144.

Lifecycle and state transitions

A Background Fetch registration progresses through five stages under Chrome 157 CORS enforcement:

  1. Renderer validation: backgroundFetch.fetch() checks URL validity, scheme, CSP, and rejects mode: "no-cors" with a TypeError before any network traffic begins.
  2. Browser preflight gate: For each queued request, BackgroundFetchJobController::StartRequest() checks mixed content and RequiresCorsPreflight(); cross-origin requests requiring a preflight fail immediately with FETCH_ERROR.
  3. Network Service fetch: BackgroundFetchDelegateProxy attaches the Origin header and forwards fetch_request_mode + credentials_mode through the Download Service into network::ResourceRequest, where the Network Service enforces CORS, CORP/COEP/DIP, and Local Network Access before streaming bytes to disk.
  4. Cross-origin response filter & progress: BackgroundFetchCrossOriginFilter validates Access-Control-Allow-Origin / Access-Control-Allow-Credentials before exposing download progress or response bodies; failures suppress progress updates and mask download-total-exceeded.
  5. Service Worker settlement: Once all requests settle, the browser wakes the Service Worker with backgroundfetchsuccess (if every record succeeded) or backgroundfetchfail (if any record failed CORS/network checks), keeping records available until the event’s waitUntil() promise settles.
Source: WICG Background Fetch lifecycle; Chromium background_fetch_job_controller.cc; Chromium download_utils.cc.

Examples

Interactive URL audit tool & CORS-safe Background Fetch registration

async function startCorsSafeBackgroundFetch(urls) {
  const reg = await navigator.serviceWorker.ready;
  if (!("backgroundFetch" in reg)) {
    throw new Error("Background Fetch API is not supported in this browser");
  }

  // Keep cross-origin requests CORS-safelisted (GET, no custom headers) so
  // Chromium's RequiresCorsPreflight() gate does not fail with "fetch-error".
  // Remote origins must return Access-Control-Allow-Origin: * (or exact origin).
  const requests = urls.map(
    (url) => new Request(url, { method: "GET", mode: "cors", credentials: "omit" })
  );

  return reg.backgroundFetch.fetch("media-pack-v1", requests, {
    title: "Downloading media pack",
    downloadTotal: 15_000_000,
  });
}
Source: WICG Background Fetch fetch(); Chromium background_fetch_job_controller.cc.

Service Worker handling of backgroundfetchfail and record.responseReady

// Inside service-worker.js
self.addEventListener("backgroundfetchsuccess", (event) => {
  event.waitUntil(
    (async () => {
      const cache = await caches.open("bg-downloads");
      const records = await event.registration.matchAll();
      for (const record of records) {
        const response = await record.responseReady;
        await cache.put(record.request, response);
      }
      await event.updateUI({ title: "Download complete" });
    })()
  );
});

self.addEventListener("backgroundfetchfail", (event) => {
  event.waitUntil(
    (async () => {
      const { id, failureReason } = event.registration;
      // CORS blocks, missing Access-Control-Allow-Origin, and preflight blocks
      // all surface as failureReason === "fetch-error".
      const records = await event.registration.matchAll();
      const failedUrls = [];
      for (const record of records) {
        try {
          await record.responseReady;
        } catch {
          failedUrls.push(record.request.url);
        }
      }
      console.error("Background fetch failed", { id, failureReason, failedUrls });
      await event.updateUI({ title: `Download failed (${failureReason})` });
    })()
  );
});
Source: WICG Background Fetch BackgroundFetchRecord; MDN BackgroundFetchRecord.responseReady.

Security and privacy

This change is a security hardening fix tracked under Chromium’s Background Fetch security meta bug (crbug.com/515243254). Previously, dispatching Background Fetch downloads with RequestMode::kNavigate allowed sites to bypass Network Service CORS checks as well as Cross-Origin Resource Policy (CORP), Cross-Origin Embedder Policy (COEP), Document Isolation Policy (DIP), and Local Network Access protections. Propagating fetch_request_mode into the Network Service closes the bypass, ensures cross-origin servers must explicitly opt in via Access-Control-Allow-Origin, and prevents cross-origin resource size disclosure by suppressing progress updates and masking download-total-exceeded behind "fetch-error" on failed CORS checks.

Source: ChromeStatus 6210300985606144; Chromium Issue 515243254; Chromium download_utils.cc; Chromium background_fetch_job_controller.cc.
