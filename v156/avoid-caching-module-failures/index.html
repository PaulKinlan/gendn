Avoid caching module failures

Changes HTML’s fetch a single module script algorithm so that failed module fetches (network errors, non-2xx HTTP statuses, CORS/SRI fetch failures, and MIME type mismatches) remove their entry from the document or worker’s module map instead of caching a permanent null failure. Subsequent calls such as dynamic import() now issue a fresh network request rather than immediately re-rejecting, enabling manual recovery over unstable networks without reloading the page or appending cache-busting query strings.

Limited availability — shipped in Firefox 155 and Chrome/Edge 156, with Safari in Technology Preview

  • Firefox · 155

why it exists

Previously, HTML’s fetch a single module script algorithm wrote a permanent null value into the document or worker’s module map whenever fetching a module failed due to a transient offline blip, flaky mobile radio, or temporary HTTP 503. Because the module map is consulted before any network activity, every subsequent import() for the same (requestURL, moduleType) pair rejected immediately without touching the network for the entire lifetime of the page or worker. Developers had to force full page reloads or invent cache-busting URL suffixes (such as import(`${url}#retry=1`), which broke module singleton identity and risked duplicate execution). Removing failed fetches from the module map allows straightforward, standards-compliant retry logic.

Source: Avoid caching module failures explainer; ChromeStatus 5214647044145152.

Syntax & entry points

This feature introduces no new JavaScript syntax or Web APIs. It modifies the runtime module-loading contract behind existing ES module entry points — dynamic import() (including import attributes for JSON/CSS modules), static import dependency graphs, and <script type="module"> — all keyed in the environment’s module map by the (requestURL, moduleType) tuple. Failed fetches reject with a TypeError and evict the module map entry, while parse failures reject with a SyntaxError and remain cached:

// Existing dynamic import() entry points governed by the module map (requestURL, moduleType)
async function loadModules() {
  const jsMod = await import("/assets/widget.js");
  const jsonMod = await import("/assets/config.json", { with: { type: "json" } });
  return { jsMod, jsonMod };
}

This reference covers both halves of the updated module map contract: module map eviction on failed fetches and in-flight callback deduplication vs. permanently cached parse/evaluation errors.

Source: HTML Living Standard — Fetch a single module script; whatwg/html#10327.

Module map failure eviction

Inputs. Any module fetch keyed by (requestURL, moduleType) in the environment settings object’s module map, where requestURL is the resolved request URL (before redirects) and moduleType is "javascript-or-wasm", "json", or "css" (driven by import(), static import, or <script type="module">).

Outputs & eviction rule. Per whatwg/html#10327 and Blink’s ModuleMap::Entry::NotifyNewSingleModuleFinished(), when a single-module fetch finishes with a null module script, the browser calls RemoveEntry() to delete moduleMap[(url, moduleType)] instead of storing null, then notifies all waiting callers with null (which rejects dynamic import() with TypeError). A later import() for the same (url, moduleType) sees no cached entry and issues a brand-new fetch. In Blink and WPT dynamic-import/repeated-imports.any.js, this covers:

  • Network errors (offline, DNS failure, TCP reset, timeout, aborted connection, CORS failure, or blocked CSP / failed Subresource Integrity fetch).
  • Non-2xx HTTP status responses (such as 404 Not Found, 500 Internal Server Error, or 503 Service Unavailable).
  • Invalid or mismatched MIME types (for example, serving application/json or text/html for a JS import(), which produces null and removes the entry so a later retry succeeds once the server sends text/javascript).
Source: whatwg/html#10327; Blink module_map.cc; WPT dynamic-import/repeated-imports.any.js.

In-flight deduplication and what stays cached

Inputs. Concurrent or sequential import() requests targeting the same (requestURL, moduleType), or a module graph whose root or transitive child fails during fetching, parsing (SyntaxError), linking, or top-level evaluation.

Outputs & failure matrix. Only fetch-stage failures that yield a null module script are evicted from the module map. Once a valid response with a matching MIME type is received, the resulting ModuleScript object is stored in the module map even if parsing or evaluation fails, preserving JavaScript’s single-evaluation module invariant:

Errors and HTTP cache pitfalls

  • Retry still rejects while broken: Evicting the module map entry causes the retry of import() to reach the network again; if the origin is still unreachable or returning 404, the retry rejects again with TypeError.
  • HTTP cache is separate from the module map: Removing the module map entry allows Fetch to run again, but if the server sent a cacheable error response (for example 404 with Cache-Control: max-age=300), the browser’s HTTP cache may still satisfy the retry with the cached error without hitting the origin. Serve transient errors (5xx, temporary 404, captive-portal responses) with Cache-Control: no-store or no-cache.
  • Parse errors (SyntaxError) remain sticky: A truncated or malformed JS/JSON payload served with HTTP 200 and a valid MIME type creates an errored ModuleScript in the module map. Retrying the exact same URL will not re-fetch corrected source until the document or worker reloads.
  • Type-attribute mismatch: Importing module.json without { with: { type: "json" } } rejects with TypeError under key (url, "javascript-or-wasm") and does not poison import("./module.json", { with: { type: "json" } }) (verified in WPT json-module/repeated-imports.any.js).
Source: HTML Living Standard; WPT json-module/repeated-imports.any.js.

Context and exposure

Applies to the module map of every Document (Window), DedicatedWorkerGlobalScope, and SharedWorkerGlobalScope (tested across all three globals in WPT repeated-imports.any.html). No secure context or permission is required beyond standard CORS requirements for module scripts. Controlled in Blink by ModuleMapDoNotCacheFailedFetch (status: "stable" in runtime_enabled_features.json5).

Source: HTML Living Standard — Module map; Blink runtime_enabled_features.json5.

Module map state transitions and concurrent deduplication

Per whatwg/html#10327, HTML replaced the legacy "fetching" string placeholder in the module map with an explicit list of pending completion callbacks:

  1. Cache hit (ModuleScript): If moduleMap[(url, moduleType)] holds a ModuleScript (succeeded or parse-errored), immediately invoke onComplete with that record and return without fetching.
  2. In-flight hit (callback list): If a fetch for (url, moduleType) is already in progress, append onComplete to the entry’s callback list and return. Concurrent import() calls share a single HTTP request and all settle together when it finishes.
  3. Cache miss: Insert a new list « onComplete » at moduleMap[(url, moduleType)] and start Fetch.
  4. Settlement: When Fetch finishes, snapshot callbacks. If the result is null (network error, non-ok status, or MIME mismatch), remove moduleMap[(url, moduleType)]; otherwise store the resulting ModuleScript. Then invoke every callback in callbacks. Because removal happens before callbacks run, a retry triggered inside a .catch() handler immediately sees an empty slot and starts a fresh fetch.
Source: whatwg/html#10327; Blink module_map.cc.

Examples

Live demo & exponential-backoff import() retry helper

async function importWithRetry(specifier, { maxAttempts = 3, baseDelayMs = 300 } = {}) {
  let lastError;
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      // Retries reuse the canonical URL — no cache-busting query string needed
      // because failed fetches are evicted from the module map.
      return await import(specifier);
    } catch (err) {
      lastError = err;
      // SyntaxError indicates a parse/link error (which remains cached in the module map);
      // only retry TypeError fetch failures.
      if (!(err instanceof TypeError) || attempt === maxAttempts) {
        throw err;
      }
      const delay = baseDelayMs * (2 ** (attempt - 1));
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
  throw lastError;
}
Source: HTML Living Standard; Avoid caching module failures explainer.

Legacy-browser fallback & JSON module type-attribute retry

// If you must also support older engines (Chrome <=155, Firefox <=154, Safari stable)
// that permanently cache null fetch failures, fall back to a retry query param only
// after confirming a plain retry failed without hitting the network.
async function importJsonConfig(url) {
  try {
    return await import(url, { with: { type: "json" } });
  } catch (err) {
    if (err instanceof TypeError) {
      // Retry the same module map key (url, "json") on Chrome 156+ / Firefox 155+
      return await import(url, { with: { type: "json" } });
    }
    throw err;
  }
}

Security and privacy

Evicting failed fetches from the module map preserves all existing security invariants: every retried module fetch runs the full Fetch, CORS, Content Security Policy (script-src), MIME-type, and Subresource Integrity (SRI) checks from scratch, and Blink continues to verify CSP and SRI metadata before reusing cached module map entries (module_map.cc). No new permissions or storage surfaces are added. Operational caution: because failed import() calls now re-hit the network, always cap retry attempts and apply exponential backoff so client retries do not amplify load during an origin outage.

Source: Blink module_map.cc; ChromeStatus 5214647044145152.
