WebTransport headers and responseHeaders

Adds custom HTTP request headers to WebTransportOptions.headers (accepting any Fetch HeadersInit) and exposes the server’s handshake reply through the read-only, immutable WebTransport.responseHeaders property, enabling authentication tokens, routing metadata, and capability negotiation on the initial extended CONNECT handshake.

Limited availability — options.headers and responseHeaders ship in Chrome 156 (BCD records 157), Firefox 160, and Safari 27.3 / preview (base WebTransport is Baseline Newly available since 2026-03-24)

  • Chrome · 156 per ChromeStatus (BCD records 157; desktop, Android, WebView)
  • Edge · Mirrors Chromium
  • Firefox · 160 (per BCD)
  • Safari · 27.3 for responseHeaders / preview for options.headers (iOS false)

Base webtransport is Baseline Newly available since 2026-03-24 on webstatus.dev, with no separate web-features entry yet for custom handshake headers (checked 2026-11-27). BCD api/WebTransport.json tracks both options_headers_parameter and responseHeaders (recording Chrome 157, Firefox 160, Safari preview / 27.3, and Safari iOS false), whereas ChromeStatus 5194104408506368 files the feature under “Enabled by default” in Chrome 156.

what Chrome 156 actually does

Verified directly in Blink’s web_transport_options.idl, web_transport.cc, and WPT webtransport/headers.https.any.html:

  • Synchronous constructor validation: WebTransport::Init() parses options.headers through Headers::Create() before opening a socket, so invalid header names, non-ByteString values (code points above U+00FF), or malformed pair arrays throw TypeError synchronously. Setting wt-available-protocols (ASCII case-insensitive) throws TypeError("The 'wt-available-protocols' header cannot be set.") — use options.protocols instead.
  • Silent Fetch forbidden request-header stripping: Entries matched by cors::IsForbiddenRequestHeader(name, value) (such as Cookie, Host, Origin, Sec-*, or Proxy-*) are silently omitted rather than throwing, matching Fetch’s request-header guard.
  • Response filtering & immutability: responseHeaders starts as null while connecting. In WebTransport::OnConnectionEstablished() — before ready fulfills — Blink builds a Headers object with Headers::kImmutableGuard (so set(), append(), and delete() throw TypeError), stripping wt-protocol (exposed via transport.protocol) as well as Fetch forbidden response-header names set-cookie and set-cookie2 (case-insensitive).
  • Secure context & Workers: Available only in secure contexts (HTTPS) in both Window and Worker scopes, matching base WebTransport.
const supportsResponseHeaders =
  typeof WebTransport === "function" &&
  "responseHeaders" in WebTransport.prototype;

async function connectWithAuth(url, token) {
  const transport = new WebTransport(url, {
    headers: {
      Authorization: `Bearer ${token}`,
      "X-Client-Capabilities": "av1,opus",
    },
  });

  // null until the extended CONNECT handshake completes
  console.log("before ready:", transport.responseHeaders);
  await transport.ready;

  const sessionId = transport.responseHeaders?.get("X-Session-Id") ?? null;
  return { transport, sessionId, supportsResponseHeaders };
}
