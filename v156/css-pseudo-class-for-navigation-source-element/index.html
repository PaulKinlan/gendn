CSS pseudo-class for navigation source element

Limited availability

  • Chrome · 156
  • Edge · mirrors Chrome per BCD
  • Firefox · not supported
  • Safari · not supported

Not a Baseline feature: webstatus.dev has no web-features entry for the selector (query returned 0 results, 2026-10-25). BCD css/selectors/navigation-source.json (verified 2026-10-25) records Chrome 156, Edge mirroring Chrome, and no Firefox or Safari support, with status.experimental: true. Single-engine feature — see browser compatibility.

The :navigation-source pseudo-class matches the element that triggered the document’s current navigation — the clicked link, the submitted form, or its submit button — and keeps matching it for the duration of that navigation. It is the CSS reflection of the Navigation API’s NavigateEvent.sourceElement, so a stylesheet can mark the outgoing element (a loading state, an outline, or a view-transition-name for an expanding-thumbnail transition) without any script.

Experimental — early-draft spec, single engine

The selector is enabled by default in Chrome 156 (no flag needed: the runtime flag record for NavigationSourcePseudoClass reads status: "stable"), but the API surface may still move: BCD marks it experimental: true, the defining spec is an early Editor’s Draft whose Privacy/Security sections are still “To be written”, no other engine ships it, and the ChromeStatus record’s implementation status text still reads “Proposed” (2026-10-25). In earlier Chrome versions you can test it via chrome://flags/#enable-experimental-web-platform-features or --enable-blink-features=NavigationSourcePseudoClass. Treat it as progressive enhancement — see error handling for how non-supporting browsers drop rules that use it.

syntax

The selector takes no arguments. Its grammar, as defined by CSS Navigation Module Level 1 § 2.2 (Editor’s Draft, fetched 2026-10-25):

:navigation-source

Like any pseudo-class it composes with other selector parts: a:navigation-source, form:navigation-source .spinner, .card:has(:navigation-source). As a single pseudo-class it contributes class-level specificity (0,1,0) per Selectors Level 4.

what it can match

The spec enumerates the elements that can trigger a navigation and therefore be matched (per § 2.2, the trigger element can be an a, an area, a form, a submit input, or a button):

  • <a> and <area> — followed links;
  • <form> — the submitted form;
  • <input type="submit"> and <button> — the activated submitter.

Formally, “the :navigation-source pseudo-class matches any element el where the current navigation state is not null, and el is its source element” (quoted verbatim, 2026-10-25). The source element is the same element the Navigation API exposes as NavigateEvent.sourceElement (IDL: readonly attribute Element? sourceElement, read from the HTML Standard 2026-10-25).

Source: css-navigation-1 § 2.2; HTML Standard — NavigateEvent; Selectors 4 — specificity

how matching is decided: the current navigation state

Whether :navigation-source matches is defined entirely by the document’s current navigation state — a spec-level tuple of old/new URL, old/new history index, navigation type, phase, and source element. The algorithm (summarized from the Editor’s Draft algorithm, fetched 2026-10-25):

  • If the document is not fully active, the state is null — nothing matches.
  • Before the document has been revealed, the state is built from the Navigation API’s activation with phase committed and source element null — so on the destination page of a cross-document navigation, :navigation-source does not match anything.
  • Otherwise the state reflects the navigation API’s ongoing (or traversing) navigate event, moving through the phases loading → ready → committed; the source element is that navigate event’s source element.
  • If there is no ongoing navigate event, the state is null — once the navigation finishes, the pseudo-class stops matching.

what that means in practice

On the page where the user clicks a link or submits a form, the triggering element starts matching when the navigation starts and — per the ChromeStatus summary — “stays selected throughout the navigation”. The explainer states the window for each kind: “For a same-document navigation, it relies on the navigation API and on its definition of whether a navigation is ‘committed’. For a cross-document navigation, it starts when the navigation is initiated, and ends in the first frame of the new page.” Styling applies on the outgoing document; the new document never sees a matching :navigation-source (its pre-reveal state carries a null source element).

Navigations that happen before the page is revealed do not reflect in CSS at all — the spec notes “navigations that occur before the page is revealed, e.g. calling pushState() in the head do not reflect in CSS” (quoted 2026-10-25).

error handling and non-supporting browsers

The pseudo-class takes no arguments, so there is no invalid-argument case. In browsers that don’t implement it (Firefox, Safari — see compatibility), :navigation-source is an unknown pseudo-class, which makes the selector invalid; per Selectors Level 4 § invalid selectors an invalid selector matches nothing, and a style rule whose complex selector list contains it is dropped entirely. Keep :navigation-source rules in their own rule (not comma-joined with selectors you need everywhere), or guard shared rules with :is()’s forgiving parsing where appropriate.

Source: css-navigation-1 — current navigation state; route-matching explainer; Selectors 4 — invalid selectors

context and exposure

This is a CSS selector feature: it is available anywhere CSS selectors run against a document (stylesheets, querySelector(), matches()), in any frame whose document is fully active. It needs no flag in Chrome 156 — the runtime feature record for NavigationSourcePseudoClass reads status: "stable" (it is also implied by the broader RouteMatching experiment, which gates the sibling :link-to() work). The state it reflects is scoped to the element’s own document: the matching algorithm consults that document’s own navigation API, so one document cannot observe another document’s navigations through this selector.

Source: runtime_enabled_features.json5; css-navigation-1 algorithm (per-document inputs)

examples

Both examples below are quoted from css-navigation-1 § 2.2 (fetched 2026-10-25). The first sets a view-transition-name on an image thumbnail inside the link that triggered the navigation — the expanding-thumbnail pattern this feature was designed for:

a:navigation-source .thumb {
  view-transition-name: active-image;
}

The second styles forms and submit buttons while their submission navigates:

form:navigation-source .submit,
.submit:navigation-source {
  outline: 3px solid green;
}

A loading indicator on the clicked link needs no script at all:

a:navigation-source::after {
  content: " …";           /* spinner/ellipsis while the navigation runs */
}
a:navigation-source {
  opacity: 0.6;
  cursor: progress;
}
Source: first two examples verbatim from css-navigation-1 § 2.2; the loading-indicator example is gendn-derived from the same matching rules (labelled accordingly)

security and privacy

  • The specification’s own Privacy Considerations and Security Considerations sections both read “To be written.” as of 2026-10-25 — the draft has not yet recorded a vendor-reviewed analysis, which is part of what the open Mozilla and WebKit position requests would surface.
  • gendn-derived observations (labelled, not from the spec): the selector exposes to CSS only information the same document’s own scripts can already read from NavigateEvent.sourceElement, and the matching algorithm’s inputs are per-document, so it does not reveal another document’s navigations. The destination page’s pre-reveal state carries a null source element, so no information about which element on the previous page was clicked crosses a document boundary via this selector.
Source: css-navigation-1 § Privacy / § Security (both “To be written”, 2026-10-25); derivation labelled gendn-derived
