WebGPU: WGSL Fragment Depth

Adds the fragment_depth WGSL language extension, introducing an optional depth_mode second parameter (less or greater) on the @builtin(frag_depth) fragment output attribute. Declaring @builtin(frag_depth, less) or @builtin(frag_depth, greater) lets a fragment shader promise that any written depth value moves monotonically in one direction relative to the rasterized fragment depth, allowing GPU hardware to preserve early-Z and hierarchical-Z culling optimizations instead of disabling them for the entire draw call.

Limited availability — ships enabled by default in Chrome 156; Safari/WebKit signaled positive via WGSL PR #6299 and Firefox has not yet signaled

  • Chrome · 156 (desktop, Android, WebView)
  • Edge · Mirrors Chromium (156)
  • Firefox · No signal yet

Support is detected synchronously at runtime with navigator.gpu.wgslLanguageFeatures.has("fragment_depth"). Neither MDN’s WebGPU documentation nor WGSL guides on MDN document fragment_depth yet, so gendn publishes the full reference here.

why it exists

Fragment shaders often write custom depth values via @builtin(frag_depth) for ray-marched impostors, custom shadow depth biasing, decals, and depth-aware volumetric effects. Without a directional guarantee, the GPU driver must assume the fragment shader could move depth in either direction (closer or farther than the rasterizer’s interpolated depth), forcing it to disable early-Z / hierarchical-Z fragment rejection for the entire draw call so every occluded pixel still executes the fragment shader. Adding the less and greater depth-mode modifiers mirrors conservative depth qualifiers already available in Vulkan/SPIR-V, Metal, HLSL, and OpenGL, allowing the driver to reject occluded fragments early whenever the interpolated depth already fails the depth test and the declared modifier cannot make it pass.

Source: ChromeStatus 5663304168112128; WGSL Fragment Depth proposal.

Syntax

Defined by gpuweb/gpuweb#6299 in WGSL §3.8.9, WGSL §4.2 requires directives, and WGSL §13.3.1.1.2 frag_depth. Both the WGSL shader grammar and the JavaScript runtime feature check are shown below:

// Optional portability directive at the top of a WGSL module (before declarations)
requires fragment_depth;

// Depth mode name-tokens (WGSL §3.8.9)
depth_mode := 'less' | 'greater'

// @builtin(frag_depth) output attribute forms (fragment stage, type f32)
@builtin(frag_depth)            // implicit unrestricted mode (any)
@builtin(frag_depth, less)      // promises output <= rasterized fragment depth
@builtin(frag_depth, greater)   // promises output >= rasterized fragment depth
// Synchronous feature detection on the WebGPU entry point (Window or DedicatedWorker)
const hasFragmentDepth = Boolean(
  navigator.gpu?.wgslLanguageFeatures?.has("fragment_depth")
);

This reference covers both halves of the surface: the fragment_depth WGSL language extension and wgslLanguageFeatures check, and the @builtin(frag_depth, less | greater) depth-mode contract.

Source: WGSL §13.3.1.1.2; WGSL §3.8.9; WGSL §4.2.

fragment_depth WGSL language extension & wgslLanguageFeatures

Inputs. Check support in JavaScript by calling navigator.gpu.wgslLanguageFeatures.has("fragment_depth") (a readonly setlike<DOMString> on GPU, exposed in Blink via wgsl_language_features.cc and mapped from wgpu::WGSLLanguageFeatureName::FragmentDepth in dawn_enum_conversions.cc). Inside WGSL, authors may optionally place requires fragment_depth; in the module’s top-level directive section before any declaration.

Outputs & behavior. Per WGSL §4.2, fragment_depth is a language extension (not a GPU device feature requiring enable or requestDevice({ requiredFeatures })). When supported by the implementation, the second parameter on @builtin(frag_depth) is active immediately whether or not requires fragment_depth; is written; adding requires fragment_depth; documents the shader’s portability bar and forces shader creation to fail cleanly on implementations that lack the extension.

Source: WGSL fragment_depth language extension; WGSL §4.2; Blink dawn_enum_conversions.cc.

@builtin(frag_depth, less | greater) depth-mode contract

Inputs. Applied to a fragment entry point’s return type or a member of its returned struct with store type f32. The optional second argument is one of two depth mode name-tokens defined in WGSL §3.8.9: less or greater. Omitting the second parameter retains unrestricted depth writes (implicitly any).

Outputs & early-Z guarantees. The output f32 sets the updated depth of the fragment in the viewport depth range (default [0.0, 1.0]). The “original depth of the fragment” is the depth property of the fragment’s RasterizationPoint (i.e. @builtin(position).z). The directional promises work as follows:

WGSL @builtin(frag_depth) depth-mode semantics and early-Z compatibility
Attribute formShader promise (when not executing discard)Early-Z / Hi-Z optimization
@builtin(frag_depth)None (unrestricted; implicitly any)Typically disables early-Z rejection for the draw call
@builtin(frag_depth, greater)Returned depth ≥ rasterized fragment depthPreserves early-Z rejection for standard depth tests (depthCompare: "less" / "less-equal"): fragments already failing at interpolated depth can only move farther away and still fail
@builtin(frag_depth, less)Returned depth ≤ rasterized fragment depthPreserves early-Z rejection for reverse-Z depth tests (depthCompare: "greater" / "greater-equal"): fragments already failing at interpolated depth can only move closer to 0 and still fail

Note that less and greater are inclusive promises (≤ and ≥ respectively, per WGSL §13.3.1.1.2) and apply only when the fragment shader returns a depth value — invoking discard exempts that fragment from the depth write.

Source: WGSL §13.3.1.1.2 frag_depth; WGSL Fragment Depth proposal.

Errors, validation, and contract violations

  • Unsupported extension (requires fragment_depth;): Calling device.createShaderModule() on an implementation that does not expose fragment_depth produces a shader-creation validation error (reported via GPUShaderModule.getCompilationInfo() and uncaptured / pushed "validation" error scopes). Guard shader variants with navigator.gpu.wgslLanguageFeatures.has("fragment_depth").
  • Invalid attribute arguments or placement: Passing any token other than less or greater (for example @builtin(frag_depth, any) or the typo lesser), applying a depth_mode parameter to any built-in other than frag_depth, using frag_depth on a non-fragment stage or input parameter, or declaring a type other than f32 fails WGSL validation at shader creation time.
  • Runtime violation of the depth-mode promise: The GPU does not throw an exception or validation error if a shader declared with @builtin(frag_depth, greater) returns a value strictly less than the rasterized depth (or strictly greater under less). Instead, per WGSL §13.3.1.1.2, an indeterminate depth value may be used for that fragment (for instance, hardware may clamp the value or cull the fragment early). Always enforce the bound explicitly in WGSL with max(inPos.z, computedDepth) for greater or min(inPos.z, computedDepth) for less.
Source: WGSL §13.3.1.1.2; WGSL §4.2; gpuweb/cts#4679.

Context and exposure

Available anywhere WebGPU is exposed: secure contexts (https:// or localhost) in Window and DedicatedWorkerGlobalScope via navigator.gpu.wgslLanguageFeatures and GPUDevice.createShaderModule(). No user permission prompt or GPUAdapter.requestDevice() feature toggle is required; because fragment_depth is a WGSL language extension, it is queried synchronously before adapter or device creation. The render pipeline using the shader must include a depthStencil configuration compatible with writing fragment depth.

Source: WGSL fragment_depth; Blink wgsl_language_features.cc.

Lifecycle and native shader-backend mapping

Compilation lifecycle. navigator.gpu.wgslLanguageFeatures is populated when the WebGPU instance initializes and remains constant for the lifetime of the browsing context. During device.createShaderModule({ code }), Chromium’s Tint compiler validates the requires fragment_depth; directive and @builtin(frag_depth, less | greater) attribute and emits the native backend qualifier when creating the GPURenderPipeline:

Examples

WGSL fragment shader with requires fragment_depth; and greater / less

The first shader uses @builtin(frag_depth, greater) for a standard depth buffer (depthCompare: "less") where an impostor or decal only pushes depth farther away from the camera, clamping with max() so the promise cannot be violated. The second shows the reverse-Z counterpart using @builtin(frag_depth, less) with depthCompare: "greater":

requires fragment_depth;

struct FragOut {
  @location(0) color: vec4<f32>,
  // Promises returned depth >= interpolated inPos.z (safe for depthCompare: "less")
  @builtin(frag_depth, greater) depth: f32,
};

@fragment
fn fs_standard_z(@builtin(position) inPos: vec4<f32>) -> FragOut {
  let biased = clamp(inPos.z + 0.002, inPos.z, 1.0);
  return FragOut(vec4<f32>(0.15, 0.55, 0.95, 1.0), biased);
}

// Reverse-Z variant (near = 1.0, far = 0.0, depthCompare: "greater"):
// pushing farther from the camera means decreasing depth (<= inPos.z).
@fragment
fn fs_reverse_z(@builtin(position) inPos: vec4<f32>) -> @builtin(frag_depth, less) f32 {
  return min(inPos.z, max(0.0, inPos.z - 0.002));
}
Source: WGSL §13.3.1.1.2; WGSL Fragment Depth proposal.

Runtime feature detection with graceful fallback in WebGPU

Query navigator.gpu.wgslLanguageFeatures.has("fragment_depth") before compiling the shader module so browsers without the extension fall back cleanly to unrestricted @builtin(frag_depth):

async function createConservativeDepthShader(device, mode = "greater") {
  const supportsFragmentDepth = Boolean(
    navigator.gpu?.wgslLanguageFeatures?.has("fragment_depth")
  );
  const validMode = mode === "less" ? "less" : "greater";
  const directive = supportsFragmentDepth ? "requires fragment_depth;\n" : "";
  const depthAttr = supportsFragmentDepth
    ? `@builtin(frag_depth, ${validMode})`
    : "@builtin(frag_depth)";
  const clampExpr = validMode === "less"
    ? "min(inPos.z, max(0.0, inPos.z - 0.002))"
    : "max(inPos.z, min(1.0, inPos.z + 0.002))";

  const code = `${directive}
struct FragOut {
  @location(0) color: vec4<f32>,
  ${depthAttr} depth: f32,
};

@fragment
fn main(@builtin(position) inPos: vec4<f32>) -> FragOut {
  return FragOut(vec4<f32>(0.2, 0.7, 0.4, 1.0), ${clampExpr});
}
`;

  const module = device.createShaderModule({ label: "conservative-depth", code });
  const info = await module.getCompilationInfo();
  const errors = info.messages.filter((m) => m.type === "error");
  if (errors.length > 0) {
    throw new Error(errors.map((m) => m.message).join("\n"));
  }
  return { module, supportsFragmentDepth };
}

Security and privacy

The fragment_depth WGSL language extension operates solely inside the caller’s own WebGPU render pass and depth attachment. It introduces no new permissions, storage, or cross-origin memory access. Checking navigator.gpu.wgslLanguageFeatures.has("fragment_depth") adds one boolean capability bit consistent with existing WGSL language extension detection. Per WGSL §13.3.1.1.2, breaking the declared less or greater promise yields an indeterminate depth value for that fragment rather than triggering undefined host behavior or cross-process GPU memory leaks.

Source: WGSL §13.3.1.1.2; ChromeStatus 5663304168112128.
