Web haptics JavaScript API

Adds navigator.playHaptics(effect, intensity) to trigger semantic, intent-driven tactile feedback ("hint", "edge", "tick", "align", "success", "error") on the user’s most recent input device. Instead of hand-tuning raw millisecond vibration patterns like navigator.vibrate(), authors express interaction intent and an optional normalized intensity in [0.0, 1.0] while the browser translates each effect to native OS waveforms under a strict anti-fingerprinting fire-and-forget contract.

Limited availability — Developer trial behind a flag in Chrome 156 (Windows 11 24H2+ backend first; not yet enabled by default); Firefox and Safari have no signal or implementation

why it exists

The legacy navigator.vibrate() API requires authors to author raw millisecond on/off duration arrays designed around mobile vibration motors, has no Safari support, and cannot express OS-native tactile intent on modern haptic touchpads, styluses, mice, or mobile actuators. The Web Haptics JavaScript API introduces a small semantic vocabulary so developers declare what happened (a subtle hover hint, a snap alignment, a discrete tick, a boundary edge, or a success/error confirmation) while the user agent selects the platform-appropriate waveform and respects user system intensity preferences.

Source: WICG Web Haptics explainer; ChromeStatus 5167864517623808.

Syntax

The live WebIDL implemented in Chromium’s navigator_haptics.idl:

enum HapticEffect {
  "hint",
  "edge",
  "tick",
  "align",
  "success",
  "error"
};

[
  ImplementedAs=HapticsController,
  RuntimeEnabled=WebHaptics,
  MeasureAs="WebDXFeature::kDRAFT_Haptics"
] partial interface Navigator {
  undefined playHaptics(HapticEffect effect, optional double intensity = 1);
};

This reference covers all three parts of the JavaScript contract: Navigator.prototype.playHaptics(), the HapticEffect enum vocabulary, and the "haptics" Permissions Policy, sticky user activation, and fenced-frame gating rules. (A companion declarative CSS haptic property built on CSS Animation Triggers is proposed in the WICG explainer but is outside this JavaScript API entry.)

Source: Blink navigator_haptics.idl; WICG Web Haptics explainer.

Navigator.prototype.playHaptics(effect, intensity)

Inputs. Accepts a required effect string belonging to HapticEffect and an optional finite double intensity defaulting to 1 (normalized range 0.0 to 1.0). Out-of-range finite values are clamped to [0.0, 1.0] in both Blink (HapticsController::PlayHaptics()) and the browser process (content::HapticsService). Where the OS exposes a system-level haptic intensity setting, effective strength is system intensity × developer intensity.

Outputs. Always returns undefined immediately (one-way fire-and-forget Mojo call). By design, the method returns no boolean or Promise so pages cannot probe whether haptic hardware is attached or whether an effect played.

Source: Blink navigator_haptics.idl; haptics_controller.cc; WICG explainer.

HapticEffect enum

Inputs & semantic mapping. Six predefined semantic strings are accepted; passing any other string fails WebIDL enum conversion with a TypeError:

"edge"Heavy boundary signal for hitting the end of a range or scroll/pull-to-refresh limit.Collide / generic / soft impact / LONG_PRESS

Outputs & device fallback. On Windows 11 24H2+, if the active input device does not advertise the preferred semantic waveform in SimpleHapticsController.SupportedFeedback, Chromium passes the OS device-type default waveform (Hover for mouse/touchpad, Click for pen) as the fallback argument to TrySendHapticWaveformWithIntensity. If neither is supported, the request is silently dropped.

Source: Blink navigator_haptics.idl; WICG explainer (Effect Vocabulary); Chromium design doc (D6.4–D6.5).

"haptics" Permissions Policy & gating rules

Inputs & required gates. Both Blink (HapticsController) and the browser-process content::HapticsService enforce four gates before forwarding to hardware:

  1. Not in a fenced frame: Calls inside a fenced frame tree are silently suppressed (matching navigator.vibrate()).
  2. Active document: Browser-side RenderFrameHost::IsActive() drops calls from BFCache-frozen or pending-deletion documents.
  3. "haptics" Permissions Policy: Default allowlist is "self" (permissions_policy_features.json5). Same-origin iframes inherit access; cross-origin iframes require explicit delegation via <iframe allow="haptics"> and HTTP Permissions-Policy: haptics=(self "https://widget.example"). Blocking logs a Permissions Policy violation report (“Haptics is disabled by permissions policy.”).
  4. Sticky user activation: Requires sticky user activation (HasStickyUserActivation()); no browser permission prompt is shown.

Outputs. When any gate fails, playHaptics() returns undefined silently without throwing (so policy/hardware differences remain unobservable to scripts).

Source: Blink haptics_controller.cc; permissions_policy_features.json5; Chromium design doc (D4, D7).

Errors, invalid arguments, and silent no-ops

  • TypeError (WebIDL binding): Thrown synchronously by navigator.playHaptics() if effect is missing or not one of the six HapticEffect values ("hint", "edge", "tick", "align", "success", "error"), or if intensity is non-finite (NaN, Infinity, -Infinity, rejected by WebIDL double).
  • Clamped intensity (no error): Finite numbers below 0.0 or above 1.0 are silently clamped to [0.0, 1.0].
  • Silent no-ops (returns undefined): Lack of sticky user activation, blocked "haptics" Permissions Policy (logs console/policy report on first bind), fenced-frame context, detached/BFCached document, non-haptic most-recent input device, unsupported OS version (<Windows 11 24H2), or user-disabled OS haptics all silently no-op.
Source: Blink navigator_haptics.idl; haptics_controller.cc; Chromium design doc.

Context, exposure, and most-recent input device targeting

navigator.playHaptics() is exposed on Window’s Navigator when WebHaptics is enabled (not on WorkerNavigator). Target selection always routes to the most recent input device: if the user last interacted with a non-haptic mouse or keyboard, nothing plays and the user agent never reroutes to another connected haptic device. Authors can optionally filter by PointerEvent.pointerType ("mouse", "pen", "touch") in event handlers, noting that mice and touchpads both report "mouse". Feature-detect with typeof navigator.playHaptics === "function" (or optional chaining navigator.playHaptics?.("align", 0.8)).

Source: WICG Web Haptics explainer; Chromium design doc (D6.6).

Lifecycle and browser-process architecture

  1. Lazy supplement & bind-time policy check: On the first call to navigator.playHaptics(), Blink creates a HapticsController supplement on Navigator, checks fenced-frame status and the "haptics" Permissions Policy once (fixed for the document lifetime), and lazily binds a one-way Mojo remote to content::HapticsService.
  2. Per-call fast path & IPC: Each call verifies HasStickyUserActivation(), clamps intensity to [0.0, 1.0], maps HapticEffect to its Mojo enum, and dispatches a one-way PlayHaptics() message.
  3. Authoritative browser re-checks: content::HapticsService (a DocumentService tied to the document lifetime) re-verifies fenced-frame status, IsActive(), "haptics" Permissions Policy, sticky user activation, and finite/clamped intensity before invoking the platform backend (on Windows, HapticsManagerImplWin on the UI thread via WinRT InputHapticsManager, primed at creation so the first click fires reliably).
  4. Navigation cleanup: Destroying or navigating away from the document drops the DocumentService and stops further haptics.
Source: Blink haptics_controller.cc; Chromium design doc (D0–D6).

Examples

Interactive effect design tool & progressive-enhancement usage

// Feature-detected semantic haptics with pointerType filtering and snap-point tracking
const VALID_EFFECTS = new Set(["hint", "edge", "tick", "align", "success", "error"]);

function triggerSemanticHaptic(effect, intensity = 1.0, pointerType = "mouse") {
  if (!VALID_EFFECTS.has(effect)) {
    throw new TypeError(`Unsupported HapticEffect: ${effect}`);
  }
  if (typeof navigator === "undefined" || typeof navigator.playHaptics !== "function") {
    return;
  }
  // Optional authoring filter (does not detect hardware capability)
  if (pointerType === "mouse" || pointerType === "pen" || pointerType === "touch") {
    const clamped = Math.min(1, Math.max(0, intensity));
    navigator.playHaptics(effect, clamped);
  }
}

function attachSnapDividerHaptics(dividerEl, snapX, tolerancePx = 4) {
  let snapped = false;
  dividerEl.addEventListener("pointermove", (event) => {
    const nearSnap = Math.abs(event.clientX - snapX) < tolerancePx;
    if (!snapped && nearSnap) {
      snapped = true;
      // Sticky activation was established by pointerdown; returns undefined
      triggerSemanticHaptic("align", 0.8, event.pointerType);
    } else if (snapped && !nearSnap) {
      snapped = false;
    }
  });
}
<!-- Delegate "haptics" Permissions Policy explicitly to a trusted cross-origin widget -->
<iframe
  src="https://widget.example/picker"
  allow="haptics"
  title="Interactive picker widget">
</iframe>

Security and privacy

  • Anti-fingerprinting fire-and-forget contract: playHaptics() returns undefined, exposes no hardware-capability query or device enumeration, and never reports whether an effect played—preventing sites from fingerprinting attached mice, pens, touchpads, or OS haptics settings.
  • Browser-process trust boundary: content::HapticsService re-verifies fenced frames, active-document state, "haptics" Permissions Policy, sticky user activation, and finite/clamped intensity in the browser process so a compromised renderer cannot bypass gating.
  • Abuse resistance & accessibility: Haptics are transient, stop immediately on navigation, respect system intensity/disable settings, and may be throttled or suppressed per origin. Because tactile cues may not fire on all devices, authors MUST treat haptics as supplementary feedback—never the sole indicator of state, success, or error.
Source: WICG Web Haptics explainer (Accessibility, Privacy & Security); Chromium design doc (Security & Privacy).
