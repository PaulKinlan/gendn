Compression dictionary transport Updates

Aligns Chromium’s <link rel="compression-dictionary"> and HTTP Link: <...>; rel="compression-dictionary" fetching behavior with the updated WHATWG HTML specification (PR #11620) and RFC 9842. Dictionary requests now use "compression-dictionary" as their Fetch RequestDestination (and Sec-Fetch-Dest header), honor the crossorigin attribute (promoting omitted No CORS to anonymous with mode: "cors" and credentials: "same-origin" instead of hardcoding credentials: "omit"), and respect referrerpolicy and the document referrer instead of hardcoding no-referrer.

Limited availability — Compression Dictionary Transport shipped in Chrome/Edge 130 with Chrome 156 aligning link fetch semantics to HTML PR #11620; Firefox supports dictionaries behind a preference (145 / preview) and Safari has not shipped

  • Chrome · 156 updates (base CDT since 130)
  • Edge · Mirrors Chromium (156 updates; base CDT since 130)
  • Firefox · Behind preference (145) / Preview
  • Safari · No release

The compression-dictionary-transport web-feature is Limited availability on webstatus.dev, and BCD html/elements/link.json (rel.compression-dictionary) records Chrome/Edge 130, Firefox 145 behind network.http.dictionaries.enable (and preview), and Safari false (checked 2026-11-27). MDN’s rel="compression-dictionary" page is a two-paragraph overview that omits crossorigin, referrerpolicy, and request credentials, and MDN’s Request.destination page does not list "compression-dictionary" — so gendn publishes a complete reference here.

why it exists

Chromium originally shipped Compression Dictionary Transport in Chrome 130 before HTML and Fetch finalized the processing model for rel="compression-dictionary". As Mozilla and Igalia implemented dictionary transport in Firefox and WebKit and added Web Platform Tests, whatwg/html#11620 standardized how <link rel="compression-dictionary"> and HTTP Link headers build their Fetch request. Chrome 156 catches Chromium up to that interoperable model so dictionary fetches expose a dedicated "compression-dictionary" request destination and obey standard HTML crossorigin and referrerpolicy attributes rather than hardcoded credentials: "omit" and no-referrer overrides.

Source: ChromeStatus 4895435813683200; whatwg/html#11620.

Syntax

HTML element, HTTP response header, Fetch metadata header, and JavaScript feature-detection forms per whatwg/html#11620 and Blink request.idl (RequestDestination enum value "compression-dictionary"):

<!-- HTML <link> element — body-ok: allowed in <head> or <body> -->
<link rel="compression-dictionary"
      href="https://cdn.example/dicts/app-v1.dict"
      crossorigin="anonymous"
      referrerpolicy="strict-origin-when-cross-origin">
# Equivalent HTTP response Link header
Link: <https://cdn.example/dicts/app-v1.dict>; rel="compression-dictionary"; crossorigin="anonymous"; referrerpolicy="strict-origin-when-cross-origin"

# Outgoing request Fetch Metadata header emitted by the browser
Sec-Fetch-Dest: compression-dictionary
Sec-Fetch-Mode: cors

This reference covers all three Chrome 156 updates: the "compression-dictionary" request destination, crossorigin mode and credentials handling, and referrerpolicy and referrer handling.

Source: whatwg/html#11620; Blink request.idl; RFC 9842.

"compression-dictionary" Fetch RequestDestination & Sec-Fetch-Dest

Inputs. Triggered whenever the user agent executes load a compression dictionary for a <link rel="compression-dictionary"> element or an HTTP Link: <...>; rel="compression-dictionary" response header (Blink sets network::mojom::RequestDestination::kCompressionDictionary in PreloadHelper::FetchCompressionDictionaryIfNeeded()).

Outputs. The Fetch request’s destination is set to "compression-dictionary" (added to the RequestDestination enum in request.idl). Servers observe Sec-Fetch-Dest: compression-dictionary on the incoming HTTP request, and Service Worker fetch handlers observe event.request.destination === "compression-dictionary" (replacing the legacy generic empty/subresource destination behavior). Under Content Security Policy, this destination maps to connect-src (falling back to default-src).

Source: whatwg/html#11620; Blink request.idl; Blink preload_helper.cc.

crossorigin attribute, request mode, and credentials

Inputs. The crossorigin attribute on <link rel="compression-dictionary"> (or the crossorigin parameter on an HTTP Link header): omitted (No CORS), "" / "anonymous", or "use-credentials".

Outputs. Per step 1 of load a compression dictionary in whatwg/html#11620 (implemented in Blink’s preload_helper.cc under CDTNewCrossOriginHandling), if crossorigin is unset (No CORS), it is promoted to anonymous before calling create a link request. This changes request mode and credentials compared to Chrome 130–155:

referrerpolicy attribute and request referrer

Inputs. The referrerpolicy attribute on <link rel="compression-dictionary"> (or the referrerpolicy parameter on an HTTP Link header), accepting standard Fetch referrer policy tokens such as no-referrer, origin, same-origin, strict-origin, strict-origin-when-cross-origin, or unsafe-url (defaulting to the document’s referrer policy when omitted).

Outputs. Under CDTNewReferrerAndReferrerPolicyHandling in preload_helper.cc, Chromium now passes params.referrer_policy and the document’s referrer into the Fetch request instead of unconditionally setting Referrer::NoReferrer() and ReferrerPolicy::kNever. As a result, dictionary fetches now emit a standard Referer header according to the link’s referrerpolicy (or the document’s default policy, typically strict-origin-when-cross-origin).

Source: whatwg/html#11620; Blink preload_helper.cc; ChromeStatus 4895435813683200.

Errors and migration pitfalls

  • CORS failures on cross-origin dictionaries: Because rel="compression-dictionary" always fetches with mode: "cors", cross-origin dictionary servers must emit a matching Access-Control-Allow-Origin header (and Access-Control-Allow-Credentials: true with a non-wildcard origin when crossorigin="use-credentials" is specified). Otherwise the fetch fails as a network error, fires error on the <link> element, and does not store the dictionary.
  • Same-origin cookies & Referer migration: Servers upgrading from Chrome 130–155 that assumed dictionary fetches never carried same-origin cookies or a Referer header will now receive same-origin credentials (credentials: "same-origin") and the document’s referrer policy by default. Set referrerpolicy="no-referrer" explicitly if you need to suppress Referer.
  • CSP & secure context requirements: Compression Dictionary Transport is active only in secure contexts (https:// or localhost) and requires the response’s Use-As-Dictionary header (RFC 9842) plus CSP connect-src permission; a blocked fetch triggers the <link> element’s error event.
  • RequestDestination check in Service Workers: Service Worker routing code that previously matched dictionary links by request.destination === "" must be updated to match request.destination === "compression-dictionary".
Source: whatwg/html#11620; RFC 9842; Blink preload_helper.cc.

Context and exposure

Compression Dictionary Transport requires a secure context (self.isSecureContext === true, i.e. HTTPS or localhost). Per whatwg/html#11620, rel="compression-dictionary" is body-ok (allowed on <link> elements in both <head> and <body>) and is listed in HTMLLinkElement.relList.supports("compression-dictionary"). It can also be triggered via HTTP Link: response headers. The "compression-dictionary" destination is observable server-side via Sec-Fetch-Dest and client-side in Service Workers via FetchEvent.request.destination.

Source: whatwg/html#11620; HTML Living Standard; RFC 9842.

Fetch triggers, idle scheduling, and load / error events

Per whatwg/html#11620, a <link rel="compression-dictionary"> triggers load a compression dictionary when: (1) created while browsing-context connected, (2) inserted into a browsing-context connected document, (3) its href attribute changes while connected, or (4) its crossorigin attribute is set, changed, or removed while connected. HTML explicitly permits user agents to delay the dictionary fetch to prioritize critical document resources; Blink schedules the fetch via ScriptedIdleTaskController (LoadDictionaryWhenIdleTask in preload_helper.cc). After consuming the response body, the browser fires error at the <link> element if the response is a network error, or load otherwise. When the response carries a valid Use-As-Dictionary header, later matching fetches send Available-Dictionary, optional Dictionary-ID, and dcb / dcz in Accept-Encoding.

Source: whatwg/html#11620; Blink preload_helper.cc; RFC 9842.

Examples

Live demo & declarative <link> / HTTP Link setup

<!-- Same-origin dictionary: omits crossorigin (promoted to anonymous: mode=cors, credentials=same-origin) -->
<link rel="compression-dictionary"
      href="/static/app-v1.dict"
      referrerpolicy="same-origin">

<!-- Cross-origin authenticated CDN dictionary: explicitly sends credentials -->
<link rel="compression-dictionary"
      href="https://cdn.example/static/app-v1.dict"
      crossorigin="use-credentials"
      referrerpolicy="no-referrer">
# Dictionary response headers required by RFC 9842 + CORS for cross-origin use
HTTP/2 200 OK
Content-Type: application/octet-stream
Cache-Control: public, max-age=86400
Use-As-Dictionary: match="/static/app-*.js", id="app-v1"
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Credentials: true

Feature detection, dynamic <link> insertion, and Service Worker inspection

function registerCompressionDictionary(href, { crossorigin = "anonymous", referrerpolicy = "strict-origin-when-cross-origin" } = {}) {
  const link = document.createElement("link");
  const supported = Boolean(link.relList?.supports?.("compression-dictionary"));
  if (!supported || !self.isSecureContext) {
    return { supported, inserted: false };
  }

  link.rel = "compression-dictionary";
  link.href = href;
  link.crossOrigin = crossorigin;
  link.referrerPolicy = referrerpolicy;
  link.addEventListener("load", () => console.log("Dictionary fetched:", href));
  link.addEventListener("error", () => console.warn("Dictionary fetch failed:", href));
  document.head.append(link);
  return { supported, inserted: true };
}

// Inside a Service Worker fetch listener, Chrome 156+ exposes the dedicated RequestDestination:
function isCompressionDictionaryFetch(event) {
  return event.request.destination === "compression-dictionary";
}
Source: whatwg/html#11620; CPS conformance suite.

Security and privacy

Promoting omitted crossorigin (No CORS) to anonymous enforces mode: "cors" on every dictionary fetch, ensuring cross-origin compression dictionaries require explicit Access-Control-Allow-Origin opt-in and cannot silently read opaque cross-origin bodies into a compression oracle (mitigating BREACH/CRIME-style side channels detailed in RFC 9842 §9 Security Considerations). Exposing Sec-Fetch-Dest: compression-dictionary lets origins enforce Fetch Metadata isolation rules specifically for dictionary requests, CSP connect-src governs allowed dictionary endpoints, and honoring referrerpolicy gives site authors direct control over Referer disclosure rather than silently overriding it.

Source: RFC 9842 §9 Security Considerations; whatwg/html#11620.
