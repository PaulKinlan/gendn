WebAudio: Configurable render quantum

Chrome 153 adds a renderSizeHint option to AudioContext and OfflineAudioContext, allowing developers to request a specific number of audio frames per render cycle — enabling trade-offs between latency and CPU overhead for their workload.

why it exists

The Web Audio API has always rendered audio in fixed 128-frame chunks (the render quantum). This gives a latency of about 2.9 ms at 44.1 kHz. While 128 frames is fine for most applications, it creates tensions at both ends of the spectrum:

  • Low-latency instruments (synthesisers, live effects) would benefit from a smaller quantum (e.g. 32 frames) to cut round-trip latency, even at the cost of more CPU interrupts.
  • Batch or background processing (audio fingerprinting, format conversion) runs more efficiently with a larger quantum (e.g. 1024 frames) to amortise callback overhead.

The renderSizeHint option lets the developer express a preference; the browser uses it as a hint, rounding to a supported size if necessary.

Source: chromestatus feature summary; Web Audio API spec §renderQuantumSize.

Inputs and outputs

Inputs: The renderSizeHint dictionary member accepts an unsigned integer (typically powers of two such as 32, 64, 128, 256, 512, 1024) or the string enum values "default" and "hardware". Passed during context construction via new AudioContext({ renderSizeHint }) or new OfflineAudioContext({ ..., renderSizeHint }).

Outputs: The renderQuantumSize attribute returns an unsigned integer reflecting the active render quantum size for the audio context. Inside an AudioWorkletProcessor, the worklet global scope exposes the identical renderQuantumSize value, determining the length of channel arrays in the process(inputs, outputs, parameters) callback.

Source: Web Audio API §renderQuantumSize; MDN AudioContext.

Errors and lifecycle

Errors: Per the Web Audio API specification, passing an integer render-quantum size outside the supported range throws a NotSupportedError: §2.5 requires it for values outside the permitted range (1 up to 6× the sample rate). The renderSizeHint categories (AudioContextRenderSizeCategory: "default" or "hardware") are advisory and map onto a supported size. If a value of the wrong type is provided, standard WebIDL type conversion throws a TypeError.

Lifecycle: The render quantum size is fixed at context instantiation time and remains immutable for the lifetime of that AudioContext or OfflineAudioContext. Graph nodes and AudioWorklet processors instantiated within the context operate synchronously on blocks of renderQuantumSize frames throughout execution.

Source: Web Audio API §renderQuantumSize; WebAudio Issue #1503.

Examples

The following example demonstrates configuring low-latency synthesis, batch offline rendering, and accessing renderQuantumSize in main thread and worklet scopes:

// 1. Low-latency interactive synthesiser: request small quantum (lower latency, more CPU)
const ctx = new AudioContext({ renderSizeHint: 32 });
console.log(`Configured render quantum: ${ctx.renderQuantumSize} frames`);

// 2. Batch processor: request large quantum (less CPU callback overhead)
const offCtx = new OfflineAudioContext({
  numberOfChannels: 2,
  length: 44100 * 10,  // 10 seconds
  sampleRate: 44100,
  renderSizeHint: 1024,
});
console.log(`Offline render quantum: ${offCtx.renderQuantumSize} frames`);

// 3. Requesting hardware-preferred quantum
const hwCtx = new AudioContext({ renderSizeHint: 'hardware' });

// 4. AudioWorkletProcessor handling variable render quantum sizes:
class DynamicQuantumProcessor extends AudioWorkletProcessor {
  process(inputs, outputs) {
    // globalThis.renderQuantumSize specifies frame buffer length per channel
    const output = outputs[0];
    const channelData = output[0];
    for (let i = 0; i < channelData.length; i++) {
      channelData[i] = 0.0;
    }
    return true;
  }
}

security and privacy

  • Timing resolution and fingerprinting: Audio render quantum sizes provide precise sub-millisecond hardware callback timing. To prevent cross-origin timing attacks and high-resolution fingerprinting, user agents may limit the minimum quantum size or restrict hardware buffer exposure to secure contexts.
  • Resource consumption: Very small render quantum sizes (e.g. < 32 frames) increase thread interrupt frequency and CPU load. Implementations enforce lower bounds to prevent audio thread starvation and denial of service.
Source: Web Audio API specification; Chromium Issue 40637820.
