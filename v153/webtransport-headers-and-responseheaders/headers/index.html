The headers member of the WebTransportOptions dictionary sets custom HTTP request headers on the extended CONNECT request that establishes a WebTransport session — “Optionally, a Headers object, an object literal, or an array of two-item arrays to set the request header list to use when establishing a WebTransport session” (spec, verbatim). Typical uses: bearer-token authentication, routing metadata for gateways and reverse proxies, and capability negotiation.

In developer trial at Chrome 153 — behind a flag; the API surface may move

Chrome 153 lists this feature under “In developer trial (Behind a flag)” (milestone=153 listing). Enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch with --enable-blink-features=WebTransportHeaders (Blink runtime feature WebTransportHeaders, status experimental — runtime_enabled_features.json5, fetched 2026-09-13). Slated to ship enabled by default in Chrome 155 (ChromeStatus record).

Syntax

// WebIDL (specification, verbatim):
dictionary WebTransportOptions {
  // ...
  HeadersInit headers = {};
  // ...
};

// Call form:
const wt = new WebTransport(url, { headers: { 'authorization': 'Bearer …' } });

HeadersInit is Fetch’s union type: sequence<sequence<ByteString>> or record<ByteString, ByteString>, and a Headers instance is accepted wherever HeadersInit is because Headers is iterable as a sequence of pairs.

Source: WebTransport editor’s draft §6.9 — headers; Fetch — HeadersInit.

Accepted values

Object literal{ 'x-token': 'abc' } — a record<ByteString, ByteString>; keys are header names, values are header values.
Array of pairs[['x-a', '1'], ['x-b', '2']] — each inner array must have exactly two items or the Headers fill algorithm throws TypeError.
Headers objectAn existing Headers instance; its entries are copied (snapshotted) during the constructor call.
Default{} — no custom headers; the CONNECT request carries only the user agent’s own headers.
Name/value validityEvery name must be a valid HTTP header name and every value a valid header value per Fetch; invalid entries make the fill algorithm throw TypeError.
Reserved namewt-available-protocols (matched after ASCII-lowercasing) is rejected with TypeError — the protocols option owns that header.
Silently droppedForbidden request-headers (Host, Origin, Cookie, Sec-*, Proxy-*, and the forbidden request-body headers, among others) are not appended and do not throw: the append happens through a Headers object with guard "request", whose append algorithm skips forbidden names without error.
Source: editor’s draft §6.2 Constructor; Fetch — Headers class (fill, append, guard); Fetch — forbidden request-header.

Effect on the request

Surviving entries are appended to the header list of the session-establishing request — the extended CONNECT request whose method is CONNECT with the :protocol pseudo-header set to webtransport. The server (and any gateway or reverse proxy on the path that inspects CONNECT-layer headers) sees them during the handshake, before any stream or datagram exists. The option has no client-side readback: nothing on the WebTransport instance reflects what was sent. Response direction is covered by responseHeaders.

Source: editor’s draft §6.2 Constructor (“Set request’s method to CONNECT… append header to requestHeaders”); ChromeStatus record — motivation.

Exceptions

All failures are synchronous TypeErrors thrown by the WebTransport constructor (the option is processed before any network activity):

ExceptionCondition
TypeErrorThe HeadersInit value is malformed: an inner sequence without exactly two items, an invalid header name, or an invalid header value (thrown by Fetch’s Headers fill algorithm).
TypeErrorAny entry’s name ASCII-lowercases to wt-available-protocols (spec §6.2: “If ascii lowercase header’s name is wt-available-protocols, then throw a TypeError”).
No errorForbidden request-headers are silently skipped by the "request"-guarded append — misspelled expectations here are a debugging trap, not an exception.
Source: editor’s draft §6.2; Fetch — Headers class.

Context and requirements

WhereSecond argument of the WebTransport constructor; WebTransport is [Exposed=(Window,Worker), SecureContext], so the option works in windows and workers, secure contexts only, with an https URL.
Server opt-inThe session only establishes against a server that advertises the HTTP/3 SETTINGS_ENABLE_WEBTRANSPORT setting (draft-ietf-webtrans-http3) — the working group’s reason custom headers need no CORS preflight.
Chrome 153Behind chrome://flags/#enable-experimental-web-platform-features or --enable-blink-features=WebTransportHeaders (see the warning above). Without the flag the member is ignored like any unknown dictionary member — feature-detect with 'responseHeaders' in WebTransport.prototype.
No credentialsThe CONNECT request never carries cookies, HTTP auth, or client certificates; anything credential-like must go through this option explicitly.
Source: editor’s draft (interface IDL, §6.2); ChromeStatus record — security risks, activation; Intent to Ship.

Lifecycle

Read onceThe dictionary is converted and the headers snapshotted synchronously inside the constructor. Mutating a passed Headers object afterwards has no effect on the session.
Sent onceHeaders ride on the single CONNECT request for this session. There is no re-send, no per-stream headers, and no way to add or change headers after construction — a new header set requires a new WebTransport session.
No retriesThe API performs no automatic retry of a failed handshake (and redirects are followed never — redirect mode is "error"), so headers are never re-transmitted without a new constructor call.
OrderingHeader processing (fill, wt-available-protocols check, guarded append) happens before the protocols option writes wt-available-protocols and before the connection attempt starts.
Source: editor’s draft §6.2 Constructor (step order and redirect mode).

Examples

Bearer-token authentication (the motivating case — keeps the token out of the URL, server logs, and telemetry):

const wt = new WebTransport('https://transport.example.com:4433/media', {
  headers: { 'authorization': `Bearer ${await getToken()}` },
});
await wt.ready;

All three accepted forms, and the two error paths:

// Headers object — snapshotted at construction time.
const h = new Headers({ 'x-tenant': 'acme' });
new WebTransport(url, { headers: h });
h.set('x-tenant', 'other');       // no effect on the session above

// Array-of-pairs form.
new WebTransport(url, { headers: [['x-region-hint', 'eu-west']] });

try {
  new WebTransport(url, { headers: { 'wt-available-protocols': 'x' } });
} catch (e) {
  // TypeError: reserved for the `protocols` option.
}

try {
  new WebTransport(url, { headers: { 'bad header name': '1' } });
} catch (e) {
  // TypeError: invalid header name (Fetch fill algorithm).
}

// NOT an error: forbidden headers are silently dropped.
new WebTransport(url, { headers: { 'origin': 'https://evil.example' } });
// The CONNECT request keeps the browser's real Origin header.
Source: behavior derived from editor’s draft §6.2 and Fetch — Headers class; not runtime-verified — no flag-enabled Chrome 153 with a WebTransport server was available to this writer.

Security and privacy

  • Injection/spoofing barrier. Forbidden request-headers cannot be set (silently dropped by the "request" guard), so a page cannot forge Host, Origin, Sec-*, or request-body framing headers on the CONNECT request.
  • Cross-origin sending without preflight. Custom headers go to any WebTransport server without a CORS preflight; the safety argument is that servers must explicitly opt in via SETTINGS_ENABLE_WEBTRANSPORT, so non-WebTransport endpoints never parse them.
  • Credentials become explicit. With no cookies or HTTP auth on the request, any credential in headers is one the page deliberately placed there — better than query strings (no log/telemetry leakage), but still visible to on-path CONNECT-inspecting intermediaries such as corporate proxies terminating the connection.
Source: ChromeStatus record — security risks; Intent to Ship — security; Fetch — forbidden request-header.
