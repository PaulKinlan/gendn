Not Baseline. BCD tracks this attribute as experimental with no stable-channel browser shipping it (BCD api/WebTransport.json — responseHeaders, fetched 2026-09-13). MDN has no page for it yet (/en-US/docs/Web/API/WebTransport/responseHeaders returned 404, checked 2026-09-13).

The read-only responseHeaders attribute of the WebTransport interface — “Once a WebTransport session has been established, holds the application-level response headers set by the server, if any. Initially null” (spec, verbatim). It is the response half of the handshake-header channel opened by the headers constructor option: what the server said back on the CONNECT response, as an immutable Headers object.

In developer trial at Chrome 153 — behind a flag; the API surface may move

Chrome 153 lists this feature under “In developer trial (Behind a flag)” (milestone=153 listing). Enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch with --enable-blink-features=WebTransportHeaders (Blink runtime feature WebTransportHeaders, status experimental — runtime_enabled_features.json5, fetched 2026-09-13). Slated to ship enabled by default in Chrome 155 (ChromeStatus record).

Syntax

// WebIDL (specification, verbatim):
interface WebTransport {
  // ...
  [SameObject] readonly attribute Headers? responseHeaders;
  // ...
};

// Access form:
await wt.ready;
const value = wt.responseHeaders?.get('x-session-region');

[SameObject] guarantees every read returns the identical Headers instance; the getter simply returns the internal [[ResponseHeaders]] slot (“A Headers object or null. Initially null”).

Source: WebTransport editor’s draft §6.3 — responseHeaders; spec PR #713 (diff) (internal-slot table); WebIDL — [SameObject].

Value

Before establishmentnull — while the state is "connecting", and forever if the handshake fails (the slot is only ever written in the connection-established steps).
After establishmentA Headers object whose header list is a copy of the CONNECT response’s header list with the wt-protocol header deleted, and whose guard is "immutable" (spec §6.2, connection-established steps, verbatim sequence).
wt-protocol exclusionThe negotiated application protocol is stripped from this object and surfaced through the separate WebTransport.protocol attribute instead.
Identity[SameObject]: repeated reads return the same instance — safe to cache, compare, and iterate multiple times.
Source: editor’s draft §6.2 Constructor (“Let responseHeaders be a copy of response’s header list… Delete wt-protocol… guard is immutable”); editor’s draft §6.3.

Exceptions

OperationBehavior
Reading wt.responseHeadersNever throws — returns null or the Headers object.
set(), append(), delete() on the returned objectThrows TypeError: the guard is "immutable", and Fetch’s mutation algorithms throw for immutable-guarded Headers.
Read methods (get(), has(), entries(), iteration)Work normally on the established object.
Source: Fetch — Headers class (guard immutable); editor’s draft §6.2.

Lifecycle and state transitions

Initialization[[ResponseHeaders]] is set to null in the constructor.
Population pointIn the connection-established network task, after the state check passes and the state flips "connecting" → "connected", the slot is written — in the same task that later resolves ready. Consequently: after await wt.ready, responseHeaders is populated. Code running before that must handle null.
Failure pathIf the handshake fails or the session is aborted while connecting, the slot is never written: responseHeaders is null when ready/closed reject.
After closeThe attribute keeps its established value after the session closes or errors — nothing in the close/error steps clears [[ResponseHeaders]].
ImmutabilityThe object never changes after population (immutable guard, [SameObject]); response headers reflect the handshake only, never later server activity.
Source: editor’s draft §6.2 (initialization and connection-established steps); editor’s draft §6.3.

Examples

Read negotiated values after the session is up:

const wt = new WebTransport('https://transport.example.com:4433/session', {
  headers: { 'x-supported-codecs': 'av1,vp9' },
});

await wt.ready;

// Guaranteed non-null here (populated before ready resolves).
const headers = wt.responseHeaders;
console.log(headers.get('x-selected-codec'));   // e.g. "av1"

// Iterate everything the server sent (minus wt-protocol):
for (const [name, value] of headers) {
  console.log(`${name}: ${value}`);
}

// The object is immutable:
try {
  headers.set('x-selected-codec', 'vp9');
} catch (e) {
  // TypeError — guard is "immutable".
}

Handling the not-yet-established and failure cases:

const wt = new WebTransport(url);
console.log(wt.responseHeaders);   // null — still "connecting"

try {
  await wt.ready;
} catch (e) {
  console.log(wt.responseHeaders); // still null — handshake failed
}
Source: behavior derived from editor’s draft §6.2 and Fetch — Headers; not runtime-verified — no flag-enabled Chrome 153 with a WebTransport server was available to this writer.

Security and privacy

  • Server-controlled data. Every value in responseHeaders is chosen by the server — treat it as untrusted input; never interpolate it into HTML or code without sanitization.
  • Immutability as integrity. The "immutable" guard means no code on the page can tamper with the record of what the server sent — useful when several modules consult it.
  • Scope of disclosure. Only the handshake response’s header list is exposed, minus wt-protocol; nothing about later HTTP/3 frames, other sessions on a pooled connection, or intermediate hops is revealed.
Source: editor’s draft §6.2; Fetch — Headers class; ChromeStatus record — security risks.
