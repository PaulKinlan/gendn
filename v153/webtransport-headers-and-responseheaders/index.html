WebTransport headers and responseHeaders

Limited availability

  • Chrome · 153, dev trial behind a flag; slated enabled-by-default in 155
  • Edge · not supported (BCD mirrors Chrome: not shipped)
  • Firefox · no signal
  • Safari · Technology Preview (WebKit change landed unflagged)

Not Baseline. The ChromeStatus record maps this addition to the umbrella Web Feature ID webtransport, which is Baseline “newly available” since 2026-03-24 per the webstatus.dev query — but that entry reflects the core WebTransport API shipped years earlier, not these two new members. There is no separate web-features entry for the headers/responseHeaders addition (query checked 2026-09-13), and in Chrome the members are behind a flag at 153.

Two additive members of the WebTransport API: the headers option in WebTransportOptions sends custom HTTP request headers on the session-establishing CONNECT handshake, and the WebTransport.responseHeaders attribute exposes the server’s response headers once the session is established. Together they let clients and servers authenticate, route, and negotiate capabilities during the handshake itself — no more tokens in query strings or extra setup round trips on a data stream.

In developer trial at Chrome 153 — behind a flag; the API surface may move

The Chrome 153 milestone listing files this feature under “In developer trial (Behind a flag)” (milestone=153 listing, verified 2026-09-13). Do not ship production code against it from 153: behavior and surface can change before it ships. To try it in Chrome 153:

  • Enable chrome://flags/#enable-experimental-web-platform-features and relaunch (flag name per the ChromeStatus record and the Intent to Ship), or
  • launch with --enable-blink-features=WebTransportHeaders — the Blink runtime feature is WebTransportHeaders, status experimental (runtime_enabled_features.json5, fetched 2026-09-13). The Finch feature name is also WebTransportHeaders.

The same feature id appears in the milestone=155 listing under “Enabled by default”: it is slated to ship enabled in Chrome 155 (desktop, Android, and WebView per the ChromeStatus record; the Intent to Ship says “Will ship enabled for all users”). This v153 page documents the dev-trial state at 153.

Source: milestone=153 listing; milestone=155 listing; Intent to Ship: WebTransport headers and responseHeaders; runtime_enabled_features.json5.

why it exists

WebTransport sessions are established with an extended HTTP CONNECT request (RFC 9220 over HTTP/3), but until this addition the API gave developers no way to put anything on that request. That forced three well-known workarounds, each bad: authentication tokens in URL query strings (credentials leak into server logs and telemetry), authentication over an initial data stream (an extra round trip before the connection is usable), and no way at all for API gateways and reverse proxies — which inspect headers at the CONNECT layer — to authorize or route WebTransport sessions through existing pipelines.

WebTransportOptions.headers lets the client attach metadata, bearer tokens, and negotiation parameters (for example supported video codecs) to the CONNECT request; WebTransport.responseHeaders lets it read what the server sent back once the session is established. The design was discussed and agreed in the W3C WebTransport Working Group (issue #263, merged as PR #713 — the diff is linked because github.com pages were not reachable from this build environment; the Intent to Ship names both) with participation from Mozilla, Apple, and Google engineers, and consensus was recorded at the November 2025 W3C TPAC meeting in Kobe.

Source: ChromeStatus record — motivation; Intent to Ship — motivation and interoperability; W3C TPAC 2025 minutes page.

Syntax

Verbatim from the WebTransport editor’s draft (the two added members shown in their surrounding IDL; fetched 2026-09-13, identical in the TR snapshot):

[Exposed=(Window,Worker), SecureContext]
interface WebTransport {
  constructor(USVString url, optional WebTransportOptions options = {});
  // ...existing members...
  [SameObject] readonly attribute Headers? responseHeaders;   // NEW
  readonly attribute DOMString protocol;
  // ...
};

dictionary WebTransportOptions {
  boolean allowPooling = false;
  boolean requireUnreliable = false;
  HeadersInit headers = {};                                   // NEW
  sequence<WebTransportHash> serverCertificateHashes = [];
  WebTransportCongestionControl congestionControl = "default";
  [EnforceRange] unsigned short? anticipatedConcurrentIncomingUnidirectionalStreams = null;
  [EnforceRange] unsigned short? anticipatedConcurrentIncomingBidirectionalStreams = null;
  sequence<DOMString> protocols = [];
  ReadableStreamType datagramsReadableType;
};

HeadersInit and Headers are the Fetch specification’s types: headers accepts a Headers object, an object literal, or an array of two-item arrays; responseHeaders returns a Headers object or null.

Source: editor’s draft §6.9 — headers; editor’s draft §6.3 — responseHeaders; Fetch — HeadersInit.

the two members

WebTransportOptions.headers

Full reference: headers member page — accepted forms, the exact constructor processing steps, every error path, and the forbidden-header filtering rules.

TypeHeadersInit, defaulting to {} — “Optionally, a Headers object, an object literal, or an array of two-item arrays to set the request header list to use when establishing a WebTransport session” (spec §6.9, verbatim)
EffectEach entry is appended to the CONNECT request’s header list during the handshake, subject to Fetch’s forbidden request-header restrictions
Hard errorA header named wt-available-protocols (case-insensitive) throws TypeError — that header is reserved for the protocols option
Source: editor’s draft §6.9; editor’s draft §6.2 Constructor.

WebTransport.responseHeaders

Full reference: responseHeaders member page — settlement timing, the immutable guard, the wt-protocol exclusion, and failure behavior.

Type[SameObject] readonly attribute Headers? — “Once a WebTransport session has been established, holds the application-level response headers set by the server, if any. Initially null” (spec §6.3, verbatim)
PopulationSet when the session reaches "connected" (just before ready resolves): a copy of the response’s header list with wt-protocol deleted, wrapped in a Headers object whose guard is "immutable"
On failureStays null — a session that never establishes never populates it
Source: editor’s draft §6.3; editor’s draft §6.2 Constructor (connection-establishment steps).

Examples

Bearer-token authentication and codec negotiation on the handshake, then reading the server’s reply headers:

// Feature-detect both members (Intent to Ship's recommended pattern).
if (!('responseHeaders' in WebTransport.prototype)) {
  // Fall back: token as a query parameter or app-level handshake.
}

const wt = new WebTransport('https://transport.example.com:4433/session', {
  headers: {
    'authorization': `Bearer ${token}`,
    'x-supported-codecs': 'av1,vp9',
  },
});

await wt.ready;

// responseHeaders is null until the session is established.
const region = wt.responseHeaders?.get('x-session-region');
const codec = wt.responseHeaders?.get('x-selected-codec');
console.log(`connected via ${region}, using ${codec}`);

All three HeadersInit forms are accepted:

// Object literal
new WebTransport(url, { headers: { 'x-a': '1' } });

// Array of two-item arrays
new WebTransport(url, { headers: [['x-a', '1'], ['x-b', '2']] });

// Headers object (snapshotted during the constructor call)
const h = new Headers();
h.append('x-a', '1');
new WebTransport(url, { headers: h });

No interactive demo for this feature exists on the Chrome Platform Showcase yet: the candidate routes /v153/webtransport-headers-and-responseheaders/ and /v155/webtransport-headers-and-responseheaders/ both returned HTTP 404 when checked on 2026-09-13, so no demo is embedded here. A live demo also needs a WebTransport server that opts in via SETTINGS_ENABLE_WEBTRANSPORT, which a static page cannot provide.

security and privacy

  • No CORS preflight — by design. The W3C WebTransport Working Group evaluated whether developer-set headers on cross-origin CONNECT requests needed a mandatory preflight and concluded that the explicit server-level opt-in via the HTTP/3 SETTINGS_ENABLE_WEBTRANSPORT setting protects non-WebTransport servers, avoiding the preflight’s latency cost.
  • Header-injection and spoofing prevention. Custom headers are filtered against Fetch’s forbidden request-header rules (so Host, Origin, Sec-*, and forbidden request-body headers cannot be set), and wt-available-protocols is additionally rejected with TypeError because the protocols option owns it.
  • No ambient credentials. WebTransport requests carry no cookies, HTTP auth, or client certificates, mitigating attacks on servers that might confuse the WebTransport handshake with an ordinary request — which is exactly why an explicit headers channel for bearer tokens is useful.
  • Response headers are immutable and filtered. The Headers object returned by responseHeaders has guard "immutable", and the wt-protocol header is deleted before exposure (the negotiated protocol is surfaced through the protocol attribute instead). Treat the remaining values as server-controlled, untrusted input.
Source: ChromeStatus record — security risks; Intent to Ship — security; editor’s draft §6.2; Fetch — forbidden request-header.
