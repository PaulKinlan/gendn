v153 · spell check custom dictionary api · method

SpellCheckCustomDictionary.addWords()

Limited availability

  • Chrome · dev trial from 153, behind a flag
  • Edge · no signal recorded
  • Firefox · under consideration
  • Safari · no signal

Chrome developer trial only — no Baseline or web-features entry (webstatus.dev query, zero matches, 2026-09-13).

Adds each string in words to the document’s custom spelling exemption list, so the browser’s spell checker stops flagging those exact words in this document. Words already present are ignored; invalid entries are silently skipped. Nothing is returned and nothing persists past the document.

In developer trial — the API surface may move

Dev trial behind a flag from Chrome 153. Enable via chrome://flags/#enable-experimental-web-platform-features (“Experimental Web Platform Features”) or --enable-blink-features=SpellCheckCustomDictionaryAPI. The draft spec (whatwg/html#12590) still names the attribute that hosts this method differently (document.spellCheckDictionary) — the method name itself, addWords(), matches in both. Do not ship production code against this API.

Source: Dev Trial instructions; runtime_enabled_features.json5.

Syntax

// WebIDL (dev-trial surface):
undefined addWords(sequence<DOMString> words);

// Call form:
document.spellCheckCustomDictionary.addWords(["Pikachu", "Charmander"]);

The draft spec’s method steps: for each word in words, append word to the associated document’s custom spelling exemption list, if word is not already in the list.

Source: Dev Trial instructions — API surface; whatwg/html#12590 (addWords method steps, transcribed from the PR diff 2026-09-13).

Parameters

words A sequence<DOMString> — an array (or any iterable) of strings to exempt from spell-check flagging in this document. Per-entry validation matches the browser custom dictionary’s and never throws; entries are checked individually:
  • Silently skipped: empty strings, words with leading or trailing whitespace, and ill-formed UTF-16 (unpaired surrogates).
  • Duplicates: words already in the set are ignored (the set semantics come from the spec’s ordered-set model).
  • Length limit: a word longer than 128 bytes of UTF-8 is skipped on its own.
  • Count limit: at most 20,000 words per document, measured against the live set (removeWords() frees capacity). Once the cap is reached, the rest of that call is dropped.
  • Multi-word strings: accepted but useless — matching is per-word, so entries containing whitespace or other word separators will generally never match (and are skipped by the whitespace rule when the spaces are leading/trailing).
Source: Dev Trial instructions — behaviour to be aware of (validation, limits); whatwg/html#12590 (ordered-set append, matching notes).

Return value

undefined. The observable effect is indirect: on subsequent spell-check passes over editable text in this document, words that exactly match a live entry are no longer flagged as misspelled. There is no return channel reporting which entries were accepted, skipped, or dropped at the cap — the surface is deliberately write-only.

Source: whatwg/html#12590 (exemption-list effect on checking); explainer — proposed approach (write-only design).

Context and prerequisites

The Dev Trial instructions split the prerequisites into two failure classes — the first four decide whether the interface exists, the last two decide whether calls have any effect:

Interface exists(1) Chrome Canary/Dev 153+ with the SpellCheckCustomDictionaryAPI flag enabled; (2) a Blink platform — desktop (Windows, macOS, Linux, ChromeOS) or Android; not Chrome on iOS (WebKit-based); (3) a secure context (https:// or http://localhost); (4) a Window context — [Exposed=Window], not available in workers. If any is missing the attribute is undefined.
Calls take effect(5) Spell checking turned on — chrome://settings/languages → Spell check on Windows/Linux/ChromeOS with a language dictionary downloaded; the same toggle on macOS where checking is done by the system NSSpellChecker; the Android system spell checker (with a service and language selected) on Android. (6) Text that actually gets spell checked: a contenteditable element, a <textarea>, or an <input type="text">, without spellcheck="false". When these fail, calls return normally and nothing changes.
Source: Dev Trial instructions — prerequisites (transcribed 2026-09-13).

Lifecycle and state transitions

AddEach accepted word joins the document’s live exemption set immediately; the suppression applies as the spell checker next processes the relevant text.
IdempotenceAdding a word twice is a no-op (set semantics: “words already present are ignored”).
ResetThe set is cleared on every navigation, including same-origin ones — a page must re-add its words after each navigation. It is discarded entirely when the document is destroyed.
ScopeThe set belongs to this document only: never shared across documents, frames, or browsing contexts; each iframe has its own.
CapacityThe 20,000-word cap tracks the live set; removeWords() frees capacity for later addWords() calls.
IndependenceWords added here do not appear in chrome://settings/editDictionary, are not synced, and do not affect other tabs; the user’s own custom dictionary keeps applying independently. A word that overlaps an underlying dictionary is expected and inert.
No eventsNo events fire; there is no way to observe the set from script.
Source: Dev Trial instructions — behaviour to be aware of; whatwg/html#12590 (transience note); explainer — implementation notes.

Examples

Add a page’s domain vocabulary once the document is ready:

const vocabulary = ["Igalia", "Wolvic", "spidermonkey"];

if ("spellCheckCustomDictionary" in document) {
  document.spellCheckCustomDictionary.addWords(vocabulary);
}

Feed a server-supplied word list (the explainer’s financial-news scenario — runtime-fetched vocabularies are a core use case for the imperative form):

const response = await fetch("/api/tickers");
const tickers = await response.json(); // e.g. ["AAPL", "GOOG", "TSMC"]
document.spellCheckCustomDictionary?.addWords(tickers);

Remember that matching is exact and case-sensitive — cover the forms you need explicitly:

// "Pikachu" alone does NOT suppress "pikachu" or "Pikachus".
document.spellCheckCustomDictionary?.addWords([
  "Pikachu", "pikachu", "Pikachus",
]);
Source: explainer — example, declarative-link discussion (fetch scenario); Dev Trial instructions — exact matching.

Security and privacy

  • Write-only. addWords() has no read counterpart; a page can only know the words it supplied itself, and cannot use this method to probe the user’s own dictionary.
  • Bounded. The 20,000-word / 128-byte limits with silent-skip semantics prevent a page from flooding renderer memory or corrupting existing state at the limit.
  • Strictly additive. The custom set can only suppress a flag, never create one, and never writes into any underlying engine, OS, or user dictionary — so nothing added here leaks into other applications or profiles.
  • Transient and isolated. Per-document scope means a third-party iframe can only affect its own document; everything is discarded with the document.
Source: explainer — privacy & security, implementation notes; Dev Trial instructions — limits.
