SpellCheckCustomDictionary: addWords()

Adds each valid string in words to the document’s custom spell-check dictionary, so the browser’s spell checker stops flagging those exact tokens as misspelled anywhere in the document. Existing squiggles for the added words are cleared immediately. Returns undefined; invalid entries and cap overflow are skipped silently — the method never throws.

Experimental — dev trial, behind a flag

Available only when the Blink runtime feature SpellCheckCustomDictionaryAPI is enabled (status experimental in runtime_enabled_features.json5, 2026-08-09): set chrome://flags/#enable-experimental-web-platform-features to Enabled, or launch with --enable-blink-features=SpellCheckCustomDictionaryAPI. The API surface may still move — the open spec PR whatwg/html#12590 reaches the same addWords() via window.spellCheckDictionary instead of document.spellCheckCustomDictionary. See the feature page’s full caveats.

Syntax

document.spellCheckCustomDictionary.addWords(words)

From the shipped Blink IDL (spell_check_custom_dictionary.idl, fetched 2026-08-09): undefined addWords(sequence<DOMString> words). The open spec PR whatwg/html#12590 declares the identical method signature and specifies its steps as: for each word in words, append word to the document’s custom spelling exemption list if not already present.

Source: Blink IDL; whatwg/html#12590.

Parameters

ParameterTypeDescription
wordssequence<DOMString>The words to add — any iterable of strings (an array in practice). Matching is exact and verbatim, so supply every form you need ("anaerobe" and "anaerobes" are distinct entries), in any script — the manual test exercises Latin and Hebrew (RTL) words. Entries containing whitespace or other word separators will generally never match a flagged token and have no effect. Per-entry validation is described under validation.

Passing a non-iterable (e.g. a bare string is iterable per-character — beware) follows standard Web IDL sequence<DOMString> conversion; the conversion itself (not the dictionary) can throw TypeError for non-iterable arguments, exactly as for any sequence-taking web API.

Source: Blink IDL — sequence<DOMString>; matching semantics per whatwg/html#12590 notes and the manual test.

Return value

None (undefined). The observable effect is entirely visual: spelling squiggles for the added words disappear from every editable region of the document — contenteditable elements, <textarea>, and text inputs — immediately, with no further interaction. Words already present, and words also known to a built-in dictionary, are inert no-ops. Script cannot read the resulting set back; the API is write-only.

Source: Blink IDL — undefined return; immediate whole-document effect per the manual test steps 1–2.

Validation, limits, and errors — the method never throws for word content

Per-word validation happens in the Blink module before anything reaches the spell checker, mirroring the browser custom dictionary’s IsValidWord() (read from spell_check_custom_dictionary.cc, 2026-08-09):

  • Empty strings are skipped.
  • Words padded with leading or trailing whitespace are skipped.
  • Ill-formed UTF-16 (unpaired surrogates) is skipped rather than being stored as a U+FFFD-mangled entry.

Surviving words are then capped in the per-frame SpellCheckProvider (spellcheck_provider.cc), against constants from spellcheck_common.h:

  • A word longer than 128 bytes of UTF-8 (kMaxDocumentCustomDictionaryWordBytes) is dropped.
  • Once the document’s set holds 20 000 words (kMaxDocumentCustomDictionaryWords), every later addition is dropped. The cap bounds the resident set, not lifetime churn — removeWords() frees room.
  • Duplicates of stored words are ignored (set semantics) and not re-broadcast.

The first time any word is dropped for a cap reason, Chrome logs exactly one console warning for the document: “SpellCheckCustomDictionary: per-document word limit reached or a word exceeded the maximum length; some additions were ignored.” No exception is ever thrown for word content, and valid words in the same call are still added. The whole call is additionally a silent no-op when the context is not a window, the frame is gone, or browser spell checking is disabled.

Source: spell_check_custom_dictionary.cc — addWords; spellcheck_provider.cc — SpellCheckCustomDictionaryChanged; spellcheck_common.h.

Context and exposure

The method lives on the SpellCheckCustomDictionary object reached via document.spellCheckCustomDictionary — [SecureContext], Exposed=Window, behind the SpellCheckCustomDictionaryAPI flag. On an insecure origin or with the flag off, the attribute itself is undefined, so there is no method to call. With spell checking disabled in browser settings the method exists but returns without effect (IsSpellCheckingEnabled() gate in spell_check_custom_dictionary.cc). Each document — including each iframe — has its own dictionary; a call in one frame never affects another. No user activation or permission is required.

Source: Blink IDL — SecureContext, Exposed=Window; GetTextCheckEntryPoint; per-frame scope per the ChromeStatus record — security.

Lifecycle and timing

  1. Valid words are forwarded to the per-frame SpellCheckProvider, which inserts them into the live per-document set (removals in the same pipeline are processed before additions).
  2. Newly-inserted words are broadcast to dictionary observers, which strip existing spelling markers for those exact words document-wide — this is why squiggles clear immediately, with no refocus or typing needed.
  3. Subsequent spell-check passes consult the set before flagging, so the words stay unflagged for the document’s lifetime.
  4. The set — and every added word — is discarded when the document is navigated away or destroyed. Nothing persists; only an anonymous word-count histogram (Spellcheck.DocumentCustomDictionary.WordCount) is recorded at teardown.

Calls are idempotent (re-adding a stored word changes nothing) and order-independent within one call’s valid entries. There is no cancellation surface; to undo, call removeWords() with the same strings.

Source: spellcheck_provider.cc; spellcheck.cc — SpellCheckCustomDictionaryChanged / NotifyDictionaryObservers; immediate-clear behavior per the manual test.

Examples

Suppress false positives for a product-vocabulary page (adapted from the explainer’s example):

document.spellCheckCustomDictionary?.addWords([
  'Igalia', 'Wolvic', 'spidermonkey',
]);

Load a vocabulary fetched at runtime — e.g. ticker symbols from a server — and share it with another vocabulary-taking API (the explainer’s cross-API pattern):

const res = await fetch('/api/tickers.json');
const tickers = await res.json();          // e.g. ['AAPL', 'GOOG', 'BRK.B']

const dict = document.spellCheckCustomDictionary;
dict?.addWords(tickers);

// The same list can feed Web Speech contextual biasing:
// recognition.phrases = tickers.map((phrase) => ({ phrase, boost: 1 }));

Security and privacy

Additions are the benign direction of this API: they can only suppress spelling flags for words the page itself supplied, inside the page’s own document. The write-only surface means added words cannot be enumerated back, by the page or by third-party script in the same document. The per-word byte cap and per-document word cap bound memory use against flooding (spellcheck_provider.cc); nothing is written to the user’s browser or OS dictionary, and nothing survives the document.

Source: explainer — privacy & security; ChromeStatus record — security risks.
