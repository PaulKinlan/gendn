SpellCheckCustomDictionary.removeWords()

Limited availability

  • Chrome · dev trial from 153, behind a flag
  • Edge · no signal recorded
  • Firefox · under consideration
  • Safari · no signal

Chrome developer trial only — no Baseline or web-features entry (webstatus.dev query, zero matches, 2026-09-13).

Removes each string in words from the document’s custom spelling exemption list; words not present are ignored. Only the page’s own custom set is affected — built-in, OS, and user dictionaries are never touched, so removing a word that also exists in an underlying dictionary does not cause it to be flagged.

In developer trial — the API surface may move

Dev trial behind a flag from Chrome 153. Enable via chrome://flags/#enable-experimental-web-platform-features (“Experimental Web Platform Features”) or --enable-blink-features=SpellCheckCustomDictionaryAPI. The draft spec (whatwg/html#12590) still names the attribute that hosts this method differently (document.spellCheckDictionary) — the method name itself, removeWords(), matches in both. Do not ship production code against this API.

Source: Dev Trial instructions; runtime_enabled_features.json5.

Syntax

// WebIDL (dev-trial surface):
undefined removeWords(sequence<DOMString> words);

// Call form:
document.spellCheckCustomDictionary.removeWords(["Wolvic", "spidermonkey"]);

The draft spec’s method steps: for each word in words, remove word from the associated document’s custom spelling exemption list, if present.

Source: Dev Trial instructions — API surface; whatwg/html#12590 (removeWords method steps, transcribed from the PR diff 2026-09-13).

Parameters

words A sequence<DOMString> — the strings to remove from this document’s exemption set. Matching against the set uses the same exact, case-sensitive comparison as suppression does, so the string must equal the previously added entry code-unit for code-unit (no case folding, no Unicode normalization). Entries not in the set — including invalid strings that could never have been added — are ignored without error.
Source: whatwg/html#12590 (“Words not present are ignored”, exact-match notes); Dev Trial instructions — exact, case-sensitive matching.

Return value

undefined. The observable effect: removed words become flaggable again on subsequent spell-check passes — unless they are also valid per a built-in, OS, or user dictionary, which this method never modifies. There is no return channel reporting whether a word was actually in the set; the surface is deliberately write-only.

Source: explainer — implementation notes (removeWords affects only the custom set); whatwg/html#12590.

Context and prerequisites

Identical to addWords(): the interface exists only in Chrome 153+ with the SpellCheckCustomDictionaryAPI flag, in a secure Window context on a Blink platform; calls only have a visible effect when spell checking is enabled and the document contains spell-checked editable text (a contenteditable element, <textarea>, or <input type="text"> without spellcheck="false").

Source: Dev Trial instructions — prerequisites.

Lifecycle and state transitions

RemoveAn exact-match entry leaves the live set immediately; the word becomes flaggable again on subsequent checking passes (unless valid per an untouched underlying dictionary).
IdempotenceRemoving an absent word is a no-op — safe to call repeatedly.
CapacityThe 20,000-word cap applies to the live set, so removals free capacity for later addWords() calls.
Why it existsThe explainer treats removeWords() as essential, not a convenience: pages need it to retract mistakes, mirror user unmarks, and bound growth. In single-page applications the document is the whole session — without removal, every view’s vocabulary leaks into subsequent views, and unlike native add-only ignore lists a long-lived page-driven document never gets an automatic reset.
Scope & resetSame set as addWords(): per-document, cleared on every navigation (including same-origin), never shared across frames, discarded with the document.
No eventsNo events fire and the set cannot be observed from script.
Source: explainer — note on why removeWords() is essential; Dev Trial instructions — limits and lifetime.

Examples

The explainer’s canonical pair — add three words, later retract two:

document.spellCheckCustomDictionary.addWords(["Igalia", "Wolvic", "spidermonkey"]);

document.spellCheckCustomDictionary.removeWords(["Wolvic", "spidermonkey"]);

Scope vocabulary to a view in a single-page application:

let activeVocabulary = [];

function setViewVocabulary(words) {
  const dict = document.spellCheckCustomDictionary;
  if (!dict) return;
  dict.removeWords(activeVocabulary); // retract the previous view's terms
  dict.addWords(words);
  activeVocabulary = words;
}

Mirror a user’s correction — if the app learns a term was wrong after all, retract it (removal must match the added string exactly, including case):

document.spellCheckCustomDictionary?.removeWords(["Chramander"]);
// "chramander" (different case) would NOT remove the entry above.

Security and privacy

  • Cannot weaken checking. Removal only shrinks the page’s own suppression set — it never deletes from built-in, OS, or user dictionaries, so a page cannot use it to degrade the user’s spell checking.
  • Write-only. No return value or observable difference between removing a present and an absent word from script, so the method cannot be used to probe set membership directly.
  • Resource hygiene. Removal is the sanctioned way to bound the live set’s size under the 20,000-word cap in long-lived documents.
  • Transient and isolated. Same per-document, discarded-on-destroy scope as the rest of the API.
Source: explainer — implementation notes, privacy & security; Dev Trial instructions — limits.
