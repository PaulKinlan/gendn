SpellCheckCustomDictionary: removeWords()

Removes each string in words from the document’s custom spell-check dictionary, so the browser’s spell checker resumes flagging those exact tokens. Unlike addWords(), the visual effect is deliberately deferred: squiggles reappear per editable region when it is next checked — typically when the user focuses it — rather than instantly. Returns undefined; words not in the set are ignored and the method never throws.

Experimental — dev trial, behind a flag

Available only when the Blink runtime feature SpellCheckCustomDictionaryAPI is enabled (status experimental in runtime_enabled_features.json5, 2026-08-09): set chrome://flags/#enable-experimental-web-platform-features to Enabled, or launch with --enable-blink-features=SpellCheckCustomDictionaryAPI. The API surface may still move — the open spec PR whatwg/html#12590 reaches the same removeWords() via window.spellCheckDictionary instead of document.spellCheckCustomDictionary. See the feature page’s full caveats.

Syntax

document.spellCheckCustomDictionary.removeWords(words)

From the shipped Blink IDL (spell_check_custom_dictionary.idl, fetched 2026-08-09): undefined removeWords(sequence<DOMString> words). The open spec PR whatwg/html#12590 declares the identical signature and specifies the steps as: for each word in words, remove word from the document’s custom spelling exemption list, if present.

Source: Blink IDL; whatwg/html#12590.

Parameters

ParameterTypeDescription
wordssequence<DOMString>The words to remove. Matching against stored entries is exact and verbatim — remove precisely the strings you added. Words not present in the set are ignored. Removal only affects the page’s own custom set: removing a word that is also in a built-in, user, or OS dictionary does not cause it to be flagged (the API is strictly additive over the underlying dictionaries).

As with addWords(), the standard Web IDL sequence<DOMString> conversion can throw TypeError for a non-iterable argument; the dictionary itself never throws for word content.

Source: Blink IDL; additive-only semantics per the explainer — implementation notes.

Return value

None (undefined). The observable effect: the removed words become flaggable again, and their squiggles come back lazily — per editable region, when that region is next spell-checked (see lifecycle). Script cannot query whether a word was actually present; the API is write-only.

Source: Blink IDL — undefined return; deferred re-flagging per the manual test.

Validation and errors — deliberately different from addWords()

The Blink module’s removal path (read from spell_check_custom_dictionary.cc, 2026-08-09, whose comments spell out the reasoning):

  • Empty and whitespace-padded strings are forwarded, not skipped. addWords() never stores them, so a removal request for one matches nothing and is a harmless no-op — filtering would add work for no behavioral difference.
  • Ill-formed UTF-16 is rejected. The internal UTF-8 conversion rewrites an unpaired surrogate to U+FFFD — a valid character that could legitimately be part of a stored entry. Forwarding such a word could silently remove that unrelated entry, so ill-formed input is dropped instead.
  • No caps apply. Removal only shrinks the set, so the 20 000-word and 128-byte limits are enforcement-free here (they gate additions); removals are processed before additions in the same pipeline, so a remove-then-add sequence behaves predictably.
  • Nothing throws and there is no error signal — not for absent words, not for invalid words. The whole call is additionally a silent no-op when the context is not a window, the frame is gone, or browser spell checking is disabled.
Source: spell_check_custom_dictionary.cc — removeWords; spellcheck_provider.cc.

Context and exposure

Identical to addWords(): reached via document.spellCheckCustomDictionary ([SecureContext], Exposed=Window, behind the SpellCheckCustomDictionaryAPI flag — the attribute is undefined when unavailable), a no-op while browser spell checking is off, scoped to this document’s own set only. A frame can never remove another frame’s words, and no user activation or permission is required for the call itself — though seeing the re-flagging depends on user interaction (below).

Source: Blink IDL; GetTextCheckEntryPoint; ChromeStatus record — per-frame design.

Lifecycle and timing — removal re-flags lazily, by design

Removing a word does not instantly repaint squiggles across the document the way adding clears them. The sequence, from the implementation and the CL that landed it (crrev.com/c/7837649):

  1. The words are erased from the per-document set in the frame’s SpellCheckProvider (removals are processed before any additions in the same pipeline).
  2. Because the downstream dictionary-update observer only reacts to added words, the Blink module explicitly invalidates the document’s “already fully checked” cold-mode cache and asks the idle spell-check controller to schedule fresh passes (InvalidateFullyCheckedRoots() + RespondToChangedContents() in spell_check_custom_dictionary.cc).
  3. Each editable region re-flags when it is next actually checked. In practice — per Chromium’s manual test — the squiggle returns when the user focuses the field (no typing needed). Gating the visible refresh on a user gesture is a privacy defense related to the user-dictionary-leaks work: it denies script a synchronous add/remove/measure probe loop.

Consequently a remove-then-measure pattern observes nothing, and users see stale-but-harmless unflagged words until they revisit a field. The words themselves stop matching immediately for any new spell-check pass. The set (and everything in it) is discarded outright when the document goes away — removeWords() exists for long-lived documents such as SPAs, where view-scoped vocabulary would otherwise leak into subsequent views (explainer).

Source: spell_check_custom_dictionary.cc — removeWords comments; crrev.com/c/7837649; manual test — note on add vs remove refresh.

Examples

Retract a mistake or mirror a user’s correction:

const dict = document.spellCheckCustomDictionary;

dict?.addWords(['Wolvic', 'spidermonkey']);
// ... the page later learns 'spidermonkey' should be flagged after all:
dict?.removeWords(['spidermonkey']);
// The squiggle returns in each editable when the user next focuses it.

Scope vocabulary to a view in a single-page app — the document is the whole session, so retract on view exit to keep the set bounded and accurate (the explainer’s core removeWords() use case):

function applyViewVocabulary(dict, words) {
  dict?.addWords(words);
  return function leaveView() {
    dict?.removeWords(words);   // frees cap room, re-arms flagging
  };
}

const leave = applyViewVocabulary(
  document.spellCheckCustomDictionary,
  ['Pikachu', 'Charmander'],
);
// on route change:
leave();
Source: patterns per the explainer — removeWords() rationale; refresh behavior per the manual test.

Security and privacy

Removal is where the anti-probing design is most visible. A hypothetical synchronous re-check would let script race add/remove cycles against ::spelling-error highlight timing to guess dictionary contents (the side channel tracked by user-dictionary-leaks and css-pseudo §highlight security); deferring the visible refresh to a user-gesture-driven check blunts that. The ill-formed-UTF-16 rejection additionally prevents a crafted removal from deleting an unrelated U+FFFD-containing entry the page previously stored. Removal never touches the user’s browser/OS dictionaries and leaves built-in dictionary behavior unchanged.

Source: spell_check_custom_dictionary.cc — removeWords comments; explainer — privacy.
