Spell Check Custom Dictionary API

Limited availability — experimental

  • Chrome · 153 dev trial, behind a flag (milestone listing)
  • Edge · not separately reported (Chromium-based)
  • Firefox · under consideration
  • Safari · no signal

Not on the Baseline register: the ChromeStatus API record marks the Web Feature ID as “Missing feature”, a webstatus.dev query returns zero matches, and BCD has no entry (api/SpellCheckCustomDictionary.json 404) — all verified 2026-08-09.

A per-document, transient custom dictionary that supplements the browser’s built-in spell-checking dictionaries without changing how they behave. A page calls document.spellCheckCustomDictionary.addWords() to mark domain-specific vocabulary — product names, tickers, fictional characters, scientific terms — as known, so the browser’s spell checker stops flagging them as misspelled inside that document. removeWords() retracts entries. The API is deliberately write-only: script can never read the dictionary back.

Experimental — developer trial, behind a flag. The API surface may move.
  • Not enabled by default. Chrome 153 lists this feature as “In developer trial (Behind a flag)” (milestone=153 listing, verified 2026-08-09). The Blink runtime flag is SpellCheckCustomDictionaryAPI, status experimental at trunk and on the M153 branch (branch-heads/7978), per runtime_enabled_features.json5 and the M153 branch copy, both fetched 2026-08-09.
  • Exact enable steps (either one):
    • Set chrome://flags/#enable-experimental-web-platform-features to Enabled and relaunch (the flag enables every experimental-status Blink feature; there is no dedicated chrome://flags entry for this API — zero matches in about_flags.cc, 2026-08-09), or
    • launch with --enable-blink-features=SpellCheckCustomDictionaryAPI.
    Additionally the page must be served from a secure context (https:// or http://localhost) and browser spell checking must be turned on (Settings › Languages) with at least one spellcheck language — otherwise the attribute is undefined or the calls are silent no-ops. These preconditions are spelled out in Chromium’s own manual test.
  • The attribute name is not settled. Chrome’s dev trial ships document.spellCheckCustomDictionary (per the shipped Blink IDL), but the open HTML Standard pull request whatwg/html#12590 proposes window.spellCheckDictionary — a different attribute name on a different global. The PR is not merged (the published HTML Standard contains neither name, verified 2026-08-09). Code written against the dev trial may need renaming before this ships.
  • No effect is observable from script. The only outcome is that spelling squiggles appear or disappear. Nothing throws, nothing returns state — debug by watching editable regions (ChromeStatus record, debuggability).

reference routes

addWords()

Add words to the per-document dictionary. Validation rules, the 20 000-word / 128-byte caps, immediate squiggle removal, and complete examples.

removeWords()

Remove words from the per-document dictionary. Why its validation differs from addWords(), and how re-flagging is deliberately deferred as a privacy defense.

why it exists

Spell checkers routinely flag words that are correct within a particular site but unknown to general dictionaries, per the ChromeStatus record’s motivation:

  • A Pokémon wiki containing names like Pikachu or Charmander.
  • A financial analysis dashboard referencing company-specific product names or tickers.
  • A medical or scientific tool using specialized terminology.

False positives in these contexts are distracting and erode user trust. Browsers let users add words via a settings panel, but until now there was no way for the page to declare its own domain vocabulary programmatically, scoped to its own context. The explainer notes the API is intentionally minimal — one call, no setup — and is not polyfillable, since no existing surface can suppress the browser’s native squiggles.

Source: ChromeStatus API record — motivation, activation risks; Spell Check Custom Dictionary API explainer.

Syntax

The Web IDL Chrome’s developer trial ships, verbatim from the Blink module (spell_check_custom_dictionary.idl and document_spell_check_custom_dictionary.idl, fetched 2026-08-09; Blink-specific extended attributes [CallWith], [ImplementedAs], [RuntimeEnabled] omitted):

[
    Exposed=Window,
    SecureContext
] interface SpellCheckCustomDictionary {
    undefined addWords(sequence<DOMString> words);
    undefined removeWords(sequence<DOMString> words);
};

partial interface Document {
    [SameObject] readonly attribute SpellCheckCustomDictionary spellCheckCustomDictionary;
};

This matches the IDL in the explainer exactly. The interface has no constructor — the only way to obtain the object is the document.spellCheckCustomDictionary getter. Both methods take a sequence<DOMString> (any iterable of strings) and return undefined; neither throws for invalid words (see validation and limits).

The open spec PR whatwg/html#12590 instead hangs a [SecureContext, SameObject] readonly attribute SpellCheckCustomDictionary spellCheckDictionary off Window, backed by a per-Document “custom spelling exemption list” (an ordered set of strings). The interface name and both method names are the same; the accessor differs. This page documents the shipped dev-trial surface and flags the divergence rather than guessing the outcome.

Source: Blink interface IDL; Blink Document partial IDL; whatwg/html#12590 diff.

Document.spellCheckCustomDictionary

A read-only accessor returning the document’s SpellCheckCustomDictionary object. It is annotated [SameObject], so every access returns the identical object — Chromium’s same-object.https.html test asserts identity across repeated accesses and across held references. Being a plain readonly attribute getter, it takes no arguments and never throws.

Exposure is conditional, and the failure mode is absence, not an exception:

  • On an insecure origin ([SecureContext]), or with the SpellCheckCustomDictionaryAPI runtime flag off, the attribute simply does not exist — document.spellCheckCustomDictionary evaluates to undefined. Feature-detect with if ('spellCheckCustomDictionary' in document).
  • The attribute is Exposed=Window only — it does not exist in workers.
  • Even when the object exists, its methods are silent no-ops if browser spell checking is disabled (see availability and platform behavior).

The object’s lifetime follows its document: each Document — including every iframe’s — gets its own object backed by its own independent word set, and the set is discarded when the document is destroyed or navigated away.

Source: document_spell_check_custom_dictionary.idl; same-object.https.html; explainer — per-document lifecycle.

how it works: a suppression filter over spell-check results

The existing spell-check pipeline is unchanged; the custom set is consulted only when results are reconciled. The per-document word set lives in the renderer’s per-frame SpellCheckProvider (document_custom_words_), and Chromium’s spell checker consults it wherever misspelling results are produced (spellcheck.cc): a token that would otherwise be flagged is skipped if it is in the profile custom dictionary or in the per-document word set. The check is strictly additive — it can only suppress a spelling flag, never create one, and removeWords() only affects the page’s own set, so removing a word that also exists in a built-in dictionary does not cause it to be flagged.

Behavioral consequences, each verified against the linked sources:

  • Exact match only. The flagged token must equal a stored word verbatim (document_custom_words_.contains(...) on the exact substring). Anaerobe does not cover anaerobes; add each form. The spec PR makes the same point normatively, and entries containing whitespace or word separators will generally match nothing.
  • Language-agnostic. The set is consulted independently of which enabled spellcheck language produced the flag — words apply across all user-enabled languages, exactly like words a user adds in browser settings (explainer, internationalization; exercised by the manual test with Latin and Hebrew words).
  • Whole-document effect. One addWords() call suppresses the squiggle for that word in every editable region of the document — contenteditable regions, <textarea>, and text inputs alike.
  • Per-document lifecycle. On navigation to a new document the set is cleared (DidCreateNewDocument in spellcheck_provider.cc). For a long-lived single-page app the document is the session — vocabulary does not reset on view switches, which is exactly why removeWords() exists (explainer). Chrome records only an anonymous word-count histogram at teardown, not the words.
  • Refresh timing is asymmetric. Adding words clears existing squiggles immediately; removal re-flags lazily — squiggles reappear per editable when it is next checked (focus by user gesture, typing, or an idle re-check pass). The asymmetry is deliberate; the removeWords() page documents the mechanism and its privacy rationale.
Source: spellcheck.cc — SpellCheckParagraph / CreateTextCheckingResults; spellcheck_provider.cc; explainer — implementation notes; add-remove-words-manual.html — all fetched 2026-08-09.

availability and platform behavior

Every one of these preconditions must hold before the API has any observable effect; none of them produces an error when unmet:

PreconditionBehavior when unmet
Runtime flag SpellCheckCustomDictionaryAPI enableddocument.spellCheckCustomDictionary is undefined
Secure context (https:// or localhost)document.spellCheckCustomDictionary is undefined ([SecureContext])
Window context (not a worker)Interface not exposed (Exposed=Window)
Browser spell checking enabled with ≥1 languageMethods return without doing anything — the implementation bails out when IsSpellCheckingEnabled() is false (spell_check_custom_dictionary.cc)

Per-platform notes, from the ChromeStatus record’s all-platforms description: the Blink API surface is platform-independent, and the suppression filter applies regardless of spell-check backend — Windows (hybrid native + Hunspell), macOS (native NSSpellChecker), Linux / ChromeOS (Hunspell in the renderer) are all supported. On Android, misspellings reported through the browser’s spell-check result path are suppressed, but squiggle-like suggestion markers originating from the Android IME/keyboard during composition are outside the browser’s pipeline and are not suppressed — a page cannot override the system keyboard’s dictionary. On Android WebView the filter applies in principle, but spell checking is disabled by default in WebView, so the API has no observable effect on typical WebView content.

Source: ChromeStatus API record — all_platforms description; spell_check_custom_dictionary.cc — GetTextCheckEntryPoint.

validation and limits — nothing ever throws

Both methods return undefined unconditionally. Invalid entries are silently skipped, and resource caps are enforced by dropping surplus words — the page keeps running either way. The concrete contract, read from spell_check_custom_dictionary.cc and spellcheck_provider.cc (2026-08-09):

RuleaddWords()removeWords()
Empty stringSkippedForwarded (harmless no-op — such words are never stored)
Leading/trailing whitespaceSkipped (matches the browser custom dictionary’s IsValidWord())Forwarded (harmless no-op)
Ill-formed UTF-16 (unpaired surrogates)Skipped — never stored as a U+FFFD-mangled entrySkipped — so it cannot accidentally remove a legitimate U+FFFD entry
Word longer than 128 bytes (UTF-8)Dropped (kMaxDocumentCustomDictionaryWordBytes)n/a — removal has no length gate
Set already holds 20 000 wordsAll further additions dropped (kMaxDocumentCustomDictionaryWords)n/a — removal shrinks the set
Duplicate of a stored wordIgnored (set semantics)n/a
Word not in the setn/aIgnored (no-op)

When any addition is dropped for a cap reason, Chrome logs one console warning per document: “SpellCheckCustomDictionary: per-document word limit reached or a word exceeded the maximum length; some additions were ignored.” The caps bound the resident set, not lifetime churn — removing words frees room for new ones. Both constants are defined in spellcheck_common.h; the explainer records the design intent that surplus words are ignored rather than corrupting state or breaking the page.

Source: spell_check_custom_dictionary.cc; spellcheck_provider.cc — SpellCheckCustomDictionaryChanged; spellcheck_common.h; explainer — resource limits.

Examples

Feature-detect, then load a domain vocabulary. The words apply to every editable region in the document as soon as the call returns:

// The attribute is absent (undefined) on insecure origins or when the
// SpellCheckCustomDictionaryAPI flag is off — feature-detect first.
if ('spellCheckCustomDictionary' in document) {
  // One call marks the whole page's domain vocabulary as known.
  document.spellCheckCustomDictionary.addWords([
    'Igalia', 'Wolvic', 'spidermonkey',
  ]);
}

A single-page app scoping vocabulary to the current view — the document outlives view switches, so retract the old view’s words when it goes away (matching is exact, so inflected forms are added individually):

const dict = document.spellCheckCustomDictionary;

function enterView(vocabulary) {
  dict?.addWords(vocabulary);          // squiggles clear immediately
  return () => dict?.removeWords(vocabulary);
  // After removal, squiggles reappear per editable when it is next
  // checked (e.g. when the user focuses it) — not instantly.
}

const leaveTickers = enterView(['AAPL', 'GOOG', 'BRK.B']);
// ... later, when the view unmounts:
leaveTickers();

Runnable material: Chromium’s own manual test page (also browsable on source.chromium.org) drives add/remove across contenteditable, textarea, RTL text, and the resource caps — it is the closest thing to a live demo today. The sister Chrome Platform Showcase route for this feature returned 404 at build time (2026-08-09), so no live iframe is embedded here.

Source: first snippet adapts the explainer’s example; SPA pattern per the explainer’s removeWords() rationale; refresh timing per the manual test.

security and privacy

  • Write-only by design. There is no read, has, size, or iteration surface — a page can only observe words it supplied itself. The explainer rejected ObservableArray and setlike shapes specifically because they would re-expose the read surface (TAG feedback: spell-check internals are “carefully designed to not be observable”).
  • Transient, per-frame state. The word set is owned by a single Document; every frame — including cross-origin third-party iframes — gets its own independent set, and an embedded third party can only affect its own document. The set is discarded at teardown. Nothing is persisted, synced, or shared, and there is no network exposure (ChromeStatus security section).
  • No writes to user or OS dictionaries. The API maps to ignored-word semantics, never learned-word semantics: it neither reads nor modifies the browser’s or operating system’s dictionaries (explainer).
  • Abuse mitigation. Input validation (empty / whitespace-padded / ill-formed UTF-16 rejected) plus the 20 000-word and 128-byte caps bound resource use; surplus words are ignored with a console warning rather than corrupting state (spellcheck_provider.cc).
  • Known adjacent side channel. A page could try to probe dictionary membership by timing ::spelling-error highlight painting. That channel predates this API and is being addressed in css-pseudo §highlight security and the user-dictionary-leaks proposal; the explainer notes fixing it would also protect the custom set. Chrome’s deferred re-check after removeWords() (gated on a user-gesture focus) is one such defense — see the removeWords() page.
