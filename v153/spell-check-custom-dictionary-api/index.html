Spell check custom dictionary API

Adds a secure-context, write-only document.spellCheckCustomDictionary object (SpellCheckCustomDictionary) with addWords(words) and removeWords(words) methods so web applications can register domain-specific vocabulary — product names, technical terms, tickers, or proper nouns — to suppress false-positive spelling underlines for the lifetime of that Document without modifying user or OS dictionaries and without allowing scripts to read entries back.

Limited availability — Developer trial behind a flag from Chrome 153 (proposed ship target Chrome 162; not yet enabled by default); Safari signaled Support and Firefox Neutral

  • Edge · Mirrors Chromium experimental flag

  • Safari · Support (WebKit #646); no release yet

No web-features or BCD entry exists for Document.spellCheckCustomDictionary yet (checked 2026-11-27 against webstatus.dev and BCD api/Document.json). MDN documents the HTML spellcheck global attribute, but has no reference page for SpellCheckCustomDictionary.

Developer trial behind a flag from Chrome 153 (not yet enabled by default): To test locally, enable chrome://flags/#enable-experimental-web-platform-features or launch Chromium with --enable-blink-features=SpellCheckCustomDictionaryAPI (defined with status: "experimental" and public: true in runtime_enabled_features.json5; there is no dedicated origin trial or standalone chrome://flags entry). ChromeStatus lists a proposed ship target of Chrome 162; the API is not yet enabled by default and requires a secure context (HTTPS or localhost).

why it exists

Editable fields in domain-specific web apps — wikis, medical or scientific tools, code/issue trackers, financial dashboards — routinely contain valid proper nouns, acronyms, and product terms unknown to general dictionaries. Previously, authors could only disable spell checking altogether via spellcheck="false" (losing real typo detection) or ask every user to add words manually to their persistent browser/OS dictionary. document.spellCheckCustomDictionary layers an ephemeral, document-scoped ignore set on top of the browser’s existing spell checker so domain words stop getting red underlines without mutating persistent user state.

Source: Igalia Spell Check Custom Dictionary API explainer; ChromeStatus 6185007701557248.

Syntax

The API introduces one write-only interface (SpellCheckCustomDictionary) exposed via one [SameObject] readonly attribute on Document in secure Window contexts:

[Exposed=Window, SecureContext]
interface SpellCheckCustomDictionary {
  undefined addWords(sequence<DOMString> words);
  undefined removeWords(sequence<DOMString> words);
};

partial interface Document {
  [SecureContext, SameObject] readonly attribute SpellCheckCustomDictionary spellCheckCustomDictionary;
};

This reference documents all four developer-facing surfaces: Document.spellCheckCustomDictionary, the SpellCheckCustomDictionary interface (matching, normalization & Chromium limits), addWords(), and removeWords().

Source: Blink spell_check_custom_dictionary.idl; document_spell_check_custom_dictionary.idl; WHATWG HTML PR #12590.

Document.spellCheckCustomDictionary

Inputs. Read-only getter on any Document in a secure Window context; takes no parameters and cannot be reassigned.

Outputs. Returns the same SpellCheckCustomDictionary instance on every access ([SameObject]), bound to that specific Document. Each browsing context (including every same-origin or cross-origin <iframe>) has its own isolated dictionary instance. Calling methods on a dictionary obtained from a frameless document (such as document.implementation.createHTMLDocument() or DOMParser) or a navigated-away document is a silent no-op so words never leak into another frame.

Source: Blink document_spell_check_custom_dictionary.idl; Blink spell_check_custom_dictionary.cc (GetTextCheckEntryPoint).

SpellCheckCustomDictionary interface, matching rules & Chromium limits

Inputs & Outputs. SpellCheckCustomDictionary has no constructor, no length/size property, no has(), and no iterator — it is deliberately write-only (matching native “ignored words” semantics rather than persistent “learned words”). The dictionary acts strictly as an additive suppression filter over spell-checker results: it can prevent a word from receiving a spelling marker, never flag a word that an underlying dictionary accepts, and applies across all user-enabled spell-check languages.

Matching rules, proposed normalization, and Chromium resource limits for SpellCheckCustomDictionary

SpellCheckCustomDictionary.addWords(words)

Inputs. Accepts words, a WebIDL sequence<DOMString> (any JS iterable of values coerced to strings, typically an Array<string>). In Blink (spell_check_custom_dictionary.cc), each element is validated before forwarding: empty strings, strings with leading or trailing whitespace, and ill-formed UTF-16 strings (containing unpaired surrogates) are silently skipped. Entries exceeding 128 UTF-8 bytes are skipped, and once the document’s live set reaches 20,000 entries, remaining words in the batch are silently ignored. Words containing internal spaces or punctuation are accepted by validation, though the spell checker splits text into words first so multi-word phrases generally will not match.

Outputs. Returns undefined synchronously. Newly added words are inserted into the frame’s document_custom_words_ set and passed to OnDictionaryUpdated(), which clears existing spelling markers under newly exempted words in that frame without touching other frames. Words are still recorded even if the user currently has spell checking disabled, so they apply immediately if spell checking is re-enabled during the document’s lifetime.

Source: Blink spell_check_custom_dictionary.cc; Chromium spellcheck_provider.cc.

SpellCheckCustomDictionary.removeWords(words)

Inputs. Accepts words, a WebIDL sequence<DOMString>. Ill-formed UTF-16 entries (unpaired surrogates) are skipped so they cannot be mangled into U+FFFD and accidentally delete a valid word containing U+FFFD. Removing a word that is not in the custom set (or that exists in the browser/OS dictionary) is a harmless no-op and never modifies underlying dictionaries.

Outputs. Returns undefined synchronously. Deletes matching words from the document’s custom set (freeing slots under the 20,000-word cap). When spell checking is enabled, Blink immediately calls InvalidateFullyCheckedRoots() on the cold-mode spell-check requester and RespondToChangedContents() on SpellChecker so editable roots are re-checked and spelling squiggles return on removed words without requiring the user to re-type.

Source: Blink spell_check_custom_dictionary.cc; Chromium spellcheck_provider.cc.

Errors, invalid inputs, and silent ignores

  • Missing or non-iterable argument: Calling addWords() or removeWords() with no argument or a non-iterable value (such as null or a number) throws a WebIDL TypeError.
  • Silent ignores (no exception thrown): Empty strings, whitespace-padded strings (" foo "), unpaired UTF-16 surrogates, words over 128 UTF-8 bytes, duplicate entries, words past the 20,000-word per-document cap, and calls on detached/frameless documents do not throw — they are silently skipped so valid words in the same batch still succeed.
  • Non-secure context: In an insecure (http://, non-localhost) context, document.spellCheckCustomDictionary is undefined ([SecureContext]).
  • No observable spelling-marker feedback: Scripts cannot inspect whether a word was underlined or suppressed; this is intentional to prevent dictionary-probing side channels.
Source: Blink spell_check_custom_dictionary.cc; Chromium spellcheck_provider.cc; Igalia explainer.

Context, exposure, and third-party isolation

Exposed exclusively on Window in secure contexts ([Exposed=Window, SecureContext]) when SpellCheckCustomDictionaryAPI is enabled. Not exposed in Workers or Worklets. Feature-detect via "spellCheckCustomDictionary" in document (or Boolean(document.spellCheckCustomDictionary)). Because storage is keyed per RenderFrame / Document, cross-origin and same-origin iframes have completely separate dictionaries; words added in one frame never suppress misspellings in another frame or in browser extensions like Grammarly.

Source: Blink spell_check_custom_dictionary.idl; Chromium spellcheck_provider.cc; Igalia explainer.

Lifecycle, SPA view scoping, and navigation reset

  1. Document creation: Each new document starts with an empty document_custom_words_ set.
  2. Registering vocabulary: Call document.spellCheckCustomDictionary.addWords(terms) once your domain glossary loads; existing markers on matching tokens are cleared asynchronously.
  3. SPA route changes: In single-page applications, call removeWords(previousTerms) when leaving a view so stale glossary terms do not leak into unrelated views or exhaust the 20,000-word cap; Blink automatically schedules a fresh spell-check pass across all editable roots.
  4. Navigation / tab close: On navigation to a new document (SpellCheckProvider::DidCreateNewDocument()) or closing the tab, the entire custom word set is discarded from memory and never persisted to disk or OS dictionaries.
Source: Chromium spellcheck_provider.cc (DidCreateNewDocument); Igalia explainer.

Examples

Live showcase editor & SPA glossary manager

class DocumentGlossary {
  #activeWords = new Set();

  static isSupported() {
    return (
      typeof document !== "undefined" &&
      "spellCheckCustomDictionary" in document &&
      document.spellCheckCustomDictionary !== null
    );
  }

  /** Replace the current view's vocabulary cleanly (ideal for SPA route transitions). */
  setViewVocabulary(words) {
    if (!DocumentGlossary.isSupported()) return false;

    const dict = document.spellCheckCustomDictionary;
    const next = new Set(
      words
        .map((w) => String(w).trim())
        .filter((w) => w.length > 0)
    );

    const toRemove = [...this.#activeWords].filter((w) => !next.has(w));
    const toAdd = [...next].filter((w) => !this.#activeWords.has(w));

    if (toRemove.length > 0) {
      dict.removeWords(toRemove);
    }
    if (toAdd.length > 0) {
      dict.addWords(toAdd);
    }

    this.#activeWords = next;
    return true;
  }

  clear() {
    if (!DocumentGlossary.isSupported() || this.#activeWords.size === 0) return;
    document.spellCheckCustomDictionary.removeWords([...this.#activeWords]);
    this.#activeWords.clear();
  }
}

// Usage: add exact casings needed (API matching is case-sensitive).
const glossary = new DocumentGlossary();
glossary.setViewVocabulary(["Igalia", "Wolvic", "WebIDL", "Pikachu", "PIKACHU"]);

Security and privacy

  • Write-only surface (no dictionary probing): SpellCheckCustomDictionary deliberately omits has(), size, and iteration (rejecting ObservableArray and SetLike designs after TAG review #1191) so scripts cannot read back or enumerate dictionary contents. Related CSS highlight timing side channels on ::spelling-error are mitigated separately in CSS Pseudo-Elements #highlight-security and the user-dictionary-leaks proposal.
  • Transient, per-document memory only: Entries never touch the user’s persistent browser dictionary or OS spell-checker database (such as macOS’s global learned dictionary) and are cleared on document navigation or tab close.
  • Strict frame isolation: Every iframe — including third-party cross-origin frames — owns an independent word set; frameless documents are ignored.
  • Abuse and memory bounds: Chromium bounds the live set to 20,000 words and 128 UTF-8 bytes per word, dropping surplus entries silently to prevent memory exhaustion without breaking page execution.
  • Secure-context gating: Restricted to [SecureContext] origins so network attackers on plaintext HTTP cannot inject misleading dictionary exemptions.
Source: Igalia explainer (Privacy & Security); w3ctag/design-reviews#1191; Chromium spellcheck_common.h.
