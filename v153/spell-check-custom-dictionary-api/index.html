Spell Check Custom Dictionary API

Limited availability

  • Chrome · dev trial from 153, behind a flag
  • Edge · no signal recorded
  • Firefox · under consideration
  • Safari · no signal

Not on the Baseline register: a webstatus.dev query returns zero matches and the ChromeStatus record marks the Web Feature ID as “Missing feature” (both verified 2026-09-13). Firefox’s view is “Under consideration” (mozilla/standards-positions#1384, open and unscreened); Safari’s is “No signal” (WebKit/standards-positions#646, open, no position stated).

document.spellCheckCustomDictionary gives a page a per-document, transient custom dictionary that supplements the browser’s built-in spell-checking dictionaries. Script calls addWords() to stop the spell checker flagging domain-specific words — product names, tickers, fictional universes, scientific terminology — inside its own document, and removeWords() to retract them. Built-in and user dictionaries are untouched, and nothing persists past the document.

In developer trial — the API surface may move

This feature is in a developer trial (behind a flag) from Chrome 153 (milestone=153 listing, verified 2026-09-13; dev-trial announcement: Ready for Developer Testing, blink-dev, 2026-08-04). The specification is still a draft WHATWG HTML pull request whose IDL already differs from the shipped surface (see Syntax) — do not ship production code against this API.

  • Enable it either via chrome://flags/#enable-experimental-web-platform-features (“Experimental Web Platform Features”) or by launching Chrome with --enable-blink-features=SpellCheckCustomDictionaryAPI — both routes are given in the owners’ Dev Trial instructions.
  • Blink runtime feature. SpellCheckCustomDictionaryAPI, status "experimental", in runtime_enabled_features.json5 (fetched 2026-09-13); the Finch name in the ChromeStatus record is the same string. There is no dedicated chrome://flags entry for this feature alone.
  • Version. Chrome Canary or Dev, milestone 153 or newer — the Dev Trial instructions note it was developed against 153.0.7983.0.
Source: Dev Trial instructions; runtime_enabled_features.json5; blink-dev — Ready for Developer Testing.

at a glance

What it isOne Document attribute, document.spellCheckCustomDictionary (see below), returning a SpellCheckCustomDictionary object with exactly two methods: addWords(words) and removeWords(words). Deliberately write-only — there is no way to enumerate, query, or clear the set wholesale.
Ships inChrome 153 as a developer trial behind a flag — the milestone=153 listing files it under “In developer trial (Behind a flag)” (verified 2026-09-13)
ScopePer-document and transient: the word set is discarded on navigation (including same-origin) and never shared across documents, frames, or browsing contexts. Every iframe — including cross-origin ones — gets its own independent dictionary.
EffectDuring spell checking the browser also consults this set; matching words are not flagged. Strictly additive suppression — it can only remove a squiggle, never create one, and it never modifies built-in, OS, or user dictionaries.
MatchingExact, case-sensitive, per-word (see matching and limits)
PrerequisitesSecure context · Window context (not workers) · the flag (see warn-block) · spell checking enabled with checkable editable text for any visible effect

why it exists

Spell checkers routinely flag words that are correct within a particular site but unknown to general dictionaries — the explainer’s examples are a Pokémon wiki (“Pikachu”, “Charmander”), a financial dashboard with company-specific product names or tickers, and medical or scientific tools using specialized terminology. Those false positives are distracting and erode user trust, and while browsers let each user add words manually through settings, that requires action from every user on every site. This API lets the page author — who already knows the domain vocabulary is valid — suppress the false positives programmatically, for their own document only.

The shape of the API is deliberately minimal. The explainer documents the alternatives that were considered and rejected: an ObservableArray attribute and a setlike interface were both dropped because they re-expose a read surface — the TAG review noted that “all of the spell check-related things are carefully designed to not be observable”, so the write-only addWords()/removeWords() pair exists precisely so there is no enumerable object to probe. A unified cross-feature CustomDictionary (shared with Web Speech contextual biasing and the Proofreader API) and a declarative <link rel="custom-dictionary"> form were deferred as future work, and document scope was chosen over DOM-subtree scope as the more conservative starting point. On platforms whose native spell-check APIs distinguish ignored from learned words, this API maps to the ignored semantics — transient and in-memory, never written into any persistent dictionary.

Source: explainer — user-facing problems, proposed approach, alternatives considered; TAG design review #1191; ChromeStatus record (motivation field).

Syntax

The surface shipped in the Chrome 153 dev trial (verbatim from the owners’ Dev Trial instructions, matching the explainer’s proposed IDL):

[Exposed=Window, SecureContext]
interface SpellCheckCustomDictionary {
  undefined addWords(sequence<DOMString> words);
  undefined removeWords(sequence<DOMString> words);
};

partial interface Document {
  [SameObject] readonly attribute SpellCheckCustomDictionary spellCheckCustomDictionary;
};

The draft specification — WHATWG HTML pull request #12590, still open and marked draft — defines the same two methods but currently differs from the shipped surface. Verbatim from the PR diff:

[Exposed=Document]
interface SpellCheckCustomDictionary {
  undefined addWords(sequence<DOMString> words);
  undefined removeWords(sequence<DOMString> words);
};

partial interface Document {
  // ...
  readonly attribute SpellCheckCustomDictionary spellCheckDictionary;
};

Discrepancies to watch (this is exactly the kind of movement the dev trial exists to settle): the PR names the attribute spellCheckDictionary while Chrome 153 exposes spellCheckCustomDictionary; the PR writes [Exposed=Document] with no SecureContext annotation while Chrome ships [Exposed=Window, SecureContext]; and the PR expresses same-object behavior through a “custom spelling dictionary holder” caching algorithm rather than Chrome’s [SameObject] annotation — behaviorally equivalent (repeated reads return the identical object, which Chrome’s same-object test asserts). The PR also states that “user agents that do not support spell checking must not expose” the attribute at all.

Source: Dev Trial instructions — API surface; whatwg/html#12590 (IDL transcribed from the PR diff, fetched 2026-09-13).

Document.spellCheckCustomDictionary

Syntax[SameObject] readonly attribute SpellCheckCustomDictionary spellCheckCustomDictionary; — read as document.spellCheckCustomDictionary. [SameObject] guarantees every read returns the identical object.
ReturnsThe document’s SpellCheckCustomDictionary object — the write-only handle to this document’s word set. In the draft spec the getter lazily creates the object on first read and caches it in the document’s “custom spelling dictionary holder” (initially null), returning the cached object thereafter. Where the feature is unavailable (flag off, insecure context, worker, non-Blink browser) the attribute is undefined.
ErrorsThe getter itself never throws. Calling a method on the undefined attribute in an unsupported context throws the page’s own TypeError — feature-detect with if ("spellCheckCustomDictionary" in document) or optional chaining.
Context & exposure[Exposed=Window, SecureContext] — window contexts only (not workers), https:// or http://localhost only, and behind the SpellCheckCustomDictionaryAPI flag (see the warn-block). The draft PR additionally requires that user agents without spell-checking support not expose the attribute at all.
LifecycleOne dictionary object per document, created on first read, stable for the document’s lifetime. The underlying word set is per-document and transient: cleared on every navigation (including same-origin) and discarded when the document is destroyed. Nothing is synced or persisted.
Exampledocument.spellCheckCustomDictionary?.addWords(["Igalia"]); (see examples)
CompatibilityChrome 153+ behind a flag; undefined everywhere else (see browser compatibility).
Security & privacyThe returned object is write-only, so its presence exposes nothing about any dictionary’s contents (see security and privacy).

Methods

Both methods take a sequence<DOMString> and return undefined; each has a full child reference:

  • SpellCheckCustomDictionary.addWords(words) — adds each string to the document’s custom spelling exemption list; words already present are ignored.
  • SpellCheckCustomDictionary.removeWords(words) — removes each string from the list; words not present are ignored. Only the custom set is affected — never the built-in or user dictionaries.
Source: whatwg/html#12590 (method steps); explainer — proposed approach.

matching semantics and limits

The draft spec models the dictionary as each document’s “custom spelling exemption list” — an ordered set of strings, initially empty. If checking is enabled for a word and that word matches any entry in the element’s node document’s list, the user agent should not indicate a spelling error for it.

Exact matchEntries are matched exactly — a code-unit comparison against the flagged word. No case folding (adding "Pikachu" does not suppress "pikachu") and no Unicode normalization (a word added in NFC does not suppress the same word typed in NFD — worth watching on macOS). Authors may need to add multiple forms, e.g. both “anaerobe” and “anaerobes”.
Per-word matchEntries are matched against individual words as identified by the user agent’s spell-checking algorithm; entries containing whitespace or other word separators will generally not match any word and have no effect.
Entry validationInvalid entries are silently skipped (matching the browser custom dictionary’s validation): empty strings, words with leading or trailing whitespace, and ill-formed UTF-16 (unpaired surrogates). No error is raised.
Limits (Chrome)20,000 words per document and 128 bytes (UTF-8) per word. The cap applies to the live set, so removeWords() frees capacity. An over-length word is skipped on its own, but once the cap is reached the rest of that addWords() call is dropped. The explainer leaves limits implementation-defined, with well-defined at-limit behavior (surplus words ignored, never corrupting existing state).
Language targetingNone beyond the status quo: words apply across all user-enabled languages, exactly as user-added custom-dictionary words do today.
Source: whatwg/html#12590 (exemption-list concept and matching notes); Dev Trial instructions — behaviour to be aware of; explainer — internationalization, resource limits.

Examples

The canonical example from the explainer — add domain words, later retract some:

document.spellCheckCustomDictionary.addWords(["Igalia", "Wolvic", "spidermonkey"]);

document.spellCheckCustomDictionary.removeWords(["Wolvic", "spidermonkey"]);

Feature-detect before use — where the flag is off (or the context is insecure, a worker, or a non-Blink browser) the attribute is undefined and calling a method on it throws a TypeError:

if ("spellCheckCustomDictionary" in document) {
  document.spellCheckCustomDictionary.addWords(vocabulary);
} else {
  // No API: users may see false-positive squiggles for domain terms.
}

Single-page applications: the document survives view switches, so scope each view’s vocabulary explicitly — the explainer calls this out as the reason removeWords() exists:

function enterView(view) {
  document.spellCheckCustomDictionary?.addWords(view.vocabulary);
}
function leaveView(view) {
  // Without this, every view's vocabulary leaks into subsequent views.
  document.spellCheckCustomDictionary?.removeWords(view.vocabulary);
}

Two further showcase demos exercise the contract: scope and lifetime (per-document scoping and navigation reset) and probe and shape (the write-only surface and matching semantics). Both routes HEAD-checked 200, 2026-09-13.

Source: explainer — example; Dev Trial instructions — prerequisites.

web platform tests

The ChromeStatus record answers “fully tested by web-platform-tests?” with No, explaining: “The blocker is that the effect this API produces — a spelling squiggle appearing or disappearing — has no representation that a Web Platform Test can legitimately observe”; renderer unit tests and manual WPT tests were added to make up for it. The tests live in Chromium’s wpt_internal tree (not upstreamed):

security and privacy

  • Transient data. The custom dictionary is discarded when the document or tab closes; nothing is written to disk, synced, or shared with other tabs.
  • No dictionary probing. The API exposes no read method — a page can only observe words it supplied itself. Words added here do not appear in chrome://settings/editDictionary and never touch the user’s own dictionary, so the API adds no new way to read what the user has taught their browser.
  • Known adjacent side channel. A highlight-timing side channel lets a page probe dictionary membership by observing ::spelling-error/::grammar-error rendering; it is being addressed in css-pseudo §highlight-security and the user-dictionary-leaks proposal. The explainer notes the same channel could in principle be used to guess the contents of the custom set itself, so fixing it benefits this API too.
  • Per-document isolation. Every iframe — including cross-origin, third-party frames — gets its own independent dictionary; an embedded third party can only add or remove words for its own document. The Chromium-side design is detailed in The Per-Document Design in Chromium.
  • Abuse limits. Word-count and word-length caps (20,000 words, 128 UTF-8 bytes per word in Chrome) bound resource use from addWords()/removeWords() churn, with well-defined at-limit behavior: surplus words are ignored rather than corrupting existing state.
  • No new network exposure. The API requires no network access.
Source: explainer — accessibility, internationalization, privacy & security; Dev Trial instructions — limits; css-pseudo §highlight-security; per-document design doc.
