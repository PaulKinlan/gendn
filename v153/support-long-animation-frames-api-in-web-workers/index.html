Support Long Animation Frames API in Web Workers

Limited availability — worker exposure is Chrome-only, behind a flag

  • Chrome · 153 dedicated workers, developer trial behind a flag (milestone listing)
  • Edge · not separately reported (Chromium-based)
  • Firefox · no signal
  • Safari · no signal

The base Long Animation Frames API is itself only “Baseline Limited availability” — Chrome/Edge 123, no Firefox or Safari support, per the webstatus.dev record for long-animation-frames. The worker exposure documented here has no web-features entry of its own, no BCD worker_support subfeature, and the LoAF spec still says [Exposed=Window] (all verified 2026-08-09).

Extends the Long Animation Frames (LoAF) API to dedicated Web Workers. LoAF today reports only on the main thread and is anchored to rendering frames, so it cannot observe work that blocks a worker’s event loop. With this change, a long task that blocks a dedicated worker’s event loop is reported as a "long-animation-frame" entry, observable from inside the worker via PerformanceObserver, with the usual per-script attribution — plus a new scriptCount attribute. This page documents the delta: what becomes observable in workers and how worker entries differ from window entries. For the base API, see MDN’s PerformanceLongAnimationFrameTiming reference.

Developer trial — the API surface is actively moving
  • Exact enable steps. The Blink feature LongAnimationFrameWorker has status "test" in runtime_enabled_features.json5 at trunk and on the M153 branch (7978), both fetched 2026-08-09. That means there is no chrome://flags entry and the “Experimental Web Platform features” toggle does not enable it (that toggle covers experimental-status features). Launch Chrome from the command line with:
    --enable-blink-features=LongAnimationFrameWorker
    — the same invocation Chromium’s own worker LoAF test documents. There is no origin trial (ChromeStatus API record: origintrial: false).
  • The reporting model has already changed after M153. On the M153 branch a worker entry is emitted for a single task that occupies the event loop for ≥ 200 ms. Chromium trunk (fetched 2026-08-09) has since moved to a queuing-delay model that also coalesces floods of short tasks into one “congested moment” entry. See when an entry is reported. Do not ship production monitoring against either behavior yet.
  • Most of the explainer is not implemented in 153. The explainer also proposes a cadence property, an executionContext property (PerformanceExecutionContextInfo), a configurable durationThreshold, an OffscreenCanvas frame-based cadence in workers, and main-thread congested moments. None of these exist in the Chromium sources read (trunk or M153 branch, 2026-08-09). Only scriptCount and the dedicated-worker exposure shipped in this prototype.
  • No spec text yet. The Long Animation Frames spec still declares both interfaces [Exposed=Window]; worker exposure is tracked in the open spec issue w3c/long-animation-frames#38 (opened 2026-07-15). The ChromeStatus record lists standards maturity “Unknown status” and no spec link.
Source: M153 runtime_enabled_features.json5; M153 animation_frame_timing_monitor.cc; trunk animation_frame_timing_monitor.h; ChromeStatus API record — all fetched 2026-08-09.

reference routes

PerformanceLongAnimationFrameTiming.scriptCount

The one new attribute this feature adds: every top-level JavaScript entry point in the reporting interval, including the short ones that never appear in scripts.

syntax

Registration is the ordinary PerformanceObserver pattern, run inside the worker (there is no way to observe a worker’s entries from the window):

// worker.js — with LongAnimationFrameWorker enabled
const observer = new PerformanceObserver((list) => {
  console.log(list.getEntries());
});
observer.observe({ type: "long-animation-frame", buffered: true });

The exposure itself is expressed in Blink’s IDL extended attributes — quoted verbatim from trunk and identical on the M153 branch (fetched 2026-08-09):

// third_party/blink/renderer/core/timing/performance_long_animation_frame_timing.idl
[Exposed(Window StableBlinkFeatures, DedicatedWorker LongAnimationFrameWorker)]
interface PerformanceLongAnimationFrameTiming : PerformanceEntry {
    [RuntimeEnabled=LongAnimationFrameWorker] readonly attribute unsigned long scriptCount;
    ...
};

// third_party/blink/renderer/core/timing/performance_script_timing.idl
[Exposed(Window StableBlinkFeatures, DedicatedWorker LongAnimationFrameWorker)]
interface PerformanceScriptTiming : PerformanceEntry { ... };

Meaning: both interfaces exist in Window unconditionally (that part is stable), and in DedicatedWorker only when the LongAnimationFrameWorker feature is on. Neither is exposed in shared or service workers. PerformanceObserver.supportedEntryTypes reflects the same gate — the M153 implementation adds "long-animation-frame" for a context that IsDedicatedWorkerGlobalScope() with the feature enabled, with the in-source comment: “Dedicated workers are supported first to validate the congested-moment reporting; shared and service workers will follow.” Feature-detect inside a worker with:

const supported = PerformanceObserver.supportedEntryTypes
    .includes("long-animation-frame");

By contrast, the W3C spec’s IDL still reads [Exposed=Window] for both interfaces — the worker exposure has no normative text yet (see Specifications).

Source: performance_long_animation_frame_timing.idl; performance_script_timing.idl; performance_observer.cc (supportedEntryTypes gating); Long Animation Frames spec IDL — fetched 2026-08-09.

what a worker entry contains — attribute by attribute

A worker entry is the same PerformanceLongAnimationFrameTiming interface, but a worker has no rendering lifecycle, no DOM, and no window, so several members behave differently. The table below is derived from the M153-branch implementation: the worker path constructs the entry from a task interval only, passing no paint-timing info, and Chromium’s timestamp conversion returns 0 for timestamps that were never set (performance.cc: “Avoid exposing raw platform timestamps” — null monotonic time → 0.0).

name / entryType"long-animation-frame" — unchanged
startTimeWhen the blocking task started, relative to the worker’s time origin
durationThe blocking task’s full duration (start to end), clamped to timer resolution. Only tasks ≥ 200 ms produce entries at all
scriptCount (new)Number of top-level JS entry points in the interval, counted regardless of individual duration. Gated on LongAnimationFrameWorker, so it also appears on window entries when the flag is on. Full reference: scriptCount
renderStart0 — never set on the worker path (no rendering lifecycle)
styleAndLayoutStart0 — never set (no style/layout in a worker)
firstUIEventTimestamp0 — never set (no UI events on a worker’s loop)
blockingDurationduration − 200 ms: the M153 worker path sets total blocking duration to the task duration minus the congestion threshold
scriptsPopulated with per-script attribution, as on the main thread: only scripts whose individual duration is ≥ 5 ms (kLongScriptDuration), and only scripts whose security origin the observing worker can access
paintTime / presentationTimeAbsent — the PaintTimingMixin members are [Exposed=Window], with the in-source comment: “Scoping the members to Window keeps the properties below out of PerformanceLongAnimationFrameTiming when it is exposed to web workers”

when an entry is reported

Chrome 153 (the dev-trial build this page is filed under): the worker’s AnimationFrameTimingMonitor observes every task on the worker’s event loop. When a task completes, if it occupied the loop for at least kCongestionThreshold = 200 ms, the monitor reports it as a “congested moment” and the worker’s performance timeline queues a "long-animation-frame" entry. The in-source comment is explicit about the scope: “A worker task that occupies the event loop for at least this long is reported as a congested moment. TODO(crbug.com/534893134): Reporting a congested moment when many small tasks saturate the task queue is a future extension.” Entries are stored in a 200-entry buffer, so buffered: true observers registered after the fact still receive them. Note the threshold is 200 ms, not the 50 ms that window LoAF uses, and there is no worker equivalent of the rendering-frame trigger: a worker running a requestAnimationFrame loop over an OffscreenCanvas gets no frame-anchored entries in this prototype (that cadence is explainer-stage).

Chromium trunk has already moved on (2026-08-09): the monitor now tracks a queuing-delay model — an open “congested moment” interval during which the task queue stays saturated (a task was queued while an earlier task was still running, i.e. backlog depth ≥ 2), accumulating scriptCount and long scripts across multiple tasks and reporting one entry when the queue drains, if the run lasted at least the threshold. The upstream WPT exercises exactly this: a flood of twenty 15 ms tasks coalesces into one entry, and a steady back-to-back iteration with backlog depth 1 must not be reported. Under the M153 build, only the first (single-long-task) scenario produces entries. Treat the M153 behavior as the floor, not the contract.

Source: M153 animation_frame_timing_monitor.cc; trunk animation_frame_timing_monitor.h; worker_performance.cc; worker_global_scope.cc; performance.cc (kDefaultLongAnimationFrameBufferSize = 200) — fetched 2026-08-09.

examples

Observe long tasks from inside the worker they block. The observer lives in the worker; the main thread never sees these entries:

// worker.js — run Chrome with --enable-blink-features=LongAnimationFrameWorker
if (PerformanceObserver.supportedEntryTypes.includes("long-animation-frame")) {
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      console.log(
        `worker event loop blocked for ${entry.duration.toFixed(0)}ms ` +
        `(${entry.scriptCount} script entry points, ` +
        `blockingDuration ${entry.blockingDuration.toFixed(0)}ms)`,
      );
      // Same-origin per-script attribution, as on the main thread.
      for (const script of entry.scripts) {
        console.log(
          `  ${script.sourceFunctionName || "(anonymous)"} in ` +
          `${script.sourceURL}: ${script.duration.toFixed(0)}ms ` +
          `via ${script.invoker}`,
        );
      }
    }
  });
  observer.observe({ type: "long-animation-frame", buffered: true });
}

// A message handler that occasionally blocks the loop past 200ms
// will now be reported — with the culprit function named.
self.onmessage = (e) => {
  const start = performance.now();
  while (performance.now() - start < e.data.busyMs) { /* simulate work */ }
};

The pattern of accumulating entry.scripts across callbacks and grouping by sourceURL — as recommended for main-thread LoAF in Chrome’s LoAF guide — works identically in a worker; the entries just describe the worker’s own event loop. The explainer’s live long-task demo (verified 200, 2026-08-09) shows the manual-instrumentation problem this replaces.

security and privacy

  • Same-origin attribution only. The entry constructor filters scripts through the observing context’s security origin: a script’s timing object is only attached when the observer’s origin can access the script’s origin. This is the same rule as window LoAF, applied with the worker as the observer. The explainer commits to the same constraint: per-script details “are exposed only for scripts that are same-origin with the observing context”.
  • Scope of observation. A worker observes only its own event loop. Worker entries do not surface in the parent document’s timeline, and a document cannot use this API to time another context’s tasks.
  • Timestamp coarsening. All exposed timestamps go through Chromium’s standard clamping (ClampTimeResolution, finer resolution only when cross-origin isolated), and never-set timestamps are reported as 0 rather than leaking raw platform values.
  • New fingerprinting surface is one bit. Until the feature ships unflagged, supportedEntryTypes in a dedicated worker reveals whether the flag is on.
Source: performance_long_animation_frame_timing.cc (origin filter); explainer — Privacy and Security Considerations.
