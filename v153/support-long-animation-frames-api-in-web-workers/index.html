Support Long Animation Frames API in Web Workers

Limited availability — developer trial, behind a flag

  • Chrome · dev trial from 153 (desktop), behind --enable-blink-features=LongAnimationFrameWorker
  • Edge · no signal
  • Firefox · no signal
  • Safari · no signal

The worker extension has no Baseline entry of its own. The ChromeStatus record reuses the parent Web Feature ID long-animation-frames, whose Baseline status is “Limited” — the main-thread API, shipped in Chrome and Edge 123 (webstatus.dev API query, verified 2026-09-13). Worker support is not covered by that entry: it is a Chrome prototype with no shipping milestone.

This feature extends the Long Animation Frames API (LoAF) to dedicated Web Workers. Today LoAF reports only on the main thread and is anchored to rendering frames, so it cannot observe work that blocks a worker’s event loop. With this change, a long task that blocks a worker’s event loop is reported as a "long-animation-frame" entry, observable from inside the worker via PerformanceObserver, with the usual per-script attribution — plus a new scriptCount property that distinguishes one long task from a flood of small ones.

Developer trial — the API surface may move

This is an experimental prototype behind a flag. Do not copy code that depends on it into production.

  • How to enable. Launch Chrome 153+ with the command-line switch --enable-blink-features=LongAnimationFrameWorker. The Blink runtime flag record is { name: "LongAnimationFrameWorker", status: "test" } (runtime_enabled_features.json5, fetched 2026-09-13). Because the status is test — not experimental — the chrome://flags#enable-experimental-web-platform-features toggle does not enable it, and there is no dedicated chrome://flags entry (no LongAnimationFrameWorker reference exists in about_flags.cc, checked 2026-09-13). There is no origin trial.
  • Scope of the prototype. Dedicated workers only. Per the ChromeStatus summary, the prototype starts by “reporting a single long task that blocks the worker’s event loop”; detecting floods of many small tasks and supporting the main thread’s congested-moment cadence are “planned as follow-up work”. The current WPT suite already exercises flood coalescing in workers, so the implementation is moving fast — expect behavior to change between milestones.
  • Not yet in the prototype. The explainer additionally proposes a cadence property ("animation-frame" | "congested-moment"), an executionContext property returning PerformanceExecutionContextInfo, an OffscreenCanvas frame-based cadence in workers, and a configurable durationThreshold. None of these appear in the Chromium IDL as of 2026-09-13 (performance_long_animation_frame_timing.idl); the shipped-behind-flag surface is worker exposure plus scriptCount.
  • No spec text yet. The LoAF specification still declares both interfaces [Exposed=Window], and the Intent to Prototype lists “Specification: No information provided”.
Source: runtime_enabled_features.json5; Intent to Prototype thread; loaf-congested-moments explainer; ChromeStatus 5387465121726464.

why it exists

Web apps increasingly offload work to Web Workers, but a worker that blocks its own event loop is invisible to today’s performance APIs. Workers usually have no rendering lifecycle, so there are no animation frames for LoAF to anchor to, and the main-thread LoAF and Long Tasks APIs cannot observe work running in a worker. As a result, a long task in a worker — which delays incoming message events and any OffscreenCanvas rendering — goes unreported even though it directly degrades responsiveness.

Rather than introduce a new API, the owners extend LoAF, “because detecting a long animation frame and detecting a congested moment are fundamentally the same task: identifying bottlenecks in an event loop and attributing them to the responsible scripts”. Reusing the existing API gives developers a single, familiar mechanism for diagnosing blocking work across both documents and workers. The demand is long-standing: extending the Long Tasks API to workers was requested in Chromium issue 41399667 (filed 2018), but Long Tasks lacks script attribution — LoAF is the richer base to build on.

Source: ChromeStatus motivation; explainer — introduction and related issues; Chromium issue 41399667.

Syntax

No new interface is introduced. The current LoAF specification declares the entry interface for window contexts only (verbatim):

[Exposed=Window]
interface PerformanceLongAnimationFrameTiming : PerformanceEntry {
    /* Overloading PerformanceEntry */
    readonly attribute DOMHighResTimeStamp startTime;
    readonly attribute DOMHighResTimeStamp duration;
    readonly attribute DOMString name;
    readonly attribute DOMString entryType;

    readonly attribute DOMHighResTimeStamp renderStart;
    readonly attribute DOMHighResTimeStamp styleAndLayoutStart;
    readonly attribute DOMHighResTimeStamp blockingDuration;
    readonly attribute DOMHighResTimeStamp firstUIEventTimestamp;
    [SameObject] readonly attribute FrozenArray<PerformanceScriptTiming> scripts;
    [Default] object toJSON();
};

The Chromium prototype changes the exposure of both LoAF interfaces and adds one member (verbatim from the Blink IDL, fetched 2026-09-13; unrelated RuntimeEnabled members elided):

[Exposed(Window StableBlinkFeatures, DedicatedWorker LongAnimationFrameWorker)]
interface PerformanceLongAnimationFrameTiming : PerformanceEntry {
    [RuntimeEnabled=LongAnimationFrameWorker] readonly attribute unsigned long scriptCount;
    // ... existing members unchanged ...
};

[Exposed(Window StableBlinkFeatures, DedicatedWorker LongAnimationFrameWorker)]
interface PerformanceScriptTiming : PerformanceEntry {
    // window/windowAttribution describe same-origin windows and are only
    // meaningful in document contexts.
    [Exposed=Window] readonly attribute ScriptWindowAttribution windowAttribution;
    [Exposed=Window] readonly attribute Window? window;
    // ... existing members unchanged ...
};

That is the entire developer-facing delta: with the flag on, both interfaces exist inside dedicated workers, window/windowAttribution stay window-only, and scriptCount appears on PerformanceLongAnimationFrameTiming in both windows and workers.

Source: Long Animation Frames API specification; performance_long_animation_frame_timing.idl; performance_script_timing.idl.

what changes in workers

A worker has no rendering pipeline, so the “frame” anchor is replaced by a congested moment: an interval during which the worker’s event loop stays saturated with backlogged tasks. The exact reporting model, transcribed from the Chromium monitor implementation and its WPT suite (full detail on the worker entries reference):

TriggerQueuing delay: a task whose scheduled run time is earlier than when the previous task started running means at least two tasks were pending at once (backlog depth ≥ 2). That opens a congested moment. A steady back-to-back chain (each task posted only after the previous one finishes, backlog depth 1) is never reported, however long the total work.
ExtensionWhile the moment is open, each task that starts within 5 ms of the previous one ending (kCongestionIdleGap) extends the interval and folds in its scripts.
Close & reportA real idle gap (> 5 ms) closes the moment. It is reported as one entry only if the saturated span was at least 200 ms (kCongestionThreshold) and at least one JavaScript entry point ran in it; shorter or script-free moments are discarded.
startTime / durationstartTime is when the backlog formed (the earlier of the two colliding scheduled times); duration spans the whole congested interval — one entry can cover a long task or a coalesced flood of many small ones.
blockingDurationRedefined for worker entries as duration − 200 ms (the span past the congestion threshold) — not the main thread’s per->50 ms-task sum.
Rendering fieldsrenderStart, styleAndLayoutStart, and firstUIEventTimestamp are never set for worker moments, so they report 0; the paint-timing mixin fields stay null (the entry is created with no paint timing info).
scripts / scriptCountscripts lists only entry points that individually ran ≥ 5 ms (kLongScriptDuration), filtered to same-origin attribution; scriptCount counts every JS entry point in the interval, so it can exceed scripts.length.
Delayed timersA timer’s scheduled time is its enqueue time plus its delay, so a setTimeout waiting out its delay does not count as backlog.
Source: animation_frame_timing_monitor.cc (OnWorkerTaskCompleted, FinalizeCongestedMoment, threshold constants); worker_performance.cc; WPT loaf-congested-moment-worker.html.

PerformanceScriptTiming in workers

Script attribution entries inside worker LoAF entries keep the main-thread contract, with these worker-specific differences:

SyntaxSame interface, now reachable as entry.scripts[n] inside a dedicated worker. Exposure (verbatim): [Exposed(Window StableBlinkFeatures, DedicatedWorker LongAnimationFrameWorker)].
InputsNone — a read-only attribution record produced by the browser; scripts are attributed automatically per JS entry point (no developer instrumentation).
OutputsinvokerType, invoker (the explainer’s worker example shows "Worker.onmessage"), executionStart, sourceURL, sourceFunctionName, sourceCharPosition, pauseDuration, plus inherited startTime/duration. Not exposed in workers: window and windowAttribution — the IDL marks both [Exposed=Window], with the comment “window/windowAttribution describe same-origin windows and are only meaningful in document contexts”.
ErrorsNo exception surface. Cross-origin scripts are silently reported without identifying source fields (see security and privacy); scripts a worker observer may not access are omitted from scripts entirely.
Context & exposureDedicated workers behind LongAnimationFrameWorker; windows unconditionally (stable since Chrome 123). Feature-detect in a worker with typeof PerformanceScriptTiming !== "undefined".
LifecycleCreated when the containing worker entry is reported (at moment close); entry points are accumulated per task and folded into the open congested moment as it extends.
ExampleSee examples — the worker observer iterates entry.scripts for sourceURL/sourceFunctionName attribution.
CompatibilityWorker exposure: Chrome 153 dev trial behind the flag only (see browser compatibility).
Security & privacyforcedStyleAndLayoutDuration remains in the worker-exposed interface but the explainer annotates forced style/layout cost as “main thread only” — workers have no document to style or lay out. Source attribution stays same-origin-gated (see security and privacy).
Source: performance_script_timing.idl; explainer — congested moment entry structure; MDN PerformanceScriptTiming (main-thread contract).

Examples

Observe the worker’s own long-animation-frame entries from inside the worker (the registration is identical to the main thread — the explainer’s “how to use” pattern):

// worker.js — requires Chrome 153+ started with
// --enable-blink-features=LongAnimationFrameWorker
if (typeof PerformanceLongAnimationFrameTiming !== "undefined") {
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      console.log(
        `Worker event loop congested for ${entry.duration.toFixed(1)}ms ` +
        `(${entry.scriptCount} script entry points)`);
      for (const script of entry.scripts) {
        // Only entry points that individually ran >= 5ms are listed here.
        console.log(
          `  ${script.invoker}: ${script.sourceFunctionName || "(top level)"} ` +
          `in ${script.sourceURL} — ${script.duration.toFixed(1)}ms`);
      }
    }
  });
  observer.observe({ type: "long-animation-frame", buffered: true });
}

Produce a reportable moment: a long task with a second message already backlogged behind it. A lone long task with an empty queue is not congestion under the queuing-delay model — something must be waiting:

// worker.js — a 250ms handler while a second message waits in the queue.
let first = true;
self.onmessage = () => {
  const until = performance.now() + (first ? 250 : 15);
  first = false;
  while (performance.now() < until) { /* busy */ }
};

// main.js — post both messages back to back so the second is
// backlogged before the first starts running (backlog depth >= 2).
const worker = new Worker("worker.js");
worker.postMessage(1);
worker.postMessage(2);

Diagnose the kind of congestion with scriptCount: a low count with a long duration is one long task; a high count with a near-empty scripts array is a flood of tiny tasks — the case classic LoAF and Long Tasks cannot surface.

Source: explainer — how to use the API; WPT worker resource (long-task scenario).

web platform tests

The ChromeStatus record answers the WPT question with “true”, and two tests exist in the long-animation-frame/ directory (both require the flag; comments in each say “run with --enable-blink-features=LongAnimationFrameWorker”):

  • loaf-congested-moment-worker.html (results on wpt.fyi) — asserts, in a dedicated worker: a backlogged long task reports an entry with duration ≥ 200; a flood of twenty 15 ms tasks coalesces into one entry attributing ≥ 10 scripts; a long flood stays one entry; two floods separated by a real idle gap report two non-overlapping entries; and a steady backlog-depth-1 iteration reports nothing.
  • loaf-script-count.tentative.html — asserts scriptCount is a number, ≥ 1, never smaller than scripts.length, and exceeds it when sub-5 ms tasks coalesce into a frame (main-thread test of the same flag-gated member).

security and privacy

  • Same-origin attribution only. Per-script details (sourceURL, sourceFunctionName, sourceCharPosition) are exposed only for scripts same-origin with the observing context, consistent with existing LoAF. In the Chromium implementation the entry constructor drops scripts whose security origin the observer cannot access before they ever reach scripts.
  • No new cross-origin timing channel. The congested interval and scriptCount aggregate work on the observer’s own event loop; a worker entry only attributes scripts running in contexts the observer is entitled to see.
  • Timestamp coarsening. Timestamps go through the platform’s standard resolution clamping (cross_origin_isolated_capability-dependent, as for all high-resolution timing).
  • Review status. ChromeStatus lists both the security and privacy reviews as “Pending” (prototype stage) — constraints may tighten before any ship.
Source: explainer — privacy and security considerations; performance_long_animation_frame_timing.cc (origin filter); ChromeStatus review gates.
