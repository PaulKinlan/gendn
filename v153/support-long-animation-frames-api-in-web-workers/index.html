Support Long Animation Frames API in Web Workers

Extends the Long Animation Frames (LoAF) API to DedicatedWorkerGlobalScope so a dedicated Web Worker can observe its own event-loop congestion via PerformanceObserver (type: "long-animation-frame"), receiving PerformanceLongAnimationFrameTiming entries with per-script PerformanceScriptTiming attribution and a new scriptCount counter that distinguishes a single blocking task from a flood of small tasks.

Limited availability — Developer trial behind a Blink test flag from Chrome 153 (not yet enabled by default); Firefox and Safari do not implement main-thread or worker LoAF

  • Chrome · Developer trial behind --enable-blink-features=LongAnimationFrameWorker from 153 (not yet enabled by default)
  • Edge · Mirrors Chromium flag (Microsoft co-authored the explainer & implementation)
  • Firefox · No signal / no release
  • Safari · No signal / no release

No web-features or BCD entry exists for worker LoAF or scriptCount yet (checked 2026-11-27 against webstatus.dev and BCD api/PerformanceLongAnimationFrameTiming.json). Base main-thread long-animation-frames is Limited availability (Chrome/Edge 123). MDN’s PerformanceLongAnimationFrameTiming covers main-thread Window LoAF only and does not cover DedicatedWorker exposure or scriptCount.

Developer trial behind a Blink test flag from Chrome 153 (not yet enabled by default): Launch Chromium with --enable-blink-features=LongAnimationFrameWorker. Note that LongAnimationFrameWorker is currently declared with status: "test" (not "experimental") in runtime_enabled_features.json5, so chrome://flags/#enable-experimental-web-platform-features alone does not enable it; pass the explicit command-line flag. There is no origin trial and no stable ship milestone yet.

why it exists

Complex web apps increasingly offload state management, IndexedDB access, parsing, and OffscreenCanvas rendering into Web Workers. Previously, both Long Tasks and Long Animation Frames were exposed only on Window and anchored to main-thread rendering frames, leaving a worker whose event loop was stalled by a long synchronous task or flooded by rapid postMessage() bursts completely invisible to web performance telemetry. Extending LoAF to workers reuses PerformanceObserver and PerformanceScriptTiming so developers can attribute worker stalls with the same API used on the main thread.

Source: WICG LoAF Congested Moments explainer; ChromeStatus 5387465121726464.

Syntax

In Blink’s current developer trial (performance_long_animation_frame_timing.idl and performance_script_timing.idl), enabling LongAnimationFrameWorker extends interface exposure to DedicatedWorker, adds "long-animation-frame" to PerformanceObserver.supportedEntryTypes inside dedicated workers, and adds scriptCount to PerformanceLongAnimationFrameTiming:

[Exposed=(Window, DedicatedWorker)]
partial interface PerformanceLongAnimationFrameTiming {
  readonly attribute unsigned long scriptCount;
};

[Exposed=(Window, DedicatedWorker)]
partial interface PerformanceScriptTiming {
  // Exposes invokerType, invoker, executionStart, pauseDuration,
  // forcedStyleAndLayoutDuration, sourceURL, sourceFunctionName,
  // sourceCharPosition, and toJSON() in DedicatedWorker;
  // window and windowAttribution remain [Exposed=Window] only.
};

This reference documents all four developer-facing surfaces of the worker trial: observing "long-animation-frame" inside a dedicated worker, PerformanceLongAnimationFrameTiming.scriptCount, PerformanceScriptTiming exposure and window-only exclusions in workers, and Blink’s worker congested-moment detection algorithm (OnWorkerTaskCompleted, kCongestionThreshold = 200ms, kCongestionIdleGap = 5ms).

Source: Blink performance_long_animation_frame_timing.idl; Blink performance_script_timing.idl; Blink performance_observer.cc.

Observing "long-animation-frame" in a dedicated worker

Inputs. Inside a dedicated worker, instantiate new PerformanceObserver(callback) and call observer.observe({ type: "long-animation-frame", buffered: true }) (or entryTypes: ["long-animation-frame"]). In performance_observer.cc, Blink adds PerformanceEntry::kLongAnimationFrame to PerformanceObserver.supportedEntryTypes whenever execution_context->IsDedicatedWorkerGlobalScope() and LongAnimationFrameWorker is enabled.

Outputs. The observer callback receives PerformanceLongAnimationFrameTiming entries with entryType: "long-animation-frame", name: "long-animation-frame", startTime relative to the worker’s performance.timeOrigin, duration equal to the clamped span of the congested interval, blockingDuration equal to span - 200ms, scriptCount, and scripts containing same-origin PerformanceScriptTiming entries that exceeded the 5ms per-script threshold (kLongScriptDuration). Rendering-specific timestamps (renderStart, styleAndLayoutStart, firstUIEventTimestamp) remain 0 in workers without a main-thread rendering lifecycle, and paintTime / presentationTime are unset because WorkerPerformance::QueueLongAnimationFrameTiming() passes paint_timing_info = std::nullopt.

Source: Blink performance_observer.cc; Blink worker_performance.cc; Blink performance_long_animation_frame_timing.cc.

PerformanceLongAnimationFrameTiming.scriptCount

Inputs. Read-only unsigned long property on PerformanceLongAnimationFrameTiming (exposed on both Window and DedicatedWorker whenever LongAnimationFrameWorker is enabled, and serialized in entry.toJSON()).

Outputs. Counts every JavaScript entry point that executed during the reported interval — including short scripts below the 5ms threshold that are omitted from entry.scripts. Compare scriptCount against duration and scripts.length to classify congestion:

  • Low scriptCount + long duration + populated scripts: A single (or small number of) expensive blocking tasks occupied the worker’s event loop.
  • High scriptCount + long duration + empty or short scripts: Queue saturation caused by a high-frequency burst of small tasks (such as rapid postMessage() handlers) piling up faster than the worker can drain them.
Source: Blink performance_long_animation_frame_timing.idl; Blink performance_long_animation_frame_timing.cc; WICG explainer §The scriptCount property.

PerformanceScriptTiming in dedicated workers

Inputs & Outputs. Each element of entry.scripts is a PerformanceScriptTiming instance (entryType: "script", name: "script") reporting invokerType ("classic-script", "module-script", "event-listener", "user-callback", "resolve-promise", "reject-promise", "user-entry-point"), invoker (for example "DedicatedWorkerGlobalScope.onmessage" or timer/callback names), executionStart, duration (elapsed time through microtask checkpoint completion), pauseDuration, forcedStyleAndLayoutDuration (0 in workers), sourceURL, sourceFunctionName, and sourceCharPosition. In performance_script_timing.idl, both window and windowAttribution are explicitly annotated [Exposed=Window], so they do not exist on PerformanceScriptTiming.prototype inside a dedicated worker (they read as undefined).

Source: Blink performance_script_timing.idl; MDN PerformanceScriptTiming.

Worker congested-moment detection algorithm

Inputs. On each completed worker task, Blink’s AnimationFrameTimingMonitor::OnWorkerTaskCompleted() inspects start_time, end_time, and the scheduler’s desired_execution_time (enqueue time for immediate tasks or scheduled run time for timers), along with the task’s script_count_ and long scripts (≥5 ms).

Outputs. Blink tracks congested intervals using three exact constants in animation_frame_timing_monitor.cc:

Blink worker congested-moment state machine parameters (animation_frame_timing_monitor.cc)
Stage / ConstantBlink value & rule
Queuing-delay triggerA congested moment opens when a completed task had desired_execution_time < prev_task_start_ (backlog depth ≥ 2: at least one runnable task was already waiting while the previous task ran). Its start time is min(scheduled, prev_scheduled_start_).
kCongestionIdleGap5ms — While each subsequent task starts within 5ms of the previous task ending, the congested interval stays open and folds in the task’s scriptCount and long scripts.
kCongestionThreshold200ms — When the worker goes idle for > 5ms (or shuts down), FinalizeCongestedMoment() checks span >= 200ms AND congestion_script_count_ > 0. Qualifying intervals emit a "long-animation-frame" entry with blockingDuration = span - 200ms; shorter or scriptless intervals are discarded.
kLongScriptDuration5ms — Individual scripts running at least 5ms are included in entry.scripts; shorter scripts increment entry.scriptCount only.

Explainer proposals not yet in the Blink prototype: The WICG explainer also proposes cadence ("animation-frame" vs "congested-moment"), configurable durationThreshold on PerformanceObserverInit, OffscreenCanvas rAF-cadence reporting in workers, and script.executionContext (PerformanceExecutionContextInfo). None of those fields are present in Blink’s current performance_long_animation_frame_timing.idl / performance_script_timing.idl yet.

Source: Blink animation_frame_timing_monitor.cc; WICG LoAF Congested Moments explainer.

Errors, unsupported contexts, and prototype caveats

  • Flag disabled or unsupported worker type: In Shared Workers, Service Workers, or when LongAnimationFrameWorker is disabled, PerformanceObserver.supportedEntryTypes does not include "long-animation-frame"; calling observer.observe({ type: "long-animation-frame" }) logs a console warning and delivers no entries (and throws a TypeError if neither type nor entryTypes is provided).
  • Isolated single long task with no queued second task: Because Blink’s current OnWorkerTaskCompleted() opens a congested moment on queuing delay (scheduled < prev_task_start_), a single isolated long task with zero other tasks arriving during it may not open a congested moment unless another task (such as a timer or incoming postMessage) is queued behind it, and a completed moment is finalized only once the idle gap exceeds 5ms or the worker closes.
  • Native-only backlog (scriptCount === 0): Blink currently drops congested intervals with congestion_script_count_ === 0 (such as pure GC/IPC stalls with no JS entry points), tracked as a TODO on crbug/534893134. In addition, accessing window or windowAttribution on a worker PerformanceScriptTiming object yields undefined because those getters are [Exposed=Window] only.
  • Buffer cap: WorkerPerformance::QueueLongAnimationFrameTiming() respects the Performance Timeline LoAF buffer limit (IsLongAnimationFrameBufferFull()); entries arriving after the buffer fills still notify live observers, but are not retained for later buffered: true observers.
Source: Blink animation_frame_timing_monitor.cc; Blink worker_performance.cc; Blink worker_global_scope.cc.

Context, exposure, and feature detection

Exposed in Window (shipped since Chrome 123; scriptCount added behind LongAnimationFrameWorker) and DedicatedWorker (behind --enable-blink-features=LongAnimationFrameWorker). Shared Workers and Service Workers are explicitly deferred (worker_global_scope.cc). Inside a dedicated worker, feature-detect reliably via PerformanceObserver.supportedEntryTypes.includes("long-animation-frame") (and check typeof PerformanceLongAnimationFrameTiming === "function").

Source: Blink performance_observer.cc; Blink worker_global_scope.cc.

Lifecycle inside a dedicated worker

  1. Worker startup: WorkerGlobalScope::CreateAnimationFrameTimingMonitor() attaches an AnimationFrameTimingMonitor to the dedicated worker’s CoreProbeSink and Thread task-time observer when LongAnimationFrameWorker is active.
  2. Task & script monitoring: As tasks execute on the worker thread, the monitor counts JS entry points (scriptCount) and records scripts ≥5 ms.
  3. Congestion close & dispatch: When the worker goes idle for >5 ms (or on WorkerGlobalScope::Dispose()), any open interval with span >= 200ms and scriptCount > 0 is queued via WorkerPerformance::QueueLongAnimationFrameTiming() into the worker’s long-animation-frame buffer and delivered to active PerformanceObserver callbacks.
  4. Reporting back to main thread: Because a main-thread observer cannot directly observe a worker’s entries, the worker serializes interesting entries (via entry.toJSON()) and forwards them over self.postMessage() or beacons them directly.
Source: Blink worker_global_scope.cc; Blink worker_performance.cc; Blink animation_frame_timing_monitor.cc.

Examples

Live showcase demo & observing worker LoAF entries

// Inside a dedicated worker (worker.js)
// Receives congested-moment entries from OnWorkerTaskCompleted (>= 200ms span, > 5ms idle gap).
function installWorkerLoafObserver(onReport) {
  const supported =
    typeof PerformanceObserver === "function" &&
    Array.isArray(PerformanceObserver.supportedEntryTypes) &&
    PerformanceObserver.supportedEntryTypes.includes("long-animation-frame");

  if (!supported) {
    return { supported: false, disconnect() {} };
  }

  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      const scriptCount = "scriptCount" in entry ? entry.scriptCount : null;
      const classification =
        scriptCount !== null && scriptCount > 10 && entry.scripts.length <= 2
          ? "tiny-task-flood"
          : "long-task-stall";

      // Each item in entry.scripts is a PerformanceScriptTiming (window / windowAttribution omitted in workers).
      onReport({
        entryType: entry.entryType,
        startTime: entry.startTime,
        duration: entry.duration,
        blockingDuration: entry.blockingDuration,
        scriptCount,
        classification,
        scripts: entry.scripts.map((s) => ({
          invokerType: s.invokerType,
          invoker: s.invoker,
          duration: s.duration,
          sourceURL: s.sourceURL,
          sourceFunctionName: s.sourceFunctionName,
          sourceCharPosition: s.sourceCharPosition,
        })),
      });
    }
  });

  observer.observe({ type: "long-animation-frame", buffered: true });
  return {
    supported: true,
    disconnect: () => observer.disconnect(),
  };
}
Source: WICG LoAF Congested Moments explainer; Blink performance_long_animation_frame_timing.idl.

Security and privacy

  • Same-origin script attribution only: In performance_long_animation_frame_timing.cc, Blink checks observer_security_origin->CanAccess(script->GetSecurityOrigin()) before pushing a PerformanceScriptTiming entry into scripts, ensuring cross-origin scripts (e.g., non-CORS scripts loaded via importScripts()) never leak sourceURL, sourceFunctionName, or sourceCharPosition.
  • Own event loop only: A dedicated worker observes only congestion on its own thread’s event loop and cannot observe main-thread windows or cross-origin workers (window and windowAttribution are not exposed in workers).
  • Timestamp coarsening: All timestamps (startTime, duration, blockingDuration, and per-script durations) pass through Performance::MonotonicTimeToDOMHighResTimeStamp() and Performance::ClampTimeResolution() respecting the worker’s crossOriginIsolated capability.
Source: WICG explainer (Privacy and Security); Blink performance_long_animation_frame_timing.cc.
