PerformanceLongAnimationFrameTiming.scriptCount

The scriptCount read-only attribute reports how many top-level JavaScript entry points ran during the entry’s reporting interval — every one of them, including scripts far too short to appear in the scripts array. It is the signal that distinguishes one long task (low count, long duration) from a queue congested by many small tasks (high count). It ships with, and is gated by, the same LongAnimationFrameWorker feature that exposes LoAF to dedicated workers.

Developer trial — behind a flag, no spec text

Available only with --enable-blink-features=LongAnimationFrameWorker (Blink feature status "test" at trunk and on the M153 branch, fetched 2026-08-09 — no chrome://flags entry, and the “Experimental Web Platform features” toggle does not enable it). The attribute appears in neither the LoAF specification nor BCD; its shape may change before shipping. See the parent page’s caveats.

syntax / value

IDL, verbatim from Chromium trunk (identical on the M153 branch, fetched 2026-08-09):

[RuntimeEnabled=LongAnimationFrameWorker] readonly attribute unsigned long scriptCount;

A read-only unsigned long. There are no parameters and no setter; reading it never throws. It is included in the entry’s toJSON() output when the feature is enabled.

Source: performance_long_animation_frame_timing.idl; performance_long_animation_frame_timing.cc (BuildJSONValue).

what is counted

The monitor increments the count once per top-level script entry point in the current reporting interval — the in-source comment reads: “A top-level script entry point of the current reporting interval (a window LoAF or a congested moment). Count it for scriptCount regardless of its duration.” Nested script invocations inside an already-running entry point are not counted separately.

Contrast with the scripts array, which lists only scripts whose individual duration is at least 5 ms (kLongScriptDuration) and which pass the same-origin filter. The two together give the diagnostic shape the explainer describes:

ShapeReading
Low scriptCount, long duration, populated scriptsA single long task blocked the event loop; scripts names the culprit
High scriptCount, scripts sparse or emptyThe loop was saturated by many short tasks, none individually long — the case classic LoAF and Long Tasks cannot surface (fully realized in the trunk coalescing model; in the M153 single-task model this shape only occurs within one long task that ran many entry points)

Context of the value: in a dedicated worker (M153), the interval is a single blocking task ≥ 200 ms. In a window, the interval is the long animation frame; window entries also expose scriptCount whenever the flag is on, since RuntimeEnabled gates the attribute, not the context.

Source: M153 animation_frame_timing_monitor.cc (PopScriptEntryPointInternal, OnWorkerTaskCompleted, OnMainThreadTaskCompleted); explainer — “The scriptCount property”.

context and exposure

  • Lives on PerformanceLongAnimationFrameTiming, which is exposed to Window (stable) and, behind LongAnimationFrameWorker, to DedicatedWorker. Not exposed in shared or service workers.
  • The attribute itself is [RuntimeEnabled=LongAnimationFrameWorker]: with the flag off, window entries have no scriptCount property at all (reading it gives undefined), and worker contexts have no LoAF entries whatsoever.
  • No permission, secure-context, or cross-origin-isolation requirement beyond what the Performance timeline already imposes.
Source: IDL exposure annotations, fetched 2026-08-09.

lifecycle

The counter accumulates while the reporting interval is open (a window long animation frame, or a worker blocking task in M153) and is snapshotted into the entry when the interval is reported; the monitor then resets it to zero for the next interval. Entries — and therefore their scriptCount — are immutable once queued on the timeline. WPT asserts the worker contract: the entry from a single backlogged long task reports scriptCount ≥ 1, and (in the upstream coalescing version) scriptCount is at least the number of attributed scripts.

Source: M153 animation_frame_timing_monitor.cc; upstream WPT loaf-congested-moment-worker.html; loaf-script-count.tentative.html.

examples

// worker.js — classify what kind of congestion an entry represents
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.scriptCount === undefined) {
      // Flag off / older Chrome: scriptCount not exposed.
      continue;
    }
    const attributed = entry.scripts.length;
    if (entry.scriptCount > attributed * 3 && entry.scriptCount > 20) {
      console.warn(
        `queue flooded: ${entry.scriptCount} entry points in ` +
        `${entry.duration.toFixed(0)}ms, only ${attributed} long enough to attribute`,
      );
    } else {
      console.warn(
        `long task(s): ${attributed} attributed scripts over ` +
        `${entry.duration.toFixed(0)}ms`,
      );
    }
  }
});
observer.observe({ type: "long-animation-frame", buffered: true });
Source: thresholds in this classification are illustrative; the count/attribution semantics follow the explainer and the Chromium sources cited above.

security and privacy

scriptCount is an aggregate over the observer’s own event loop: it counts entry points without identifying them, and the identifying detail (sourceURL etc.) remains behind the existing same-origin filter on the scripts array. The explainer states the constraint directly: “The congested-moment interval and scriptCount aggregate work on the observer’s own event loop; they do not expose the internal timing of cross-origin frames or workers beyond what LoAF already permits.” While the feature is flag-gated, the attribute’s presence adds one fingerprinting bit (flag on/off).

Source: explainer — Privacy and Security Considerations; performance_long_animation_frame_timing.cc.
