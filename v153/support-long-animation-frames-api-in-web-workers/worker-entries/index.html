Chrome prototype; no Baseline/web-features entry of its own (the ChromeStatus record maps to the parent long-animation-frames feature, verified 2026-09-13).

Inside a dedicated worker, a "long-animation-frame" entry does not describe a rendering frame — workers have none. It reports a congested moment: an interval during which the worker’s event loop stayed saturated with backlogged tasks for at least 200 ms, with per-script attribution for the work responsible.

Developer trial — behavior transcribed from the prototype

Everything on this page describes the Chromium prototype behind --enable-blink-features=LongAnimationFrameWorker as of 2026-09-13, transcribed from the Blink implementation and its WPT suite. There is no spec text for worker entries yet (the LoAF spec is still [Exposed=Window]), so thresholds, trigger conditions, and field semantics may all change. The explainer’s proposed cadence and executionContext properties are not implemented.

Source: runtime_enabled_features.json5; Intent to Prototype.

Syntax and requirements

Registration is identical to the main thread, from inside the worker:

// In DedicatedWorkerGlobalScope:
const observer = new PerformanceObserver(callback);
observer.observe({ type: "long-animation-frame", buffered: true });

// Buffered entries are also available synchronously:
performance.getEntriesByType("long-animation-frame");

The exposure making this possible (verbatim from the Blink IDL): [Exposed(Window StableBlinkFeatures, DedicatedWorker LongAnimationFrameWorker)] on both PerformanceLongAnimationFrameTiming and PerformanceScriptTiming. Requirements: a dedicated worker (shared and service workers are not in the exposure list) in Chrome 153+ launched with --enable-blink-features=LongAnimationFrameWorker.

Source: performance_long_animation_frame_timing.idl; explainer — how to use the API.

Parameters (observer options)

type"long-animation-frame" — the same entry type string as on the main thread; the worker extension deliberately reuses it rather than minting a new type.
bufferedtrue replays entries recorded before the observer was registered, up to the entry-type buffer limit (the prototype stops buffering when the long-animation-frame buffer is full but still delivers new entries to live observers).
durationThresholdNot configurable in the prototype. The 200 ms congestion threshold is the compile-time constant kCongestionThreshold; a per-observer durationThreshold is one of the explainer’s goals but is not implemented as of 2026-09-13.
Source: animation_frame_timing_monitor.cc (constants); worker_performance.cc (buffer handling); explainer — goals.

Entry fields in a worker

The entry is a normal PerformanceLongAnimationFrameTiming; what changes off the main thread is what each field means:

name / entryTypeBoth "long-animation-frame", unchanged.
startTimeWhen the backlog formed: the earlier of the two colliding scheduled times that opened the congested moment (min(scheduled, prev_scheduled_start) in the monitor).
durationThe whole congested span, from startTime to the end of the last task folded in. Always ≥ 200 ms — shorter moments are discarded. One entry can cover a single long task or a coalesced flood spanning many tasks.
blockingDurationduration − 200 ms — the span past the congestion threshold (SetTotalBlockingDuration(span - kCongestionThreshold)). This differs from the main-thread definition (sum of per-task time past 50 ms).
renderStart, styleAndLayoutStart, firstUIEventTimestamp0 — the worker moment’s timing info only ever sets the interval start/end, scripts, script count, and blocking duration; the rendering timestamps stay unset, and null timestamps convert to 0 in the entry.
Paint-timing fieldsStay null: the worker entry is created with paint_timing_info = nullopt.
scriptsEntry points that individually ran ≥ 5 ms (kLongScriptDuration), same-origin-filtered, accumulated across the whole moment. In workers each PerformanceScriptTiming omits window/windowAttribution (window-only attributes).
scriptCountEvery JS entry point in the moment, regardless of duration — see the scriptCount reference.
toJSON()Serializes the above; scriptCount is included only while the flag is enabled.
Source: animation_frame_timing_monitor.cc (FinalizeCongestedMoment); performance_long_animation_frame_timing.cc; performance_script_timing.idl.

Lifecycle: how a congested moment opens, extends, and closes

  1. Open on queuing delay. After each worker task, the monitor compares the task’s scheduled run time (enqueue time for immediate tasks; enqueue + delay for timers, so a timer waiting out its delay is not backlog) with when the previous task started running. Scheduled-before-previous-started means two tasks were pending at once (backlog depth ≥ 2) — a moment opens, backdated to when the backlog formed.
  2. Extend while busy. Each subsequent task starting within 5 ms (kCongestionIdleGap) of the previous one ending extends the moment and folds in that task’s script entry points.
  3. Close on idle. A gap > 5 ms means the worker actually went idle; the moment ends at the previous task’s end. It is reported only if the span reached 200 ms (kCongestionThreshold) and at least one JS entry point ran in it — a moment with scriptCount == 0 is backlog from worker-internal/native tasks with no JS attribution and is not reported.
  4. Deliver. The entry is queued on the worker’s own performance timeline (buffered if the buffer has room) and delivered to observers in that worker. Reporting happens at close, so an entry always arrives after the congestion has drained — this is a post-hoc diagnostic, not a live back-pressure signal.

Consequences locked in by the WPT suite: two floods separated by a real idle gap report two distinct, non-overlapping entries; a steady async iteration (each task posted only after the previous finishes, backlog depth 1) reports nothing regardless of total work.

Source: animation_frame_timing_monitor.cc (OnWorkerTaskCompleted); WPT loaf-congested-moment-worker.html; explainer — non-goals (post-hoc observation).

Errors and silent non-reporting

There is no exception surface: nothing here throws. The failure modes are silences, which matter when debugging why no entry arrives:

  • Flag off / other browsers: the interfaces are absent from worker scope, and observe({ type }) with an unsupported type is ignored per the Performance Timeline processing model rather than throwing.
  • Span under 200 ms, backlog depth never exceeded 1, or no JS entry point in the moment: the moment is discarded (see lifecycle above).
  • Cross-origin scripts: filtered out of scripts for observers that cannot access their origin — the entry may arrive with fewer attributed scripts than ran.
Source: Performance Timeline specification; animation_frame_timing_monitor.cc; performance_long_animation_frame_timing.cc (origin filter).

Examples

A worker that reports its own congestion and posts a summary to the page:

// worker.js — Chrome 153+, --enable-blink-features=LongAnimationFrameWorker
if (typeof PerformanceLongAnimationFrameTiming !== "undefined") {
  new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      self.postMessage({
        kind: "worker-congestion",
        startTime: entry.startTime,
        duration: entry.duration,          // whole congested span, >= 200ms
        blockingDuration: entry.blockingDuration, // span - 200ms
        scriptCount: entry.scriptCount,    // every JS entry point
        topScripts: entry.scripts.map((s) => ({
          invoker: s.invoker,
          source: `${s.sourceFunctionName || "(top level)"} @ ${s.sourceURL}`,
          duration: s.duration,
        })),
      });
    }
  }).observe({ type: "long-animation-frame", buffered: true });
}

Reading the shape of an entry: scriptCount low + duration long = one long task blocked the loop; scriptCount high + scripts short or empty = a flood of sub-5 ms tasks saturated it (each too small to be listed, all counted).

Security and privacy

  • Script attribution (sourceURL, sourceFunctionName, sourceCharPosition) is same-origin-gated, consistent with main-thread LoAF; the Chromium entry constructor drops scripts the observer’s origin cannot access.
  • The interval and scriptCount aggregate only the observer’s own event loop — no cross-origin or cross-thread timing is exposed beyond what LoAF already permits.
  • Timestamps are clamped to the platform’s standard timer resolution for the context’s isolation level.
