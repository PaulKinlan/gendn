Web Install API

Limited availability

  • Chrome · 153 (desktop, per milestone listing — see availability caveats)
  • Edge · co-developed; ran the same origin trial; no separate ship record
  • Firefox · no position yet
  • Safari · opposed

Not Baseline: webstatus.dev tracks this as navigator-install with status “limited” and no browser support dates recorded, and BCD has no Navigator.install entry (both verified 2026-08-09).

The Web Install API lets a website install a web app: navigator.install() installs the currently loaded page as an app (a current-document install), and navigator.install({ manifest, manifestId }) installs a different app identified by its manifest URL (a background-document install) — including apps from other origins, gated behind a user permission. Every call requires transient user activation and user consent through browser UI; the promise resolves on completed installation and rejects with a small, deliberate error taxonomy otherwise.

Read before relying on this — availability caveats
  • Listing vs. source state. The milestone=153 listing files this feature under “Enabled by default”, and the ChromeStatus API record carries a ship stage with desktop milestone 153 — but the same record's browser status still reads “In development”, and the Blink runtime feature WebAppInstallation is status: "test" (not stable-enabled) in runtime_enabled_features.json5 at trunk and on the M153 branch (7978), with no fieldtrial_testing_config entry (all verified 2026-08-09). The base feature is base_feature_status: "enabled" and copied to the web-exposed flag if: "overridden" — consistent with a server-side (Finch) rollout rather than a branch-visible flag flip. Feature-detect ('install' in navigator) before use.
  • Exact enable steps. Desktop Chrome/Edge: chrome://flags/#web-app-installation-api (the entry toggles blink::features::kWebAppInstallation, desktop only, per about_flags.cc), or launch with --enable-features=WebAppInstallation.
  • Origin-trial history and API shape churn. An origin trial (WebAppInstallation) ran in Chrome and Edge 143–150 (initially 143–148, extended to 150). The OT exposed the earlier install(install_url) / install(install_url, manifest_id) shape, which the explainer says is being replaced by the manifest-based dictionary shape. Trunk still ships all overloads, with the install_url ones marked for removal (crbug.com/520025525).
  • Desktop first. The runtime feature enables no Android status (status: {"Android": "", "default": "test"}), the OT was Windows/macOS/Linux/ChromeOS only (origin_trial_os), and the flags entry is kOsDesktop. Do not expect this API on Android or WebView yet.
  • Standards maturity. The spec is an open pull request against the W3C Manifest spec (w3c/manifest#1175, “Incubation” per ChromeStatus) covering only the zero-argument signature so far; WebKit's position is oppose. The surface may still move.
Source: ChromeStatus API record; runtime_enabled_features.json5 (trunk); M153 branch copy; about_flags.cc; origin-trial README — all fetched 2026-08-09.

reference routes

navigator.install()

Full member reference: all four overloads, InstallParams and WebInstallResult dictionaries, the complete error taxonomy with thrown-vs-rejected behavior, preconditions, and the install algorithms.

why it exists

Per the ChromeStatus record's motivation, the web has no way for a site to install a web app — the capability “must be baked into the platform to allow for websites to distribute content without relying on proprietary protocols or invoking platform specific stores”. The explainer frames the problems this solves:

  • Hidden, inconsistent install entry points. Each browser buries installation behind different address-bar icons, menus, or prompts that users may never discover.
  • No standard install UI a developer can offer. beforeinstallprompt exists only in Chromium browsers and can only install the currently loaded app.
  • No web-platform support for app catalogs. Cross-origin installation — a store-like site installing apps from other origins — previously had no built-in path at all.

Explicit non-goals: defining what “installation” means per platform, silent installs (consent is always required), installing non-app content without a manifest, installing native apps or extensions, and reporting arbitrary apps' install state back to callers.

Source: explainer — User-Facing Problem, Goals, Non-goals.

how it works: current-document vs. background-document installs

The explainer defines two install types with different trust requirements:

  1. Current-document install — navigator.install(). Installs the currently loaded page. The document must link to a manifest whose JSON declares an id; the browser shows its normal install confirmation UI. No extra permission is involved.
  2. Background-document install — navigator.install({ manifest, manifestId }). Installs the app described by the manifest at the given URL without loading its page. The browser fetches the manifest with credentials mode "omit" (no cookies). If the manifest URL is cross-origin to the calling document, the user must first grant the calling origin the “web-app-installation” permission; the install confirmation UI then names both the requesting site and the app being installed.

The app identity rule is central: a web app's identity is its manifest id (computed from start_url when absent). The caller may omit manifestId only when the fetched manifest declares an id; if the caller supplies one, it must match the browser-computed id or the promise rejects with DataError. Open design decisions recorded in the explainer: the manifest URL must currently be same-origin with the app's start_url; relative URLs inside the manifest resolve against the manifest URL; service-worker registration at install time is deferred (browsers can launch the app after install instead).

An earlier trialed design took an install_url (a document URL loaded in the background) instead of a manifest URL; it was dropped for privacy (cross-origin fetches disclosed credential state), performance, and URL-brittleness reasons, but its overloads are still present on trunk — see the member page.

Source: explainer — Proposed Approach, A note on manifest id, Alternatives considered, Open Questions.

syntax

Web IDL as shipped in Chromium (trunk, verbatim from navigator_web_install.idl, install_params.idl, and web_install_result.idl, attributes trimmed to the web-visible surface; fetched 2026-08-09):

[RuntimeEnabled=WebAppInstallation]
partial interface Navigator {
  Promise<WebInstallResult> install();
  // Deprecated OT-era shape, marked for removal (crbug.com/520025525):
  Promise<WebInstallResult> install(USVString install_url);
  Promise<WebInstallResult> install(USVString install_url, USVString manifest_id);
  Promise<WebInstallResult> install(InstallParams params);
};

dictionary InstallParams {
  required USVString manifest;
  // If present, must be a valid absolute URL. Pass undefined, null, or omit
  // completely if the JSON at `manifest` contains an `id` field.
  USVString? manifestId;
};

dictionary WebInstallResult {
  USVString manifestId;
};

The in-progress specification (w3c/manifest#1175) so far defines only the zero-argument form, as [SecureContext, NewObject] Promise<undefined> install(); with an internal [[installPromise]] slot that makes concurrent calls reject with InvalidStateError. Chromium's shipped IDL returns Promise<WebInstallResult> rather than Promise<undefined>. Full per-overload semantics: navigator.install().

Source: Chromium IDL files linked above; w3c/manifest#1175 diff.

the web-app-installation permission

Background-document installs are gated behind a new Permissions API powerful feature named "web-app-installation", registered in Chromium's permission_descriptor.idl. The permission attaches to the requesting origin: once granted, that origin can request installs of other apps without re-prompting (each install still shows its own confirmation UI). Current-document installs never prompt for this permission. If the user denies it, subsequent navigator.install() calls from that origin abort.

const { state } = await navigator.permissions.query({
  name: "web-app-installation",
});
switch (state) {
  case "granted":
  case "prompt":
    // Offer the install button.
    break;
  case "denied":
    // navigator.install() will abort; hide the install UI
    // or link to the app's own page instead.
    break;
}

Caveat from permission_utils.cc: when the WebAppInstallation runtime feature is disabled, permissions.query({ name: "web-app-installation" }) itself rejects with a TypeError (“The Web App Install API is not enabled.”) — so wrap the query in a try/catch when feature-detecting.

Source: explainer — New “installation” permission for origins (snippet adapted from its example); permission_utils.cc; permission_descriptor.idl.

permissions policy

The API is additionally controlled by a web-app-installation permissions-policy directive, registered in permissions_policy_features.json5 with the default allowlist self (the file's feature_default default, EnableForSelf). Where policy disallows the feature, every overload throws a SecurityError (“Access to the feature "web-app-installation" is disallowed by Permissions Policy.” — navigator_web_install.cc). A site can disable the API for itself entirely with:

Permissions-Policy: web-app-installation=()

Note the API is also hard-blocked in contexts the policy header cannot re-enable: sandboxed documents, subframes (main frame only), prerendering documents, and fenced frames — see context and exposure on the member page.

Source: permissions_policy_features.json5; navigator_web_install.cc — fetched 2026-08-09.

examples

Install the current site (requires the manifest to declare an id):

const button = document.querySelector('#install');
button.hidden = !('install' in navigator);

button.addEventListener('click', async () => {
  try {
    await navigator.install();
    // Installed (or the user accepted a launch of the already-installed app).
  } catch (err) {
    if (err.name === 'AbortError') {
      // User dismissed the install prompt — no action needed.
    } else if (err.name === 'DataError') {
      // No manifest link, or the manifest has no `id`.
    }
  }
});

Install another app from its manifest URL (app-catalog case; may prompt for the web-app-installation permission when cross-origin):

async function installFromCatalog() {
  try {
    const result = await navigator.install({
      // If relative, URLs resolve against the currently loaded document.
      manifest: 'https://music.example.com/manifest.webmanifest',
      // Omit manifestId only if that manifest declares an `id`.
      manifestId: 'https://music.example.com/?source=pwa',
    });
    console.log('installed', result.manifestId ?? '(id not disclosed)');
  } catch (err) {
    switch (err.name) {
      case 'TypeError':   /* invalid manifest / manifestId URL */ break;
      case 'DataError':   /* fetch failed, malformed manifest, or id mismatch */ break;
      case 'AbortError':  /* user declined permission or install */ break;
      case 'NotAllowedError': /* called without transient user activation */ break;
    }
  }
}

security and privacy

  • Prompt-spam defenses. Transient user activation is required and consumed per call; the API is blocked in sandboxed contexts and cross-origin subframes; cross-origin installs sit behind the user-facing web-app-installation permission (denying it blocks the origin). Browsers may further restrict use to installed apps or throttle repeated requests.
  • Minimal cross-origin disclosure. The promise deliberately exposes little: success, DataError for data/manifest problems, AbortError for user cancellation. Manifest fetches for background installs use credentials mode "omit" so no cookies or identifying state reach the target server. For background (manifest-based) installs, Chromium currently strips even the manifest id from the success result while the disclosure question is evaluated (crbug.com/520052963). The explainer notes residual side channels (focus/blur revealing whether a dialog appeared) that bound how much withholding results can help.
  • No permission inheritance. An installed app's permissions are bound to its own origin; installing does not copy or grant anything from the installing origin — the same-origin security model is unchanged.
  • Private browsing. The feature is unavailable in private/off-the-record profiles (apps aren't installable there), and the explainer directs UAs to avoid failure timing that would create a reliable private-mode detection channel.
Source: explainer — Accessibility, Privacy, and Security Considerations; navigator_web_install.cc.
