ProfilerMarker

The ProfilerMarker enumeration is the vocabulary of browser activities a JS Self-Profiling sample can be annotated with: "script", "gc", "style", "layout", "paint", and "other". Which values a page can actually observe depends on its security context — only style and layout are exposed without cross-origin isolation.

Origin trial — Chrome 153–161

Available behind the “JS Self-Profiling Markers” origin trial or the --enable-blink-features=ExperimentalJSProfilerMarkers flag. The defining spec change (PR #89) is unmerged, and the Intent to Experiment warns the marker vocabulary “could change during standardization”. Registration steps: feature overview.

Syntax

Verbatim from the spec PR:

enum ProfilerMarker { "script", "gc", "style", "layout", "paint", "other" };

An earlier revision of the explainer gated the whole marker member with a WebIDL [CrossOriginIsolated] extended attribute; the current design removed it in favor of the per-value runtime filter described under availability by context, so the enum itself carries no extended attributes.

Source: spec PR #89 (IDL fetched from the PR branch 2026-09-13; the same PR removes the [CrossOriginIsolated] attribute from markers.md).

values

The spec PR makes the mapping from engine activity to marker value intentionally implementation-defined (“as engine architectures differ”) and gives the following as non-normative guidance:

ValueThe user agent is expected to report it…
"script"While executing author script — activity per the HTML script processing model
"gc"During garbage collection. GC interrupts stack execution without unwinding it, so a gc-marked sample can still carry a stackId; the explainer stresses the ≈10 ms sampled, after-the-fact resolution means this “should not be considered a weak reference to a GC event”
"style"While recalculating computed style
"layout"While computing box geometry (reflow)
"paint"While rasterizing or compositing document content
"other"For user-agent work that fits none of the above. When no category applies (idle), no marker is set at all — absence is the seventh, implicit state

The style/layout/paint trio corresponds to the rendering stages sketched in the HTML event loop’s update-the-rendering steps (the explainer also cites the resize-observer event-loop description).

Source: spec PR #89 — non-normative marker guidance; markers explainer — format proposal.

availability by context

Which enum values can reach a page is decided per sample by the “filter a marker” algorithm, after same-origin attribution has already discarded markers for cross-origin documents’ work:

ContextObservable values
Cross-origin isolated (Cross-Origin-Opener-Policy: same-origin + Cross-Origin-Embedder-Policy: require-corp)All six: script, gc, style, layout, paint, other
Regular (non-isolated) contextstyle and layout only
Non-isolated with a user-agent opt-in (the PR names “an origin-trial token or a document policy” as examples)May be widened by the user agent, but never across origins

The ChromeStatus record states the restricted set is not a temporary trial limitation: script, gc, and paint “remain permanently gated behind cross-origin isolation; only style and layout are exposed in non-isolated documents.”

Source: spec PR #89 — filter a marker; Conditional Markers Exposure explainer; ChromeStatus record (ongoing constraints).

suppression, not errors

The enum has no failure mode a program can observe as an exception. A value outside the context’s allowed set is not rejected, coerced, or reported — the “filter a marker” algorithm returns null and the sample’s marker member is left absent, indistinguishable from an idle sample by design. Consumers therefore cannot tell “the engine was idle” apart from “a sensitive marker was suppressed” in a non-isolated context; code that needs the full vocabulary must deploy cross-origin isolation rather than attempting detection. Nothing here changes the base API’s error behavior (constructor-time NotAllowedError/RangeError per the published specification).

Source: spec PR #89 — filter a marker (steps 1–3); JS Self-Profiling specification.

context and exposure

The enum is a trace-vocabulary type, not a runtime global you can feature-detect: it appears only as string values on ProfilerSample.marker in traces returned by Profiler.stop() (the Profiler interface is [Exposed=(Window, Worker)]; Chrome samples the main thread). Prerequisites are the base API’s js-profiling Document Policy plus, in Chrome 153–161, the origin-trial token or the ExperimentalJSProfilerMarkers Blink flag. To detect the feature, run a short profile and check whether any sample carries a marker member — there is no static signal.

Source: JS Self-Profiling specification; runtime_enabled_features.json5; markers explainer (questionnaire §18).

lifecycle and stability

Treat the vocabulary as versioned by the standardization process, not frozen. The Intent to Experiment commits Chrome to keeping the implementation “aligned with the spec PR” and warns that if review “requires narrowing the exposed markers, participants may see the marker set change” during the trial (Chrome 153–161); the graceful-degradation design means withdrawn values simply stop appearing while traces stay structurally valid. Within a single trace, each sample’s value is fixed at capture time by the “take a sample” algorithm and never rewritten. Robust consumers should switch on the six known strings and route anything unrecognized with absent markers, so a future vocabulary addition cannot break analysis.

Source: Intent to Experiment (risks); ChromeStatus record (experiment risks); spec PR #89.

Examples

Bucket every sample by marker value, tolerating unknown future values:

const KNOWN = new Set(["script", "gc", "style", "layout", "paint", "other"]);

function bucket(trace) {
  const counts = { script: 0, gc: 0, style: 0, layout: 0, paint: 0, other: 0, none: 0, unknown: 0 };
  for (const { marker } of trace.samples) {
    if (marker === undefined) counts.none++;
    else if (KNOWN.has(marker)) counts[marker]++;
    else counts.unknown++; // future vocabulary — do not throw
  }
  return counts;
}

Check whether the full (isolation-gated) vocabulary can appear in this context before relying on gc/paint analysis:

if (!crossOriginIsolated) {
  console.warn(
    "Not cross-origin isolated: only style/layout markers can appear " +
    "(script/gc/paint/other are filtered). Serve COOP+COEP to widen.",
  );
}
Source: patterns derived from the markers explainer scenarios and the spec PR #89 filtering rules; not runtime-verified in this build environment (no Chrome 153 with the trial token — see critique).

security and privacy

The enum’s values are partitioned by disclosure risk. gc, paint, script, and other can reflect engine work shared across contexts — engine-wide garbage collection can correlate activity between origins, and painting may composite other frames’ content — so they are confined to cross-origin-isolated environments, where the process boundary removes the cross-origin victim. style and layout reveal only timing the document could already measure by forcing its own synchronous flushes, which is the argument for exposing them without isolation; that argument is the part of the design the Intent to Experiment says is “still under review”, tracing back to the 2021 security review in WICG/js-self-profiling#61. Feature-level analysis: overview — security and privacy.

Source: spec PR #89 — Conditional marker exposure; Intent to Experiment (risks); markers explainer — privacy and security.
