ProfilerSample.marker

The optional marker member of a ProfilerSample names the browser activity the user agent was performing when that sample was captured — a ProfilerMarker value such as "script", "gc", or "layout". When the member is absent, the engine was idle, the work belonged to a cross-origin document, or the value was filtered out of a non-isolated context.

Origin trial — Chrome 153–161

Available behind the “JS Self-Profiling Markers” origin trial or the --enable-blink-features=ExperimentalJSProfilerMarkers flag; the defining spec change (PR #89) is unmerged and the field’s exposure rules may still change. Registration steps: feature overview.

Syntax

Verbatim from the spec PR (the whole amended dictionary, for context):

dictionary ProfilerSample {
  required DOMHighResTimeStamp timestamp;
  unsigned long long stackId;
  ProfilerMarker? marker;
};

Read it from the samples of the trace returned by Profiler.stop(): trace.samples[n].marker. There is no way to set, request, or configure it — the user agent populates it during sampling. The normative definition: “marker MUST return the value it was initialized to by the take a sample algorithm, or be absent if no marker was set.”

Source: spec PR #89 — ProfilerSample dictionary (IDL fetched from the PR branch 2026-09-13).

accepted values and constraints

TypeProfilerMarker? — nullable enum in IDL, but in practice a sample either carries one of the six string values or omits the member entirely; serialized traces never contain "marker": null
Possible values"script", "gc", "style", "layout", "paint", "other" — per-value semantics in the ProfilerMarker reference
DefaultAbsent. No marker member means the “capture a marker” algorithm returned null: idle, unattributable, cross-origin, or filtered
Who writes itThe user agent only, inside the “take a sample” algorithm; author code cannot influence which marker a sample receives
Context constraintIn a context without cross-origin isolation, only "style" and "layout" can appear (unless the user agent widens the set via an opt-in such as the origin-trial token)
Source: spec PR #89; markers explainer — format proposal.

reading the field

Reading sample.marker yields the enum string when a marker was captured and exposed, and undefined otherwise. Because absence is meaningful (“if member is missing idle state is assumed”, per the explainer — extended by the filtering rules to also cover suppressed and cross-origin work), consumers should treat the field as tri-state in analysis: a specific activity, known-nothing (absent), and — on engines without the feature at all — never present. All three degrade to the same code path. A sample can carry both a stackId and a non-script marker: garbage collection interrupts the stack without unwinding it, so the marker tells you the sampled stack was paused, not executing.

Source: markers explainer — format proposal and GC scenario; spec PR #89 (marker definition).

errors

The field has no exception surface. Nothing about markers throws: an unexposed or unattributable marker results in an absent member, never an error — the spec PR’s “filter a marker” algorithm returns null rather than failing, and the ChromeStatus record frames the same property as graceful degradation (“an absent marker means idle … existing traces stay valid”). The only errors you can hit are the base API’s own: new Profiler() throws NotAllowedError when the document lacks the js-profiling Document Policy, and that behavior is unchanged by this feature (see the base specification).

Source: spec PR #89 — filter a marker; ChromeStatus record (experiment risks); JS Self-Profiling specification.

context and exposure

Where samples come fromProfiler is [Exposed=(Window, Worker)] in the published spec; traces are produced wherever a profiler can run. Chrome’s implementation samples the main thread (the explainer’s questionnaire: the API “only capture[s] samples from the Main thread”)
Base prerequisitesServe the document with the js-profiling Document Policy header and construct a Profiler — markers add no new options or permissions
Feature gateChrome 153–161: a valid origin-trial token (Origin-Trial header or meta tag) or --enable-blink-features=ExperimentalJSProfilerMarkers; Blink runtime feature ExperimentalJSProfilerMarkers, status experimental
Same-origin ruleA marker is only attached when the work’s responsible document is same-origin with the profiler
Isolation ruleFull marker set requires cross-origin isolation (Cross-Origin-Opener-Policy: same-origin + Cross-Origin-Embedder-Policy: require-corp); without it only style/layout pass the filter
Source: JS Self-Profiling specification (Profiler IDL, Document Policy); spec PR #89 (capture/filter algorithms); runtime_enabled_features.json5; markers explainer (questionnaire §18).

lifecycle

The marker is decided once per sample, inside the “take a sample” algorithm that runs at each tick of the profiler’s sampleInterval: the user agent picks the candidate marker describing its current top-level work, applies the same-origin attribution check, applies the isolation filter, and only then initializes the member. The value is immutable thereafter and only becomes observable when Profiler.stop() resolves with the finished trace — markers are never streamed mid-session. Timing is therefore sampled, trailing, and coarse: the ChromeStatus record describes markers as “best-effort, sampled annotations (≈10 ms interval)” that “must not be relied upon for correctness”, and the explainer stresses that a gc marker is not a precise GC event reference. If the trial’s security review narrows the marker set, previously captured traces stay valid — samples just stop carrying the withdrawn values.

Source: spec PR #89 — take a sample / capture a marker; ChromeStatus record (ongoing constraints); markers explainer (GC resolution note).

Examples

Find the samples where your code was paused by garbage collection — the case markers were built for, since these samples keep their stackId:

const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10_000 });
allocateAggressively();
const trace = await profiler.stop();

const gcPauses = trace.samples.filter(
  (s) => s.marker === "gc" && s.stackId !== undefined,
);
// Each entry: your stack was on-CPU-but-paused while the engine collected.
console.log(`${gcPauses.length} samples were GC pauses under a live stack`);

Split a slow trace into “my JavaScript” vs “browser rendering work” before shipping it to a RUM endpoint:

function summarize(trace) {
  let script = 0, rendering = 0, unknown = 0;
  for (const s of trace.samples) {
    if (s.marker === "script") script++;
    else if (s.marker === "style" || s.marker === "layout" || s.marker === "paint") rendering++;
    else unknown++; // absent marker, "gc", or "other"
  }
  return { script, rendering, unknown, total: trace.samples.length };
}
Source: patterns derived from the trace scenarios in the markers explainer and the owner demo js-profiler-markers-demo; not runtime-verified in this build environment (no Chrome 153 with the trial token — see critique).

security and privacy

The member is the feature’s entire disclosure surface, and both mitigations act directly on it: work for a document that is not same-origin with the profiler never produces a marker (so the field cannot label cross-origin activity), and the values that can correlate engine work across contexts (script, gc, paint, other) are withheld unless the environment is cross-origin isolated. What remains observable without isolation — own-document style/layout timing — is information a page can already obtain by forcing synchronous style and layout flushes (getComputedStyle(), getBoundingClientRect()).
