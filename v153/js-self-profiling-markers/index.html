JS Self-Profiling Markers

Limited availability

  • Chrome · origin trial, desktop 153–161
  • Edge · no announced trial (see compatibility)
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register: a webstatus.dev query returns only the base profiler feature (itself “Limited availability”, Chrome-only since 94) and no entry for the markers extension exists (query, zero matches, verified 2026-09-13). The ChromeStatus record carries Web Feature ID 4217, but no matching web-features entry is published yet.

The JS Self-Profiling API lets a page sample its own call stacks on real user devices. This Chrome 153 origin trial adds an optional marker field to each captured ProfilerSample that names the browser activity running when the sample was taken — script, gc, style, layout, paint, or other — so the gaps and misattributed time in a field trace can finally be told apart from your own JavaScript.

Origin trial — API surface may change

This feature is in an origin trial from Chrome 153 to Chrome 161 (desktop milestones per the ChromeStatus record). The marker vocabulary and its cross-origin-isolation gating are still being standardized in an unmerged spec PR (WICG/js-self-profiling#89; the published spec contains no marker member — verified 2026-09-13). The trial owners state the marker set could narrow during review, and markers are best-effort annotations, so treat them as diagnostic signal, never program correctness.

  • Register for the trial. Sign up your origin for the “JS Self-Profiling Markers” origin trial (Chromium trial name JSSelfProfilingMarkers) and copy the issued token.
  • Serve the token. Either send it as an HTTP response header — Origin-Trial: <token> — or embed it in the page as <meta http-equiv="origin-trial" content="<token>">. Third-party tokens are not supported for this trial (ot_has_third_party_support: false in the ChromeStatus record).
  • Local testing without a token. Launch Chrome 153+ with --enable-blink-features=ExperimentalJSProfilerMarkers, or enable chrome://flags/#enable-experimental-web-platform-features — the Blink runtime feature record is { name: "ExperimentalJSProfilerMarkers", origin_trial_feature_name: "JSSelfProfilingMarkers", status: "experimental" } (fetched from trunk 2026-09-13).
  • File feedback on the WICG/js-self-profiling issue tracker.
Source: ChromeStatus feature 5201297767792640; origin trial registration; runtime_enabled_features.json5; Intent to Experiment.

why it exists

A self-profiled trace records stacks only for the page’s own JavaScript. Everything else the browser does on the main thread — style recalculation, layout, paint, garbage collection — shows up either as an unexplained gap between stacks or, worse, as time misattributed to whatever frame was on the stack: garbage collection interrupts script without unwinding it, so a function that triggers heavy GC looks identical to a function that is simply slow. DevTools profilers solve this locally with activity categories, but field profiling through the JS Self-Profiling API had no equivalent, so RUM pipelines could not tell scripting cost from rendering cost on real user devices.

The markers extension attaches that missing category to each sample. The origin trial (Chrome 153–161) is explicitly framed as validating two things at production scale: whether per-sample markers let developers attribute slow field traces to browser activity outside their JavaScript and act on it, and whether the marker data is accurate and stable enough on real devices to drive optimization decisions. The feature is Microsoft-driven (the ChromeStatus record is owned by monicach@microsoft.com and victorhuang@microsoft.com), with Excel Online and Datadog named as consuming partners, and a W3C TAG review open (status “Pending” per ChromeStatus).

Source: blink-dev — Intent to Experiment: JS Self-Profiling Markers; markers explainer — introduction and context; ChromeStatus record (motivation, experiment goals).

Syntax

The feature adds one enum and one optional dictionary member. Verbatim from the spec change in WICG/js-self-profiling#89 (identical IDL in the markers explainer, which no longer carries the earlier [CrossOriginIsolated] attribute — gating moved into the filter a marker algorithm):

enum ProfilerMarker { "script", "gc", "style", "layout", "paint", "other" };

dictionary ProfilerSample {
  required DOMHighResTimeStamp timestamp;
  unsigned long long stackId;
  ProfilerMarker? marker;
};

For comparison, the published specification’s ProfilerSample has no marker member yet (PR not merged as of 2026-09-13):

dictionary ProfilerSample {
  required DOMHighResTimeStamp timestamp;
  unsigned long long stackId;
};
Source: spec PR #89 (IDL fetched from the PR branch 2026-09-13); published JS Self-Profiling specification — ProfilerSample.

how it hangs off the existing API

Markers add no new interface, method, event, or option: you start a profiler exactly as before, and the marker appears (when exposed) on the samples inside the trace that Profiler.stop() resolves with. The relevant surrounding surface, verbatim from the published specification:

[Exposed=(Window, Worker)]
interface Profiler : EventTarget {
  readonly attribute DOMHighResTimeStamp sampleInterval;
  readonly attribute boolean stopped;

  constructor(ProfilerInitOptions options);
  Promise<ProfilerTrace> stop();
};

dictionary ProfilerInitOptions {
  required DOMHighResTimeStamp sampleInterval;
  required unsigned long maxBufferSize;
};

dictionary ProfilerTrace {
  required sequence<ProfilerResource> resources;
  required sequence<ProfilerFrame> frames;
  required sequence<ProfilerStack> stacks;
  required sequence<ProfilerSample> samples;
};

Two consequences worth spelling out. First, because marker rides on ProfilerSample, its granularity is the profiler’s sampleInterval (requested at construction; the ChromeStatus record describes the effective marker resolution as “≈10 ms interval” sampling). Second, a sample can carry both a stackId and a non-script marker — that is the whole point: GC interrupts a stack without unwinding it, so the stack stays attributed while the marker reveals the interruption. The base API requires the document to be served with the Document-Policy: js-profiling header (spec §Profiling Sessions); markers change nothing about that prerequisite.

Source: JS Self-Profiling specification (IDL fetched 2026-09-13); ChromeStatus record (ongoing constraints).

the exposure model: capture, attribute, filter

The spec PR makes marker capture a two-step, privacy-gated pipeline inside the existing “take a sample” algorithm:

  1. Capture a marker. The user agent picks the ProfilerMarker value that best describes the top-level work it was performing when the sample was taken (or null if none applies). If that work was performed for a specific document that is not same-origin with the profiler’s origin, the marker is dropped — markers never describe cross-origin documents’ work.
  2. Filter a marker. If the profiler’s environment has its cross-origin isolated capability set (the document was served with Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp), every marker value passes. Otherwise only "style" and "layout" pass; "script", "gc", "paint", and "other" are suppressed and the sample’s marker member is simply absent.

The PR also permits user agents to widen the filtered set through an explicit opt-in — naming “an origin-trial token or a document policy” as examples — provided the opt-in never exposes markers cross-origin. Chrome’s trial description matches this model (“Marker exposure is same-origin and gated on cross-origin isolation for non-script activity”), and the Intent to Experiment notes the non-isolated style/layout exposure is itself still under security review, so the split could move during the trial. Details and per-value semantics: ProfilerMarker reference.

Source: spec PR #89 — “capture a marker” and “filter a marker” algorithms; Conditional Markers Exposure explainer; Intent to Experiment (risks).

Examples

Profile a workload and aggregate time by browser activity (requires the base API’s Document-Policy: js-profiling response header, plus this trial’s token or flag):

// Markers need no new options — feature-detect on the trace instead.
const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10_000 });

renderTheExpensiveThing();

const trace = await profiler.stop();

// Aggregate sample counts by marker. An absent marker means the engine
// was idle, the work was cross-origin, or the value was filtered out
// in a non-cross-origin-isolated context.
const byMarker = {};
for (const sample of trace.samples) {
  const key = sample.marker ?? "(none)";
  byMarker[key] = (byMarker[key] ?? 0) + 1;
}
console.table(byMarker);
// e.g. { script: 41, layout: 12, style: 7, gc: 3, "(none)": 9 }

What a trace looks like with markers, from the explainer (cross-origin-isolated context, so every value can appear; note the GC samples that keep their stackId):

security and privacy

  • Cross-origin work is never labeled. The “capture a marker” algorithm drops any marker for work performed for a document that is not same-origin with the profiler, so a page cannot use markers to observe what the browser is doing for embedded cross-origin content.
  • Side-channel gating. gc, paint, script, and other can reflect engine work correlated across contexts (engine-wide GC; compositing that includes other frames), so they are exposed only under cross-origin isolation — the same COOP+COEP boundary that gates SharedArrayBuffer and high-resolution timers. The ChromeStatus record states the restricted markers “remain permanently gated behind cross-origin isolation”.
  • style/layout are treated as already-observable. A document can synchronously force and time its own style and layout today (getComputedStyle(), getBoundingClientRect()), so the PR exposes those two markers without isolation — this specific exposure is the part still under security review (tracked from the 2021 review in WICG/js-self-profiling#61).
  • GC timing is deliberately coarse. The explainer notes marker data arrives only after the trace completes, at sampling resolution (≈10 ms), so a gc marker “should not be considered a weak reference to a GC event” — aligning with the W3C TAG design principle against exposing GC timing (design principles §js-gc).
  • No PII, no persistent state, no sensors per the explainer’s security & privacy questionnaire.
