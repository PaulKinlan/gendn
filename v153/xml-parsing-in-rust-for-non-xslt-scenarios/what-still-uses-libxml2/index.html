What still uses libxml2 in Chrome 153

The other half of the migration

“Non-XSLT scenarios” is a precise boundary. This page documents which XML processing in Chrome 153 remains on the C libraries (libxml2/libxslt), why, and the sourced conditions for their eventual removal.

Anything that can feed the XSLT pipeline stays on libxml2, because Chromium’s libxslt integration consumes libxml2 document structures — the runtime-flag comment for the umbrella XMLParsingRust flag is blunt: switching everything to Rust “breaks XSLT as the Rust XML parsing code paths is incompatible with libxslt”. Fragment parsing and a couple of internal helpers also remain on libxml2 in Chrome 153.

The gate, in code

The libxml2 fallback is the tail of Document::CreateParser() (document.cc, fetched 2026-09-13) — reached by framed, non-SVG XML documents, i.e. exactly the documents a <?xml-stylesheet type="text/xsl"…?> processing instruction could transform:

// Reached only when the document has a frame and is not an SVG document:
if (RuntimeEnabledFeatures::XMLParsingRustEnabled()) {   // default OFF
  data_->using_rust_xml_parser_ = true;
  return MakeGarbageCollected<XMLDocumentParserRs>(*this, View());
} else {
  return MakeGarbageCollected<XMLDocumentParser>(*this, View());  // libxml2
}

And the corresponding flag declarations in runtime_enabled_features.json5 (verbatim; no status means not enabled anywhere by default):

{
  // Switches from XML parsing through libxml2 to parsing XML using the
  // Rust xml crate. This makes parsing memory safe but breaks XSLT
  // as the Rust XML parsing code paths is incompatible with libxslt.
  // https://crbug.com/441911594
  name: "XMLParsingRust"
},
{
  // Enables the Rust XML parser for situations where we know
  // no XSLT processing will be required. This covers usage of
  // JS DOMParser API to parse XML, and usage of XMLHttpRequest
  // with its responseXML document.
  // https://crbug.com/466303347
  name: "XMLRustForNonXslt",
  status: "stable",
},
Source: document.cc — Document::CreateParser(); runtime_enabled_features.json5.

Outputs — unchanged behavior on these paths

Because these scenarios did not migrate, Chrome 153 produces byte-for-byte the behavior of earlier releases on them: libxml2 error strings, libxml2 parsing quirks, and the full XSLT 1.0 pipeline via libxslt. Nothing on these paths changed in this milestone; the observable changes documented under compatibility differences apply only to the migrated entry points.

Source: document.cc (unchanged libxml2 branch); Intent to Ship (scope limited to the four scenarios).

Error surface

Unchanged for these scenarios: libxml2’s error catalogue feeds the same XMLErrors rendering (“error on line… at column…”) as before (xml_errors.cc is shared by both backends). A practical consequence for developers: the same malformed markup can yield different error wording depending on whether it is parsed by DOMParser (Rust path) or served as a framed XML navigation (libxml2 path) in Chrome 153 — another reason never to string-match parser errors.

Source: xml_errors.cc; document.cc (per-document backend selection).

Context — the XSLT dependency

These scenarios stay on libxml2 only because of XSLT. Chrome’s XSLT support is itself being removed under Deprecate and remove XSLT (ChromeStatus 4709671889534976), whose record (fetched 2026-09-13) shows deprecation development from Chrome 143 and a deprecation trial spanning Chrome 152–175 for sites that need migration time. Flipping the umbrella XMLParsingRust flag today would break XSLTProcessor and <?xml-stylesheet?> transforms — which is why it ships default-off and this feature exists as the safe subset.

Source: ChromeStatus — Deprecate and remove XSLT; runtime_enabled_features.json5 (XMLParsingRust comment).

Lifecycle — the removal endgame

The sequencing is stated in the Intent to Ship’s security section: “Almost all XML parsing we perform will run through the Rust memory-safe parser. When XSLT deprecation concludes, we can deactivate libxml2 XML parsing and move to Rust XML parsing completely.” Until then the umbrella flag XMLParsingRust (tracking bug crbug.com/441911594) remains the switch for the final step, and the libxml2 code paths above are maintained. No milestone for the final deactivation is committed in any source fetched for this page; the XSLT deprecation trial running through Chrome 175 (ChromeStatus record) is the earliest bound implied by the public record.

Source: Intent to Ship (security section); crbug.com/441911594; XSLT deprecation record.

Examples — code that stays on the C libraries in 153

// XSLTProcessor: stylesheet + transform run through libxslt/libxml2.
const xslt = new XSLTProcessor();
const sheet = new DOMParser().parseFromString(`
  <xsl:stylesheet version="1.0"
      xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
    <xsl:template match="/"><out><xsl:value-of select="//title"/></out></xsl:template>
  </xsl:stylesheet>`, "application/xml");
xslt.importStylesheet(sheet);                    // libxml2/libxslt path
const data = new DOMParser().parseFromString(
  "<doc><title>hi</title></doc>", "application/xml");
const result = xslt.transformToDocument(data);   // libxml2/libxslt path

// Fragment parsing inside an XML document — libxml2 path in Chrome 153:
const xdoc = new DOMParser().parseFromString("<root/>", "application/xml");
xdoc.documentElement.innerHTML = "<child>text</child>";

// Framed XML navigation (tab/iframe showing feed.xml, XSLT PI honored):
// <?xml-stylesheet type="text/xsl" href="feed.xsl"?> … → libxml2 + libxslt

Note the boundary running through a single workflow: the two DOMParser calls above use the Rust parser (frameless documents), while importStylesheet/transformToDocument re-parse and transform through libxml2/libxslt.

Source: path attribution per xslt_processor_libxslt.cc, xml_document_parser.cc (XmlDocPtrForString, ParseDocumentFragment), and document.cc.

Security and privacy

The honest security accounting of Chrome 153: the C attack surface (libxml2/libxslt) remains reachable from web content through XSLT scenarios and XML fragment parsing until the XSLT removal completes — that is why the ChromeStatus security section frames this feature as “almost all” rather than “all” XML parsing becoming memory-safe. The deprecation-trial structure of the XSLT removal bounds how long that residual surface persists for sites that opt in to the trial.

Source: ChromeStatus record (security risks); XSLT deprecation record.
