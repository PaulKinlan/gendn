XML parsing in Rust for non-XSLT scenarios

Not a Baseline-tracked feature — internal implementation change, no new API

  • Chrome · 153 (milestone listing)
  • Edge · not separately reported (Chromium-based)
  • Firefox · unaffected (own parser)
  • Safari · unaffected (own parser)

This entry documents Chrome swapping its internal XML parsing engine from libxml2 (C) to the memory-safe Rust xml crate in scenarios that never involve XSLT. There is no web-exposed API surface: the Intent to Ship states “No browser vendor or developers signals were solicited as there is no functional change or introduction of new API”, the ChromeStatus record lists no Web Feature ID, a webstatus.dev query returns zero matches, and there is no BCD key for the migration itself (the affected APIs — DOMParser, XMLHttpRequest.responseXML — keep their existing BCD entries because their contracts are unchanged). All verified 2026-09-06.

Starting in Chrome 153, XML that reaches the browser through the DOMParser API, XMLHttpRequest.responseXML, standalone SVG documents, or SVG loaded as an external image is parsed by a memory-safe Rust parser instead of libxml2. The parse result is intended to be functionally identical — same DOM, same well-formedness rules — while eliminating the class of memory-corruption vulnerabilities that C parsers are prone to. XML documents that may still need XSLT (top-level non-SVG XML navigations in a frame) stay on libxml2 until Chrome’s separate XSLT deprecation concludes.

what changed: the four scenarios

Chrome parses XML in two broad situations: documents that might be transformed by XSLT (a top-level XML navigation carrying an <?xml-stylesheet?> processing instruction), and everything else. The Rust parser is incompatible with libxslt, so this change targets only the “everything else” set — scenarios where Chrome is certain no XSLT processing will occur. Verbatim from the Intent to Ship:

  1. DOMParser Web API — parseFromString() with an XML MIME type.
  2. Accessing responseXML of XMLHttpRequest — the parsed Document for XML responses.
  3. SVG standalone images — “accessing a image.svg document directly as a top level navigation”.
  4. SVG external images — “a main document embedding an SVG as an external image resource” (e.g. <img src="icon.svg">). Per the intent’s measurement note, SVG usage as external images “remains high at about 60%” of page loads, so this is the highest-traffic path.

Scenarios 3 and 4 were unlocked by a prior deprecation: Remove Inline XSLT for production of SVG removed the last way an SVG image could legitimately depend on XSLT.

Source: Intent to Ship — summary (verbatim list); chromestatus 5143784390262784

how Chrome picks the parser

The decision is made in Document::CreateParser() in third_party/blink/renderer/core/dom/document.cc (fetched 2026-09-06), quoted verbatim (HTML documents take the HTML parser before this point):

// Use the Rust XML parser for situations non-XSLT situations: XMLHttpRequest,
// JS DOMParser API, where no dom_window_ is available, or for SVG images.
if (!GetFrame() || IsSVGDocument()) {
  // ...
  if (RuntimeEnabledFeatures::XMLRustForNonXsltEnabled()) {
    data_->using_rust_xml_parser_ = true;
    return MakeGarbageCollected<XMLDocumentParserRs>(*this, View());
  }
}

// FIXME: this should probably pass the frame instead
if (RuntimeEnabledFeatures::XMLParsingRustEnabled()) {
  data_->using_rust_xml_parser_ = true;
  return MakeGarbageCollected<XMLDocumentParserRs>(*this, View());
} else {
  return MakeGarbageCollected<XMLDocumentParser>(*this, View());
}

Read as a contract: an XML document that has no frame (documents created by DOMParser and XMLHttpRequest never have one) or is an SVG document (both standalone and external-image SVG) is parsed by XMLDocumentParserRs when XMLRustForNonXslt is enabled — which it is by default in Chrome 153. Any other XML document — a framed, non-SVG XML navigation, exactly the case that may carry an <?xml-stylesheet?> PI — still gets the libxml2-backed XMLDocumentParser unless the separate, XSLT-breaking XMLParsingRust flag is turned on.

Source: Document::CreateParser, document.cc (verbatim); runtime_enabled_features.json5

what stays the same

The intent’s compatibility position is that the Rust implementation is “expected and shown to be functionally equivalent to the C++ based implementation. No functional change.” Specifics visible in the implementation:

  • API contracts are untouched. DOMParser.parseFromString(), XMLHttpRequest.responseXML, and SVG loading keep their specified signatures and semantics — nothing on MDN about them changes.
  • XHTML named entities still resolve. XMLDocumentParserRs pre-registers the Latin-1, Symbol, Special, and HTML5 entity maps (add_xhtml_entities() in xml_ffi.rs with entities.rs), matching the libxml2 path’s handling of &nbsp; and friends in XHTML.
  • XML prolog handling matches. Version numbers other than 1.0 are silently processed as 1.0, mirroring the old parser and the XML 1.0 prolog note; standalone and encoding declarations are carried onto the document as before (see StartDocument in xml_document_parser_rs.cc).
  • DOCTYPE nodes are still created (name, public ID, system ID), and the tree-depth guard is the same shared constant: parsing fails fatally with “Excessive node nesting.” beyond kMaxXMLTreeDepth = 5000 (defined in xml_document_parser.h, used by both parsers).
  • DTD-dependent behavior was already unsupported. The intent notes remaining upstream xml-rs conformance-test failures “pertain to functionality that we do not use (DTD parsing, for example), or are because of conflicting specifications” — custom entity definitions in internal DTD subsets were not a supported Chrome behavior on these paths before, and are not now.
Source: Intent to Ship — interoperability and compatibility; xml_ffi.rs; xml_document_parser_rs.cc

error reporting: what is observably different

Well-formedness failures surface through the same channels as before — but the text of error messages now comes from the Rust xml crate rather than libxml2. If your code or tests string-match parser error messages, this is the one place the swap can be visible:

SurfaceBehavior after the swap
DOMParserA malformed document still yields a document whose root content is a <parsererror> element (Blink’s shared XMLErrors::InsertErrorMessageBlock(), called identically from XMLDocumentParserRs). Detect the element, not its message text.
XMLHttpRequest.responseXMLStill null for a non-well-formed response: the header for XMLDocumentParserRs::WellFormed() notes it is “Used by the XMLHttpRequest to check if the responseXML was well formed”, and it returns true only when the Rust reader recorded no error.
Error message textProduced by the Rust crate; the FFI layer strips the crate’s row:col prefix and passes row and column separately into Blink’s existing error formatting (try_get_error_details() in xml_ffi.rs). Wording differs from libxml2’s messages for the same malformed input.
Error positionsRow and column are reported from the Rust reader’s position tracking; the position of the last successfully parsed event is used where an exact error position is unavailable.
Streaming end-of-inputAn “Unexpected end of stream” condition mid-parse is treated as resumable (is_error_resumable()) so chunked document loads do not error prematurely; a genuinely unbalanced root at the true end of input is converted to a fatal error at finish time.
Nesting limitFatal “Excessive node nesting.” error beyond 5000 open elements — unchanged, shared constant with the libxml2 path.
Source: xml_ffi.rs — try_get_error_details, is_error_resumable (verbatim behavior); xml_document_parser_rs.h — WellFormed() comment; xml_document_parser_rs.cc

performance: a measured, bounded regression

The intent is unusually candid here. A 1%-of-stable experiment measured the Blink.XMLParsing.NonXsltXmlParsingTime.Combined histogram and “confirms an isolated parser performance regression”, while “guard rail metrics are unaffected on all relevant platforms”:

  • Android: parsing 36% slower at the 50th percentile to 54% slower at the 99th.
  • Windows: 23% slower at the 25th percentile, 74% at the 95th, up to 209% at the 99th.
  • In absolute terms: “parse times reaching only tens of milliseconds” even at those percentiles.

If your application parses very large XML payloads on the client (multi-megabyte feeds, large SVG assets), budget for parse times up to roughly 2–3× at the tail on Windows — still tens of milliseconds in the measured distribution — and consider moving heavy parsing off the critical path (e.g. into a worker via fetch + DOMParser on demand).

Source: Intent to Ship — ergonomics (verbatim figures)

testing, bisecting, and reporting regressions

Because this is a behavior-preserving swap, the practical developer contract is: if XML that parsed before Chrome 153 stops parsing (or parses differently), that is a Chromium bug — verify and report it. The intent records that “two or three compatibility issues were identified during the experiment phase and have been fixed” and rates the residual risk “very low”, but the reporting path is the safety net.

  1. Confirm the parser is the variable. Blink runtime features can be toggled from the command line (RuntimeEnabledFeatures.md). Run your repro twice: 
    # Rust parser for the four non-XSLT scenarios (Chrome 153 default)
chrome

# Old libxml2 path restored for those scenarios
chrome --disable-blink-features=XMLRustForNonXslt
    If the behavior difference tracks the flag, it is this migration.
  2. Do not ship the flags as a workaround. XMLRustForNonXslt is a transition mechanism; the stated end state is to “deactivate libxml2 XML parsing and move to Rust XML parsing completely” once XSLT deprecation concludes. The opposite flag, --enable-blink-features=XMLParsingRust, force-routes almost all XML parsing through Rust today but “breaks XSLT” per its flag comment — useful only for testing the future state.
  3. File the regression. Report at issues.chromium.org against component Blink>DOM (component query), referencing tracking bug crbug.com/466303347, with the XML input that reproduces the difference.

There is no chrome://flags entry for this feature (the ChromeStatus record lists flag: false); the command-line switches above are the only toggle.

examples

Parsing XML with DOMParser — detect failure structurally, never by matching error text (the message wording changed with this migration and differs across browsers anyway):

const doc = new DOMParser().parseFromString(xmlString, "application/xml");

// Cross-browser, parser-agnostic failure check:
const parseError = doc.querySelector("parsererror");
if (parseError) {
  // Malformed XML. Fine to LOG parseError.textContent for humans,
  // but do not branch on its wording.
  console.warn("XML did not parse:", parseError.textContent);
} else {
  useDocument(doc);
}

XMLHttpRequest.responseXML — the well-formedness contract is unchanged: null means the response was not well-formed XML:

const xhr = new XMLHttpRequest();
xhr.open("GET", "/inventory.xml");
xhr.responseType = "document";
xhr.onload = () => {
  const doc = xhr.responseXML;   // Document, or null if not well-formed
  if (doc === null) {
    console.warn("inventory.xml is not well-formed XML");
    return;
  }
  render(doc.querySelectorAll("item"));
};
xhr.send();

The Chrome Platform Showcase entry for this feature has no live demo route yet (HEAD-checked 404, 2026-09-06) — and an internal parser swap with no intended behavior difference has little to demo beyond the snippets above. If a demo lands it will appear at that URL.

Source: MDN — DOMParser.parseFromString (parsererror contract); MDN — XMLHttpRequest.responseXML (null on failure); chrome-platform-showcase (404 at fetch time)

web platform tests

There is no feature-specific WPT (there is no new feature to test); instead, the migration is validated by the existing XML conformance surface. The intent answers “Is this feature fully tested by web-platform-tests?” with “Yes” — the relevant suites are the DOM parsing tests (wpt.fyi/results/domparsing) and the XMLHttpRequest tests covering responseXML (wpt.fyi/results/xhr), which now exercise the Rust parser in Chrome. Additionally, the upstream xml-rs crate runs XML conformance test suites “with a good pass rate”; investigated failures concern functionality Chrome does not use (DTD parsing) or conflicting specifications, per the intent.

security and privacy

  • Security is the point. Verbatim from the intent: “This change’s main intention is to improve security. Almost all XML parsing we perform will run through the Rust memory-safe parser. When XSLT deprecation concludes, we can deactivate libxml2 XML parsing and move to Rust XML parsing completely.” XML parsers are a classic memory-corruption attack surface because they process untrusted network input; Rust’s memory safety removes that bug class for these paths.
  • The vendored crate is treated as security-critical. Chromium’s README.chromium for the xml crate (v1.4.0) records Security Critical: yes and a manual update mechanism (crbug.com/449898466).
  • No privacy delta. No new data is collected, stored, or exposed; the change is not observable cross-origin. The only new telemetry is the parse-time histogram used to monitor the rollout.
Source: Intent to Ship — security section (verbatim); README.chromium for the xml crate
