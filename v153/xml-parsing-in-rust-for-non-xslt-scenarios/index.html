XML parsing in Rust for non-XSLT scenarios

Not a web platform feature — browser-internal implementation change

  • Chrome · 153 (desktop, Android, WebView)
  • Chrome on iOS · no milestone in the ChromeStatus record
  • Firefox · no signal (unaffected — Chromium-internal change)
  • Safari · no signal (unaffected — Chromium-internal change)

Not on the Baseline register: a webstatus.dev query returns zero matches (verified 2026-09-13). That is expected — this entry changes which parser implementation Chrome uses internally, not any developer-facing API, and the Intent to Ship solicited no vendor signals because “there is no functional change or introduction of new API”.

From Chrome 153, XML parsing for scenarios that can never involve XSLT — DOMParser.parseFromString(), XMLHttpRequest.responseXML, standalone SVG navigations, and SVG loaded as an external image — runs through a memory-safe parser written in Rust (the xml-rs crate) instead of the C-based libxml2. The parse result is intended to be functionally identical; the change removes a whole class of memory-corruption vulnerabilities from XML processing.

No new API — nothing to adopt, but watch for regressions

This is a parser engine swap behind existing standardized APIs. There is nothing to feature-detect and no code to change. What developers should know:

  • Behavior is intended to be identical. The Intent to Ship states the new implementation is “expected and shown to be functionally equivalent to the C++ based implementation”, and notes that “two or three compatibility issues were identified during the experiment phase and have been fixed” — with “a very low risk of previously unforeseen compatibility issues” remaining. See observable compatibility differences.
  • Parse error message text can differ. Code that string-matches the contents of a <parsererror> document was never on a standardized contract and may see different wording. The error mechanism (error document for DOMParser, null responseXML) is unchanged. See changed error surfaces.
  • XML parsing gets measurably slower in these scenarios (tens of milliseconds at worst in the shipped experiment’s measurements) — see the sourced numbers.
  • If XML that parsed in Chrome 152 fails in 153, report it — see reporting regressions.
Source: Intent to Ship: XML Parsing in Rust for non XSLT scenarios; ChromeStatus feature 5309598397497344.

why it exists

libxml2 is a large C library, and parsing untrusted XML in C is a recurring source of memory-corruption vulnerabilities. The ChromeStatus summary is explicit that the point of this change is security: “To improve browser security and protect users against memory-related vulnerabilities, Chrome 153 updates its XML parsing engine to a memory-safe Rust implementation for several common scenarios. This foundational update eliminates potential memory corruption bugs while maintaining full compatibility with existing web standards.”

The blocker for replacing libxml2 wholesale is XSLT: Chromium’s libxslt integration operates on libxml2 document structures, so “the Rust XML parsing code paths is incompatible with libxslt” (runtime flag comment). Chrome is deprecating and removing XSLT on a separate track; in the meantime this feature migrates every scenario where XSLT provably cannot occur. Two preparatory removals cleared the path: inline XSLT for the production of SVG (which made scenarios 3 and 4 — the SVG image paths — XSLT-free; see the gendn v147 reference) and externally loaded entities in XML parsing (a libxml2 capability the Rust parser deliberately does not implement — the Intent to Deprecate and Remove states “The Rust-based XML parser we intend to migrate to, does not support external entities and we don’t think it’s necessary or desirable to implement this feature”).

The endgame, from the Intent to Ship’s security section: “Almost all XML parsing we perform will run through the Rust memory-safe parser. When XSLT deprecation concludes, we can deactivate libxml2 XML parsing and move to Rust XML parsing completely.”

Source: ChromeStatus summary; Intent to Ship; Intent to Deprecate and Remove: Externally loaded entities in XML parsing; runtime_enabled_features.json5.

reporting regressions

The compatibility promise of this rollout is “no functional change”. If XML content that worked in Chrome 152 breaks in Chrome 153 in one of the affected scenarios, that is a regression the Chromium team wants reported.

Where to fileFile a new Chromium issue via the Chromium bug reporting guidelines, component Blink>DOM (the blink component recorded on the ChromeStatus entry), and reference the tracking bug crbug.com/466303347.
What to includeThe XML source (or a URL), which entry point parses it (DOMParser, XMLHttpRequest.responseXML, standalone SVG navigation, or SVG as <img>), the Chrome version from chrome://version, and the behavior difference versus Chrome 152 (or versus a 153 run with the flag disabled — see the verification example below).
What a regression looks likeA document that previously produced a DOM now produces a <parsererror> error document (DOMParser), responseXML that was a Document is now null (its well-formedness check is the parser’s WellFormed(), per xml_document_parser_rs.cc and the XHR spec), or an SVG image that rendered before now fails to render.
Not a regressionDifferent wording inside a <parsererror> element with the same well-formed/not-well-formed outcome. Error message text is not a standardized contract and changed with the parser backend — see compatibility differences.
Isolating the causeThe parser choice is controlled by the Blink runtime feature XMLRustForNonXslt (runtime_enabled_features.json5). Launching Chrome with --disable-blink-features=XMLRustForNonXslt restores the libxml2 path for the non-XSLT scenarios; if the problem disappears, it is this rollout.
Rollout controlThe ChromeStatus API record lists the Finch study name XMLParsingRust — the staged-rollout mechanism under which the pre-ship 1%-at-stable experiment ran, and the record notes “Two or three compatibility issues were identified during the experiment phase and have been fixed.”
Security-sensitive findingsSuspected parser security bugs (in either backend) follow the separate Chromium security bug process, which restricts visibility of the report.

A minimal before/after verification harness — run it in Chrome 153, then again with --disable-blink-features=XMLRustForNonXslt, and attach both outputs to the report:

const source = /* the XML that regressed */ `<root><child attr="value"/></root>`;

const doc = new DOMParser().parseFromString(source, "application/xml");
const err = doc.querySelector("parsererror");
console.log(err ? `PARSE ERROR: ${err.textContent}` : `OK: root=${doc.documentElement.tagName}`);

// The same document through XHR (responseXML is null when not well-formed):
const xhr = new XMLHttpRequest();
xhr.open("GET", URL.createObjectURL(new Blob([source], { type: "application/xml" })));
xhr.onload = () => console.log("responseXML:", xhr.responseXML);
xhr.send();

Examples

Nothing changes in how these APIs are called — the examples below simply exercise each migrated scenario and show the unchanged developer-facing contract:

// Scenario 1 — DOMParser (frameless XML document → Rust parser in Chrome 153+)
const doc = new DOMParser().parseFromString(
  `<note><to>Ada</to><body>Reindeer flotilla</body></note>`,
  "application/xml");
console.log(doc.documentElement.tagName); // "note" — same DOM as Chrome 152

// Scenario 2 — XMLHttpRequest.responseXML
const xhr = new XMLHttpRequest();
xhr.open("GET", "/api/feed.xml");
xhr.onload = () => {
  // Document when well-formed, null when not — contract unchanged.
  console.log(xhr.responseXML?.querySelectorAll("item").length);
};
xhr.send();

// Scenarios 3 & 4 — SVG: standalone navigation and external image resource
// <img src="diagram.svg"> and opening diagram.svg directly both parse the
// SVG document with the Rust parser; rendering is unchanged.
const img = new Image();
img.onload = () => console.log("SVG decoded", img.naturalWidth);
img.src = "diagram.svg";
Source: scenario list per the Intent to Ship; responseXML null-on-error contract per the XMLHttpRequest Standard.

web platform tests

The Intent to Ship answers “Is this feature fully tested by web-platform-tests?” with “Yes”. Because the change swaps the implementation behind existing standardized surfaces, the relevant coverage is the existing suites that drive those surfaces: wpt.fyi/results/domparsing (DOMParser and XML fragment behavior) and wpt.fyi/results/xhr (responseXML). The Intent additionally notes that the upstream xml-rs crate runs XML conformance test suites “with a good pass rate”, remaining upstream failures pertaining “to functionality that we do not use (DTD parsing, for example), or are because of conflicting specifications”.

security and privacy

  • The change is itself a security mitigation. XML parsers process fully attacker-controlled input; a memory-safe implementation eliminates the memory-corruption class of parser bugs. The ChromeStatus security section: “This change’s main intention is to improve security. Almost all XML parsing we perform will run through the Rust memory-safe parser.”
  • Reduced feature surface is deliberate. The Rust parser does not implement synchronous external entity/DTD loading — a classic XXE-adjacent surface that Chromium deprecated and removed separately before this migration (usage was ~0.000015% of page loads per the use counter; Firefox never supported it, per the Intent to Deprecate and Remove).
  • No new data exposure. No new API, permission, or state is introduced; parsing remains in the renderer process on the same inputs as before.
  • Remaining C surface. libxml2/libxslt remain reachable from XSLT scenarios and fragment parsing until XSLT removal completes.
Source: ChromeStatus security risks section; blink-dev — externally loaded entities I2D&R; use counter 529.
