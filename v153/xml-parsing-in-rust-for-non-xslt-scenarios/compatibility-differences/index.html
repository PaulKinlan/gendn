← XML parsing in Rust for non-XSLT scenarios

v153 · xml parsing in rust · migration behavior

Observable compatibility differences

Official claim: functionally equivalent

The Intent to Ship: “the new memory-safe implementation is expected and shown to be functionally equivalent to the C++ based implementation. No functional change” — with the caveats quoted on this page. Everything below is drawn from the intent thread and the Chromium implementation, fetched 2026-09-13; nothing here was independently verified in a running Chrome 153 build.

What a developer can actually observe differing (or explicitly staying the same) between Chrome’s libxml2 backend and the Rust backend in the migrated scenarios: error-message wording, entity and DTD handling, encoding-declaration handling, parse performance — and the parity guarantees implemented on purpose.

Parser configuration

The Rust backend is the xml-rs crate (vendored as xml v1.4.0, per third_party/rust Cargo.toml), configured verbatim as follows in xml_ffi.rs:

let parser_config = ParserConfig::new()
    .override_encoding(Some(Encoding::Utf8))
    .ignore_invalid_encoding_declarations(true)
    .ignore_comments(false)
    .ignore_end_of_stream(true)
    .allow_multiple_root_elements(false);

Reading that configuration: input reaches the crate already decoded (as UTF-8), so the document’s encoding="…" declaration does not drive decoding at this layer and an inaccurate declaration is not itself a fatal error; comments become DOM Comment nodes; incremental network chunks do not end the stream; and multiple root elements remain a well-formedness error, as in XML 1.0.

Source: xml_ffi.rs — create_reader(); vendored crate manifest; xml-rs documentation; XML 1.0.

Input handling differences

Input constructBehavior under the Rust parser
External entities / external DTDs (SYSTEM/PUBLIC loads)Never loaded. The Rust parser “does not support external entities” (Intent to Deprecate and Remove). This is not new in 153: Chrome removed synchronous external-entity loading for all its XML parsing separately (ChromeStatus 6734457763659776; deprecate 144, remove 145 proposed in that thread), precisely to make this migration possible
DTD internal subsetThe DOCTYPE’s name, public id, and system id are surfaced and a DocumentType node is created (DocType callback in xml_document_parser_rs.cc). Beyond that, the Intent notes upstream test failures “pertain to functionality that we do not use (DTD parsing, for example)” — DTD-driven validation is not part of the browser contract in either backend
XHTML named character references (&nbsp; etc.)Preserved for the spec’s DOCTYPE allowlist. When the DOCTYPE public id matches the list in xhtml_subset.cc (XHTML 1.0 Strict/Transitional/Frameset, XHTML 1.1, XHTML Basic 1.0, XHTML+MathML(+SVG), MathML 2.0, XHTML Mobile 1.0/1.1/1.2 — implementing the HTML Standard’s XHTML parsing rule), the parser injects the HTML entity tables statically (add_xhtml_entities loading LAT1_MAP, SYMBOL_MAP, SPECIAL_MAP, HTML5_MAP in xml_ffi.rs) instead of reading a DTD

Output — DOM parity and what was fixed

The produced DOM is intended to be indistinguishable: same elements, attributes, namespaces, comments, CDATA, processing instructions, and DocumentType node. The Intent to Ship records the honest residual: “Two or three compatibility issues were identified during the experiment phase and have been fixed… A very low risk of previously unforeseen compatibility issues remains, but I consider it unlikely.” One documented edge in the wrapper: a processing-instruction target/data that XML’s character rules accept but Blink’s createProcessingInstruction rejects is silently dropped — deliberately “follow[ing] the non-Rust implementation” rather than raising a well-formedness error (xml_document_parser_rs.cc).

Source: Intent to Ship (interoperability section); xml_document_parser_rs.cc.

Changed error surfaces

The error mechanism is shared, the error text is not:

  • Unchanged frame: both backends report through Blink’s XMLErrors, which renders the same <parsererror> element and formats every line as <type> on line <lineNumber> at column <columnNumber>: <message> (xml_errors.cc).
  • Changed wording: the <message> part now comes from xml-rs (xml::reader::Error, with its row:col prefix stripped in try_get_error_details, xml_ffi.rs) instead of libxml2’s message catalogue. Code that string-matches parsererror contents will see different text for the same malformed input.
  • Unchanged outcomes: fatal errors still stop parsing and insert the error block once (InsertErrorMessageBlock); responseXML is still null for non-well-formed responses; warnings still do not fail the parse (xml_document_parser_rs.cc — HandleError).
  • Streaming edge handled: a chunk boundary that momentarily leaves the root element unbalanced is recognized via the crate’s resumable “Unexpected end of stream” syntax error and parsing resumes with the next chunk instead of failing (is_error_resumable in xml_ffi.rs).
Source: xml_errors.cc; xml_ffi.rs; xml_document_parser_rs.cc.

Context — where these differences can be observed

Only in the migrated scenarios (DOMParser, XMLHttpRequest.responseXML, standalone and external-image SVG) on Chrome 153+ for desktop, Android, and WebView (ChromeStatus record). XSLT-capable paths keep libxml2 behavior — including its error strings — until that pipeline is removed (details). The external-entity difference predates this feature: it applies to both backends since the separate removal (ChromeStatus 6734457763659776).

Source: ChromeStatus record; ChromeStatus — externally loaded entities.

Lifecycle — how differences were flushed out

The migration ran as a Finch-controlled 1%-at-stable experiment before shipping; the compatibility issues it surfaced (“two or three”) were fixed prior to the Intent, and guard-rail metrics stayed flat on all platforms. Upstream, the crate’s XML conformance suites run “with a good pass rate”, with residual failures investigated and attributed to unused functionality (DTD parsing) “or… conflicting specifications”. Any newly discovered difference in the wild is a regression to report against crbug.com/466303347 — process on the overview.

Source: Intent to Ship (interoperability + ergonomics sections); tracking bug.

Examples — probing the differences safely

Detect parse failure structurally, never by matching error text (the text legitimately changed):

// ROBUST: structural error detection — identical across parser backends.
function parseXml(text, type = "application/xml") {
  const doc = new DOMParser().parseFromString(text, type);
  const err = doc.querySelector("parsererror");
  if (err) throw new Error("XML not well-formed"); // do NOT parse err.textContent
  return doc;
}

// FRAGILE (may break in Chrome 153): matching libxml2's message wording.
// if (err.textContent.includes("Opening and ending tag mismatch")) { … }

// XHTML named entities still resolve for the spec's DOCTYPE allowlist:
const xhtml = parseXml(
  `<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Strict//EN"
    "http://www.w3.org/TR/xhtml1/DTD/xhtml1-strict.dtd">
   <html xmlns="http://www.w3.org/1999/xhtml"><body>&nbsp;&copy;</body></html>`,
  "application/xhtml+xml");

// External entities are NOT fetched (both backends, since the separate removal):
// <!ENTITY ext SYSTEM "https://example.com/x"> …&ext;… will not load example.com.
Source: entity allowlist and static tables per xhtml_subset.cc and xml_ffi.rs; external-entity removal per the I2D&R thread.

Security and privacy

Every difference on this page trades toward a smaller attack surface: no external entity fetches (an exfiltration/SSRF-adjacent channel that also made parsing synchronous and network-dependent), no libxml2 memory-unsafety in the migrated paths, and a statically-defined entity table instead of DTD-driven entity definition. The residual risk called out by the Intent is compatibility, not security: “A very low risk of previously unforeseen compatibility issues remains.”

Source: Intent to Ship (security section); externally loaded entities I2D&R.
