Web app HTML install element

Limited availability

  • Chrome · 153 desktop (milestone listing; gated — see caveats)
  • Edge · not separately reported (Chromium-based)
  • Firefox · no signal
  • Safari · opposed

Not Baseline. The web-features id is install; webstatus.dev reports Baseline status “limited” with an empty per-browser support map (API record), and BCD has no <install> entry (all verified 2026-08-09). Vendor positions: Mozilla — no signal, WebKit — oppose (positions filed for the Web Install family).

The <install> element is a declarative HTML element that lets a page offer installation of a web app — the current site or, via attributes, an app from another origin — with no JavaScript required. It renders a user-agent-controlled button (“Install”), inherits the Permission Element (PEPC) security and styling model, and reports outcomes through a bubbling installresult event. It is the declarative counterpart of the imperative Web Install API (navigator.install()) — both share one backend for manifest fetch, validation, consent UI, and error taxonomy.

Read before relying on this — gated, incubating, and one attribute design is scheduled for removal
  • Listing vs. flag state. The milestone=153 listing files this feature under “Enabled by default”, but the Blink runtime feature InstallElement is status: {"Android": "", "default": "test"} — i.e. not enabled by default in the defaults visible in public source — at trunk and on the M153 branch (branch-heads/7978), with an origin-trial hook (origin_trial_feature_name: "InstallElement", os: win/mac/linux/chromeos) and base_feature_status: "enabled" + copied_from_base_feature_if: "overridden" (a server-side/Finch rollout path; Finch name InstallElement). The ChromeStatus API record itself still says status “Proposed”. Check availability in your build before shipping.
  • Exact enable steps. Desktop: chrome://flags/#web-app-install-element (wired to blink::features::kInstallElement, desktop-only per about_flags.cc) or launch with --enable-blink-features=InstallElement. Android is excluded ("Android": "" in the runtime-features entry). When the feature is off, <install> parses as an HTMLUnknownElement and renders its fallback children.
  • The installurl/manifestid design is end-of-life. The repo documents two attribute designs. The install-URL design (installurl + manifestid) is the origin-trial-era surface and “will reach end of life at its Origin Trial conclusion”; a Chromium TODO (crbug.com/520025525) removes the installurl code and renames manifestId to id. Write new code against the manifest-URL design (manifest + manifestid) and expect renames.
  • No formal spec yet. The ChromeStatus record has no spec link (standards maturity: “Incubation”); the normative material is the WICG/install-element explainers, the Permission Elements spec for the shared infrastructure, and the Web Install API explainer for backend behavior.

reference routes

the installresult event and InstallResultEvent

Full contract of the post-activation result event: IDL, the InstallResult enum, bubbling/delegation behavior, async dispatch, what maps to "invalid_data", and the cross-origin disclosure rationale.

why it exists

Per the explainer, acquiring web apps is fragmented and hidden: every browser has different install entry points (address-bar icons, buried menu items), users often don't know a site can be installed, developers have no standard declarative way to present an install action, and cross-origin installation (an app catalog installing apps from other sites) has no built-in platform support. beforeinstallprompt can only install the currently loaded app.

The <install> element addresses this declaratively: the user agent controls the button's text and iconography, which gives the browser a trustworthy signal of user intent and protection against spoofing — users who click a button labelled “Install” are unlikely to be surprised when an install flow begins. Basic usage needs no JavaScript, fallback content gives progressive enhancement in unsupporting browsers, and the PEPC infrastructure supplies the security, styling, and validation rules. The imperative sibling, navigator.install(), serves complementary use cases; replacing it is an explicit non-goal.

Source: manifest-URL explainer — User-Facing Problem, Goals, Non-goals; ChromeStatus API record — motivation.

Syntax

<!-- Install the current page's app. -->
<install></install>

<!-- Install a specific app by its manifest URL (current design). -->
<install manifest="https://app.example.com/manifest.webmanifest"></install>

<!-- Manifest that does not declare an `id`: supply the computed manifest id too. -->
<install manifest="https://app.example.com/manifest.webmanifest"
         manifestid="https://app.example.com/?source=catalog"></install>

<!-- Fallback content renders where the element is unsupported/disabled. -->
<install manifest="https://music.youtube.com/manifest.webmanifest">
  <a href="https://music.youtube.com/" target="_blank">Launch YouTube Music</a>
</install>

In a supporting browser the user agent replaces the element's presentation with its own localized button (“Install”, or potentially “Launch” — see activation behavior); child content is the fallback for browsers where the element is unsupported or disabled, where it parses as an unknown element and renders its children normally. The button label is localized via the inherited lang attribute (ComputeInheritedLanguage() selects the translated “Install”/“Launch” string).

Source: manifest-URL explainer — Sample Code, Element fallback content; html_install_element.cc — UpdateAppearanceTask; html_install_element.h.

manifest

Optional. URL of the web app manifest to install. On activation, the browser fetches and parses the JSON manifest directly from this URL (no intermediate page load) and presents the install consent UI (Chromium path: ElementInstallFromManifest with ManifestInstallOptions{manifest_url, manifest_id?}). May point to a different origin than the embedding page — this is the cross-origin app-catalog case. If omitted (and installurl is also absent), the currently loaded page's app is targeted. A value that does not parse as a valid URL dispatches installresult with "invalid_data" without contacting the network. Reflected by the IDL attribute manifest (nullable USVString, [CEReactions, Reflect, URL]).

Source: manifest-URL explainer — Element attributes; html_install_element.cc — OnActivated, GetCheckedManifestInstallOptions; web_install.mojom.

manifestid

Optional. The app's computed manifest id. May be omitted if and only if the JSON at manifest contains an id field; when supplied, it must match the user-agent-computed manifest id of the app being installed, otherwise the install fails with an "invalid_data" result. Setting manifestid alone (no manifest, no installurl) is a developer error: activation immediately dispatches installresult with "invalid_data". An unparsable URL value is likewise "invalid_data". Reflected by the IDL attribute manifestId; a rename of manifestId to id (matching navigator.install()) is planned in crbug.com/520025525.

Source: manifest-URL explainer — Element attributes, results note; html_install_element.cc — OnActivated (“only the manifest ID was set… error case”); html_install_element.idl.

installurl (deprecated design)

Optional. A page URL to install (origin-trial-era design; scheduled for removal). On activation the browser loads the page at installurl in the background, discovers its <link rel="manifest">, fetches and validates the manifest, then shows the install dialog (Chromium path: InstallFromElement with InstallOptions{install_url, manifest_id?}). If both installurl and manifest are set, installurl takes priority in the current implementation. Without a manifestid, the manifest reached via installurl must itself declare an id. The WICG README states this design “will reach end of life at its Origin Trial conclusion”; new code should use manifest. Reflected by the IDL attribute installURL.

Source: install-URL explainer — Element attributes; WICG/install-element README (end-of-life note); html_install_element.cc — OnActivated (“Install URL takes priority”).

the HTMLInstallElement interface

Verbatim from Chromium's IDL (trunk and the M153 branch are identical, fetched 2026-08-09) — no formal spec IDL exists yet:

[RuntimeEnabled=InstallElement, Exposed=Window]
interface HTMLInstallElement : HTMLElement {
  [HTMLConstructor] constructor();

  attribute EventHandler oninstallresult;

  // TODO(crbug.com/520025525): Remove install_url code. Also rename
  // `manifestId` to `id` to match navigator_web_install.idl.
  [CEReactions, Reflect, URL] attribute USVString? installURL;
  [CEReactions, Reflect, URL] attribute USVString? manifestId;
  [CEReactions, Reflect, URL] attribute USVString? manifest;
};

HTMLInstallElement includes InPagePermissionMixin;

The explainer's earlier sketch ([ReflectURL] attribute USVString installurl) differs from the shipped IDL above; the implementation is authoritative here. installURL, manifestId, and manifest reflect the content attributes and resolve as URLs. The element is a HTMLCapabilityElementBase subclass in Chromium (the PEPC base class), carries permission descriptor WEB_APP_INSTALLATION, and counts use via WebDX feature kDRAFT_InstallElement.

Source: html_install_element.idl (trunk); M153 branch copy; html_install_element.cc — constructor.

pre-activation validation: InPagePermissionMixin

The element includes the PEPC InPagePermissionMixin (normative home: the Permission Elements spec). Chromium's mixin IDL, verbatim:

interface mixin InPagePermissionMixin {
  readonly attribute boolean isValid;
  readonly attribute DOMString invalidReason;
  readonly attribute PermissionState initialPermissionStatus;  // "granted" | "denied" | "prompt"
  readonly attribute PermissionState permissionStatus;

  attribute EventHandler onpromptaction;
  attribute EventHandler onpromptdismiss;
  attribute EventHandler onvalidationstatuschange;
};
  • isValid — true when the element is currently a legitimate click target (visible, unoccluded, styled within bounds, past its cooldowns). A violation blocks activation and surfaces in DevTools → Issues.
  • invalidReason — the blocking reason. Strings produced by the Chromium implementation: type_invalid, illegal_subframe, illegal_sandbox (<install>-specific — any sandboxed document), unsuccessful_registration, recently_attached, intersection_changed, intersection_out_of_viewport_or_clipped, intersection_occluded_or_distorted, style_invalid, attribute_changed.
  • initialPermissionStatus / permissionStatus — reflect the backing web-app-installation permission state.
  • onvalidationstatuschange — fires when validation status changes.
  • Honest caveat: onpromptaction and onpromptdismiss are exposed by the mixin but never fired for <install> — outcomes are reported via installresult instead. A Chromium TODO (crbug.com/533049447) plans to split the mixin so these dead handlers are not exposed here.

Install-data problems (bad manifest URL, unfetchable/unparseable manifest, mismatched id) are not validation errors: they surface after activation as an "invalid_data" install result and do not disable the element — the developer can fix the markup and the user can retry.

// Observe why an <install> element is (temporarily) not clickable.
const el = document.querySelector('install');
el.addEventListener('validationstatuschange', () => {
  if (!el.isValid) {
    console.debug('install element blocked:', el.invalidReason);
    // e.g. "recently_attached" right after insertion, "style_invalid"
    // if page CSS breaks the contrast/size bounds, "illegal_subframe"
    // when not in a top-level frame.
  }
});
Source: Chromium InPagePermissionMixin IDL (defined alongside HTMLGeolocationElement); html_capability_element_base.cc — GetClickingEnabledState, DisableReasonToInvalidReasonString; Permission Elements spec — permission mixin; manifest-URL explainer — Results, errors, and debuggability.

activation behavior and lifecycle

On a trusted activation (DOMActivate) that passes the PEPC checks, Chromium's HTMLInstallElement::OnActivated picks exactly one path:

  1. No attributes → install the current document's app via the shared backend (InstallFromElement(null)). Per the backend contract, installing the current document without an explicit id requires the site's manifest to define an id; otherwise the result is a data error.
  2. installurl present (takes priority over manifest if both are set) → validate installurl/manifestid as URLs (failure → enqueue installresult "invalid_data", stop) → background-load the page, discover and validate its manifest, show the consent dialog.
  3. manifest present (no installurl) → validate URLs (failure → "invalid_data") → the browser fetches the manifest JSON directly and shows the consent dialog.
  4. Only manifestid present → immediately "invalid_data".

The consent UI shows the security-sensitive fields — app name, origin, icon — before anything is installed; user consent is always required (silent install is a stated non-goal). The outcome comes back asynchronously as one bubbling installresult event per activation: "success", "aborted" (user cancelled or a browser-side condition stopped the install), or "invalid_data".

Already-installed apps: the design allows the UA to render a “Launch” state whose activation follows launch handler algorithms — but in current Chromium the installed-state query deliberately always reports not installed while a width-based side channel (“Launch” renders slightly wider than “Install”) is mitigated (crbug.com/485281836). Expect the Install presentation everywhere for now.

Source: html_install_element.cc — DefaultEventHandler, OnActivated, UpdateAppearance; web_install.mojom — InstallOptions states; manifest-URL explainer — Activation behavior, already-installed.

Examples

An app catalog installing cross-origin apps by manifest URL, with fallback links and one delegated result listener (the UA-dispatched installresult bubbles):

<div id="app-catalog">
  <install manifest="https://suite.example/mail/manifest.webmanifest" id="mail">
    <a href="https://suite.example/mail/">Open Mail</a>
  </install>
  <install manifest="https://suite.example/tasks/manifest.webmanifest"
           manifestid="https://suite.example/tasks/?source=catalog" id="tasks">
    <a href="https://suite.example/tasks/">Open Tasks</a>
  </install>
</div>

<script>
  // Feature-detect: when the runtime feature is off, <install> is an
  // HTMLUnknownElement and only the fallback links render.
  if ('HTMLInstallElement' in window) {
    document.getElementById('app-catalog')
      .addEventListener('installresult', (event) => {
        switch (event.result) {
          case 'success':      // installed (or the UA took a reasonable action)
            console.log(`${event.target.id}: installed`);
            break;
          case 'aborted':      // user cancelled or a browser-side condition; no action needed
            break;
          case 'invalid_data': // developer error — fix manifest/manifestid and retry
            console.warn(`${event.target.id}: bad install data`);
            break;
        }
      });
  }
</script>

The inline handler form works too: <install manifest="…" oninstallresult="report(event.result)"></install>, as does the IDL property el.oninstallresult. See the event reference for the full contract.

security and privacy

  • UA-controlled rendering defeats spoofing. The page cannot change the button's text or iconography; PEPC styling restrictions (contrast, font-size bounds), occlusion detection, and post-attach/move cooldowns prevent clickjacking. Consent UI attributes the request: the user sees which site is asking and which app (name, origin, icon) would be installed.
  • Install-state is deliberately not observable. The element's rendering must not reveal whether an app is installed (width differences between “Install”/“Launch”, DOM/CSS-detectable state, SVG foreignObject readback are all called out); Chromium currently forces the not-installed presentation while mitigations are designed (crbug.com/485281836).
  • Coarse outcomes limit cross-origin probing. The installresult values are deliberately coarse — "aborted" does not distinguish user cancellation from browser-side conditions — so an installing origin learns as little as possible about install state, manifest contents, or app identity. How much to expose is a tracked open question shared with navigator.install().
  • Context gates shrink the abuse surface. Top-level frames only, no sandboxed documents, no fenced frames, and the web-app-installation permissions policy (default self) gates delegation.
  • Manifest origin checks. Sites that want installs of their app only from their own origin can inspect Fetch Metadata on manifest requests (Sec-Fetch-Dest: manifest with a non-same-origin Sec-Fetch-Site) and respond accordingly.
  • Private modes. Apps are not installable from private browsing, and failures must not reveal that private mode is the reason.
