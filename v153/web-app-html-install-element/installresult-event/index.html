the installresult event

The user agent dispatches one installresult event at an <install> element per activation, reporting the outcome of the triggered install as an InstallResultEvent whose result is "success", "aborted", or "invalid_data". UA-dispatched events bubble, so one delegated listener can serve a whole catalog. Identity: chromestatus.com/feature/5152834368700416.

Gating and churn apply

The interface is behind the same InstallElement runtime feature as the element — see the overview warn-block for enable steps and rollout state. The result set is deliberately coarse and the explainer says it “may be refined over time (e.g. narrowing "aborted" to specifically mean user cancellation)”; a Chromium TODO (crbug.com/534847491) records the same intent.

Syntax

Chromium's IDL, verbatim (no formal spec text exists yet; the explainer's WebIDL sketch matches):

enum InstallResult { "success", "aborted", "invalid_data" };

[RuntimeEnabled=InstallElement, Exposed=Window]
interface InstallResultEvent : Event {
  constructor(DOMString type, optional InstallResultEventInit eventInitDict = {});
  readonly attribute InstallResult result;
};

dictionary InstallResultEventInit : EventInit {
  InstallResult result;
};

Listen any of three ways:

el.addEventListener('installresult', (event) => { /* event.result */ });
el.oninstallresult = (event) => { /* ... */ };
<install manifest="https://app.example.com/manifest.webmanifest"
         oninstallresult="report(event.result)"></install>

constructor parameters

typeDOMString, required — the event type; the UA uses "installresult"
eventInitDictOptional InstallResultEventInit — extends EventInit (bubbles, cancelable, composed) with result, an InstallResult enum value. Script-constructed events keep the standard bubbles = false default; only UA-dispatched events set bubbles = true
Source: install_result_event.idl (including the bubbling comment).

the result attribute

Read-only; one of the three InstallResult values. Chromium maps the shared backend's WebInstallServiceResult one-to-one: kSuccess → "success", kAbortError → "aborted", kDataError → "invalid_data".

resultMeaning
"success"The app was installed. (The explainer adds that if the app was already installed, the UA should take a reasonable action, such as launching.)
"aborted"The user cancelled, or a browser-side condition prevented the install from completing. Deliberately not distinguishable — no action needed.
"invalid_data"A developer error: the element was given install data it can't act on — a malformed manifest/installurl URL or manifestid, a manifest that can't be fetched or parsed, a manifestid that doesn't match the UA-computed id, or a manifestid with nothing to install from. It does not disable the element: fix the markup and the user can retry. (An earlier design surfaced this as an install_data_invalid invalidReason and disabled the element; that was removed in favor of this event.)

Where navigator.install() rejects its promise with DOMException names, the element surfaces the same backend outcomes through this event — that is the designed division of labor.

Source: explainer — result table and invalid_data note (quoted); html_install_element.cc — ToInstallResult, ToV8InstallResult; web_install.mojom — WebInstallServiceResult.

dispatch timing and bubbling

  • Per-activation, transient. The result rides on the event, not the element, because the install flow is asynchronous — element state could be overwritten by a later attempt before a handler runs.
  • Asynchronously enqueued. Chromium enqueues the event for async dispatch (EnqueueEvent(…, TaskType::kUserInteraction)) on every outcome path — including immediate data errors — so timing stays consistent whether or not the backend was contacted.
  • Bubbles when UA-dispatched. The UA sets bubbles = true so a page with several <install> elements can subscribe once on a common ancestor and use event.target to tell them apart. Script-constructed InstallResultEvents default to bubbles = false like any other event.
  • Not cancelable, no default action. Nothing in the IDL or dispatch path sets cancelable; the event is a report, not a hook to alter the install.
  • Pre-activation failures never reach this event. PEPC presentation blockers (visibility, styling, occlusion, cooldowns, illegal contexts) prevent activation entirely and surface via isValid/invalidReason and DevTools Issues instead.
Source: html_install_element.cc — DispatchInstallResultEvent; install_result_event.idl comments; explainer — Results, errors, and debuggability.

Examples

Delegated handling for a catalog (from the explainer, verbatim pattern):

// One delegated listener on the catalog container handles every <install>
// inside it; event.target identifies which app the result belongs to.
document.getElementById('app-catalog').addEventListener('installresult', (event) => {
  console.log(`${event.target.id}: ${event.result}`);
});

Switch on the result at a single element:

const el = document.querySelector('install');
el.addEventListener('installresult', (event) => {
  switch (event.result) {
    case 'success':
      showToast('App installed — find it in your launcher.');
      break;
    case 'aborted':
      // The user cancelled, or a browser-side condition stopped the install.
      break;
    case 'invalid_data':
      // Developer error: fix the manifest / manifestid attributes and retry.
      reportError(new Error('install element given invalid data'));
      break;
  }
});

security and privacy

The result vocabulary is the disclosure boundary between the installing origin and the user's decision. "aborted" intentionally conflates user cancellation with browser-side conditions so a (possibly cross-origin) installer cannot probe why an install did not happen; how much outcome information should ultimately be exposed is an open question shared with navigator.install() (see the Web Install API explainer's privacy section). "invalid_data" reports only that the developer-supplied data was unusable — it does not reveal manifest contents, install state, or private-mode status.
