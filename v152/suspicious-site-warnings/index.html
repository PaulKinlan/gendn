Suspicious site warnings

Not a web-platform API — Chrome-only browser security UI

  • Chrome · 152 (milestone listing; Enhanced protection users)
  • Edge · not applicable (Chrome’s Safe Browsing UI)
  • Firefox · not applicable
  • Safari · not applicable

Baseline does not apply: this feature ships no web-exposed interface, so it has no web-features entry (a webstatus.dev query returns zero matches), no BCD key, no entry in Blink’s runtime_enabled_features.json5, and no MDN page (an MDN search returns no matching document) — all verified 2026-09-06. What this page documents is the observable behavior contract: when the warning triggers, what users and admins can do about it, and what — if anything — a page or site owner can observe.

Starting in Chrome 152, users enrolled in Safe Browsing > Enhanced protection who visit a site whose signals indicate it is potentially malicious get a warning in a by-passable pop-up, which must be addressed before they continue. It sits below the confidence threshold of the existing full-page red interstitials, which continue to appear on confirmed malicious sites. There is no author-facing API: the warning is browser UI, driven by Safe Browsing’s real-time URL lookup verdicts, controllable by users via their protection level and by administrators via two existing enterprise policies.

Rollout nuance — verify on your own build before relying on the fine print

The milestone=152 listing files this feature under “Enabled by default” (the listing is authoritative for gendn), and it only ever activates for users who opted into Enhanced protection. Three caveats as of 2026-09-06:

  • At Chromium trunk the gating flag is BASE_FEATURE(kSuspiciousSiteWarnings, base::FEATURE_DISABLED_BY_DEFAULT) in components/safe_browsing/core/common/features.cc — the on-by-default state on release builds is a server-side (Finch) rollout, not a compiled-in default.
  • To test deterministically, enable chrome://flags/#suspicious-site-warnings (registered for Desktop and Android in about_flags.cc, flag expiry milestone 155 per flag-metadata.json) or launch with --enable-features=SuspiciousSiteWarnings — and set Safe Browsing to Enhanced protection.
  • The ChromeStatus API record carries stale/partial metadata: status text “Proposed”, an Android-only shipping milestone (android: 152, desktop: null), while the Chromium tree contains both a desktop bubble and an Android dialog implementation. Disclosed here rather than resolved by fiat.

why it exists

Safe Browsing’s red interstitials fire on confirmed malicious sites. That leaves a gap: sites Google’s systems consider potentially malicious — signals present, confirmation absent. Enhanced protection exists precisely to close that gap: per Google’s Safe Browsing documentation, it “sends more information about your activity to Google in real time to offer stronger, more customized protection”, analyzing data from visited sites to “detect and warn you about potentially risky sites and iframes, even if Google didn’t know about them before”.

Suspicious site warnings are the visible half of that promise in Chrome 152: instead of either blocking outright or staying silent, Chrome interposes a lighter-weight, by-passable pop-up for the uncertain middle tier. The warning must be addressed before the user continues, but — unlike the interstitial — it is designed to be dismissed and remembered (a 30-day per-site bypass), because a “suspicious” verdict is expected to include false positives.

Source: ChromeStatus summary; Google Chrome Help — Safe Browsing protection levels; suspicious_site_warning_allowlist.h

there is no web-exposed API

Nothing about this feature is visible to page script, markup, or headers. The verdict is computed and consumed entirely in Chrome’s browser process; the warning renders in browser chrome (a bubble anchored to the window on desktop, a modal dialog on Android), not in the page. Evidence, each independently checkable: Blink’s runtime_enabled_features.json5 has no entry for it (it is a base::Feature in the browser-side Safe Browsing component, not a Blink runtime feature); the web-features register has no entry; and no IDL, event, header, or DOM surface appears anywhere in the implementation directories linked on this page. Consequently there is nothing for a page to feature-detect, no event on bypass, and no signal to the site that a warning was shown — the site sees an ordinary visit (or, if the user heeds the warning before commit-time content loads are consumed, an abandoned one).

Source: runtime_enabled_features.json5 (no entry, verified 2026-09-06); webstatus.dev query (zero matches); suspicious_site_ui.h

how a warning triggers — the verdict contract

the contract, verbatim

The decision point is in the real-time URL lookup service — the Safe Browsing mechanism behind Enhanced protection’s “in real time” checks. From components/safe_browsing/core/browser/realtime/url_lookup_service_base.cc at trunk (fetched 2026-09-06):

if (rt_threat_type == RTLookupResponse::ThreatInfo::SOCIAL_ENGINEERING &&
    rt_verdict_type == RTLookupResponse::ThreatInfo::WARN) {
  return base::FeatureList::IsEnabled(kSuspiciousSiteWarnings)
             ? SB_THREAT_TYPE_WARNABLE_SUSPICIOUS_SITE
             : SB_THREAT_TYPE_SAFE;
}

Read as a contract: a Safe Browsing real-time lookup response whose threat type is SOCIAL_ENGINEERING and whose verdict type is WARN (rather than DANGEROUS, which drives the interstitial path) maps to the threat type SB_THREAT_TYPE_WARNABLE_SUSPICIOUS_SITE when the feature is enabled — and is treated as SB_THREAT_TYPE_SAFE (no warning at all) when it is not. The server-side signals that produce the WARN verdict are not public; Google’s help documentation describes them only as analysis of site data to detect “potentially risky sites”. This page does not speculate about them.

Source: url_lookup_service_base.cc (verbatim); Safe Browsing protection levels

inputs: who and what is checked

Three conditions must all hold before the contract above is even evaluated:

  • Enhanced protection enrollment. The feature is defined for “users of Safe Browsing > Enhanced protection” (ChromeStatus summary). Standard-protection and no-protection users are outside its scope; real-time lookups with page-content signals are the Enhanced-protection mechanism.
  • A real-time URL lookup actually runs for the navigation and returns a ThreatInfo with the threat/verdict pair above.
  • The SuspiciousSiteWarnings feature is enabled on the client (Finch rollout in Chrome 152, or the flag/switch in the rollout note).
Source: ChromeStatus summary; url_lookup_service_base.cc; Safe Browsing protection levels

outputs: what the verdict produces

A SB_THREAT_TYPE_WARNABLE_SUSPICIOUS_SITE verdict does not block the navigation the way interstitial-class threats do. The navigation proceeds; the platform controller (desktop / Android) stages a warning for that navigation ID and shows it once the navigation commits and Safe Browsing checks complete — “while prioritizing full-page interstitials” (both controllers’ class comment, verbatim): if the same navigation also earns an interstitial, the interstitial wins. The ChromeStatus summary states the same layering from the user’s side: the pop-up warning “is in addition to the red interstitial warnings, which will continue to be shown on confirmed malicious websites.”

Source: suspicious_site_controller_desktop.h; suspicious_site_controller_android.h; ChromeStatus summary

the warning UI and the user’s choices

The warning is a bubble on desktop and a modal dialog on Android, both implemented behind the shared entry points ShowSuspiciousSiteWarning(web_contents, navigation_id) and ShowSuspiciousSiteBubble(web_contents) declared in suspicious_site_ui.h (“Implemented by platform-specific controllers”). The desktop controller exposes exactly three UI event handlers — OnBackToSafetyClicked(), OnMarkAsSafeClicked(), OnLearnMoreClicked() — plus OnBubbleDestroyed(); the Android dialog’s handlers are OnContinueButtonClicked(), OnHelpCenterLinkClicked(), and HandleBackNavigation(), with dialog dismissal routed through CloseDialog(). That is the complete choice surface.

recorded outcomes and interactions

Every warning resolves to one SuspiciousSiteWarningOutcome, and each user gesture maps to a SuspiciousSiteWarningUserInteraction — both enums are defined, verbatim below, in the allowlist header and recorded to the UMA histogram SafeBrowsing.SuspiciousSiteWarning.WarningOutcome (histograms.xml). These are internal metrics, not web-exposed values — listed because they are the authoritative statement of which endings the warning can have.

EnumValues (verbatim)
SuspiciousSiteWarningOutcomekUnknown = 0, kBypassed = 1, kAdhered = 2, kDismissedBySystem = 3
SuspiciousSiteWarningUserInteractionkUnknown = 0, kShown = 1, kMarkAsSafe = 2, kBackToSafetyButton = 3, kDismissed = 4, kManualNavigation = 5, kCloseTab = 6, kLearnMore = 7, kSystemBack = 8, kDestroyed = 9

Chrome may additionally show a HaTS satisfaction survey after a warning (feature kSuspiciousSiteWarningSurvey, disabled by default, with separate survey triggers for users who proceeded vs. heeded — features.cc).

Source: suspicious_site_warning_allowlist.h (verbatim enums); histograms.xml; features.cc

lifecycle: from verdict to outcome

  1. Stage. ShowForWebContents(web_contents, navigation_id) attaches the controller to the tab for one specific main-frame navigation ID.
  2. Defer. The controller observes the WebContents and the AsyncCheckTracker, and holds the warning “until Safe Browsing checks complete and the navigation commits, while prioritizing full-page interstitials” (class comment, verbatim on both platforms). Tab visibility changes also gate display (OnVisibilityChanged; the controller tracks an is_suspended_ state).
  3. Show. The bubble/dialog appears (ShowBubble(); interaction kShown). During the warning, the suspicious URL is tracked by the controller (current_suspicious_url_, “the suspicious URL currently added to the allowlist for this warning”).
  4. Resolve. The user heeds (kAdhered), bypasses (kBypassed — host allowlisted for 30 days), or the system dismisses the warning (kDismissedBySystem). One outcome per warning; the tracked outcome starts at kUnknown and is finalized as the user interacts.
Source: suspicious_site_controller_desktop.h; suspicious_site_controller_android.h

the 30-day local bypass allowlist

Bypassing a warning is remembered locally. The contract, from the header comment of SuspiciousSiteWarningAllowlist, verbatim: “When a user clicks ‘Mark as Safe’ (or ‘Continue anyway’) on an SSW warning, the host is added to this local allowlist for a 30-day TTL. While allowlisted, SSW warnings for that host will not be displayed.” The TTL constant is kDefaultExpirationTimeout = base::Days(30). The class API is small and host-keyed: AllowSiteForHost(host), IsSiteAllowedForHost(host), RevokeUserAllowException(host), and two Clear(…) overloads taking a time range (and optionally a pattern filter).

storage and scope

  • Keyed by host, not by full URL or origin scheme — every method takes a host string.
  • Stored in the profile’s HostContentSettingsMap: “a host is marked as allowlisted … if a dictionary value is present”, so the entry lives with the profile’s content-settings storage.
  • Auto-expiring: “expired entries are automatically filtered out by the framework via ContentSettingConstraints” — no cleanup action needed after 30 days; the warning becomes eligible again.
  • Deletable: individual revocation (RevokeUserAllowException) and time-ranged clearing (Clear(delete_begin, delete_end, …)) exist — the time-range signature matches Chrome’s browsing-data deletion pattern. Whether the entries sync across a user’s devices is not stated in these sources; treat it as undocumented.
Source: suspicious_site_warning_allowlist.h (verbatim comments and member list, fetched 2026-09-06)

what site owners can do

If Chrome shows suspicious-site warnings on your site, nothing in the page tells you so — there is no header, console message, or API (see above). The public, owner-facing paths are the standard Safe Browsing ones:

  • Check your site’s current Safe Browsing status in the Google Transparency Report site-status checker.
  • Diagnose and request review through Search Console’s Security Issues report, which is Google’s documented flow for identifying flagged content and requesting re-evaluation.
  • General background on what Safe Browsing flags and why: safebrowsing.google.com.

Honesty note: those flows are documented for Safe Browsing’s confirmed-threat listings. As of 2026-09-06, none of the public sources on this page documents a dedicated review path for the sub-threshold “suspicious” verdict specifically — whether the Search Console flow surfaces or clears it is not publicly specified. This gap is recorded rather than papered over.

Source: Google Transparency Report; Search Console security issues documentation; Google Safe Browsing

enterprise policy controls

The admin-facing surface is two existing policies, named by the ChromeStatus record as the controls for this warning. Their contracts below are quoted from the canonical policy definitions in the Chromium tree; the rendered documentation lives in the Chrome Enterprise policy list.

SafeBrowsingProtectionLevel

Controls whether Safe Browsing is on and in which mode — and therefore whether suspicious site warnings can appear at all, since they require Enhanced protection. Type int-enum; values, verbatim from the policy definition:

ValueMeaningEffect on this feature
0 — NoProtection“Safe Browsing is never active.”No suspicious site warnings (no Safe Browsing at all)
1 — StandardProtection (default)“Safe Browsing is always active in the standard mode.”No suspicious site warnings — the feature is Enhanced-protection-only
2 — EnhancedProtection“Safe Browsing is always active in the enhanced mode… requires sharing more browsing information with Google.”Suspicious site warnings active (Chrome 152+, subject to rollout)

Contract details from the same definition: if set as mandatory, users cannot change the Safe Browsing setting; it can also be set as recommended (can_be_recommended: true), leaving the user in control; unset means Standard protection with user choice. dynamic_refresh: true (applies without restart), per_profile: true.

SafeBrowsingAllowlistDomains

Excludes specific domains from Safe Browsing checks entirely — the ChromeStatus record names it as the way for admins “to exclude specific sites from triggering the warning”. Type: list of strings. The matching contract, verbatim from the policy definition: “Safe Browsing will trust the domains you designate. It won’t check them for dangerous resources such as phishing, malware, or unwanted software… This policy does not support regular expressions; however, subdomains of a given domain are allowlisted. Fully qualified domain names (FQDNs) are not required.” Example value from the definition: ["mydomain.com", "myuniversity.edu"]. Marked sensitive: true (it weakens a security boundary); dynamic_refresh: true, per_profile: true. Note the blast radius: it does not suppress only this pop-up — it turns off Safe Browsing checks (including download and password-reuse protection) for those domains.

examples

Because a page cannot trigger, detect, or demo the warning itself, the live example explores the boundary honestly — it probes every plausible place a Safe Browsing verdict might be exposed to script and demonstrates that the answer is “nothing”, with controls that prove the probing works:

Reproduce the feature state locally (test builds where the Finch rollout has not reached you):

# Enable the client-side feature explicitly, then turn on
# Enhanced protection in chrome://settings/security
chrome --enable-features=SuspiciousSiteWarnings

# or flip the flag UI equivalent:
#   chrome://flags/#suspicious-site-warnings

Enterprise: force Enhanced protection (which activates the warnings) while exempting internal domains from Safe Browsing checks — a Linux managed policies JSON example; the same two values map to Windows registry / macOS plist / Google Admin console equivalents documented in the policy list:

// /etc/opt/chrome/policies/managed/safebrowsing.json
{
  "SafeBrowsingProtectionLevel": 2,
  "SafeBrowsingAllowlistDomains": ["intranet.example.com"]
}

And the inverse — an admin who wants no suspicious-site pop-ups at all pins the protection level at or below Standard:

{
  "SafeBrowsingProtectionLevel": 1
}

security and privacy

  • The feature is itself a security control: it surfaces sub-threshold Safe Browsing verdicts that previously produced no user-visible signal, narrowing the window in which an Enhanced-protection user interacts with a probably-deceptive site.
  • Privacy cost lives in the prerequisite, not the warning. Warnings only exist under Enhanced protection, which “sends more information about your activity to Google in real time”, including “the URLs you visit and a small sample of page content” (Google’s Safe Browsing help, verbatim). The warning adds no new data collection of its own in the sources here; the verdicts arrive on the already-running real-time lookup.
  • Bypass state is stored locally in the profile’s content settings with a 30-day auto-expiry, and is revocable/clearable (see the allowlist). Interaction outcomes are recorded to UMA histograms as anonymous enumerations.
  • Enterprise allowlisting is deliberately blunt: SafeBrowsingAllowlistDomains is flagged sensitive: true in its definition because it exempts domains from all Safe Browsing checks, not just this pop-up — admins trading warning fatigue for coverage should know the trade.
  • Nothing is exposed to the web: no page can learn that a warning was shown, bypassed, or heeded (see no web-exposed API) — so the warning leaks no browsing-state signal to the site being warned about.
Source: Safe Browsing protection levels (verbatim quotes); allowlist header; SafeBrowsingAllowlistDomains.yaml
