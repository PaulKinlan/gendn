Immersive Audio Model and Formats (IAMF) decoding support

Limited availability

  • Chrome · 152 behind a flag (developer trial); listed as enabled by default from 153
  • Edge · not separately reported (Chromium-based)
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register: a webstatus.dev query returns zero matches, the ChromeStatus API record marks the Web Feature ID as “Missing feature”, and MDN browser-compat-data contains no IAMF entry (published data.json greps clean; all verified 2026-08-09).

Native decoding and playback of the Immersive Audio Model and Formats (IAMF) — the Alliance for Open Media's open, royalty-free spatial audio format — inside HTML media elements via Media Source Extensions (MSE). In Chrome 152 this is a developer trial behind a flag: the decode path is compiled in, but the runtime feature that switches it on is disabled by default. There is no new JavaScript API — existing MSE workflows gain a new supported codecs string family, iamf.*, once the feature is enabled.

Developer trial in Chrome 152 — exact enable steps
  • Behind a flag in 152, default in 153. This feature id appears in the milestone=152 listing under “In developer trial (Behind a flag)” and in the milestone=153 listing under “Enabled by default” (both verified 2026-08-09). The API surface and gating may still change before stable; do not ship production code that assumes IAMF support without feature-detecting it. The canonical gendn reference for the shipped behavior is the v153 page.
  • How to enable in 152: launch Chrome with the command-line switch --enable-features=IamfAudioDecoding. The gate is the media runtime feature kIamfAudioDecoding, declared FEATURE_DISABLED_BY_DEFAULT on the M152 branch (branch-heads/7977 media_switches.cc, fetched 2026-08-09); the two-argument BASE_FEATURE macro derives the feature string IamfAudioDecoding from the identifier (base/feature.h).
  • There is no chrome://flags entry and no Blink flag. about_flags.cc has no IAMF entry, and Blink's runtime_enabled_features.json5 contains no IAMF feature (both grepped 2026-08-09) — --enable-blink-features does not apply. The command-line switch above is the only local enable path; verify decode support in a running build via MediaSource.isTypeSupported() or chrome://media-internals.
  • Build prerequisite already met in official builds: the iamf_tools software decoder is compiled in by default (media_use_iamf_tools = true in media_options.gni, which notes “actual usage depends on the kIamfAudioDecoding feature flag”); the platform/hardware path is off (enable_platform_iamf_audio = false).
  • MSE only, no encrypted content. The IAMF path is wired through the MSE MP4 stream parser (stream_parser_factory.cc); direct <audio src> file playback has no IAMF handling in the sources read, and the decoder rejects encrypted configurations (kUnsupportedEncryptionMode in iamf_audio_decoder.cc) — no EME.
Source: chromestatus.com/feature/5113656292540416; M152 branch media_switches.cc; base/feature.h; media_options.gni — all fetched 2026-08-09.

syntax: the codecs parameter

The developer-facing string is the codecs parameter of the MSE MIME type, defined by IAMF §6.4 on top of RFC 6381:

iamf.<primary_profile>.<additional_profile>.<sub-codec codecs elements>

# e.g. IAMF (simple profile only) carrying an Opus substream:
audio/mp4; codecs="iamf.000.000.opus"

The spec's own examples: iamf.xxx.yyy.Opus, iamf.xxx.yyy.mp4a.40.2, iamf.xxx.yyy.fLaC, iamf.xxx.yyy.ipcm, where xxx/yyy are the three-digit profile fields.

fields

FieldContract
primary_profileThree decimal digits, 0–255: 0 = IA Simple Profile, 1 = IA Base Profile, 2 = IA Base-Enhanced Profile (added in IAMF v1.1.0), 3–255 reserved.
additional_profileSame three-digit mapping; an additional profile the IA Sequence complies with. A sequence complying only with the primary profile repeats it (hence iamf.000.000.opus).
sub-codec element(s)The codecs string the stream would carry in its own track, unencapsulated: opus, mp4a.40.2 (AAC-LC), fLaC, ipcm.

Chromium parser acceptance in 152

Chromium's ParseIamfCodecId accepts a string as IAMF when it starts with iamf (the bare string iamf is accepted “for test purposes only”), splits into at least four period-delimited elements, both profile fields are exactly three digits with values ≤ 255, and the lower-cased sub-codec element is exactly opus, mp4a, flac, or ipcm — with mp4a requiring the two further hex fields 40 (object type indication) and 2 (audio object type, i.e. AAC-LC). Over-long strings and anything else fail closed as an unrecognized codec id. Rejected examples: iamf.0.0.opus (profile fields must be three digits), iamf.256.000.opus (profile > 255), iamf.000.000.vorbis (sub-codec not in the accepted set), iamf.000.000.mp4a (missing 40.2). The full field-by-field walkthrough lives on the v153 codecs-parameter reference.

where the string appears

Anywhere an MP4 MIME type is declared for MSE: MediaSource.isTypeSupported(mime) support queries and MediaSource.addSourceBuffer(mime). Chromium registers the iamf and iamf.* codec patterns for both audio/mp4 and video/mp4 (stream_parser_factory.cc), so an IAMF audio track can ride alongside video or be delivered audio-only. In an un-flagged Chrome 152, isTypeSupported() returns false for these strings — AudioCodec::kIAMF support resolves through IsIamfAudioDecodingSupported(), which requires the kIamfAudioDecoding runtime feature (supported_types.cc; media_switches.cc).

Source: IAMF §6.4 Codecs Parameter String (quoted); RFC 6381; audio_codecs.cc — ParseIamfCodecId; supported_types.cc — fetched 2026-08-09.

container and playback path

IAMF reaches the renderer as an audio track inside a standard MP4 file, per IAMF §6 (ISO-BMFF IAMF Encapsulation): the track's sample description box (stsd) carries an IA Sample Entry — AudioSampleEntry('iamf') — containing a mandatory IA Configuration Box (iacb, configurationVersion = 1) that holds the sequence's descriptor OBUs. The encapsulation in spec syntax (IAMF §6.2, quoted):

class IASampleEntry extends AudioSampleEntry('iamf') {
  IAConfigurationBox ia_configuration_box;
}

class IAConfigurationBox extends Box('iacb') {
  unsigned int (8) configurationVersion = 1;
  leb128() configOBUs_size;
  unsigned int (8 x configOBUs_size) configOBUs;
}

End to end (in a 152 build with the flag enabled): the page appends MP4 segments through MSE — isTypeSupported() → addSourceBuffer() → appendBuffer(). When the declared codecs string matches iamf/iamf.*, Chromium's MSE stream-parser factory builds its MP4 stream parser with has_iamf = true (stream_parser_factory.cc). Demuxed IA Samples feed IamfAudioDecoder, a software decoder built on the bundled iamf_tools library, which renders to the device's output layout. Direct file playback (<audio src>) does not use this path — the FFmpeg demuxer has no IAMF handling in the sources read — so delivery is via MSE. A malformed or missing iacb configuration surfaces as decoder initialization failure (“requires extra_data descriptors”, kUnsupportedConfig) — the standard media error event on the element, not a silent stall.

Source: IAMF §6 ISO-BMFF encapsulation; stream_parser_factory.cc; iamf_audio_decoder.cc; media_options.gni — fetched 2026-08-09.

decoding and rendering behavior

Once a stream initializes, IamfAudioDecoder (iamf_audio_decoder.cc, trunk sources read 2026-08-09) imposes a concrete contract:

AspectBehavior (from source)
Initialization rejectsNon-IAMF codec (kUnsupportedCodec); any encrypted configuration (kUnsupportedEncryptionMode); missing descriptor extra-data (kUnsupportedConfig, “requires extra_data descriptors”)
Output formatSigned 32-bit little-endian PCM (kInt32LittleEndian is verified at init)
Output layoutsMono; stereo (including IAMF binaural — headphone rendering arrives as stereo); 5.1; 7.1
High channel counts5.1.4 and 7.1.4 map to the high-channel layouts only when kEnableHighChannelLayouts is enabled (a separate feature); otherwise the stream falls back to discrete 10- or 12-channel output
Unsupported layoutsOther IAMF layouts resolve to CHANNEL_LAYOUT_UNSUPPORTED and fail initialization

Decoder support for AudioCodec::kIAMF is compiled in with the iamf_tools build flag and gated at runtime by kIamfAudioDecoding via IsIamfAudioDecodingSupported() (supported_types.cc; media_switches.cc) — in Chrome 152 that means the enable steps above are a prerequisite for every row in this table.

examples

Feature-detect first — in an un-flagged Chrome 152 the check below fails, which is the honest signal to fall back to a flat stereo mix:

const mime = 'audio/mp4; codecs="iamf.000.000.opus"';

if (!MediaSource.isTypeSupported(mime)) {
  // Chrome 152 without --enable-features=IamfAudioDecoding lands here.
  // Serve a plain stereo (e.g. AAC or Opus) rendition instead.
  playFallbackRendition();
} else {
  const mediaSource = new MediaSource();
  const audio = document.querySelector('audio');
  audio.src = URL.createObjectURL(mediaSource);

  mediaSource.addEventListener('sourceopen', async () => {
    const sourceBuffer = mediaSource.addSourceBuffer(mime);
    const segment = await fetch('/media/immersive-segment.mp4');
    sourceBuffer.appendBuffer(await segment.arrayBuffer());
    sourceBuffer.addEventListener('updateend', () => audio.play(), { once: true });
  }, { once: true });
}

Try real bitstreams in a flagged 152 build: Chromium's own test files include an IAMF stereo and an IAMF 7.1.4 sample, and AOMedia hosts an IAMF binaural web demo (all three verified 200, 2026-08-09). The sister Chrome Platform Showcase routes for this feature (v152, v153) both returned 404 at build time (2026-08-09), so no live iframe is embedded — the snippet above and the AOMedia demo are the runnable path.

security and privacy

  • No new script-visible surface. The feature adds a codec family to the existing MSE support matrix — no new interfaces, methods, events, permissions, or storage. In the trial period, isTypeSupported() differences additionally reveal whether a user runs a flagged build — one more bit on the codec-support fingerprinting vector that already exists for every codec.
  • Parser/decoder attack surface. Support introduces a new demux+decode path fed by remote media. The decoder is the AOM reference implementation (iamf-tools) running inside Chromium's sandboxed media pipeline; malformed-stream hardening is inherited from that project rather than specified for web developers.
  • No encrypted content. Encrypted configurations are rejected at decoder initialization (kUnsupportedEncryptionMode), so IAMF playback cannot be combined with EME on this path — there is no DRM or license-handling surface to reason about.
  • Playback policies unchanged. Autoplay, volume, and output-device selection keep their existing HTML-media semantics; the decoder renders to the device-selected output layout without exposing spatial scene contents to script.
Source: iamf_audio_decoder.cc; explainer.
