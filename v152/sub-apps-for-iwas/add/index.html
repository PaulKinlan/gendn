subApps.add(install_paths)

Requests installation of one or more sub apps under the calling parent Isolated Web App. Takes relative paths to each sub app’s start HTML page, shows the user one unified consent prompt for the whole batch, then installs each entry independently — partial success is a normal outcome, reported per path.

Syntax

const response = await window.subApps.add(install_paths);
// Promise<SubAppsAddResponse> add(sequence<USVString> install_paths);

dictionary SubAppsAddResponse {
  record<USVString, USVString> installedApps;  // install path -> manifest id
  record<USVString, DOMException> failedApps;  // install path -> failure
};
Source: Blink sub_apps.idl at trunk and spec §4.1, fetched 2026-08-30

Inputs

install_paths — a sequence<USVString> of relative paths, each pointing at a sub app’s start HTML page (the page must link a web app manifest). Each path must be a valid relative path: not a valid absolute URL, starts with / but not //, non-empty, and parses against the document’s base URL. At most 20 paths per call, and the parent may hold at most 50 installed sub apps in total (spec §5.6 quotas).

Source: spec §4.1 and §5.6, fetched 2026-08-30

Outputs

A Promise<SubAppsAddResponse>. The dictionary splits per-path results so one bad entry does not fail the batch:

installedAppsrecord<USVString, ManifestId> — each successfully installed install path mapped to the sub app’s manifest id (the manifest’s id, falling back to start_url without fragment). These ids are the handles remove() takes and the keys list() returns
failedAppsrecord<USVString, DOMException> — each failed install path mapped to the DOMException naming why (see Errors)
Source: spec §4.1, fetched 2026-08-30

Errors

SecurityErrorRejects the promise: the document is not allowed to use the sub-apps policy-controlled feature
NotSupportedErrorRejects the promise: called from a sub-app document (sub apps cannot nest)
TypeErrorRejects the promise: an entry is not a valid relative path, or fails to parse against the base URL
QuotaExceededErrorRejects the promise: more than 20 paths in this call, or the call would push the parent past 50 installed sub apps
NotAllowedErrorRejects the promise: the user denied the unified installation prompt
DataErrorPer-path in failedApps: fetching/processing that sub app’s manifest failed
InvalidStateErrorPer-path in failedApps: a sub app with the same manifest id is already installed
ConstraintErrorPer-path in failedApps: scope overlap with the parent or an installed sub app, or the path points at the parent’s own manifest
OperationErrorPer-path in failedApps: the platform install failed with a system or database error
Source: spec §4.1 method steps, fetched 2026-08-30

Context and exposure

Callable only on the SubApps instance at window.subApps: [Exposed=Window, SecureContext, IsolatedContext] in Blink’s sub_apps.idl and the spec — an installed Isolated Web App on desktop Chrome, never an ordinary tab. Every call additionally requires the sub-apps policy-controlled feature (default allowlist 'none'; Permissions-Policy: sub-apps=(self) on the parent document) and rejects with NotSupportedError when called from a sub-app document — sub apps cannot manage sub apps.

Source: spec §4, §6.1; Blink IDL — all fetched 2026-08-30

Lifecycle

Path and quota validation happen up front; then, in parallel: the user agent requests consent through one unified installation dialog covering every requested sub app (spec §5.3 — one prompt, not one per app; deniable as a whole with NotAllowedError), then for each path fetches and processes the manifest, derives the manifest id, checks duplicate-id and scope constraints, and registers the sub app with the platform launcher. The promise resolves once every entry has landed in installedApps or failedApps. Enterprise policies (DefaultSubAppsWithoutPromptsSetting and the per-origin allow/block lists) can suppress the prompt. One disclosed ambiguity, preserved rather than invented: the spec’s “fetch and process the manifest” algorithm is an explicit stub (“write the ‘fetch and process the manifest’ algorithm”, Issue #2), so the detailed manifest fetching/validation rules behind the DataError path are not yet normatively defined — everything else above is specified today.

Source: spec §4.1, §5.3, §4.4 (stub); policies from the ChromeStatus record — fetched 2026-08-30

Examples

// Parent IWA document; "sub-apps" permissions policy declared
// (Permissions-Policy: sub-apps=(self) served from the Signed Web Bundle).
const { installedApps, failedApps } =
    await window.subApps.add(["/calc", "/docs"]);

// Partial success is normal: guard before using a manifest id.
const calcId = installedApps["/calc"];
for (const [path, err] of Object.entries(failedApps)) {
  console.warn(`${path} failed: ${err.name}`); // DataError, ConstraintError, ...
}

Security and privacy

The unified consent prompt names the requesting origin and shows each sub app being installed (spec §5.3); installation extends the app’s OS reach only after that express permission. The shared threat model — single origin identity, bidirectional permission inheritance, explicit consent, quota limits — is documented in the parent reference’s security section from spec §5.
