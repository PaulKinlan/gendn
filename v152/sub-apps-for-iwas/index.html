Sub apps for IWAs

Limited availability

  • Chrome · 152 (inside Isolated Web Apps; mobile unknown)
  • Edge · unknown
  • Firefox · no signal
  • Safari · no signal

This API is not Baseline and is unlikely to become Baseline in its current form: it is an Isolated Web Apps–specific API, exposed only in IsolatedContext. webstatus.dev has no web-feature entry for it (the features API returned zero results, checked 2026-08-30), BCD has no SubApps entry and no subApps member in api/Window.json (raw files checked 2026-08-30), and the ChromeStatus record reports “No signal” from Firefox and Safari.

The Sub Apps API lets a parent Isolated Web App (IWA) programmatically install, list, and remove auxiliary applications (“sub apps”) through window.subApps. Each sub app appears to the operating system as a fully distinct application — its own launcher icon, name, shelf/taskbar window, and OS integrations such as file-type associations — while sharing the parent IWA’s origin, storage, permissions, resources, and update lifecycle. A suite-style IWA (say, mail + docs + spreadsheet) can ship as one signed bundle with one install and update pipeline, yet present its modules as separate apps.

Source: Sub Apps API spec (WICG unofficial draft) §1 Introduction and WICG/sub-apps explainer, both fetched 2026-08-30; chromestatus.com/feature/6260680824061952
Isolated Web Apps only — this API does not exist on the open web

The entire API surface is annotated [SecureContext, IsolatedContext] in both the spec IDL and Blink’s sub_apps.idl at trunk (fetched 2026-08-30): window.subApps is undefined in a normal browser tab or an ordinary installed PWA. It is exposed only inside an installed Isolated Web App (Chrome ships IWAs on desktop today; mobile exposure unknown — see the compatibility table), and even there each call is further gated by the sub-apps permissions-policy feature, whose default allowlist is 'none'. The spec is a WICG unofficial draft and its “fetch and process the manifest” algorithm is still a stub (“write the ‘fetch and process the manifest’ algorithm”, Issue #2) — details may still move.

Syntax

Web IDL, verbatim from Blink’s third_party/blink/renderer/modules/subapps/sub_apps.idl at trunk (fetched 2026-08-30; extended attributes ImplementedAs/RuntimeEnabled/MeasureAs/CallWith/RaisesException elided — they are Blink plumbing, not developer surface). The spec’s IDL index matches this shape, with one divergence noted below.

[SecureContext, Exposed=Window, IsolatedContext]
partial interface Window {
  [SameObject] readonly attribute SubApps subApps;
};

dictionary SubAppsAddResponse {
  record<USVString, USVString> installedApps;
  record<USVString, DOMException> failedApps;
};

dictionary SubAppsRemoveResponse {
  sequence<USVString> removedApps;
  record<USVString, DOMException> failedApps;
};

dictionary SubAppsListResult {
  required DOMString appName;
};

[Exposed=Window, SecureContext, IsolatedContext]
interface SubApps {
  Promise<SubAppsAddResponse> add(sequence<USVString> install_paths);
  Promise<SubAppsRemoveResponse> remove(sequence<USVString> manifest_ids);
  Promise<record<USVString, SubAppsListResult>> list();
};

Divergence, disclosed: the spec types manifest ids with typedef USVString ManifestId (installedApps is record<USVString, ManifestId>, remove() takes sequence<ManifestId>); Blink’s IDL spells those positions plain USVString. The typedef is documentation-only — the wire types are identical.

Source: Blink sub_apps.idl at main and spec IDL index, both fetched 2026-08-30

Window.subApps

Read-only attribute returning the SubApps instance for the window ([SameObject] — the same object on every access, created alongside the Window per spec §3.1). It takes no inputs, never throws, and its presence is the feature-detection point: in any context that is not a secure, isolated context the attribute is not exposed at all, so test if ("subApps" in window) before use. Behind the runtime feature SubApps (status stable in runtime_enabled_features.json5 at trunk, fetched 2026-08-30); the associated chrome://flags entry from the ChromeStatus record is #enable-sub-apps. The attribute lives for the lifetime of its Window; no state transitions.

Source: spec §3 Extensions to the Window interface; runtime_enabled_features.json5; ChromeStatus API record

subApps.add(install_paths)

Full member reference: subApps.add() →

Input: a sequence<USVString> of relative paths pointing at each sub app’s start HTML page (each page must link a web app manifest). A path is a valid relative path only if it is not a valid absolute URL, starts with / but not //, is non-empty, and parses against the document’s base URL. Output: a Promise<SubAppsAddResponse>; per-path results are split across two members so one bad path does not fail the batch:

SubAppsAddResponse
installedAppsrecord<USVString, ManifestId> — maps each successfully installed install path to the sub app’s manifest id (the manifest’s id, falling back to start_url without fragment). Keep these ids — they are the handles remove() takes
failedAppsrecord<USVString, DOMException> — maps each failed install path to the DOMException naming why it failed (see the error table)

Lifecycle: the browser validates paths and quota synchronously, then, in parallel, shows one unified consent dialog covering every requested sub app (spec §5.3: one prompt, not one per app), then fetches and processes each manifest and registers each sub app with the platform launcher. Enterprise deployments can suppress the prompt via the DefaultSubAppsWithoutPromptsSetting, SubAppsWithoutPromptsAllowedForOrigins, and SubAppsWithoutPromptsBlockedForOrigins policies (named on the ChromeStatus record).

Errors (all from spec §4.1 method steps) — whole-promise rejections first, then per-path failures reported inside failedApps:

add() error contract
SecurityErrorRejects the promise: the document is not allowed to use the sub-apps policy-controlled feature
NotSupportedErrorRejects the promise: called from a sub-app document (sub apps cannot nest)
TypeErrorRejects the promise: an entry is not a valid relative path, or fails to parse against the base URL
QuotaExceededErrorRejects the promise: more than 20 paths in this call, or the call would push the parent past 50 installed sub apps (spec §5.6 limits)
NotAllowedErrorRejects the promise: the user denied the unified installation prompt
DataErrorPer-path in failedApps: fetching/processing that sub app’s manifest failed
InvalidStateErrorPer-path in failedApps: a sub app with the same manifest id is already installed
ConstraintErrorPer-path in failedApps: scope overlap, in the spec’s literal §4.1 conditions — “the scope of parentApp’s manifest is a prefix of the manifest’s scope” (the parent’s scope prefixes the NEW sub app’s scope — verbatim direction), the new scope prefixes (or is prefixed by) an already-installed sub app’s scope, or the path points at the parent’s own manifest
OperationErrorPer-path in failedApps: the platform install failed with a system or database error
Source: spec §4.1 add() method, fetched 2026-08-30

subApps.remove(manifest_ids)

Full member reference: subApps.remove() →

Input: a sequence<USVString> of manifest ids of the sub apps to uninstall — the ids add() returned in installedApps (or the keys of list()’s result). Each id must satisfy the same valid-relative-path rules as add() paths. Output: a Promise<SubAppsRemoveResponse> with removedApps (sequence<ManifestId> of uninstalled ids) and failedApps (record<USVString, DOMException>). Lifecycle: uninstallation runs in parallel with no user prompt in the spec’s steps; the sub app is removed from the system launcher and registry.

remove() error contract
SecurityErrorRejects the promise: sub-apps policy-controlled feature not allowed
NotSupportedErrorRejects the promise: called from a sub-app document
TypeErrorRejects the promise: an id is not a valid relative path or fails to parse
NotFoundErrorPer-id in failedApps: no installed sub app has this manifest id
OperationErrorPer-id in failedApps: platform uninstall failed with a system error
Source: spec §4.2 remove() method, fetched 2026-08-30

subApps.list()

Full member reference: subApps.list() →

Input: none. Output: a Promise<record<USVString, SubAppsListResult>> mapping each installed sub app’s manifest id to a SubAppsListResult whose single required member appName is the name from that sub app’s manifest. Lifecycle: reads the platform registry in parallel; no prompt. Errors: SecurityError (policy not allowed) and NotSupportedError (called from a sub-app document) reject synchronously-queued, as in the other methods; OperationError rejects the whole promise if reading the platform registry fails — there is no per-entry failure map here.

Source: spec §4.3 list() method, fetched 2026-08-30

Permissions policy: sub-apps

The API is gated by a policy-controlled feature named sub-apps with a default allowlist of 'none' — even inside an IWA, every method rejects with SecurityError unless the parent app’s document explicitly declares the policy (the spec notes user agents MAY override the default to 'self' for particular origins, for example on user decision). Concretely, the declaration is a Permissions-Policy response header on the parent document — the explainer’s own example is:

Permissions-Policy: sub-apps=(self)

In an IWA, response headers are served from the app’s Signed Web Bundle, so this header ships inside the bundle with the parent document’s response. Declaring the policy inside a sub app has no effect: sub-app documents cannot use the API at all (NotSupportedError), so sub apps cannot install further sub apps. Permission state is otherwise shared bidirectionally: any permission (camera, USB, file system…) granted to a sub app is granted to the parent and vice versa (spec §5.2).

Source: spec §6.1 Permissions Policy and §5.2 Permission Inheritance, fetched 2026-08-30

Examples

Install two sub apps, keep their manifest ids, enumerate, and offer an explicit uninstall action — adapted from the WICG explainer’s examples (fetched 2026-08-30), which use exactly this window.subApps surface:

<!-- Prerequisites: running inside an installed IWA, and the parent
     document declares the "sub-apps" permissions policy (its default
     allowlist is 'none', so undeclared = SecurityError on every call).
     type="module" gives the snippet top-level-adjacent await. -->
<button id="undo-calc" hidden>Uninstall calculator</button>

<script type="module">
// Feature-detect: only exists in an installed IWA (IsolatedContext)
if ("subApps" in window) {
  let calcId;
  try {
    // Install: relative paths to each sub app's start page.
    // One unified permission prompt covers both.
    const { installedApps, failedApps } =
        await window.subApps.add(["/calc", "/docs"]);

    // installedApps maps install path -> manifest id; keep the ids.
    // Partial success is normal: a path in failedApps has NO installedApps
    // entry, so guard before using its id.
    calcId = installedApps["/calc"];

    for (const [path, err] of Object.entries(failedApps)) {
      console.warn(`${path} failed: ${err.name}`); // e.g. DataError, ConstraintError
    }
  } catch (err) {
    // Whole-batch rejection — e.g. NotAllowedError when the user
    // declines the unified prompt. Nothing was installed.
    console.warn(`add() rejected: ${err.name}`);
  }

  // Enumerate: manifest id -> { appName }. list() can reject whole-promise
  // with OperationError (registry read failure), so it gets the same
  // controlled handling as add().
  let installed = {};
  try {
    installed = await window.subApps.list();
  } catch (err) {
    console.warn(`list() rejected: ${err.name}`);
  }
  for (const [id, { appName }] of Object.entries(installed)) {
    console.log(`${appName} (${id})`);
  }

  // If /calc was ALREADY installed, add() reported InvalidStateError in
  // failedApps and returned no id — recover it from the registry.
  // appName is the only sub-app metadata list() exposes, so match on it.
  calcId ??= Object.keys(installed)
    .find((id) => installed[id].appName === "Calculator");

  // Uninstall by manifest id — behind its OWN labelled action: consent
  // to install does not imply consent to undo it, and the spec's
  // remove() steps show no browser prompt (§4.2).
  const undo = document.querySelector("#undo-calc");
  if (calcId !== undefined) {
    undo.hidden = false;
    undo.addEventListener("click", async () => {
      if (!confirm("Uninstall the calculator sub app?")) return;
      try {
        const { removedApps, failedApps } = await window.subApps.remove([calcId]);
        console.log(`removed: ${removedApps.join(", ")}`);
        for (const [id, err] of Object.entries(failedApps)) {
          console.warn(`${id}: ${err.name}`); // e.g. NotFoundError, OperationError
        }
      } catch (err) {
        // SecurityError / NotSupportedError — EventTarget ignores an
        // async listener's promise, so catch it here.
        console.warn(`remove() rejected: ${err.name}`);
      }
    });
  }
}
</script>

Security and privacy

The spec’s §5 Security and Privacy Considerations is normative about the threat model: a sub app has no separate origin — parent and sub apps are one entity to the same-origin policy and share cookies, IndexedDB, LocalStorage, and Cache Storage (§5.1); permissions are inherited bidirectionally (§5.2); installation requires express user consent through a unified prompt naming the requesting origin (§5.3); name/icon spoofing risk is mitigated by restricting the API to isolated contexts with signature verification (§5.4); OS-integration reach is bounded by per-integration user approval (§5.5); and launcher exhaustion is bounded by the 50-installed / 20-per-prompt quotas (§5.6).

Source: spec §5, fetched 2026-08-30
