User Agent Image Replacement API

Limited availability

  • Chrome · origin trial (v152 listing) · behind UAImageReplacementAPI
  • Edge · no signal
  • Firefox · no signal
  • Safari · no signal

Chrome-only, experimental. There is no Baseline status: webstatus.dev has no matching web-features entry, BCD has no entry, and MDN's HTMLImageElement reference does not document these members (all checked 2026-08-23). The ChromeStatus API record lists Firefox, Safari and web-developer views as “No signal”.

The User Agent Image Replacement API lets a page observe when the browser replaces an image's content on the user's behalf — for example a generative-AI “virtual try-on” render substituted into a product photo. It extends HTMLImageElement with two events, uareplacestart and uareplaceend, and one read-only boolean attribute, replacedByUserAgent, so the page can adapt surrounding content (captions, zoom widgets, size labels) that only makes sense for the original image. Pages cannot trigger, prevent, or read the replacement content itself.

Origin trial — API surface may change; exact enable steps Listed under “Origin trial” for Chrome 152 in the milestone=152 listing. The explainer is an early design sketch (“It has not been approved to ship in Chrome”) — do not put this in production without a fallback. To use it:
  • Local testing: launch Chrome with --enable-blink-features=UAImageReplacementAPI. The Blink runtime feature UAImageReplacementAPI (with origin_trial_feature_name: "UAImageReplacementAPI") is defined in runtime_enabled_features.json5 (verified 2026-08-23); there is no chrome://flags entry recorded for it.
  • Origin trial: register your origin for the “UAImageReplacementAPI” trial in the Chrome Origin Trials console and serve the token in an Origin-Trial header or meta tag.
  • Feature-detect before use: if ("replacedByUserAgent" in HTMLImageElement.prototype) { … } — the members simply don't exist when the feature is off.

syntax

The complete IDL, verbatim from Chromium's html_image_element.idl (fetched 2026-08-23) — these three lines are the entire API:

// partial interface HTMLImageElement (Blink IDL, verbatim):
[RuntimeEnabled=UAImageReplacementAPI, Measure] readonly attribute boolean replacedByUserAgent;
[RuntimeEnabled=UAImageReplacementAPI] attribute EventHandler onuareplacestart;
[RuntimeEnabled=UAImageReplacementAPI] attribute EventHandler onuareplaceend;

Both events are created as plain Event instances (Event::Create in html_image_element.cc): they carry no payload, do not bubble, and are not cancelable. They are enqueued on the DOM-manipulation task source, so they fire asynchronously after the state change. Each member's contract is on its own page: replacedByUserAgent, uareplacestart, uareplaceend.

Source: html_image_element.idl; html_image_element.cc

the model: observe, don't control

The explainer frames the problem: browsers increasingly modify media on the user's behalf (its example is a generative-AI virtual try-on replacing a product photo), and surrounding author content — size labels, zoom viewers, captions — can then mislead the user. The API gives authors a coordination signal with deliberate limits (the explainer's stated non-goals):

  • No replacement-content access — the replacement may reflect user data or intent; the page never sees its pixels or source.
  • No content-driven replacement — authors cannot initiate a replacement of any kind.
  • No enumeration of replacement kinds — what feature caused the replacement is withheld (a possible privacy-reviewed future enhancement).

The observable lifecycle, verified against the Chromium implementation in html_image_element.cc: when the user agent starts a replacement (StartImageReplacement()), the element's layout disposition switches to image-replacement and a uareplacestart event is enqueued; from then on replacedByUserAgent returns true. When the substitution finishes, fails, or is reverted — the element leaves the image-replacement disposition and returns to its primary content — a uareplaceend event is enqueued and replacedByUserAgent returns false. Replacement only starts for an image that has successfully loaded (the implementation notes it “wouldn't have started image replacement if the image had not loaded/if there was an error”). Because the events are asynchronous, a script that attaches listeners late should also read replacedByUserAgent to catch a replacement that already happened.

Source: explainer — goals/non-goals + proposed approach; html_image_element.cc — StartImageReplacement / SetLayoutDisposition / ResetImageReplacement

examples

The explainer's e-commerce scenario: hide a zoom widget (which renders from the original image) while a user-agent replacement is showing, and handle the case where replacement happened before the script ran:

const imageEl = document.querySelector("img.product-view");
const zoomLens = document.querySelector(".zoom-lens");

if ("replacedByUserAgent" in HTMLImageElement.prototype) {
  // Replacement began — the zoom lens would show the wrong content.
  imageEl.addEventListener("uareplacestart", () => {
    zoomLens.style.display = "none";
  });

  // Replacement finished, failed, or was reverted — original is back.
  imageEl.addEventListener("uareplaceend", () => {
    zoomLens.style.display = "block";
  });

  // Events are async; catch a replacement that predates this script.
  if (imageEl.replacedByUserAgent) {
    zoomLens.style.display = "none";
  }
}

A document-level capturing listener for uareplacestart can track which elements are currently replaced across the whole page (the explainer suggests this pattern for analytics). No live demo is embedded: a replacement can only be initiated by browser UI acting for the user — a page cannot script it — and the Chrome Platform Showcase v152 index has no route for this feature yet (HEAD-checked 404, 2026-08-23).

security and privacy

  • Data protection: the API intentionally never exposes replacement content — the explainer encourages user agents to “prevent sensitive replacement content from being accessed by the page without explicit user intent” (it may reflect user data such as a photo of the user).
  • Anti-fingerprinting: uareplacestart/uareplaceend fire only when an actual replacement is initiated by explicit user intent or user-configured policy; per the explainer, pages “MUST NOT be able to probe for replacement capabilities” without the user actually using such a feature. The mere existence of the members reveals only that the origin trial / flag is on.
  • User-agent discretion: browsers may withhold the fact of replacement entirely when it is sensitive — authors must not assume the signal is exhaustive.
  • Accessibility interplay: when a UA replaces image content it may also override the accessible description (alt/ARIA), so assistive technologies describe the substitute rather than the original — another reason pages should not re-derive descriptions from the original image while replacedByUserAgent is true.
