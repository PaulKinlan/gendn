User Agent Image Replacement API

Limited availability — origin trial

  • Chrome · origin trial 152–157 (desktop)
  • Edge · no separate signal (Chromium-based)
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register: a webstatus.dev query returns no matching web-feature entry (checked 2026-09-06). Chrome-only, behind an origin trial; the ChromeStatus record lists Firefox and Safari positions as “No signal” and overall Chrome status as “Proposed”.

Three small additions to HTMLImageElement that let a page observe when the browser replaces an image's content on the user's behalf (for example, a generative-AI virtual try-on render substituted for a product photo): a replacedByUserAgent read-only boolean, and uareplacestart and uareplaceend events. The page cannot trigger, block, or read the replacement — it can only react, for example by hiding a zoom overlay or size caption that no longer matches what the user sees.

Origin trial — API surface may change This feature is in a Chrome origin trial from Chrome 152 to Chrome 157 (desktop; the ChromeStatus API record lists desktop milestones only). Its overall status is “Proposed” and the explainer states it “has not been approved to ship in Chrome” — names and behavior may change or the API may be withdrawn. Do not ship production code that depends on it without feature detection. Exact enable steps:
  1. Origin trial (for your site's visitors): register your origin for the “User Agent Image Replacement API” trial and serve the token with your pages — either the HTTP response header Origin-Trial: <token> or <meta http-equiv="origin-trial" content="<token>"> in the document <head> (see the origin-trials guide).
  2. Local testing: launch Chrome 152+ with --enable-blink-features=UAImageReplacementAPI. The Blink runtime feature is UAImageReplacementAPI (origin_trial_feature_name: "UAImageReplacementAPI" in runtime_enabled_features.json5, fetched 2026-09-06).
  3. No chrome://flags entry: the Intent to Experiment answers “Flag name on about://flags” with “No information provided”, and the runtime-feature entry carries no status field — so the generic “Experimental Web Platform features” flag does not enable it. Only an origin-trial token or the --enable-blink-features switch does.
  4. Feature-detect before use: if ("replacedByUserAgent" in HTMLImageElement.prototype) { … }.

why it exists

Browsers are growing features that modify media in the page on the user's behalf — the explainer's motivating example is a Chrome generative-AI feature that lets a user replace a product photo (a model wearing a jacket) with a render of themselves wearing it. The replacement happens inside browser-controlled UI; the page never initiates it and cannot see the replacement pixels. But surrounding page content can now be wrong: a “model is 6′1″ wearing size M” caption, a custom zoom lens that re-renders the original image, analytics that assume the product photo is what the user is looking at.

This API gives authors the minimal observation primitive to fix that: know when replacement starts and ends, and whether a given image is currently replaced — nothing more. The explainer records that sites affected by Chrome's image-replacement features asked for exactly this, both to avoid confusing UX and to understand how users of these features interact with their pages. Explicit non-goals: no access to the replacement media, no page-initiated replacement, and no enumeration of which replacement feature is running (left out for privacy and compatibility reasons).

Source: Explainer — introduction, user-facing problem, goals and non-goals; chromestatus.com/feature/5076374013476864.

Syntax

The shipping Chromium IDL, verbatim from html_image_element.idl (fetched 2026-09-06 — there is no formal spec IDL; the explainer describes the same three members in prose):

// partial view of interface HTMLImageElement
[RuntimeEnabled=UAImageReplacementAPI, Measure] readonly attribute boolean replacedByUserAgent;
[RuntimeEnabled=UAImageReplacementAPI] attribute EventHandler onuareplacestart;
[RuntimeEnabled=UAImageReplacementAPI] attribute EventHandler onuareplaceend;

Listener form (equivalent to the handler attributes):

img.addEventListener("uareplacestart", (event) => { /* replacement began */ });
img.addEventListener("uareplaceend",   (event) => { /* finished, failed, or reverted */ });
if (img.replacedByUserAgent) { /* currently showing substitute content */ }

Both events are plain Event objects — created with Event::Create(…), so bubbles, cancelable, and composed are all false — and are queued on the <img> element as DOM-manipulation tasks (asynchronous dispatch). The event type names uareplacestart and uareplaceend are registered verbatim in Blink's event_type_names.json5.

Source: Chromium html_image_element.idl; Chromium html_image_element.cc — StartImageReplacement, ResetImageReplacement; Explainer — proposed approach.

Members

The complete developer-facing surface is three members on HTMLImageElement, each with a full reference page:

  • replacedByUserAgent — read-only boolean; true while the element currently displays substitute content provided by the user agent. Use it for the “did replacement happen before my script ran?” check.
  • uareplacestart event (and onuareplacestart) — fired when the user agent begins substituting the image content.
  • uareplaceend event (and onuareplaceend) — fired when the substitution finishes, fails, or is reverted.
Source: Explainer — proposed approach; Chromium html_image_element.idl.

Context

Exposure: the three members live on HTMLImageElement (<img> only — not <picture>, not CSS background images), in Window contexts where HTMLImageElement is exposed. They exist only when the UAImageReplacementAPI runtime feature is enabled for the execution context — via origin-trial token or the --enable-blink-features=UAImageReplacementAPI switch (see the enable steps above); the implementation checks RuntimeEnabledFeatures::UAImageReplacementAPIEnabled(GetExecutionContext()) before dispatching either event.

Non-bubbling events: because the events are plain non-bubbling Events, a bubble-phase listener on document never sees them. To track replacements across a whole page, the explainer recommends a capturing listener on the document for uareplacestart (capture reaches the target even for non-bubbling events), then observing uareplaceend on each affected element.

What the page never learns: which browser feature performed the replacement, or the replacement pixels. In the current Chromium implementation the substitute content is presented in a user-agent shadow root containing an iframe, isolated from the page (ReplacementFrameToken() in html_image_element.cc); canvas readback of the <img> reflects the original resource. Whether pages are notified at all is user-agent (even per-feature) specific — a browser may withhold these signals when the replacement is sensitive.

Source: Chromium html_image_element.cc; Chromium runtime_enabled_features.json5; Explainer — proposed approach, privacy goals.

Lifecycle

An <img> element's replacement state, as implemented in Chromium (the explainer deliberately leaves when replacement occurs, and what ends it, to the user agent — the following traces the current implementation, fetched 2026-09-06):

  1. Normal: the element shows its own content; replacedByUserAgent is false. Replacement only ever starts from a browser feature acting on explicit user intent — never from page code, and only for an image that has loaded successfully.
  2. Replacement starts: the element's layout switches to a replacement disposition and a uareplacestart event is queued. From this point replacedByUserAgent reports true.
  3. Replaced: the substitute content renders in browser-controlled UI (a UA shadow-root iframe) in the element's place. The element's own DOM (src, currentSrc, natural sizes) still describes the original image.
  4. Replacement ends: the disposition resets and a uareplaceend event is queued; replacedByUserAgent returns to false. In the current implementation this happens when the user reverts or the feature finishes/fails, and also when the document changes under the element: removal from a connected document, moving the element to another document, or a source change (new src/srcset selection) whose URL no longer matches the replaced original or its <picture> candidate set.

Exactly which user actions or browser features trigger steps 2 and 4 is not part of the API contract — the explainer states that when replacement occurs, what ends it, and whether the page is notified at all are user-agent- and feature-specific.

Source: Chromium html_image_element.cc — StartImageReplacement, ResetImageReplacement, ResetLayoutDisposition, RemovedFrom, DidMoveToNewDocument; Explainer — proposed approach.

Errors

The API surface throws nothing and reports no error objects. Reading replacedByUserAgent is an infallible boolean getter, and the events carry no failure detail: a replacement that fails is signalled the same way as one that finishes or is reverted — a single uareplaceend event. The page cannot distinguish the three outcomes; after uareplaceend the observable truth is simply that the element is showing its own content again (replacedByUserAgent === false).

On builds where the feature is disabled (no origin-trial token, no flag — see the at-a-glance table), the three members are absent entirely: img.replacedByUserAgent is undefined, and the events never fire. That absence is the feature-detection signal, not an error.

Source: Chromium html_image_element.idl — no exceptions declared; Explainer — uareplaceend covers “finishes, fails, or is reverted”.

Examples

The explainer's worked example, verbatim: an e-commerce page disables its custom zoom lens while a virtual try-on render is displayed, because the lens would re-render the original image and confuse the user.

const imageEl = document.querySelector('img.product-view');
const zoomLens = document.querySelector('.zoom-lens');

// Listen for replacement start
imageEl.addEventListener('uareplacestart', () => {
  // Temporarily disable custom interactive zoom while substitution is in progress
  zoomLens.style.display = 'none';
});

// Listen for replacement end
imageEl.addEventListener('uareplaceend', () => {
  // Re-enable interactive zoom if replacement was reverted or canceled
  zoomLens.style.display = 'block';
});

// Check if the replacement happened before this script executed.
if (imageEl.replacedByUserAgent) {
  zoomLens.style.display = 'none';
}

Page-wide tracking with a capturing listener (the pattern the explainer recommends, needed because the events don't bubble):

document.addEventListener("uareplacestart", (event) => {
  const img = event.target;             // the replaced <img>
  img.closest("figure")?.classList.add("ua-replaced");
  img.addEventListener("uareplaceend", () => {
    img.closest("figure")?.classList.remove("ua-replaced");
  }, { once: true });
}, { capture: true });                  // capture: true is required — no bubbling
Source: Explainer — example; showcase routes HEAD-checked 2026-09-06.

Accessibility

When the user agent replaces an image's visual content, the original alt text may describe the wrong picture. The explainer says the UA may override the accessible description (alt text or ARIA attributes) so assistive technologies convey the substitute content accurately. Authors should still treat replacement as a cue to review their own adjacent text: captions, figure descriptions, and aria-describedby targets that reference the original image content are the page's responsibility, and these events are the hook for updating them.

Source: Explainer — accessibility considerations.

Security and privacy

  • Anti-fingerprinting: the explainer requires that uareplacestart / uareplaceend fire only when an actual replacement is initiated by explicit user intent or user-configured browser policy — pages MUST NOT be able to probe for replacement capability by observing side effects. A user who never invokes a replacement feature is indistinguishable from a browser without the API's triggers.
  • Replacement isolation is the feature's job, not this API's: the API only reports lifecycle transitions. For privacy-sensitive transformations (e.g. virtual try-on using the user's photo) the user agent is expected to isolate the substitute image so page scripts cannot read it — in Chromium via a UA shadow-root iframe, with canvas pixel readback reflecting only the original resource. Non-sensitive transformations (colorization, upscaling) may not need isolation; the user agent judges per feature.
  • Information can be withheld: a user agent may decline to fire these events at all when the fact of replacement is itself sensitive — the privacy goal explicitly empowers UAs to limit what the page learns per their own stance and user preferences.
  • Minimal disclosure by design: no enumeration of which replacement feature ran (a possible future, explicitly optional enhancement), no replacement media access, no page-initiated replacement.
Source: Explainer — privacy & security considerations, goals, non-goals; Chromium html_image_element.cc — UA shadow-root presentation.
