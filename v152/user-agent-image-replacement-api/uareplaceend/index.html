v152 · origin trial · htmlimageelement event

uareplaceend event

Fired at an HTMLImageElement when a user-agent content substitution finishes, fails, or is reverted — the element is showing its own image again. From this point replacedByUserAgent is false, and UI that was adjusted on uareplacestart (hidden zoom widgets, suppressed captions) can be restored.

Origin trial — may change or be removed Part of the Chrome 152 origin-trial listing for the User Agent Image Replacement API. Enable locally with --enable-blink-features=UAImageReplacementAPI or register in the Origin Trials console; see the overview's enable steps.

syntax

// Event handler IDL attribute, verbatim from Chromium html_image_element.idl:
[RuntimeEnabled=UAImageReplacementAPI] attribute EventHandler onuareplaceend;

// Usage:
imageElement.addEventListener("uareplaceend", (event) => { /* ... */ });
imageElement.onuareplaceend = (event) => { /* ... */ };
Source: html_image_element.idl

inputs

None from the page's perspective — script can neither trigger nor cancel the end of a replacement. What ends a replacement is user-agent (and feature) specific; the explainer deliberately leaves “what changes to the document cause image replacement to end” to the user agent.

Source: explainer — proposed approach

outputs

A plain Event with type "uareplaceend", targeted at the HTMLImageElement. Created with Event::Create(event_type_names::kUareplaceend) in html_image_element.cc: no payload, non-bubbling, not cancelable. The event does not distinguish finish vs. failure vs. revert — one event covers all three end reasons.

Source: html_image_element.cc; explainer

errors

There is no separate error event: a failed substitution surfaces as this same uareplaceend (the explainer: fired when the substitution “finishes, fails, or is reverted”). Listeners should treat it purely as “the original content is authoritative again”. With the runtime feature off the event never fires and onuareplaceend is absent from the prototype — feature-detect with "onuareplaceend" in HTMLImageElement.prototype.

Source: explainer — proposed approach; html_image_element.idl

context and exposure

Dispatched to HTMLImageElement in Window contexts when the UAImageReplacementAPI runtime feature is enabled (origin trial token or --enable-blink-features=UAImageReplacementAPI, per runtime_enabled_features.json5). Chrome-only; no other engine has signalled support (ChromeStatus API record).

Source: runtime_enabled_features.json5; ChromeStatus API record

lifecycle

Enqueued (asynchronously, DOM-manipulation task source) whenever the element leaves the image-replacement layout disposition: SetLayoutDisposition() fires it on any disposition change away from replacement, and ResetImageReplacement() restores the primary content — the implementation notes a valid image resource must exist, since replacement would not have started on an unloaded or errored image. Each uareplacestart is eventually paired with one uareplaceend; by the time listeners run, replacedByUserAgent already reads false.

Source: html_image_element.cc — SetLayoutDisposition / ResetImageReplacement

examples

// Restore UI that was suspended during a UA replacement.
const img = document.querySelector("img.product-view");
const zoomLens = document.querySelector(".zoom-lens");

img.addEventListener("uareplaceend", () => {
  // Original pixels are back (finished, failed, or reverted — same signal):
  zoomLens.style.display = "block";
});
Source: explainer — example (“Re-enable interactive zoom if replacement was reverted or canceled”)

security and privacy

Same posture as uareplacestart: fires only around a replacement the user (or their configured policy) actually initiated, exposes timing and target only, and may be withheld by the user agent when the replacement is sensitive — pages must not treat it as a capability probe (explainer, anti-fingerprinting).
