WebRTC Diagnostic Logging API

Limited availability

  • Chrome · 156+ on desktop (origin trial 151–156; no Android/WebView milestone recorded)
  • Edge · mirrors Chrome (BCD)
  • Firefox · not supported, no signal
  • Safari · not supported, no signal

Not on the Baseline register (no web-features entry at webstatus.dev, re-verified 2026-11-26). Shipped enabled by default on desktop in Chrome 156 (ChromeStatus 5091582546149376 records desktop 156 with no Android or WebView milestone; BCD api/RTCPeerConnection.json records Chrome 156 for all three static methods). Historically ran as a desktop origin trial (Chrome 151–156; an earlier chromestatus API snapshot accurate as of 2026-08-24 listed desktop 156 as estimate with status text “Proposed”).

The WebRTC Diagnostic Logging API lets an authorized application ask the browser to record internal WebRTC diagnostic logs for local debugging of hard-to-reproduce connectivity and media-quality issues. The app never sees the log contents — it only receives a session ID. With explicit user authorization, the collected log can also be shared with the browser vendor to help fix user-agent bugs; that share path is user-authorised and implementation-defined, and the API itself no longer carries an upload switch.

Shipped on desktop in Chrome 156 (origin trial in Chrome 150–155)

This API was in an origin trial in Chrome 150 (trial window Chrome 151–156 on desktop); it shipped enabled by default on desktop in Chrome 156 (ChromeStatus 5091582546149376; ChromeStatus records no Android or WebView milestone). The origin-trial registration and flag steps below are only needed before Chrome 156. See the current reference at Chrome 156: WebRTC Diagnostic Logging API.

  • Pre-156 origin trial (concluded): registered at developer.chrome.com/origintrials with a <meta http-equiv="origin-trial"> tag or Origin-Trial header (ChromeStatus registration id 352969620795162625), over HTTPS. (The current IDL does not itself carry a SecureContext marker on the RTCPeerConnection extension; the HTTPS requirement came from the trial, not from the interface.)
  • Collection and upload still require explicit user authorization; the authorization UI is implementation-defined (UI controls, prompts, and/or enterprise policies such as WebRtcDiagnosticLogCollectionAllowedForOrigins).

Implementation/debug note: the surface on this page is enabled by the runtime feature RTCDiagnosticLogging, which now has status: {"Android": "", "default": "stable"} in runtime_enabled_features.json5 — stable on desktop, disabled on Android — and it carries origin_trial_feature_name: RTCDiagnosticLogging. The pre-rewrite surface (navigator.rtc with promises) is what the separate RTCLegacyDiagnosticLogging feature gates, and that one is still status: experimental. So --enable-blink-features=RTCDiagnosticLogging forces the new surface on pre-156 builds, and RTCLegacyDiagnosticLogging is the flag for the old one.

Syntax

The API is exposed as a set of static methods on the RTCPeerConnection interface — synchronous calls, not the promise-returning navigator.rtc surface of the earlier draft. IDL from the WebRTC Extensions specification:

[Exposed=Window]
partial interface RTCPeerConnection {
  static DOMString startDiagnosticLogging(optional RTCDiagnosticLoggingOptions options = {});
  static undefined stopDiagnosticLogging();
  static undefined cancelDiagnosticLogging();
};

dictionary RTCDiagnosticLoggingOptions {
  record<DOMString, DOMString> metadata;
};
Source: W3C WebRTC Extensions — Diagnostic Logging (IDL); WICG WebRTC Diagnostic Logging (the incubation document, serving the same surface)

startDiagnosticLogging(options)

Begins a logging session. The user agent starts recording internal WebRTC logs, and the call returns a unique session ID (a UUID) — the only piece of diagnostic information the application ever receives. There is no promise: the returned string is the session ID. The session lives in an [[RTCDiagnosticLoggingSessionId]] internal slot on the relevant global object, which the specification initializes to null. (The W3C WebRTC Extensions specification is internally inconsistent about where this slot lives: its Internal slots section defines it on the relevant global object, while its algorithm steps reference RTCPeerConnection/[[RTCDiagnosticLoggingSessionId]]; this page follows the Internal slots definition.)

startDiagnosticLogging() — parameters, return value, exceptions
PartDetail
Parametersoptions (optional) — metadata (record of string key–value pairs): custom metadata attached to the log. This is the dictionary's only member; the earlier draft's allowUpload switch has been removed from the API.
Metadata limitsAt most 5 key–value pairs; each key and each value at most 100 characters
ReturnsDOMString — the unique session ID (the specification says it is a randomly generated UUID, and SHOULD be in RFC 4122 §4.4 form)
ExceptionsInvalidStateError — the relevant global object already has a non-null [[RTCDiagnosticLoggingSessionId]] internal slot, i.e. a session is already running. TypeError — the metadata exceeds 5 entries, or any key or value exceeds 100 characters. (The WICG incubation document's step for the metadata case still reads “return a promise rejected with a TypeError” even though this operation is now synchronous; the W3C specification already reads “throw a TypeError”.)

stopDiagnosticLogging()

Ends the session and finalizes the log file. The user agent must not log WebRTC activity for the session afterwards. The call returns undefined; whether the finalized log is ever shared with the browser vendor is a matter of user authorization and user-agent behaviour, not of an API switch.

stopDiagnosticLogging() — return value and exceptions
PartDetail
Returnsundefined
ExceptionsInvalidStateError — the [[RTCDiagnosticLoggingSessionId]] internal slot is null, i.e. no session is running

cancelDiagnosticLogging()

Stops the session and discards everything collected; the user agent must not log afterwards, and because the data is discarded it cannot be shared. The call returns undefined. Two naming mismatches are worth knowing about, and neither changes what you call: the WICG incubation document's section heading for this operation reads discardDiagnosticLogging() while its IDL — the authoritative surface, and what implementers type — declares cancelDiagnosticLogging() (the W3C specification has no discardDiagnosticLogging anywhere); and the explainer's example code uses cancelLogging(). The explainer also still names the second operation finishDiagnosticLogging() where the IDL says stopDiagnosticLogging().

cancelDiagnosticLogging() — return value and exceptions
PartDetail
Returnsundefined
ExceptionsInvalidStateError — the [[RTCDiagnosticLoggingSessionId]] internal slot is null, i.e. no session is running
Source: W3C WebRTC Extensions — Diagnostic Logging (methods); WICG explainer

What the app can and cannot see

The design deliberately keeps diagnostic content away from the application. The explainer states as an explicit non-goal that the API exposes nothing to the app beyond the session ID — the logs may contain internal information about user activity. The finished log is stored as a local file that the user can access, and any share path gives it to the user agent (the browser vendor) — never to the site. The format of the log and the mechanism by which it may be shared are intentionally unspecified; the only hard requirement is explicit user authorization. A site can attach small pieces of metadata (for example an app identifier) so a shared log can be matched to a bug report filed with the browser vendor.

Source: WICG explainer — goals, non-goals, privacy & security

Examples

// Before starting a call — begin a session (metadata only: <= 5 pairs, <= 100 chars each)
const sessionId = RTCPeerConnection.startDiagnosticLogging({
  metadata: { app: "my-call-app" },
});   // synchronous: DOMString, not a promise
// The app stores the session ID — it is the ONLY data it ever gets back.

// When the call ends normally — finalize the log locally
RTCPeerConnection.stopDiagnosticLogging();

// When the captured session is not useful — discard it entirely
RTCPeerConnection.cancelDiagnosticLogging();
Source: WICG explainer — proposed approach; W3C WebRTC Extensions — Diagnostic Logging

Browser compatibility

Browser support for all three static methods (startDiagnosticLogging_static, stopDiagnosticLogging_static, cancelDiagnosticLogging_static) is now recorded in BCD api/RTCPeerConnection.json (verified 2026-11-26, flagged experimental in BCD metadata). Note the platform scope difference: ChromeStatus and Chromium trunk restrict default enablement to desktop (no Android or WebView milestone recorded on ChromeStatus; RTCDiagnosticLogging is disabled on Android in runtime_enabled_features.json5).
