WebRTC Diagnostic Logging API

Limited availability

  • Chrome · origin trial 151–156
  • Edge · not separately reported
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register — webstatus.dev search for “webrtc diagnostic” returns no web-features entry for this API (queried 2026-08-16). Chrome-only origin trial on desktop. This feature entered the roadmap under Chrome 150; the OT stage on the chromestatus record (updated 2026-08-12) now gives the desktop trial window as Chrome 151–156 (an earlier revision of this page recorded 150–155 from July 2026 data), with the ship stage estimating desktop 156, status “Proposed”.

The WebRTC Diagnostic Logging API lets an authorized application ask the browser to record internal WebRTC diagnostic logs for local debugging of hard-to-reproduce connectivity and media-quality issues. The app never sees the log contents — it only receives a session ID it can attach to a bug report. With allowUpload and explicit user authorization, the collected log can also be shared out of band with the browser vendor.

Origin trial — API surface may move

This API is available through a desktop origin trial (window Chrome 151–156; ship estimate 156, status “Proposed”, per the chromestatus API as updated 2026-08-12). The spec draft has already moved relative to what Chrome implements — see Specification drift. To use it:

  • Register your origin for the WebRTC Diagnostic Logging API trial (Chromium trial name RTCDiagnosticLogging) at developer.chrome.com/origintrials and serve the token via a <meta http-equiv="origin-trial"> tag or the Origin-Trial response header.
  • Serve the page over HTTPS — the interface is [SecureContext].
  • For local testing, --enable-blink-features=RTCDiagnosticLogging also enables the binding: the runtime-enabled feature is RTCDiagnosticLogging (status: experimental, origin_trial_feature_name: RTCDiagnosticLogging in runtime_enabled_features.json5).
  • Enterprises can enable collection without a token via the WebRtcDiagnosticLogCollectionAllowedForOrigins policy, which the chromestatus summary names as the diagnostic-log enable path.
Source: chromestatus.com/feature/5091582546149376; Chromium runtime_enabled_features.json5; Chrome Enterprise policy list

Syntax

What Chrome ships is defined by the Chromium IDL, not the (newer) spec draft. The API hangs off Navigator as a single [SameObject] read-only rtc attribute returning an RTC instance with three asynchronous session methods. Verbatim from the three Chromium IDL files (extended attributes like CallWith/Measure elided):

// third_party/blink/renderer/modules/webrtc/navigator_rtc.idl
[ImplementedAs=RTC] partial interface Navigator {
  [SameObject, SecureContext, RuntimeEnabled=RTCDiagnosticLogging]
  readonly attribute RTC rtc;
};

// third_party/blink/renderer/modules/webrtc/rtc.idl
[Exposed=Window, SecureContext, RuntimeEnabled=RTCDiagnosticLogging]
interface RTC {
  Promise<DOMString> startDiagnosticLogging(optional RTCStartDiagnosticLoggingOptions options = {});
  Promise<undefined> finishDiagnosticLogging(optional RTCFinishDiagnosticLoggingOptions options = {});
  Promise<undefined> cancelDiagnosticLogging();
};

// third_party/blink/renderer/modules/webrtc/rtc_diagnostic_logging_options.idl
dictionary RTCDiagnosticLoggingOptions {
  record<DOMString, DOMString> metadata = {};
};
dictionary RTCStartDiagnosticLoggingOptions : RTCDiagnosticLoggingOptions {
  boolean allowUpload = false;
};
dictionary RTCFinishDiagnosticLoggingOptions : RTCDiagnosticLoggingOptions {
};
Source: Chromium navigator_rtc.idl; rtc.idl; rtc_diagnostic_logging_options.idl (all fetched 2026-08-16)

startDiagnosticLogging(options)

Begins a logging session: the user agent starts recording internal WebRTC logs for the calling context. Resolves with a unique session ID (the spec’s algorithm generates a UUID) — the only piece of diagnostic information the application ever receives.

startDiagnosticLogging() — parameters, return value, exceptions
PartDetail
Parametersoptions (optional RTCStartDiagnosticLoggingOptions, default {}) — allowUpload (boolean, default false): allow sharing the collected log with the user agent, subject to explicit user authorization; metadata (record of string key–value pairs, default {}): custom metadata attached to the log
Metadata limitsAt most 5 entries; each key and each value at most 100 characters (spec algorithm text)
ReturnsPromise<DOMString> — resolves with the unique session ID
ExceptionsPromise rejected with a TypeError if metadata exceeds 5 entries, or any key or value exceeds 100 characters

finishDiagnosticLogging(options)

Ends the session and finalizes the log. The promise resolves when the session is successfully closed; the user agent must not log WebRTC activity for the session afterwards. Takes an optional RTCFinishDiagnosticLoggingOptions (a metadata-only dictionary, same 5 × 100-character limits and TypeError rejection), so metadata can also be attached at finish time — an update relative to the July 2026 draft, whose finishDiagnosticLogging() took no arguments. If the session was started with allowUpload: true, the user agent may then upload the finalized log to a user-agent-defined endpoint — only with user authorization.

cancelDiagnosticLogging()

Stops the session and discards everything collected. The promise resolves when the session is terminated; the user agent must not log afterwards, and because the data is discarded it cannot be uploaded.

Source: WICG WebRTC Diagnostic Logging — methods and algorithms; Chromium rtc.idl

Specification drift — navigator.rtc vs RTCPeerConnection statics

The current WICG editor’s draft (fetched 2026-08-16) no longer defines the RTC interface. It moves the same three methods onto RTCPeerConnection as static members — RTCPeerConnection.startDiagnosticLogging(), .finishDiagnosticLogging(), .cancelDiagnosticLogging() — with the same three option dictionaries. Chromium main (and the origin-trial binding) still implements the navigator.rtc entry point; the Chromium IDL carries a TODO referencing crbug.com/481412281 (“Add spec link when available”). Code written against the trial should feature-detect both shapes without assuming either global exists:

const pc = globalThis.RTCPeerConnection;   // may be undefined in non-WebRTC environments
const rtcLogging =
  navigator.rtc ??                          // Chrome origin-trial surface
  (pc && "startDiagnosticLogging" in pc ? pc : null);  // current draft shape (statics)
if (!rtcLogging) {
  // Neither surface available: trial token missing, flag off, or unsupported browser.
}
Source: WICG draft — IDL index (RTCPeerConnection partial, static methods); Chromium navigator_rtc.idl

What the app can and cannot see

The design deliberately keeps diagnostic content away from the application. The explainer states as an explicit non-goal that the API exposes anything to the app beyond the session ID — the logs may contain internal information about user activity. The finished log is stored as a local file the user can access, and the optional upload path shares it with the user agent (the browser vendor) — never with the site. The log format and upload mechanism are intentionally unspecified; the hard requirement is explicit user authorization for both collection and upload. A site can attach small pieces of metadata (for example an app identifier) so a shared log can be matched to a bug report filed with the browser vendor — the chromestatus summary compares the session-ID flow to crash-report IDs.

Source: WICG explainer — goals, non-goals, privacy & security; chromestatus feature summary

Examples

// Chrome origin-trial surface (navigator.rtc)
// Before starting a call — begin a session (optionally allow upload + metadata)
const sessionId = await navigator.rtc.startDiagnosticLogging({
  allowUpload: true,
  metadata: { app: "my-call-app" },   // <= 5 pairs, <= 100 chars each
});
// The app stores the session ID — it is the ONLY data it ever gets back.

// A session ends in exactly ONE of two ways:
if (callCompletedNormally) {
  // Finalize the log locally (finish-time metadata is allowed too)
  await navigator.rtc.finishDiagnosticLogging({
    metadata: { outcome: "call-completed" },
  });
} else {
  // Discard everything collected — nothing can be uploaded afterwards
  await navigator.rtc.cancelDiagnosticLogging();
}
