WebRTC Diagnostic Logging API

Limited availability

  • Chrome · origin trial 151–156
  • Edge · not separately reported
  • Firefox · no signal
  • Safari · no signal

Not on the Baseline register (no web-features entry at webstatus.dev). Chrome-only origin trial on desktop (window: Chrome 151–156); the feature detail (chromestatus API, accurate as of 2026-08-24) estimates desktop shipping at 156 with status text “Proposed”.

The WebRTC Diagnostic Logging API lets an authorized application ask the browser to record internal WebRTC diagnostic logs for local debugging of hard-to-reproduce connectivity and media-quality issues. The app never sees the log contents — it only receives a session ID. With explicit user authorization, the collected log can also be shared with the browser vendor to help fix user-agent bugs; that share path is user-authorised and implementation-defined, and the API itself no longer carries an upload switch.

Origin trial — API surface may move

In Chrome 150 this API is available through an origin trial on desktop (trial window: Chrome 151–156; ship estimate 156, status “Proposed”, per the chromestatus API as accurate on 2026-08-24). To use it:

  • Register your origin for the WebRTC Diagnostic Logging API trial at developer.chrome.com/origintrials and serve the resulting token (<meta http-equiv="origin-trial"> tag or Origin-Trial header). The trial's registration id on ChromeStatus is 352969620795162625.
  • Serve the page over HTTPS — an origin trial requires a secure origin. (The current IDL does not itself carry a SecureContext marker on the RTCPeerConnection extension; the requirement here comes from the trial, not from the interface.)
  • Collection and upload both require explicit user authorization; the authorization UI is implementation-defined (UI controls, prompts, and/or enterprise policies).

Implementation/debug note: the surface on this page is enabled by the runtime feature RTCDiagnosticLogging, which now has status: {"Android": "", "default": "stable"} in runtime_enabled_features.json5 — stable on desktop, disabled on Android — and it carries origin_trial_feature_name: RTCDiagnosticLogging. The pre-rewrite surface (navigator.rtc with promises) is what the separate RTCLegacyDiagnosticLogging feature gates, and that one is still status: experimental. So --enable-blink-features=RTCDiagnosticLogging now forces the new surface, and RTCLegacyDiagnosticLogging is the flag for the old one.

Syntax

The API is exposed as a set of static methods on the RTCPeerConnection interface — synchronous calls, not the promise-returning navigator.rtc surface of the earlier draft. IDL from the WebRTC Extensions specification:

[Exposed=Window]
partial interface RTCPeerConnection {
  static DOMString startDiagnosticLogging(optional RTCDiagnosticLoggingOptions options = {});
  static undefined stopDiagnosticLogging();
  static undefined cancelDiagnosticLogging();
};

dictionary RTCDiagnosticLoggingOptions {
  record<DOMString, DOMString> metadata;
};
Source: W3C WebRTC Extensions — Diagnostic Logging (IDL); WICG WebRTC Diagnostic Logging (the incubation document, serving the same surface)

startDiagnosticLogging(options)

Begins a logging session. The user agent starts recording internal WebRTC logs for the calling browsing context and its descendants, and the call returns a unique session ID (a UUID) — the only piece of diagnostic information the application ever receives. There is no promise: the returned string is the session ID.

startDiagnosticLogging() — parameters, return value, exceptions
PartDetail
Parametersoptions (optional) — metadata (record of string key–value pairs): custom metadata attached to the log. This is the dictionary's only member; the earlier draft's allowUpload switch has been removed from the API.
Metadata limitsAt most 5 key–value pairs; each key and each value at most 100 characters
ReturnsDOMString — the unique session ID (the specification says it is a randomly generated UUID, and SHOULD be in RFC 4122 §4.4 form)
ExceptionsInvalidStateError — the relevant global object already has a non-null [[RTCDiagnosticLoggingSessionId]] internal slot, i.e. a session is already running. TypeError — the metadata exceeds 5 entries, or any key or value exceeds 100 characters. (The specification's step for the metadata case still reads “return a promise rejected with a TypeError” even though this operation is now synchronous; the limits are normative, the promise wording is a leftover from the pre-rewrite draft.)

stopDiagnosticLogging()

Ends the session and finalizes the log file. The user agent must not log WebRTC activity for the session afterwards. The call returns undefined; whether the finalized log is ever shared with the browser vendor is a matter of user authorization and user-agent behaviour, not of an API switch.

stopDiagnosticLogging() — return value and exceptions
PartDetail
Returnsundefined
ExceptionsInvalidStateError — the [[RTCDiagnosticLoggingSessionId]] internal slot is null, i.e. no session is running

cancelDiagnosticLogging()

Stops the session and discards everything collected; the user agent must not log afterwards, and because the data is discarded it cannot be shared. The call returns undefined. Two naming mismatches are worth knowing about, and neither changes what you call: the specification's own section heading for this operation reads discardDiagnosticLogging() while its IDL — the authoritative surface, and what implementers type — declares cancelDiagnosticLogging(); and the explainer's example code uses cancelLogging(). The explainer also still names the second operation finishDiagnosticLogging() where the IDL says stopDiagnosticLogging().

cancelDiagnosticLogging() — return value and exceptions
PartDetail
Returnsundefined
ExceptionsInvalidStateError — the [[RTCDiagnosticLoggingSessionId]] internal slot is null, i.e. no session is running
Source: W3C WebRTC Extensions — Diagnostic Logging (methods); WICG explainer

What the app can and cannot see

The design deliberately keeps diagnostic content away from the application. The explainer states as an explicit non-goal that the API exposes nothing to the app beyond the session ID — the logs may contain internal information about user activity. The finished log is stored as a local file that the user can access, and any share path gives it to the user agent (the browser vendor) — never to the site. The format of the log and the mechanism by which it may be shared are intentionally unspecified; the only hard requirement is explicit user authorization. A site can attach small pieces of metadata (for example an app identifier) so a shared log can be matched to a bug report filed with the browser vendor.

Source: WICG explainer — goals, non-goals, privacy & security

Examples

The embedded example above has not been migrated yet. Reading taken 2026-10-06: that showcase artefact still calls the pre-rewrite surface — navigator.rtc with startDiagnosticLogging / finishDiagnosticLogging / cancelDiagnosticLogging and the allowUpload option, all returning promises — so it demonstrates the earlier draft rather than the live one documented on this page. The reason it lags is structural rather than editorial: these demos live in the Chrome Platform Showcase repository, not in this one, and their migration is tracked separately. Treat the block below, not the iframe, as the reference for the current surface.

// Before starting a call — begin a session (metadata only: <= 5 pairs, <= 100 chars each)
const sessionId = RTCPeerConnection.startDiagnosticLogging({
  metadata: { app: "my-call-app" },
});   // synchronous: DOMString, not a promise
// The app stores the session ID — it is the ONLY data it ever gets back.

// When the call ends normally — finalize the log locally
RTCPeerConnection.stopDiagnosticLogging();

// When the captured session is not useful — discard it entirely
RTCPeerConnection.cancelDiagnosticLogging();
