Disable SVG filters on plugins and iFrames

Limited availability — security behavior change

  • Chrome · 150 (enabled by default)
  • Edge · not separately reported
  • Safari · equivalent restriction shipped
  • Firefox · under consideration

Not on the Baseline register — this is a security behavior restriction, not a new API, and has no web-features entry at webstatus.dev. Chrome 150 enables it by default. WebKit already ships an equivalent restriction (SVG filters disabled on plugins and cross-origin iframes, still allowed on same-origin iframes); Firefox currently applies SVG filters to all iframes and plugins and lists the change as under consideration.

Chrome 150 stops SVG reference filters from being applied to embedded plugins (for example, PDF viewers) and to cross-origin or restricted iframes (for example, sandboxed ones). When a plugin or such an iframe would be painted with an SVG filter effect, the effect tree is traversed to find the highest ancestor without SVG filters, and that ancestor’s effect is applied instead.

Behavior change — embedded content may render differently

This removes a capability rather than adding one. If your page applies filter: url(…) effects to (an ancestor of) a plugin, a cross-origin iframe, or a sandboxed iframe, those filters silently stop affecting that embedded content in Chrome 150:

  • The change targets SVG reference filters (filter values that reference a <filter> element). Painting falls back to the highest ancestor effect without SVG filters.
  • Same-origin, unrestricted iframes are not affected — WebKit’s shipped restriction draws the same line.
  • There is no opt-out flag recorded on ChromeStatus; the TAG-review field notes this is “disabling one we perhaps should not have supported”.
Source: chromestatus.com/feature/5117170452398080; w3c/csswg-drafts#13846; WebKit standards-positions#654

What changed, and why

SVG filters can arbitrarily manipulate the pixels of whatever they are applied to. Applied to an embedded document the embedding page cannot otherwise read, that power enables two documented attack classes:

  • SVG clickjacking — dynamic SVG filters disguise cross-origin content (redrawing it as something innocuous) so users are manipulated into clicks they would not otherwise make. Described in the December 2025 “SVG clickjacking” write-up cited by the ChromeStatus motivation.
  • Pixel-timing side channels — filter painting time can depend on the pixel values being filtered, letting an attacker reconstruct protected content by timing paint operations (the “Pixel Perfect Timing Attacks with HTML5” technique).

The proposed normative rule (from the spec pull request): user agents must not apply SVG reference <filter> elements to cross-origin/restricted iframes or web plugins because of their ability to arbitrarily manipulate pixels. As of 2026-07-26 the pull request is not yet merged into the published Filter Effects editor’s draft, which is why ChromeStatus records the standards status as “Proposed”.

Source: ChromeStatus motivation; SVG clickjacking (lyra.horse, 2025-12); Pixel Perfect Timing Attacks with HTML5 (Black Hat US-13); w3c/csswg-drafts#13846

Syntax

No new syntax is introduced. The restriction changes how one existing class of filter values behaves on embedded content. The filter property grammar from Filter Effects Module Level 1:

filter: none | <filter-value-list>

<filter-value-list> = [ <filter-function> | <url> ]+

The <url> alternative is a filter reference — “a filter reference to a <filter> element. For example url(commonfilters.svg#filter)”. It is this reference-filter class that Chrome 150 stops applying to plugins and cross-origin/restricted iframes. <filter-function> values (blur(), grayscale(), and friends) are fixed-function shorthands defined by the same specification and are not named by the proposed rule, which is scoped to SVG reference filters.

Source: Filter Effects Module Level 1 — the filter property (grammar and <url> definition quoted verbatim); scope of the rule from w3c/csswg-drafts#13846

Examples

The pattern the restriction defuses — an SVG reference filter used to disguise a cross-origin frame:

<svg width="0" height="0" aria-hidden="true">
  <filter id="disguise">
    <!-- feColorMatrix / feComponentTransfer / feDisplacementMap ...
         arbitrary per-pixel rewriting of whatever this filter is applied to -->
  </filter>
</svg>

<style>
  .overlay { filter: url(#disguise); }
</style>

<!-- Before Chrome 150: the cross-origin frame is repainted through #disguise.
     From Chrome 150: the reference filter is NOT applied to this iframe; painting
     falls back to the highest ancestor effect without SVG filters. -->
<iframe class="overlay" src="https://bank.example/transfer" title="example"></iframe>
Source: composed from the Filter Effects reference-filter syntax and the behavior described on chromestatus.com/feature/5117170452398080; attack shape from the SVG clickjacking write-up
