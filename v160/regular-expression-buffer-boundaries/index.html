Regular Expression Buffer Boundaries

Chrome 160 enables the TC39 Stage 3 RegExp buffer boundary assertions \A, \z, and \Z in Unicode-mode (u or v flag) regular expressions. They match the start of the entire input, the exact end of the input, and the end of the input before an optional trailing line terminator sequence, regardless of whether the m (multiline) flag is set.

Chrome 160 details & Unicode-mode requirement

In Unicode-aware mode (u or v flag), the TC39 proposal specification defines three zero-width Assertion escapes equivalent to RegExp modifier expressions:

  • \A — synonym for (?-m:^): matches only at index 0 of the input string, even under /m.
  • \z — synonym for (?-m:$): matches only at the exact end of the input string, even under /m.
  • \Z — synonym for (?=(?:\r\n|\n|\r|\u2028|\u2029)?(?-m:$)): matches at the end of the input string or immediately before a single trailing line terminator (including \r\n).

Annex B trap outside u/v mode: Without the u or v flag, ECMA-262 Annex B parses \A, \z, and \Z as legacy identity escapes matching the literal characters "A", "z", and "Z" without throwing a SyntaxError. None of the three escapes are valid inside a character class ([\A] throws a SyntaxError under u/v).

// Feature detection: Unicode-mode compilation throws SyntaxError on unsupported engines.
function supportsRegExpBufferBoundaries() {
  try {
    return new RegExp("\\Aok\\Z", "u").test("ok\r\n");
  } catch {
    return false;
  }
}

// Mix buffer-start (\A) with line-start (^) under /mu:
const re = /\A#!.*|^\s*\/\/.*/gmu;
re.exec("#!/usr/bin/env node\n  // comment"); // matches hashbang at start of buffer, then line comments

// Caution: omitting `u` or `v` silently falls back to Annex B identity escapes!
/\A/.test("A"); // true (matches literal "A", NOT start of input)
