Deprecate and remove WebRTC peer connection method

Removes the legacy, non-standard RTCPeerConnection.createDTMFSender() method in Chrome 160 across desktop, Android, and Android WebView as part of Interop 2026. Applications sending DTMF keypad tones must migrate to the standards-compliant RTCRtpSender.dtmf attribute on an audio RTCRtpSender.

Removed in Chrome 160 (non-standard legacy method) — replacement RTCRtpSender.dtmf is Baseline Widely available since 2022-07-15

  • Chrome · Removed in 160 (added in 27; replacement RTCRtpSender.dtmf since 66)
  • Edge · Chromium-based (removed with 160; replacement since 79)
  • Firefox · Never implemented (replacement RTCRtpSender.dtmf since 52)
  • Safari · Never implemented (replacement RTCRtpSender.dtmf since 13.1)

RTCPeerConnection.createDTMFSender() was never part of W3C WebRTC 1.0 and was never implemented in Firefox or Safari (BCD api/RTCPeerConnection.json). The standard replacement RTCRtpSender.dtmf is supported in Chrome 66+, Edge 79+, Firefox 52+, and Safari 13.1+ (BCD api/RTCRtpSender.json; base webrtc is Baseline Widely available since 2022-07-15 per webstatus.dev, checked 2026-11-24).

Deprecated & removed in Chrome 160

RTCPeerConnection.prototype.createDTMFSender() is removed starting in Chrome 160 on Windows, macOS, Linux, ChromeOS, Android, and Android WebView. Calling pc.createDTMFSender(track) now throws TypeError: pc.createDTMFSender is not a function.

  • Migration path: Replace pc.createDTMFSender(audioTrack) with sender.dtmf, where sender is the RTCRtpSender returned by pc.addTrack(audioTrack, stream), pc.addTransceiver("audio").sender, or pc.getSenders().find((s) => s.track === audioTrack).
  • Verify before rollout: Audit third-party WebRTC SDKs and telephony/IVR clients against Chrome 160; see the Chromium release schedule and UseCounter popularity timeline.

why it was removed

RTCPeerConnection.createDTMFSender(track) dates back to an early pre-1.0 WebRTC draft shipped in Chrome 27. The finalized W3C WebRTC 1.0 specification moved DTMF sending from a factory method on RTCPeerConnection to the read-only dtmf attribute on each audio RTCRtpSender. Blink remained the only major browser engine exposing createDTMFSender(); internally, Chromium’s own RTCPeerConnection::createDTMFSender() simply scanned getSenders() for the track and returned found_rtp_sender->dtmf(). Removing it in Chrome 160 aligns Blink with Firefox, Safari, and the Interop 2026 webrtc/historical.html test suite.

Source: ChromeStatus motivation (5160724576993280); Blink rtc_peer_connection.cc; WPT webrtc/historical.html.

Syntax

Removed legacy Blink WebIDL (rtc_peer_connection.idl) alongside the standard W3C WebRTC 1.0 replacement (rtc_rtp_sender.idl and rtc_dtmf_sender.idl):

// REMOVED in Chrome 160 (legacy Blink-only, non-standard)
partial interface RTCPeerConnection {
  RTCDTMFSender createDTMFSender(MediaStreamTrack track);
};

// STANDARD REPLACEMENT (W3C WebRTC 1.0)
partial interface RTCRtpSender {
  readonly attribute RTCDTMFSender? dtmf;
};

[Exposed=Window]
interface RTCDTMFSender : EventTarget {
  undefined insertDTMF(DOMString tones,
                       optional unsigned long duration = 100,
                       optional unsigned long interToneGap = 70);
  attribute EventHandler ontonechange;
  readonly attribute boolean canInsertDTMF;
  readonly attribute DOMString toneBuffer;
};

This reference covers the removed method (RTCPeerConnection.createDTMFSender()), the standard migration target (RTCRtpSender.dtmf), and the shared RTCDTMFSender interface.

Source: W3C WebRTC 1.0 — Peer-to-peer DTMF; Blink rtc_peer_connection.idl; Blink rtc_rtp_sender.idl; Blink rtc_dtmf_sender.idl.

Removed: RTCPeerConnection.createDTMFSender()

Pre-160 inputs & outputs. Accepted a single MediaStreamTrack (must have track.kind === "audio" and already belong to one of the connection’s RTCRtpSender objects) and returned the sender’s RTCDTMFSender. If the connection was closed it threw InvalidStateError; if track.kind !== "audio", if no matching RTCRtpSender existed, or if no DTMF sender could be created, it threw SyntaxError.

Chrome 160 behavior. "createDTMFSender" in RTCPeerConnection.prototype is false and pc.createDTMFSender is undefined. Any unmigrated call to pc.createDTMFSender(track) throws a synchronous TypeError.

Source: Blink RTCPeerConnection::createDTMFSender; WPT webrtc/historical.html.

Standard replacement: RTCRtpSender.dtmf

Inputs & receiver. Read-only attribute accessed directly on an RTCRtpSender instance returned by pc.addTrack(track, ...streams), pc.addTransceiver("audio").sender, or pc.getSenders(). Takes no parameters.

Outputs & lifecycle. Returns the sender’s RTCDTMFSender when the sender’s media kind is "audio", or null for video senders (and senders created without an audio kind). Unlike the removed factory method, sender.dtmf is available immediately on the RTCRtpSender and stays bound to that sender across sender.replaceTrack() transitions.

Source: W3C WebRTC 1.0 — RTCRtpSender.dtmf; MDN RTCRtpSender.dtmf.

RTCDTMFSender interface

Members, inputs, outputs, and lifecycle. Both the removed method and RTCRtpSender.dtmf yield the same RTCDTMFSender object, transmitting RFC 4733 / RFC 7874 telephone-event packets over the audio RTP stream:

RTCDTMFSender members and contracts (from W3C WebRTC 1.0 §7)
MemberInputs / typeOutputs & behavior
insertDTMF(tones, duration, interToneGap)tones: string of 0–9, A–D (a–d uppercased), #, *, , (2 s pause); duration: 40–6000 ms (default 100, clamped); interToneGap: ≥30 ms (default 70, clamped)Returns undefined; replaces any queued toneBuffer and begins asynchronous playout (passing "" clears pending tones)
canInsertDTMFreadonly booleantrue only when the sender has an active audio track, is sending, and a telephone-event payload type has been negotiated in SDP

Source: W3C WebRTC 1.0 — RTCDTMFSender; RFC 7874.

Errors and migration pitfalls

  • TypeError on Chrome 160+: calling pc.createDTMFSender(track) throws TypeError because createDTMFSender no longer exists on RTCPeerConnection.prototype.
  • null on video senders: RTCRtpSender.dtmf returns null (never throws) for non-audio senders; guard if (!sender?.dtmf) before calling insertDTMF().
  • InvalidStateError on insertDTMF(): thrown synchronously if dtmf.canInsertDTMF is false (for example before ICE/SDP negotiation completes, if the audio transceiver direction is "recvonly"/"inactive", or if the peer did not negotiate telephone-event).
  • InvalidCharacterError on insertDTMF(): thrown synchronously if tones contains characters outside 0-9, A-D, a-d, *, #, and ,.
Source: W3C WebRTC 1.0 — insertDTMF(); WPT webrtc/historical.html.

Context and exposure

RTCPeerConnection, RTCRtpSender.dtmf, and RTCDTMFSender are exposed in Window contexts only (not Web Workers). Acquiring a microphone track via navigator.mediaDevices.getUserMedia({ audio: true }) requires a secure context and user permission; reading sender.dtmf and calling insertDTMF() require no extra permissions once an audio sender is active.

Source: Blink rtc_rtp_sender.idl; Blink rtc_dtmf_sender.idl.

Examples

Migrating from pc.createDTMFSender() to RTCRtpSender.dtmf

// BEFORE (removed in Chrome 160 — throws TypeError; never worked in Firefox/Safari):
// const dtmf = pc.createDTMFSender(audioTrack);

// AFTER (standard W3C WebRTC 1.0 — works in Chrome 66+, Edge 79+, Firefox 52+, Safari 13.1+):
const pc = new RTCPeerConnection();
const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
const [audioTrack] = stream.getAudioTracks();

const sender = pc.addTrack(audioTrack, stream);
const dtmf = sender.dtmf;

// Or, if looking up an existing sender by track:
function getDtmfSenderForTrack(peerConnection, track) {
  if (track.kind !== "audio") return null;
  const match = peerConnection.getSenders().find((s) => s.track === track);
  return match?.dtmf ?? null;
}

if (dtmf) {
  dtmf.ontonechange = (event) => {
    console.log(event.tone ? `Playing tone ${event.tone}` : "DTMF playout complete");
  };

  // Call after SDP negotiation completes and telephone-event is active
  if (dtmf.canInsertDTMF) {
    dtmf.insertDTMF("1234#*", 120, 70);
  }
}
Source: W3C WebRTC 1.0 — DTMF example; MDN RTCRtpSender.dtmf.

Security and privacy

Removing RTCPeerConnection.createDTMFSender() introduces no security or privacy risks (ChromeStatus 5160724576993280) and reduces Chromium-only attack surface and browser fingerprinting divergence by matching Firefox and Safari’s RTCPeerConnection.prototype surface. The replacement RTCRtpSender.dtmf transmits DTMF telephone-event packets over the existing SRTP-encrypted audio session (RFC 7874) with no additional permissions or network exposure.

Source: ChromeStatus security_risks (5160724576993280); W3C WebRTC 1.0 — Peer-to-peer DTMF.
