CSS color-mix() with one or more colors

Extends the CSS color-mix() functional notation from exactly two colors to a comma-separated list of one or more <color> items, each with an optional <percentage [0,100]>. Passing three or more colors folds them left to right without manual nested color-mix() math, passing a single color converts it into the interpolation color space (and optionally scales its alpha), and percentages totaling less than 100% make the result partially transparent.

Limited availability — color-mix() with 1 or 3+ colors ships in Firefox 150 and Safari 27, with Chrome 161 closing the interop gap (two-color color-mix() is Baseline Widely available since 2025-11-09)

why it exists

Previously, color-mix() accepted strictly two color arguments. Blending three or more colors required nested color-mix() calls where each inner call collapsed into a single operand of the outer call, forcing authors to compute non-intuitive compound percentages (for example, an equal three-way mix of red, lime, and blue required color-mix(in srgb, color-mix(in srgb, red, lime), blue 33.3333%)). Meanwhile, converting a single token into a specific interpolation color space or applying an alpha multiplier required either a dummy transparent second operand or relative color syntax. Allowing a comma-separated list of one or more <color> items matches Firefox 150 and Safari 27 and simplifies multi-stop palette blending, color-space conversion, and Canvas 2D color styling.

Source: ChromeStatus summary (5009529854099456); w3c/csswg-drafts#11530; w3c/csswg-drafts#12234.

Syntax

Formal CSS value-definition grammar from CSS Color Module Level 5 §3 (the # multiplier accepts one or more comma-separated color-percentage items, replacing the legacy two-argument form; <color-interpolation-method>? defaults to in oklab with shorter hue for polar spaces):

<color-mix()> = color-mix( <color-interpolation-method>? , [ <color> && <percentage [0,100]>? ]# )

<color-interpolation-method> =
  in [ <rectangular-color-space> | <polar-color-space> <hue-interpolation-method>? | <custom-color-space> ]

<rectangular-color-space> =
  srgb | srgb-linear | display-p3 | display-p3-linear | a98-rgb | prophoto-rgb | rec2020 | lab | oklab | xyz | xyz-d50 | xyz-d65

<polar-color-space> = hsl | hwb | lch | oklch
<hue-interpolation-method> = [ shorter | longer | increasing | decreasing ] hue

Within each list item, the <color> and optional <percentage [0,100]> may appear in either order (red 20% or 20% red). When <color-interpolation-method> is omitted, the leading comma is also omitted (for example, color-mix(red, green 20%, blue) is equivalent to color-mix(in oklab, red, green 20%, blue)).

This reference covers all three parts of the Chrome 161 variadic color-mix() contract: variadic color lists and left-to-right pairwise folding, single-color conversion and alpha scaling, and variadic percentage normalization.

Source: CSS Color 5 §3 color-mix(); CSS Color 5 §3.1 Colorspace for mixing.

Variadic color list & left-to-right pairwise folding

Inputs. Two or more comma-separated [ <color> && <percentage [0,100]>? ] items inside color-mix(), plus an optional <color-interpolation-method> (defaulting to in oklab; polar spaces default to shorter hue).

Outputs & folding algorithm. After percentage normalization yields normalized weights and a leftover percentage, CSS Color 5 §3.3 evaluates N ≥ 2 colors by folding from left to right using an item stack:

  1. Push the normalized items onto item stack with the first argument on top.
  2. While item stack has 2 or more items: pop the top two items a and b in order, compute combined = a.percentage + b.percentage, and interpolate a and b in the target color space (per CSS Color 4 §13 Color Interpolation) with progress b.percentage / combined if combined > 0, or 0.5 if combined == 0.
  3. Push the resulting intermediate color back onto item stack with weight combined, and repeat until one item remains.
  4. Multiply the sole remaining color’s alpha channel by alpha mult = 1 - leftover and return that <color>.

Rectangular vs. cylindrical polar order dependence. In rectangular orthogonal spaces (srgb, srgb-linear, display-p3, display-p3-linear, a98-rgb, prophoto-rgb, rec2020, lab, oklab, xyz*), the fold reduces to an order-independent weighted average: color-mix(in srgb, red, lime, blue) produces color(srgb 0.333333 0.333333 0.333333) regardless of argument order. In cylindrical polar spaces (hsl, hwb, lch, oklch), however, argument order changes the result because pairwise hue interpolation (shorter, longer, increasing, decreasing) depends on the intermediate hue produced by the preceding pair — for example, color-mix(in oklch, red, lime, blue) computes to a different hue than color-mix(in oklch, blue, red, lime).

Source: CSS Color 5 §3.3 Calculating the Result of color-mix(); CSS Color 4 §13 Color Interpolation.

Single-color form — color-space conversion & alpha scaling

Inputs. Exactly one [ <color> && <percentage [0,100]>? ] item in color-mix(), with an optional <color-interpolation-method> (defaulting to in oklab).

Outputs. Per CSS Color 5 §3.3 and w3c/csswg-drafts#12234, when the normalized item list has length 1, color-mix() converts that sole color directly into the interpolation color space and multiplies its alpha channel by alpha mult = 1 - leftover:

  • No percentage (or 100%): leftover is 0%, so alpha mult is 1. For example, color-mix(in oklch, teal) computes to the exact same color as oklch(from teal l c h), and color-mix(in hsl, teal) converts teal into HSL.
  • Percentage below 100%: leftover is 100% - p, so the resulting color’s alpha is multiplied by p / 100%. For example, color-mix(in srgb, red 40%) computes to color(srgb 1 0 0 / 0.4) — replacing the older two-color color-mix(in srgb, red 40%, transparent) idiom.
  • 0% single color: color-mix(in srgb, red 0%) is valid and produces a fully transparent color (alpha = 0) in the target space.
Source: CSS Color 5 §3.3; w3c/csswg-drafts#12234; Blink css_color_mix_value.cc.

Variadic percentage normalization

Inputs & outputs. Every color-mix() call runs CSS Values 5 §6.1 normalize mix percentages with force normalization = true across all N ≥ 1 items (implemented in Blink’s CSSColorMixValue::NormalizeMixPercentages()):

Variadic color-mix() percentage normalization cases (CSS Values 5 §6.1 + CSS Color 5 §3.3)
Input patternNormalized weights & leftoverExample & computed output
All percentages omittedEach of the N colors receives 100% / N; leftover = 0% (alpha mult = 1)color-mix(in srgb, red, lime, blue) → 1/3 each → color(srgb 0.333333 0.333333 0.333333)
Partial percentages, specified sum < 100%Remaining 100% - specified sum splits evenly across omitted items; leftover = 0%color-mix(in srgb, red 20%, lime, blue) → 20% / 40% / 40%, opaque
Partial percentages, specified sum ≥ 100%specified sum clamps to 100%, so every omitted item receives 0%; specified weights scale down by 100% / totalcolor-mix(in srgb, red 60%, lime 60%, blue) → blue gets 0%; result is 50% red + 50% lime = color(srgb 0.5 0.5 0)

Note the all-0% behavior defined in w3c/csswg-drafts#14013 and CSS Color 5 §3.3: unlike legacy two-color documentation (including the current MDN color-mix() page), specifying 0% for every color is valid and folds left to right at progress 0.5 with final alpha 0.

Source: CSS Values 5 §6.1; CSS Color 5 §3.2; w3c/csswg-drafts#14013; Blink css_color_mix_value.cc.

Errors, validation, and progressive-enhancement fallbacks

  • Parse-time invalidation (literal range & empty list): Literal percentages below 0% or above 100% (for example, color-mix(in srgb, red 120%, lime, blue) or color-mix(in srgb, red -10%, lime, blue)), zero color arguments (color-mix(in srgb)), or a trailing comma are invalid at parse time; the CSS declaration is dropped and CSS.supports() returns false.
  • calc() percentage clamping at computed-value time: Per CSS Values 4 numeric function clamping and Blink’s ResolvePercentage(), math functions such as calc(120%) or calc(-10%) are accepted at parse time and clamped to [0%, 100%] before normalization rather than invalidating the declaration.
  • Older browsers (Chrome ≤160 without flag): Browsers that only support two-color color-mix() reject any 1-color or 3+-color color-mix() declaration at parse time. Always list a two-color nested fallback (or relative color fallback) before the variadic declaration, or guard enhancements with @supports (color: color-mix(in oklab, red, green, blue)) and @supports (color: color-mix(in oklab, red)).
Source: CSS Color 5 §3; Blink css_color_mix_value.cc; WPT color-valid-color-mix-function.html.

Context, exposure, and Canvas 2D

Variadic and single-color color-mix() values work anywhere CSS accepts a <color> — style rules, CSS custom properties (including @property with syntax: "<color>"), SVG paint attributes/properties, and CSS.supports() — with no secure context, permission, or user activation required. They also work in HTML Canvas 2D fillStyle and strokeStyle on both the main thread and inside Web Workers via OffscreenCanvas (for example, assigning ctx.fillStyle = "color-mix(in srgb, red, lime, blue)" parses and serializes to "color(srgb 0.333333 0.333333 0.333333)"). CSS Typed OM color objects remain gated behind a separate experimental flag (CSSColorTypedOM).

Source: CSS Color 5 §3; Blink style_color.cc; Blink runtime_enabled_features.json5.

Resolution timing, serialization, and animation

Computed vs. used value. When every color operand in color-mix() can be resolved independently of the element’s color property, the expression resolves eagerly at computed-value time to a single color in the interpolation color space. When an operand depends on currentcolor (or another unresolved color value), Blink retains an internal StyleColor::UnresolvedColorMix value at computed-value time so inheritance and dynamic color changes update descendants correctly, resolving channels at used-value time.

Serialization. Per CSSColorMixValue::CustomCSSText() and w3c/csswg-drafts#14465, default in oklab (with shorter hue) is omitted from specified-value serialization, and literal percentages are omitted only when all N items equal 100% / N (equal percentages above 100% / N such as red 75%, blue 75% are preserved in serialization to match WPT and other engines). When a specified percentage contains a non-literal expression like calc(), percentages serialize as specified.

Transitions & animations. CSS transitions and animations interpolate the resulting computed colors as normal <color> values; the variadic color-mix() notation itself introduces no special interpolation lifecycle.

Source: CSS Values 5 §6.2 Mix Resolution; Blink css_color_mix_value.cc; Blink style_color.cc; w3c/csswg-drafts#14465.

Examples

Live demo & progressive-enhancement three-color mix

.tri-swatch {
  /* Progressive enhancement: nested 2-color fallback for older browsers */
  background-color: color-mix(
    in oklab,
    color-mix(in oklab, #1d4ed8, #10b981),
    #e11d48 33.3333%
  );
  /* Variadic 3-color mix (Chrome 161+, Firefox 150+, Safari 27+) */
  background-color: color-mix(in oklab, #1d4ed8, #10b981, #e11d48);
}

/* Explicit perceptual space with weighted percentages summing below 100% (alpha = 0.85) */
.tinted-badge {
  background-color: color-mix(in oklch, rebeccapurple 45%, teal 25%, gold 15%);
}
Source: CSS Color 5 §3; CSS Color 5 §3.3.

Single-color conversion, opacity fade, and normalization corners

:root {
  --brand: #008080;
}

/* Single-color conversion to OKLCH (equivalent to oklch(from var(--brand) l c h)) */
.converted {
  color: color-mix(in oklch, var(--brand));
}

/* Single-color alpha fade (40% opacity, replacing color-mix(..., transparent)) */
.soft-backdrop {
  background-color: color-mix(in oklab, var(--brand) 40%, transparent);
  background-color: color-mix(in oklab, var(--brand) 40%);
}

/* Specified percentages already reach 120% -> omitted 3rd color gets 0% weight */
.clamped-omitted {
  border-color: color-mix(in srgb, red 60%, lime 60%, blue);
}

/* Polar spaces fold left-to-right: order changes the resulting hue */
.polar-a { background-color: color-mix(in oklch, red, lime, blue); }
.polar-b { background-color: color-mix(in oklch, blue, red, lime); }
Source: CSS Values 5 §6.1; CSS Color 5 §3.3; w3c/csswg-drafts#12234.

Feature detection and Canvas 2D fillStyle

const supportsVariadic = CSS.supports("color", "color-mix(in oklab, red, green, blue)");
const supportsSingle = CSS.supports("color", "color-mix(in oklch, teal)");

function paintMix(canvas) {
  const ctx = canvas.getContext("2d");
  if (!ctx) return;

  ctx.fillStyle = supportsVariadic
    ? "color-mix(in srgb, red, lime, blue)"
    : "color-mix(in srgb, color-mix(in srgb, red, lime), blue 33.3333%)";

  ctx.fillRect(0, 0, canvas.width, canvas.height);
  return { supportsVariadic, supportsSingle, serialized: ctx.fillStyle };
}
Source: CSS Color 5 §3; CPS conformance suite (canvas-fillstyle-variadic).

Security and privacy

Extending color-mix() from two colors to one or more colors is a pure CSS value parser and interpolation change that runs inside the existing color resolution pipeline. It introduces no new permissions, storage, network capabilities, or fingerprinting surface beyond standard CSS color support detection via CSS.supports(). Existing privacy protections for :visited link styling and system colors apply identically to variadic color-mix() operands.

Source: ChromeStatus 5009529854099456; CSS Color 5 §3 color-mix().
