Long Animation Frames style duration

Two new timing fields — styleDuration and forcedStyleDuration — introduced in the Chrome 148 origin trial for the Long Animation Frames (LoAF) API, letting developers distinguish time spent in style and layout from other work inside a slow frame (shipped by default in Chrome 157 with an updated property split).

Limited availability — Chromium-only (Chrome 148–153 origin trial; shipped in Chrome 157 per ChromeStatus / 158 per BCD); MDN reference pages for these properties do not exist yet (checked 2026-11-27)

  • Chrome · 148–153 OT; 157 (ChromeStatus) / 158 (BCD)
  • Edge · Mirrors Chrome
  • Firefox · Not supported (#929)
  • Safari · Not supported (#283)

Historical Origin Trial (Chrome 148–153) — shipped by default in Chrome 157 (API changed)

This feature was in origin trial in Chrome 148–153; it shipped enabled by default in Chrome 157 on desktop, Android, and WebView per ChromeStatus 5171478175809536 (milestone 157 listing; Intent to Ship) — note that MDN BCD records version_added: "158". The origin trial token was only needed before shipping. API surface changed before shipping: this Chrome 148 page documents styleDuration and forcedStyleDuration on PerformanceLongAnimationFrameTiming; the shipped Chromium IDL exposes styleDuration and layoutDuration on PerformanceLongAnimationFrameTiming and puts forcedStyleDuration and forcedLayoutDuration on PerformanceScriptTiming (see also BCD PerformanceScriptTiming.json, verified 2026-11-27).

why it exists

The Long Animation Frames API (LoAF) reports every frame that takes more than 50 ms to render. Before this addition, the PerformanceLongAnimationFrameTiming entry exposed total frame duration (duration) and script execution time (blockingDuration), but lumped style recalculation and layout into the general duration bucket. In pages that trigger forced layouts (style reads after DOM writes), style and layout often dominate the slow frame — but developers had no way to confirm this from the LoAF entry alone.

Adding styleDuration (total time for style + layout) and forcedStyleDuration (time for forced style + layout triggered mid-frame) makes it possible to diagnose layout-thrashing patterns directly from the performance timeline.

Source: chromestatus feature summary; spec PR #30.

shape of the API

Two new properties on PerformanceLongAnimationFrameTiming in the Chrome 148 origin trial (see the shipping note above for the Chrome 157/158 split across PerformanceLongAnimationFrameTiming and PerformanceScriptTiming):

Chrome 148 origin-trial properties on PerformanceLongAnimationFrameTiming
PropertyTypeDescription
styleDurationDOMHighResTimeStampTotal time (ms) spent in style recalculation and layout during the frame
forcedStyleDurationDOMHighResTimeStampSubset of styleDuration that was forced (layout triggered mid-frame by a script)

All other existing LoAF properties (duration, blockingDuration, renderStart, scripts, etc.) remain unchanged.

Source: w3c/long-animation-frames PR #30.

example

const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.entryType !== 'long-animation-frame') continue;

    console.log(`LoAF: ${entry.duration.toFixed(1)} ms total`);
    console.log(`  style+layout:        ${entry.styleDuration.toFixed(1)} ms`);
    console.log(`  forced style+layout: ${entry.forcedStyleDuration.toFixed(1)} ms`);

    // Threshold: warn if >50% of the frame is forced layout
    const forcedRatio = entry.forcedStyleDuration / entry.duration;
    if (forcedRatio > 0.5) {
      console.warn('Layout thrashing detected in this frame');
    }
  }
});

observer.observe({ type: 'long-animation-frame', buffered: true });
