Web app manifests can now carry built-in translations for name, short name, description, and icons using _localized-suffixed fields. The browser picks the closest match to the user's language — no server-side manifest switching or separate manifest files needed.

why it exists

Before Chrome 148, a PWA that needed localized names had to either serve a different manifest from a different URL per locale, or use server-side content negotiation to rewrite the manifest dynamically. Neither approach integrates cleanly with install-time metadata or icon selection. Manifest Localization bakes translations directly into the manifest file using a standardised _localized suffix convention, matching the existing pattern used by the web app manifest specification's internationalization work in W3C.

Source: Chrome for Developers — Manifest Localization blog, W3C Localizable Manifests spec, May 2026.

the manifest fields

Any localizable manifest member gains a companion field whose name is the original field name with _localized appended. Each companion field is an object whose keys are BCP 47 language tags and whose values are localization entries.

Formal syntax

The manifest is JSON, so there is no IDL. This is a summary notation of the Web Application Manifest *_localized members section (Editor’s Draft, read 2026-11-15); the quoted names are literal JSON keys and ? marks an optional key:

"<member>_localized": language-map

language-map          = { <language-tag>: localized-value, ... }   ; BCP 47 tag keys
localized-value       = string | localized-text-object            ; name, short_name, description
                      | [ image-resource, ... ]                   ; icons (same shape as "icons")
localized-text-object = { "value": string,
                          "dir"?:  "ltr" | "rtl" | "auto",
                          "lang"?: <language-tag> }

; Localizable members in the spec:
;   manifest:      name, short_name, icons
;   shortcut item: name, short_name, description, icons
; Chrome/Edge 148 also localize the manifest's top-level description.

The spec lists only name, short_name and icons at the top level. Top-level description is localizable in Chrome and Edge 148 according to the launch post; description itself is defined in Manifest Application Information, which has no _localized text.

Localization entry

KeyRequiredDescription
valueYesThe translated string (or array of icon objects for icons_localized).
dirNoText direction override: "ltr", "rtl", or "auto". Defaults to the manifest's top-level dir.
langNoLanguage override for the value. Defaults to the map key.

For text members a plain string is also accepted as shorthand: "de": "Farbwähler" is the same as "de": { "value": "Farbwähler" }, with dir taken from the manifest’s top-level dir and lang from the map key.

Localizing shortcuts

Each item in shortcuts accepts the same companions for its own name, short_name, description and icons. The spec’s “process a shortcut” steps run the same text and image localization steps on every item. The item’s default name is still required.

"shortcuts": [{
  "name": "New forecast",
  "name_localized": { "fr": "Nouvelle prévision", "de": "Neue Vorhersage" },
  "url": "/new",
  "icons": [{ "src": "/icons/new.png", "sizes": "96x96" }],
  "icons_localized": {
    "fr": [{ "src": "/icons/new-fr.png", "sizes": "96x96" }]
  }
}]

Processing rules and invalid values

Nothing throws: a manifest is parsed by the browser, and invalid localized data is silently skipped, leaving the default value in place. Following the spec’s processing steps:

  • If a *_localized member is not a JSON object, the whole member is ignored.
  • A language entry whose key, or whose lang, is not a structurally valid BCP 47 tag is dropped.
  • A text entry that is neither a string nor an object with a usable value is dropped. Values have leading and trailing ASCII whitespace stripped.
  • A dir that is not "ltr", "rtl" or "auto" is ignored and the manifest’s dir is used instead.
  • Localized icon lists go through the same image-resource processing as icons, resolved against the manifest URL. Invalid icon entries are dropped.
  • Which entry is shown is up to the browser: the spec says it SHOULD pick the entry whose language tag best matches the user’s preferences, and otherwise use the default (un-suffixed) value.

Localized values follow the normal manifest lifecycle: the browser reads them when it fetches the manifest for installation, and picks up changes through its usual manifest update check.

example

Localizing name and short_name

{
  "name": "Weather Now",
  "name_localized": {
    "fr": { "value": "Météo en direct" },
    "de": { "value": "Aktuelles Wetter" },
    "ja": { "value": "天気ナウ" },
    "ar": { "value": "الطقس الآن", "dir": "rtl" }
  },
  "short_name": "Weather",
  "short_name_localized": {
    "fr": { "value": "Météo" },
    "de": { "value": "Wetter" },
    "ja": { "value": "天気" },
    "ar": { "value": "الطقس", "dir": "rtl" }
  },
  "description": "Real-time weather for your location.",
  "description_localized": {
    "fr": { "value": "Météo en temps réel pour votre emplacement." },
    "de": { "value": "Echtzeit-Wetter für Ihren Standort." }
  },
  "start_url": "/",
  "display": "standalone",
  "icons": [
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}

Language selection

The browser matches the user's preferred language (from the OS or browser settings) against the keys in the localized maps using BCP 47 lookup (subtag fallback). A French-Canadian user (fr-CA) sees the fr value if no fr-CA key is present. If no matching key is found, the base (non-suffixed) field value is used.

The spec itself only says the browser SHOULD choose the best match for the user’s preferences. The fr-CA → fr fallback above describes the expected lookup behaviour, not a step defined in the spec, and it was not verified in Chrome for this page.

Locale-specific icons

{
  "icons": [
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" }
  ],
  "icons_localized": {
    "ja": [
      { "src": "/icons/icon-512-ja.png", "sizes": "512x512", "type": "image/png" }
    ]
  }
}

browser support

BCD has no entry for *_localized members yet. BCD manifests/webapp/name.json, short_name.json and shortcuts.json have no localized sub-features, and there are no name_localized.json-style files (checked 2026-11-15). The table is therefore interim, from the ChromeStatus record and the launch post:

Browser*_localized membersNotes
Chrome148 (desktop)ChromeStatus records desktop 148 only; Android and WebView are not recorded (unknown). Finch feature name WebAppManifestLocalization; no flag.
Edge148Per the launch post (the feature was implemented by the Microsoft Edge team).
FirefoxNot supportedNo implementation recorded. BCD lists desktop Firefox without even the base name member (version_added: false). Position: No signal (mozilla/standards-positions#1366).
SafariNot supportedNo implementation recorded. Position: No signal (WebKit/standards-positions#627).

Where localization is not supported, browsers ignore the unknown *_localized keys and use the default name, short_name, description and icons, so keep those set to sensible values. webstatus.dev rates the feature Baseline limited (queried 2026-11-15).
