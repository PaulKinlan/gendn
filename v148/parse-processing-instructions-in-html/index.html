Parse processing instructions in HTML

Limited availability

  • Chrome · 150 (148 behind a flag)
  • Edge · 150
  • Firefox · not shipped
  • Safari · not shipped

Not Baseline. webstatus.dev reports the html-processing-instructions web feature as limited availability (API record, queried 2026-11-15): Chrome and Chrome Android 150 (2026-06-30), Edge 150 (2026-07-02), no Firefox or Safari implementation. The ProcessingInstruction interface itself (XML documents, target, data) has worked in every engine for decades. See the full table.

Chrome 148 teaches the HTML parser to recognise processing instructions — the <?target data?> syntax already used in XML and SVG — and expose them as ProcessingInstruction nodes in the DOM. Parsers and streaming frameworks can use them as lightweight range markers or directives without touching element structure.

Behind a flag in Chrome 148 — not an origin trial Correction (2026-11-15): earlier revisions of this page called this an origin trial. ChromeStatus records no origin trial: its experiment intent is described as “a finch (to 1% stable) rather than an OT”, and the feature ships enabled by default in Chrome 150 (intent to ship). It appears in the milestone-150 listing, not the milestone-148 listing (queried 2026-11-15); the shipped reference is v150/parse-processing-instructions-in-html. In Chromium 148 the parser change and the attribute methods sit behind HTMLProcessingInstruction, marked experimental in runtime_enabled_features.json5 (branch 7778). To try it in Chrome 148, enable chrome://flags/#enable-experimental-web-platform-features or launch with --enable-blink-features=HTMLProcessingInstruction. Without it, <?…> in HTML is still turned into a comment.

why it exists

Processing instructions (PIs) are an established DOM primitive in XML: they appear as ProcessingInstruction nodes and carry an arbitrary target and data string that tooling can act on while leaving element structure untouched. Until this feature, the HTML parser silently discarded PIs. The motivation is to enable two new use-cases without adding new element types that would affect CSS layout:

  • Range markers — <?start id?> / <?end id?> pairs delimit DOM regions (used by out-of-order streaming and syntax-highlighting tools).
  • Parser directives — targets can signal to a streaming parser how to buffer or flush content.
Source: chromestatus summary and whatwg/html PR #12118.

syntax

Formal syntax (HTML)

Verbatim from HTML Standard §13.1.7. Processing instructions must have the following format:

1. "<?".
2. A target.
3. Either of the following two options:
     - Zero or more ASCII whitespace.
     - One or more ASCII whitespace, followed by data.
4. Optionally, a U+003F (?).
5. A U+003E (>).
  • target: ASCII alphanumerics, - and _; must start with an ASCII alpha or _, and must not be an ASCII case-insensitive match for xml or xml-stylesheet.
  • data: text that must not contain > nor end with ?.
  • Differences from XML: in HTML a PI can end with > or ?>; <?xml …?> and <?xml-stylesheet …?> stay bogus comments for compatibility; only this restricted target subset is allowed, not XML’s full Name production.

The parser creates a ProcessingInstruction node with .target and .data properties.

DOM interface (formal syntax)

Verbatim from DOM Standard §4.13. The attribute methods are what this feature adds; Chromium 148’s processing_instruction.idl declares all seven under RuntimeEnabled=HTMLProcessingInstruction but has no constructor.

[Exposed=Window]
interface ProcessingInstruction : CharacterData {
  constructor(DOMString target, optional DOMString data = "");
  readonly attribute DOMString target;
  boolean hasAttributes();
  sequence<DOMString> getAttributeNames();
  DOMString? getAttribute(DOMString name);
  undefined setAttribute(DOMString name, DOMString value);
  undefined removeAttribute(DOMString name);
  boolean toggleAttribute(DOMString name, optional boolean force);
  boolean hasAttribute(DOMString name);
};

Attribute map. Each PI has an attribute map parsed from its data with the “rules for parsing pseudo-attributes” (name="value" pairs). Changing data re-parses the map; if the data does not parse as pseudo-attributes the map is simply empty. Every attribute mutation rewrites data as name="value" pairs separated by spaces, with &, <, > and " escaped as entities.

example

Processing instructions can be placed directly in HTML documents and queried using standard DOM tree traversal:

Inserting a PI in HTML and reading it from JS

<!-- HTML source -->
<div>
  <?highlight start="1" end="3"?>
  <p>Line one</p>
  <p>Line two</p>
  <p>Line three</p>
  <?highlight end?>
</div>

<script>
// Walk childNodes and collect PIs
const pis = [];
document.body.querySelectorAll('*').forEach(el => {
  for (const child of el.childNodes) {
    if (child.nodeType === Node.PROCESSING_INSTRUCTION_NODE) {
      pis.push({ target: child.target, data: child.data });
    }
  }
});
console.log(pis);
// [{ target: "highlight", data: "start=\"1\" end=\"3\"" },
//  { target: "highlight", data: "end" }]
</script>

Using createProcessingInstruction from JS

const pi = document.createProcessingInstruction('stream', 'flush-before');
document.body.prepend(pi);
// <?stream flush-before?>

Reading and writing pseudo-attributes

// HTML: <div><?start name="results">Loading…<?end></div>
const walker = document.createTreeWalker(document.body, NodeFilter.SHOW_PROCESSING_INSTRUCTION);
for (let pi = walker.nextNode(); pi; pi = walker.nextNode()) {
  if (!('getAttribute' in pi)) break;   // feature-detect (Chrome 150+, or 148 with the flag)
  console.log(pi.target, pi.getAttribute('name'));   // "start" "results", then "end" null
}

const marker = document.createProcessingInstruction('marker', '');
marker.setAttribute('name', 'a<b');
console.log(marker.data);               // name="a&lt;b"
marker.toggleAttribute('hidden');       // true; data is now: name="a&lt;b" hidden=""
marker.setAttribute('bad name', 'x');   // throws InvalidCharacterError
Source: method steps and data serialisation from DOM Standard §4.13.
