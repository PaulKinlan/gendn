CSS Custom Highlight Universal Selector ::highlight(*)

Limited availability

  • Chrome · 158
  • Edge · mirrors Chromium
  • Firefox · no support for * (position: under consideration)
  • Safari · no support for * (position: support)

The * argument is a Chrome 158 addition to ::highlight(). The parent Custom highlights web-feature is Baseline Newly available since 2026-03-24 on webstatus.dev (Chrome 105, Firefox 149, Safari 17.2; queried 2026-11-08), but that status covers ::highlight(<custom-ident>) only. BCD css/selectors/highlight.json has no sub-feature for the universal argument yet, and the ChromeStatus record lists its web-feature as “Missing feature”. Treat ::highlight(*) as Chromium-only progressive enhancement.

Introduces a universal selector for custom highlights, ::highlight(*), which matches the highlight pseudo-elements of all custom highlights regardless of their name. The * argument contributes zero specificity, so its declarations act as a base style that rules naming a specific highlight override through the cascade.

why it exists

The CSS Custom Highlight API styles Ranges registered in CSS.highlights through ::highlight(name). An app with many highlight names (search hits, spelling categories, per-collaborator selections, syntax tokens) had to repeat shared declarations once per name. ::highlight(*) writes those shared declarations once; because the argument adds no specificity, any rule that names a highlight still overrides it.

Source: ChromeStatus record — motivation; csswg-drafts#9091 resolution.

Syntax

Grammar from CSS Pseudo-Elements Level 4 §3.1, quoted verbatim (fetched 2026-11-08):

::highlight(<highlight-name-selector>)

<highlight-name-selector> = '*' | <custom-ident>
ArgumentMatchesSpecificity of the pseudo-element
<custom-ident> (e.g. search)The single custom highlight whose custom highlight name is that identifierEquivalent to a type selector (0,0,1)
* (new in Chrome 158)Every custom highlight, regardless of its custom highlight nameZero (0,0,0)

“Custom highlight” means a Highlight object registered in the HighlightRegistry (CSS.highlights.set(name, highlight)). ::highlight(*) does not match the UA highlights ::selection, ::target-text, ::spelling-error or ::grammar-error; those keep their own pseudo-elements.

Source: css-pseudo-4 — ::highlight(); CSS Custom Highlight API — HighlightRegistry.

Where it can appear and what it may style

  • Originating element: like any pseudo-element it follows a compound selector (article ::highlight(*), .editor::highlight(*)) or stands alone (implicitly *::highlight(*)).
  • Allowed properties: the same restricted set as every highlight pseudo-element — color, background-color, text-decoration and its associated properties (including text-underline-position and text-underline-offset), text-shadow, stroke-color, fill-color, stroke-width, and custom properties. Other properties are ignored. The spec notes that only color and background-color are interoperably supported so far.
  • Highlight inheritance: highlight pseudo-elements inherit from the parent element’s corresponding highlight pseudo-element, not from the originating element, so a universal base set on an ancestor flows down to every named highlight that does not override it.
Source: css-pseudo-4 §3.2 Styling Highlights and §3.5 Cascading and Per-Element Highlight Styles.

Cascade and specificity (the output)

Because the * argument contributes zero specificity, the outcome for a given highlight is decided by ordinary cascade rules:

Competing rulesSpecificityWinner
::highlight(*) vs ::highlight(search)(0,0,0) vs (0,0,1)::highlight(search), regardless of source order
p::highlight(*) vs ::highlight(search)(0,0,1) vs (0,0,1)Tie — the later rule in source order wins
.doc ::highlight(*) vs ::highlight(search)(0,1,0) vs (0,0,1).doc ::highlight(*) — the originating compound still counts

Only the argument is zero-specificity; the originating element selector keeps its normal weight. To keep the universal rule a true base layer, write it bare or put it in an earlier @layer.

Source: css-pseudo-4 — specificity of ::highlight(); Selectors Level 4 §17 Calculating specificity.

Invalid input and older browsers

A selector the browser cannot parse invalidates the whole style rule. In browsers without this feature (Chrome 157 and earlier, current Firefox and Safari) ::highlight(*) is an invalid selector, so:

  • A rule whose only selector is ::highlight(*) is dropped and the UA default (no custom styling) applies.
  • A selector list that mixes it in is dropped entirely: ::highlight(*), ::highlight(search) { … } also loses the search styling. Keep the universal rule in its own block.
  • Feature-detect with @supports selector(::highlight(*)) or CSS.supports("selector(::highlight(*))").

Verified in headless Chrome 153 (pre-feature) on 2026-11-08: a stylesheet containing ::highlight(*) {…} and ::highlight(b) {…} exposed only the ::highlight(b) rule in cssRules, and CSS.supports("selector(::highlight(*))") returned false while CSS.supports("selector(::highlight(a))") returned true. Selectors have no exception surface beyond this.

Source: Selectors Level 4 §3.9 Invalid selectors and error handling; CSS Conditional Rules Level 4 — selector() in @supports.

Context and lifecycle

::highlight(*) matches whatever is currently in CSS.highlights for the document: registering, deleting or clearing entries (set(), delete(), clear()) or mutating a Highlight’s ranges restyles the affected text on the next rendering update; no CSS change is needed when a new highlight name appears. Where custom highlights overlap, each highlight’s pseudo-element is painted separately, ordered by Highlight.priority and then registration order, so the universal base style applies to each overlapping layer independently.

Source: CSS Custom Highlight API §Priority of Overlapping Highlights; §5.1 Repaints.

Examples

The smallest complete use: one rule styles every registered custom highlight.

::highlight(*) { background-color: #fff3b0; color: #1a1a1a; }

Shared base style with per-category overrides

<p id="note">Teh quick brown fox jumpd over the lazy dog.</p>

<style>
  /* Base for every custom highlight; zero specificity from the * argument. */
  ::highlight(*) {
    text-decoration-line: underline;
    text-decoration-thickness: 2px;
    text-decoration-color: currentColor;
  }

  /* Named rules (0,0,1) win over the base without !important. */
  ::highlight(spelling) { text-decoration-style: wavy; text-decoration-color: firebrick; }
  ::highlight(search)   { background-color: #ffe066; color: #1a1a1a; }
</style>

<script>
  const text = document.getElementById("note").firstChild;
  const range = (start, end) => {
    const r = new Range();
    r.setStart(text, start);
    r.setEnd(text, end);
    return r;
  };

  if ("highlights" in CSS) {
    CSS.highlights.set("spelling", new Highlight(range(0, 3), range(20, 25)));
    CSS.highlights.set("search", new Highlight(range(4, 9)));
    // A name registered later is styled by ::highlight(*) with no new CSS.
    CSS.highlights.set("review", new Highlight(range(35, 39)));
  }
</script>

Progressive enhancement for older browsers

/* Never combine with named selectors in one list — an unsupported
   ::highlight(*) would invalidate the whole rule. */
@supports selector(::highlight(*)) {
  ::highlight(*) { background-color: #e8eefc; color: #1a1a1a; }
}

/* Fallback: style the names you know about explicitly. */
@supports not selector(::highlight(*)) {
  ::highlight(spelling) { background-color: #e8eefc; color: #1a1a1a; }
  ::highlight(search)   { background-color: #e8eefc; color: #1a1a1a; }
}

The spec says UAs should expose custom highlights to assistive technologies using Highlight.type, but don't rely on that. Use highlights for transient visual marks and <mark> when the highlighted text is meaningful. Don't rely on colour alone: pair it with an underline style, and keep text and highlight background at 4.5:1 contrast or higher.

Source: css-pseudo-4 — ::highlight(); CSS Custom Highlight API — highlight types and assistive technology; showcase demos.

Security and privacy

The feature only widens which existing highlight pseudo-elements a selector matches. It adds no new inputs, storage or cross-origin channel, and highlight pseudo-elements can't use layout-affecting properties. The ChromeStatus record lists security and privacy review as “Pending” and records no feature-specific concerns. The highlight security and privacy considerations concern the UA ::spelling-error and ::grammar-error pseudo-elements, which can leak a user’s dictionary. ::highlight(*) doesn’t match those, so it can’t be used to style or probe them.
