OfflineAudio­Context.start­Rendering(chunkSize)

Renders the next chunkSize sample-frames of the audio graph and resolves with them as an AudioBuffer. Call it repeatedly to pull a long or open-ended render out in bounded-memory pieces. With no argument it keeps its classic meaning on a finite context — render everything that is left — so existing code is unaffected. New argument in Chrome 158 (ChromeStatus 5109900936085504).

syntax

startRendering()
startRendering(chunkSize)

Spec IDL (Web Audio API § startRendering(chunkSize), verbatim):

Promise<AudioBuffer> startRendering(optional unsigned long? chunkSize = null);

Chromium IDL (offline_audio_context.idl, verbatim, extended attributes trimmed): two overloads pending removal of the runtime flag — behaviourally identical to the spec signature.

Promise<AudioBuffer> startRendering();
[RuntimeEnabled=OfflineAudioContextIncrementalRendering] Promise<AudioBuffer> startRendering(unsigned long? chunkSize);
Source: spec; offline_audio_context.idl

parameters

chunkSize (optional)

Number of sample-frames to render in this call. unsigned long?, default null; omitting it, passing undefined or passing null all mean “no chunk size”.

  • Rounded up to the next multiple of the render quantum size (128 frames, or the renderSizeHint you set). 1000 → 1024; 128 → 128.
  • Trimmed on a finite context so the chunk never runs past length: the last chunk is exactly the remaining frames.
  • When omitted: all remaining frames for a finite context; one render quantum for a length: null context.
  • 0 is rejected with NotSupportedError in Chromium (the spec text does not address 0).
  • Conversion: as a plain unsigned long (no [EnforceRange]), values go through Web IDL ConvertToInt: fractions truncate, NaN/Infinity become 0 (so are rejected), and negatives wrap modulo 232 (-1 becomes 4 294 967 295). Validate before calling.
Source: spec algorithm; offline_audio_context.cc (CalculateEffectiveChunkSize, zero check); Web IDL ConvertToInt

return value

A Promise that fulfils with a new AudioBuffer per call: numberOfChannels and sampleRate equal to the context’s, length equal to the computed chunk length (see the bufferLength table), holding the samples that follow the previous chunk with no gap or overlap. Promises from overlapping calls fulfil in call order.

Observable side effects: the first call moves state from "suspended" to "running"; currentTime advances by the chunk’s duration as it renders; when the final frame of a finite context is delivered the context closes itself (state → "closed") and fires complete with the final chunk as renderedBuffer. With chunkSize omitted on a finite context the single buffer is the whole render, exactly as before Chrome 158.

const ctx = new OfflineAudioContext({ numberOfChannels: 2, sampleRate: 44100, length: 1000 });
const a = await ctx.startRendering(300);   // a.length === 384 (3 × 128)
const b = await ctx.startRendering(300);   // b.length === 384
const c = await ctx.startRendering(300);   // c.length === 232 — trimmed; ctx.state === "closed"
Source: begin offline rendering; WPT incremental-rendering (same rounding/trimming asserted with a 256-frame quantum)

exceptions

All failures are reported by rejecting the returned promise with a DOMException; startRendering does not throw synchronously.

context and exposure

  • Method of OfflineAudioContext, which is [Exposed=Window] only — not available in workers or worklets.
  • No secure-context requirement, no permission, no user activation. The document must be fully active.
  • Enabled by default from Chrome 158 via the OfflineAudioContextIncrementalRendering runtime feature (status: "stable" in runtime_enabled_features.json5). In engines without it, chunkSize is ignored (extra arguments are dropped) and a second call rejects with InvalidStateError — detect with typeof OfflineAudioContext.prototype.close === "function".

lifecycle

  1. Call — checks run (closed? all frames committed?), the chunk length is computed, an AudioBuffer is allocated, [[committed frames]] grows by its length and the buffer joins the render queue.
  2. Render — if nothing else is queued the render thread starts at once and state becomes "running"; otherwise the chunk waits its turn. Scheduled suspend() points inside the chunk pause it until resume().
  3. Resolve — the promise fulfils with the buffer, [[rendered frames]] grows, and the next queued chunk starts. Between chunks with nothing queued, Chromium leaves state at "running".
  4. Finish — finite: after the last frame the context closes and complete fires once (Chromium) with the final chunk. Open-ended: nothing finishes until you call close(), which rejects any queued chunks with AbortError.

Calls are not idempotent: each one consumes frames. Re-entrancy is safe — WPT verifies that calling startRendering (or close()) synchronously while a chunk promise is being resolved neither duplicates nor drops frames.

Source: begin offline rendering; offline_audio_context.cc (OnChunkRendered); WPT

examples

Keep one chunk in flight while you encode the previous one

async function* renderChunks(ctx, chunkSize) {
  // Request the next chunk before processing the current one so rendering
  // and encoding overlap; at most two buffers are alive at once.
  let next = ctx.startRendering(chunkSize);
  while (true) {
    const chunk = await next;
    const done = ctx.state === "closed";      // finite context just finished
    if (!done) next = ctx.startRendering(chunkSize);
    yield chunk;
    if (done) return;
  }
}

const ctx = new OfflineAudioContext({ numberOfChannels: 2, sampleRate: 48000, length: 48000 * 600 });
buildGraph(ctx);
for await (const chunk of renderChunks(ctx, 48000)) {
  await encode(chunk);                        // placeholder for your encoder/muxer
}

Feature-detect and fall back

async function renderAll(ctx, onChunk, chunkSize = 16384) {
  if (typeof OfflineAudioContext.prototype.close !== "function") {
    onChunk(await ctx.startRendering());     // pre-158: one AudioBuffer for everything
    return;
  }
  while (ctx.state !== "closed") {
    onChunk(await ctx.startRendering(chunkSize));
  }
}

security and privacy

Chunked rendering returns the same samples a one-shot render of the same graph would; it exposes no new information about the device or user. The Web Audio fingerprinting considerations in the spec’s Privacy Considerations apply unchanged. The practical risk is resource use: a loop that keeps requesting chunks from an open-ended context runs indefinitely, so bound your loop and call close().
