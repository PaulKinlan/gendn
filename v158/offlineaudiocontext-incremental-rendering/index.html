OfflineAudioContext incremental rendering

Limited availability

  • Chrome 158 · shipped
  • Edge 158 · shipped (Chromium)
  • Firefox · not supported
  • Safari · not supported

Not Baseline. The webstatus.dev entry offline-audio-context-incremental-rendering reports limited availability (API record, queried 2026-11-15). Its web-features definition keys support off api.OfflineAudioContext.close, which BCD records as Chrome 158 and Firefox/Safari not supported.

Chrome 158 turns OfflineAudioContext rendering into a pull-based, chunked process. startRendering(chunkSize) renders only the next chunkSize sample-frames and resolves with that chunk as an AudioBuffer; you call it again for the next chunk. A context may now be created with length: null to render an open-ended stream, and the new close() method stops rendering and releases the context. Memory use is bounded by the chunk you ask for instead of by the whole render, so long exports (for example a two-hour project) no longer need one giant AudioBuffer.

why it exists

Before Chrome 158, startRendering() allocated an AudioBuffer big enough for the entire render before producing anything. The explainer gives the motivating case: exporting a two-hour video project from a browser-based editor. At 48 kHz with 4 channels of 32-bit float that is 7200 s × 48 000 × 4 × 4 bytes ≈ 5.5 GB of audio held in memory just to be written to a file and thrown away (arithmetic is gendn’s, from the explainer’s parameters). On constrained devices the tab can be killed mid-export. A single buffer at the end also makes it hard to interleave audio with video frames coming out of WebCodecs, which a muxer needs in timestamp order.

The Web Audio issue #2445 discussion (ClipChamp and Mediabunny developers took part) weighed a ReadableStream API and an ondataavailable event; the Working Group chose the smallest change — an optional chunk size on the existing method, a nullable length, and close() — which PR #2675 wrote into the spec.

syntax

The OfflineAudioContext interface as it now reads in the Web Audio API Editor’s Draft (quoted verbatim from the spec IDL, 2026-11-15). The members this feature adds or changes are startRendering(chunkSize), close() and the nullable length:

[Exposed=Window]
interface OfflineAudioContext : BaseAudioContext {
    constructor(OfflineAudioContextOptions contextOptions);
    constructor(unsigned long numberOfChannels, unsigned long length, float sampleRate);
    Promise<AudioBuffer> startRendering(optional unsigned long? chunkSize = null);
    Promise<undefined> resume();
    Promise<undefined> suspend(double suspendTime);
    Promise<undefined> close();
    readonly attribute unsigned long? length;
    attribute EventHandler oncomplete;
};

dictionary OfflineAudioContextOptions {
    unsigned long numberOfChannels = 1;
    unsigned long? length = null;
    required float sampleRate;
    (AudioContextRenderSizeCategory or unsigned long) renderSizeHint = "default";
};

Call forms:

const ctx = new OfflineAudioContext({ numberOfChannels, sampleRate, length });   // length may be null
const ctxOpen = new OfflineAudioContext({ numberOfChannels, sampleRate });       // length defaults to null

promise = ctx.startRendering();            // whole remaining render (finite) or one render quantum (null length)
promise = ctx.startRendering(chunkSize);   // next chunkSize frames, rounded up to a render-quantum multiple
promise = ctx.close();                     // stop rendering; context becomes "closed"

Chromium’s shipping IDL (offline_audio_context.idl) still spells startRendering as two overloads — startRendering() and a runtime-enabled startRendering(unsigned long? chunkSize) — with a TODO against crbug 530596178 to collapse them into the spec’s single optional unsigned long? chunkSize = null signature once the flag is removed. Script cannot observe the difference: no argument, undefined and null all mean “no chunk size”.

how chunked rendering works

Every startRendering call now commits a number of frames, allocates an AudioBuffer of that size, renders the graph into it, and resolves with it. The context keeps two counters — [[committed frames]] (frames promised to some call) and [[rendered frames]] (frames delivered) — plus a queue, [[rendered buffers]], of chunks still to render. Rendering continues from exactly where the previous chunk stopped: the graph, scheduled sources, automation and currentTime carry over, so concatenating the chunks gives the same samples as one big render (checked by the WPT data-integrity test).

how bufferLength is chosen

Given chunkSize (or null), the context’s length and the render quantum size (128 frames unless renderSizeHint changed it), the startRendering algorithm computes bufferLength:

Resulting AudioBuffer length per call
Context lengthchunkSizebufferLength
finite Lnull / omittedL − committed — all remaining frames (the classic one-shot render)
finite Lnn rounded up to a render-quantum multiple, but never more than L − committed (the last chunk is trimmed exactly)
nullnull / omittedone render quantum (128 by default)
nullnn rounded up to a render-quantum multiple

So with a 128-frame quantum, startRendering(1000) yields 1024 frames, and with renderSizeHint: 256, startRendering(300) yields 512 (the WPT case). On a finite context of 1000 frames, two startRendering(300) calls with a 256 quantum return 512 then 488 frames.

Spec note: the spec text rounds up after choosing “length − committed” for the final chunk, which read literally could over-run L; Chromium (CalculateEffectiveChunkSize) and the WPT both trim the final chunk to exactly the remaining frames, and that is the behaviour to rely on.

queueing, completion and auto-close

  • Calls may overlap. You can call startRendering(chunkSize) again before the previous promise settles; each call commits its frames immediately and its buffer is appended to the queue. Chunks render one after another and promises resolve in call order.
  • State. The first call moves state from "suspended" to "running". In Chromium the context stays "running" between chunks (reaching a chunk boundary is not a suspend), as the WPT asserts.
  • Finite contexts close themselves. When [[rendered frames]] reaches length, a control message closes the context: state becomes "closed" and statechange fires. Any later startRendering or close() rejects with InvalidStateError.
  • complete event. Fires only for finite contexts. Chromium fires it once, after the final chunk, with that final chunk as renderedBuffer — not the whole render. (The spec algorithm as written queues it after each chunk of a finite render; Chromium’s OnChunkRendered fires it only when the render is complete.) Use the promises, not this event, to collect chunks.
  • Open-ended contexts never close themselves and never fire complete; call close().
  • suspend(t) still works across chunks: a suspend scheduled at a chunk boundary takes effect when the next startRendering begins that quantum.

failure modes of the model

A chunk request is refused (the returned promise rejects) when the context is "closed" or every frame of a finite length is already committed (InvalidStateError), when chunkSize is 0 or the rounded bufferLength of an open-ended render would exceed 232−1 frames, or the AudioBuffer cannot be allocated (NotSupportedError in Chromium). Chunks still queued when close() runs reject with AbortError. Full table: startRendering errors.

examples

Export a long, finite render in one-second chunks

const sampleRate = 48000;
const seconds = 2 * 60 * 60;                 // a two-hour timeline
const ctx = new OfflineAudioContext({
  numberOfChannels: 2,
  sampleRate,
  length: seconds * sampleRate,
});
buildGraph(ctx);                             // your sources, effects, automation

const incremental = typeof OfflineAudioContext.prototype.close === "function";

if (incremental) {
  // Peak memory is one chunk (~375 KB here), not the whole render.
  while (ctx.state !== "closed") {
    const chunk = await ctx.startRendering(sampleRate);   // 48000 frames, a multiple of 128
    await writeToEncoder(chunk);             // e.g. AudioData -> AudioEncoder -> muxer
  }
  // A finite context closes itself after the last chunk; no close() needed.
} else {
  // Older engines: one huge AudioBuffer.
  await writeToEncoder(await ctx.startRendering());
}

Open-ended render, stopped on demand

const ctx = new OfflineAudioContext({ numberOfChannels: 1, sampleRate: 44100, length: null });
const osc = new OscillatorNode(ctx, { frequency: 440 });
osc.connect(ctx.destination);
osc.start();

console.log(ctx.length);                     // null

let frames = 0;
while (frames < 5 * ctx.sampleRate) {        // stop after ~5 s of audio
  const chunk = await ctx.startRendering(1024);
  frames += chunk.length;                    // 1024 each time
  analyse(chunk.getChannelData(0));
}
await ctx.close();                           // required: open-ended contexts never close themselves

The startRendering, close and undefined-length pages have further examples (pipelined chunk requests, a cancel button, feature detection for the nullable length).

security and privacy

  • No new data exposed. Chunks contain exactly the samples the same graph already produced through one-shot startRendering(); nothing about the device or user is added. The existing Web Audio fingerprinting surface (small DSP differences between engines) is described in the spec’s Privacy Considerations and is unchanged by chunking.
  • Resource use moves from memory to time. An open-ended context keeps a rendering thread and graph alive until close() or document teardown; pages should close contexts they no longer need.
  • Reviews. ChromeStatus lists the security and privacy reviews and the W3C TAG design review #1282 as “Pending”, and its security-risks field is empty (record fetched 2026-11-15).
