CSS flow-start and flow-end alignment keywords

flow-start and flow-end are positional CSS Box Alignment keywords that align an item or content group to the starting or ending edge of item placement — following reversed directions in Flexbox (row-reverse, column-reverse, wrap-reverse) and CSS Grid Lanes (fill-reverse, track-reverse), and falling back to logical start/end elsewhere. flex-start and flex-end become legacy value aliases for flow-start and flow-end and serialize as flow-start and flow-end in computed styles.

Limited availability — Chrome 158+ only (not yet in Firefox or Safari)

  • Chrome · 158 (desktop; BCD mirrors Android / WebView)
  • Edge · 158 (BCD mirrors Chrome; 9/9 WPT pass)
  • Firefox · No release (Mozilla position: Positive; Bug 2073732)
  • Safari · No release (WebKit standards-positions#723 open)

why it exists

In CSS Box Alignment, start and end always align to the container’s writing-mode logical edges, ignoring layout-specific placement reversals. Flexbox originally solved this with flex-start and flex-end, which follow flex-direction: row-reverse / column-reverse and flex-wrap: wrap-reverse, but those names were explicitly flexbox-only. When CSS Grid Lanes (CSS Grid 3) added placement reversal controls (fill-reverse, track-reverse), authors had no layout-agnostic alignment keywords that tracked the start and end of item placement. The CSS Working Group resolved in w3c/csswg-drafts#14052 to introduce flow-start and flow-end as the canonical placement-relative keywords and make flex-start and flex-end legacy value aliases for them across Flexbox, Grid, and Grid Lanes.

Source: ChromeStatus motivation (5069051687731200); w3c/csswg-drafts#14052; w3c/csswg-drafts#12803.

Syntax

flow-start and flow-end are added to the CSS Box Alignment Level 3 <self-position> and <content-position> value productions, accepted by all six alignment longhands (align-content, justify-content, align-items, justify-items, align-self, justify-self) and their three shorthands (place-content, place-items, place-self), optionally preceded by an <overflow-position> keyword (safe or unsafe):

/* CSS Box Alignment Level 3 — §4.1 Positional Alignment */
<self-position> = center | start | end | self-start | self-end |
                  flow-start | flow-end | flex-start | flex-end

<content-position> = center | start | end |
                     flow-start | flow-end | flex-start | flex-end

<overflow-position> = unsafe | safe

/* Accepted in longhands and place-* shorthands */
align-content:   flow-start | flow-end | safe flow-start | unsafe flow-end;
justify-content: flow-start | flow-end | safe flow-start | unsafe flow-end;
align-items:     flow-start | flow-end | safe flow-start | unsafe flow-end;
justify-items:   flow-start | flow-end | safe flow-start | unsafe flow-end;
align-self:      flow-start | flow-end | safe flow-start | unsafe flow-end;
justify-self:    flow-start | flow-end | safe flow-start | unsafe flow-end;
place-content:   flow-start flow-end;
place-items:     safe flow-start unsafe flow-end;
place-self:      flow-start flow-end;

“flow-start: Aligns the alignment subject to be flush with the edge of the alignment container corresponding to the start of placement. In a flex formatting context, this corresponds to the flex container’s main-start or cross-start side, as appropriate. In grid lanes layout, this corresponds to the side of the grid lanes container from which item placement proceeds in the axis being aligned. When used outside of a flex formatting context or grid lanes layout, this value behaves as start, unless otherwise specified by the layout model.”

This reference documents four parts of the Chrome 158 contract: flow-start alignment behavior, flow-end alignment behavior, flex-start / flex-end value aliasing, and specified vs computed serialization and lifecycle.

Source: CSS Box Alignment 3 §4.1 Positional Alignment (verbatim grammar & quote fetched 2026-11-24); w3c/csswg-drafts#14539.

flow-start — inputs and resolved edge by layout mode

Inputs. The keyword flow-start (case-insensitive) is valid anywhere <self-position> or <content-position> is accepted: align-content, justify-content, align-items, justify-items, align-self, justify-self, and the place-content, place-items, and place-self shorthands. It may be combined with safe or unsafe overflow alignment (for example safe flow-start).

Outputs. flow-start aligns the alignment subject flush with the container edge from which item placement begins in the aligned axis:

Resolved alignment edge for flow-start across CSS layout modes
Formatting contextAxisResolved edge for flow-start
Flex container (display: flex / inline-flex)Main axis (justify-content)main-start edge (flips when flex-direction is row-reverse or column-reverse)
Flex containerCross axis (align-content, align-items, align-self)cross-start edge (flips when flex-wrap: wrap-reverse)
Grid Lanes container (CSS Grid 3)Grid axis or stacking axisSide of the container from which item placement proceeds in that axis (flips under placement reversal such as fill-reverse or track-reverse; matches logical start when not reversed)
Regular Grid, Block, or other layout modesInline or block axisBehaves identically to logical start (writing-mode relative), unless another layout mode defines placement reversal

In CSS Box Alignment 3, flow-start also replaces flex-start as the canonical default fallback alignment (for example for stretch and space-between when items overflow or only one subject exists).

Source: CSS Box Alignment 3 flow-start; CSS Grid 3; w3c/csswg-drafts#14539.

flow-end — inputs and resolved edge by layout mode

Inputs. The keyword flow-end (case-insensitive) is accepted in the same nine alignment properties (six longhands and three place-* shorthands), optionally paired with safe or unsafe (for example unsafe flow-end).

Outputs. flow-end aligns the alignment subject flush with the container edge opposite the start of placement in the aligned axis:

Resolved alignment edge for flow-end across CSS layout modes
Formatting contextAxisResolved edge for flow-end
Flex container (display: flex / inline-flex)Main axis (justify-content)main-end edge (flips under row-reverse / column-reverse)
Flex containerCross axis (align-content, align-items, align-self)cross-end edge (flips under wrap-reverse)
Grid Lanes container (CSS Grid 3)Grid axis or stacking axisEdge opposite the side from which item placement proceeds in that axis (flips under fill-reverse / track-reverse; matches logical end when not reversed)
Regular Grid, Block, or other layout modesInline or block axisBehaves identically to logical end (writing-mode relative), unless another layout mode defines placement reversal
Source: CSS Box Alignment 3 flow-end; w3c/csswg-drafts#14539.

flex-start and flex-end as legacy value aliases

Inputs. Existing stylesheets and scripts using flex-start and flex-end (with or without safe/unsafe) continue to parse identically across all alignment longhands and place-* shorthands.

Outputs. CSS Box Alignment 3 redefines flex-start as a legacy value alias for flow-start, and flex-end as a legacy value alias for flow-end. Consequently, flex-start and flex-end are no longer restricted to flex layout: in Grid Lanes containers they follow item-placement direction and reversal identically to flow-start and flow-end, while keeping existing Flexbox behavior and falling back to logical start/end in regular Grid or Block containers.

Source: CSS Box Alignment 3 flex-start & flex-end; CSS Cascade 5 legacy value alias; ChromeStatus summary.

Specified vs computed serialization, kill-switch, and lifecycle

Serialization contract. In Chrome 158 (verified against WPT flow-start-and-end-serialization.html and Blink’s CSSFlowStartAndEndSerialization feature), specified and computed serialization differ intentionally:

Specified vs computed value serialization in Chrome 158 (from WPT flow-start-and-end-serialization.html)
Authored declarationel.style.getPropertyValue(...) (specified)getComputedStyle(el).getPropertyValue(...) (computed)
align-content: flex-start"flex-start""flow-start"
align-content: flex-end"flex-end""flow-end"
align-content: safe flex-start"safe flex-start""safe flow-start"
align-content: unsafe flex-end"unsafe flex-end""unsafe flow-end"
align-content: flow-start"flow-start""flow-start"
place-content: flex-start flex-end"flex-start flex-end""flow-start flow-end"
place-items: safe flex-start unsafe flex-end"safe flex-start unsafe flex-end""safe flow-start unsafe flow-end"

Separate Finch kill-switch. Because legacy web scripts or test suites may compare getComputedStyle(el).justifyContent === "flex-start", Chromium gates the computed-style canonicalization behind a second runtime flag (CSSFlowStartAndEndSerialization, depending on CSSFlowStartAndEnd) so serialization can be reverted independently via Finch if site-compat breakages are reported without disabling the flow-start and flow-end keywords.

Lifecycle. Alignment properties are non-inherited (except justify-items, which is inherited via legacy keyword mechanics when applicable, and align-self: auto / justify-self: auto which inherit the parent’s *-items value). Changing an alignment declaration or a container’s direction/reversal property triggers normal style recalculation and layout synchronously before paint; positional alignment keywords animate discretely.

Source: WPT flow-start-and-end-serialization.html; WPT align-content-computed.html; Blink runtime_enabled_features.json5; ChromeStatus interop_compat_risks.

Errors, invalid values, and cross-browser fallbacks

CSS Box Alignment declarations never throw JavaScript exceptions on invalid or unsupported values; unrecognized keywords are dropped at parse time according to standard CSS error handling:

  • Unsupported browsers (Chrome < 158, Firefox, Safari): A bare justify-content: flow-start declaration is ignored. Provide flex-start / flex-end immediately before flow-start / flow-end in the same rule block so older engines fall back cleanly to identical placement-relative behavior in Flexbox.
  • Feature detection: Use @supports (align-content: flow-start) in CSS or CSS.supports("align-content", "flow-start") in JavaScript.
  • Computed-style comparisons in JS: Code that inspects getComputedStyle(el).justifyContent (or any other alignment property) must accept both "flow-start" and "flex-start" (and "flow-end" / "flex-end") to remain compatible across Chrome 158+ and browsers not yet shipping canonical serialization.
  • Invalid combinations: Pairing two positional keywords in one longhand (e.g. align-content: flow-start center) or combining flow-start with baseline is invalid and discarded at parse time.
Source: WPT align-content-valid.html; WPT flow-start-and-end-serialization.html; ChromeStatus interop_compat_risks.

Context and exposure

flow-start and flow-end are CSS values usable in any document stylesheet, shadow DOM stylesheet, inline style attribute, @supports rule, or CSSOM call (CSSStyleDeclaration.setProperty(), CSS.supports()). They require no secure context, no permission, no user activation, and no JavaScript. They do not exist in Web Workers or non-DOM contexts.

Source: CSS Box Alignment 3 §4.1; WPT flow-start-and-end-serialization.html.

Examples

No interactive demo is published on the Chrome Platform Showcase for v158/css-flow-start-and-flow-end-alignment-keywords/ yet (HEAD check returned 404 on 2026-11-24).

Placement-relative alignment with cross-browser fallback

.toolbar {
  display: flex;
  flex-direction: row-reverse;
  /* Fallback for Chrome < 158, Firefox, and Safari */
  justify-content: flex-start;
  align-items: flex-end;
  /* Canonical placement-relative keywords (Chrome 158+) */
  justify-content: flow-start;
  align-items: safe flow-end;
}

/* Shorthand syntax with overflow-position keywords */
.card-grid {
  display: grid;
  place-items: safe flow-start unsafe flow-end;
}
Source: CSS Box Alignment 3 §4.1; WPT align-content-valid.html.

Reading computed alignment safely across Chrome 158+ and other engines

const el = document.querySelector(".toolbar");
el.style.justifyContent = "flex-start";

// Specified value preserves authored spelling in Chrome 158:
console.log(el.style.getPropertyValue("justify-content")); // "flex-start"

// Computed value serializes canonically as "flow-start" in Chrome 158+,
// and as "flex-start" in browsers that have not shipped this change:
const computed = getComputedStyle(el).justifyContent;
const isFlowStart = computed === "flow-start" || computed === "flex-start";

// Feature detection for the new keywords:
const supportsFlowKeywords = CSS.supports("align-content", "flow-start");
Source: WPT flow-start-and-end-serialization.html.

Security and privacy

flow-start and flow-end are pure CSS layout alignment keywords that alias existing flex-start and flex-end behavior. They introduce no new storage, network capability, cross-origin information leak, permission, or device fingerprinting surface beyond existing CSS layout measurement. Chromium’s ChromeStatus API record lists both security and privacy reviews as Pending (checked 2026-11-24) with no reported security risks; CSS Box Alignment 3 Privacy & Security Considerations notes no new privacy or security concerns.

Source: ChromeStatus 5069051687731200; CSS Box Alignment 3 — Privacy and Security Considerations.
