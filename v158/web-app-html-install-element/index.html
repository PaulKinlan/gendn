HTML install element

The declarative <install> HTML element (HTMLInstallElement) renders a browser-controlled install control that lets a secure top-level page offer web app installation for the current document or for another same-origin or cross-origin web app identified by its manifest URL and optional manifestid, without writing beforeinstallprompt boilerplate. It ships alongside the imperative Web Install API (navigator.install()) and supersedes the Chrome 148–153 origin-trial surface with renamed attributes (manifest), capability-element validation (isValid, invalidReason, validationstatuschange), and the bubbling installresult event (InstallResultEvent).

Limited availability — Chromium desktop only (not Baseline; Firefox no signal, Safari opposed)

  • Edge · 158 (desktop; co-authored by Microsoft Edge; mirrors Chromium desktop)

Why it exists

Previously, websites could only offer installation for the currently loaded page by intercepting the non-standard beforeinstallprompt event in JavaScript, and app catalogs, search experiences, or multi-app suites had no declarative way to offer cross-origin web app installation without navigating users away or relying on platform app stores.

The <install> element provides a browser-rendered, anti-clickjacking-protected HTML control that carries a stronger user-intent signal than an arbitrary scripted button. It works without JavaScript for basic install actions, falls back cleanly to its child DOM content in non-supporting browsers, and reuses the same manifest resolution, consent dialog, and policy model as navigator.install().

Source: ChromeStatus motivation (5152834368700416); WICG Web Install / <install> Element draft §Introduction.

Syntax & WebIDL

HTML element markup (children act as progressive-enhancement fallback content in browsers that do not support <install>):

<!-- Current-document install (omitting both manifest and manifestid) -->
<install>
  <a href="/install-help">How to install this app</a>
</install>

<!-- Explicit-manifest install (same-origin or cross-origin) -->
<install
  manifest="https://music.example/manifest.webmanifest"
  manifestid="https://music.example/app">
  <a href="https://music.example/">Open Music Example</a>
</install>

Verbatim shipped WebIDL from Chromium’s html_install_element.idl, install_result_event.idl, install_result_event_init.idl, and global_event_handlers.idl (matching the WICG Web Install specification):

[RuntimeEnabled=InstallElement, Exposed=Window]
interface HTMLInstallElement : HTMLElement {
  [HTMLConstructor] constructor();

  [CEReactions, Reflect, URL] attribute USVString manifestId;
  [CEReactions, Reflect, URL] attribute USVString manifest;

  [MeasureAs=CapabilityElementIsValid] readonly attribute boolean isValid;
  [MeasureAs=CapabilityElementInvalidReason] readonly attribute DOMString invalidReason;
  [MeasureAs=CapabilityElementOnValidationStatusChange] attribute EventHandler onvalidationstatuschange;
};

partial interface mixin GlobalEventHandlers {
  [RuntimeEnabled=InstallElement] attribute EventHandler oninstallresult;
};

enum InstallResult { "success", "aborted", "invalid-data" };

[RuntimeEnabled=InstallElement, Exposed=Window]
interface InstallResultEvent : Event {
  constructor(DOMString type, optional InstallResultEventInit eventInitDict = {});
  readonly attribute InstallResult result;
};

dictionary InstallResultEventInit : EventInit {
  InstallResult result = "aborted";
};

<install> element & HTMLInstallElement (manifest, manifestId)

Content model & fallback behavior. <install> is flow, phrasing, interactive, and palpable content; its content model is phrasing content. In supporting browsers, child nodes are treated as fallback content — they are not rendered, focusable, or exposed in the accessibility tree while the native browser-controlled button is rendered. In non-supporting browsers, <install> parses as an unknown element and renders its child fallback nodes normally. The element is not form-associated, has no disabled content attribute (activation blockers control activatability instead), and defaults to tabindex="0".

Inputs (content & reflected IDL attributes).

Attributes on <install> / HTMLInstallElement and target-selection rules (Blink html_install_element.cc & WICG spec)
Content / IDL attributeTypeResolution & target-selection behavior
manifest / element.manifestUSVString (reflected URL)Optional URL of the target web app’s manifest JSON file. Leading/trailing HTML whitespace is stripped and relative URLs resolve against document.baseURI. Omitting both manifest and manifestid installs the current document’s web app (requires the current document’s linked manifest to declare an explicit id same-origin with the document). A present-but-empty or unparseable manifest fails activation with installresult ("invalid-data").
manifestid / element.manifestIdUSVString (reflected URL)Optional manifest ID assertion. Leading/trailing HTML whitespace is stripped and relative URLs resolve against document.baseURI. Omit only when the target manifest explicitly declares an id member; if present, it must be non-empty, valid, and equal to the browser’s computed manifest ID. Supplying manifestid without manifest fails activation with installresult ("invalid-data").

Outputs & constructor. Calling document.createElement("install") or custom-element extension via [HTMLConstructor] yields an HTMLInstallElement instance inheriting from HTMLElement. The user agent renders localized label text and iconography controlled by the element’s inherited lang and dir attributes; authors cannot replace the native label text.

Activation validation: isValid, invalidReason, and onvalidationstatuschange

Inputs & outputs. Like other capability elements inheriting from Blink’s HTMLCapabilityElementBase, HTMLInstallElement continuously monitors context, visibility, occlusion, and styling preconditions to defend against clickjacking:

  • element.isValid (readonly boolean): true when no activation blocker is active and user activation will proceed; false when blocked.
  • element.invalidReason (readonly DOMString): "" (empty string) when isValid is true, or a machine-readable reason string identifying the active blocker when isValid is false.
  • validationstatuschange / element.onvalidationstatuschange (EventHandler): Non-bubbling Event fired at the <install> element whenever isValid or invalidReason changes.

installresult event, InstallResultEvent, InstallResult, and oninstallresult

Inputs & constructor. Script can construct synthetic events with new InstallResultEvent(type, eventInitDict) where eventInitDict is an optional InstallResultEventInit dictionary extending EventInit with result defaulting to "aborted" (and standard bubbles: false). When the user agent dispatches installresult in response to user activation on <install>, Blink sets bubbles: true and queues the event asynchronously on the user interaction task source so a single delegated listener on a catalog container can observe multiple <install> elements. oninstallresult is mixed into GlobalEventHandlers, so it is usable as both an HTML content attribute and a DOM event handler property on elements, Document, and Window.

Outputs & error taxonomy (InstallResult enum). Each InstallResultEvent exposes a single readonly event.result string; HTMLInstallElement stores no persistent result property:

InstallResult enum values returned by InstallResultEvent.result
event.resultMeaning & triggersRecommended handling
"success"The user accepted installation (or confirmed launching an already-installed app).Announce completion via an accessible live region (dispatching installresult does not announce automatically) and update UI state if appropriate.
"aborted"The user dismissed the confirmation dialog or denied web-app-installation permission; the browser suppressed the flow (e.g., Incognito/off-the-record profile or enterprise policy); another install request was already active on the top-level traversable; or the document navigated/became inactive.Treat as a normal cancellation; do not auto-reprompt or nag the user.
"invalid-data"manifest URL was empty/invalid or non-trustworthy; manifestid was set without manifest or was empty/invalid; legacy installurl attribute was present; current document had no linked manifest; manifest fetch failed, redirected, returned non-2xx or non-JSON MIME type; manifest JSON was malformed; manifest lacked an explicit id when manifestid was omitted; manifestid mismatched the computed ID; or manifest origin differed from resolved start_url origin.Verify the manifest URL returns valid JSON with an explicit id (or matching manifestid) and same-origin start_url; show a helpful fallback link.

Silent activation ignores (no installresult fired). Per the WICG activation algorithm and html_install_element.cc, activation silently returns without dispatching installresult if event.isTrusted is false (synthetic element.click()), if element.isValid is false, if event.defaultPrevented is true, or if the document’s execution context is gone.

Source: WICG spec §Activation behavior & InstallResultEvent; Blink install_result_event.idl; Blink html_install_element.cc.

Context, exposure, and lifecycle

Context & exposure. HTMLInstallElement and InstallResultEvent are exposed on Window only (not Workers). Eligible initiating documents must be fully active, primary top-level browsing contexts (not iframes or fenced frames), non-sandboxed, and permitted by the web-app-installation Permissions Policy; explicit manifest URLs must be HTTP(S) with a potentially trustworthy origin. Web app installation is unavailable in Incognito/off-the-record profiles.

Lifecycle & state transitions. (1) On insertion into the DOM, <install> runs capability-element registration and enters a brief "recently_attached" cooldown before isValid becomes true and validationstatuschange fires. (2) Any attribute mutation, layout shift, clipping, occlusion, or invalid style sets isValid = false and fires validationstatuschange. (3) On a trusted click or keyboard activation while isValid === true, Blink validates manifest/manifestid (failing immediately with "invalid-data" on invalid syntax or legacy installurl), acquires the top-level traversable’s active install lock (only one request may run at a time), resolves and fetches the manifest with credentials: "omit" and no referrer/redirects/service-worker interception, obtains permission and user consent via browser chrome UI, and queues a bubbling installresult event on the user-interaction task source. If the page navigates or is destroyed mid-flow, the UA cancels the prompt and aborts the request. As with navigator.install(), an explicit-manifest install does not load the target document, so its service worker registers on first launch.

Source: WICG spec §Common request preconditions & §Lifecycle and rendering; Blink html_install_element.cc; Blink html_capability_element_base.cc.

App catalog with fallback content, validation tracking, and delegated installresult

<section id="app-catalog" aria-label="Installable apps">
  <!-- Same-origin current-document install -->
  <install id="install-this-app">
    <a href="/install-guide">Install this app from your browser menu</a>
  </install>

  <!-- Cross-origin explicit-manifest install -->
  <install
    manifest="https://music.example/manifest.webmanifest"
    manifestid="https://music.example/app">
    <a href="https://music.example/" rel="noopener">Open Music Example</a>
  </install>

  <p id="install-status" role="status" aria-live="polite"></p>
</section>
const catalog = document.querySelector("#app-catalog");
const statusEl = document.querySelector("#install-status");

// Feature detection: check HTMLInstallElement in window
const supportsInstallElement = "HTMLInstallElement" in window;

if (supportsInstallElement && catalog) {
  // Optional: inspect origin-level "web-app-installation" permission state
  if (navigator.permissions?.query) {
    navigator.permissions
      .query({ name: "web-app-installation" })
      .then((perm) => console.debug("web-app-installation permission:", perm.state))
      .catch(() => {});
  }

  // Monitor activation-blocker state on each <install> element
  for (const el of catalog.querySelectorAll("install")) {
    el.addEventListener("validationstatuschange", () => {
      if (!el.isValid) {
        console.debug("Install control currently blocked:", el.invalidReason);
      }
    });
  }

  // User-agent-dispatched installresult bubbles, so one delegated listener suffices
  catalog.addEventListener("installresult", (event) => {
    if (!statusEl) return;
    switch (event.result) {
      case "success":
        statusEl.textContent = "App installed successfully.";
        break;
      case "aborted":
        statusEl.textContent = "Installation was cancelled.";
        break;
      case "invalid-data":
        statusEl.textContent = "Unable to install: app manifest data was invalid.";
        break;
    }
  });
}

Security and privacy

  • Clickjacking & synthetic-click defenses: <install> inherits capability-element visibility, occlusion, contrast/style validation, and post-attach/post-move cooldown timers; activation ignores untrusted events (isTrusted === false) and blocked controls (isValid === false).
  • Preventing installed-state side channels: The specification prohibits exposing whether an arbitrary cross-origin app is already installed via timing, layout, CSS, canvas, or event differences. In Chromium’s html_install_element.cc, UpdateAppearance() currently always passes is_installed = false (rendering “Install” rather than “Launch”) while mitigations for width-based side channels (crbug.com/485281836) are finalized, and explicitly suppresses installed-state appearance inside <canvas> subtrees.
  • Credential-free, isolated manifest fetching: Explicit-manifest retrieval uses GET with credentials: "omit", strips referrer headers, rejects redirects, requires a JSON MIME type, bypasses service workers, obeys CSP manifest-src and Local Network Access checks, uses the initiating document’s network partition key, never exposes response bytes to script, and requires the manifest URL to be same-origin with its resolved start_url.
  • Strict context & origin boundaries: Disallowed in all subframes, fenced frames, and sandboxed documents; cross-origin installs require the web-app-installation origin permission and always present browser-controlled confirmation UI that isolates untrusted app metadata from origin identity.
Source: WICG Web Install spec §Privacy & Security considerations; Blink html_install_element.cc; W3C TAG design review #1245.
