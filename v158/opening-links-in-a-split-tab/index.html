Opening links in a split tab

Lets web authors request that a navigation open in a side-by-side split tab alongside the opener within the same browser window, using either imperative window.open() window features (split, splitposition, splitsize) or a new declarative windowfeatures HTML attribute (reflected as windowFeatures) on <a>, <area>, and <form>. Split layout is always a permission-free user-agent hint that degrades to an ordinary new tab (or an explicit popup fallback) when unavailable.

Limited availability — Experimental developer trial in Chrome 158 (not Baseline; behind a flag)

  • Chrome · 158 behind a flag (Origin Trial planned in Chrome 160–170)
  • Edge · Chromium-based (original explainer co-author; experimental)
  • Firefox · Not supported (No signal)
  • Safari · Not supported (No signal)

No webstatus.dev or BCD entry exists yet (checked 2026-11-24). ChromeStatus 5136319775899648 tracks a Developer Trial starting in Chrome 158 (desktop & Android) and a planned Origin Trial in Chrome 160–170.

Experimental — behind a flag in Chrome 158. This API is a pre-incubation proposal (mfreed7/split-tabs; whatwg/html#13153) and feature names (split, splitposition, splitsize, windowfeatures) may change before standardization. To enable it in Chrome 158, launch Chrome with --enable-blink-features=WindowOpenSplitTab (or enable Experimental Web Platform Features, since WindowOpenSplitTab has status: "experimental" and no standalone chrome://flags entry in about_flags.cc as of 2026-11-24). An Origin Trial (including third-party origin trials) is planned for Chrome 160–170.

why it exists

Modern browsers increasingly offer split-tab views (tiling two tabs side-by-side inside one browser window), yet HTML and window.open() previously offered only two destinations for a new top-level navigable: a full-size tab in the current window, or a detached popup window. Search results pages, coding/design live-preview editors, documentation portals, mail/office document previewers, and in-page assistants had no way to ask the browser to open a destination alongside the source tab while keeping full top-level navigable semantics (unlike an <iframe>) and without requiring the heavyweight multi-monitor window-management permission.

Source: ChromeStatus summary (5136319775899648); mfreed7/split-tabs §Use Cases.

Syntax

This feature adds three window-feature tokens to window.open() and a reflected windowFeatures IDL attribute (windowfeatures HTML content attribute) to <a>, <area>, and <form> (verified verbatim from Blink’s html_hyperlink_element_utils.idl, html_form_element.idl, and create_window.cc):

// Imperative: window.open(url, target, windowFeatures)
window.open(url, "_blank", "popup=0,split");
window.open(url, "_blank", "popup=0,split,splitposition=right,splitsize=40");
window.open(url, "_blank", "split,popup"); // fallback to popup if split unavailable

// Declarative HTML content attribute on <a>, <area>, and <form>
<a href="https://example.com" windowfeatures="split,splitposition=right,splitsize=40">
  Open side-by-side
</a>

// WebIDL additions (RuntimeEnabled=WindowOpenSplitTab)
partial interface mixin HTMLHyperlinkElementUtils {
  [CEReactions, Reflect] attribute DOMString windowFeatures;
};

partial interface HTMLFormElement {
  [CEReactions, Reflect] attribute DOMString windowFeatures;
};

This reference covers both surfaces: imperative window.open() split features and declarative windowfeatures attribute & windowFeatures IDL reflection.

Source: Blink html_hyperlink_element_utils.idl; Blink html_form_element.idl; Blink create_window.cc.

Imperative window.open() split features — inputs and outputs

Inputs. Passed in the comma-separated third argument (windowFeatures) of window.open(), tokenized ASCII case-insensitively by the HTML window-features tokenizer (where the last occurrence of a repeated key wins):

New window.open() split feature tokens and parsing rules in Chromium 158 (from create_window.cc and window_features.mojom)
Feature tokenAccepted valuesSemantics & defaults
splitBoolean (bare split, 1, yes, true vs. 0, no, false)Requests opening the new navigable in a split tab alongside the opener. Suppresses the legacy “non-empty feature string implies popup” heuristic when truthy. Mutually exclusive with popup: when both are truthy, split wins and popup becomes the fallback if a split cannot be created.
splitpositionleft, right, top, bottomOptional side hint for the new pane. Ignored unless split is truthy. Unrecognized values reset to kUnspecified (user-agent default, typically right / inline-end). Browsers that do not support stacked top/bottom splits may fall back to side-by-side or default placement.
splitsizeInteger percentage 1–99 (kMinSplitSize..kMaxSplitSize)Optional percentage of the split allocated to the new pane (opener receives the remainder). Parsed with loose integer parsing; non-numeric or out-of-range values (< 1 or > 99, or empty/yes/true) reset to unset (user-agent default, typically 50). Chromium clamps the effective browser UI split to 10–90%. Ignored unless split is truthy.

Outputs. window.open() returns a WindowProxy handle with window.opener intact (identical to normal window.open()) unless noopener or noreferrer is also specified (in which case it returns null). Whether the browser honored the split request is intentionally not exposed to script. In WPT open-features-split.tentative.html, BarProp.visible (locationbar, menubar, personalbar, scrollbars, statusbar, toolbar) is true for "split" (even alongside width/height/resizable=no/menubar=no), and false only when popup is explicitly requested (e.g. "split,popup") or when split=0 re-enables the legacy heuristic.

Critical legacy fallback rule: on browsers that do not implement split, any non-empty windowFeatures string triggers the legacy popup check and opens a detached popup window. Prefix with "popup=0,split" so unsupported browsers open a normal tab instead of a popup.

Source: Blink create_window.cc; Blink window_features.mojom; WPT open-features-split.tentative.html.

Declarative windowfeatures attribute & windowFeatures IDL

Inputs. The windowfeatures HTML content attribute is accepted on <a>, <area>, and <form> and reflects as the DOMString IDL property el.windowFeatures (default ""). It uses the same tokenizer as window.open(), but restricts recognized tokens to layout/container hints only:

  • Allowed in windowfeatures: split, splitposition, splitsize, popup, width/innerWidth, height/innerHeight, left/screenX, top/screenY.
  • Ignored in windowfeatures: noopener, noreferrer (controlled via the HTML rel attribute instead), and legacy chrome booleans (location, toolbar, menubar, resizable, scrollbars, status). Crucially, the legacy popup heuristic does not apply to the attribute: <a windowfeatures="width=400,height=300"> and <a windowfeatures="toolbar=0,menubar=0"> keep BarProp.visible === true.

Outputs & target/opener interaction.

  • Implied target="_blank": when windowfeatures requests split or popup and target is omitted, the navigation implicitly targets a new top-level navigable as if target="_blank" were set, overriding any document <base target>.
  • Existing targets win: when target is _self, _parent, _top, or the name of an existing frame/window, that navigable is navigated and windowfeatures is ignored.
  • Opener default differs from imperative: declarative links keep HTML’s default noopener for _blank navigations; add rel="opener" if you need window.opener.
  • Graceful fallback: browsers without windowfeatures support ignore the unknown attribute and open an ordinary new tab without needing popup=0.
Source: WPT declarative-windowfeatures.tentative.html; mfreed7/split-tabs §Declarative form; Blink create_window.cc.

Errors, invalid inputs, and feature detection

Neither window.open() split tokens nor the windowfeatures attribute throw new exceptions. Unknown feature tokens, unrecognized splitposition keywords, and invalid or out-of-range splitsize values are silently ignored and revert to user-agent defaults. If popup blocking suppresses a call lacking transient user activation, window.open() returns null as usual.

  • API feature detection: check "windowFeatures" in HTMLAnchorElement.prototype to detect whether the browser implements this surface.
  • No split-outcome detection: there is intentionally no navigator.splitTabSupported API and no return field indicating whether a split tab was actually created, to avoid exposing window geometry, form factor, or user settings as a fingerprinting vector.
Source: mfreed7/split-tabs §Feature detection; mfreed7/split-tabs §2.20.

Context and exposure

Exposed in standard Window browsing contexts (both HTTP and HTTPS; no Secure Context requirement and no permission prompt), subject to existing window.open() and link-navigation rules (transient user activation, popup blocker, and iframe sandbox="allow-popups"). Works identically in Incognito/Private Browsing. Not exposed in Workers. In Chrome 158, gated behind the WindowOpenSplitTab runtime flag (Origin Trial planned in Chrome 160–170).

Source: Blink runtime_enabled_features.json5; mfreed7/split-tabs §2.14–2.15.

Lifecycle and state transitions

Split hints apply at open time only; there is no API to resize or reposition an existing split tab later (the user and browser own the split once opened). Key lifecycle transitions:

  • Focus: imperative window.open() with user activation moves focus into the newly opened split pane; declarative links respect user click modifiers (for example Ctrl/Cmd-click opens in the background and overrides the split disposition).
  • Already-split opener: if the requesting tab is already part of a split (user-created or script-created), a new split request does not evict the adjacent pane; it falls back to an ordinary new tab. To update a pane you opened, navigate or postMessage() the existing WindowProxy handle or reuse its named target.
  • Closing collapses the split: calling openedWindow.close() from the opener (or window.close() inside the script-opened split) closes the split pane and returns the remaining tab to full window width.
  • COOP isolation: if the opened split navigates to a document with an incompatible Cross-Origin-Opener-Policy, the browsing context group switches, openedWindow.closed becomes true, and the target name can no longer be reused.
Source: mfreed7/split-tabs §Behavior; mfreed7/split-tabs §COOP navigation.

Examples

Imperative split preview with safe legacy fallback and live handle

const openPreviewBtn = document.querySelector("#open-preview");
let previewWin = null;

openPreviewBtn.addEventListener("click", () => {
  // Include popup=0 so browsers without split-tab support open a normal tab
  // instead of falling into the legacy non-empty-features popup heuristic.
  previewWin = window.open(
    "/preview.html",
    "_blank",
    "popup=0,split,splitposition=right,splitsize=45",
  );

  if (previewWin) {
    previewWin.addEventListener("load", () => {
      previewWin.postMessage({ type: "sync", draft: "# Hello split" }, location.origin);
    });
  }
});

// Close the split pane and restore the opener to full width
document.querySelector("#close-preview").addEventListener("click", () => {
  if (previewWin && !previewWin.closed) {
    previewWin.close();
  }
});
Source: mfreed7/split-tabs §Examples; mfreed7/split-tabs §Legacy fallback.

Security and privacy

Split tabs grant no new cross-origin capability beyond existing window.open() and hyperlink navigation, while addressing two key concerns:

  • No fingerprinting surface: pages cannot query whether split tabs are supported on the current device/window or whether a split was actually created; navigator.splitTabSupported was deliberately omitted.
  • Adjacent-pane spoofing & UI clamping: because both panes are visible simultaneously and an opener handle can navigate the openee (unless noopener or Cross-Origin-Opener-Policy isolates them), user agents must display clear per-pane origins and an unambiguous divider, clamp splitsize (10–90% in Chromium) so a page cannot open a deceptive sliver, honor split requests only from an active non-split tab with transient user activation, and respect user click modifiers.
  • Process-sharing note: keeping the opener on same-site splits can place both visible panes in the same renderer process/main thread; sites wanting isolation should use noopener or Cross-Origin-Opener-Policy.
Source: mfreed7/split-tabs §Privacy & Security; W3C TAG design review #1309.
