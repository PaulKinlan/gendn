WebTransport anticipated concurrent incoming streams

Limited availability (these two members) — WebTransport itself is Baseline Newly available

  • Chrome · 158
  • Edge · 158 (BCD mirrors Chrome)
  • Safari · 26.4
  • Firefox · 161 (beta; not yet released)

The webtransport web feature on webstatus.dev is Baseline newly available since 2026-03-24 (queried 2026-11-22) — but that status covers the WebTransport API as a whole. The anticipatedConcurrentIncoming* members are not yet listed among the feature’s compat keys in web-features webtransport.yml, so there is no published Baseline status for them. Computed by gendn from BCD api/WebTransport.json: Chrome 158, Safari 26.4 and Firefox 161 — and BCD’s Firefox release table lists 161 as beta, due 2026-11-24. Until that release ships, these members are limited availability.

Two hints that let a WebTransport application say, when it creates a session, how many server-initiated streams it expects to have open at once — anticipatedConcurrentIncomingUnidirectionalStreams and anticipatedConcurrentIncomingBidirectionalStreams. Each is both a WebTransportOptions constructor option and a read/write WebTransport attribute of type [EnforceRange] unsigned short? (default null). The browser can then advertise a larger initial QUIC stream allowance, so a server that fans out many streams does not stall waiting for stream credit. Values below 100 never lower the allowance: the spec requires clients to initially permit at least 100 streams of each type.

Chrome: when the hint takes effectChrome reads the hint once, at session establishment. Its dedicated HTTP/3 client advertises an initial allowance of max(100, hint) for each stream type when the hint is non-null, and leaves the QUIC default (at least 100) when it is null (dedicated_web_transport_http3_client.cc, kMinimumIncomingWebTransportStreams = 100). The attribute setters only update the stored value: “The value is used during session establishment (via Connect()), not sent post-handshake” (web_transport.cc, read 2026-11-22). The spec phrases the setter as a SHOULD for future negotiations, so assigning a new value to a connected transport in Chrome 158 changes what the getter returns but not the allowance already advertised
ErrorsTypeError for any value outside 0–65535, including -1, 65536, ±Infinity and NaN, from the constructor and from both setters; a rejected assignment leaves the stored value unchanged (Web IDL [EnforceRange]; asserted by WPT anticipated-concurrent-incoming-streams.https.any.js)
