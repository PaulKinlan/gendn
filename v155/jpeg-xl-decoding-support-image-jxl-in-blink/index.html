JPEG XL decoding support (image/jxl) in blink

Limited availability — not Baseline

  • Chrome · 155 (2026-10-06)
  • Edge · Chromium-based; no own record yet
  • Firefox · Nightly-only (default-on in 153 Nightly)
  • Safari · 17 (2023-09-18)

The webstatus.dev jpegxl web feature (the Intent’s own Web Feature ID; queried 2026-10-11) is Limited availability: Chrome/Chrome Android available since 155 (2026-10-06), Safari/Safari iOS since 17 (2023-09-18), and no Firefox release recorded — the Firefox 153 release notes list the Rust JPEG XL decoder as “enabled by default in Nightly” behind image.jxl.enabled (Firefox bug 2040074). Serve JPEG XL with a fallback; see examples.

From Chrome 155, Blink decodes JPEG XL (image/jxl) images, using jxl-rs, a memory-safe pure-Rust decoder. JPEG XL is a modern image format standardized as ISO/IEC 18181 that offers progressive decoding for improved perceived loading performance, support for wide color gamut, HDR, and high bit depth, and support for animation. This entry adds decoding — no new JavaScript API surface; .jxl resources simply work wherever Blink decodes images.

what changed

Chromium historically did not decode JPEG XL (an earlier flagged implementation was removed in 2022; the format’s return was one of the most-requested web platform features — the developer-signals issue linked by webstatus.dev carries 515 upvotes). From Chrome 155, Blink decodes image/jxl resources wherever it decodes images; the ChromeStatus record and Intent describe the change at the codec level (“decoding JPEG XL (image/jxl) images in Blink”) rather than enumerating per-surface support. What the format itself brings, per the ChromeStatus summary:

CapabilityWhat it means for pages
Progressive decodingA partially-downloaded .jxl renders a usable preview, “for improved perceived loading performance”
Wide color gamut, HDR, high bit depthColor fidelity beyond 8-bit sRGB in a single compressed format
AnimationAnimated images without GIF’s palette and size limits
Memory-safe decoderChrome’s implementation is jxl-rs, pure Rust — image decoders parse untrusted bytes, so memory safety is a security property here

Nothing in the sources read records a change to the Accept request header advertising image/jxl; until such server-visible advertising is documented, prefer client-side format selection with <picture> (below) over server-side content negotiation.

Source: ChromeStatus record and Intent to Ship (capabilities quoted from the summary); webstatus.dev jpegxl (developer-signals link)

syntax

No new API — the surfaces are the existing image-loading ones. The format is selected by MIME type (IANA: image/jxl; conventional extension .jxl):

<!-- Direct use: works in Chrome 155+, Safari 17+; broken image elsewhere -->
<img src="photo.jxl" alt="…">

<!-- Safe deployment: the browser picks the first source it can decode -->
<picture>
  <source srcset="photo.jxl" type="image/jxl">
  <source srcset="photo.avif" type="image/avif">
  <img src="photo.jpg" alt="…">
</picture>

The <picture> selection mechanism is the HTML Standard’s type attribute on <source>: a <source> whose type is a MIME type the user agent does not support is skipped, so browsers without JPEG XL fall through to AVIF or JPEG with no script and no broken images.

Source: HTML Standard — the source element’s type attribute; IANA media-type registry

examples

Script feature-detection, when markup fallback isn’t enough (e.g. choosing texture URLs): attempt to decode a tiny JPEG XL and see whether it succeeds (snippet gendn-derived; the embedded showcase demo runs exactly this kind of probe live):

// Probe with a real (small) .jxl asset you serve yourself —
// only a successful decode is proof of support.
function supportsJXL(probeUrl = '/img/probe.jxl') {
  return new Promise((resolve) => {
    const img = new Image();
    img.onload = () => resolve(img.naturalWidth > 0);
    img.onerror = () => resolve(false);
    img.src = probeUrl;
  });
}

// createImageBitmap gives a diagnosable error instead of a bare onerror:
async function supportsJXLDiagnosable(probeUrl = '/img/probe.jxl') {
  try {
    const response = await fetch(probeUrl);
    await createImageBitmap(await response.blob());
    return true;
  } catch {
    return false;
  }
}

if (await supportsJXL()) {
  useTextures('.jxl');   // progressive, HDR-capable
} else {
  useTextures('.avif');  // fallback chain
}
Source: detection pattern exercised by the showcase decode-probe demo; <picture> fallback per the HTML Standard; snippets gendn-derived (labelled)

security and privacy

An image decoder is one of the largest attack surfaces a browser exposes to untrusted bytes, which is why the implementation choice is itself the security story here: Chrome’s JPEG XL support ships on jxl-rs, “a memory-safe pure Rust decoder” (ChromeStatus summary), tested against the same conformance corpus as the C++ reference implementation per the Intent. The Intent records “no special risks” for interoperability/compatibility and “new feature, no special risk” for WebView. Decoded images follow the platform’s existing same-origin rules for image data (e.g. canvas origin-cleanliness); the sources read record no JPEG-XL-specific privacy considerations beyond the format-support bit that any new codec adds to passive fingerprinting surface.

Source: ChromeStatus summary; Intent to Ship (Risks sections)
