Additional Windowing Controls

Extends the Window Management API for installed desktop web applications with four asynchronous Window methods — maximize(), minimize(), restore(), and setResizable(boolean) — alongside two CSS media features, display-state and resizable, so custom or remote-desktop (VDI) titlebars can control and react to native window state and user resizability.

Limited availability — Chrome 155 enables Additional Windowing Controls by default on ChromeOS and behind a flag on other desktop platforms; Firefox and Safari do not implement it

  • Chrome · 155 (ChromeOS default; other desktop OSes behind flag)
  • Edge · Mirrors Chromium (flag on non-ChromeOS desktop)
  • Firefox · No signal
  • Safari · No signal

Both window-management-resizing and display-state report Limited availability on webstatus.dev (checked 2026-11-27). BCD api/Window.json and BCD css/at-rules/media.json record Chrome 155 enabled by default on ChromeOS and behind chrome://flags/#enable-desktop-pwas-additional-windowing-controls on other desktop platforms (matching Blink runtime_enabled_features.json5). Note that MDN’s legacy Window.setResizable() page documents only the Netscape 4.x Firefox no-op and MDN has no pages for maximize(), minimize(), restore(), display-state, or resizable.

why it exists

Virtual Desktop Infrastructure (VDI) web clients and desktop-class Progressive Web Apps that draw custom or streamed titlebars previously lacked any way to trigger native window minimize, maximize, or restore transitions, lock user-driven window resizing, or reflect OS-applied window states in CSS. Existing APIs such as window.resizeTo() and window.moveTo() cannot express minimized/maximized states or disable drag handles, leaving remote application titlebars redundant or non-functional. Additional Windowing Controls builds on the Window Management API to bridge local window managers and installed web application windows.

Source: ChromeStatus 5201832664629248; Additional Windowing Controls Explainer.

Syntax

WebIDL from Blink’s additional_windowing_controls.idl and W3C Window Management §3.2, plus CSS media feature grammar from §3.6.1 display-state and §3.6.2 resizable:

[
  SecureContext,
  ImplementedAs=AdditionalWindowingControls,
  RuntimeEnabled=DesktopPWAsAdditionalWindowingControls
] partial interface Window {
  [CallWith=ScriptState, RaisesException] Promise<undefined> maximize();
  [CallWith=ScriptState, RaisesException] Promise<undefined> minimize();
  [CallWith=ScriptState, RaisesException] Promise<undefined> restore();
  [CallWith=ScriptState, RaisesException] Promise<undefined> setResizable(boolean resizable);
};
@media (display-state: normal | minimized | maximized | fullscreen) { /* ... */ }
@media (display-state) { /* boolean context: always true */ }

@media (resizable: true | false) { /* ... */ }
@media (resizable) { /* boolean context: matches when resizable is true */ }

This reference documents all six surfaces in detail: window.maximize(), window.minimize(), window.restore(), window.setResizable(), @media (display-state), and @media (resizable).

Source: Blink additional_windowing_controls.idl; W3C Window Management §3.2; §3.6.1; §3.6.2.

Window.prototype.maximize()

Inputs. None (window.maximize() takes zero arguments).

Outputs & behavior. Runs the request a window display state change algorithm with targetState = "maximized" and returns a Promise<undefined>. After verifying context, web-app scope, transient user activation (unless in an Isolated Web App), and the window-management permission, Blink consumes transient activation in non-isolated contexts. If the window’s current WindowShowState is already kMaximized, the promise resolves immediately with undefined; otherwise Blink requests maximization from the host OS window manager and resolves with undefined once applied or rejects with NotAllowedError ("Could not maximize the window.") if the platform refuses.

Source: W3C Window Management §3.2.4 maximize(); Blink additional_windowing_controls.cc.

Window.prototype.minimize()

Inputs. None (window.minimize() takes zero arguments).

Outputs & behavior. Runs request a window display state change with targetState = "minimized" and returns a Promise<undefined>. Requires the same primary top-level web-app context, transient user activation (consumed in non-isolated contexts), and window-management permission as maximize(). If the window is already kMinimized, resolves immediately with undefined; otherwise requests minimization from the OS window manager and resolves with undefined or rejects with NotAllowedError ("Could not minimize the window.") if disallowed by the platform (for example, while blocked by a modal dialog or in a tabbed window).

Source: W3C Window Management §3.2.3 minimize(); Blink additional_windowing_controls.cc.

Window.prototype.restore()

Inputs. None (window.restore() takes zero arguments).

Outputs & behavior. Runs request a window display state change with targetState = "restored" and returns a Promise<undefined>. Requires primary top-level web-app scope, transient user activation (consumed in non-isolated contexts), and window-management permission. If the window is already in the normal (or default) show state, resolves immediately with undefined. Otherwise, per §3.2.2: from minimized it unminimizes to the pre-minimized state; from fullscreen it exits fullscreen to the pre-fullscreen state; and from maximized it unmaximizes to the normal display state. Rejects with NotAllowedError ("Could not restore the window.") if the platform rejects the request.

Source: W3C Window Management §3.2.5 restore(); Blink additional_windowing_controls.cc.

Window.prototype.setResizable(resizable)

Inputs. One required boolean parameter, resizable (coerced per WebIDL boolean conversion): false locks the window against user-initiated resizing (mouse drag handles, resize keyboard shortcuts, window frame resize controls, and user-initiated fullscreen toggle); true re-enables user resizing.

Outputs & behavior. Returns a Promise<undefined> that resolves with undefined once the host window manager applies the new resizability state, or rejects with NotAllowedError ("Could not set the window to be resizable." / "Could not set the window to be non-resizable.") if denied or unsupported. Crucially, unlike maximize(), minimize(), and restore(), both W3C Window Management §3.2.6 and Blink’s AdditionalWindowingControls::setResizable() pass require_user_activation = false — setResizable() does not require or consume transient user activation, though it still requires web-app scope and the window-management permission. Setting setResizable(false) blocks user-driven resizing, while script-driven APIs such as window.resizeTo(), window.maximize(), and Element.prototype.requestFullscreen() remain allowed unless restricted separately.

Source: W3C Window Management §3.2.6 setResizable(); Blink additional_windowing_controls.cc; Additional Windowing Controls Explainer.

@media (display-state) CSS media feature

Inputs. Discrete CSS media feature accepting four keywords: normal, minimized, maximized, or fullscreen, plus the value-less boolean form (display-state). Any other token (such as 0, none, or a length) evaluates as unknown.

Outputs & behavior. Matches the host OS window’s current display state (in Blink’s DisplayStateMediaFeatureEval(), WindowShowState::kDefault, kInactive, and kNormal all match normal). In boolean context, @media (display-state) always evaluates to true because a window always has a display state. Works declaratively in CSS rules and imperatively via window.matchMedia("(display-state: maximized)") with change listeners — and tracks OS-initiated state changes even without the window-management permission. In child frames (<iframe>), display-state does not reflect the parent window and always evaluates to normal.

Source: W3C Window Management §3.6.1 display-state; Blink media_query_evaluator.cc; WPT display-state.tentative.html.

@media (resizable) CSS media feature

Inputs. Discrete CSS media feature accepting true or false, plus the value-less boolean form (resizable). Numeric or unknown values (0, 1, none, lengths) are invalid/unknown.

Outputs & behavior. Matches whether the window is currently user-resizable (evaluated in Blink’s ResizableMediaFeatureEval()). In boolean context, @media (resizable) matches when the window is user-resizable (equivalent to (resizable: true)), and @media not (resizable) or @media (resizable: false) matches when user resizing is disabled (for example after await window.setResizable(false)). Reflects resizability changes in CSS and via window.matchMedia("(resizable: true)") change events without requiring the window-management permission. In child browsing contexts (<iframe>), resizable always evaluates to true rather than leaking the top-level window’s lock state.

Source: W3C Window Management §3.6.2 resizable; Blink media_query_evaluator.cc; WPT resizable.tentative.html.

Errors and recovery

All four JavaScript methods — maximize(), minimize(), restore(), and setResizable() — reject their returned promises with DOMException values rather than throwing synchronously. Unknown values for display-state or resizable never throw; they evaluate to false in CSS and matchMedia(). Note an important spec-vs-implementation difference in Blink’s additional_windowing_controls.cc:

Context, exposure, and permissions

  • Secure context & scope: maximize(), minimize(), restore(), and setResizable() are exposed only on Window in secure contexts ([SecureContext]), and execute only in a primary top-level, non-prerendering browsing context inside an installed web application scope (Document::IsInWebAppScope(), such as a standalone desktop PWA or Isolated Web App). They are not exposed in Workers or regular browser tabs (in a normal tab the methods exist on window when the feature is enabled, but reject with InvalidStateError).
  • window-management permission & Permissions Policy: All four methods check the window-management Permissions Policy (default allowlist 'self') and request the window-management permission via Chromium’s permission service, prompting the user on first use if not already granted.
  • User activation: maximize(), minimize(), and restore() require and consume transient user activation in standard PWAs (bypassed in Isolated Web Apps). setResizable() does not require transient user activation.
  • CSS media features without permission: @media (display-state) and @media (resizable) require neither the window-management permission nor installed web-app scope in top-level frames, so stylesheets and matchMedia() can observe user-driven window transitions. In child frames (<iframe>), both features are clamped to constant values (display-state: normal and resizable: true).
Source: Blink additional_windowing_controls.idl; Blink additional_windowing_controls.cc; W3C Window Management §3.6.

Lifecycle, ordering, and state transitions

Each call to maximize(), minimize(), restore(), or setResizable() queues asynchronous work on the window placement task source, requests/verifies the window-management permission, and then talks to the native window manager via Blink’s ChromeClient:

  • Idempotency: Calling maximize() when already maximized, minimize() when already minimized, or restore() when already in the normal state is a no-op that resolves immediately with undefined (after permission and activation checks).
  • restore() target state: Restoring from maximized returns to normal; restoring from minimized returns to the state active before minimization (which may be maximized or normal); restoring from fullscreen exits fullscreen back to the pre-fullscreen state.
  • Observing transitions via MediaQueryList: There is no dedicated displaystatechange DOM event. Subscribe to window.matchMedia("(display-state: maximized)"), window.matchMedia("(display-state: minimized)"), window.matchMedia("(display-state: fullscreen)"), and window.matchMedia("(resizable: true)") using addEventListener("change", ...) to stay synchronized with both API calls and OS window-manager actions.
  • Activation consumption: Because maximize(), minimize(), and restore() consume transient activation on completion (in non-IWA apps), do not chain two state-change calls sequentially from a single click.
Source: W3C Window Management §3.2.2; Blink additional_windowing_controls.cc; Additional Windowing Controls Explainer.

Examples

Interactive demonstrations for this feature (same ChromeStatus ID 5201832664629248, built for its earlier developer-trial milestone) are published on the Chrome Platform Showcase — Additional Windowing Controls: window state controls, display-state media queries, setResizable() lock, and custom titlebar (not embedded in an iframe here because Additional Windowing Controls only operates in primary top-level installed web-app windows).

Controlling window state and resizability in a custom titlebar

const hasAwc =
  typeof window.maximize === "function" &&
  typeof window.minimize === "function" &&
  typeof window.restore === "function" &&
  typeof window.setResizable === "function";

async function runWindowAction(action, statusEl) {
  if (!hasAwc) {
    statusEl.textContent = "Additional Windowing Controls unavailable.";
    return;
  }
  try {
    if (action === "maximize") await window.maximize();
    else if (action === "minimize") await window.minimize();
    else if (action === "restore") await window.restore();
    else if (action === "lock") await window.setResizable(false);
    else if (action === "unlock") await window.setResizable(true);
    statusEl.textContent = `Applied: ${action}`;
  } catch (err) {
    // InvalidStateError outside installed PWA scope; NotAllowedError on denied permission/gesture
    statusEl.textContent = `${err.name}: ${err.message}`;
  }
}

function wireTitlebarButtons(container, statusEl) {
  container.addEventListener("click", (event) => {
    const button = event.target.closest("button[data-awc]");
    if (!button) return;
    runWindowAction(button.dataset.awc, statusEl);
  });
}
Source: W3C Window Management §3.2.3–3.2.6; Blink additional_windowing_controls.cc.

Adapting UI with @media (display-state) and @media (resizable)

/* Swap maximize vs. restore icon in a custom titlebar based on window display-state */
.btn-restore {
  display: none;
}

@media (display-state: maximized), (display-state: fullscreen) {
  .btn-maximize {
    display: none;
  }
  .btn-restore {
    display: inline-flex;
  }
}

/* Indicate locked window size when setResizable(false) is active */
.resize-grip {
  cursor: nwse-resize;
}

@media (resizable: false) {
  .resize-grip {
    display: none;
    cursor: default;
  }
}
function observeWindowState(onStateChange) {
  const states = ["normal", "minimized", "maximized", "fullscreen"];
  const queries = states.map((state) => ({
    state,
    mql: window.matchMedia(`(display-state: ${state})`),
  }));
  const resizableQuery = window.matchMedia("(resizable: true)");

  const report = () => {
    const active = queries.find((q) => q.mql.matches)?.state ?? "unknown";
    onStateChange({ displayState: active, resizable: resizableQuery.matches });
  };

  for (const { mql } of queries) mql.addEventListener("change", report);
  resizableQuery.addEventListener("change", report);
  report();
}
Source: W3C Window Management §3.6.1 & §3.6.2; WPT display-state.tentative.html; WPT resizable.tentative.html.

Security and privacy

  • Abuse and UI spoofing mitigations: Allowing arbitrary pages to minimize, maximize, restore, or lock window resizing could enable clickjacking, trap users in non-resizable windows, or disrupt desktop workflow. Accordingly, maximize(), minimize(), restore(), and setResizable() are restricted to secure, top-level installed web application windows with explicit window-management user permission, and the three state-changing methods also require and consume transient user activation (except in Isolated Web Apps).
  • No cross-frame state leakage: Although @media (display-state) and @media (resizable) do not require permission in top-level windows, both are clamped in child browsing contexts (<iframe>) to display-state: normal and resizable: true, preventing embedded third-party frames from fingerprinting or correlating user window-management actions across origins.
  • Programmatic resize boundaries: Calling setResizable(false) disables user resize handles and user-initiated fullscreen, but does not prevent script-initiated fullscreen (Element.prototype.requestFullscreen()); administrators or embedders who need to block fullscreen should also use the fullscreen Permissions Policy.
Source: Additional Windowing Controls Explainer (Security & Privacy); W3C Window Management §3.6; Blink additional_windowing_controls.cc.
