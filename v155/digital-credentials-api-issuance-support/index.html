Digital Credentials API (issuance support)

Extends navigator.credentials.create() with a digital option (DigitalCredentialCreationOptions) and the digital-credentials-create Permissions Policy so issuing websites — such as governments, universities, or banks — can securely provision digital credentials (for example via OpenID4VCI) into a user’s wallet application using Android Credential Manager on Android or cross-device CTAP on desktop, returning a DigitalCredential response.

Limited availability — credential issuance ships in Chrome 155 (desktop & Android); presentation shipped in Chrome 141 and Safari 26, while Firefox opposes the API and Safari has no issuance release yet

  • Chrome · 155 (desktop & Android; no WebView or iOS)
  • Edge · Mirrors Chromium (155)
  • Firefox · Negative position (not implemented)
  • Safari · Presentation in 26; issuance not shipped yet

webstatus.dev digital-credentials reports Limited availability (tracking presentation support in Chrome 141 and Safari 26; checked 2026-11-27). BCD api/DigitalCredential.json and BCD api/CredentialsContainer.json do not yet track the Chrome 155 create({ digital }) issuance path or the digital-credentials-create Permissions Policy. MDN has no dedicated DigitalCredential reference page and its CredentialsContainer.create() page does not document digital.

why it exists

Chrome 141 shipped presentation support (navigator.credentials.get({ digital })) so relying parties could request digital IDs from a user’s wallet, but credential issuers still had to rely on custom URL schemes, deep links, or opaque QR redirects to provision credentials into a mobile wallet — mechanisms that the browser and OS cannot mediate consistently across platforms or protect against origin spoofing. Adding issuance support to navigator.credentials.create({ digital }) routes provisioning requests through Android Credential Manager (CredMan) on Android and cross-device CTAP on desktop, binding the issuing origin cryptographically to the request and giving users a consistent browser-mediated consent flow.

Source: ChromeStatus 5099333963874304; Digital Credentials Explainer.

Syntax

  required sequence<DigitalCredentialCreateRequest> requests;

  required DOMString protocol;
  required object data;

  readonly attribute USVString protocol;
  [SameObject] readonly attribute object data;
  static boolean userAgentAllowsProtocol(DOMString protocol);
  object toJSON();
};

This reference documents every surface of digital credential issuance: navigator.credentials.create({ digital }), DigitalCredentialCreationOptions (requests), DigitalCredentialCreateRequest (protocol, data), DigitalCredential (protocol, data, userAgentAllowsProtocol(), toJSON()), and the digital-credentials-create Permissions Policy.

Source: W3C Digital Credentials §7.5–7.7; §9 Permissions Policy; Blink credential_creation_options.idl; Blink digital_credential.idl.

navigator.credentials.create({ digital, signal })

Inputs. A CredentialCreationOptions dictionary carrying the digital member (a DigitalCredentialCreationOptions object) and an optional signal (AbortSignal) for cancellation. Per W3C Digital Credentials §7.7, DigitalCredential mandates user mediation ([[implicitMediation]] = "required"), so interactive user consent is always required regardless of mediation.

Outputs & behavior. Returns a Promise<Credential?> that resolves to a DigitalCredential instance containing the wallet’s issuance response (protocol and data), or rejects with a DOMException or TypeError on policy, activation, validation, cancellation, or transport failure.

Source: W3C Digital Credentials — [[Create]] internal method; Blink authentication_credentials_container.cc; Blink digital_identity_credential.cc.

DigitalCredentialCreationOptions (requests)

Inputs. A dictionary with one required member: requests, a non-empty sequence<DigitalCredentialCreateRequest> listing one or more protocol-specific issuance requests the issuer can fulfill (allowing the issuer to supply fallback protocol versions in a single call).

Outputs & behavior. Blink filters requests through FilterSupportedRequests(..., kIssuance) before checking user activation or running JSON serialization. Requests with unsupported protocols are dropped; if the filtered list is empty (including when requests is []), navigator.credentials.create() rejects with a TypeError without invoking the wallet UI.

Source: W3C Digital Credentials §7.5 DigitalCredentialCreationOptions; Blink digital_identity_credential.cc.

DigitalCredentialCreateRequest (protocol, data)

Inputs. Each entry in requests requires two members:

  • protocol (DOMString, required): Registry identifier for the issuance protocol. In Chrome 155’s CheckDigitalCredentialSupportedProtocol(), allowed issuance protocols are "openid4vci" and "openid4vci-v1".
  • data (object, required): Protocol-specific issuance payload (for example, an OpenID4VCI credential offer object). Must be JSON-serializable via JSON.stringify() (no circular references, BigInt values, or throwing getters).

Outputs & behavior. Blink serializes each surviving request’s data object to JSON and forwards { protocol, data } over Mojo to the browser process, which attaches the verified requesting origin and hands the payload to Android CredMan or the cross-device CTAP transport.

Source: W3C Digital Credentials §7.6 DigitalCredentialCreateRequest; Blink digital_credential_creation_options.idl; Blink digital_identity_credential.cc.

DigitalCredential interface (protocol, data, userAgentAllowsProtocol(), toJSON())

Inputs & members. Returned by a resolved navigator.credentials.create({ digital }) promise (and shared with presentation via get({ digital })). Inherits id (empty string "") and type ("digital") from Credential, and defines:

  • credential.protocol (readonly attribute USVString): The issuance protocol identifier selected by the wallet (for example "openid4vci-v1").
  • credential.data ([SameObject] readonly attribute object): The protocol-specific response object returned by the wallet (parsed from the wallet’s JSON response).
  • DigitalCredential.userAgentAllowsProtocol(protocol) (static boolean): Takes a DOMString protocol identifier and returns true if the user agent allows that presentation or issuance protocol (e.g., "openid4vci", "openid4vci-v1", "openid4vp-v1-signed", "org-iso-mdoc") and false otherwise. Does not reflect whether the OS or any installed wallet supports the protocol.
  • credential.toJSON() (object): Returns a JSON-serializable plain object representation ({ id, type, protocol, data }) suitable for sending back to the issuer’s backend via JSON.stringify(credential).

Outputs & behavior. Reading data repeatedly returns the same object reference ([SameObject]). Calling DigitalCredential.userAgentAllowsProtocol("openid4vci-v1") before building an issuance request lets issuers feature-detect Chrome 155 issuance support cleanly without triggering user activation or prompts.

Source: W3C Digital Credentials §7.7 DigitalCredential; userAgentAllowsProtocol(); Blink digital_credential.idl.

Permissions-Policy: digital-credentials-create

Inputs. Policy-controlled feature token "digital-credentials-create" used in the HTTP Permissions-Policy header or the <iframe allow="digital-credentials-create"> attribute. Default allowlist is 'self'.

Outputs & behavior. Controls whether a document is permitted to call navigator.credentials.create({ digital }). Same-origin frames inherit access by default; cross-origin iframes are blocked (rejecting with NotAllowedError) unless the embedder explicitly delegates allow="digital-credentials-create" and the HTTP header permits that origin. Independent of digital-credentials-get (which governs presentation).

Source: W3C Digital Credentials §9 digital-credentials-create; Blink permissions_policy_features.json5.

Context, exposure, and prerequisites

  • Secure Window context only: DigitalCredential and navigator.credentials.create({ digital }) are exposed only on Window in secure contexts ([Exposed=Window, SecureContext]) with a non-opaque origin. Not available in Web Workers or Service Workers.
  • Permissions Policy: Gated by digital-credentials-create (default allowlist 'self'). Cross-origin iframes require explicit delegation via both the parent’s Permissions-Policy header (if restricted) and <iframe allow="digital-credentials-create">.
  • Transient user activation: Every issuance call requires transient user activation (for example, inside a button click handler). Note that Blink evaluates the protocol filter on DigitalCredentialCreationOptions.requests before checking activation, so an unsupported protocol rejects with TypeError even without a click.
  • Platform wallet prerequisites: On Android, requires a compatible wallet app registered with Android IdentityCredential Credential Manager (CredMan). On desktop, Chrome presents a cross-device CTAP QR code so a mobile wallet can complete provisioning over Bluetooth proximity. Android WebView and iOS are not supported.
Source: Blink digital_credential.idl; Blink digital_identity_credential.cc; ChromeStatus 5099333963874304.

Lifecycle, concurrency, and cancellation

  1. Feature & protocol probe (no activation needed): Check "DigitalCredential" in window && typeof DigitalCredential.userAgentAllowsProtocol === "function" && DigitalCredential.userAgentAllowsProtocol("openid4vci-v1") to confirm browser support for issuance before rendering an “Add to Wallet” button.
  2. Single in-flight request: Chrome permits at most one active navigator.credentials.get() or navigator.credentials.create() digital credential exchange at a time; a second overlapping call rejects immediately with NotAllowedError.
  3. Mediated wallet handoff: On Android, Chrome hands the serialized DigitalCredentialCreateRequest list and verified origin to Android CredMan, which displays an OS wallet picker and user consent prompt. On desktop, Chrome displays a cross-device CTAP QR code pairing dialog so the user’s phone wallet receives the request over a proximity-verified channel.
  4. Cancellation: Passing an AbortController.signal in CredentialCreationOptions.signal aborts the Mojo request and dismisses browser/OS UI, rejecting the promise with signal.reason (or AbortError).
  5. Completion & serialization: Upon user approval and wallet completion, the promise resolves to a DigitalCredential whose protocol, data, and toJSON() carry the protocol response back to the issuing site.
Source: Blink digital_identity_credential.cc; W3C Digital Credentials [[Create]]; ChromeStatus 5099333963874304.

Issuing a digital credential with OpenID4VCI, protocol detection, and AbortSignal

function supportsDigitalIssuance(protocol = "openid4vci-v1") {
  return (
    typeof window !== "undefined" &&
    "DigitalCredential" in window &&
    typeof window.DigitalCredential.userAgentAllowsProtocol === "function" &&
    window.DigitalCredential.userAgentAllowsProtocol(protocol)
  );
}

async function issueCredential(credentialOffer, { timeoutMs = 120000 } = {}) {
  const candidateProtocols = ["openid4vci-v1", "openid4vci"].filter((p) =>
    supportsDigitalIssuance(p),
  );

  if (candidateProtocols.length === 0) {
    throw new Error("This browser does not support Digital Credentials issuance.");
  }

  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort("Issuance timed out."), timeoutMs);

  try {
    // Must be called from a user gesture (e.g., button click handler)
    const credential = await navigator.credentials.create({
      digital: {
        requests: candidateProtocols.map((protocol) => ({
          protocol,
          data: credentialOffer,
        })),
      },
      signal: controller.signal,
    });

    if (!(credential instanceof DigitalCredential)) {
      return null;
    }

    // Serialize via toJSON() or inspect protocol & data directly
    return {
      protocol: credential.protocol,
      data: credential.data,
      payload: credential.toJSON(),
    };
  } finally {
    clearTimeout(timer);
  }
}
Source: W3C Digital Credentials §7.5–7.7; Blink digital_identity_credential.cc.

Security and privacy

  • Mandatory user mediation & activation: Every navigator.credentials.create({ digital }) call requires transient user activation and mandatory browser/OS consent UI ([[implicitMediation]] = "required"), preventing silent credential injection or background wallet probing.
  • Origin binding & Permissions Policy: The browser binds the calling document’s secure, non-opaque origin to the issuance request sent to Android CredMan or the cross-device CTAP channel, and blocks cross-origin iframes unless explicitly delegated via digital-credentials-create.
  • Anti-fingerprinting in userAgentAllowsProtocol(): Per W3C Digital Credentials §7.7, DigitalCredential.userAgentAllowsProtocol() MUST reflect only the browser’s static protocol allowlist and MUST NOT vary based on installed wallet applications, OS version, or hardware capabilities.
  • Cross-device proximity check: On desktop, CTAP QR pairing requires physical proximity (Bluetooth) between the desktop browser and the user’s mobile wallet, defending against remote phishing of QR codes.
Source: W3C Digital Credentials §7.7; §9 Permissions Policy; Digital Credentials Explainer.
