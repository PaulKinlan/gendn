WebTransport send groups and send-stream prioritization

Upgrades outgoing WebTransport streams in Chromium from plain WritableStream objects to WebTransportSendStream instances and adds WebTransport.createSendGroup(), WebTransportSendGroup, per-stream sendGroup and sendOrder prioritization, and byte-progress statistics via getStats() on both streams and groups while preserving WritableStream transferability.

Limited availability — send groups, stream prioritization, and stats are not Baseline (base WebTransport is Baseline Newly available since 2026-03-24)

  • Chrome · 159 (desktop, Android, WebView)
  • Edge · Chromium-based (BCD mirror)
  • Firefox · 155 send groups / 121 sendOrder (stats full in 160)
  • Safari · 26.4 (group getStats() partial in BCD)

The base webtransport web-feature is Baseline Newly available since 2026-03-24 per webstatus.dev, but send-group scheduling and send-stream statistics have engine differences recorded in BCD WebTransportSendGroup.json and BCD WebTransportSendStream.json (checked 2026-11-24). Chromium 159 ships send groups, sendOrder, and full stream/group byte stats; the spec’s specialized WebTransportWriter is not yet implemented in Chromium.

why it exists

Real-time media, cloud gaming, and telemetry applications multiplex multiple independent data flows — such as audio frames, video keyframes, delta frames, and control state — over a single WebTransport session. Without send groups and ordering weights, all outgoing streams compete in a flat pool where a burst of large delta frames can starve audio or control streams. Send groups partition outgoing streams into fairness domains so competing flows share bandwidth without starving one another, while sendOrder establishes strict priority among streams within a group (for example, sending keyframes before P-frames). Exposing getStats() on both WebTransportSendStream and WebTransportSendGroup lets applications measure written, sent, and QUIC-acknowledged bytes to detect congestion and drop stale frames proactively.

Source: ChromeStatus motivation (5235261159112704); W3C WebTransport Explainer §8.

Syntax

Normative WebIDL from the W3C WebTransport specification alongside Chromium’s Blink IDL in Chrome 159:

  WebTransportSendGroup createSendGroup();

WebTransport.createSendGroup()

Inputs. Takes no parameters. Must be called on a live (connecting or connected) WebTransport instance.

Outputs. Synchronously returns a newly allocated, distinct WebTransportSendGroup object bound exclusively to the calling WebTransport session. Repeated calls return distinct group instances even when no streams have been assigned yet.

Errors. Throws a synchronous InvalidStateError DOMException if the WebTransport session is already closed or failed. In Chromium, also throws OperationError if the internal 32-bit group identifier counter is exhausted.

Source: W3C WebTransport createSendGroup(); Blink web_transport.cc; WPT sendgroup.https.any.js.

WebTransportSendGroup and getStats()

Inputs. WebTransportSendGroup has no constructor and is created only via transport.createSendGroup(). Its single method getStats() accepts no arguments.

Outputs. group.getStats() returns a Promise resolving to a WebTransportSendStreamStats dictionary summing bytesWritten, bytesSent, and bytesAcknowledged across all active and finalized streams assigned to the group. An empty group resolves immediately with all counters at 0. Finalized stream counters remain included in the group total even after individual streams or the parent WebTransport session close.

Reassignment caveat. In Chromium 159, moving an already-finalized stream to a different group subtracts its lifetime counters from the previous group and adds them to the new group (open spec discussion in w3c/webtransport#802).

Source: W3C WebTransport WebTransportSendGroup; Blink web_transport_send_group.cc; WPT send-stream-stats.https.any.js.

WebTransportSendStream (sendGroup, sendOrder, getStats(), transfer)

Inputs & outputs. WebTransportSendStream subclasses WritableStream and is the runtime object returned by createUnidirectionalStream() and exposed on bidirectional.writable. It preserves stream instanceof WritableStream === true and inherits WritableStream’s transfer steps (postMessage(stream, [stream]) transfers the underlying writable pipe across realms without breaking existing code).

WebTransportSendOptions and WebTransportSendStreamOptions

Inputs. Both createUnidirectionalStream(options) and createBidirectionalStream(options) accept an optional WebTransportSendStreamOptions dictionary inheriting from WebTransportSendOptions:

  • sendGroup (WebTransportSendGroup?, default null): assigns the new stream to the specified send group at creation time. Passing a group from another WebTransport instance causes stream creation to reject with InvalidStateError.
  • sendOrder (long long, default 0): sets the stream’s initial priority weight within its send group (or among ungrouped streams).
  • waitUntilAvailable (W3C spec boolean = false): not yet implemented in Chromium 159 (crbug.com/487117768); stream creation rejects immediately if peer stream limits are exhausted.

Outputs & datagrams. The same WebTransportSendOptions dictionary (sendGroup and sendOrder) is also accepted by transport.datagrams.createWritable(options), returning a WebTransportDatagramsWritable whose sendGroup and sendOrder attributes can be read and updated dynamically.

Source: W3C WebTransport WebTransportSendStreamOptions; Blink web_transport_send_stream_options.idl; WPT sendgroup.https.any.js.

WebTransportSendStreamStats

Inputs & outputs. Returned as the resolved dictionary from both WebTransportSendStream.getStats() and WebTransportSendGroup.getStats(). All three fields are non-negative unsigned long long byte counters initialized to 0:

Fields of WebTransportSendStreamStats
FieldType (default)Meaning
bytesWrittenunsigned long long (0)Total application payload bytes successfully accepted by the stream(s) via write().
bytesSentunsigned long long (0)Total stream bytes transmitted on the wire by the QUIC transport (never exceeds bytesWritten; advances asynchronously).
bytesAcknowledgedunsigned long long (0)Total stream bytes confirmed received by the peer via QUIC acknowledgments (bytesAcknowledged <= bytesSent <= bytesWritten).

Comparing bytesWritten - bytesSent measures local send-buffer backlog; comparing bytesSent - bytesAcknowledged measures in-flight unacknowledged bytes.

Source: W3C WebTransport WebTransportSendStreamStats; WPT send-stream-stats.https.any.js.

Errors, breaking-change note, and recovery

  • InvalidStateError (DOMException): thrown synchronously by transport.createSendGroup() on a closed or failed transport, thrown synchronously by the stream.sendGroup setter when given a group from a different WebTransport session, and rejected asynchronously when passed a foreign sendGroup inside WebTransportSendStreamOptions to createUnidirectionalStream() / createBidirectionalStream().
  • OperationError (DOMException): thrown synchronously by createSendGroup() in Chromium if the 32-bit group ID counter overflows.
  • TypeError: writing a non-BufferSource chunk to a WebTransportSendStream rejects the write promise with TypeError (verified by WPT sendstream-bad-chunk.https.any.html).
  • Constructor / prototype check migration: in Chrome < 159, outgoing streams were plain WritableStream objects (stream.constructor === WritableStream). In Chrome 159+, stream.constructor === WebTransportSendStream while stream instanceof WritableStream remains true. Replace exact constructor equality checks with instanceof WritableStream or feature-detect "WebTransportSendStream" in globalThis.
  • Cross-engine getStats() fallback: Firefox < 160 rejects WebTransportSendStream.getStats() with NotSupportedError and resolves WebTransportSendGroup.getStats() with an empty object {}; wrap getStats() calls in try/catch and verify typeof stats.bytesAcknowledged === "number".
Source: ChromeStatus interop & compatibility risks; WPT sendstream-bad-chunk.https.any.js; BCD WebTransportSendStream.json.

Context and exposure

WebTransportSendGroup and WebTransportSendStream are exposed in Window and Worker (including dedicated, shared, and service workers) and require a Secure Context (https:// or http://localhost). Creating streams or send groups requires an active WebTransport session; no special Permissions Policy or user activation is needed.

Source: W3C WebTransport §7; Blink web_transport_send_stream.idl.

Lifecycle and state transitions

A WebTransportSendGroup is created while its parent WebTransport is connecting or connected and remains valid for the session’s lifetime (including post-close getStats() queries). Streams can be attached to a send group at creation time via options.sendGroup and moved between groups (or ungrouped with null) at any point before closing; each sendGroup or sendOrder mutation sends an immediate asynchronous priority update over Mojo to Chromium’s QUIC network stack. When a stream finishes or aborts, its final byte counters are snapshotted into the stream and rolled into its current group’s finalized totals so subsequent getStats() calls resolve immediately without a network-service round trip. Calling postMessage(stream, [stream]) transfers the underlying WritableStream pipe across realms.

Source: Blink web_transport_send_stream.cc; Blink web_transport_send_group.cc; WPT send-stream-stats.https.any.js.

Examples

No live interactive demo exists yet on the Chrome Platform Showcase for Chrome 159 (checked 2026-11-24). The examples below demonstrate send-group isolation, dynamic priority elevation, and congestion-aware byte statistics.

Isolating audio and video flows with send groups and sendOrder

const transport = new WebTransport("https://media.example.com/ingest");
await transport.ready;

// Feature-detect send groups before creating fairness domains
const supportsSendGroups = typeof transport.createSendGroup === "function";
const audioGroup = supportsSendGroups ? transport.createSendGroup() : null;
const videoGroup = supportsSendGroups ? transport.createSendGroup() : null;

// Pass WebTransportSendStreamOptions ({ sendGroup, sendOrder }) to prioritize keyframes over delta frames
const keyframeStream = await transport.createUnidirectionalStream(
  videoGroup ? { sendGroup: videoGroup, sendOrder: 100 } : undefined,
);
const deltaStream = await transport.createUnidirectionalStream(
  videoGroup ? { sendGroup: videoGroup, sendOrder: 10 } : undefined,
);

// Audio uses an independent send group so video bursts do not starve it
const audioStream = await transport.createUnidirectionalStream(
  audioGroup ? { sendGroup: audioGroup, sendOrder: 50 } : undefined,
);

const encoder = new TextEncoder();
const writer = keyframeStream.getWriter();
await writer.write(encoder.encode("keyframe-payload"));
await writer.close();

// Dynamically reprioritize or reassign an open stream
if ("sendOrder" in deltaStream) {
  deltaStream.sendOrder = 200;       // promote within videoGroup
  deltaStream.sendGroup = null;      // or detach to the ungrouped pool
}
Source: W3C WebTransport Explainer §8; WPT sendgroup.https.any.js.

Monitoring send backlog with getStats() and cross-browser guards

async function readSendProgress(streamOrGroup) {
  if (typeof streamOrGroup?.getStats !== "function") {
    return null;
  }
  try {
    const stats = await streamOrGroup.getStats();
    // Firefox < 160 resolves group.getStats() with {}
    if (typeof stats.bytesAcknowledged !== "number") {
      return null;
    }
    return {
      written: stats.bytesWritten,
      queuedLocally: stats.bytesWritten - stats.bytesSent,
      inFlight: stats.bytesSent - stats.bytesAcknowledged,
      acked: stats.bytesAcknowledged,
    };
  } catch (err) {
    // Firefox < 160 rejects WebTransportSendStream.getStats() with NotSupportedError
    if (err instanceof DOMException && err.name === "NotSupportedError") {
      return null;
    }
    throw err;
  }
}

const groupProgress = await readSendProgress(videoGroup);
if (groupProgress && groupProgress.queuedLocally > 256 * 1024) {
  // Back off or drop low-priority delta frames
  await deltaStream.abort(new WebTransportError("Congestion drop", { streamErrorCode: 1 }));
}

Security and privacy

Send groups and stream prioritization introduce no new network permissions, origin boundaries, or cross-origin channels. Every WebTransportSendGroup is scoped to a single secure-context WebTransport session, and Chromium rejects attempts to assign a send group created on one WebTransport instance to a stream on another instance (throwing InvalidStateError). Byte statistics returned by getStats() only report counters for data written and transmitted by the application’s own streams and groups, without exposing shared network state from other origins. ChromeStatus records security and privacy reviews as Pending (checked 2026-11-24).

Source: ChromeStatus security_risks (5235261159112704); W3C WebTransport Privacy & Security Considerations.
