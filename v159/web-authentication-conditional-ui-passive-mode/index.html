Web Authentication Conditional UI Passive Mode

Conditional UI Passive Mode (also referred to as “Ambient” sign-in) lets a site invoke navigator.credentials.get() with mediation: "conditional" and uiMode: "passive" so the browser immediately surfaces available passkeys (and optionally saved passwords) in an unobtrusive, non-modal prompt — without requiring a sign-in form or autofill-tagged <input> on the page. If the user has no eligible credentials, no UI is shown and the promise stays pending.

Limited availability — Origin Trial in Chrome 159 (desktop only); not Baseline (parent WebAuthn is Baseline Widely available)

  • Chrome · 159–170 Origin Trial (desktop)
  • Edge · No release / no BCD entry
  • Firefox · No signal
  • Safari · No signal

Passive Mode has no dedicated web-feature id or BCD entry yet (checked 2026-11-24 against BCD api/CredentialsContainer.json and BCD api/PublicKeyCredential.json). The parent WebAuthn web-feature is Baseline Widely available since 2024-03-07 per webstatus.dev, which does not cover uiMode: "passive" or conditionalPassiveGet. Always feature-detect via PublicKeyCredential.getClientCapabilities() and retain an explicit sign-in path.

Origin Trial (Desktop Chrome 159–170) — draft API subject to change.

This feature is an active Origin Trial on desktop platforms (Windows, macOS, Linux, ChromeOS) from Chrome 159 through Chrome 170, backed by the open specification pull request w3c/webauthn#2485. Enable it in one of two ways:

  • Production Origin Trial: register for trial WebAuthenticationAmbient (ChromeStatus Origin Trial ID 942941171980697601) and serve the token via an Origin-Trial HTTP header or <meta http-equiv="origin-trial"> tag.
  • Local testing (no token): enable chrome://flags/#web-authentication-ambient-signin or launch Chrome with --enable-features=WebAuthenticationAmbientSignin (Blink runtime feature WebAuthenticationAmbient in runtime_enabled_features.json5).

why it exists

Standard WebAuthn Conditional UI (mediation: "conditional") integrates passkeys into form autofill, which works well on dedicated sign-in pages that contain an <input autocomplete="username webauthn"> field. On content pages without a login form — such as a paywalled article or an e-commerce catalog visited by a signed-out returning user — conditional autofill cannot surface credentials, while a modal WebAuthn dialog would interrupt users who have no passkey or do not wish to sign in. Passive Mode bridges that gap: it lets the page request silent discovery on load (without user activation), showing a quiet, permission-bubble-style suggestion in Chrome’s top-left chrome only when matching credentials exist, and remaining completely invisible otherwise.

Source: Explainer: Conditional UI without Autofill; ChromeStatus motivation (5068149209825280).

Syntax

Relevant WebIDL from Blink’s credential_request_options.idl and w3c/webauthn PR #2485 (checked 2026-11-24):

enum CredentialUiModeRequirement {
  "active",
  "immediate",
  "passive"
};

partial dictionary CredentialRequestOptions {
  CredentialMediationRequirement mediation = "optional";
  CredentialUiModeRequirement uiMode = "active";
  PublicKeyCredentialRequestOptions publicKey;
  boolean password = false;
  AbortSignal signal;
};

partial enum ClientCapability {
  "conditionalPassiveGet"
};

“If options.uiMode is passive, the prompt SHOULD be minimally disruptive to other user activity such that the user does not have to interact with the prompt.”

Spec vs. Chrome 159 note: PR #2485 and the explainer also propose uiMode: "active" with mediation: "conditional" and capability "conditionalActiveGet", and name the spec enum CredentialUiMode. In Chrome 159’s Origin Trial, Blink defines CredentialUiModeRequirement and implements only Passive Mode (uiMode: "passive" + "conditionalPassiveGet"); "conditionalActiveGet" is not implemented in Blink’s public_key_credential.cc (verified 2026-11-24). Also note that the explainer’s prose briefly writes “the PublicKeyCredentialRequestOptions contains uiMode: 'passive'”, while its code example, PR #2485 algorithm, and Blink IDL all place uiMode on the top-level CredentialRequestOptions dictionary.

This reference documents three surfaces: CredentialRequestOptions.uiMode, ClientCapability "conditionalPassiveGet", and the passive conditional mediation ceremony (lifecycle, coexistence with autofill, errors, and security).

Source: Blink credential_request_options.idl; w3c/webauthn PR #2485; Explainer: Conditional UI without Autofill.

CredentialRequestOptions.uiMode — inputs and valid combinations

Input. uiMode is an optional member on the CredentialRequestOptions dictionary passed to navigator.credentials.get(options). In Blink’s IDL its enum type is CredentialUiModeRequirement (values "active", "immediate", "passive"; default "active"). To activate Conditional UI Passive Mode, you MUST pass both:

  • mediation: "conditional"
  • uiMode: "passive"
  • publicKey: a valid PublicKeyCredentialRequestOptions object (with challenge, optional rpId, etc.)
  • password: true (optional): includes saved PasswordCredential entries alongside discoverable passkeys in the same passive bubble.
  • signal (optional): an AbortSignal used to cancel the pending request (for example before launching a modal sign-in or passkey registration).

Output. navigator.credentials.get() returns a Promise<Credential | null>. When the user selects a passkey in the passive bubble (or autofill dropdown), the promise resolves with a PublicKeyCredential. If password: true was also passed and the user chooses a saved password, it resolves with a PasswordCredential. If the user has no eligible credentials or ignores/dismisses the passive bubble without interacting with autofill, the promise never resolves (unless aborted via signal or the document is unloaded).

ClientCapability — "conditionalPassiveGet"

Inputs & invocation. Call the static method await PublicKeyCredential.getClientCapabilities() (no arguments; exposed on Window in a secure context).

Outputs. Resolves to a plain record (Record<DOMString, boolean>) mapping capability names to booleans. When the Origin Trial token or flag is active on a supported desktop platform, the returned object includes the key "conditionalPassiveGet" with a boolean value indicating whether the client can present Passive Mode conditional UI. When the runtime feature WebAuthenticationAmbient is disabled, Blink explicitly removes "conditionalPassiveGet" from the returned map (so caps.conditionalPassiveGet is undefined).

Errors. Rejects with InvalidStateError if the calling document’s execution context is detached. In browsers predating getClientCapabilities() (Chrome < 133, Firefox < 135, Safari < 17.4), the static method itself is undefined, so guard with typeof PublicKeyCredential?.getClientCapabilities === "function".

Source: Blink public_key_credential.cc (OnGetClientCapabilitiesComplete); w3c/webauthn PR #2485; BCD api/PublicKeyCredential.json.

Passive conditional mediation ceremony — lifecycle and coexistence

In w3c/webauthn PR #2485, the authentication algorithm initializes a per-request flag conditionalNonAutofillTriggered = false and runs silent credential discovery:

  1. No user activation required. The page may call navigator.credentials.get() immediately on page load.
  2. Silent discovery. The browser checks for eligible discoverable credentials for the RP without showing UI. If none exist, no bubble is displayed and the promise remains unresolved.
  3. One-shot non-modal prompt. If eligible credentials exist and conditionalNonAutofillTriggered is false, the browser sets the flag to true and displays a non-modal suggestion bubble (top-left of the Chrome desktop window, similar to a permission prompt) listing credential metadata such as name and displayName.
  4. Coexistence with autofill. If the page also contains an <input> or <textarea> with autocomplete="username webauthn" (or "current-password webauthn"), dismissing or ignoring the passive bubble does not reject the promise: focusing that input still offers the same credentials in autofill UI under the same pending request.
  5. Selection & settlement. Selecting a credential in either surface issues the assertion to that authenticator and resolves the promise once completed.
  6. Cancellation & exclusivity. Pass an AbortController’s signal and call controller.abort() before starting a modal navigator.credentials.get() or navigator.credentials.create() call, because WebAuthn allows only one pending request per document at a time.
Source: w3c/webauthn PR #2485 (#GetAssn-ConditionalMediation-NonAutofill); Explainer: Conditional UI without Autofill; Author reference demo script.js.

Context, permissions, and exposure

  • Exposure: Window only (navigator.credentials and PublicKeyCredential are not exposed in Workers).
  • Secure context: Required (https:// or localhost).
  • Cross-origin iframes: Permitted when the embedding frame delegates the publickey-credentials-get Permissions Policy (allow="publickey-credentials-get"). In Chrome, the passive bubble title displays the requesting frame’s origin so users can verify which site is requesting sign-in.
  • User activation: Not required — passive mode is specifically designed to be invoked on page load.
  • Platform scope in Chrome 159: Desktop only (Windows, macOS, Linux, ChromeOS) during the Origin Trial.
Source: ChromeStatus API record (5068149209825280); Explainer — Cross-origin iframes; Blink runtime_enabled_features.json5.

Examples

No interactive demo exists yet on the Chrome Platform Showcase for Chrome 159. The feature owner’s standalone prototype demo is live at kenrb.github.io/test/ambient/.

Feature detection and passive sign-in on page load

let passiveController = null;

async function startPassiveSignIn(challengeBytes) {
  if (typeof PublicKeyCredential?.getClientCapabilities !== "function") {
    return;
  }

  const caps = await PublicKeyCredential.getClientCapabilities();
  if (!caps.conditionalPassiveGet) {
    // Passive mode unavailable (no Origin Trial / flag or unsupported browser).
    // Fall back to explicit sign-in link or standard conditional autofill.
    return;
  }

  passiveController = new AbortController();

  try {
    const credential = await navigator.credentials.get({
      signal: passiveController.signal,
      mediation: "conditional",
      uiMode: "passive",
      publicKey: {
        challenge: challengeBytes,
        rpId: window.location.hostname,
        userVerification: "preferred",
      },
      // Optional: also surface saved passwords in the same passive bubble.
      password: true,
    });

    if (credential?.type === "public-key") {
      // Send assertion to server to verify challenge and establish a session.
      await verifyPasskeyAssertion(credential);
    } else if (credential?.type === "password") {
      await verifyPasswordCredential(credential);
    }
  } catch (err) {
    if (err.name === "AbortError") {
      return; // Cancelled intentionally (e.g. user clicked Sign In or Create Passkey).
    }
    console.error("Passive sign-in failed:", err);
  }
}

// Always abort a pending passive request before calling modal create() or get():
async function onExplicitSignInClick() {
  passiveController?.abort();
  passiveController = null;
  // Proceed with modal sign-in...
}

Coexisting with a sign-in form (passive bubble + autofill)

When a page invokes navigator.credentials.get() with mediation: "conditional" and uiMode: "passive" alongside a login form, ignoring the passive bubble keeps the request active for autofill:

<!-- If the user ignores the passive bubble, focusing this input still offers
     the same credentials from the single pending conditional request. -->
<form action="/login" method="post">
  <label for="acct">Username</label>
  <input id="acct" name="username" autocomplete="username webauthn" required>
  <button type="submit">Continue</button>
</form>

Security and privacy

  • No credential-presence oracle: Just like standard Conditional UI, when the user has no eligible credentials for the Relying Party, no UI is displayed and the returned promise never resolves or rejects. A site cannot probe whether a signed-out visitor owns a passkey or saved password.
  • Clickjacking mitigation: Chrome renders the passive bubble using its permissions prompt infrastructure, which applies an input-delay clickjacking protection preventing clicks on bubble buttons immediately after display.
  • Cross-origin framing clarity: When invoked inside a cross-origin iframe (requiring the publickey-credentials-get Permissions Policy), Chrome displays the requesting frame’s origin in the bubble title so users can verify the authentic recipient of the credential.
  • Review status: ChromeStatus lists Chromium’s security review, privacy review, and W3C TAG review #1291 as Pending (checked 2026-11-24).
Source: ChromeStatus security_risks & review status; Explainer: Conditional UI without Autofill; w3ctag/design-reviews#1291.
