CSSImportRule.styleSheet

CSSImportRule.styleSheet is now nullable in Chromium and returns null whenever an @import rule has no associated stylesheet — notably when its supports(...) import condition evaluates to false. This aligns Chromium with CSSOM, CSS Cascade 5, Firefox, and WebKit, and requires callers inspecting conditional @import rules to guard against null before accessing styleSheet.cssRules or other CSSStyleSheet properties.

Newly converging across engines — nullable styleSheet on false supports() has no BCD subfeature yet (base @import is Baseline Widely available)

  • Chrome · 159 (desktop, Android, WebView)
  • Edge · Chromium-based (inherits 159; no BCD subfeature yet)
  • Firefox · Shipped (Bugzilla 1427715)
  • Safari · WebKit IDL nullable since March 2025 (PR #42784; exact Safari version unrecorded in BCD)

The base import (@import) web-feature is Baseline Widely available since 2018-01-29 per webstatus.dev, and BCD api/CSSImportRule.json records base styleSheet support since Chrome 1 / Edge 12 / Firefox 1 / Safari 1. However, neither BCD nor MDN’s CSSImportRule.styleSheet article (which still states “An @import at-rule always has an associated stylesheet” as of 2026-11-24) tracks nullable styleSheet behavior yet.

why it exists

CSS Cascade 5 allows @import rules to carry a supports(...) feature-query condition so browsers skip fetching fallback stylesheets on engines that already support newer features. Both CSSOM and CSS Cascade 5 require CSSImportRule.styleSheet to be nullable (CSSStyleSheet?) and to return null when no stylesheet is associated — specifically including when a supports() condition evaluates to false. Before Chrome 159, Blink exposed a non-null CSSStyleSheet object even when the supports() condition did not match, making it impossible to distinguish an active imported stylesheet from a skipped conditional import via rule.styleSheet and diverging from Firefox and WebKit. Chrome 159 aligns Chromium with both specifications.

Source: ChromeStatus summary & motivation (5123480866783232); CSS Cascade 5 §2.1.

Syntax and interface contract

The normative WebIDL for CSSImportRule in CSSOM §6.4.4 declares styleSheet as a nullable read-only attribute returning CSSStyleSheet?:

[Exposed=Window]
interface CSSImportRule : CSSRule {
  readonly attribute USVString href;
  [SameObject, PutForwards=mediaText] readonly attribute MediaList media;
  [SameObject] readonly attribute CSSStyleSheet? styleSheet;
  readonly attribute CSSOMString? layerName;
  readonly attribute CSSOMString? supportsText;
};

/* CSS Cascade 5 — conditional @import syntax */
@import [ <url> | <string> ]
        [ layer | layer(<layer-name>) ]?
        [ supports([ <supports-condition> | <declaration> ]) ]?
        <media-query-list>?;

“The styleSheet attribute must return the associated CSS style sheet, if any, or null otherwise.”

“Additionally, if a <supports-condition> blocks the application of the imported style sheet, the UA must not fetch the style sheet (unless it is loaded through some other link) and must return null for the import rule’s CSSImportRule.styleSheet value (even if it is loaded through some other link).”

This reference covers three parts of the contract: the nullable CSSImportRule.styleSheet getter, conditional @import supports() evaluation and lifecycle, and companion CSSImportRule attributes.

Source: CSSOM §6.4.4 (normative quote fetched 2026-11-24); CSS Cascade 5 §2.1 (normative quote fetched 2026-11-24).

CSSImportRule.styleSheet — inputs and outputs

Inputs. Accessed as a zero-argument read-only getter (rule.styleSheet) on any CSSImportRule instance obtained from sheet.cssRules (where rule instanceof CSSImportRule and rule.type === CSSRule.IMPORT_RULE). Because the attribute is read-only, attempting to assign rule.styleSheet = ... fails silently in sloppy mode and throws a TypeError in strict mode.

Outputs. Returns either a CSSStyleSheet object (annotated [SameObject] when present, so repeated reads return the same wrapper identity) or null when the @import rule has no associated stylesheet:

Conditional @import supports() evaluation and lifecycle

Inputs & outputs. When a stylesheet parses an @import rule carrying supports(<supports-condition> | <declaration>) (a bare declaration such as supports(display: flex) is interpreted as a <supports-decl>), the browser evaluates the supports condition statically against its own CSS feature support:

  • Rule still appears in cssRules: Both matching and non-matching @import rules produce a CSSImportRule entry in parentStyleSheet.cssRules (verified in WPT cssimportrule.html, where a <style> containing one true and one false supports() import produces cssRules.length === 2).
  • No fetch & null sheet on false condition: When the supports condition is false, the user agent does not fetch the URL for this rule and sets no associated stylesheet, so rule.styleSheet === null. Even if the exact same URL is imported unconditionally elsewhere on the page, this rule’s styleSheet remains null.
  • Cascade layer ordering: Per CSS Cascade 5 §2, an optional layer or layer(<layer-name>) declaration on an @import is subject to the rule’s import conditions (as if wrapped in an @supports block).

Lifecycle. Feature support conditions are invariant for a given browser session, so an @import blocked by a false supports() condition stays null for the lifetime of that CSSImportRule. Unlike <media-query-list> conditions (which can change dynamically as the viewport or print mode changes), a false supports() condition never transitions to a loaded stylesheet without replacing the rule.

Source: CSS Cascade 5 §2 & §2.1; WPT css/cssom/cssimportrule.html.

Errors, migration risks, and recovery

Accessing rule.styleSheet itself does not throw an exception. However, ChromeStatus explicitly flags a real migration hazard for Chromium-only code and CSS tooling:

  • TypeError on unchecked dereference: Script that walks sheet.cssRules and writes rule.styleSheet.cssRules without checking rule.styleSheet !== null will now throw TypeError: Cannot read properties of null (reading 'cssRules') in Chrome 159+ when encountering an @import with a false supports() condition (matching Firefox and WebKit). Guard with optional chaining (rule.styleSheet?.cssRules) or an explicit if (rule.styleSheet) check.
  • SecurityError on cross-origin sheets: When rule.styleSheet is non-null, reading rule.styleSheet.cssRules on a cross-origin stylesheet served without CORS headers still throws DOMException (SecurityError) per standard CSSOM origin checks; wrap recursive stylesheet walkers in try { ... } catch.
  • Read-only assignment: Assigning to read-only attributes (styleSheet, href, layerName, or supportsText) fails silently in sloppy mode and throws a TypeError in strict mode; by contrast, assigning a string to media succeeds via [PutForwards=mediaText].
  • Android WebView note: ChromeStatus notes the same null-check compatibility risk applies to embedded Android WebView content; the change is guarded by CSSImportRuleStyleSheetNullable.
Source: ChromeStatus interop_compat_risks & webview_risks (5123480866783232); CSSOM §6.4.4.

Context and exposure

CSSImportRule is exposed only in Window contexts ([Exposed=Window] in CSSOM WebIDL), not in Web Workers or Worklets. Reading rule.styleSheet requires no secure context, permission, or user activation; it operates on any accessible CSSStyleSheet (including <style> elements, same-origin <link rel="stylesheet"> sheets, and shadow root stylesheets).

Source: CSSOM §6.4.4 ([Exposed=Window]).

Examples

No interactive demo exists yet on the Chrome Platform Showcase for Chrome 159 (checked 2026-11-24).

Checking CSSImportRule.styleSheet for conditional @import supports() rules

<style id="conditional-imports">
  @import url("modern-grid.css") supports(display: flex);
  @import url("legacy-fallback.css") supports(not (display: flex));
</style>

<script>
  const { cssRules } = document.getElementById("conditional-imports").sheet;

  for (const rule of cssRules) {
    if (!(rule instanceof CSSImportRule)) continue;

    if (rule.styleSheet === null) {
      // Condition did not match (e.g. supports(not (display: flex)) on modern browsers):
      // stylesheet was not fetched and has no associated CSSStyleSheet,
      // while href, supportsText, layerName, and media remain inspectable.
      console.log(
        `Skipped @import ${rule.href}`,
        { supports: rule.supportsText, layer: rule.layerName, media: rule.media.mediaText }
      );
      continue;
    }

    console.log(`Loaded @import ${rule.href}:`, rule.styleSheet);
  }
</script>
Source: WPT css/cssom/cssimportrule.html; CSS Cascade 5 §2.1.

Null-safe and CORS-safe recursive stylesheet walker

function collectActiveStyleSheets(rootSheet, visited = new Set()) {
  if (!rootSheet || visited.has(rootSheet)) return visited;
  visited.add(rootSheet);

  let rules;
  try {
    rules = rootSheet.cssRules;
  } catch (err) {
    // Cross-origin stylesheet without CORS headers throws SecurityError.
    return visited;
  }

  for (const rule of rules) {
    if (rule instanceof CSSImportRule && rule.styleSheet !== null) {
      collectActiveStyleSheets(rule.styleSheet, visited);
    }
  }
  return visited;
}
Source: CSSOM §6.4.4; ChromeStatus compatibility guidance (5123480866783232).

Security and privacy

Returning null from CSSImportRule.styleSheet when a supports() condition is false reduces unnecessary network fetches and avoids synthesizing a placeholder CSSStyleSheet object for a stylesheet that was never loaded. CSS Cascade 5 §2.1 further specifies that styleSheet must remain null even if the same URL was loaded elsewhere in the document, preventing a blocked conditional import from exposing another link’s stylesheet handle. Cross-origin CSSStyleSheet.cssRules origin restrictions remain unchanged whenever styleSheet is non-null. ChromeStatus notes no new security risks and lists security/privacy reviews as Pending (checked 2026-11-24).

Source: CSS Cascade 5 §2.1; ChromeStatus security_risks & review status (5123480866783232).
