WebTransport keying material export

Adds WebTransport.prototype.exportKeyingMaterial(label, context, outputLength), returning a Promise<Uint8Array> of cryptographic keying material derived from the session’s underlying TLS exporter for channel binding and application-level authentication without exposing TLS traffic keys.

Limited availability — 3-argument exportKeyingMaterial() is not Baseline (parent WebTransport is Baseline Newly available since 2026-03-24)

  • Chrome · 159 (desktop, Android, WebView; 3-arg API)
  • Edge · Mirrors Chromium (159)
  • Firefox · 155 (2-arg) / 160 (3-arg, desktop only; Android false)
  • Safari · 27.3 in BCD (3-arg landed in WebKit PR #69982)

The parent webtransport web-feature is Baseline Newly available since 2026-03-24 per webstatus.dev, but exportKeyingMaterial() is not part of that Baseline set. In BCD api/WebTransport.json (checked 2026-11-24), exportKeyingMaterial lists Chrome 159, Firefox 155 (desktop; Firefox Android false), and Safari 27.3, while the outputLength_parameter subfeature still reads Chrome false and Safari false (lagging Chrome 159’s 3-argument ship).

Chrome 159 specifics & cross-browser signature differences

  • Exact TLS exporter label & context wire format: in Chromium’s DedicatedWebTransportHttp3Client::ExportKeyingMaterial() and SerializeWebTransportExporterContext(), Chrome invokes the QUIC crypto stream’s TLS exporter with the fixed label "EXPORTER-WebTransport" and an exporter context encoded as [uint64 session_id (HTTP/3 CONNECT stream ID)][uint8 label_length][label][uint8 context_length][context] (matching draft-ietf-webtrans-http3 §4.8). Including the CONNECT stream ID ensures that separate WebTransport sessions sharing one HTTP/3 connection derive distinct keying material even with identical application labels and contexts. Servers must construct the exact same exporter label, context framing, and output length — a mismatch produces different bytes with no protocol error.
  • Enforced bounds: Chromium enforces 0 ≤ label.byteLength ≤ 255, 0 ≤ context.byteLength ≤ 255, and 1 ≤ outputLength ≤ 4096 in both Blink (web_transport.cc) and the network service, rejecting out-of-range inputs with RangeError and missing required arguments with TypeError.
  • Calling before ready: calls made while the session is still connecting are queued in Blink (PendingExportKeyingMaterialRequest) and dispatched once the session connects, or rejected with InvalidStateError if the session closes or fails before export completes (asserted by WPT export-keying-material.https.any.js).
  • Distinguishing 3-arg vs legacy 2-arg signatures: checking "exportKeyingMaterial" in WebTransport.prototype alone matches Firefox 155–159’s earlier 2-argument form (which omitted outputLength). Check WebTransport.prototype.exportKeyingMaterial.length === 3 to detect the standardized 3-argument signature.
// Distinguish the standardized 3-argument API (Chrome 159+, Firefox 160+, WebKit PR #69982)
// from Firefox 155–159's earlier 2-argument signature.
const supportsStandardExporter =
  typeof WebTransport !== "undefined" &&
  typeof WebTransport.prototype.exportKeyingMaterial === "function" &&
  WebTransport.prototype.exportKeyingMaterial.length === 3;

if (supportsStandardExporter) {
  const enc = new TextEncoder();
  const wt = new WebTransport("https://example.com:4433/wt");
  // Safe to invoke while connecting; queues until the session connects (or rejects if closed).
  const keyBytes = await wt.exportKeyingMaterial(
    enc.encode("app.example/channel-binding-v1"),
    enc.encode("session-auth"),
    32, // 1..4096 bytes in Chromium
  );
  console.log(`Derived ${keyBytes.byteLength} bytes of session-bound keying material`);
}
