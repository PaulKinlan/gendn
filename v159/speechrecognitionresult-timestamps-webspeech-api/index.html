SpeechRecognitionResult Timestamps (WebSpeech API)

Adds two read-only double attributes — speechStartTime and speechEndTime — to SpeechRecognitionResult, reporting the acoustic start and end offsets (in seconds) of each recognized speech segment on the recognition session’s audio timeline, floored to 2 ms multiples and returning 0.0 when unavailable. In Chromium, the same feature also rebases SpeechRecognitionEvent.timeStamp onto the recognizer’s latest audio end time. This Chrome 159 shipped reference supersedes the pre-rename Chrome 153 developer-trial page (which documented the earlier audioStartTime / audioEndTime proposal).

Limited availability — Chromium desktop (Windows, Mac, Linux) only (not Baseline; Firefox no position, Safari no signal)

  • Chrome · 159 (stable 2026-12-08; Windows, Mac, Linux desktop; ChromeOS, Android, WebView off)
  • Edge · Chromium-based (mirrors Chromium desktop)
  • Firefox · Not supported (Closed Without a Position)
  • Safari · Not supported (No signal)

No dedicated webstatus.dev entry exists for these attributes; the host speech-recognition web-feature is Baseline Limited availability (checked 2026-11-27). ChromeStatus 5811907077472256 lists this feature as Enabled by default in Chrome 159 (stable 2026-12-08 per ChromeStatus channels) on desktop only (android: null, webview: null), and Chromium’s runtime_enabled_features.json5 enables WebSpeechTimestamps on Windows, Mac, and Linux via CL 8836060 while keeping ChromeOS, Android, and WebView off. BCD api/SpeechRecognitionResult.json does not yet carry keys for speechStartTime or speechEndTime (covering only isFinal, item, and length, verified 2026-11-27); the compatibility table below is an interim primary-source compilation.

Why it exists

Previously, a SpeechRecognitionResult exposed what was recognized (transcript and confidence) but nothing about when in the audio stream that phrase was spoken. Voice Activity Detection events (speechstart / speechend) fire only once per continuous session or after 500–1500 ms of trailing silence, and result event delivery time conflates acoustic speech boundaries with ASR processing and main-thread queuing delays.

Attaching speechStartTime and speechEndTime (in seconds on the session audio timeline) directly to each SpeechRecognitionResult unlocks four developer workflows: generating synchronized WebVTT/SRT subtitle cues (new VTTCue(start, end, text)), click-to-seek meeting transcripts, live WebRTC caption lip-sync, and text-based audio/video editing — while Chromium’s SpeechRecognitionEvent.timeStamp rebasing lets latency-sensitive apps measure delivery lag cleanly against performance.now().

Source: ChromeStatus summary & motivation (5811907077472256); Web Speech API Timestamps explainer; WebAudio/web-speech-api#191.

Syntax & WebIDL

Verbatim shipped Chromium WebIDL from speech_recognition_result.idl (matching Web Speech API §4.1.8, noting Chromium retains [LegacyNoInterfaceObject] on the host interface):

[
    LegacyNoInterfaceObject
] interface SpeechRecognitionResult {
    readonly attribute unsigned long length;
    getter SpeechRecognitionAlternative item(unsigned long index);
    readonly attribute boolean isFinal;
    [RuntimeEnabled=WebSpeechTimestamps] readonly attribute double speechStartTime;
    [RuntimeEnabled=WebSpeechTimestamps] readonly attribute double speechEndTime;
};

The two read-only attributes live on SpeechRecognitionResult, not on SpeechRecognitionAlternative. Pre-existing members (length, item(), isFinal) are unchanged and documented on MDN SpeechRecognitionResult. This reference documents the three Chrome 159 behaviors gated by WebSpeechTimestamps: SpeechRecognitionResult.speechStartTime, SpeechRecognitionResult.speechEndTime, and SpeechRecognitionEvent.timeStamp rebasing.

Source: Web Speech API §4.1.8; Blink speech_recognition_result.idl.

SpeechRecognitionResult.speechStartTime

Inputs & receiver. Read-only attribute with no parameters, accessed on any SpeechRecognitionResult instance returned in event.results[i] during a result event (both interim results with isFinal === false and final results with isFinal === true).

Outputs & timeline semantics. Returns a non-nullable double representing the start of the speech segment corresponding to this recognition result, as an offset in seconds on the session audio timeline — where 0.0 is the first audio frame consumed from the audio source (microphone or supplied MediaStreamTrack) and time advances with the duration of each consumed audio frame. Because it is measured on the audio stream timeline rather than a system clock, it is unaffected by audio output latency, device/system clock drift, or faster-than-real-time recognition. In Chromium (speech_recognition_result.cc), the getter returns 0.0 when the recognizer did not report a timing value, and otherwise floors the base::TimeDelta to a multiple of 2 ms (kFuzzInterval = base::Milliseconds(2)) before returning .InSecondsF().

Source: Web Speech API §4.1.8 speechStartTime; Blink speech_recognition_result.cc.

SpeechRecognitionResult.speechEndTime

Inputs & receiver. Read-only attribute with no parameters, accessed on any SpeechRecognitionResult instance inside event.results (both interim and final results).

Outputs & timeline semantics. Returns a non-nullable double representing the end of the speech segment corresponding to this recognition result, in seconds on the same session audio timeline as speechStartTime. Returns 0.0 when timing is absent from the underlying recognizer; otherwise floored to a 2 ms multiple and converted to seconds. For a valid timed speech segment, 0 <= result.speechStartTime <= result.speechEndTime and result.speechEndTime - result.speechStartTime yields segment duration in seconds (passable directly to new VTTCue(result.speechStartTime, result.speechEndTime, text)).

Detecting unavailable timing. Because both attributes are non-nullable double returning 0.0 when absent, distinguish a timed utterance from an untimed backend by checking typeof result.speechEndTime === "number" && result.speechEndTime > 0 (or result.speechEndTime > result.speechStartTime) rather than checking for !== null.

Source: Web Speech API §4.1.8 speechEndTime; Blink speech_recognition_result.cc.

SpeechRecognitionEvent.timeStamp rebasing (Chromium WebSpeechTimestamps)

Inputs & mechanism. In Chromium’s speech_recognition.cc (updated in CL 8797156), when AudioStarted() fires the audiostart event, Blink records audio_start_ticks_ = base::TimeTicks::Now(). When ResultRetrieved() processes a batch of results, it computes latest_audio_end_time (the maximum audio_end_time across results in the batch) and sets the dispatched SpeechRecognitionEvent’s platform timestamp as:

  • If WebSpeechTimestamps is enabled, latest_audio_end_time.has_value(), and !audio_start_ticks_.is_null(): event_time_stamp = std::min(audio_start_ticks_ + *latest_audio_end_time, base::TimeTicks::Now()).
  • Otherwise (feature disabled, recognizer supplied no timestamps, or audiostart has not fired): falls back to base::TimeTicks::Now().
  • nomatch events (SpeechRecognitionEvent::CreateNoMatch) carry no recognized speech segment and always use base::TimeTicks::Now().

Outputs & practical effect. Because event.timeStamp on a timed result event is rebased onto when the latest speech segment ended (clamped so it is never later than now, since audiostart is reported after the first captured audio chunk), comparing performance.now() - event.timeStamp in milliseconds measures end-to-end recognition and IPC delivery lag.

Source: Blink speech_recognition.cc (ResultRetrieved, AudioStarted); Blink speech_recognition_event.cc; CL 8797156.

Errors, context/exposure, and lifecycle

Errors & failure modes. Reading speechStartTime or speechEndTime never throws. Because both attributes are readonly, attempting to assign to them fails silently in sloppy mode or throws a TypeError in strict mode. If the speech backend provides no timing information, Chromium returns 0.0 for both attributes rather than throwing or returning NaN/null, and event.timeStamp falls back to base::TimeTicks::Now() whenever WebSpeechTimestamps is disabled, audiostart has not fired, or the event is nomatch. Note also that Chromium’s speech_recognition_result.idl marks SpeechRecognitionResult with [LegacyNoInterfaceObject], so referencing global SpeechRecognitionResult directly throws a ReferenceError in Chrome — always feature-detect on an actual result object inside the result event handler (typeof result.speechStartTime === "number").

Context & exposure. Exposed only on Window in Secure Contexts (https:// or localhost) as part of the Web Speech API (SpeechRecognition / webkitSpeechRecognition); not available in Workers. Requires existing speech-recognition permissions (microphone permission or an explicit MediaStreamTrack passed to recognition.start(track)); no extra permission is needed for timestamps.

Lifecycle & state transitions. (1) Calling recognition.start() (or recognition.start(track)) begins consuming audio frames, establishing the session audio timeline at 0.0 seconds and firing audiostart (where Blink anchors audio_start_ticks_). (2) As the recognizer streams interim hypotheses (isFinal === false), each new SpeechRecognitionResult carries updated speechStartTime and speechEndTime bounds; subsequent events may replace interim results at indices >= event.resultIndex with refined text and updated timestamps. (3) Once a segment finalizes (isFinal === true), its result entry and timestamps remain stable in event.results for the rest of the session. (4) Stopping and starting a new recognition session resets the session audio timeline to 0.0.

Source: Web Speech API §4.1.8 & §4.1.10; Blink speech_recognition_result.idl; Blink speech_recognition.cc.

Generating VTTCue captions, click-to-seek transcripts, and measuring delivery lag

const SpeechRec = window.SpeechRecognition || window.webkitSpeechRecognition;

function startTimedTranscription(videoEl, onLagWarning) {
  if (!SpeechRec) return null;

  const recognition = new SpeechRec();
  recognition.continuous = true;
  recognition.interimResults = true;

  const track = videoEl ? videoEl.addTextTrack("captions", "Transcript", "en") : null;
  if (track) track.mode = "showing";

  const transcriptEntries = [];

  recognition.addEventListener("result", (event) => {
    // Chromium rebases event.timeStamp onto audio_start_ticks_ + latest_audio_end_time
    // (clamped <= now), so performance.now() - event.timeStamp measures delivery lag in ms.
    const deliveryLagMs = Math.max(0, performance.now() - event.timeStamp);
    if (deliveryLagMs > 1500 && typeof onLagWarning === "function") {
      onLagWarning(deliveryLagMs);
    }

    for (let i = event.resultIndex; i < event.results.length; i++) {
      const result = event.results[i];
      if (!result.isFinal) continue;

      const text = result[0]?.transcript?.trim();
      if (!text) continue;

      // Feature-detect on the live result instance (SpeechRecognitionResult has
      // LegacyNoInterfaceObject in Chromium) and guard against 0.0 unavailable timing.
      const hasTiming =
        typeof result.speechStartTime === "number" &&
        typeof result.speechEndTime === "number" &&
        result.speechEndTime > result.speechStartTime;

      if (hasTiming) {
        transcriptEntries.push({
          text,
          startTime: result.speechStartTime,
          endTime: result.speechEndTime,
        });
        if (track && typeof VTTCue === "function") {
          track.addCue(new VTTCue(result.speechStartTime, result.speechEndTime, text));
        }
      } else {
        // Graceful fallback when running on an engine/platform without segment timestamps
        transcriptEntries.push({ text, startTime: null, endTime: null });
      }
    }
  });

  recognition.start();
  return { recognition, transcriptEntries };
}
Source: adapted from Web Speech API Timestamps explainer and Blink speech_recognition.cc.

Security and privacy

  • Fingerprinting via sub-millisecond timing: High-precision engine timestamps could expose CPU speed, thermal throttling, or system load as a cross-origin fingerprinting vector. Following W3C High Resolution Time Level 3 and HTMLMediaElement.currentTime precedent, the Web Speech API spec leaves precision implementation-defined so user agents can coarsen or jitter values.
  • 2 ms quantization in Chromium: Blink’s FuzzTimestamp() in speech_recognition_result.cc floors every raw base::TimeDelta to a multiple of base::Milliseconds(2) before converting to seconds (for example, 1.2357 s is exposed as 1.234), so unquantized engine timestamps never cross the V8 binding layer.
  • No new audio or device capability: Timestamps describe only the audio already captured under existing Web Speech API consent (microphone permission or caller-provided MediaStreamTrack). The specification also prohibits personalizing recognition on a MediaStreamTrack to limit fingerprinting.
  • Clamped event.timeStamp rebasing: CL 8797156 ensures rebased SpeechRecognitionEvent.timeStamp never exceeds base::TimeTicks::Now() and stays gated behind WebSpeechTimestamps.
Source: Web Speech API Timestamps explainer §Security and Privacy; Web Speech API §3 Security and privacy considerations; Blink speech_recognition_result.cc; CL 8797156.
