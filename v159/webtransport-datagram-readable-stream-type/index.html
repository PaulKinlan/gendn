WebTransport Datagram readable stream type

Adds the optional datagramsReadableType member to WebTransportOptions. When omitted, transport.datagrams.readable is now a default ReadableStream that yields each incoming WebTransport datagram as a discrete Uint8Array chunk (preserving 0-byte datagrams and message boundaries). Pass { datagramsReadableType: "bytes" } to opt into a readable byte stream that supports ReadableStreamBYOBReader buffer reuse.

Limited availability — datagramsReadableType is not Baseline (parent WebTransport is Baseline Newly available since 2026-03-24)

  • Chrome · 159 (desktop, Android, WebView)
  • Edge · Mirrors Chromium (159)
  • Firefox · 160 in BCD (default stream shipped earlier; "bytes" via Bugzilla #2007755)
  • Safari · Preview in BCD (WebKit #319830; Safari iOS false)

The parent webtransport web-feature is Baseline Newly available since 2026-03-24 per webstatus.dev, but options.datagramsReadableType is a newer subfeature tracked separately in BCD api/WebTransport.json as options_datagramsReadableType_parameter (currently marked experimental: true, Chrome false [not yet updated for Chrome 159], Firefox 160, Safari Technology Preview, Safari iOS false; checked 2026-11-24).

why it exists

WebTransport datagrams are discrete, unordered messages of zero or more bytes — not a continuous byte stream. Exposing incoming datagrams unconditionally through a readable byte stream caused two semantic mismatches: a BYOB reader cannot return a 0-byte read without confusing stream mechanics (so empty datagrams are skipped when a BYOB request is active), and reading with a min byte count can coalesce multiple distinct datagrams into one buffer, erasing message boundaries. Making a default ReadableStream the default preserves both empty datagrams and per-datagram boundaries, while datagramsReadableType: "bytes" preserves zero-copy BYOB allocation control for latency-sensitive apps (such as game state or sensor telemetry) that opt in explicitly.

Source: ChromeStatus motivation (5148774971342848); W3C WebTransport Editor’s Draft note; WebTransport explainer.

Syntax

The feature adds one optional dictionary member to WebTransportOptions using the WHATWG Streams ReadableStreamType enum, which controls how WebTransportDatagramDuplexStream.readable is set up during construction:

// WebTransport constructor option (verbatim from W3C WebTransport & Blink web_transport_options.idl)
dictionary WebTransportOptions {
  ReadableStreamType datagramsReadableType;
};

// From WHATWG Streams Standard (only defined value is "bytes")
enum ReadableStreamType { "bytes" };

// Stream affected on the constructed WebTransport instance
[Exposed=(Window,Worker), SecureContext]
interface WebTransportDatagramDuplexStream {
  readonly attribute ReadableStream readable;
};

This reference covers three parts of the Chrome 159 contract: the WebTransportOptions.datagramsReadableType constructor option, the resulting datagrams.readable stream mode behavior, and the pullDatagrams BYOB view validation and empty-datagram rules.

Source: W3C WebTransport WebTransportOptions; Blink web_transport_options.idl; WHATWG Streams ReadableStreamType.

WebTransportOptions.datagramsReadableType — inputs and validation

Inputs. Pass datagramsReadableType inside the optional second argument (options) to new WebTransport(url, options). Because the IDL member has no default value, it is either omitted (undefined) or set to "bytes" — the sole member of the ReadableStreamType enum. Passing any other string (including "" or "default") fails Web IDL enum conversion and throws a synchronous TypeError from the WebTransport() constructor before any network request starts.

Outputs. The constructor stores datagramsReadableType in the internal [[ReadableType]] slot of the session’s WebTransportDatagramDuplexStream and uses it once to initialize transport.datagrams.readable. There is no read-only attribute exposing the chosen type directly on WebTransport or WebTransportDatagramDuplexStream; callers distinguish modes by attempting getReader({ mode: "byob" }) or tracking the options they passed.

Source: W3C WebTransport §6.2 Constructor; datagramsReadableType definition; Blink web_transport.cc.

datagrams.readable stream modes — default vs "bytes"

Outputs and behavior. Depending on datagramsReadableType, the WebTransport() constructor initializes transport.datagrams.readable in one of two modes (both using pullDatagrams as the underlying pull algorithm with a high-water mark of 0 in the spec, or Chromium’s count queueing strategy for the default stream):

pullDatagrams BYOB view validation, empty datagrams, and buffer sizing

Inputs & outputs during BYOB reads. When datagramsReadableType is "bytes" and a consumer calls reader.read(view) on a ReadableStreamBYOBReader, the normative pullDatagrams algorithm runs each time a datagram is dequeued:

  1. If the incoming datagram has byte length 0 while a BYOB request view is active, pullDatagrams skips it and recursively pulls the next datagram.
  2. If view.byteLength is smaller than the incoming datagram’s byte length, the stream errors and the pending read() promise rejects with a RangeError (preventing silent truncation or splitting of a datagram).
  3. If view is a DataView or any typed array whose element size is not 1 byte (such as Uint16Array or Float32Array), the stream errors and read() rejects with a TypeError. Only byte-sized typed arrays (Uint8Array, Int8Array, Uint8ClampedArray) satisfy the elementSize === 1 check.
  4. Otherwise, the datagram bytes are copied into the supplied buffer, detaching the original view and resolving read() with { value: filledView, done: false }. Reclaim value.buffer on each iteration to reuse the allocation.

Recommended buffer size. Both the WebTransport spec and RFC 9221 §3 (QUIC Datagram) recommend allocating a 64 KiB (65536-byte) ArrayBuffer for BYOB datagram reads so an unexpectedly large incoming datagram does not error the stream with RangeError.

Source: W3C WebTransport pullDatagrams; RFC 9221 §3; Blink DatagramUnderlyingByteSource.

Cross-version migration note. Because Chrome < 159 ignored datagramsReadableType and always created a byte stream, passing { datagramsReadableType: "bytes" } is backwards-compatible with Chrome 97–158 (which ignore unknown dictionary members) while keeping BYOB reads working in Chrome 159+, Firefox 160+, and WebKit. Conversely, apps that rely on default ReadableStream behavior (including empty datagrams) should check whether getReader({ mode: "byob" }) succeeds if they must distinguish Chrome < 159 from Chrome 159+.

Source: WPT datagrams.https.any.js; W3C WebTransport pullDatagrams; ChromeStatus interop & compat risks.

Context and exposure

WebTransport and WebTransportDatagramDuplexStream are exposed in Window and Worker contexts ([Exposed=(Window,Worker), SecureContext]) and require a secure context (HTTPS origin). datagramsReadableType requires no extra permission or user activation beyond constructing a WebTransport session to an HTTPS URL.

Source: Blink web_transport.idl; W3C WebTransport interface.

Lifecycle and state transitions

The readable stream type is fixed at construction time when new WebTransport(url, options) creates transport.datagrams.readable; it cannot be switched after construction. Reading from datagrams.readable can begin before await transport.ready resolves (incoming datagrams queue in [[IncomingDatagramsQueue]] subject to incomingMaxBufferedDatagrams and incomingMaxAge). Canceling the reader invokes the underlying cancel algorithm; closing or failing the WebTransport session closes or errors datagrams.readable regardless of stream mode. In "bytes" mode, any RangeError (buffer too small) or TypeError (non-byte view) during pullDatagrams permanently errors datagrams.readable for that session without closing the underlying WebTransport connection.

Source: W3C WebTransport §6.2 Constructor; pullDatagrams; WPT datagrams.https.any.js.

Examples

No interactive demo exists yet on the Chrome Platform Showcase for Chrome 159 (HEAD-checked 404 on 2026-11-24). The examples below work directly against any WebTransport HTTP/3 echo endpoint.

Default readable stream — preserving datagram boundaries and empty datagrams

// Omit datagramsReadableType to get a default ReadableStream (Chrome 159+ standard).
const transport = new WebTransport("https://example.com:4433/wt");
await transport.ready;

const reader = transport.datagrams.readable.getReader();
try {
  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    // value is a Uint8Array representing exactly one datagram (including 0-byte datagrams).
    console.log(`Received datagram (${value.byteLength} bytes)`);
  }
} finally {
  reader.releaseLock();
}
Source: WPT datagrams.https.any.js; W3C WebTransport spec.

Opting into BYOB reads with datagramsReadableType: "bytes" and buffer reuse

// Opt into a readable byte stream for zero-allocation BYOB reads.
const transport = new WebTransport("https://example.com:4433/wt", {
  datagramsReadableType: "bytes",
});
await transport.ready;

// Safe fallback if a browser (such as older Firefox) does not support "bytes" yet.
let reader;
try {
  reader = transport.datagrams.readable.getReader({ mode: "byob" });
} catch {
  reader = transport.datagrams.readable.getReader();
}

// Allocate 64 KiB (RFC 9221 §3 recommended max) so pullDatagrams never errors with RangeError.
let buffer = new ArrayBuffer(65536);

try {
  while (true) {
    const isByob = reader instanceof ReadableStreamBYOBReader;
    // Always pass a 1-byte-element TypedArray (Uint8Array); DataView/Uint16Array reject with TypeError.
    const { value, done } = isByob
      ? await reader.read(new Uint8Array(buffer))
      : await reader.read();
    if (done) break;

    processDatagram(value);

    // Reclaim the transferred buffer for the next BYOB read.
    if (isByob) {
      buffer = value.buffer;
    }
  }
} finally {
  reader.releaseLock();
}
Source: WPT datagrams.https.any.js; RFC 9221 §3; MDN WebTransport() constructor.

Security and privacy

datagramsReadableType selects only the JavaScript stream adapter (default ReadableStream versus readable byte stream) used to surface already-received WebTransport datagrams. It grants no new network capabilities, exposes no new transport metadata, introduces no persistent storage or fingerprinting surface, and leaves all WebTransport security invariants intact (secure context required, HTTPS origin, TLS/QUIC encryption, and server certificate validation). Applications using "bytes" mode should still avoid retaining or sharing pooled ArrayBuffer slices across untrusted consumers after datagram buffers are reused.

Source: ChromeStatus security_risks (5148774971342848); W3C WebTransport Privacy and Security Considerations.
