Secure Payment Confirmation: Locale Validation

Updates Secure Payment Confirmation’s locale field so Chrome validates the caller-supplied BCP 47 language tags against the browser’s UI dialog locale and rejects with a NotSupportedError DOMException if none match. When locale is omitted or empty, validation is skipped; when a mismatch occurs, callers can retry with re-localized strings or a broader primary language tag so merchant-supplied text matches the browser dialog.

Limited availability — Chromium-only (Secure Payment Confirmation ships in Chrome and Edge; Firefox and Safari do not implement SPC)

  • Chrome · 154 (desktop, Android — kSPCLocaleValidation enabled by default)
  • Edge · 154 (Chromium-based mirror)
  • Firefox · N/A (does not implement Secure Payment Confirmation)

why it exists

A Secure Payment Confirmation (SPC) dialog mixes browser-owned chrome (such as “Verify your identity” and button labels) with merchant- or issuer-supplied strings (instrument.displayName, payeeName, and entity logo labels). Previously, callers could pass a locale list expecting the browser to translate the dialog, yet Chrome always renders the SPC dialog in the browser’s own UI language and silently ignored locale — risking a confusing mixed-language payment confirmation dialog. Validating locale against the dialog language and rejecting mismatches with NotSupportedError lets payment callers detect a mismatch during canMakePayment() and retry with translated data elements or fall back gracefully.

Source: ChromeStatus 5126146013396992; w3c/secure-payment-confirmation#343; PR #345.

Syntax

WebIDL member on SecurePaymentConfirmationRequest (from W3C Secure Payment Confirmation and Blink’s secure_payment_confirmation_request.idl):

partial dictionary SecurePaymentConfirmationRequest {
  sequence<USVString> locale;
};

Pass locale inside the data object of a PaymentMethodData entry whose supportedMethods is "secure-payment-confirmation" when constructing a new PaymentRequest([methodData], details). This reference covers SecurePaymentConfirmationRequest.locale, the BCP 47 matching algorithm, and NotSupportedError handling.

Source: W3C SPC locale; Blink secure_payment_confirmation_request.idl.

SecurePaymentConfirmationRequest.locale

Inputs. An optional sequence<USVString> of BCP 47 language tags representing the locale(s) of the caller’s supplied display strings (for example ["en-US", "en"] or ["fr-CA", "fr"]).

Outputs & opt-out behavior. If locale is omitted (undefined) or an empty array ([]), locale validation is completely skipped and the SPC request proceeds regardless of the browser’s UI language. If locale contains one or more tags, at least one tag must match the browser’s SPC dialog locale for the request to remain valid.

Source: W3C SPC locale; PR #345; Chromium secure_payment_confirmation_validation.cc.

BCP 47 language tag matching algorithm

Inputs & outputs. Per merged W3C SPC PR #345 and Chromium’s MatchLanguageTags() in secure_payment_confirmation_validation.cc, each tag in locale is tested against the browser’s application locale (delegate_->GetApplicationLocale()). Matching succeeds as soon as any tag satisfies the rules below (note: standard RFC 4647 language negotiation is intentionally not performed, because the browser does not change its dialog language):

SPC locale matching outcomes against browser dialog locale

Omitted or []Any (e.g., "en-US")Pass (skipped)Empty/absent locale skips validation
["en-US"] or ["EN-us"]"en-US"MatchBoth have multiple subtags (region); ASCII case-insensitive exact match
["en-GB"]"en-US"No match (NotSupportedError)Both include region subtags and differ — exact match required
["en"]"en-US"MatchRequest tag has primary language subtag only; primary subtags match

["fr-CA", "en"]"en-GB"MatchAny matching tag in the list succeeds ("en" matches "en-GB")

Spec vs. Chromium detail on malformed tags: W3C SPC PR #345 specifies throwing a TypeError if a tag is not a well-formed BCP 47 language tag. In Chromium’s current MatchLanguageTags(), an unparseable tag returns std::nullopt from LanguageTagConverter::FromString() and is skipped (failing with NotSupportedError if no other tag matches). Canonicalize tags with Intl.getCanonicalLocales() before constructing the request to stay portable across both behaviors.

Source: W3C SPC PR #345; Chromium secure_payment_confirmation_validation.cc; RFC 5646 (BCP 47).

NotSupportedError rejection and retry handling

Error path & inputs/outputs. Because the renderer process does not know the browser’s UI application locale, PaymentRequest::Init() validates locale in the browser process. When kSPCLocaleValidation is enabled and IsValidSecurePaymentConfirmationRequest() returns kLocaleDoesNotMatch, the browser sends client_->OnError(mojom::PaymentErrorReason::NOT_SUPPORTED, error_message) and tears down the browser-side PaymentRequest. On the JavaScript side:

  • new PaymentRequest([{ supportedMethods: "secure-payment-confirmation", data }], details) does not throw synchronously on a locale mismatch.
  • Calling await request.canMakePayment() (recommended preflight check, requires no user activation) or await request.show() rejects with a NotSupportedError DOMException.
  • Notice that canMakePayment() distinguishes a locale mismatch (rejects with NotSupportedError) from “no matching credential available” (resolves to false).
  • Recovery / retry: Catch NotSupportedError, retry with a broader primary language subtag (e.g. ["en"] instead of ["en-GB"]) or alternative localized copy, or omit locale (or fall back to a non-SPC checkout flow) if no language match is possible.
Source: Chromium payment_request.cc; Chromium secure_payment_confirmation_validation.cc; W3C SPC PR #345.

Context and prerequisites

Secure Payment Confirmation runs inside the Payment Request API in Window secure contexts (https:// or localhost). Cross-origin iframes require the payment Permissions Policy (allow="payment"). canMakePayment() requires no user activation (and is the recommended place to detect NotSupportedError before showing UI); show() requires transient user activation. Note that PaymentMethodData.data is JSON-serialized by the Payment Request constructor, so plain data values (no throwing getters) must be passed.

Source: W3C SPC spec; W3C Payment Request API.

Validation timing and request lifecycle

  1. Construction (renderer, synchronous): new PaymentRequest(...) serializes the SPC data payload and sends Mojo PaymentRequest::Init to the browser process.
  2. Browser-side validation (asynchronous): PaymentRequest::Init() runs ValidateSecurePaymentConfirmationRequest() with delegate_->GetApplicationLocale(). If kLocaleDoesNotMatch occurs, the browser invokes client_->OnError(NOT_SUPPORTED, ...) and deletes the browser-side request instance.
  3. Preflight via canMakePayment(): Rejects with NotSupportedError if locale validation failed, or resolves to true / false if locale matched (or was omitted/empty).
  4. Retry with new PaymentRequest: Because a failed PaymentRequest is torn down after OnError, each retry attempt with updated locale and localized display strings must construct a fresh PaymentRequest instance before calling canMakePayment() or show().
Source: Chromium payment_request.cc; W3C SPC PR #345.

Examples

Live demo and canMakePayment() locale-fallback pattern

// Preflight SPC locale validation with canMakePayment() and fall back cleanly
async function createLocalizedSpcRequest({
  rpId,
  credentialId,
  challenge,
  instrumentIcon,
  amount,
  localizedVariants, // e.g. [{ locale: ["fr-CA"], displayName: "Carte ····4242", payeeName: "Boutique" }, ...]
}) {
  const details = {
    total: { label: "Total", amount },
  };

  for (const variant of localizedVariants) {
    // Validate BCP 47 syntax up front for cross-engine portability
    const canonicalLocales = Intl.getCanonicalLocales(variant.locale);

    const request = new PaymentRequest(
      [{
        supportedMethods: "secure-payment-confirmation",
        data: {
          rpId,
          credentialIds: [credentialId],
          challenge,
          instrument: {
            displayName: variant.displayName,
            icon: instrumentIcon,
          },
          payeeName: variant.payeeName,
          locale: canonicalLocales,
          timeout: 60000,
        },
      }],
      details,
    );

    try {
      const canPay = await request.canMakePayment();
      return { request, canPay, matchedVariant: variant };
    } catch (err) {
      if (err && err.name === "NotSupportedError") {
        // Dialog language did not match variant.locale; try next variant (e.g., primary subtag)
        continue;
      }
      throw err;
    }
  }

  return null; // Fall back to non-SPC payment flow or retry without locale
}
Source: W3C SPC PR #345; Chromium payment_request.cc; Upstream SPC locales sample.

Security and privacy

  • Locale fingerprinting oracle: As documented in W3C SPC PR #345 (§ Fingerprinting via locale), returning NotSupportedError from canMakePayment() lets a caller silently probe the browser’s UI dialog locale by issuing successive requests with different locale tags until one does not reject. Rare browser UI locales can contribute to fingerprinting, though the spec notes this locale is often already observable through navigator.language / navigator.languages and Intl APIs.
  • Anti-confusion payment integrity: Rejecting mismatched locales protects users against payment confirmation dialogs whose browser chrome and merchant-supplied strings disagree in language, reducing confusion during high-stakes payment authorization.
Source: W3C SPC PR #345 (§ Fingerprinting via locale); w3c/secure-payment-confirmation#343.
