Private Verification Tokens

An experimental, browser-managed HTTP protocol (Sec-Private-Verification-Token) built on Anonymous Tokens with Hidden Metadata (ATHM) that lets registered top-level sites transfer a 1-bit, unlinkable trust signal established during regular browsing into cookie-free navigations (including Incognito mode) to reduce CAPTCHAs and anti-bot friction without exposing browsing identity or leaking state back out of private mode.

Limited availability — Chrome Origin Trial (M154–M165, desktop & Android); not yet enabled by default and not implemented in Firefox or Safari

  • Chrome · Origin trial M154–M165 (desktop & Android; behind kEnablePrivateVerificationTokens)
  • Edge · No shipping release (disabled by default in Chromium)
  • Firefox · No signal (authors expect negative feedback from W3C AFCG)
  • Safari · No signal

No web-features or BCD entry exists on webstatus.dev or MDN (checked 2026-11-27). Private Verification Tokens (PVT) is a pre-incubation proposal distinct from the shipping Private State Token API: PVT exposes no page-level JavaScript API and transfers a single bit one-way from regular browsing to cookie-free navigations on registered same-site (eTLD+1) origins.

Origin trial — not yet enabled by default: Private Verification Tokens is scheduled for a Chrome Origin Trial from milestone 154 to 165 on desktop and Android (ChromeStatus 6210457816924160; Intent to Experiment). In Chromium’s net/base/features.cc, kEnablePrivateVerificationTokens is FEATURE_DISABLED_BY_DEFAULT and there is no dedicated chrome://flags UI toggle. Enable locally with --enable-features=EnablePrivateVerificationTokens (optionally with PrivateVerificationTokensCustomIssuer or proxy parameters in private_verification_tokens_features.cc). Users can opt out at chrome://settings/content/autoVerify. The protocol, wire sizes, and registration process remain pre-incubation and may change before any shipping decision.

why it exists

As automated traffic and AI agents increasingly clear cookies and rotate fingerprints to mimic first-time visitors, websites have responded with heavier CAPTCHA and interstitial challenges. Users browsing in private/Incognito modes start with cleared state too, so anti-bot heuristics disproportionately challenge legitimate Incognito users. Private Verification Tokens (PVT) lets a registered top-level site issue cryptographically unlinkable, 1-bit (nBuckets = 2) ATHM tokens during regular browsing and redeem a single token on a subsequent cookie-free navigation in Incognito mode — transferring a minimal humanness/trust verdict strictly one way into private browsing without allowing cross-site tracking or exfiltration back to regular browsing.

Source: PVT explainer — Goals & Overview; ChromeStatus 6210457816924160.

Protocol surface & wire formats

Private Verification Tokens exposes no DOM or JavaScript API to web pages. All browser-to-origin interactions occur over HTTP and Chrome’s component-updated issuer configuration. The complete v1 developer/operator surface verified in Chromium’s components/private_verification_tokens/ and chrome/browser/private_verification_tokens/ comprises four parts:

// 1. Redemption HTTP request header (attached by browser on cookie-free top-level navigations):
Sec-Private-Verification-Token: <base64(132-byte marshaled AthmToken)>
//    AthmToken = uint16 token_type (0xC07E) || uint8 issuer_key_id[32] (SHA-256)
//                || uint8 t_enc[32] || uint8 P_enc[33] || uint8 Q_enc[33]

// 2. Issuance HTTP POST endpoint (regular profile; credentials_mode = include):
POST <issuerRequestUrl> HTTP/1.1
Accept: application/private-token-response
Content-Type: application/private-token-request
// Body: batchSize * 36-byte AthmTokenRequest || 4-byte big-endian version (1)
// Response (200 OK, Content-Type: application/private-token-response, max 7168 bytes):
// Body: batchSize * 355-byte TokenResponse (big_u[33] || big_v[33] || ts[32] || proof[257])

// 3. Component-updated issuer configuration JSON (v1 top-level key "1"):
//    issuers[]: { issuerRequestUrl, version: 1, publicKey, publicKeyProof,
//                 batchSize (2..20), expiration (unix sec string),
//                 redeemers (1..2 same-eTLD+1 HTTPS origins), deploymentId }

// 4. Proxy prefetch & Incognito session limits:

Sec-Private-Verification-Token HTTP request header

Inputs & attachment conditions. Defined as net::HttpRequestHeaders::kSecPrivateVerificationToken (http_request_headers.h) and managed by PrivateVerificationTokensURLLoaderThrottle::WillStartRequest(), the browser first strips any pre-existing Sec-Private-Verification-Token header so page script cannot forge it, then attaches a fresh Base64-encoded token when all of the following hold:

  • The request is browser-initiated (!request->request_initiator.has_value()) for an outermost main-frame navigation (request->is_outermost_main_frame).
  • The request URL’s origin matches isolation_info.top_frame_origin() and is listed in a non-expired issuer’s redeemers array.
  • The request carries no Cookie header (!request->headers.HasHeader("Cookie")) and does not omit credentials (credentials_mode != kOmit).
  • Anti-abuse Auto-verify is allowed for both issuer and redeemer, the parent profile’s token store holds an unexpired token for the matching issuer, and (in Incognito) the issuer has not already redeemed a token in this session and fewer than 2 distinct issuers have redeemed so far.

Outputs & server verification. The header value is standard Base64 encoding of a single 132-byte marshaled ATHM token (2-byte token type 0xC07E + 32-byte SHA-256 issuer key ID + 98-byte unblinded ATHM token: t_enc[32], P_enc[33], Q_enc[33] per draft-yun-cfrg-athm-00 §5.4.1 and RFC 9578 §5.3). The origin server Base64-decodes the header, locates its private key by the 32-byte key ID, verifies the ATHM token, extracts the 1-bit hidden metadata bucket (0 or 1), and sets a session cookie if it wants to prevent subsequent cookie-free navigations from burning additional tokens.

Source: private_verification_tokens_url_loader_throttle.cc; privacy_pass_athm_batch_request.h; draft-yun-cfrg-athm-00 §5.4.1.

ATHM batch token issuance HTTP endpoint

Inputs (browser request). Triggered in regular (non-Incognito) browsing by PrivateVerificationTokensService::MaybeFetchTokens() whenever a browser-initiated navigation visits a registered issuer whose cached token count is at or below floor(batchSize / 2). PrivateVerificationTokensFetcher sends an HTTP POST to issuerRequestUrl with credentials_mode = kInclude (sending user cookies so the issuer can compute its trust verdict), Content-Type: application/private-token-request, and Accept: application/private-token-response (RFC 9578 §5.1). The binary request body contains batchSize concatenated 36-byte AthmTokenRequest structs (33-byte blinded request + 3-byte header) followed by a 4-byte big-endian protocol version integer (0x00000001).

Outputs (issuer response). The issuer selects a hidden metadata bucket in {0, 1} (num_buckets = 2), signs each blinded request with its ATHM private key, and returns HTTP 200 OK with Content-Type: application/private-token-response and a binary body of batchSize concatenated 355-byte TokenResponse structs (big_u[33] || big_v[33] || ts[32] || issuance_proof[257]; maximum body size 7168 bytes for max_batch_size = 20). The browser verifies every DLEQ issuance proof via PrivacyPassAthmBatchRequest::Finalize(), unblinds the tokens into 132-byte marshaled tokens, and persists them to disk.

Source: private_verification_tokens_fetcher.cc; private_verification_tokens_parameters.cc; privacy_pass_athm_batch_request.cc.

Registered issuer configuration JSON schema

Inputs & fields. Registered issuers and their ATHM public keys are distributed to Chrome via component updater (or overridden locally via --enable-features=EnablePrivateVerificationTokens with PrivateVerificationTokensCustomIssuer) and parsed by PrivateVerificationTokensIssuerConfig under top-level version key "1" → "issuers" array:

Proxy cache initialization & Incognito session limits

Inputs & feature parameters. To prevent a site from inferring Incognito mode simply by noticing the presence or absence of tokens on a user’s first visit, the PVT explainer and private_verification_tokens_features.cc define optional background prefetching through a browser-operated PVT proxy server controlled by three base::FeatureParam settings on kEnablePrivateVerificationTokens: use_proxy (boolean, default false), proxy_url (default "https://pvtproxy.googleapis.com/v1:proxyRequest"), and proxy_refresh_interval (default 5 hours).

Outputs & session caps. When use_proxy is enabled and an issuer’s local cache is empty, Chrome prefetches cookie-free default-bucket tokens via pvtproxy.googleapis.com and marks them is_proxied = true in storage (tracked separately via UnproxiedTokenCountForIssuer). During any single Incognito (Off-The-Record) session, OtrIssuerTracker enforces two deterministic caps: (1) each issuer receives at most one redeemed token per Incognito session, and (2) at most max_distinct_issuers_per_session = 2 distinct registered issuers may receive a token in that Incognito session.

Source: private_verification_tokens_features.cc; private_verification_tokens_service.cc; PVT explainer — Initializing PVT Cache.

Errors, rejection paths, and fail-open recovery

  • Forged or redirected Sec-Private-Verification-Token headers: WillStartRequest() unconditionally removes any caller-supplied Sec-Private-Verification-Token header before evaluating redemption, and WillRedirectRequest() adds Sec-Private-Verification-Token to removed_headers so a redeemed token is never forwarded across HTTP redirects.
  • Issuance network & proof failures (application/private-token-request / application/private-token-response): PrivateVerificationTokensFetcher enforces a 1 minute timeout, retries up to 2 times on network change / DNS resolution failures, and caps responses at 7168 bytes. Non-OK network errors (kNetNotOk), empty responses (kNullResponse), wrong body lengths (kInvalidResponseBodyLength), or invalid ATHM DLEQ proofs (kClientFinalizeFailed) abort storage silently without interrupting page navigation.
  • Malformed issuer configuration: Any issuer entry missing or failing validation for issuerRequestUrl, version != 1, Base64 publicKey/publicKeyProof, batchSize outside [2, 20], non-future expiration, redeemers exceeding 2 origins or mismatching eTLD+1, or missing deploymentId is silently dropped during ParseEntry().
  • Proxy & session-cap exhaustion: If use_proxy prefetch against pvtproxy.googleapis.com fails, or an Incognito session has already reached max_distinct_issuers_per_session (2) or already redeemed for that issuer, Chrome simply omits the header and proceeds with the normal navigation (fail-open; origins must fall back to their normal challenge/verification path).
Source: private_verification_tokens_url_loader_throttle.cc; private_verification_tokens_fetcher.cc; private_verification_tokens_issuer_config.cc; private_verification_tokens_service.cc.

Context, eligibility, and current Chromium constraints

PVT operates only on https: origins (with localhost exempted for development) on browser-initiated outermost main-frame navigations. Subframes, subresources, script-initiated fetch() / XMLHttpRequest calls, and requests with credentials: "omit" never trigger issuance or redemption. Two Chromium browser-level policies also gate eligibility in PrivateVerificationTokensService::IsIssuerAllowed():

  • Auto-verify content setting: Blocked whenever the user disables ContentSettingsType::ANTI_ABUSE (chrome://settings/content/autoVerify) for the issuer or redeemer origin.
  • Origin-trial scope in Chromium main: In the current Chromium implementation checked on 2026-11-27, IsIssuerAllowed() checks both IsAntiAbuseEnabled(issuer) and IsSearchEngineSameOrigin(issuer) (matching the profile’s default search provider origin in TemplateURLService), reflecting the initial scoped Origin Trial rollout; general registration beyond the initial trial is marked TBD in the explainer’s Registration Process section.
Source: private_verification_tokens_service.cc; PVT explainer — Registration Process.

Lifecycle, persistence, and single-use consumption

  1. Configuration load: Chrome loads registered issuer configs (including ATHM public keys, proofs, batchSize, expiration, and redeemers) via component updater and opens the profile’s SQLite database (PrivateVerificationTokens).
  2. Issuance (regular profile only): On a browser-initiated navigation to a registered issuer in a regular profile, if unexpired stored tokens are ≤ batchSize / 2 and no fetch is already in flight for that issuer, Chrome generates a blinded ATHM batch request, POSTs it with cookies, verifies the DLEQ proofs, and stores the unblinded tokens on disk.
  3. Redemption (regular cookie-free or Incognito): On a cookie-free, browser-initiated top-level navigation to a registered redeemer, Chrome attaches one token from the parent profile’s store in Sec-Private-Verification-Token.
  4. Deferred deletion & cookie race safety: Chrome does not delete the token before sending the request. Only in WillRedirectRequest() or WillProcessResponse() — and only if the network stack did not strip the header because cookies were attached later (!response_head.pvt_token_removed_due_to_cookies) — does Chrome record the issuer in OtrIssuerTracker and delete the spent token from SQLite.
  5. Clearing site data: Clearing browsing/site data calls DeleteTokensByFilter() with matching first-party StorageKeys to wipe stored PVTs.
Source: private_verification_tokens_url_loader_throttle.cc; private_verification_tokens_service.cc; private_verification_tokens_store.h.

Examples

Motivation demo & server-side Sec-Private-Verification-Token inspection

// Server-side handler (Node / Fetch-style Request) parsing Sec-Private-Verification-Token.
// Expected v1 marshaled AthmToken layout (132 bytes):
//   [0..1]   uint16 big-endian token_type (0xC07E)
//   [2..33]  32-byte SHA-256 issuer key ID
//   [34..131] 98-byte ATHM Token (t_enc[32] || P_enc[33] || Q_enc[33])
function parsePvtHeader(request) {
  const header = request.headers.get("Sec-Private-Verification-Token");
  if (!header) return { present: false };

  const bytes = Uint8Array.from(atob(header), (c) => c.charCodeAt(0));
  if (bytes.length !== 132) {
    return { present: true, valid: false, reason: "unexpected-length" };
  }
  const tokenType = (bytes[0] << 8) | bytes[1];
  if (tokenType !== 0xc07e) {
    return { present: true, valid: false, reason: "unexpected-token-type" };
  }
  return {
    present: true,
    valid: true,
    tokenType,
    issuerKeyId: bytes.slice(2, 34),
    athmToken: bytes.slice(34, 132),
  };
}

Security and privacy

PVT is designed specifically around strict privacy boundaries across regular and Incognito browsing:

  • 1-bit unlinkable entropy: ATHM tokens carry only 1 bit of hidden metadata (nBuckets = 2), and tokens with the same metadata are cryptographically unlinkable to their issuance context.
  • Strictly one-way, same-site transfer: Tokens flow only from regular browsing into cookie-free navigations on registered origins sharing the same eTLD+1, never from Incognito back into regular browsing and never in third-party/subframe contexts.
  • Anti-collusion & anti-Incognito-detection guards: Each Incognito session caps redemptions to 1 token per issuer and at most 2 distinct registered issuers total (preventing multi-domain bit exfiltration). Attaching PVTs on any cookie-free navigation (plus optional proxy cache prefetching of default-bucket tokens) mitigates sites detecting private mode from token presence alone.
  • User control & transparency: Users can disable PVT via chrome://settings/content/autoVerify and clear stored tokens via standard site-data deletion; registered issuers must appear in a publicly inspectable list and commit to trust/rate-limiting/IVT-only use.
Source: PVT explainer — Privacy Considerations; private_verification_tokens_service.cc; draft-yun-cfrg-athm-00 §5.1.
