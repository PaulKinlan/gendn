Fetch API: Forward reason from AbortController to fetch Response

Interoperability catch-up — spec-required behavior

  • Chrome · abort(reason) since 98; forwarded to the Response in 154
  • Edge · expected to mirror Chrome
  • Firefox · already ships the forwarding (ChromeStatus view: Shipped/Shipping)
  • Safari · position request closed without a position

There is no dedicated web-feature entry on webstatus.dev for this forwarding behavior (checked 2026-09-27; the umbrella aborting web-feature — AbortController/AbortSignal — is Baseline widely available). BCD records the underlying abort() reason parameter (Chrome 98, Firefox 97, Safari 15.4) but has no subfeature yet for the reason reaching the Response; see the full table.

When you abort a fetch() with controller.abort(reason), the custom reason is supposed to surface everywhere the failure does. Before Chrome 154, Chromium only rejected the fetch() promise itself with your reason — reads on the Response body (response.text(), the body ReadableStream) failed with a generic AbortError instead. Chrome 154 forwards the developer-supplied reason to the Response’s methods and its stream, closing a compliance gap with the Fetch standard.

syntax

No new API surface is added — the change is where an existing value shows up. The Fetch Standard’s abort algorithm (quoted from “abort a fetch() call”) requires the abort reason to be applied to all three failure channels:

To abort a fetch() call with a promise, request, responseObject, and an error:

1. Reject promise with error.
     (This is a no-op if promise has already fulfilled.)
2. If request's body is non-null and is readable,
     then cancel request's body with error.
3. If responseObject is null, then return.
4. Let response be responseObject's response.
5. If response's body is non-null and is readable,
     then error response's body with error.

The error passed in is the AbortSignal’s abort reason: the fetch-method steps abort with “requestObject’s signal’s abort reason”, and when the abort crosses realms the spec uses “the result of deserialize a serialized abort reason given controller’s serialized abort reason and relevantRealm” (a reason that cannot be serialized reaches the other side as a generic "AbortError" DOMException, per the DOM Standard’s signal-abort machinery).

Concretely, in Chrome 154+ your abort(reason) value now appears in the rejections of:

examples

Distinguish a deliberate timeout from a user cancellation while streaming a body — the catch around the read loop now sees your reason, not just the catch around fetch():

class TimeoutCancel extends Error {
  constructor() { super("timed out"); this.name = "TimeoutCancel"; }
}

const controller = new AbortController();
setTimeout(() => controller.abort(new TimeoutCancel()), 5000);

try {
  const response = await fetch("/big-download", { signal: controller.signal });
  const reader = response.body.getReader();
  for (;;) {
    const { done, value } = await reader.read();  // ← rejects with the reason in Chrome 154+
    if (done) break;
    consume(value);
  }
} catch (err) {
  if (err instanceof TimeoutCancel) {
    // Pre-154 Chromium: err here was a generic AbortError DOMException,
    // so this branch was unreachable once the headers had arrived.
    showTimeoutUI();
  } else {
    throw err;
  }
}

Because this is a compliance fix on a years-old API, feature-detecting it is impractical — there is no new member to probe. Write error handling that checks your custom reason and falls back on err.name === "AbortError", which stays correct in older Chromium, in engines that haven’t caught up, and whenever a cross-realm reason couldn’t be serialized.
