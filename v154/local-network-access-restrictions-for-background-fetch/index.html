Local Network Access restrictions for Background Fetch

Requires Background Fetch requests targeting local or loopback network endpoints to hold the service worker origin’s Local Network Access (LNA) permission. Closes a security bypass where Background Fetch skipped LNA checks applied to regular Fetch requests, bringing Chromium into alignment with the Background Fetch and Local Network Access specifications.

Limited availability — Chromium-only API enforcement (Background Fetch itself ships only in Chromium; Firefox ships LNA without Background Fetch; Safari ships neither)

  • Chrome · 154 (desktop, Android — kBackgroundFetchLocalNetworkAccess enabled by default)
  • Edge · 154 (Chromium-based mirror)
  • Firefox · N/A (ships LNA, does not support Background Fetch)
  • Safari · no signal (does not support Background Fetch)

Both local-network-access (Chrome/Edge 145+) and background-fetch (Chrome 74+, Edge 79+) are Limited availability on webstatus.dev (checked 2026-11-27). BCD api/BackgroundFetchManager.json and MDN’s BackgroundFetchManager.fetch() page do not yet document Local Network Access restrictions or LNA permission prerequisites, so gendn provides the full implementation reference here.

why it exists

The Background Fetch specification routes every queued request through the Fetch standard, which enforces Local Network Access (LNA) checks when a public origin contacts a local or loopback IP address. Previously, Chromium’s Background Fetch download pipeline created network requests without attaching the service worker’s ClientSecurityState or LNA network service observer, allowing sites to bypass LNA restrictions by scheduling downloads through registration.backgroundFetch.fetch() instead of fetch(). Chrome 154 closes this gap so Background Fetch obeys the exact same LNA permission and enterprise policy rules as regular service worker fetches.

Source: ChromeStatus 6225598451154944; Background Fetch spec; Local Network Access spec.

Syntax and affected API surface

This change introduces no new WebIDL methods or options; it changes the runtime security gate applied to existing BackgroundFetchManager.fetch() calls, checked via existing Permissions API descriptors and governed by existing LNA enterprise policies:

// 1. Existing Background Fetch call (now subject to LNA checks per request)
const bgFetch = await serviceWorkerRegistration.backgroundFetch.fetch(
  id,          // DOMString
  requests,    // RequestInfo | sequence<RequestInfo>
  options      // optional BackgroundFetchOptions
);

// 2. Existing Permissions API queries to check LNA grants beforehand
const localPerm = await navigator.permissions.query({ name: "local-network" });
const loopbackPerm = await navigator.permissions.query({ name: "loopback-network" });

// 3. Observable failure state on BackgroundFetchRegistration when LNA blocks a request
// bgFetch.result === "failure"
// bgFetch.failureReason === "fetch-error"

This reference documents all three parts of the Chrome 154 contract: LNA enforcement on Background Fetch requests, "local-network" / "loopback-network" permission prerequisites, and enterprise policy controls.

Source: Blink background_fetch_manager.idl; Blink background_fetch_registration.idl; Blink permission_descriptor.idl.

BackgroundFetchManager.fetch() Local Network Access enforcement

Inputs & mechanism. Every request URL supplied to registration.backgroundFetch.fetch(id, requests, options) (including redirects) is now dispatched through a dedicated URLLoaderFactory created in BackgroundFetchJobController::InitializeUrlLoaderFactory() when features::kBackgroundFetchLocalNetworkAccess is enabled. Chromium populates factory_params->client_security_state from registration->active_version()->BuildClientSecurityState() and attaches a URLLoaderNetworkServiceObserver created via CreateURLLoaderNetworkObserverForServiceOrSharedWorker() for the service worker’s origin.

Outputs & target classification. Requests from a public origin to a public endpoint proceed unchanged. Requests from a less-private origin (such as a public https:// site) to a local address (RFC 1918 private ranges, link-local) or loopback address (127.0.0.0/8, ::1) trigger the Network Service’s Local Network Access check against the service worker origin’s granted permissions and enterprise policies. If permitted, downloads continue normally; if denied, the request fails.

Source: Chromium background_fetch_job_controller.cc; Chromium content_features.cc; Local Network Access spec.

"local-network" and "loopback-network" permission prerequisites

Inputs & permission names. Per Local Network Access and Blink’s permission_descriptor.idl, local-network requests require the "local-network" permission and loopback requests require the "loopback-network" permission (with "local-network-access" as the combined umbrella descriptor where applicable).

Outputs & why pre-granting is mandatory. A Background Fetch executes under the origin’s service worker and can outlive the page that started it; a service worker has no visible document UI to display an interactive permission prompt. Therefore, if the service worker’s origin does not already hold a "granted" permission state (established earlier from a foreground secure-context page or via enterprise policy), the LNA check fails without prompting. Applications targeting local servers should inspect navigator.permissions.query({ name: "local-network" }) (or "loopback-network") in the page first and trigger an interactive foreground request/prompt while the user is present before calling backgroundFetch.fetch().

Source: Local Network Access spec; Blink permission_descriptor.idl; ChromeStatus 6225598451154944.

Errors and observable failure states

  • Blocked Background Fetch request (failureReason: "fetch-error"): Because DNS resolution and LNA verification happen asynchronously when the Background Fetch download runs, backgroundFetch.fetch() itself may resolve with a BackgroundFetchRegistration even when the target URL will be blocked. When LNA rejects the request, the background fetch aborts with registration.result === "failure" and registration.failureReason === "fetch-error" (defined in background_fetch_registration.idl), firing the backgroundfetchfail event in the service worker.
  • No separate LNA failure reason enum value: Background Fetch does not distinguish LNA denial from CORS, Mixed Content, or network errors in failureReason; all report "fetch-error" to avoid leaking local network topology.
  • Service worker unavailable: If the active service worker registration disappears before InitializeUrlLoaderFactory() can build its ClientSecurityState, background_fetch_job_controller.cc aborts the job with SERVICE_WORKER_UNAVAILABLE.
  • Permissions query fallback (TypeError): Calling navigator.permissions.query({ name: "local-network" }) on browsers that do not recognize that permission descriptor rejects with a TypeError; always wrap the query in try/catch.
Source: Chromium background_fetch_job_controller.cc; Blink background_fetch_registration.idl; Background Fetch spec.

Context, exposure, and prerequisites

BackgroundFetchManager is exposed in Window and Worker contexts on a ServiceWorkerRegistration (requiring a secure context and an active service worker). Starting a background fetch requires user activation or the background-fetch permission; additionally, reaching a local or loopback destination now requires the service worker’s origin to hold the matching LNA permission ("local-network" or "loopback-network") and not be restricted by Permissions Policy.

Source: Blink background_fetch_manager.idl; Local Network Access spec; ChromeStatus 6225598451154944.

Lifecycle and background execution ordering

  1. Foreground check & permission grant: Before registering a local-network Background Fetch, the foreground page queries navigator.permissions.query({ name: "local-network" }) (or "loopback-network") and, if state === "prompt", issues a small foreground fetch() to trigger the user permission prompt.
  2. Registration & factory setup: When registration.backgroundFetch.fetch() starts processing requests, BackgroundFetchJobController::DidGetRegistrationForRequest() verifies the active service worker and calls InitializeUrlLoaderFactory() to bind the service worker’s ClientSecurityState and network observer to each BackgroundFetchRequestInfo.
  3. Download & LNA check: BackgroundFetchDelegateProxy::StartRequest() passes the configured URLLoaderFactory to the download manager, which runs LNA checks on the resolved target IP (and any redirect hops).
  4. Completion or failure event: If all requests pass LNA and complete with OK responses, the service worker receives backgroundfetchsuccess. If any request is blocked by LNA, the job fails with failureReason === "fetch-error" and dispatches backgroundfetchfail.
Source: Chromium background_fetch_job_controller.cc; Chromium background_fetch_delegate_proxy.cc.

Examples

Live demo, permission pre-check, and service worker failure handling

// Foreground page: verify LNA permission before scheduling a local Background Fetch
async function startLocalFirmwareDownload(firmwareUrl, sizeBytes) {
  if (!("BackgroundFetchManager" in self)) {
    throw new Error("Background Fetch is not supported in this browser.");
  }

  // 1. Check whether the origin already has "local-network" permission
  let permissionState = "unknown";
  try {
    const status = await navigator.permissions.query({ name: "local-network" });
    permissionState = status.state;
  } catch {
    // Older browsers may not recognize the "local-network" permission descriptor
  }

  if (permissionState === "denied") {
    throw new Error("Local network access is denied; Background Fetch will fail with fetch-error.");
  }

  // 2. If "prompt", trigger a lightweight foreground request so the user can grant LNA
  if (permissionState === "prompt") {
    await fetch(firmwareUrl, { method: "HEAD", targetAddressSpace: "local" });
  }

  // 3. Schedule the Background Fetch; the service worker inherits the origin's LNA grant
  const swReg = await navigator.serviceWorker.ready;
  return swReg.backgroundFetch.fetch("firmware-update", [firmwareUrl], {
    title: "Downloading local device firmware",
    downloadTotal: sizeBytes,
  });
}

// Service worker: handle LNA-blocked or network-failed background fetches
function handleBackgroundFetchFail(event) {
  const { id, result, failureReason } = event.registration;
  if (result === "failure" && failureReason === "fetch-error") {
    console.warn(`Background fetch "${id}" failed (LNA permission, CORS, or network error).`);
  }
}

Security and privacy

This feature is a direct security hardening fix closing an LNA policy bypass (crbug.com/455486148). Without it, a malicious public page could register a service worker and queue Background Fetch requests to private routers, printers, or loopback services that persist after the tab closes without ever prompting the user for Local Network Access permission. Binding the service worker’s ClientSecurityState and network observer to Background Fetch downloads ensures LNA checks, Permissions Policy restrictions, and enterprise opt-ins/overrides apply uniformly across Fetch and Background Fetch, while keeping blocked failures opaque as generic "fetch-error" outcomes.

Source: ChromeStatus 6225598451154944; crbug.com/455486148; Local Network Access spec.
