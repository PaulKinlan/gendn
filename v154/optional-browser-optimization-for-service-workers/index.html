Optional browser optimization for Service Workers

Specifies and ships ServiceWorkerAutoPreload, an optional browser loading optimization that dispatches a GET navigation network request in parallel with cold Service Worker startup. When the fetch event handler calls fetch(event.request) — or falls back without calling event.respondWith() — Chrome reuses the already-in-flight network response instead of paying Service Worker bootstrap latency twice. Chrome 154 is the stepped-rollout milestone removing the temporary ServiceWorkerAutoPreloadEnabled enterprise policy introduced in Chrome 140.

Limited availability — Chromium-only optimization (initial rollout Chrome 140, enterprise policy removed in Chrome 154); Firefox Positive, Safari supportive on spec PR

  • Chrome · 140+ (kServiceWorkerAutoPreload enabled by default; policy removed in 154)
  • Edge · Mirrors Chromium (140+)
  • Firefox · Not yet implemented (Positive position)
  • Safari · Not yet implemented (WebKit reviewer approved spec PR)

No dedicated web-features entry exists on webstatus.dev or MDN for ServiceWorkerAutoPreload (checked 2026-11-27), because it is an optional user-agent optimization in W3C Service Workers Handle Fetch with no new JavaScript API surface. Base service-workers is Baseline Widely available, and service-workers-static-routes (used for opting out via InstallEvent.addRoutes()) is Limited availability (Chrome/Edge 123+).

why it exists

Service Workers intercept roughly 15% of Chrome page loads, but starting a stopped Service Worker on a cold navigation can add tens to hundreds of milliseconds before the fetch handler even executes. Many Service Workers act as pass-through handlers (calling event.respondWith(fetch(event.request))) or fall back to the network without calling respondWith() — meaning the browser sits idle waiting for worker startup before issuing the navigation HTTP request. Although the Navigation Preload API solves the same latency problem, adoption remained low because it requires explicit worker code changes (registration.navigationPreload.enable() and reading event.preloadResponse). ServiceWorkerAutoPreload applies parallel navigation preloading automatically with zero script changes while still letting the fetch handler control the final response.

Source: WICG ServiceWorkerAutoPreload explainer; ChromeStatus 5194817700364288.

Syntax & developer-facing surface

ServiceWorkerAutoPreload adds no new JavaScript interfaces or WebIDL members. Its developer- and admin-facing surface consists of three concrete contracts: (1) the optional responseForAutoPreload branch in W3C Service Workers Handle Fetch (consumed transparently by fetch(event.request) or fetch-handler fallback), (2) the declarative opt-out using InstallEvent.addRoutes() with source: "fetch-event", and (3) the temporary ServiceWorkerAutoPreloadEnabled Chrome enterprise policy removed in Chrome 154:

// 1. Handle Fetch optional optimization (W3C Service Workers PR #1756):
//    If navigation GET && active worker has non-empty fetch handler
//       && !navigationPreloadEnabled
//       && timingInfo.workerMatchedRouterSource !== "fetch-event":
//         browser MAY speculatively fetch(request) into responseForAutoPreload
//         in parallel with Service Worker startup; consumed by fetch(event.request)
//         or by browser fallback when event.respondWith() is not called.

// 2. Developer opt-out via Service Worker Static Routing API (InstallEvent.addRoutes):
installEvent.addRoutes({
  condition: { urlPattern: new URLPattern({}) }, // or narrower RouterCondition
  source: "fetch-event",
});

// 3. Enterprise policy (Chrome M140-M153; removed in Chrome 154):
//    Policy name: ServiceWorkerAutoPreloadEnabled
//    Schema: boolean (default: true; dynamic_refresh: true; per_profile: true)

Jump directly to each contract below: ServiceWorkerAutoPreload auto-preload dispatch, InstallEvent.addRoutes() "fetch-event" opt-out, and ServiceWorkerAutoPreloadEnabled policy migration.

Source: w3c/ServiceWorker#1756; W3C Service Workers Handle Fetch; ServiceWorkerAutoPreloadEnabled.yaml.

ServiceWorkerAutoPreload parallel navigation dispatch

Inputs & triggering conditions. In W3C Service Workers Handle Fetch and Chromium’s ServiceWorkerMainResourceLoader::MaybeStartAutoPreload(), ServiceWorkerAutoPreload operates on a navigation Request when all of the following hold: the request URL uses http: or https:, the HTTP method is GET, the request targets an outermost main frame (not a subframe or subresource), the controlling active Service Worker has at least one non-empty fetch listener, the Service Worker is not currently running (running_status() != kRunning), NavigationPreload is disabled, and no static routing rule matched with source: "fetch-event" (or another terminating source).

Outputs & consumption rules. When dispatched, the browser starts a speculative network request (responseForAutoPreload) in parallel with Service Worker bootstrap and attaches no special identification header (unlike Service-Worker-Navigation-Preload), so the request hits the regular HTTP cache and matches a normal navigation request identically:

  • Consumed inside the fetch handler: When the handler calls fetch(event.request) with the unmodified navigation Request, the call resolves directly from responseForAutoPreload without issuing a second network request. Other fetch() calls (such as fetch("/analytics"), fetch(event.request.clone()), or fetch(new Request(event.request, { ... }))) dispatch normal network requests and do not consume responseForAutoPreload.
  • Consumed on fallback: If the fetch handler returns without calling event.respondWith(), the browser commits responseForAutoPreload directly as the fallback navigation response instead of starting a fresh network fetch after handler completion.
  • Discarded when unused: If the fetch handler answers from CacheStorage or constructs a synthetic new Response(...) without calling fetch(event.request), the browser discards (and may cancel) responseForAutoPreload. Commit responsibility remains FetchResponseFrom::kServiceWorker — the browser never bypasses the fetch handler’s chosen response.
Source: w3c/ServiceWorker#1756; WICG explainer; Chromium service_worker_main_resource_loader.cc.

Developer opt-out via InstallEvent.addRoutes() ("fetch-event")

Inputs. During the Service Worker install event, call event.addRoutes(rules) with a RouterRule (or array of rules) whose condition matches the navigation URLs that must not be speculatively preloaded (for example, { urlPattern: new URLPattern({}) } for all requests, or a specific path pattern) and whose source is "fetch-event".

Outputs & observable effect. Per w3c/ServiceWorker#1756, matching a rule with source: "fetch-event" sets timingInfo’s worker matched router source to "fetch-event". In Chromium’s service_worker_main_resource_loader.cc, ServiceWorkerRouterSourceType::kFetchEvent sets race_network_request_mode = RaceNetworkRequestMode::kSkipped, which guarantees MaybeStartAutoPreload() is skipped while still executing the fetch handler normally (and still honoring explicit NavigationPreload if the site enabled it). Note that event.addRoutes() returns a Promise<undefined>; pass it to event.waitUntil() so the router rules are persisted before installation finishes.

Source: w3c/ServiceWorker#1756; WICG explainer — Opt-out; Chromium service_worker_main_resource_loader.cc.

ServiceWorkerAutoPreloadEnabled enterprise policy & Chrome 154 removal

Inputs & schema. ServiceWorkerAutoPreloadEnabled (defined in ServiceWorkerAutoPreloadEnabled.yaml) is a per-profile, dynamically refreshable boolean policy (default: true) introduced in Chrome 140 across desktop, ChromeOS, Android, and Fuchsia. Setting it to false sets prefs::kServiceWorkerAutoPreloadEnabled = false, causing ChromeContentBrowserClient::IsServiceWorkerAutoPreloadAllowed() to return false so navigation requests always wait for Service Worker startup.

Outputs & Chrome 154 migration. Per ChromeStatus 5194817700364288 (stepped rollout stage for milestone 154) and the policy definition’s own deprecation notice (“This policy is a temporary measure to control the feature and will be removed in M154”), enterprise administrators can no longer rely on ServiceWorkerAutoPreloadEnabled starting in Chrome 154. Internal applications that still require suppressing speculative network preloads must migrate to the web-standard InstallEvent.addRoutes({ ..., source: "fetch-event" }) opt-out inside their Service Worker script.

Source: ServiceWorkerAutoPreloadEnabled.yaml; Chrome Enterprise Policy ServiceWorkerAutoPreloadEnabled; ChromeStatus API record (5194817700364288).

Errors, redirects, and edge cases

  • Redirects in ServiceWorkerAutoPreload: When the auto-preloaded network request receives an HTTP 3xx redirect, the browser hands redirect processing back to the fetch handler so the handler’s configured redirect mode (including opaque-redirect filtered responses) is respected identically to a non-preloaded fetch(event.request).
  • Aborted or terminated navigations: Per w3c/ServiceWorker#1756, if the parent fetch controller transitions to "terminated" or "aborted", the browser aborts autoPreloadFetchController and sets responseForAutoPreload’s value to null.
  • Network errors & offline mode: If the speculative preload fails due to a network error while the device is offline, fetch(event.request) rejects with the same TypeError it would have produced without ServiceWorkerAutoPreload, and a cache-first handler that never calls fetch(event.request) still serves its cached response normally.
  • Invalid addRoutes() opt-out rules: Calling event.addRoutes() outside the install event handler throws an InvalidStateError DOMException, and malformed condition / source: "fetch-event" descriptors reject the returned promise with a TypeError. Guard calls with if (event.addRoutes) for browsers that do not implement the Static Routing API.
  • Removed ServiceWorkerAutoPreloadEnabled policy: Once removed in Chrome 154, setting ServiceWorkerAutoPreloadEnabled: false in managed policies is ignored as an unknown/deprecated policy and will not suppress auto-preloading.
Source: w3c/ServiceWorker#1756; WICG explainer — Redirect; MDN InstallEvent.addRoutes(); ServiceWorkerAutoPreloadEnabled.yaml.

Context, eligibility, and extension interactions

ServiceWorkerAutoPreload runs only in secure contexts with an active Service Worker registration (https: or http://localhost) and applies exclusively to outermost main-frame GET navigations. Verified directly in ServiceWorkerMainResourceLoader::MaybeStartAutoPreload(), Chromium suppresses auto-preload in the following contexts:

Lifecycle, routing precedence, and timing

On an outermost main-frame GET navigation controlled by a stopped Service Worker, Chromium evaluates loading strategies in strict order inside ServiceWorkerMainResourceLoader:

  1. Static Router evaluation: Registered InstallEvent.addRoutes() rules run first. A matched "network" or "cache" rule bypasses the fetch handler entirely; "race-network-and-fetch-handler" forces a full race (kForced); "fetch-event" sets kSkipped to disable auto-preload.
  2. NavigationPreload vs. ServiceWorkerAutoPreload: If race_network_request_mode is kDefault, Chromium checks MaybeStartNavigationPreload() first. Only when Navigation Preload is not enabled does Chromium call MaybeStartAutoPreload().
  3. Parallel execution & single-use handoff: The browser starts the navigation network fetch and kicks off Service Worker startup concurrently. Inside the fetch handler, the first matching fetch(event.request) takes ownership of the preloaded response stream; if the handler never calls respondWith(), the browser commits the preloaded stream directly on fallback. If the handler responds from another source, the preloaded request is canceled.
Source: Chromium service_worker_main_resource_loader.cc; W3C Service Workers Handle Fetch.

Examples

Live timeline demo & Service Worker fetch handler benefiting from ServiceWorkerAutoPreload

// sw.js — Benefits automatically from ServiceWorkerAutoPreload with zero API changes.
self.addEventListener("fetch", (event) => {
  if (event.request.mode !== "navigate") return;

  // Non-matching side-effect fetches still dispatch normally:
  // fetch("/telemetry/nav-start");

  // Passing the unmodified event.request consumes responseForAutoPreload
  // instead of waiting for SW startup and issuing a second network request.
  event.respondWith(
    fetch(event.request).catch(() => caches.match("/offline.html")),
  );
});
Source: WICG ServiceWorkerAutoPreload explainer — How it works.

Opting out with InstallEvent.addRoutes() and source: "fetch-event"

// sw.js — Opt out of ServiceWorkerAutoPreload when your cache-first handler
// must avoid speculative network requests reaching your origin server.
self.addEventListener("install", (event) => {
  if (typeof event.addRoutes === "function") {
    event.waitUntil(
      event.addRoutes([
        {
          condition: {
            urlPattern: new URLPattern({ pathname: "/app/*" }),
          },
          source: "fetch-event",
        },
      ]),
    );
  }
});

Security and privacy

ServiceWorkerAutoPreload issues only standard GET navigation requests to the same URL the user is already navigating to, respecting existing HTTP cache partitioning, credentials, TLS, and navigation restrictions (such as Connection Allowlists on NavigationRequest). Because no distinguishing request header is attached, servers cannot use auto-preload to fingerprint browser startup timing beyond standard navigation traffic, and unlike BestEffortServiceWorker, the browser never bypasses the Service Worker’s fetch handler security or response-filtering logic. The primary operational tradeoff is that a cache-first Service Worker whose fetch handler never calls fetch(event.request) can trigger an extra speculative GET request to the origin server while the worker boots; origins that rely on side-effecting GET navigations or want zero speculative traffic should register a static routing rule with source: "fetch-event".

Source: WICG explainer — Tradeoffs & NavigationPreload FAQ; Chromium service_worker_main_resource_loader.cc.
