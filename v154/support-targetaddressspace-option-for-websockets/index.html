Support targetAddressSpace option for WebSockets

Adds the targetAddressSpace member to the WebSocketInit options dictionary, allowing secure-context pages to declare that a ws:// WebSocket connection to a hostname targets a "local" or "loopback" destination. Matching fetch()’s existing targetAddressSpace option, this provides a permission-gated carve-out from Mixed Content blocking for local network devices that cannot easily obtain public TLS certificates.

Limited availability — Chromium-only Local Network Access extension riding on the WebSocketInit options bag; Firefox and Safari have no signal

  • Chrome · targeted at 154 (desktop, Android; trunk flag LocalNetworkAccessWebSocketsTargetAddressSpace)
  • Edge · Chromium-based (mirrors Chrome)
  • Firefox · no signal
  • Safari · no signal

The parent local-network-access web-feature is Limited availability on webstatus.dev (Chrome/Edge 145+; checked 2026-11-27), while base websockets is Baseline Widely available. BCD api/WebSocket.json has no key for WebSocketInit or targetAddressSpace, and MDN’s WebSocket() reference covers only the classic protocol-string and array constructor forms.

To test locally when not enabled by default, launch Chromium with --enable-blink-features=WebSocketOptionBag,LocalNetworkAccessWebSocketsTargetAddressSpace or enable chrome://flags/#enable-experimental-web-platform-features.

why it exists

Local Network Access (LNA) requires a secure context (https://) to prompt for permission to reach devices on a user’s local network, yet Mixed Content rules normally block ws:// connections from https:// pages. Local hardware — printers, IoT bridges, 3D printers, and local developer tools — rarely holds publicly trusted TLS certificates for wss://. Previously, developers had to force users to type literal private IP addresses to qualify for mixed-content exemptions (see WICG/local-network-access#16). Bringing targetAddressSpace to the WebSocket options bag mirrors fetch(url, { targetAddressSpace }) so secure web apps can connect to local hostnames such as ws://local-server.example under explicit user permission.

Source: ChromeStatus 4779920606756864; WICG/local-network-access#126; issue #16 comment.

Syntax

WebIDL extension to WebSocketInit and the shared IPAddressSpace enum (combining WICG/local-network-access PR #125, Blink’s websocket_init.idl, and request.idl):

enum IPAddressSpace {
  "loopback",
  "local",
  "private",
  "public",
  "unknown"
};

partial dictionary WebSocketInit {
  [RuntimeEnabled=LocalNetworkAccessWebSocketsTargetAddressSpace]
  IPAddressSpace targetAddressSpace;
};

Pass targetAddressSpace inside the second argument (protocolsOrOptions) of new WebSocket(url, options), optionally alongside protocols (see Add options bag to WebSocket constructor). This reference documents WebSocketInit.targetAddressSpace, the IPAddressSpace enum values, and Mixed Content carve-out and LNA enforcement.

Source: WICG/local-network-access PR #125; Blink websocket_init.idl; Blink request.idl.

WebSocketInit.targetAddressSpace

Inputs. An optional IPAddressSpace string member on the WebSocketInit dictionary passed as the second parameter of new WebSocket(url, protocolsOrOptions). When omitted, Blink initializes the connection’s internal target address space to IPAddressSpace::kUnknown (no declared target address space, so standard Mixed Content rules apply).

Outputs. The parsed targetAddressSpace value is forwarded from DOMWebSocket::Create() into WebSocketChannelImpl::Connect() and over Mojo to the Network Service’s WebSocket connector. There is no ws.targetAddressSpace getter on the resulting WebSocket instance; the option affects only connection eligibility and LNA verification.

Source: WICG/local-network-access PR #125; Blink dom_websocket.cc; Blink websocket_channel_impl.cc.

IPAddressSpace values for WebSockets

Inputs & outputs per enum value. Blink reuses the IPAddressSpace enum from request.idl, but ParseOptionBag() in dom_websocket.cc explicitly rejects the legacy "private" alias and "unknown":

Mixed-content carve-out and Local Network Access enforcement

Inputs & algorithm. When WebSocketChannelImpl::Connect() runs on a secure origin (https://) with a ws:// URL, Blink calls ShouldBlockWebSocketByMixedContentCheck(url, target_address_space). Setting targetAddressSpace to "local" or "loopback" bypasses the Mixed Content block (matching LNA § Integration with Mixed Content) and hands target_address_space to the Network Service’s WebSocket handshake.

Outputs & verification. Passing targetAddressSpace is a declaration, not an unconditional bypass: the Network Service still runs the Local Network Access check after DNS resolution. Both conditions must hold for the handshake to succeed: (1) the user (or enterprise policy) has granted the corresponding LNA permission for the calling origin, and (2) the resolved remote IP actually falls in the declared address space ("local" or "loopback"). If a hostname resolves to a public IP despite targetAddressSpace: "local", or if the user denies the permission prompt, the WebSocket handshake is blocked.

Source: Blink websocket_channel_impl.cc; Local Network Access § Integration with Mixed Content; ChromeStatus 4779920606756864.

Errors and failure modes

  • Synchronous TypeError on invalid IPAddressSpace: Passing "private", "unknown", or any non-enum string for targetAddressSpace throws a TypeError synchronously during new WebSocket(...).
  • Synchronous SyntaxError when options bag is unsupported: On browsers without WebSocketOptionBag support, passing an options object as the second argument coerces it to "[object Object]" as a subprotocol name and synchronously throws a SyntaxError DOMException.
  • Synchronous SecurityError on unexempted Mixed Content: Opening ws:// from https:// without a valid "local" or "loopback" targetAddressSpace (or when the feature flag is off) triggers Mixed Content blocking and throws a SecurityError DOMException.
  • Asynchronous connection failure (error + close events): If the user denies the LNA permission prompt, the origin is blocked by Permissions Policy, or the resolved IP does not match the declared targetAddressSpace, the constructor returns a WebSocket in CONNECTING state and the connection fails asynchronously by firing error followed by close (typically abnormal closure code 1006).
Source: Blink dom_websocket.cc; Blink websocket_channel_impl.cc; WebSockets Living Standard.

Context, permissions, and prerequisites

WebSocket is exposed in both Window and Worker contexts ([Exposed=(Window,Worker)]). However, Local Network Access permission grants require a secure context (https:// or localhost) and appropriate Permissions Policy delegation for cross-origin iframes (local-network / loopback-network / local-network-access). In a Window, a first-time local WebSocket request can trigger the browser’s LNA permission prompt; in a dedicated/shared/service worker without an active prompt UI, the origin should already hold the grant before opening the socket. Note also that Chrome logs a deprecation warning console message when opening a non-secure ws:// socket from a secure origin even when allowed by the LNA carve-out.

Source: Local Network Access spec; Blink websocket_channel_impl.cc; ChromeStatus 4779920606756864.

Connection lifecycle and ordering

  1. Option bag parsing (synchronous): DOMWebSocket::Create() reads protocols and targetAddressSpace from WebSocketInit, validating enum values and throwing TypeError on "private", "unknown", or unknown strings.
  2. Mixed-content gate (synchronous): WebSocketChannelImpl::Connect() checks ShouldBlockWebSocketByMixedContentCheck(url, target_address_space); "local" and "loopback" pass the gate.
  3. Handshake & DNS / LNA check (asynchronous): The Network Service resolves the hostname, compares the resolved IP’s address space against target_address_space, verifies or prompts for the required LNA permission, and either completes the WebSocket upgrade (firing open) or aborts the connection (firing error then close).
  4. Cleanup & BFCache: As with any active WebSocket, Blink registers a scheduling handle disabling Back/Forward Cache while the connection is open (unless disconnected on BFCache). Calling socket.close() tears down the channel normally.
Source: Blink dom_websocket.cc; Blink websocket_channel_impl.cc; WICG/local-network-access PR #125.

Examples

Live demo, feature probe, and local WebSocket connection

// 1. Feature-detect whether WebSocket reads targetAddressSpace from WebSocketInit
function supportsWebSocketTargetAddressSpace() {
  let read = false;
  const options = {
    get targetAddressSpace() {
      read = true;
      return "local";
    },
  };
  try {
    const ws = new WebSocket("wss://example.invalid/", options);
    ws.close();
  } catch {
    // Throws SyntaxError on browsers without WebSocketInit support
  }
  return read;
}

// 2. Connect from an https:// page to a local device over ws:// using a hostname
function connectLocalPrinter(hostname, subprotocols = ["escpos"]) {
  const url = `ws://${hostname}:9100/stream`;
  if (!supportsWebSocketTargetAddressSpace()) {
    throw new Error("Browser does not support WebSocketInit.targetAddressSpace.");
  }

  // Use "local" for LAN devices or "loopback" for 127.0.0.1 / ::1.
  // Never pass "private" or "unknown" — Blink throws a TypeError.
  const socket = new WebSocket(url, {
    protocols: subprotocols,
    targetAddressSpace: "local",
  });

  socket.addEventListener("open", () => {
    console.log("Connected with subprotocol:", socket.protocol);
  });
  socket.addEventListener("error", () => {
    // Fires if LNA permission was denied or DNS resolved to a non-local IP
    console.error("Local WebSocket connection blocked or unreachable.");
  });
  return socket;
}

Security and privacy

  • No Mixed Content bypass to public hosts: Setting targetAddressSpace: "local" or "loopback" permits an unencrypted ws:// handshake from an https:// page only if DNS resolves to an IP actually in that address space. Attempting to spoof targetAddressSpace: "local" for a public hostname fails the Network Service’s address-space check rather than downgrading transport security on the public internet.
  • User permission gate: Every cross-address-space WebSocket connection from a public origin to a local or loopback server requires an explicit Local Network Access permission grant ("local-network" or "loopback-network"), mitigating drive-by CSRF and port scanning against LAN routers and local services.
  • DNS rebinding & error opacity: If a connection is rejected due to a missing permission or an address-space mismatch, the WebSocket API exposes only a generic asynchronous error / close failure without revealing the resolved IP address to page script.
Source: Local Network Access spec; WICG/local-network-access PR #125; ChromeStatus 4779920606756864.
